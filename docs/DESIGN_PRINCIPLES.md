## 1. 運用前提

**この章が全ての根拠である。** ここが変わったら、第3章の設定値を全て見直す。

> **水域によって前提が違う。** 1.1〜1.2 は桜川本流の前提であり、
> **霞ヶ浦では成立しない**(1.2b)。設定値を water body から独立に決めてはいけない。
> 2026-08-06 の実機テストは全区間が霞ヶ浦側で行われた。
> 逆走判定は**正しく働いていた**（実際に逆走していた）が、レーンの被覆が
> 足りず、岸も片側しか定義されていない。前提の違いは「誤作動」ではなく
> **被覆の穴**として現れる。

### 1.1 水域（桜川本流）

| 項目 | 値 |
| --- | --- |
| 場所 | 茨城県土浦市 桜川 |
| 川幅 | 概ね 40〜50m、狭所 35m |
| カーブ | 蛇行区間あり。カーブ間隔は最短 200m、最長 700m |
| 岸の危険区域 | 岸の基準線から水面側へ約5m |
| 実効航路幅 | 通常 30〜40m、狭所 25m(川幅から両岸の危険区域を引いた値) |

### 1.2 航行ルール（桜川本流）

- **右側通行。** 航路を中心線で二分し、各艇は自分から見て右側を進む。
- **片側1レーン。** 対向艇とは常にすれ違う。追い越しは同一レーン内で起きる。
- 片側レーン幅は実効航路幅の半分 = 通常 15〜20m、**狭所 12.5m**。
- すれ違い時の艇の中心間距離は、両者がレーン中央を保っていれば
  通常 15〜20m、狭所 12.5m。

### 1.2b 霞ヶ浦（開水面）——**1.1〜1.2 の前提が成立しない水域**

桜川河口から霞ヶ浦側へ出た水域。ラクスマリーナの桟橋から発着する。

| 項目 | 値 |
| --- | --- |
| 水域の形 | **開水面。** 対岸は数百m先 |
| 岸 | **北岸しか定義していない。南側は未定義**(2026-08-06 時点) |
| レーンの意味 | **「推奨経路」であって「越えない取り決め」ではない** |
| 休憩場所 | 桟橋、待機水域、岸沿い |

実測(2026-08-06、5端末):

- 航跡から `shore_south` までは**最短でも 520m**。両岸が 60m 以内に揃う点は **0%**。
- 航跡の **17〜44%** がどちらのレーンにも入っていない(4x は 44%)。
  レーンを片側 50m 広げても、A 28.8% / B 19.1% / C 22.0% が外に残る。
  10% 未満にするには両レーンが重なるまで広げるしかなく、そこまで広げると
  「逆走」に意味が無くなる。

**したがって:**

1. **レーンの被覆が足りない。** 逆走判定が発火しない区間が広い。
   ただしこれは**警告漏れ**であって誤発報ではない。
   レーンから外れていれば判定は動かないので、誤って鳴ることはない。

   > **一度これを根拠に「開水面では逆走判定を出さない」としたが、撤回した。**
   > 利用者の確認により、実機ログで鳴った逆走警告は**すべて正しかった**
   > （実際に逆走していた）。同じ艇に載せた2台が同期して発火していた観測とも整合する。
   > **正しく働いている警告を、被覆率の統計を理由に止めてはいけない。**
   > うるささは頻度で解く（`guidanceBurstCount`）。
   > 開水面で**誤発報**が実測されたときだけ、除外を検討する。

   > **2026-10-27・28 の実機ログで、誤った逆走注意が実測された(事実の訂正)。**
   > 原因は2つあった(`docs/実装計画_2026-10-30_速度方位の検証と監視バイブ.md`)。
   > (a) iOSが方位を出せない状態(方位精度±180°)に入ると方位が止まり、正しい向きで
   > 漕いでいても逆走と表示された。これは自艇の速度・方位の検証で是正した
   > (`GnssMotionValidity`。再生で逆走の表示は 527→82 / 1353→548 / 1573→486 測位)。
   > (b) 西端の折り返し直後と、地図上の中心線から13m以内での逆走注意(音19回)。
   > 実際の往路・復路の分かれ目は地図上の中心線より15〜22m南にあった。
   > 方位が正常な区間では、正しい向きでの逆走表示は3人とも6秒以下だった。
   > (b)を地図の修正で解くか、判定に余裕を持たせるかは、現地確認とチームの
   > 通行規則の判断の後に利用者と決める(判定は止めていない)。

2. **岸警告は北岸だけが対象**であることを承知して使う。
   南側へ寄っても警告は出ない。これは警告漏れだが、
   **データが無いことを「安全」と読み替えない**(原則6)。
   南岸を定義するまでは、この水域の岸警告を「両岸を見ている」と説明してはいけない。
3. 片側1レーン幅(12.5m)を根拠にした設定値は、この水域では検算の前提にならない。

### 1.2c 水域をまたぐ設定値の扱い

| 設定値 | 依存する前提 | 開水面での扱い |
| --- | --- | --- |
| レーン由来の逆走判定 | 1.2 片側1レーン | **有効のまま。**被覆は落ちるが誤発報はしない |
| 岸の水面側オフセット | 1.1 岸の危険区域 | 定義済みの岸にだけ効く |
| 他艇の帯(狭所12.5mの検算) | 1.2 すれ違い間隔 | 検算の前提が変わる。再検算が要る |
| 中心線予測 | 航路が一本道であること | レーン外では直線予測へ縮退する(既存の挙動) |

**新しい水域を足すときは、まずこの節へ前提を書いてから設定値を決める。**
逆順にすると、2026-08-06 と同じことが起きる。

### 1.3 練習形態

| 項目 | 値 |
| --- | --- |
| 同時に川に出る艇数 | 2〜12艇 |
| コーチ艇 | **いない** |
| 休憩場所 | 橋の下、または航路の端 |
| 艇種 | 1x / 2- / 2x / 2+ / 4- / 4x / 4+ / 8+(混在する)。寸法は漕手の人数で決まり、2-/2+ は 2x、4-/4+ は 4x と同じ |
| 巡航速度 | 概ね 3〜5 m/s |
| 漕手による端末操作 | **できない**(両手がオールで塞がり、端末は艇に固定されている) |
| 監視者による端末操作 | **できる**(陸上で端末を手に持っている) |

### 1.4 前提から直ちに従うこと

- **橋の下と岸際に停まるのは正常な運用である。** 異常ではない。
- **岸から数mを走るのは正常な運用である。** 実効航路幅25mの狭所で
  8+(全長19.9m・全幅7.5m)がすれ違うとき、岸への余裕は片側数mしかない。
- **対向艇と十数mですれ違うのは正常な運用である。** これを危険として扱うと、
  すれ違うたびに警告が出て、確実に形骸化する。
- **監視者は陸上にいる。** コーチ艇からの監視を前提にした機能を、
  安全経路の必須要素にしてはならない。
- **画面の常時点灯は「航行中だけ」必要である。**
  漕手は航行中に端末を触れないので、画面が消えたら復帰させる手段がない。
  したがって航行中は常時点灯させ、タップを前提にした操作を安全経路へ置いてはならない。
  一方**監視者は陸上で端末を操作できる**ので、監視中に常時点灯させる理由はない。
  電池を無駄に使うだけであり、**監視中は常時点灯しない**。
- **カーブは 200m ごとに来る。** 5m/s で 10秒先 = 50m 先を予測するなら、
  予測は必ずカーブをまたぐ。直線予測は前提と噛み合わない。

## 2. 設計原則

### 原則1: 機能を止めない

能力が欠けているときに、航行開始をブロックしたり警告経路を無効化したりしない。
**「縮退運転 + 明示的な警告」で継続する**(`SafetyRunMode.runningDegraded` /
`unavailable` と system fault 警告)。

音声・危険区域データ・通信・GPS のいずれが欠けても航行は開始できる。
位置情報権限だけは例外(原理的に全機能が成立しない)。

**なぜ:** 使えない状況で止まるアプリは、使える状況でも起動されなくなる。
機能が半分でも動いていれば、半分の価値は出る。

### 原則2: 使い方は使い手が決める

どういうシチュエーションで使うかはユーザーの自由である。
アプリは「正しい使い方」を強制しない。

- 一人で漕ぐときも、12艇で漕ぐときも使える。
- 警告を切って地図と記録だけ使うのも正当な使い方である。
- 危険区域データが未整備の水域で使うのも正当な使い方である。

**なぜ:** 想定外の使い方こそが実運用である。制約を増やすほど、
実際の練習で起きることに対応できなくなる。

> **原則1との関係(2026-10-27 利用者確認):** 原則1の「警告経路を無効化しない」は、
> **アプリが条件しだいで勝手に止めること**を禁じるもので、利用者が自分で警告を切ることは禁じない。
> 警告を切って使うのは正当である。アプリ内の警告音量は下限30%(`warningAudioAppVolumeMin`)のままにするが、
> それは警告を止めさせないためではなく、聞き分けの調整で聞こえない音量まで下げてしまわないため。
> 消したい人は端末の音量で消せる。

### 原則3: その時々で出せる最大限の価値を出す

「全部揃っていないから何も出さない」ではなく、
**「今揃っているもので出せるものを出し、欠けているものを明示する」**。

- 他艇が受信できなければ、固定危険区域の警告は出す。
- 中心線が作れなければ、直線予測へ縮退して警告は出し続ける。
- GPS が劣化していれば、不確実性を広げたまま警告・記録・共有を続ける。

### 原則4: 過剰警告は安全機能の破壊である

警告漏れ(false negative)を避けることを優先する。
ただし、**形骸化した警告は警告漏れと同じである**。鳴りっぱなしの音は
必ず無視され、無視される警告は存在しないのと変わらない。

第1章の「正常な運用」で鳴る警告は、安全側に倒した設計ではなく**不具合**として扱う。

### 原則5: 「どれだけまずいか」と「どれだけ切迫しているか」を混ぜない

- **内部レベル lv0〜3** = どれだけまずいか(停止距離内か・確度)。
  表示色・優先順位・ログにだけ使う。
- **鳴り始め** = どれだけ切迫しているか(到達までの時間)と、当たり判定の確度で決める。
  鳴り方は1種類(読み上げの繰り返し)で、段階で鳴り方を変えない(3.3.1)。

詳細は [CLAUDE.md](../CLAUDE.md) の「提示ポリシー」。

### 原則5.1: 警告の主表示は対象・状態だけにする

警告チップの主表示は、利用者が次に目視すべき対象または確認すべき状態を、短い語だけで
示す。物理的な危険区域・他艇では「岸」「橋」「橋脚」「中洲」「流木」「杭」「工事船」
のように**対象名だけ**を表示し、「〜に接近」「注意」「危険」などの自明な語尾は足さない。
警告は接近・進入・異常を検知したから表示されているので、主表示で同じ事実を繰り返しても
判断材料は増えず、横幅と一瞥で読める時間だけを消費する。

GPSや位置共有などのsystem faultは、対象名にできないため「GPSが途絶」「位置共有が停止」の
ように、利用者が確認すべき能力低下を短く示す。残り時間、件数、必要な補足は2行目・詳細・
アクセシビリティへ置けるが、主表示を冗長にしない。音声の語句、内部のリスクレベル、警告
発生条件は主表示の文言から推測させず、それぞれ独立して扱う。

### 原則6: データ欠損は安全の根拠にならない

受信途絶・GPS 断を「脅威が消えた」証拠に使わない。
情報が無いことは、危険が無いことを意味しない。

### 原則7: 設定値には前提を書く

`lib/config/` の各値には、**第1章のどの前提から導かれたか**をコメントで残す。
根拠のない数値は、次に触る人が動かせない。

## 3. 前提から導かれる設定値

各値が第1章のどの前提に対応するかを示す。前提が変わったらこの表を辿って見直す。

> **この章は根拠の記録である。いまの値はコード(`lib/config/`)が正。**
> 値を変えたらこの表も同じ変更で直す(2026-10-27 に全行をコードと照合し、一致を確認した)。

### 3.1 岸・固定危険区域

| 設定値 | 現在値 | 根拠となる前提 |
| --- | --- | --- |
| `shoreProximityCautionDistanceMeters` | 3.0m | 1.4「岸から数mを走るのは正常」。岸を大きく取ると常時鳴る |
| `bridgeProximityCautionDistanceMeters` | 6.0m | 橋脚衝突の帰結が大きい。ただし毎回くぐる(近接注意の音は鳴らさない対象なので、距離を広げても音は増えない) |
| `bridgePierProximityCautionDistanceMeters` | 6.0m | 水中に立つ実体への衝突は最悪。局所的なので流木と同じ距離でも形骸化しない |
| `driftwoodProximityCautionDistanceMeters` | 6.0m | 水面下で見えず帰結が最悪。桜川で実際に発生する |
| `audibleProximityCategories` | `{driftwood, island, pile, bridgePier}` | 1.4「岸際走行は正常」。岸を鳴らすと形骸化する。杭・橋脚は水中に立つ局所的な実体 |
| `bandCappedCategories` | `{}`(空) | 橋脚を別の区域として描けるようになったため、橋も橋脚も当たる予測なら同じく鳴らす。橋の下で休むことは低速静音(下の行)が受け持つ |
| `lowSpeedAudioMuteSpeedMetersPerSecond` | 1.667m/s（分速100m） | 1.3「休憩は橋の下・航路の端」。3秒続いたら、橋脚・橋・岸・逆走だけ音を止め、表示・記録は続ける |
| `defaultStaticSweepClearanceMeters` | 1.5m | 排他領域の横幅と全艇種で一致(= 従来動作) |
| `shoreStaticSweepClearanceMeters` | 0.0m | 1.4 + 1.2 狭所レーン中央11.25m。下記の実測を参照 |

**岸の掃引クリアランス(2026-07-26 実機テストで是正):**

静的区域の掃引に排他領域(1x で横幅9m)を使っていたため、
GPS帯1.5mと合わせて**岸の基準線から11mで発報**していた。
1.2 の狭所ではレーン中央を守っても艇中心は岸から11.25m しかなく、
**規定どおり漕いでも鳴る境界に正常運用が乗っていた**(3.5-2 の懸念が実測で確定)。
実機ログでは連続音488サンプルのうち368サンプル(75%)が
艇中心が岸区域の外側にいる状態だった。

排他領域は「他船に空けてほしい水面」を表す概念であり、
**並走することが正常な岸**へ当てるのが誤りだった。
静的区域の掃引は「船体領域の横幅 + kind別クリアランス」に変え、
岸だけ 0m(= 船体+オールの実寸)とした。
前後方向(`h`)と `s` は排他領域のままなので、
**岸へ向かって進む艇の検知時刻は変わらない**。

| GPS accuracy | 変更前 | 変更後(岸) | 狭所レーン中央11.25mに対する余裕 |
| --- | --- | --- | --- |
| 5m | 10.10m | 8.60m | 0.25m → **2.65m** |
| 15m | 11.00m | 9.50m | 0.25m → **1.75m** |

### 3.2 他艇・すれ違い

| 設定値 | 現在値 | 根拠となる前提 |
| --- | --- | --- |
| `nearMissSeparationMeters` | 2.0m | 1.2 狭所レーン幅 12.5m。**下記3.5の要検討項目** |
| `nearbyBoatRadius` | 300m | 1.3 2〜12艇。桜川の見通し距離 |
| `boatStaleTimeoutSeconds` | 30秒 | 停止中送信10秒の3倍。幽霊艇と通信ジッタの分離 |
| `boatPredictionTimeoutSeconds` | 6秒 | 5m/s で 30m の外挿が限界 |

**すれ違いの余裕の計算(狭所・8+同士の最悪ケース):**

- 8+ の排他領域 全幅 `w` = 10.5m(片側 5.25m)
- 2艇の排他領域が接触しない最小中心間距離 = 10.5m
- 狭所でレーン中央を保った実際の中心間距離 = 12.5m
- **余裕 = 2.0m**

つまり、狭所で 8+ 同士が規定どおりすれ違うと、領域間の隙間はちょうど 2m である。

**艇種別の停止距離と領域寸法の証拠境界:** `boat_config.dart` の停止係数と
船体・排他領域寸法は既存運用から継承した値で、元の実測記録・文献出典は
リポジトリに残っていない。実測済みと推測せず、次の停止時間相当を
回帰契約として維持する。来歴、代表速度での計算、更新条件は
[艇種別安全定数の根拠台帳](design_notes/2026-08-20_艇種別安全定数の根拠台帳.md)に記録する。

| 艇種 | 停止時間相当 | 証拠の状態 |
| --- | ---: | --- |
| 1x | 6.95秒 | 継承値。実測・文献は未記録 |
| 2x | 6.60秒 | 継承値。実測・文献は未記録 |
| 4x | 6.68秒 | 継承値。実測・文献は未記録 |
| 8+ | 8.15秒 | 継承値。実測・文献は未記録 |

2-/2+ は 2x、4-/4+ は 4x の停止係数と領域寸法をそのまま使う(2026-10-20 追加)。
前提は「漕手の人数が同じなら艇の大きさは変わらない」(利用者の判断)であり、
艇種別の値を新しく作ったのではない。最大の艇は引き続き 8+ なので、
3.2 のすれ違い余裕の計算は変わらない。2+/4+ の cox はバウ側に乗るので、

**逆走注意(2026-07-26 実機テストで是正):**
従来は「区域内に現在地があるか」だけで判定しており、進行方向を見ていなかった。
実機ログでは77分で16回この区域へ出入りしており、正常に漕いでいるだけで
16回鳴ることになる。航路中心線と右側通行から規定方位を求め、
方位差が120度以上のときだけ発報する。中心線が作れないときは、方向を確かめられない
まま従来どおり区域内で発報する(原則1: 縮退運転。理由コード `reverse_direction_unverified`)。

### 3.3.1 警告音は1種類(2026-10-23 利用者決定)

以前は到達10秒以内を連続音、10〜13秒を3秒間隔の断続音にしていた。これを廃止し、
衝突警告の鳴り方を「読み上げの繰り返し」1種類にした。確度の違いは鳴り方ではなく
**鳴り始めの早さ**で表す(確実なら13秒前、確度が低ければ10秒前)。

理由:

- 1.3・1.4 のとおり漕手は両手がオールで塞がっており、聞き分けているのは
  「鳴っている/鳴っていない」だけである。段階が変わっても、することは
  「振り返って確認する」で同じ。行動の変わらない区別を覚えさせるのは負担になる。
- 断続音の帯は3秒しかなく、3秒間隔では実質1回しか鳴らなかった。
- 他分野で段階を分けているのは、段階ごとに行動が変わり、間隔も十数秒以上ある場合
  (航空の TCAS・EGPWS)である。駐車センサーのように切迫度を音で伝える例もあるが、
  桜川の読み上げ音声(0.5〜1.4秒)では間隔を詰める余地が小さい。
- 一方、確度の低い警報が長く鳴ると警報全体が無視される(cry-wolf、原則4)。
  そのため確度の低い候補は鳴らし方ではなく鳴り始めを10秒へ遅らせる。
  10秒は8+の停止時間8.15秒を上回るので、止まりきれる時点では必ず鳴る。

実機ログ15本(約13.2時間)を新旧で再生した結果(`tool/replay_field_log.dart`):

| | 変更前 | 変更後 |
| --- | ---: | ---: |
| 繰り返し音が鳴っていた秒数 | 942 | 1,264 |
| うち岸 | 595 | 861 |
| うち確度の低い候補 | 0(断続音だった) | 115 |
| 音の候補が立っていた秒数(鳴り方を問わない) | 1,547 | 1,547 |

音の候補が立っていた秒数はログ15本のすべてで新旧一致した。音が新しく立つ場面も
消えた場面もなく、増えたのは「断続音だった時間が繰り返し音になった」ぶんだけである
(1時間あたり約24秒、うち確度の低い候補が約9秒)。
再生には他艇が入っていない(`track.csv` に他艇が無い)ため、他艇の警告の増え方は
この表に含まれない。他艇は到達10〜13秒の1回の読み上げが繰り返しに変わる。
確度の低い候補の繰り返しが現場で形骸化するようなら、まず
`primaryWarningLeadSeconds` を短くする(下限8.5秒)。断続音へは戻さない。

**鳴り始めの秒数の検証(2026-10-23):** 複数艇の練習を数式で作り、アプリの判定部品へ
通して 9〜20秒を比べた([シミュレーションの記録](design_notes/2026-10-23_警告の鳴り始め_シミュレーション.md))。
13秒のままでよい。秒数を1秒延ばすと余裕は約1秒、鳴っている時間は約4%増える。
秒数より、音声1本を岸・橋の読み上げが使って他艇の読み上げが入れないこと(桜川上流の
危ない場面の2〜6%)と、狭い川でのすれ違い・追い越しの鳴りすぎの方が影響が大きい。
前者は同日、岸・橋(桁)への重なりを音声の順位だけ下げて直した
(`AlertCandidateComparator.compareForAudio`。岸・橋は通過・並走が正常な区域なので
近づいてくる相手に譲る。橋脚など硬い物への重なりは最優先のまま)。
シミュレーションの書き出しで再現した見積もりでは、桜川上流の取りこぼしは0%になり、
岸・橋の警告の1.5%で音声が一度も流れず、3.8%で遅れる(中央値7秒)。
その間は「他艇に注意」が鳴っており、無音にはならない。

### 3.4 休憩・停止

| 設定値 | 現在値 | 根拠となる前提 |
| --- | --- | --- |
| `stableStopSpeedMetersPerSecond` | 0.4 m/s | 1.3「休憩は橋の下・航路の端」 |
| `stableStopConfirmationDuration` | 5秒 | 同上。停止中の固定障害物の反復音を抑える |
| `shipDomainMaxLowSpeedLateralInflationMeters` | 4.0m | 岸際の休憩・折り返しの回頭で過剰警告にしない上限 |
| `sendIntervalStoppedSec` | 10秒 | 休憩が長いことを前提にした通信量削減 |
| `staticOverlapClosingRateMetersPerSecond` | 0.3 m/s | 岸との並走・桟橋への係留は「まずい」が「切迫していない」(原則5) |
| `staticOverlapImminentGrace` | 5秒 | 縮まらないまま重なり続けたら表示のみへ落とす |
| `closingRateWindow` | 3秒 | 接近速度を求める観測窓 |

**重なりの切迫度(2026-07-26 実機テストで是正):**
`currentOverlap` を無条件に連続音(imminent)へ昇格させていたため、
岸と並走している間・桟橋に着けている間は連続音が鳴り続けた。
`currentOverlap` は原則5の「どれだけまずいか」であって
「どれだけ切迫しているか」ではない。距離が縮まっていなければ1段下げ、
猶予後は表示のみにする。**距離が取れないときは接近中として扱う**(原則6)。
他艇は相手が接近してくるため対象外。

### 3.4.1 陸上判定(音のゲート)

| 設定値 | 現在値 | 根拠となる前提 |
| --- | --- | --- |
| `ashoreLandSideMarginMeters` | 12.0m | 1.1 川幅40〜50m + 1.4「岸から数mを走る」。水上で成立するには20m級の誤差が要る |
| `ashoreAccuracyMarginFactor` | 2.0 | 誤差が大きいときほど陸上と決めつけない |
| `ashoreConfirmationDuration` | 30秒 | 単発の異常測位で確定させない |
| `ashoreBaselineRelevanceRadiusMeters` | 200m | 霞ヶ浦の沖では基準線の半平面を延長した判定が信頼できない |

艇庫での準備・艇の運搬中は岸の危険区域の内側にいるため連続音が鳴っていた。
**止めるのは音だけ**で、検知・表示・記録・位置共有は継続する(原則1)。
陸上確定は遅く(30秒)、水上復帰は水面側の測位1点で即座、という非対称にしてある。
GPS品質が good でないとき・accuracy が取れないときは判定しない。
画面に常時表示し、「音を戻す」で手動解除できる(原則2)。

### 3.4.2 system fault の提示

| 設定値 | 現在値 | 根拠となる前提 |
| --- | --- | --- |
| `dynamicReceiveFaultConfirmSec` / `ClearSec` | 15秒 | 3.4 停止中送信10秒 + 通信ジッタでは発報しない。15秒 < 鮮度上限30秒 |
| `safetyEvaluationStallSeconds` | 3秒 | GPS入力途絶と評価停止を分離し、評価停止を常設表示する |
| `persistentSystemFault` | 全カテゴリ表示のみ | 漕ぎながら対処できない能力情報で物理警告の音声を覆わない |
| `systemFaultWarningAudioAsset` | 航行中は未使用 | 監視機能用の資産は残すが、自艇航行のsystem faultへは割り当てない |

system faultは消さない。候補・バナー・能力バッジ・`runMode` に残し、
データ欠損を「安全」と誤認させない(原則1・6)。音声だけを全カテゴリから外し、
物理的な衝突警告を聞き取れる単一チャンネルとして保つ。

### 3.5 前提と噛み合っていない疑いがある値(要検討)

第1章を明文化した結果、次の値は運用前提と衝突している可能性がある。
**変更は単体テスト(特に実データ統合テスト)の更新とセットで行う。**

1. **`nearMissSeparationMeters` = 2.0m**
   3.2 の計算どおり、狭所で 8+ 同士が**規定どおり**すれ違うと隙間はちょうど 2.0m。
   境界上に正常運用が乗っており、狭所のすれ違いごとに lv1 が立ちうる。
   lv1 は表示のみで音は鳴らないため実害は小さいが、「注意表示が常時出ている」
   状態は原則4に反する。艇種の組み合わせ別に見直すか、
   狭所では中心線からの逸脱量で判定する方が前提と整合する。

2. ~~**岸の危険区域の扱い全般**~~ → **2026-07-26 の実機テストで確定・是正済み。**
   懸念どおり、右側通行の通常操舵で掃引警告が立っていた(3.1 の表を参照)。
   静的掃引のクリアランスを kind 別にして是正した。
   回帰は `test/services/static_sweep_clearance_test.dart` が実データで固定している。

3. **コーチ機能(`use_coach_watch`)の位置づけ**
   1.3 のとおりコーチ艇はいない。陸上からの監視、または不使用が前提である。
   安全経路がこの機能に依存していないことを維持する。
   2026-07-26 の実機テストを受けて、**監視モードの音は既定で無効**にした
   (`coachAudibleAnomalyKindNames` が空)。監視者は画面を見られる位置におり、
   音はトランシーバーと干渉し近隣にも響く。異常表示は消していない。
   **2026-10-30 利用者決定:** 航行中の艇の漕手に警告の音(単発・連続音)が鳴ったら、
   監視端末を**バイブ**で1回知らせ、地図の札と艇一覧でその艇を目立たせる
   (`useObserverWarningAlerts`)。音は今までどおり鳴らさない。バイブは画面表示中だけで、
   同じ艇・同じ種類が続く間は繰り返さず、複数艇でも2秒に1回へまとめる(原則4)。
   オン・オフは艇一覧の上(既定オン)。受信した他艇の警告状態をここで使うことは、
   不変条件12の改訂(監視端末の通知・表示は可)による。安全経路は今までどおり依存しない。

## 4. やらないこと

第2章の原則を、してはいけないことの形で言い換えたもの。Git・Firebase Rules の本番反映・ストア提出などの
運用の決まりは [AGENTS.md](../AGENTS.md) が正(Rules の反映はエージェントが行う)。

- **航行開始・警告経路を条件付きで無効化すること**(原則1に反する)
- **「安全のため」を理由に自由度を削ること**(原則2に反する)
- **正常な運用で鳴る警告を放置すること**(原則4に反する)
- 近接注意距離を 0 にして警告を止めること
  (対象外にするのは `FixedObstacleWarningSettings` の役割)
- 警告関連の設定値をハードコードすること(`lib/config/` に置く)
- Firebase プロジェクト設定・認証方式・課金設定の変更(Rules の本番反映は除く。AGENTS.md)
- 既存機能の理由なき削除、大規模リファクタリング
