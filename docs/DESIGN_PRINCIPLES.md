# 設計原則

作成日: 2026-07-26
対象: Rowing Navigator 桜川版

このファイルは本プロジェクトの**最上位規範**である。
[DESIGN.md](DESIGN.md) が「何があるか」を記述するのに対し、ここには「何を前提に、
何を優先して作るか」を書く。設定値を変える・機能を足す・警告の出し方を変える判断は、
すべてここに書かれた前提と原則から導く。

`design_notes/` の各文書は、その時点の要件定義であって現在有効な方針ではない。
過去の判断理由を辿るときだけ参照する。

## 1. 運用前提

**この章が全ての根拠である。** ここが変わったら、第3章の設定値を全て見直す。

### 1.1 水域

| 項目 | 値 |
| --- | --- |
| 場所 | 茨城県土浦市 桜川 |
| 川幅 | 概ね 40〜50m、狭所 35m |
| カーブ | 蛇行区間あり。カーブ間隔は最短 200m、最長 700m |
| 岸の危険区域 | 岸の基準線から水面側へ約5m |
| 実効航路幅 | 通常 30〜40m、狭所 25m(川幅から両岸の危険区域を引いた値) |

### 1.2 航行ルール

- **右側通行。** 航路を中心線で二分し、各艇は自分から見て右側を進む。
- **片側1レーン。** 対向艇とは常にすれ違う。追い越しは同一レーン内で起きる。
- 片側レーン幅は実効航路幅の半分 = 通常 15〜20m、**狭所 12.5m**。
- すれ違い時の艇の中心間距離は、両者がレーン中央を保っていれば
  通常 15〜20m、狭所 12.5m。

### 1.3 練習形態

| 項目 | 値 |
| --- | --- |
| 同時に川に出る艇数 | 2〜12艇 |
| コーチ艇 | **いない** |
| 休憩場所 | 橋の下、または航路の端 |
| 艇種 | 1x / 2x / 4x / 8+(混在する) |
| 巡航速度 | 概ね 3〜5 m/s |
| 漕手による端末操作 | **できない**(両手がオールで塞がり、端末は艇に固定されている) |
| 監視者による端末操作 | **できる**(陸上で端末を手に持っている) |

### 1.4 前提から直ちに従うこと

- **橋の下と岸際に停まるのは正常な運用である。** 異常ではない。
- **岸から数mを走るのは正常な運用である。** 実効航路幅25mの狭所で
  8+(全長19.9m・全幅7.5m)がすれ違うとき、岸への余裕は片側数mしかない。
- **対向艇と十数mですれ違うのは正常な運用である。** これを危険として扱うと、
  すれ違うたびに警告が出て、確実に形骸化する。
- **監視者は陸上にいる。** コーチ艇からの監視を前提にした機能を、
  安全経路の必須要素にしてはならない。
- **画面の常時点灯は「航行中だけ」必要である。**
  漕手は航行中に端末を触れないので、画面が消えたら復帰させる手段がない。
  したがって航行中は常時点灯させ、タップを前提にした操作を安全経路へ置いてはならない。
  一方**監視者は陸上で端末を操作できる**ので、監視中に常時点灯させる理由はない。
  電池を無駄に使うだけであり、**監視中は常時点灯しない**。
- **カーブは 200m ごとに来る。** 5m/s で 10秒先 = 50m 先を予測するなら、
  予測は必ずカーブをまたぐ。直線予測は前提と噛み合わない。

## 2. 設計原則

### 原則1: 機能を止めない

能力が欠けているときに、航行開始をブロックしたり警告経路を無効化したりしない。
**「縮退運転 + 明示的な警告」で継続する**(`SafetyRunMode.runningDegraded` /
`unavailable` と system fault 警告)。

音声・危険区域データ・通信・GPS のいずれが欠けても航行は開始できる。
位置情報権限だけは例外(原理的に全機能が成立しない)。

**なぜ:** 使えない状況で止まるアプリは、使える状況でも起動されなくなる。
機能が半分でも動いていれば、半分の価値は出る。

### 原則2: 使い方は使い手が決める

どういうシチュエーションで使うかはユーザーの自由である。
アプリは「正しい使い方」を強制しない。

- 一人で漕ぐときも、12艇で漕ぐときも使える。
- 警告を切って地図と記録だけ使うのも正当な使い方である。
- 危険区域データが未整備の水域で使うのも正当な使い方である。

**なぜ:** 想定外の使い方こそが実運用である。制約を増やすほど、
実際の練習で起きることに対応できなくなる。

### 原則3: その時々で出せる最大限の価値を出す

「全部揃っていないから何も出さない」ではなく、
**「今揃っているもので出せるものを出し、欠けているものを明示する」**。

- 他艇が受信できなければ、固定危険区域の警告は出す。
- 中心線が作れなければ、直線予測へ縮退して警告は出し続ける。
- GPS が劣化していれば、不確実性を広げたまま警告・記録・共有を続ける。

### 原則4: 過剰警告は安全機能の破壊である

警告漏れ(false negative)を避けることを優先する。
ただし、**形骸化した警告は警告漏れと同じである**。鳴りっぱなしの音は
必ず無視され、無視される警告は存在しないのと変わらない。

第1章の「正常な運用」で鳴る警告は、安全側に倒した設計ではなく**不具合**として扱う。

### 原則5: 「どれだけまずいか」と「どれだけ切迫しているか」を混ぜない

- **内部レベル lv0〜3** = どれだけまずいか(停止距離内か・確度)。
  表示色・優先順位・ログにだけ使う。
- **緊急度バンド** = どれだけ切迫しているか(到達までの時間だけ)。音を決める。

詳細は [CLAUDE.md](../CLAUDE.md) の「提示ポリシー」。

### 原則5.1: 警告の主表示は対象・状態だけにする

警告チップの主表示は、利用者が次に目視すべき対象または確認すべき状態を、短い語だけで
示す。物理的な危険区域・他艇では「岸」「橋」「橋脚」「中洲」「流木」「杭」「工事船」
のように**対象名だけ**を表示し、「〜に接近」「注意」「危険」などの自明な語尾は足さない。
警告は接近・進入・異常を検知したから表示されているので、主表示で同じ事実を繰り返しても
判断材料は増えず、横幅と一瞥で読める時間だけを消費する。

GPSや位置共有などのsystem faultは、対象名にできないため「GPSが途絶」「位置共有が停止」の
ように、利用者が確認すべき能力低下を短く示す。残り時間、件数、必要な補足は2行目・詳細・
アクセシビリティへ置けるが、主表示を冗長にしない。音声の語句、内部のリスクレベル、警告
発生条件は主表示の文言から推測させず、それぞれ独立して扱う。

### 原則6: データ欠損は安全の根拠にならない

受信途絶・GPS 断を「脅威が消えた」証拠に使わない。
情報が無いことは、危険が無いことを意味しない。

### 原則7: 設定値には前提を書く

`lib/config/` の各値には、**第1章のどの前提から導かれたか**をコメントで残す。
根拠のない数値は、次に触る人が動かせない。

## 3. 前提から導かれる設定値

各値が第1章のどの前提に対応するかを示す。前提が変わったらこの表を辿って見直す。

### 3.1 岸・固定危険区域

| 設定値 | 現在値 | 根拠となる前提 |
| --- | --- | --- |
| `shoreProximityCautionDistanceMeters` | 3.0m | 1.4「岸から数mを走るのは正常」。岸を大きく取ると常時鳴る |
| `bridgeProximityCautionDistanceMeters` | 5.0m | 橋脚衝突の帰結が大きい。ただし毎回くぐる |
| `bridgePierProximityCautionDistanceMeters` | 6.0m | 水中に立つ実体への衝突は最悪。局所的なので流木と同じ距離でも形骸化しない |
| `driftwoodProximityCautionDistanceMeters` | 6.0m | 水面下で見えず帰結が最悪。桜川で実際に発生する |
| `audibleProximityCategories` | `{driftwood, island}` | 1.4「岸際走行は正常」。岸を鳴らすと形骸化する |
| `bandCappedCategories` | `{bridge}` | 1.3「休憩は橋の下」+ 毎回通過する。連続音まで上げない |
| `lowSpeedAudioMuteSpeedMetersPerSecond` | 1.667m/s（分速100m） | 1.3「休憩は橋の下・航路の端」。橋脚・岸・逆走・未移行の橋だけ音を止め、表示・記録は続ける |
| `defaultStaticSweepClearanceMeters` | 1.5m | 排他領域の横幅と全艇種で一致(= 従来動作) |
| `shoreStaticSweepClearanceMeters` | 0.0m | 1.4 + 1.2 狭所レーン中央11.25m。下記の実測を参照 |

**岸の掃引クリアランス(2026-07-26 実機テストで是正):**

静的区域の掃引に排他領域(1x で横幅9m)を使っていたため、
GPS帯1.5mと合わせて**岸の基準線から11mで発報**していた。
1.2 の狭所ではレーン中央を守っても艇中心は岸から11.25m しかなく、
**規定どおり漕いでも鳴る境界に正常運用が乗っていた**(3.5-2 の懸念が実測で確定)。
実機ログでは連続音488サンプルのうち368サンプル(75%)が
艇中心が岸区域の外側にいる状態だった。

排他領域は「他船に空けてほしい水面」を表す概念であり、
**並走することが正常な岸**へ当てるのが誤りだった。
静的区域の掃引は「船体領域の横幅 + kind別クリアランス」に変え、
岸だけ 0m(= 船体+オールの実寸)とした。
前後方向(`h`)と `s` は排他領域のままなので、
**岸へ向かって進む艇の検知時刻は変わらない**。

| GPS accuracy | 変更前 | 変更後(岸) | 狭所レーン中央11.25mに対する余裕 |
| --- | --- | --- | --- |
| 5m | 10.10m | 8.60m | 0.25m → **2.65m** |
| 15m | 11.00m | 9.50m | 0.25m → **1.75m** |

### 3.2 他艇・すれ違い

| 設定値 | 現在値 | 根拠となる前提 |
| --- | --- | --- |
| `nearMissSeparationMeters` | 2.0m | 1.2 狭所レーン幅 12.5m。**下記3.5の要検討項目** |
| `nearbyBoatRadius` | 300m | 1.3 2〜12艇。桜川の見通し距離 |
| `boatStaleTimeoutSeconds` | 30秒 | 停止中送信10秒の3倍。幽霊艇と通信ジッタの分離 |
| `boatPredictionTimeoutSeconds` | 6秒 | 5m/s で 30m の外挿が限界 |

**すれ違いの余裕の計算(狭所・8+同士の最悪ケース):**

- 8+ の排他領域 全幅 `w` = 10.5m(片側 5.25m)
- 2艇の排他領域が接触しない最小中心間距離 = 10.5m
- 狭所でレーン中央を保った実際の中心間距離 = 12.5m
- **余裕 = 2.0m**

つまり、狭所で 8+ 同士が規定どおりすれ違うと、領域間の隙間はちょうど 2m である。

### 3.3 カーブ・予測

| 設定値 | 現在値 | 根拠となる前提 |
| --- | --- | --- |
| `enableChannelAwarePrediction` | true | 1.1 カーブ間隔 200〜700m。直線予測では 50m 先が外岸へ突っ込む |
| `defaultWarningTimeSeconds` | 10.0秒 | 5m/s で 50m 先。カーブ1つ分より短い |
| `minimumChannelHalfWidthMeters` | 8.0m | 1.1 川幅の実測より広めのガード |
| `maximumChannelHalfWidthMeters` | 60.0m | 同上 |
| `maxChannelCurvatureMarginMeters` | 3.0m | 折れ線近似の残差 + 川なりに曲がる見込み |
| `reverseGuidanceHeadingErrorDegrees` | 120度 | 1.2 右側通行・片側1レーン。川を横切る90度は逆走にしない |
| `reverseGuidanceLaneAmbiguityMeters` | 5.0m | 中心線近傍はGPS誤差で規定方位が180度反転する。片側レーン中央は中心線から6〜10mなので、レーンを守る艇は判定対象に残る |

**逆走注意(2026-07-26 実機テストで是正):**
従来は「区域内に現在地があるか」だけで判定しており、進行方向を見ていなかった。
実機ログでは77分で16回この区域へ出入りしており、正常に漕いでいるだけで
16回鳴ることになる。航路中心線と右側通行から規定方位を求め、
方位差が120度以上のときだけ発報する。中心線が作れない・カバー範囲外の
ときは従来どおり区域内で発報する(原則1: 縮退運転)。

### 3.4 休憩・停止

| 設定値 | 現在値 | 根拠となる前提 |
| --- | --- | --- |
| `stableStopSpeedMetersPerSecond` | 0.4 m/s | 1.3「休憩は橋の下・航路の端」 |
| `stableStopConfirmationDuration` | 5秒 | 同上。停止中の固定障害物の反復音を抑える |
| `shipDomainMaxLowSpeedLateralInflationMeters` | 4.0m | 岸際の休憩・折り返しの回頭で過剰警告にしない上限 |
| `sendIntervalStoppedSec` | 10秒 | 休憩が長いことを前提にした通信量削減 |
| `staticOverlapClosingRateMetersPerSecond` | 0.3 m/s | 岸との並走・桟橋への係留は「まずい」が「切迫していない」(原則5) |
| `staticOverlapImminentGrace` | 5秒 | 縮まらないまま重なり続けたら表示のみへ落とす |
| `closingRateWindow` | 3秒 | 接近速度を求める観測窓 |

**重なりの切迫度(2026-07-26 実機テストで是正):**
`currentOverlap` を無条件に連続音(imminent)へ昇格させていたため、
岸と並走している間・桟橋に着けている間は連続音が鳴り続けた。
`currentOverlap` は原則5の「どれだけまずいか」であって
「どれだけ切迫しているか」ではない。距離が縮まっていなければ1段下げ、
猶予後は表示のみにする。**距離が取れないときは接近中として扱う**(原則6)。
他艇は相手が接近してくるため対象外。

### 3.4.1 陸上判定(音のゲート)

| 設定値 | 現在値 | 根拠となる前提 |
| --- | --- | --- |
| `ashoreLandSideMarginMeters` | 12.0m | 1.1 川幅40〜50m + 1.4「岸から数mを走る」。水上で成立するには20m級の誤差が要る |
| `ashoreAccuracyMarginFactor` | 2.0 | 誤差が大きいときほど陸上と決めつけない |
| `ashoreConfirmationDuration` | 30秒 | 単発の異常測位で確定させない |
| `ashoreBaselineRelevanceRadiusMeters` | 200m | 霞ヶ浦の沖では基準線の半平面を延長した判定が信頼できない |

艇庫での準備・艇の運搬中は岸の危険区域の内側にいるため連続音が鳴っていた。
**止めるのは音だけ**で、検知・表示・記録・位置共有は継続する(原則1)。
陸上確定は遅く(30秒)、水上復帰は水面側の測位1点で即座、という非対称にしてある。
GPS品質が good でないとき・accuracy が取れないときは判定しない。
画面に常時表示し、「音を戻す」で手動解除できる(原則2)。

### 3.4.2 system fault の鳴らし方

| 設定値 | 現在値 | 根拠となる前提 |
| --- | --- | --- |
| `dynamicReceiveFaultConfirmSec` / `ClearSec` | 15秒 | 3.4 停止中送信10秒 + 通信ジッタでは発報しない。15秒 < 鮮度上限30秒 |
| `visualFirstSystemFaultCategories` | 受信・共有系 | 通信の途絶は、いま行動を変える必要があるものではない |
| `systemFaultRecueInterval` | 5分 | 表示は消さず(原則1・6)、音だけ減らす |
| `systemFaultWarningAudioAsset` | 専用音 | 衝突音の流用をやめる。実機で音173回中99回が衝突音だった(原則4) |

### 3.5 前提と噛み合っていない疑いがある値(要検討)

第1章を明文化した結果、次の値は運用前提と衝突している可能性がある。
**変更は単体テスト(特に実データ統合テスト)の更新とセットで行う。**

1. **`nearMissSeparationMeters` = 2.0m**
   3.2 の計算どおり、狭所で 8+ 同士が**規定どおり**すれ違うと隙間はちょうど 2.0m。
   境界上に正常運用が乗っており、狭所のすれ違いごとに lv1 が立ちうる。
   lv1 は表示のみで音は鳴らないため実害は小さいが、「注意表示が常時出ている」
   状態は原則4に反する。艇種の組み合わせ別に見直すか、
   狭所では中心線からの逸脱量で判定する方が前提と整合する。

2. ~~**岸の危険区域の扱い全般**~~ → **2026-07-26 の実機テストで確定・是正済み。**
   懸念どおり、右側通行の通常操舵で掃引警告が立っていた(3.1 の表を参照)。
   静的掃引のクリアランスを kind 別にして是正した。
   回帰は `test/services/static_sweep_clearance_test.dart` が実データで固定している。

3. **コーチ機能(`use_coach_watch`)の位置づけ**
   1.3 のとおりコーチ艇はいない。陸上からの監視、または不使用が前提である。
   安全経路がこの機能に依存していないことを維持する。
   2026-07-26 の実機テストを受けて、**監視モードの音は既定で無効**にした
   (`coachAudibleAnomalyKindNames` が空)。監視者は画面を見られる位置におり、
   音はトランシーバーと干渉し近隣にも響く。異常表示は消していない。

## 4. やらないこと

- **航行開始・警告経路を条件付きで無効化すること**(原則1に反する)
- **「安全のため」を理由に自由度を削ること**(原則2に反する)
- **正常な運用で鳴る警告を放置すること**(原則4に反する)
- 近接注意距離を 0 にして警告を止めること
  (対象外にするのは `FixedObstacleWarningSettings` の役割)
- 警告関連の設定値をハードコードすること(`lib/config/` に置く)
- Firebase プロジェクト設定・認証方式・課金設定の変更
- 既存機能の理由なき削除、大規模リファクタリング

## 5. 前提が変わったときのチェックリスト

第1章のどれかが変わったら、次を順に確認する。

- [ ] 川幅・実効航路幅が変わった → 3.1、3.2 を全て再計算する
- [ ] 航行ルール(右側通行・片側1レーン)が変わった → 3.2 と中心線予測の妥当性
- [ ] カーブ間隔が変わった → 3.3 と `defaultWarningTimeSeconds`
- [ ] 艇数の上限が変わった → `nearbyBoatRadius`、送信間隔、RTDB 転送量試算
