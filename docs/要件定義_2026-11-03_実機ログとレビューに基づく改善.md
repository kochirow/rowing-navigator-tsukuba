## R1. 終了時の「今日の記録」シートと、途切れた記録

### R1-1. 根拠

- 11/03 の記録は 06:58:28 に桟橋で途切れ、12:00:57 の次回起動で見つかった。記録は未完了のまま残り、利用者には何も表示されていない。
- ログは各自が LINE で送って集めている。今は記録の画面か一括送信まで行かないと送れない。
- 警告の良し悪しは、漕いだ本人の感覚がいちばんの手がかりになる。山下さんの「港を出るまでずっと鳴っていた」は、ログを港の中まで掘り下げるきっかけになり、R4 の実装につながった。

### R1-2. 画面

```
┌ 今日の練習 ─────────────────────────┐
│ 2.2 km ・ 19分                              │
│ 鳴った警告：他艇 3・岸 4・逆走注意 7         │
│                                              │
│ 警告のタイミング（任意）                     │
│  [早すぎ][少し早い][ちょうど][少し遅い][遅すぎ] │
│ 警告の量（任意）                             │
│  [少なすぎ][少し少ない][ちょうど][少し多い][多すぎ] │
│ ひとこと（任意）                             │
│ ┌────────────────────────┐ │
│ │港を出るまでずっと鳴っていた            │ │
│ └────────────────────────┘ │
│                                              │
│ [          ログを送る          ]             │
│              あとで                          │
└──────────────────────────────┘
```

途切れた記録のときは、先頭に「前回の航行は終了ボタンを押さずに終わりました（06:58 まで記録）」と出す。

### R1-3. 評価の目盛り

満足度の★ではなく、真ん中を「ちょうどよい」にした両側の5段階にする。★だと「合わない」の向き（早かったのか遅かったのか）が分からないためである。

| 値 | 警告のタイミング | 警告の量 |
| --- | --- | --- |
| −2 | 早すぎた | 少なすぎた |
| −1 | 少し早かった | 少し少なかった |
| 0 | ちょうどよい | ちょうどよい |
| +1 | 少し遅かった | 少し多かった |
| +2 | 遅すぎた | 多すぎた |

- 5つのボタンを横に並べ、選んだものだけを強調する。もう一度押すと未選択に戻る。
- 真ん中のボタンは他より少し幅を広げ、「ちょうど」と書く。両端は言葉で向きを示す。

### R1-5. 設計方針

- 表示のきっかけは、保存の完了を受け取る別の hook に置く。`use_navigator.dart` には「保存した記録のID」を渡す口だけを足す（行数とimportの予算が上限近いため。2026-11-03 時点で 5575/5600 行・86/86 import）。
- 練習の直後に聞くのは、記憶がいちばん新しいからである。Strava も、運動の同期直後に画面の大半を覆う編集画面を出す形にしている。
- 評価の集計（R1-3 の値の平均・分布）は、警告の量と鳴り始めを見直すときの物差しにする（改善提案 3.3）。

### R1-6. 完了判定

1. 条件を満たす航行を終えるとシートが出る。評価・ひとことは入れても入れなくても送れる
2. 「少し遅い」を押してから閉じても、記録画面に +1 が残っている。もう一度押すと未選択に戻る
3. 送ったZIPの `manifest.json` に `userFeedback`（`timingOffset: 1` など）があり、`feedback.txt` に「少し遅かった（+1）」と出る。未入力の項目は null（ファイルでは「未入力」）
4. 一括送信の `bundle_manifest.json` に記録ごとの評価が入る
5. 途切れた記録を置いて起動すると、地図でシートが出て、記録が完了に直る（11/03 のログで終了時刻 06:58:28）
6. 航行中・監視中には出ない。シートの例外で航行開始が止まらない

## R3. 監視端末の背面通知

第2版から変更なし。

- 「漕手に警告の音が鳴った」「更新途絶（90秒）」を、監視端末が背面にあっても通知で出す。本文は「艇名：種類」。艇ごとに1つのIDで上書きする
- 通知は音を鳴らさない（DESIGN_PRINCIPLES 3.5-3）。iOS は Time Sensitive、Android は監視専用のチャンネル（重要度「高」・音なし・バイブあり）
- 「長時間停止」の背面通知は、通知用の閾値を別に持つ。係留区域・港の中・陸上判定中の艇は対象外。過去20セッションでは、係留区域の外での停止は3分以上が1練習あたり約1.1回、5分以上が約0.4回、10分以上が約0.15回（12艇なら約13回・約5回・約2回）
- 種類ごとのオン・オフを艇一覧の上に置く。通知の記録を監視ログへ残す
- iOS で音なしの通知がバイブするかは、公式の文書が無く、実機で確かめる

## R4. 港の中の警告の鳴り方（実装済み・座標は未作図）

### R4-1. 根拠

- 山下さん（11/03）：「岸を蹴って水上に出てから港を出るまで、ずっと警告が鳴ってた」
- 花澤さん（10/28）：「湾内から湾外へ行くときに、かなりの確率で逆漕コールが出る」
- 直近5回の霞ヶ浦の練習で、ラクスマリーナ桟橋から450m以内・レーンの外（港の中）で鳴ったのは49回。霞ヶ浦全体の100回のほぼ半分だった

| 港の中の49回 | 回数 | 内訳 |
| --- | --- | --- |
| 岸 | 23 | 確実に当たる予測が17、確実＋誤差込みが4、誤差だけが2。自艇の速さの中央値1.1m/s |
| 逆走注意 | 20 | すべて危険区域 v11（10/30）より前。v11 の 11/03 は0回 |
| 他艇 | 6 | 自艇の速さの中央値0.8m/s。11/03 は桟橋で待つ自艇へ他艇が8mまで近づき、計約23秒 |

港の中の岸の警告は、測位の誤差ではなく確実な予測で鳴っている。今の鳴り始め（13秒前）は1.1m/s で14m先にあたり、壁まで十数mしかない港の中では、向きを変えるたびに壁が予測に入る。止まるのに必要な時間は艇種ごとに6.6〜8.15秒で、速さによらない。港の中では、13秒のうち停止時間を超える約5秒分が先を見すぎている。

### R4-2. 決まったこと（2026-11-03 利用者承認）

- 港の中を地図データの新しい区域（`harborAreas`）として描き、その中だけ鳴り方を変える
- 港の中で、自艇・相手とも1.5m/s未満なら他艇の音を1回だけにする（2026-08-05 の「片方でも動いていれば今どおり鳴らす」を港の中に限って緩める）
- 港の中の岸の鳴り始めを「艇種の停止時間＋1秒」にし、1回だけにする
- 港の範囲は利用者がプロットツールで描く

### R4-3. 実装した鳴り方

| 対象 | 港の中での鳴り方 |
| --- | --- |
| 岸 | 到達までが「停止時間＋1秒」（1x 7.95秒、8+ 9.15秒）を超える候補は表示だけ。以内なら1回だけ読み上げる。自艇の測位の誤差の円だけで重なる候補（`own_position_set_entry`・`gps_guard_entry` だけで `continuous_domain_entry` を含まない）は表示だけ |
| 他艇 | 自艇も相手も1.5m/s未満なら1回だけ。相手が1.5m/s以上、または相手の速度が分からなければ今までどおり繰り返す。係留区域で両者0.4m/s未満なら今までどおり無音 |
| 逆走注意 | 読み上げない（判定・表示・記録は残す） |
| 杭・流木・橋脚・中州・橋 | 変えない |

「止まりきれる時点では必ず鳴る」（10秒が8+ の停止時間8.15秒を上回る、という根拠）は、停止時間＋1秒にすることで港の中でも保たれる。全艇種で停止時間を下回らないことをテストで固定した。

## R7. 位置取得の用途指定を全端末で一斉に `maritime` へ切り替える

### R7-1. 根拠

iOS では漕いでいる最中に方位精度が±180°（方位が使えない）になる測位が多く、10/30 から位置の変化で方位を求め直している（`gnss_motion_validity.dart`）。位置取得の用途指定は今 `fitness`（`geo_service.dart`）で、水上の航行向けの `maritime` に変えると方位を失う割合が下がる可能性がある。効果は公式の文書からは分からず、実機で測るしかない。

### R7-2. 方針（2026-11-03 利用者判断）

- 第2版の「同じ艇に2台載せ、片方だけ `maritime`」はやめる。誰がいつアプリを使うかはその場で決まり、端末ごとに設定を割り振れないためである。
- **プラグインの更新と既定の `maritime` への変更を1つのビルドに入れ、全員に即日配る。** すぐ実機ログを取り、切り替え前（`fitness`・旧プラグイン）のログと比べて評価する。悪ければ次のビルドで戻す。
- 中身はログで検証できるようにする（R7-R2）。プラグインの更新と用途指定の変更の効果は、このビルドだけでは分けられない。悪化したときは、まず用途指定だけを `fitness` に戻したビルドを配り、プラグインの影響か用途指定の影響かを切り分ける。

`maritime` が効くのは、iOS 27 の SDK で作り、iOS 27 以上の端末で動かしたときだけである。それ以外の iOS 端末では `otherNavigation` になる（geolocator_apple 2.4.0 の変更履歴）。11/03 の端末は iOS 26.6.2 なので、iOS 26 の端末では実際には `otherNavigation` が効く。Android は用途指定の影響を受けない。

### R7-3. 要件

| ID | 種別 | 要件 |
| --- | --- | --- |
| R7-R1 | MUST | `geolocator_apple` を 2.4.3 以上へ上げる（今 2.3.13）。2.4.1〜2.4.3 は `getCurrentPosition` の挙動を変えているので、航行開始の位置取得のテストを通す。`kCLDistanceFilterNone` の扱い（`iosDistanceFilterNone` の注記）が新しい版でも同じか確かめる |
| R7-R2 | MUST | 指定した用途指定、実際に効いた種類（`maritime`／`otherNavigation`／`fitness`）、`geolocator_apple` の版を、`navigation_started` と `gps_environment_snapshot` に記録する。ログだけで、どの端末で何が効いていたかが分かるようにする |
| R7-R3 | MUST | リリース版の既定を `maritime` にする。値は `lib/config/` に前提（R7-1・R7-2）付きで置く |
| R7-R4 | MUST | 「詳細（開発用）」で、その端末だけ `fitness` に戻せるようにする。水上で悪化に気づいたとき、次のビルドを待たずに戻せるようにするため。切り替えは次の航行開始から効く。戻した端末は R7-R2 の記録で分かる |
| R7-R5 | MUST | 用途指定の変更で、航行開始・背面での測位の継続（`pauseLocationUpdatesAutomatically: false`・`allowBackgroundLocationUpdates: true`）を変えない |
| R7-R6 | SHOULD | 切り替え前後の比較（R7-4 の値）を、診断ログのフォルダを渡すと出す集計を `tool/` に置く |

### R7-4. 比べ方と判定

- 同じ端末の、切り替え前の実機ログ（`fitness`）と切り替え後のログを比べる。0.7m/s以上の測位に限り、水域（桜川／霞ヶ浦）ごとに分ける。
- 比べる値：方位精度179°以上の割合、速度精度3m/s以上の割合、track.csv の方位の出どころが位置の変化（`position`）だった割合、測位精度の中央値と90%点、更新間隔の中央値と最大、背面での測位の途切れ、電池の減り（%/時）、1時間あたりの警告の回数。
- 前後の比較は、天候・場所・艇・漕ぎ方の違いを含む。1回の練習で決めず、切り替え後の練習3回以上・iOS 端末3台以上を目安にする。同じ日に Android の端末があれば、用途指定の影響を受けない参照として、その日の測位環境の目安にする。
- **採用**：方位を失う割合が下がり、測位精度・更新間隔・電池が悪くならない。DESIGN_PRINCIPLES 第3章に根拠を書く。
- **戻す**：航行開始の位置取得の失敗、背面での測位の停止、測位精度や更新間隔の明らかな悪化のどれかが出たら、次のビルドで既定を `fitness` に戻す（R7-2 の切り分け）。方位が改善しなかっただけでも戻す（変える理由がない）。
- 「悪くならない」の目安：測位精度の90%点の増加2m以内、更新間隔の中央値は変わらない、電池の減りの増加2割以内。

## R9. 受信側で相手の方位・速度を確かめ直す — 見送り

2026-11-03 利用者の判断で見送る。段0（記録だけ）も作らない。

### R9-1. 見送る理由

1. **実際の問題が見つかっていない。** 実ログの4組（7/26・7/30・8/05・10/28）では、どの方式でも鳴る秒の違いは0秒だった。相手の方位が壊れていて本当に当たりそうだった場面は1つも無かった（付録A-2）。効果が出たのは、壊れた値を人工的に入れた合成実験だけである。
2. **原因は送信側で対処済み。** 送信側は 10/30 から、精度の悪い GNSS の速度・方位を使わず、位置の変化から求め直した値を送っている（`conservative_position_estimator.dart`、`b206f8a`）。合成実験で入れた壊れ方（方位90°ずれ・速度1/4）が今も送られるかは確かめていない。R9 は送信側の推定に受信側の推定を重ねるだけになる。
3. **古い版の相手は一斉の更新で居なくなる。** R7 で全員に新しいビルドを配る。
4. **副作用がある。** 合成のすれ違いで鳴る件数が増えた（V3 で 33→39件・22→35件）。6秒間の位置の動きは、折り返し・停止・低速で今の動きから遅れたり揺れたりするので、正しい送信値を悪くしうる（付録A-4）。

### R9-2. 見直す条件

実機ログで「相手の方位・速度が誤っていて、警告が遅れた・鳴らなかった」場面が見つかったら見直す。その場面は R8-R1（他艇の観測に相手の速度と方位の信頼性を残す）と、2艇の診断ログの突き合わせで確かめられる。見直すときは付録A を出発点にし、受信の間隔・遅れ・停止・折り返しを入れて提示の状態機械まで通した再生で、増える音と救える場面の両方を比べる。

| V0 | 今のアプリ |
| V1 | 相手が0.5m/s未満のとき、レーンの向き×位置の速さの仮の相手を足す |
| V2 | 送られた値と位置の動きが食い違うとき、レーンの向きの仮の相手を足す |
| V3 | V2 と同じ条件で、位置の動きの向きの仮の相手を足す（レーンを使わない） |
| V4 | V2 と同じ条件で、送られた値を位置の動きで置き換える |

「鳴る秒」は、評価関数の候補から、鳴り始めの規則（確実なら13秒、確度が低い・仮の相手なら10秒）と、係留区域の静音で決めた。提示の状態機械は通していない。

### A-2. 実ログ4組

別々の艇の組は4組（7/26・7/30・8/05・10/28）。どの組でも、方式による鳴る秒の違いは0秒だった。10/28 の約17mのすれ違いは正しいレーンどうしの正常なすれ違いで、どの方式も鳴らさなかった。実ログには「相手の方位が壊れていて本当に当たりそうだった場面」が無く、効果の判定には使えなかった。

### A-3. 合成シナリオ（測位誤差3m）

正面衝突160件（最接近6m未満）、すれ違い400件（10m以上）。値は「10秒前までに鳴った件数・最接近の何秒前に鳴り始めたか（中央値）」。

| 場面・相手のデータ | V0 | V1 | V2 | V3 | V4 |
| --- | --- | --- | --- | --- | --- |
| 正面・正常 | 157件・15秒 | 同じ | 同じ | 同じ | 同じ |
| 正面・方位90°ずれ・速度1/4 | 1件・6秒 | 1件・6秒 | 2件・6秒 | 136件・11秒 | 156件・14秒 |
| 正面・0.4m/s・方位ずれ | 1件・7秒 | 2件・7秒 | 2件・7秒 | 136件・11秒 | 156件・14秒 |
| すれ違い・正常（鳴った件数） | 10 | 10 | 10 | 10 | 10 |
| すれ違い・方位ずれ・速度1/4 | 33 | 33 | 33 | 39 | 37 |
| すれ違い・0.4m/s | 22 | 22 | 22 | 35 | 37 |

### A-4. 限界

- 合成の相手は中心線に沿ってまっすぐ一定の速さで進む。実際の艇は蛇行し、カーブでは位置の動きの向きが遅れる。
- 受信は毎秒・遅れなしとして扱った。実際は2〜10秒ごとで、外挿が入る。
- 提示の状態機械を通していないので、鳴る秒の絶対値は実機と違う。方式の間の比較にだけ使える。
- 「正面・正常」「すれ違い・正常」で方式による差が無かったのは、この合成条件（まっすぐ・一定の速さ・毎秒受信）での結果である。停止・折り返し・低速・受信の遅れがあるとき、正常な相手でも位置の動きと送信値が食い違い、V3・V4 が値を変えうる（R9-1 の4）。
- 壊れた値の入れ方（方位90°ずれ・速度1/4）は、10/30 の送信側の修正の後にも起きるとは確かめていない（R9-1 の2）。
