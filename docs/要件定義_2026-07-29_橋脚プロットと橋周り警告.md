# 要件定義: 橋脚の手動プロットと、橋周り警告ロジックの更新

作成日: 2026-07-29
対象: プロットツール(`tool/obstacle-plotter/`)とアプリ(`lib/`)の両方
上位規範: [docs/DESIGN_PRINCIPLES.md](DESIGN_PRINCIPLES.md)(食い違ったらそちらが優先)

## 0. 用語

| 用語 | 意味 | この文書での扱い |
| --- | --- | --- |
| 橋(bridge) | 橋の桁・上部構造の投影範囲。**水面上を横断する** | 通過区域。艇は毎回この下をくぐる |
| 橋脚(bridge pier) | 水中に立つ橋の柱。**当たれば艇が壊れる実体** | 真の固定危険区域 |
| スパン | 隣り合う橋脚の間の、実際に通れる水面 | 明示データとしては持たない(橋脚の間として結果的に決まる) |

## 1. 背景と問題

### 1.1 現状のデータ

`assets/data/sakuragawa_obstacles.json`(profile version 4)の橋は、
`dangerZoneBaselines` に `kind: "bridge"` の**閉じた5点(実質4辺の矩形)**として入っている。
実測は次のとおりで、**川幅方向に55〜77m、つまり川を丸ごと横断している**。

| id | 名前 | 辺長 [m] |
| --- | --- | --- |
| `bridge_suigo` | 水郷橋 | 75.0 / 22.0 / 73.0 / 19.7 |
| `bridge_railway` | 橋2 | 75.0 / 17.5 / 77.4 / 17.6 |
| `bridge_sakuragawa` | 桜川橋 | 64.3 / 13.3 / 64.3 / 13.3 |
| `bridge_nioi` | 匂橋 | 68.0 / 6.3 / 70.7 / 8.4 |
| `bridge_zenigame` | 銭亀橋 | 55.0 / 9.8 / 54.6 / 11.2 |
| `bridge_tsuchiura` | 土浦橋 | 32.7 / 18.2 / 34.6 / 19.0 |
| `bridge_gakuen` | 学園大橋 | 29.3 / 27.5 / 25.2 / 24.1 |

これが `LegacyDangerZoneGenerator` で辺ごとに内外 ±5m
(`defaultBridgeExpansionMeters`)へ展開されるため、
**川の全幅にわたる幅20〜37mの帯が危険区域になる**。

### 1.2 何が問題か

DESIGN_PRINCIPLES 1.3 は「休憩場所 = 橋の下、または航路の端」、
1.4 は「橋の下と岸際に停まるのは正常な運用である」と定めている。
つまり現在のデータは、**正常な運用そのものを危険区域として塗っている**。
これは原則4(過剰警告は安全機能の破壊である)に正面から反する。

いまはその破壊を、提示側の緩和で押さえ込んでいる。

- `bandCappedCategories = {'bridge'}` — 連続音まで上げない
- `_capObstacleRiskLevel()` — 橋起因のリスクは lv2 で頭打ち
- `audibleProximityCategories` に bridge を入れていない — 近接注意では鳴らさない

この緩和には代償がある。**橋脚に正面から突っ込んでいる艇にも、連続音が鳴らない。**
`alert_presentation_config.dart:149` のコメントは、この妥協を明示的に一時措置と
書き残している(「橋脚そのものを別kindへ分離できたら、橋脚はこの対象から外す」)。
本要件はこの TODO の回収である。

### 1.3 やること(一文)

橋脚を実体として別kindでプロットし、
**橋脚には本来の警告強度を与え、橋の桁は評価対象から外す。**
ただし橋脚が未プロットの橋は、従来動作のまま維持する(原則1: 縮退運転)。

## 2. 全体方針

### 2.1 3つの不変な約束

1. **橋脚が未プロットの橋は、いまと寸分違わず動く。**
   データが揃っていないことを理由に警告を減らさない(原則6)。
   移行は橋ごとに独立して進められること。
2. **スパン中央を通常速度で通過する艇には、音を鳴らさない。**
   これは実データを使う統合テストで機械的に担保する。
3. **橋脚へ向かっている艇には、他の固定障害物と同じ強度で鳴らす。**
   band cap も lv2 cap も橋脚には掛けない。

### 2.2 橋と橋脚の関係(データモデルの核)

橋脚は `bridgeId` で親の橋を指す。**アプリはこの関連だけで移行状態を判定する。**

```
橋脚が1つ以上ぶら下がっている橋  →  その橋の桁は「表示のみ」。警告は橋脚が担う
橋脚が1つもぶら下がっていない橋  →  従来どおり桁の帯で警告する(縮退運転)
```

フラグやビルド設定で切り替えない。**データの有無がそのまま挙動を決める。**
これにより、7本の橋を1本ずつ現地確認しながら移行でき、
途中の版でも「橋脚も帯も無い橋」が生じない。

## 3. データ仕様

### 3.1 橋脚(新規)

橋脚は `obstacles` 配列へ **kind `bridgePier` のポリゴンとして**入れる。
`dangerZoneBaselines` には入れない。

**理由:** 基準線は辺ごとに ±N m の矩形へ展開される仕組みで、
2m×5m の橋脚を ±5m 展開すると 12m×15m の塊になり、実体より遥かに大きくなる。
橋脚は「実際の水中断面をそのまま描き、余裕は近接注意距離と掃引クリアランスで与える」
のが正しい。`obstacles` のポリゴンは `PresetObstacleService.loadPresets()
(lib/services/preset_obstacle_service.dart:432付近)` が座標校正だけ掛けて
そのまま `StaticObstacle` にするので、新しい展開経路を足す必要がない。

```jsonc
{
  "id": "bridgepier_nioi_1",    // 全小文字。命名規約 bridgepier_<橋のsuffix>_<連番>
  "name": "匂橋 橋脚1（左岸側）",
  "kind": "bridgePier",         // キャメルケース。3.1.1 を参照
  "bridgeId": "bridge_nioi",    // 必須。dangerZoneBaselines の橋 id を指す
  "points": [ {"lat":…, "lng":…}, … ]   // 3点以上。水中断面の実形状(反時計/時計不問)
}
```

- `points` は**航空写真から読み取った水面での実断面**。橋の桁の幅ではない。
  桁が張り出していても、水中に立っている柱の輪郭だけを描く。
- 1つの橋脚が水中で複数の柱に分かれている(門型橋脚の脚が2本など)場合は、
  **柱ごとに別の橋脚オブジェクト**にする。柱の間の水面は通れないことが多いが、
  艇が通れる幅(8+ 全幅7.5m + 余裕)がないなら、まとめて1つの多角形で囲ってよい。
  判断基準を `description` に残すこと。
- `warningAudio` は省略する(kind別既定音を使う)。

#### 3.1.1 大文字の可否は「id」と「kind」で違う

**`id`(= ツールの `exportId`)だけが全小文字を要求される。`kind` は要求されない。**
両者を混同しないこと。

| 場所 | 値 | 大文字 |
| --- | --- | --- |
| プロファイル JSON の `id` | `bridgepier_<橋のsuffix>_<連番>` | **不可** |
| ツールの `exportId` | 同上 | **不可** |
| 校正定数 `shared_safety_calibration.g.dart` の id | 上の `id` がそのまま入る | **不可** |
| Firestore Rules の hazard-allowlist | 同上 | **不可** |
| プロファイル JSON の `kind` | `bridgePier` | 可 |
| ツールの `ObjectKind` | `'bridgePier'` | 可 |
| Dart の `StaticObstacleKind` | `bridgePier` | 可 |
| 音声ファイル名 | `bridge_pier_warning.mp3` | 可(既存同様のsnake_case) |

**`kind` にキャメルケースを使ってよい根拠:**
プロットツールの検証は `exportId` にしか文字種の制約を掛けていない
(`tool/obstacle-plotter/src/validate/project.ts:25`)。`kind` は TypeScript の
ユニオン型で縛られているだけで、正規表現の検査は無い。実際、**既存の kind に
`testZone` / `ashoreArea` / `navigableWater` というキャメルケースが現に通っており**、
同梱JSONの `test_zone_land` も `"kind": "testZone"` で入っている。
Dart 側も enum `testZone` と `.name` がそのまま一致している。
したがって `bridgePier` は既存の慣習どおりであり、
**`.name` 以外の変換層(`jsonValue` のような仕組み)は要らない。**
`StaticObstacleKind.fromJson` は現状のまま `.name` で照合してよい。

**`id` が全小文字でなければならない根拠:**
`exportId` は表示用のラベルではなく、**生成コードの識別子として文字列連結で
展開される**。`tool/obstacle-plotter/server/changeset.ts:24` は

```ts
`&& (!values.keys().hasAny(['${object.exportId}']) || validScaledVertexOffsetList(values.${object.exportId}, N))`
```

のように、Firestore Rules の**裸のプロパティアクセス**へ埋め込み、
同じ値が `allowedSourceIds`(Dart)にも入る。文字種が絞られていることが、
この連結を安全にしている前提である。

加えて、小文字固定でないと**大小しか違わない2つの id を作れてしまう**。
重複検査は `Set` の完全一致なので `bridgePier_1` と `bridgepier_1` は
両方通るが、Firestore のフィールド名は大文字小文字を区別するため
**別々のフィールドになり、片方へ書いた座標校正値がもう片方に効かない**。
CHANGESET.md をレビューする人間の目には、ほぼ同じ文字列にしか見えない。
安全データが静かに壊れる類の不具合なので、制約は緩めない。

`exportId` は `${kind}_${uuid}` で自動生成される機械IDであり、
人が手で打つ場面はほとんどない。守る価値は実在し、払うコストはほぼ無い。

**ただし UX は直す(5.1 に含める)。** インスペクタの export ID 入力欄は、
入力時に自動で小文字へ正規化する。制約を保ったまま、エラーに当たること自体を
なくす。`kind.toLowerCase()` を掛けている既定値の生成
(`src/model/factories.ts:57`)は、この正規化と同じ意図なのでそのまま残す。

### 3.2 橋(既存、意味を追加)

`dangerZoneBaselines` の `kind: "bridge"` はそのまま残す。座標も変えない。
`bridgeId` で参照されているかどうかだけで、アプリ側の扱いが変わる。

将来「橋脚を全橋に入れ終えた」時点で、橋の桁を
`dangerZoneBaselines` から表示専用の別セクションへ移す整理を検討してよいが、
**本要件のスコープには含めない**(移行中に橋の帯を消すと縮退先が無くなる)。

### 3.3 プロファイル版数とハッシュ

- `obstacles` に新しい id が増え、既存の橋の意味が変わるため、
  **`currentHazardProfileDataVersion` を 4 → 5 に上げる**
  (`lib/config/hazard_profile_config.dart`)。
- 版が変わることで、現地で合わせた既存の座標校正値(共有・端末内の両方)は
  適用されなくなる。これは意図した動作である。橋の座標自体は変えないが、
  **橋脚は校正されていない新規座標なので、現地確認をやり直す必要がある。**
- `tool/update_hazard_profile_hash.sh` で SHA-256 を更新する。
- `dart run tool/generate_hazard_constants.dart` で
  `lib/models/shared_safety_calibration.g.dart` と
  `firestore.rules` の hazard-allowlist を再生成する。
  **橋脚の id が校正対象allowlistへ入るので、Rules のデプロイが必要になる。**
  デプロイはレビュー後に人がやる(ツールからもCIからも触らない)。

`DangerZoneKind`(`lib/models/danger_zone_settings.dart`)へは**追加しない。**
`DangerZoneKind` は基準線を矩形へ展開するときの片側距離を持つ列挙で、
橋脚は展開しないため対応する設定項目が無い。
`_staticKindForDangerZone` も触らない。

**互換性:** `StaticObstacleKind.fromJson` は未知値を `generic` へ落とすので、
古いアプリが新しいプロファイルを読んでも(通常は同梱なので起きないが)
橋脚は「危険区域」として警告される。安全側への縮退であり、これでよい。
`PresentationStateCodec` の受信側は**未知のカテゴリコードを捨てず、そのまま記録する**こと
(復号側で未知コードに遭遇しても例外にしない)。

### 4.2 橋の桁を評価から外す条件

`PresetObstacleService.loadPresets()` で、

1. `obstacles` を走査し、`kind == StaticObstacleKind.bridgePier` の `bridgeId` 集合を作る。
2. `dangerZoneBaselines` の `kind == bridge` のうち、その集合に含まれる id は
   **`LegacyDangerZoneGenerator` へ渡さない**(危険区域を生成しない)。
3. 地図表示用の形状としては残す。橋がどこにあるかは画面から消さない。

橋脚の `bridgeId` が、存在しない橋 id を指していた場合:
**橋脚は有効なまま、橋の帯も残す。** 関連が壊れているときに帯を消すと、
不正データが警告を消す根拠になる(原則6)。診断ログへ
`bridge_pier_orphaned`(橋脚id・参照先id)を出し、プロットツール側の検証で弾く。

### 4.3 診断・可視化

- 起動時の診断イベントへ `bridge_piers_unplotted` を出す。
  値は橋脚が1つも紐づいていない橋の id 一覧。
  これは異常ではなく**移行の進捗**なので、system fault にはしない。画面にも出さない。
- 練習ログの提示状態には 4.1 の `'p'` コードで残る。
  移行前後で「橋でどう鳴っていたか」を突き合わせられるようにする。

### 4.4 設定値と根拠

DESIGN_PRINCIPLES.md 3.1 の表へ追記すること。

| 設定値 | 提案値 | 根拠 |
| --- | --- | --- |
| `bridgePierProximityCautionDistanceMeters` | 6.0m | 帰結が最悪(コンクリート構造物への正面衝突)で、かつ橋脚は局所的なので、岸のように常時鳴ることがない。流木(6.0m)と同格に置く |
| `staticSweepClearanceMeters`(橋脚) | 1.5m(既定) | 岸のように並走することが正常な対象ではない。排他領域相当の既定でよい |
| `staticSweepLowSpeedLateralInflationFactor`(橋脚) | 既定 | 橋の下での折り返し・停止は正常だが、抑制は下記の安定停止で効く。ここを弄らない |
| `bandCappedCategories` | 橋脚は**対象外** | 橋脚は通過する区域ではなく当たる実体。連続音まで上げてよい |
| `_capObstacleRiskLevel()` | 橋脚は**対象外** | 停止距離内で確実に当たるなら lv3 でよい |
| `audibleProximityCategories` | `'bridgePier'` を**追加** | 近接注意でも1回は鳴らす。局所的なので形骸化しない。ただし 6.2 の懸念を現地で確認する |

**橋(桁)側の設定は一切変更しない。** `bridgeProximityCautionDistanceMeters = 5.0`、
`bandCappedCategories = {'bridge'}`、lv2 cap はそのまま残す。
橋脚が未プロットの橋の縮退動作がこれに依存している。

### 4.5 同じ橋の橋脚を1つにまとめる

CLAUDE.md の「静的警告は `sourceId` 単位に集約する」を橋脚へ拡張する。
`SafetyOrchestrator`(`lib/services/safety_orchestrator.dart:855` 付近)の
集約キーを、橋脚については `bridgeId` にする。

**理由:** 狭いスパンを抜けるとき、左右2本の橋脚が同時に近接注意距離へ入る。
集約しないと「橋脚に注意」が2重に立ち、同じ橋で2回鳴る(橋の手前面・奥面で
2回鳴っていた問題と同型)。代表は**最も切迫している(TTE最小、無ければ最近接の)**
橋脚とする。

### 4.5.1 低速時は、橋脚・岸・逆走の**音を鳴らさない**

**要件:** 自艇の速度が **分速100m(1.667 m/s)未満**のとき、
`bridgePier` / `shore` / `reverse` の警告音を鳴らさない。

**根拠(運用):** 岸に寄ってコーチの指示を受ける、橋の下や航路の端で休憩する、
という運用が桜川では日常的にある(DESIGN_PRINCIPLES 1.3「休憩場所 = 橋の下、
または航路の端」/ 1.4「橋の下と岸際に停まるのは正常な運用である」)。
その間に鳴る警告は、原則4の言う「正常な運用で鳴る警告 = 不具合」そのものである。
指示を聞いている最中に読み上げが被るのは、警告を潰すだけでなく、
コーチの声を潰す。

**根拠(閾値):** 分速100m = 1.667 m/s = 5:00/500m。
既存の `RowingPaceProfile.workPaceLimitSecPer500`(4:00/500m = 2.083 m/s)より
さらに遅く、**どの艇種でも「漕いでいる」とは言えない速度**である。
巡航は 3〜5 m/s(1.1)なので、通常の航行中にこの閾値を下回ることはない。

**対象と対象外を混ぜないこと。**

| 種別 | 低速時の音 | 理由 |
| --- | --- | --- |
| `bridgePier` | **止める** | 橋の下で休む。本要件 |
| `shore` | **止める** | 岸に寄って指示を受ける・休憩する |
| `reverse` | **止める** | 停止・漂流中の「向き」に逆走の意味がない |
| `bridge`(桁) | **止める** | 橋脚未プロットの橋での縮退動作を、橋脚と揃える |
| `curve` | 従来どおり | 進んでいなければそもそも区域進入が起きない。特例を足さない |
| `island` / `driftwood` / `generic` | **止めない** | 中州・流木は寄って休む対象ではない。低速で流されて当たる事故が現に起きうる |
| 他艇 | **止めない** | 相手が接近してくる。自艇が止まっていることは安全の根拠にならない |
| system fault | **止めない** | 速度と無関係 |

**止めるのは音だけである。**
検知・内部レベル判定・画面バナー・地図表示・練習ログ記録・位置共有は
すべて従来どおり継続する(原則1・原則6)。
`ashore_detector` が陸上判定で音だけを止めているのと同じ形にする。
実装も同じ場所、**`SafetyOrchestrator` の提示段階で音声指令を落とす**方式にし、
`CollisionRiskEvaluatorService` の判定そのものには触れない。
判定側で切ると、記録に「そこで危険が無かった」と残ってしまう。

**ヒステリシスは非対称にする。**

| 遷移 | 条件 |
| --- | --- |
| 静音へ入る | 1.667 m/s 未満が **3秒継続** |
| 静音から出る | 1.667 m/s 以上の測位が **1点でも出たら即座** |

単発のGPSノイズで速度が落ちた瞬間に音が消えるのを防ぎ、
漕ぎ出した瞬間には確実に音が戻る。安全側(音が鳴る側)へ倒れる向きを速くする。
速度は `RobustPositionEstimator` の推定速度を使う(生のGPS速度ではない)。
**速度が取得できないときは静音にしない**(データ欠損は静音の根拠にならない・原則6)。

**既存の安定停止抑制(0.4 m/s・5秒)との関係:**
本要件は上位互換になる(1.667 > 0.4)ので、対象の4種別については
安定停止抑制が実質的に働かなくなる。**それでも安定停止抑制のコードは残す。**
`island` / `driftwood` / `generic` には引き続き効いており、
`stableStopSpeedMetersPerSecond` は 3.4 の表で別の前提に紐づいている。

**設定値の置き場所:** `lib/config/alert_presentation_config.dart` に
`lowSpeedAudioMuteSpeedMetersPerSecond = 100 / 60`(= 1.6667)と
`lowSpeedAudioMuteConfirmation = Duration(seconds: 3)`、および対象カテゴリ
`lowSpeedMutedCategories = {'bridgePier', 'shore', 'reverse', 'bridge'}` を置く。
分速表記が根拠なので、**コメントに「分速100m」と併記する**こと。

**残る懸念(現地で確認する):** 1.667 m/s は、8+ の停止時間8.15秒で
約13.6m の停止距離に相当する。つまり「音が鳴らない速度」でも、
惰性で橋脚まで13m進みうる。橋脚に限っては、この静音が効いている間に
実際に接触しうる速度域が残っている。運用上の必要性が明確なので本要件どおり
実装するが、6.2 の現地確認で「静音中に橋脚へ寄っていく状況」を必ず観察し、
問題があれば橋脚だけ閾値を下げる(例: 分速50m)ことを検討する。
**画面バナーは静音中も出ている**ので、監視者と、端末を見られる状況の漕手には
情報が残る。

### 4.6 明示的に変更しないこと

- **確度による1段下げは橋脚にも掛ける。** `gps_guard_entry` /
  `heading_uncertainty_entry` の降格を橋脚だけ免除しない。
  橋の下は GPS 精度が落ちる場所であり、そこで「不確かな重なり」を
  確実扱いにすると、くぐるたびに連続音が鳴る。
- **安定停止中の抑制はそのまま適用する。** 橋の下での休憩(0.4m/s 未満が5秒)は
  正常運用であり、固定障害物の反復音は抑えたままでよい。
  風で橋脚へ 0.4m/s 以上で流されているなら鳴る。それは正しい。
- **`gps_unavailable` の確定10秒を、橋の通過を理由に伸縮させない。**
  5m/s で幅25mの橋を抜けるのは5秒であり、既存の非対称(確定10秒・解除0秒)で
  すでに吸収されている。橋の位置に応じた特例を入れると、
  「データ欠損を安全の根拠にする」経路が生まれる(原則6)。
- **陸上判定(`ashore_detector`)は無関係。** 岸の基準線だけを見ており、橋脚は使わない。
- **航路中心線の導出ロジックは変更しない。** 橋脚は中心線の材料にしない
  (中心線は「実際に通る線」であり、障害物から自動生成するものではない)。
  ただし 5.4 のツール側検証で、中心線が橋脚を貫かないことを担保する。

### 4.7 音声アセット

新規 `assets/audio/bridge_pier_warning.mp3` を追加する。読み上げ内容は
**「橋脚に注意」**。既存の `bridge_warning.mp3`(「橋に注意」)とは別ファイルにする
(CLAUDE.md「種類ごとに別の音声を割り当てること」)。

手順は CLAUDE.md のとおり厳守する。

1. WAV マスターを `tool/audio_src/` へ置く(VOICEVOX / ずんだもん、既存と同じ話者)
2. `./tool/normalize_warning_audio.sh` で `assets/audio/*.mp3` を生成
3. `./tool/check_warning_audio.sh` で音圧を確認(目標 -10 LUFS、ファイル間差 2.5 LU 以内)

長さは既存同様 0.5〜1.4 秒、末尾 0.15 秒の無音を持つこと。緊急版は作らない。

### 5.2 作図の操作要件

橋脚は 2〜5m 程度の小さな構造物で、既存の岸・橋(数十m)とは作図の精度要求が違う。
クリックだけで描かせると、実用にならない。次を満たすこと。

1. **親の橋を選んだ状態で「橋脚を追加」できる。** `bridgeId` が自動で埋まる。
   手動で付け替えるプルダウンも用意する(親の候補は `kind==='bridge'` のみ)。
2. **矩形入力の補助。** 2点(橋脚の長辺の両端)+ 幅[m] の入力から矩形を生成する
   モードを持つ。実際の橋脚はほぼ矩形か小判型なので、これが主たる入力手段になる。
   任意ポリゴンの手描きも従来どおり残す。
3. **寸法の常時表示。** 選択中のオブジェクトの外接矩形(長辺×短辺、m)を
   インスペクタへ表示する。橋脚が実寸から桁違いにずれていることに、
   書き出す前に気づけるようにする。
4. **複製と平行移動。** 同じ橋の橋脚は同形状であることが多い。
   選択した橋脚を複製し、地図上でドラッグして置ける。
5. **作図中のズーム下限。** 橋脚モードでは、一定以上の縮尺(目安: 画面幅 ≤ 100m)
   でないと頂点を確定できない。低ズームでの数mのクリック誤差をそのまま
   保存させない。下限に達していないときは、理由を画面に出す。

### 5.3 現地写真との突き合わせ

橋脚は航空写真だけでは水面下の広がりが分からない。
`verificationStatus` を作図者が正しく選べるよう、橋脚の既定値は `draft` とし、
**`aerial_only` のままの橋脚が1つでもあるプロジェクトは、
変更適用パッケージの生成時に警告(errorではない)を出す。**
実際に現地で見た結果は `description` へ日付付きで残す。

### 5.4 検証(`src/validate/project.ts`)

| コード | レベル | 条件 |
| --- | --- | --- |
| `bridgePier.geometry` | error | `geometry.type !== 'polygon'` または頂点 < 3 |
| `bridgePier.bridgeId.missing` | error | `bridgeId` が空 |
| `bridgePier.bridgeId.unknown` | error | `bridgeId` がどの `kind==='bridge'` オブジェクトの `exportId` とも一致しない |
| `bridgePier.size` | error | 外接矩形の長辺 > 20m、または短辺 < 0.5m。実寸としてありえない |
| `bridgePier.outsideBridge` | warning | 橋脚の重心が、親の橋のポリゴン(±10m)の外にある。親の取り違え検出 |
| `bridgePier.overlapsCenterline` | **error** | 航路中心線が橋脚ポリゴン、またはその外側 `bridgePierProximityCautionDistanceMeters`(6m)以内を通る |
| `bridgePier.spanTooNarrow` | warning | 同じ `bridgeId` の橋脚どうし、または橋脚と岸基準線の間隔が 12m 未満。8+(全幅7.5m)が通れるスパンが無いことを作図者に確認させる |
| `bridge.noPier` | warning | `kind==='bridge'` に橋脚が1つも紐づいていない。移行の未完了を可視化する(errorにはしない) |

`bridgePier.overlapsCenterline` を error にするのは、
**中心線が橋脚を貫いていると、川なり予測が毎回橋脚へ突っ込む**ためである。
`enableChannelAwarePrediction` が有効な現状では、これは「橋を通るたびに
確実に連続音が鳴る」データを配布することを意味する(原則4)。
README の「航路中心線は中州・橋脚を避けて引く」という口頭ルールを、
機械的な検証へ格上げする。

### 5.5 変更適用パッケージ

`CHANGESET.md` に次を含めること。

- 追加/変更した橋脚の一覧(id・親の橋・寸法・`verificationStatus`)
- **`currentHazardProfileDataVersion` を上げる指示と、その理由**
- `tool/update_hazard_profile_hash.sh` / `generate_hazard_constants.dart` の実行手順
- `firestore.rules` の hazard-allowlist 差分と、**別途デプロイが必要である旨**
- 「橋脚を追加した橋では、桁の帯による警告が止まる」ことの明記と、
  現地で確認すべき項目(6.3 のチェックリスト)

ツールは従来どおり、アプリ資産・Firestore を自動更新しない。

## 6. 検証

### 6.1 単体・統合テスト(必須)

実データ(`assets/data/sakuragawa_obstacles.json`)を使う統合テストが、
設定値の意図と実効値の乖離を検出する唯一の手段である。次を必ず追加する。

| テスト | 内容 | 期待 |
| --- | --- | --- |
| スパン通過(**本命**) | 橋脚をプロット済みの各橋について、隣り合う橋脚の中点を 5m/s・中心線方位で通過する軌跡 | 音の出る警告(`imminent`/`approaching`/単発)が**一切立たない** |
| 橋脚へ直進 | スパン中央からずれ、橋脚正面へ 5m/s で 40m 手前から接近 | TTE≤7s で `imminent`、内部レベル lv3 まで到達しうる |
| 未プロットの橋 | 橋脚を持たない橋を通過 | 現行と同一の挙動(band cap 済み・lv2 上限)。**現行テストがそのまま通ること** |
| 桁の帯の消滅 | 橋脚を持つ橋の桁が `loadPresets` の返す危険区域に含まれない | 含まれない。ただし表示用の形状としては取得できる |
| 孤児橋脚 | `bridgeId` が存在しない橋を指す | 橋脚も桁も両方有効。診断に `bridge_pier_orphaned` |
| 集約 | 狭いスパンで左右2本の橋脚が同時に近接 | 警告は1つ。代表は最も切迫している橋脚 |
| 橋の下の停止 | 橋脚から4mで 0.2m/s の停止が10秒継続 | 反復音・断続音が抑制される |
| **低速静音(4.5.1)** | 岸に接舷して 1.0m/s で 10秒 | 岸の**音が鳴らない**。バナー・記録・位置共有は従来どおり出ている |
| 低速静音の境界 | 1.60m/s と 1.70m/s | 前者は静音、後者は鳴る |
| 低速静音のヒステリシス | 1.0m/s が2秒 → 3秒 → その後 2.0m/s の測位1点 | 2秒では鳴る/3秒で静音/2.0m/s の1点で即座に復帰 |
| 低速静音の対象外 | 1.0m/s で流木・中州・他艇へ接近 | **鳴る**。静音は4種別だけ |
| 低速静音と速度欠損 | 速度が取得できない状態が継続 | 静音しない(鳴る) |
| 逆走の低速静音 | 1.0m/s で逆走区域を逆向きに滞在 | 読み上げが鳴らない。バナーは出る |
| kind の往復 | 全 `StaticObstacleKind` について `fromJson(kind.name) == kind` | 一致する。既存 `testZone` と同様に `bridgePier` も素で往復する |
| exportId の文字種 | ツール側で大文字を含む export ID を入力 | 自動で小文字化され、`object.id` エラーに当たらない(3.1.1) |
| 音声資産 | `warningAudioAssets` の全ファイルが存在し、音圧が揃う | `tool/check_warning_audio.sh` が通る |
| 生成物 | 校正定数・Rules・ハッシュ | `dart run tool/generate_hazard_constants.dart --check` と `tool/update_hazard_profile_hash.sh --check` が通る |

ツール側は `npm test` に、プロファイル往復(読込→書出しで橋脚と `bridgeId` が保存される)、
5.4 の各検証コードの発火、旧 `schemaVersion` の読込みを追加する。

### 6.2 現地で確認すること(テストでは証明できない)

- **橋の下で休憩している間、橋脚の音が鳴り続けないか。**
  近接注意で鳴らす対象に橋脚を入れる(4.4)ため、ここが最大の懸念点である。
  安定停止の抑制と `proximityAudioRearmMeters`(3m)で足りるはずだが、
  風で流されて停止判定を外れたり入ったりする状況は机上で再現できない。
  **鳴り続けるなら `audibleProximityCategories` から橋脚を外す**
  (掃引による警告は残るので、橋脚へ向かっていれば依然として鳴る)。
- 橋の下での GPS 劣化中に、橋脚の誤警告が増えていないか。
- 橋脚の座標が実物と合っているか(校正が必要か)。
- **低速静音(4.5.1)中に、橋脚・岸へ実際に寄っていく状況で困らないか。**
  1.667 m/s は 8+ で約13.6m の停止距離に相当する。静音のまま惰性で
  橋脚へ寄る余地が残る。問題があれば橋脚だけ閾値を下げる(例: 分速50m)。
- **低速静音が、漕ぎ出しで確実に解除されるか。** 発艇直後の最初の数ストロークで
  音が戻ること。ここが戻らないと、静音が航行全体へ漏れる。
- コーチの指示を受けている最中に、警告の読み上げが被らなくなったか
  (これが 4.5.1 を入れた目的なので、目的を達したかを直接確認する)。

### 6.3 リリース手順

1. 橋を1本選び、橋脚をプロットして変更適用パッケージを作る
2. 反映 → `dart analyze lib test` → `flutter test` → 実機ビルド
3. その橋を実際に通過し、6.2 を確認する
4. 問題なければ次の橋へ。7本すべてが済むまで `bridge.noPier` 警告が残る

**一度に7本まとめてやらない。** 1本目で分かることが必ずある。
