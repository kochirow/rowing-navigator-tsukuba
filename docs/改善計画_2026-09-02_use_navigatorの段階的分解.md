## 1. なんのためにやるのか

### 1.1 目的

> **現地で見つかった不具合を直し続けても、[CLAUDE.md](../CLAUDE.md) の
> 13個の不変条件が壊れないようにする。**

このアプリの価値は「警告が鳴るべきときに鳴る」でしか実現しない。
コーチ艇がいない桜川で、2〜12艇が対向艇と十数mですれ違う
（[DESIGN_PRINCIPLES.md](DESIGN_PRINCIPLES.md) 第1章）。
その一点が守られなければ、他の何が良くても意味がない。

警告が鳴らなくなる原因は2つしかない。

1. **判定そのものが誤っている。**
2. **判定は正しいのに、配線が壊れている。**
   （評価が回らない・候補が渡らない・音声要求が届かない・
   前回航行の後片付けが今回の状態を消す・開始工程の失敗が全体を止める）

1 は `lib/services/` へ純Dartとして切り出され、`test/services/` の78ファイルで
守られている。`collision_risk_evaluator_service.dart` は1,562行あるが、
それは責務の量であって、テストがある。**問題は 1 ではない。**

**2 の全部が `use_navigator.dart` の中にある。そしてそこだけがテストの外にある。**
これがこのリファクタの唯一の理由である。

**不変条件を規範として扱ってよい根拠。** 13項目は `d2b32cb`(2026-07-30)で
一括して文書化されたもので、実装しながら1項目ずつ承認されたものではない。
**2026-09-02 に利用者が全項目を読み、自身の判断と整合することを確認した**ため、
本計画はこれを規範として扱う（CLAUDE.md の同節も参照）。

なお、仮に将来どれかの方針が変わっても、**このリファクタの手順は変わらない。**
リファクタの仕事は振る舞いを変えないことであり、必要なのは
「不変条件が最善であること」ではなく「不変条件が**いまのコードについて事実**であること」
だからである。方針の変更は設計判断であり、実機で確かめて行う別の作業である。

### 1.2 なぜ「増やさない」では解けないのか

設計原則1（機能を止めない）は、能力が欠けたときの**縮退処理**を要求する。
設計原則6（データ欠損は安全の根拠にならない）は、欠けた事実を残す**診断**を要求する。
実際、過去3ヶ月の `use_navigator.dart` への増分（+5,774行 / 20コミット）の大半は、
`fix(diagnostics)` と共有・測位の縮退処理である。

**この増加は正しい。** 実機ログを読んで縮退経路を1つずつ塞いできた結果であり、
止めるべきものではない。今後も現地テストのたびに増える。

したがって「これ以上増やさない」は目的に反する。
**増えること自体は許し、増える先を1つのクロージャにしない**、これが唯一の対処である。
ラチェット（`check_hotspot_budget.dart`）は増加を可視化するが、
行き先を作らない限り、いずれ「理由を書いて上限を上げる」しかなくなる。

### 1.3 目的でないもの

次はこのリファクタの目的ではない。判断に迷ったら、これらを理由にしない。

- **行数を減らすこと。** 行数は残高であって目標ではない。
- **コードをきれいにすること・設計の一貫性。**
- **テストカバレッジの数値。**
- **AIエージェントが読めるようにすること。** 前回これを理由の一つに挙げたが、
  これは目的ではない。正しくは「変更が局所化され、離れた場所の不変条件を
  踏まないこと」であり、人が書いても同じである。

### 1.4 成功をどう測るか

**主指標**（目的に直結する）

- [不変条件×テスト対応表](review/2026-08-20_重要な不変条件と既存テスト対応表.md) の
  **未保護1件・部分的5件**が減ること。
- **1つの安全上の判断を変えるのに、`use_navigator.dart` の何箇所を触るか。**
  直近の実測: 逆走注意の音声トグル1個（`5d73135`）で**12箇所**。
  内訳は state宣言・診断payload 2箇所・setter・開始時のリセット・
  return・`UseNavigator` クラス4箇所。

**副指標**（主指標の副産物として下がるはず）

- ラチェット値。下げる方向にしか動かさない。

**測らないもの**: 目標行数。`useNavigator` が
「状態の公開・コントローラ生成・イベント委譲・UI反映」だけになれば結果は何行でもよい。

### 2.3 決定的な発見: 終了には規律があり、開始にはない

`stopNavigation` は既に**手順パターン**を持っている（4692行〜）。

```dart
Future<bool> attempt(String label, Future<void> Function() operation,
    {Duration? timeout}) async { … }
```

各工程に名前があり、`NavigationStopBudget` で残り時間を配分し、
世代ガードで古い工程の書き込みを弾き、失敗を `navigation_stop_step_failed` として残す。
`NavigationStopBudget` は `lib/hooks/navigation_stop_budget.dart` へ切り出され、
`test/hooks/navigation_stop_budget_test.dart` で固定されている。

**`startNavigation` にはこれがない。** 664行の直列コードに、
`ensureStartIsCurrent()` の呼び出しが7箇所、try/catch が5組、`.timeout()` が5箇所、
それぞれ独自の縮退処理として散っている。

そして不変条件表で**唯一「未保護」なのが不変条件5「音声・危険区域データ・通信の
いずれが欠けても航行開始をブロックしない」**である。これは設計原則1そのものであり、
その履行地点が、規律のない664行の中にある。

**このリファクタの中心はここである。**

## 3. 2026-08-20 の計画から変える点

| 前回 | 今回 | 理由 |
|---|---|---|
| Phase 2: テスト用DIコンテナを先に作る | **撤回** | フック全体をマウントするテストは Firebase・Geolocator・プラットフォームチャネルの偽装が必要で、遅く不安定になる。さらに**モノリスに対するテストはモノリスを固定する**。切り出しを助けず妨げる。時計の注入は、切り出した単位に切り出すときだけ入れる（`estimator_clock.dart` が前例） |
| Phase 3: シナリオテスト5本を先に書く | **撤回** | 5本中「フレーム停止中の音声要求」は `warning_presentation_frame_independence_test.dart` で保護済み。残り4本は対象を切り出せばそのまま単体テストになる。先にモノリス相手に書くと同じ作業を2回やる |
| Phase 4: 触るついでに切り出す（opportunistic） | **専用PRにする** | 現地で見つかった不具合の修正に構造変更を混ぜると、レビューで最も見たい差分が埋もれる。振る舞い不変の専用PRのほうが「移動しただけ」と確認でき、レビューが速い |

| `home_map_screen.dart` は最後 | **当面やらない** | 下記 5. |

## 4. 計画

各PRは**振る舞いを変えない**。合格条件は 6. に共通で置く。

### PR1: `startNavigation` を手順化し、不変条件5を固定する

**なぜ最初か。** 13個中唯一の未保護がここで、設計原則1の履行地点だからである。

**やること。**

1. 同じファイルの `stopNavigation` にある `attempt()` パターンを開始工程へ適用する。
   新しい設計の発明ではなく、このコードベースで既に動いている型の横展開である。
2. 各工程に名前と**失敗時の方針**を明示する。3種類しかない。
   - **続行**（音声準備、共有設定の取得、障害物profile、Firebase開始 など）
   - **続行 + system fault を立てる**（能力が落ちたことを提示に残す）
   - **中断**（位置情報権限のみ。原理的に全機能が成立しない唯一の例外）
3. 手順表と実行器を純Dartへ出す（`lib/hooks/navigation_start_sequence.dart`）。
   `navigation_stop_budget.dart` の隣に置き、同じ形にする。

**得られるテスト。** 手順表を回して、**どの工程が失敗しても
`mode` が `navigator` になり、対応する system fault が立つ**ことを表で固定する。
不変条件5が「未保護」から外れる。

**見込み。** 664行 → 350行前後 + 手順表。`ensureStartIsCurrent` の7箇所は
実行器の世代ガード1箇所へ集約される。

**リスクと歯止め。** 開始工程は安全経路である。ただし壊れ方が
「出艇できない / GPSも共有も付かないまま始まる」であり、
[quick_review](review_guide/quick_review.md) の **F4（航行が始まらない・途中で止まる）** と実機起動1回で必ず露見する。
静かに壊れない。振る舞い不変に収まらないと分かった時点で中止し、報告する。

### PR2: 診断記録を `SessionDiagnosticsRecorder` へ出す

**なぜ2番目か。** 732行 + 専用ref約25個と最も大きく、増加の主因であり、
**安全経路の外側**だからである（記録の失敗が安全経路を止めてはならない、は
CLAUDE.md の明文）。原則6が今後も要求し続ける診断の受け皿をここで作る。

**やること。** 純Dartクラスへ次を移す。

- `appendDiagnosticEvent` / `appendAlertEvent` / `appendRuntimeDiagnostic` /
  `queuePreSessionDiagnostic`（seq採番・elapsedMs付与・上限到達時のdrop計数・
  開始前イベントの保留とflush）
- `recordSafetyDiagnostics`、GPS品質・端末の向き・電池の変化検知、heartbeat
- `loadSessionDiagnosticMetadata`

インタフェースは「読み取り専用のスナップショットを受け、イベントを積む」だけに保つ。
**時計はこのクラスにだけ注入する。DIコンテナは作らない。**

**得られるテスト。** seq採番の単調性、`elapsedMs` が壁時計変更で乱れないこと、
上限到達時に落とした件数が残ること、開始前イベントが開始後にflushされること。

**見込み。** −700行前後、useRef 108 → 83前後。

### PR3: `runGpsWatchdogTick` の判断を分離する

403行の中で「復旧を試みるか・測位ポーリングするか・system fault へ昇格させるか」を
決めている部分を、状態スナップショットの純関数へ出す。副作用はフックに残す。
`receive_fault_debouncer.dart` が同じ形の前例である。

隣接する `buildSystemCandidates`（69行）も一緒に出す。
不変条件3の未保護範囲（`useNavigator` が必要な system candidate を常に渡す配線）が
ここで埋まる。不変条件1・4の「部分的」もここで詰まる。

- `stopNavigation` の実行器を PR1 の手順実行器と共通化する

## 5. やらないこと

**目的から導いた除外である。**「まだやらない」ではなく「やらない理由がある」。

### `processPosition`（561行）・`applySafetyAssessment`・`buildMyBoat` — 触らない

**ここは行数が多いこと自体が正しい唯一の場所である。**
1Hzで全状態を見る必要が実際にあり、`test/services/` と `tool/replay_alerts.dart`、
`test/replay/metamorphic_test.dart` で守られ、最もレビューされている。

### `UseNavigator` の戻り値54フィールドの整理 — いまはやらない

フック本体が小さくなり、この199行が比率として目立ってから再評価する。

### `home_map_screen.dart`（2,188行） — 当面やらない

13個の不変条件のうちこの画面が担うのは6（地図描画は安全判定用の拡張を反映しない）と

なお 2026-08-20 に codex が指摘したとおり「表示だから壊れても目で分かる」は誤りで、

## 6. 各PRの合格条件

1. **振る舞いを変えない。** 差分の大半が「移動」であること。
2. `flutter test` の結果が変わらない（既存テストは同じく通る。**新規テストのみ増える**）。
3. `dart analyze lib test tool` がクリーン（`tool` を必ず含める。CLAUDE.md 参照）。
4. `bash tool/review/smoke_check.sh` が通る。特に診断イベントカタログと
   鮮度階層（3s / 6s / 30s、停止送信10s）。
5. **ラチェット値（recommended と hard の両方）を下げる。**
   余白を使い直して元の大きさへ戻さない。
6. 不変条件表を更新し、その PR で「未保護 / 部分的」がどう動いたかを書く。
7. 主指標の変化を PR 本文に書く。行数だけを成果として書かない。

## 7. 中止条件

次のいずれかに当たったら、そのPRを中止して報告する。

- 振る舞い不変に収まらないことが分かった（縮退の順序、後片付けの順序、
  警告の出方のいずれかが変わる）。
- 既存テストを書き換えないと通らない。**既存テストの変更は、
  振る舞いが変わった証拠として扱う。**
- 切り出し先が結局同じ153スロットを参照し、呼び出し側が薄くならない。

## 8. 進め方

新機能開発は止めない。ただし PR1〜3 は**振る舞い不変の専用PR**として立て、
現地の不具合修正とは混ぜない。1PRずつ、前のPRがマージされてから次に入る。
