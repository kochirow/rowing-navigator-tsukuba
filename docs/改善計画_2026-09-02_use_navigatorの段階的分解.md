## 0. 再レビューの結論

**大規模な整理は行わない。最初の小さな1PRだけに着手し、その結果を見て次を決める。**

現在の集中は保守上の問題だが、アプリはCIを通り、13個の不変条件の中核も既存テストで

## 1. なんのためにやるのか

### 1.1 目的

> **現地で見つかった不具合を直し続けても、[CLAUDE.md](../CLAUDE.md) の
> 13個の不変条件が壊れないようにする。**

そのために、システムを**「一つの変更で理解・確認しなければならない範囲が小さい状態」**へ
スリム化し、保守性を上げる。総行数の削減は目的ではない。責務を説明する型やテストが
増えるため、コードベース全体の行数が一時的に増えてもよい。逆に、ファイルを分けただけで
状態・依存関係・変更箇所が減らないなら、それはスリム化ではない。

このアプリの価値は「警告が鳴るべきときに鳴る」でしか実現しない。
コーチ艇がいない桜川で、2〜12艇が対向艇と十数mですれ違う
（[DESIGN_PRINCIPLES.md](DESIGN_PRINCIPLES.md) 第1章）。
その一点が守られなければ、他の何が良くても意味がない。

警告が鳴らなくなる原因は、大きく次の2つに分けられる。

1. **判定そのものが誤っている。**
2. **判定は正しいのに、配線が壊れている。**
   （評価が回らない・候補が渡らない・音声要求が届かない・
   前回航行の後片付けが今回の状態を消す・開始工程の失敗が全体を止める）

1 の中核は `lib/services/` へ純Dartとして切り出され、`test/services/` の78ファイルで
比較的厚く守られている。`collision_risk_evaluator_service.dart` は1,562行あるが、
責務に対応するテストがあるため、**現時点の優先課題は 1 より 2 である。**
ただし、テストがあることを理由に判定本体を将来の確認対象から永久に外すものではない。

**2 の主要な調整処理が `use_navigator.dart` に集中し、フック全体の配線は直接テスト
されていない。** これがこのリファクタを行う主な理由である。

**不変条件を規範として扱ってよい根拠。** 13項目は `d2b32cb`(2026-07-30)で
一括して文書化されたもので、実装しながら1項目ずつ承認されたものではない。
**2026-09-02 に利用者が全項目を読み、自身の判断と整合することを確認した**ため、
本計画はこれを規範として扱う（CLAUDE.md の同節も参照）。

なお、仮に将来どれかの方針が変わっても、**このリファクタの手順は変わらない。**
リファクタの仕事は振る舞いを変えないことであり、必要なのは
「不変条件が最善であること」ではなく「不変条件が**いまのコードについて事実**であること」
だからである。方針の変更は設計判断であり、実機で確かめて行う別の作業である。

### 1.2 なぜ「増やさない」では解けないのか

設計原則1（機能を止めない）は、能力が欠けたときの**縮退処理**を要求する。
設計原則6（データ欠損は安全の根拠にならない）は、欠けた事実を残す**診断**を要求する。
実際、過去3ヶ月の `use_navigator.dart` への増分（+5,774行 / 20コミット）の大半は、
`fix(diagnostics)` と共有・測位の縮退処理である。

この増加の多くには、実機ログを読んで縮退経路を1つずつ塞いできたという必要な理由がある。
ただし、**必要な機能であることと、現在の実装が最小で重複していないことは別である。**
一括して不要とは扱わず、責務ごとに重複と持ち主を調べる。今後も現地テストのたびに
必要な処理は増えうる。

したがって「これ以上増やさない」は目的に反する。
**必要な増加は許し、増える先を1つのクロージャにしない**ことを対処の中心にする。
ラチェット（`check_hotspot_budget.dart`）は増加を可視化するが、
行き先を作らない限り、いずれ「理由を書いて上限を上げる」しかなくなる。

### 1.3 目的でないもの

次はこのリファクタの目的ではない。判断に迷ったら、これらを理由にしない。

- **行数を減らすこと。** 行数は残高であって目標ではない。
- **見た目をそろえるだけの整理・抽象化。** 保守性を上げない統一は行わない。
- **テストカバレッジの数値。**
- **AIエージェントが読めるようにすること。** 前回これを理由の一つに挙げたが、
  これは目的ではない。正しくは「変更が局所化され、離れた場所の不変条件を
  踏まないこと」であり、人が書いても同じである。

### 1.4 成功をどう測るか

**主指標**（目的に直結する）

- [不変条件×テスト対応表](review/2026-08-20_重要な不変条件と既存テスト対応表.md) の
  **未保護1件・部分的5件**が減ること。
- **1つの安全上の判断を変えるのに、`use_navigator.dart` の何箇所を触るか。**
  直近の実測: 逆走注意の音声トグル1個（`5d73135`）で**12箇所**。
  内訳は state宣言・診断payload 2箇所・setter・開始時のリセット・
  return・`UseNavigator` クラス4箇所。
- 切り出した責務について、**状態の持ち主が1つに決まり、入口と出口がテストで説明できる**こと。
- その責務を変更するときに読む必要のある依存先、可変状態、編集箇所が実際に減ること。
- 削除したコードについて、後述する「削除の証拠」が残ること。

**副指標**（主指標の副産物として下がるはず）

- ラチェット値。下げる方向にしか動かさない。

**測らないもの**: 目標行数と、コードベース全体の純減行数。`useNavigator` が
「状態の公開・コントローラ生成・イベント委譲・UI反映」だけになれば結果は何行でもよい。

## 4. 計画

各PRは**振る舞いを変えない**。合格条件は 7. に共通で置く。
実装前に、そのPRが触る範囲について「振る舞い保存表」を作る。表には、入力、出力、
状態変更、副作用の順序、待つ処理と待たない処理、timeout、世代確認、失敗時の継続・中断、
診断イベントを記録する。移動後に全行を照合し、表の各行が同じであることを確認する。

### PR1: 診断イベントの入れ物を `SessionDiagnosticBuffer` へ出す

**なぜ最初か。** 診断約732行を一度に1クラスへ移すと、別の巨大クラスを作るだけになる。
最初は、採番・保持上限・開始前保留という小さな一責務だけを切り出す。
警告判断そのものではないため、小さい単位を安全に外へ出す手順を検証できる。
ただし診断は「失敗を見えるようにする」安全機能なので、消してよい付属物とは扱わない。

**やること。**

- `appendDiagnosticEvent` / `appendAlertEvent` / `appendRuntimeDiagnostic` /
  `queuePreSessionDiagnostic` が共有する、seq採番・elapsedMs付与・保持上限・drop計数・
  開始前イベントの保留とflushだけを移す。
- GPS品質・端末の向き・電池・heartbeat・起動メタデータなど、**イベント内容を決める処理は
  このPRでは移さない。** それらまで持たせると役割を一文で説明できなくなるためである。

インタフェースは「完成済みイベントを受けて、順序と上限を守って保持する」だけにする。
経過時間に必要な時計だけを注入し、DIコンテナは作らない。

**固定するテスト。** 代表的なイベントの時刻・type・detailsを変えずに保持できること、
seq採番の単調性、`elapsedMs`、上限到達時のdrop件数、開始前イベントのflush。
イベントカタログと既存ログを読むtoolとの互換性も解析で確認する。

**続行判断。** この小さな切り出しで、診断用stateの持ち主と変更箇所が実際に減らなければ、
「分けただけ」と判断してrevertし、次の切り出し方法を再検討する。

### PR2: `startNavigation` を、現在の動作のまま手順化する

**なぜ2番目か。** 不変条件5の主要な履行地点だが、最も壊したくない場所でもある。
PR1で切り出し・診断互換・レビューの手順が機能したことを確認してから着手する。

**先に固定すること。** 現在の664行を工程ごとに表にし、各工程について次を実コードから
記録する。

- 成功時に変更するstateと、次工程へ渡す値
- 例外を握って続けるのか、外側のcatchへ進み開始全体を中断するのか
- system fault、常設表示、診断イベントのどれに現れるか
- `await`するか、バックグラウンド実行するか
- timeout値と、7箇所にある世代確認の位置
- 失敗後の後片付けの順序

**やること。** `navigation_stop_budget.dart` の考え方を参考に、手順の実行器を
`lib/hooks/navigation_start_sequence.dart` へ出す。ただし、続行・中断の区分、
timeout、非同期化、世代確認を**現在と同じ位置・意味のまま**移す。
世代確認を7箇所から1箇所へまとめることは、順序の意味が変わるため今回はしない。
実行器へ大量のstate setterやコールバックを渡す必要があるなら、フックを別ファイルから
遠隔操作するだけでスリム化にならない。その場合は全体の実行器化を止め、単独で完結する
工程だけを候補にするか、現状維持とする。

**固定するテスト。** 工程の順序、各工程の失敗後に次のどの工程が実行されるか、古い世代が
どこで停止するか、部分的に開始した資源が逆順ではなく現在と同じ順序で解放されるかを、
注入した小さなコールバックで確認する。

**重要な分離。** この確認で「音声・危険区域・通信の失敗が、実際には航行開始を
中断している」など不変条件5との不一致が見つかっても、このPRでは直さない。
リファクタは現在の動作を保存して終え、別のバグ修正PRとして利用者へ報告する。
理想の動作へ直すことと、コードを移すことを混ぜない。

不変条件5の対応表は、このPRのテストが直接証明できた範囲だけ更新する。

### PR3: `runGpsWatchdogTick` の判断を分離する

403行の中で「復旧を試みるか・測位ポーリングするか・system fault へ昇格させるか」を
決めている部分を、状態スナップショットの純関数へ出す。副作用はフックに残す。
`receive_fault_debouncer.dart` が同じ形の前例である。

隣接する `buildSystemCandidates`（69行）は、同じ状態スナップショットで一体として
説明できる場合だけ一緒に出す。別責務なら別PRにする。
不変条件3の未保護範囲（`useNavigator` が必要な system candidate を常に渡す配線）と、
不変条件1・4の「部分的」について、直接テストできる範囲を増やす。対応表の状態は、
実際に追加できたテストの証拠を見てから変更する。

### PR4以降（PR1〜3の結果を見てから決める）

- `stopNavigation` の実行器を PR2 の手順実行器と共通化できるか検討する
- 共有安全設定の取得・監視・適用（267行）
- GPS品質・端末の向き・電池・heartbeatなどの診断生成を、状態の持ち主ごとに分けられるか検討する

先に約束しない。PR1〜3で主指標がどれだけ動いたかを見て、続けるか止めるかを判断する。

## 5. 削ぎ落としてよいもの・いけないもの

この計画でいう「スリム化」は、短く書き換えることではなく、責務を適切な持ち主へ移し、
**同じ仕事を二重にしている部分だけを証拠付きで消すこと**である。

### スリム化できたかの判定

切り出し後、次の問いにすべて「はい」と言えることを確認する。1つでも「いいえ」なら、
行数が減っていても採用しない。

1. 新しい部品の役割を一文で説明できる。
2. その役割に関する可変状態の持ち主が1つになっている。
3. 呼び出し側は、内部の手順ではなく入力と結果だけを知ればよい。
4. 同じ変更を行うときに触る箇所・読む依存先が以前より少ない。
5. 値を右から左へ渡すだけの中継層、重複model、汎用DI基盤を増やしていない。
6. 新しい部品を単独で速くテストできる。

テスト・型・振る舞い保存表の追加で総行数が増えても、上の条件を満たせば保守性は向上する。
逆に、総行数だけ減っても条件を満たさなければ、将来の変更コストは下がっていない。

### 削除してよい条件

次のすべてを満たすものだけを削除する。削除内容、根拠、代わりの持ち主、守るテストを
PRの「削除台帳」に1件ずつ書く。

1. 参照元を全件調べ、到達不能か、同じ入力から同じ結果を作る重複だと説明できる。
2. 削除後の責務の持ち主が1つに決まり、入口と出口がテストされる。
3. 失敗時の縮退、再試行、世代ガード、後片付け、診断のいずれも失わない。
4. ログのイベント名・field・schema、保存データ、公開APIとの互換性を壊さない。
5. コメントを削除する場合は、コードを言い換えただけで、設計理由・運用前提・失敗時の意図を
   何も含まないことを確認する。

### 削除してはいけないもの

- 安全側のフォールバック、再試行、世代ガード、部分失敗後の後片付け
- 「失敗が見えない」を防ぐ診断、常設表示、drop計数
- 設計理由を記録したコメント
- 名前や処理が似ているだけで、失敗条件・時間軸・持ち主が違う処理
- テストを通すためだけのコード短縮、1行化、抽象化

行を別ファイルへ移しただけのものは「削除」と数えない。行数の減少は成果の証拠ではなく、
責務の移動または重複除去の結果としてのみ扱う。

## 7. 各PRの合格条件

1. **振る舞い保存表の全項目が前後で一致する。** とくに処理順、timeout、非同期処理、
   世代確認、縮退、後片付け、診断が同じであること。
2. `flutter test` が通り、既存テストの期待値・assertion・対象ケースを弱めていない。
   import先やテスト用組み立ての機械的変更は許すが、期待値変更は原則として中止条件にする。
3. `dart analyze lib test tool` がクリーン（`tool` を必ず含める。CLAUDE.md 参照）。
4. `bash tool/review/smoke_check.sh` が通る。特に診断イベントカタログと
   鮮度階層（3s / 6s / 30s、停止送信10s）。
5. [quick_review](review_guide/quick_review.md) のF1〜F6について、影響あり・なし・
   実機でのみ確認可能を表にし、影響ありの経路にはテスト根拠を付ける。
6. 診断イベント、保存データ、公開APIの互換性を確認する。意図的な変更が必要なら、
   リファクタPRから分離する。
7. 切り出しで下がった指標だけラチェットを下げる。新しい停止上限は、原則として
   **旧停止上限から実際の減少分を引く**。これにより小変更の余白は残すが、
   切り出した分の余白をもう一度使って元の大きさへ戻せない。
8. 不変条件表を更新し、そのPRで「未保護 / 部分的」がどう動いたかを、直接証明できた
   範囲だけ書く。状態が動かなかった場合も正直に書く。
9. 主指標と削除台帳をPR本文に書く。行数だけを成果として書かない。
10. 1PRを単独でrevertでき、新機能・不具合修正・設定値変更を混ぜていない。

### マージと現場投入を分ける

CI成功は、実機・バックグラウンド・2台間共有・水上で機能が失われていない証明ではない。
PR1〜3はCIとレビューを満たせば個別にマージできるが、**PR2またはPR3を含む版を現場投入する前**に、
人が次を1回確認する。

1. 実機で航行を開始・終了でき、画面更新と航行記録が続く。
2. 音声が鳴る設定で警告音を確認し、画面のsystem fault表示も確認する。
3. 可能なら2台で、互いの位置が表示・更新されることを確認する。
4. バックグラウンド復帰後にGPS、警告、共有が再開することを確認する。

これは将来の実装時に必要な人の確認であり、計画文書を更新する今回の作業では不要である。

## 8. 中止条件

次のいずれかに当たったら、そのPRを中止して報告する。

- 振る舞い不変に収まらないことが分かった（縮退の順序、後片付けの順序、
  警告の出方のいずれかが変わる）。
- 既存テストの期待値・assertion・対象ケースを弱めないと通らない。
- 切り出し先が結局同じ153スロットを参照し、呼び出し側が薄くならない。
- 1つのPRで複数の責務、設定値変更、不具合修正まで必要になった。
- 削除する処理がフォールバック・診断・後片付けではないと証明できない。
- 「現在どう動くか」と「本来どう動くべきか」が食い違い、利用者の判断が必要になった。

## 9. 進め方

新機能開発は止めない。ただし PR1〜3 は**振る舞い不変の専用PR**として立て、
現地の不具合修正とは混ぜない。1PRずつ、前のPRがマージされてから次に入る。
各PRの後に、主指標、不変条件表、F1〜F6、削除台帳、レビュー負荷を見て、次へ進む利益が
残っているかを判断する。PR3まで完走すること自体を目標にせず、危険が利益を上回れば止める。
