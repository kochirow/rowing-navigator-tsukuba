# アプリレビュー手順(動くことの監査)

**この文書がレビュー手順の本体である。** Claude Code は `.claude/skills/full-app-review/SKILL.md`
から、codex は `AGENTS.md` からここへ来る。どちらのエージェントも同じ手順で作業する。

## 0. 最優先の問い

**「現場で機能が動かない事態が起きないか」。**

このアプリで失敗とは、コードが汚いことではなく、次が起きることである。

1. **鳴るべき警告が鳴らない**
2. **位置共有が止まり、自艇が他艇から見えなくなる**
3. **他艇が画面と衝突評価から消える**
4. **航行が始まらない、途中で止まる**
5. **落ちる・固まる・電池が尽きる**
6. **上の失敗が誰にも見えないまま走り続ける**

レビューの価値は、この6つのどれかを1つでも減らせたかで測る。
指摘の数ではない。**「動く証拠を1つ増やす」か「壊れ方を1つ塞ぐ」かのどちらかになっていない指摘は、S3 に落とす。**

## 1. モードと検証範囲

- **差分・限定レビュー**：指定差分と影響経路を対象とし、関連テスト・解析で検証する。全体用smoke checkやF1〜F6全項目は必須ではない。
- **動作確認（機能監査の既定）**：[quick_review.md](quick_review.md) のF1〜F6から対象に関係する項目を選ぶ。
- **総合レビュー**：明示的な全体監査、または広範な安全・設計変更の確認は、§3と [full_review_passes.md](full_review_passes.md) を使う。

重大な問題を見つけたら直ちに報告し、その原因・影響経路の確認は依頼範囲で続ける。総合監査への大幅な範囲拡張だけ確認し、その回答を待つ間も独立した確認を進める。

### 検証の選び方

変更と依頼範囲に見合う検証を使う。同じ内容・環境で成功済みのローカル検証、または対象コミットの成功CIを再利用できる。変更・失敗・未解決の懸念がある場合に該当部分を再実行する。

| 対象 | 検証 |
| --- | --- |
| 文書のみ | 差分・参照確認。アプリ全テスト不要 |
| 限定されたコード | 関連テストと `dart analyze lib test tool` |
| 安全・共有基盤・認証・Rules・設定の横断変更、影響不明 | 全テストと該当するRules/データ等の検証 |
| 同一状態を成功CIが検証済み | CI結果を引用し、未検証の挙動に集中 |
| CI結果が取得できない | 未確認と明記。依頼・影響範囲で検証を選び、取得不能だけを全テストの理由にしない |

動作確認・総合監査の共通チェックには `bash tool/review/smoke_check.sh` を使える。
`--base <ref>` でコミット済み差分も含める。比較元なしのautoは未コミット差分だけを分類するため、変更レビューでは比較元を指定する。
安全・認証・共有の契約に影響しないと確認できた限定コードの対象テストは `--targeted <test-path> ...` で明示する。対象を絞れないコード変更は全テストへ進む。
`--static` は共通静的チェック、`--analyze` は解析と診断カタログ、`--full` は全解析・全テストを実行する。省略した検証を実施済みとしない。

レビューだけの依頼ではアプリのビルド・起動・署名・配布を行わない。許可済みのローカルreplayは開始を知らせて実行し、再承認を待たない。本番操作・実機操作はそれぞれの権限に従う。

## 2. 共通のルール

- **レビューのみの依頼では指摘に留める。** 修正も依頼されている場合は、所見と対象状態を記録してから修正し、影響した判定を再確認する。
- **根拠のない OK を書かない。** 判定には `ファイル:行` か実行結果を添える。
  判断できないものは「要確認」であって OK ではない。
- **見ていないものは「見ていない」と書く。** 薄く見て OK と書くのが最も悪い。
  次のレビューがそこを「確認済み」として飛ばす。
- **読んだだけで確定しない。** 数値検算・テスト・replay・実機ログのどれかで裏を取り、
  取れなかったものは証拠の格付けを「未確認」にする
  ([verification.md](verification.md))。
- **自己反証する。** 指摘を確定する前に「これを否定する材料はどこにあるか」を探す。
  過去のレビューでは、この工程で仮説が3件覆った。**訂正は成果であり、失敗ではない。**
- **CI が担保している層は再確認しない。** `dart format` / `flutter analyze` / `flutter test` /
  hazardハッシュ / 生成allowlist / 音圧 は `.github/workflows/ci.yml` が守っている。
  CI が見られない層(運用時の振る舞い・境界条件・移行・現場の失敗)に集中する。
- **`flutter analyze` はこの作業パスでは必ずクラッシュする。** `dart analyze lib test tool` を使う。
- **CI が緑であることは、実機・本番Rules・水上での安全の証拠にならない**(AGENTS.md)。
  報告には必ず「なお確認していないこと」を書く。

## 3. 総合版の進め方

### 3.1 開始手順

1. `bash tool/review/inventory.sh <前回レビューのSHAか日付>` で規模・テスト有無・変更範囲を取る。
2. `CLAUDE.md`、`docs/DESIGN_PRINCIPLES.md`、`AGENTS.md` の適用規範を確認する。同じ作業内で確認済みかつ変更されていない箇所の再読は不要。
3. 前回の指摘を回収する。`docs/review/`・`docs/reviews/`・`safety_reviews/` の最新報告から
   **未解決の S1/S2 と「証明されていないこと」を一覧化**し、再発・劣化の確認対象に入れる。
4. `docs/review/YYYY-MM-DD_全体レビュー/00_計画.md` を
   [report_templates.md](report_templates.md) の形で作る。
   パス割りは [full_review_passes.md](full_review_passes.md) を規模の変化に合わせて調整する。
5. 以降パスごとに §3.2 を繰り返し、依頼された範囲の完了まで継続する。パス数だけを理由に終了しない。実際の障害・ユーザー指定の区切り・実行上の制限がある場合に中断し、再開点を残す。
   `00_計画.md` の状態表が進捗の唯一の真実で、再開はここを読むところから始める。

### 3.2 1パスの手順

1. **対象ファイルを全行読む。** 抜粋読みはしない。境界条件は抜粋の外にある。
   読み切れない規模ならパスを分割する(黙って一部読みで終えない)。
2. **照合する規範を先に列挙する。** 設計原則・不変条件(CLAUDE.md の13項目)・設定値の根拠を、
   コードを読む前に書き出す。後から辻褄を合わせない。
3. **観点を当てる。** [viewpoints.md](viewpoints.md) の A〜N から、パス割り表が指定する
   主観点 ＋ 全パス共通の **B(警告漏れ)・D(不変条件)・G(縮退運転)・N(制御動作)**。
4. **裏を取る**(§2)。5. **自己反証する**(§2)。
6. **分類して記録する。** 重大度 S1/S2/S3、FN/FP、証拠の格付け。
   「テストが無い」は指摘とは別枠に書く。
7. **持ち越しを書く。** 他パスを見ないと判断できない疑問を明記し、該当パスで回収する。
8. `00_計画.md` の状態表と指摘件数を更新する。

### 3.3 重大度

| 重大度 | 意味 |
| --- | --- |
| **S1** | §0 の6つが実際に起きる。鳴らない・止まる・消える・落ちる・見えない |
| **S2** | 条件が重なると S1 に寄与する。誤報側の問題はここが上限(ただし**鳴り続けて形骸化する**ものは S1) |
| **S3** | 保守性・一貫性・死んだコード・根拠コメントの欠落 |

| 格付け | 書いてよい根拠 |
| --- | --- |
| **確認済** | 該当行を読んだ + 数値検算・テスト実行・ログ・replay のいずれかで確かめた |
| **推定** | コードからの論理的帰結。実行や観測では確かめていない |
| **未確認** | 仮説。実機・本番Rules・水上でしか確かめられないものを含む |

### 3.4 総合版の完了条件

1. `00_計画.md` の全パスに到達度(**全行読了 / 一部 / 未読**)と完了日がある。
   中断時は未完了範囲と理由を先頭に書き、「総合レビュー完了」とは区別する。
2. 各パス記録に、規範の列挙・観点ごとの判定+根拠・持ち越しがある。根拠のない OK が1つもない。
3. すべての NG に、再現条件(入力→誤った出力)・FN/FP・重大度・格付け・修正の方向がある。
4. P05 が衝突警告の安全レビュー(`.claude/skills/collision-safety-review/SKILL.md`)の
   完了条件を満たしている。**この文書は skill 形式だが中身は手順書なので、codex はそのまま読んで従う。**
5. 前回レビューの未解決 S1/S2 を、再発・劣化・解消のいずれかで判定した表がある。
6. P16 で F1〜F6(軽量版の壊れ方)を通しで確認し、同時に鳴りうる警告の競合表を作った。
7. P17 で重複・矛盾・訂正を整理し、優先順位と実装順序(依存関係)を出した。
8. `99_最終報告と実装計画.md` に「なお証明されていないこと」「利用者(人)がやること」がある。
9. S1 が0件、または各 S1 に対処方針(直す/直さない理由)が明記されている。
