# 観点 A〜N

各パスでは、パス割り表が指定する**主観点**に加えて、
**B(警告漏れ)・D(不変条件)・G(縮退運転)・N(制御動作)を必ず**当てる。
この4つが「現場で機能が動くか」に直結する軸である。
判定は OK / NG / 要確認 の3値で、根拠は `ファイル:行` か実行結果。

**指摘は「壊れ方」に結び付ける。** その指摘が実現すると、軽量版の F1〜F6
(鳴らない / 共有が止まる / 他艇が消える / 航行が止まる / 落ちる / 失敗が見えない)の
どれになるのかを書く。どれにもならないなら S3 である。

---

## A. 設計原則との整合

**判定基準:** その値・分岐・仕様が `docs/DESIGN_PRINCIPLES.md` 第1章の運用前提から導けるか。
導けないなら、前提が書かれていないか、前提が変わったのに値が追随していない。

- 川幅40〜50m(狭所35m)・右側通行の片側1レーン・カーブ間隔200〜700m・同時2〜12艇・
  コーチ艇なし・休憩は橋の下か航路の端。この前提で成立するか。
- 霞ヶ浦(開水面)では成立しない前提を、桜川の値で押し通していないか(1.2b)。
  新しい水域の値が 1.2c の記述より先に入っていないか。
- 「安全のため」を理由に使い方の自由度を削っていないか(原則2)。
- 設定値に前提が書かれているか(原則7)。根拠コメントの無い定数は S3。

## B. 警告漏れ(false negative)

**判定基準:** 境界条件・データ欠損・縮退経路で、鳴るべき警告が消えないか。

- データ欠損が「脅威なし」に落ちる経路(原則6・不変条件3)。
  `try/catch` で握りつぶす、NaN が比較を全部 false にする、`null` を安全側に読み替える。
- 抑制(静音・降格・デバウンス・ヒステリシス)が、消してはいけない対象まで消していないか。
  低速静音・安定停止抑制・陸上判定・band cap・lv cap の**対象外リスト**が実装と一致するか。
- 鮮度・タイムアウトで艇が評価対象から落ちる窓が空かないか(不変条件2の階層)。
- 詳細な監査は `collision-safety-review` skill のチェックリスト A〜H に委譲する。

## C. 過剰警告・形骸化(false positive)

**判定基準:** 正常な運用で鳴らないか。**正常な運用で鳴る警告は不具合である**(原則4)。

正常な運用とは: 岸から数mを走る / 橋の下や航路の端で休む / 対向艇と十数mですれ違う /
折り返しで回頭する / 岸に寄ってコーチの指示を受ける / 桟橋に係留する。

- 鳴り続ける警告・毎周回鳴る警告は、S2 ではなく **S1 に上げてよい**(形骸化は警告の喪失)。
- 反復間隔・再武装条件が、同じ対象に何度も鳴らせる形になっていないか。
- 「重なっている(currentOverlap)」を無条件に連続音へ上げていないか。

## D. 不変条件(全パス共通)

`CLAUDE.md`「重要な不変条件」13項目のうち、そのパスに該当するものを**明示的に列挙してから**
実コードへ突き合わせる。特に落ちやすいもの:

- (1) リスク評価は送信間隔と独立に毎秒実行される。
- (2) 鮮度の階層 `freshUntil`(3s) < 予測TTL(6s) < stale(30s)、`sendIntervalStoppedSec`(10s) < 30s。
- (3) データ欠損 ≠ 安全。`unusable` の3秒打ち切りには必ず system fault が同時に立つ。
- (6) 地図描画は安全判定用の拡張を反映しない。
- (7) `distanceMeters` は符号付き。0へ潰さない。
- (8) `boundingRadius` は領域の実寸を下回らない。
- (12)(13) 他艇の警告状態・1ストロークの波形は**記録/表示専用**。安全経路と位置payloadへ混ぜない。
- Wakelock を呼ぶのは `use_screen_wakelock.dart` だけ。監視中は保持しない。

## E. 数値・幾何・単位

- 単位([m]/[s]/[m/s]/度/ラジアン)、int と double、緯度経度と平面座標の取り違え。
- 緯度経度をそのまま平面として扱ってよいのは交差判定まで。**距離・角度**へ流用していないか。
- 特異点: 速度0、極小 dt、真北またぎ、経度180度、極付近、自己交差・重複頂点・頂点数<3。
- 浮動小数の完全一致比較、`==0.0`、NaN/Infinity の伝播。
- epsilon の次元(長さの epsilon を面積・角度へ使い回していないか)。

## F. 状態・並行性・ライフサイクル

- `SafetySnapshot` の単一writerが保たれているか。他所から状態を書いていないか。
- `await` をまたいだ状態の陳腐化、再入、キャンセルされたはずの処理の後着。
- Stream購読・Timer・AnimationController・onDisconnect の解放漏れ。画面遷移と航行の寿命の食い違い。
- 音声要求の直列キュー(並行実行すると段階が上がる瞬間に古い要求が新しい音を止める)。
- アプリのバックグラウンド遷移・OS割込み(電話・他アプリの音声)・端末スリープからの復帰。
- iOS と Android の差(バックグラウンド位置、オーディオセッション、権限の粒度)。

## G. 縮退運転(原則1)

**判定基準:** 能力が欠けたときに、止まらず継続し、かつ**明示的に警告する**か。

- 音声・危険区域データ・通信・中心線・センサーのいずれが欠けても航行を開始・継続できるか
  (位置情報権限だけが例外)。
- 欠けたことが `SafetyRunMode` / system fault / バッジのどれで見えるか。
  **黙って劣化する経路は、それ自体が S2 以上。**
- フォールバックが安全側か。時間軸や予測地平を失っていないか。失ったことがログに残るか。

## H. テスト網羅と CI の守備範囲

- 指摘した境界条件に単体テストがあるか。無いものは「テスト不足」欄へ(指摘とは別枠)。
- CI が守っているのはどこまでか。`ci.yml` のジョブと、そこで**検出できない**変更を言語化する。
- 実データ(`assets/data/sakuragawa_obstacles.json`)を使う統合テストが生きているか。
  設定値の意図と実効値の乖離を検出する唯一の手段である。
- テストが「実装のコピー」になっていないか(同じ式で期待値を作ると恒真になる)。

## I. UI・実操作

**判定基準:** 直射日光・濡れた手・グローブ・揺れる艇上・一瞬のチラ見で成立するか。

- 数字は大型+等幅、タッチターゲット48dp以上、アイコンには日本語小ラベル、最小12px。
- 色・角丸・余白はデザイントークン経由(`context.colors` / `context.dimens`)。
  警告のしきい値・時間は `lib/config/`。両テーマ(明/暗)で確認したか。
- 計器は画面上部40%まで。`SafetyBanner` と音声エラーだけがこの制限の外。
- 状態はトースト禁止・常設バッジへ。メニュー項目は状況で消さず無効表示にする。
- 航行終了・記録削除は確認ダイアログ必須。
- **表示専用のものが警告に昇格していないか**(レーン横断位置・波形・他艇の警告状態)。

## J. プライバシー・通信コスト・Rules

- 送信データの最小性。`live_positions` は全艇が全艇ぶんを購読するので、1バイトが艇数の二乗で効く。
- `stroke_traces` のような重いものが `live_positions` へ混ざっていないか(不変条件13)。
- `database.rules.json` / `firestore.rules` の `.validate` とクライアントの生成値が矛盾しないか。
  **拒否されると書き込み全体が落ちる**(位置＋プロファイルの atomic update)。
- 送信間隔の下限がサーバー到着時刻基準であることと、クライアントの発火間隔の余裕。
- 個人情報・端末ログ・実機ログが成果物へ混ざらないこと。

## K. 保守性

- 設定値のハードコード(`lib/config/` へ出ていないもの)。
- 同じ問題への独立2実装、死んだコード、未使用アセット、参照されない public API。
- 責務の漏れ出し(UI が安全判定をしている、service が表示都合を持っている)。
- コメントと実装の乖離。**コメントが古い方が実装より危険**(次の変更の根拠にされる)。

## L. 実機ログ・観測との乖離

**判定基準:** コードから期待される振る舞いが、実機ログに実際に現れているか。
この観点が 2026-08-12 のレビューで最も多くの新事実を出した。

- 実機ログ(`../実機テストログデータ/`)と `tool/replay_*.dart` を突き合わせる。
- 「起こりうる」と書く前に、ログに**起きた形跡があるか**を数える。頻度が分かれば重大度が変わる。
- ログに出ていない = 起きていない、ではない。**その事象がログに出る経路があるか**を先に確認する。
  記録されない失敗は、レビューでも運用でも見えない。それ自体が指摘になる。
- 端末ごとの差(共有できた端末/できなかった端末)を比べる。全期間ゼロの入力は強い手がかり。

## M. リリースと移行

**判定基準:** 版が混ざった状態・データが更新された状態で、安全機能が成立するか。
過去唯一の S1 はここから出た(アプリ更新中に版違いの艇が互いの地図と警告から消える)。

- `appVersion` / `protocolVersion` / hazard profile version / Rules の版が、
  **どれか1つでも一致しないと通信が成立しない**構造になっていないか。
- 更新の途中(片方だけ新版)で何が起きるか。全艇が同時に更新することはない。
- profile version を上げたときに失効するもの(座標校正値)と、再デプロイが要るもの(Rules)。
- 端末内保存データ(セッション・設定・練習ログ)の後方互換。読めない古いデータで落ちないか。
- 生成物(`tool/generate_hazard_constants.dart`・ハッシュ)と手編集データの整合。

## N. 制御動作(全パス共通)

安全機能を「ファイルの集合」ではなく「制御の連鎖」として見る観点。
**GPS → 推定 → 評価 → 提示 → 音/表示 → 漕手の回避行動** の各段について、次の4種を問う。
(system-theoretic な危険分析の分類を、このアプリの語彙に置き換えたもの)

| 種別 | このアプリでの問い |
| --- | --- |
| **出ない** | 必要な警告・表示・送信が出ない条件は何か。上流の欠損・抑制・例外で消えるか |
| **誤って出る** | 危険でないのに出る条件は何か(観点C)。出た結果、漕手が無用な回避をして別の危険に近づかないか |
| **遅い/早い** | 予測地平・予告13秒、本警告10秒、データ不能時の物理警告上限3秒などの非対称が、回避操作に要する時間と合っているか。1秒周期の粒度で段階が飛ばないか |
| **続きすぎ/止まりすぎ** | 鳴りっぱなしで他の警告を覆い隠さないか。早く止まって再武装せず、再接近で二度と鳴らない状態にならないか |

さらに **漕手が受け取れるか** を問う。両手はオールで塞がり、端末は艇に固定され、
背後は見えない。読み上げは同時に2本鳴らせない。**同時に鳴りうる警告の組み合わせを列挙し、
どれが負けるか**を確認する(負けてよいのは、より切迫した衝突警告に負けるときだけ)。
