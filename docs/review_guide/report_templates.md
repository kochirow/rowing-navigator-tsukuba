# 記録の雛形

- 軽量版(動作確認レビュー): `docs/review/YYYY-MM-DD_動作確認レビュー.md` の**1ファイル**。
- 総合版: `docs/review/YYYY-MM-DD_全体レビュー/` に 計画 + 1パス1ファイル + 最終報告。

**過去のレビューを上書きしない**(日付で分ける)。

---

# 全体レビュー計画(YYYY-MM-DD 開始)

## 目的
<何のためのレビューか。リリース前 / 大きな機能追加後 / 実機テスト前後 など>

## 対象
現在のワーキングツリー全体(HEAD との差分ではない)。レビュー対象HEAD: <SHA>(<ブランチ>)。
確認していないもの: ビルド / 実機 / 本番Rules / 水上。

## 運用ルール
- 指摘のみ。修正はしない。優先度確定後に別作業で直す。

## 進捗
| パス | 完了日 | 到達度 | S1 | S2 | S3 | テスト不足 |

## 99_最終報告と実装計画.md

```markdown
# 最終報告と実装計画

作成日: YYYY-MM-DD / 対象HEAD: <SHA>

## 0. このレビューの到達度(先に明示する)
| 段 | パス | 到達度 |
指摘が少ない層は「問題が少ない」と「見ていない」の両方がありうる。
未完了分は第N章に一覧化する。

## 1. 全指摘一覧(重大度順)
S1 / S2 / S3 の表。各行に出典パスへのリンクと証拠の格付け。

## 2. 重複・矛盾・訂正の整理
同一の指摘の統合、パス間で結論が変わったもの、レビュー中に撤回したもの。

## 3. 優先順位と実装順序
依存関係を明示する(A を直さないと B の修正が別の問題を生む、など)。
「直さない」と決めたものは、その理由も書く。

## 4. なお証明されていないこと
実機・本番Rules・水上・長時間運用でしか確かめられないもの。
レビューで見ていない領域。ログに記録が無くて判定できなかったもの。

## 5. 利用者(人)がやること
Firebase Rules の本番反映、署名、ストア提出、実機・水上での確認など。
```

## 書き方の約束

- **誇張しない。** 「重大な欠陥」「必ず起きる」は、それを示す証拠があるときだけ。
  無いときは「起こりうる」「頻度は未確認」と書く。
- **撤回を隠さない。** 誤りが分かったら、結論だけ差し替えるのではなく経緯を残す。
- **人が判断する材料を書く。** 「どうすべきか」だけでなく「何と引き換えになるか」。
- 個人の航跡・端末ログ・API キーを本文へ貼らない。集計値と件数までにする。
