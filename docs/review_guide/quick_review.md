# 軽量版: 動作確認レビュー(F1〜F6)

**問い: 「この状態でリリースして、現場で機能が動かない事態が起きないか」**

総合版がファイル単位で網羅するのに対し、軽量版は**壊れ方(症状)から辿る**。
1〜2セッションで終える。実機テストの前後、機能追加の後、リリース前の点検に使う。

記録は1ファイル: `docs/review/YYYY-MM-DD_動作確認レビュー.md`。

## 手順

1. `bash tool/review/smoke_check.sh` を実行する
   (鮮度階層・音声アセット・無言catch・生成物整合)。**引数はいらない。**
   未コミットの変更があるか HEAD の CI が緑でないときは解析とテスト全実行まで自動で走り
   (約90〜110秒)、CI が緑のコミットなら静的のみ(1.3秒)で済ませる。
   **NG が出たらそこを先に潰す。**
2. 直前の変更範囲を確認する(`git log --oneline -20`、`git diff --stat <前回レビュー>..HEAD -- lib`)。
   変更が F1〜F6 のどれに触れるかを最初に決める。**触れていない F も、確認は省略するが「省略した」と書く。**
3. F1〜F6 を順に辿る。各 F は「症状 → 消える箇所 → 確認方法」で書いてある。
   判定は OK / NG / 要確認 + 根拠(`ファイル:行` か実行結果)。
4. 実機ログがあれば当てる(`verification.md` の replay 3種)。「起こりうる」で止めず、件数を数える。
5. S1 相当(警告が鳴らない・共有が止まる・他艇が消える・航行が止まる)が1件でも出たら、
   **その場で報告し、総合版のパスへ切り替えるかを利用者に確認する。**

## やらないこと

全行読了・UI の細部・保守性・命名・死んだコードは軽量版の対象外。
**「見ていない」と書けば足りる。薄く見て OK と書くのが最も悪い。**

---

## F1. 鳴るべき警告が鳴らない

**症状:** 他艇・橋脚・岸・カーブが近いのに、音も表示も出ない。または表示だけで音が出ない。

**経路:** GPS入力 → 品質選別 → Kalman推定 → リスク評価 → 提示ポリシー → 状態機械 → 音声再生

| 消える箇所 | 確認 |
| --- | --- |
| 測位が落ちる(`gps_position_filter` の精度・速度飛び・時刻) | 1点目の粗い測位が後続を長時間はじく形になっていないか(2026-08-12 の P1 と同種) |
| `AlertDataQuality.unusable` の3秒打ち切り | 打ち切りと**同時に** system fault が必ず立つか(不変条件3) |
| 他艇が評価に入っていない | → **F3 へ**。他艇警告は受信できた艇からしか作れない |
| 提示段階の抑制 | 陸上判定 / 低速静音(分速100m未満) / 安定停止抑制(0.4m/s・5秒) / `bandCappedCategories` / `audibleProximityCategories` の**対象外リスト**が意図どおりか |
| 音声チャンネルの競合 | 読み上げは同時に2本鳴らない。**同時に鳴りうる組み合わせを列挙し、どれが負けるかを表にする**。負けてよいのはより切迫した衝突警告に対してだけ |
| 再生そのもの | 直列キューの詰まり、OS割込み(通話・他アプリ)からの復帰、Bluetooth 経路の切替、サイレントスイッチ(`respectSilence: false`)、アセットのロード失敗 |
| 反復・再武装 | 一度鳴って解除された後、再接近で鳴り直すか(退出後5秒・逆走60秒の再武装) |

**確認方法:** 実機ログがあれば `flutter test tool/replay_field_log.dart --dart-define=LOG_DIR=<診断フォルダ>` で
1練習あたりの発報回数を出す(**ログの長さに比例して時間がかかるので、実行前に一声かける**)。**0回**が並ぶなら、鳴らない側の不具合を疑う根拠になる。

## F2. 位置共有が止まる(自艇が他艇から見えなくなる)

**症状:** 自分の画面は正常なのに、他の艇からは自艇が見えない/止まって見える。

| 消える箇所 | 確認 |
| --- | --- |
| 書き込みが Rules で拒否される | `database.rules.json` の `.validate`。必須フィールド、値域、**送信間隔の下限(1900ms・サーバ到着時刻基準)**。拒否は位置とプロファイルの atomic update **全体**に及ぶ |
| 送信の初期設定が失敗したまま | `clear` + `onDisconnect` 登録の失敗が**再試行されるか**。送信本体は無限再試行なのに setup が0回、という非対称が過去にあった |
| 認証・所属・App Check | `auth.uid == boatId`、teamId、招待状態。端末ごとに UID が違うのは正常 |
| `onDisconnect` の誤発火 | 一時的な切断で自艇のレコードが消え、他艇から即座に見えなくなっていないか |
| 送信間隔の適応 | 他艇を受信できない間に10秒送信へ落ちていないか(`receiveUnavailable` は2秒維持)。落ちると予測TTL(6秒)を超え、他艇の評価から周期的に消える |
| 失敗が見えるか | `sharing_capability_monitor` の `publishSetupComplete` / `sinceLastPublishAck` / `authorization` がバッジに出るか。**表示のみで音は足さない** |

**確認方法:** `firebase_rules_test/` の Emulator テスト。実機ログ `events.jsonl` の
`permission-denied` 件数と、拒否された工程(setup / 位置 / プロファイル)の内訳。

## F3. 他艇が画面と評価から消える

**症状:** 他の艇が地図に出ない、出ても止まっている、途中で消える。他艇警告が原理的に発生しない。

| 消える箇所 | 確認 |
| --- | --- |
| 受信 payload の検証で落ちる | `remote_boat_message.tryParse` の失敗理由。**版の不一致を失敗理由にしていないか**(`protocol_config`)。過去に `appVersion` の厳格一致で「更新中の艇が互いに消える」S1 があり、いまは互換判断を `protocolVersion` だけにして解消済み。**毎回ここが復活していないかを見る** |
| 鮮度で落ちる | `freshUntil`(3s) < `boatPredictionTimeoutSeconds`(6s) < `boatStaleTimeoutSeconds`(30s)、`sendIntervalStoppedSec`(10s) < 30s。`smoke_check.sh` の3番が自動判定する |
| 時刻ずれで落ちる | 相手端末の時計ずれ・`serverUpdatedAt:futureTimestamp` による拒否(2026-08-05 に693件の前例)。サーバ時刻オフセットを取得できているか |
| 購読が無通知で止まる | `resilient_stream_supervisor` の `silenceTimeout` と再購読。**再購読しすぎ**(251回の前例)も暖機を失って悪化させる |
| 名簿・所属 | roster が取れないと誰も表示されない。取れないことが表示に出るか |
| 描画側で消える | `map_render_update_policy` の更新間引き、色(`boat_palette`)、ズーム、レイヤの `zIndex` |

**確認方法:** `other_boat_track_store` のテスト、`events.jsonl` の拒否イベント件数。
**「他艇0隻」は正常でもあり得る**(最初の出艇・全艇上陸後)。
0隻そのものではなく、**受信できる能力を確認できない状態**だけを異常として扱う(原則6)。

## F4. 航行が始まらない・途中で止まる

**症状:** 開始ボタンが効かない、画面が更新されない、警告も表示も凍る。

| 消える箇所 | 確認 |
| --- | --- |
| 開始のブロック | **不変条件5。音声・危険区域データ・通信のどれが欠けても開始できること。**位置情報権限だけが例外。追加の前提条件を足していないか |
| 権限とOS設定 | 「使用中のみ」「常に許可」、正確な位置のオフ、バックグラウンド遷移、iOS の位置配信の絞り |
| 評価が止まる | `safety_evaluation_liveness`(1秒タイマー停止と評価未完了を区別)。`pipeline_unresponsive` がバナー・能力バッジ・`runMode` に出て、物理警告の音声を奪わないか |
| 例外で経路が死ぬ | `smoke_check.sh` の5番(無言catch候補)を1件ずつ判定。**幾何計算の例外がフォールバックで時間軸を失っていないか** |
| Wakelock | 呼ぶのは `use_screen_wakelock.dart` だけ。航行中のみ保持、監視中は保持しない。画面が消えたら漕手は復帰させられない |
| 縮退の告知 | 止まったのではなく縮退したことが `SafetyRunMode` とバッジで見えるか |

## F5. 落ちる・固まる・電池が尽きる

| 見るところ | 確認 |
| --- | --- |
| 例外 | parse・幾何・platform channel。release ビルドで診断に残るか |
| 蓄積 | 航跡・練習ログ・波形リングの上限。長時間(2時間)航行での増加 |
| 描画負荷 | 地図更新の間引き、ポリゴン枚数(岸は約310枚)、`static_obstacle_index` で周辺に絞れているか |
| 通信量 | `live_positions` は12艇が12艇ぶんを購読する(144倍)。重いものを混ぜていないか(不変条件13) |
| 電池 | Wakelock の保持範囲、送信頻度、センサー(SPM)のオン時間 |

## F6. 失敗が誰にも見えない(横断)

**F1〜F5 で見つけた失敗経路のすべてについて問う。**

- その失敗は**診断イベントとして記録されるか**(`smoke_check.sh` の6番=カタログ整合)。
- **利用者の画面に出るか**(バッジ・バナー・`SafetyRunMode`)。トーストではなく常設表示か。
- 音を足すべきか。**system faultは全カテゴリ表示のみ。**漕ぎながら対処できない
  情報を読み上げると、本当に鳴るべき物理的な衝突警告を覆い隠す。
- 記録も表示も無い失敗は、**それ自体を NG とする**。運用でもレビューでも二度と見つからない。
  過去に1台が118分間「受信できない」まま走り、`stream_error` は0件で、乗員には何も出なかった。

---

## 完了条件

1. `smoke_check.sh` を実行し、NG がゼロ、または各 NG に説明が付いている。
2. F1〜F6 のすべてに判定(OK / NG / 要確認 / **今回は見ていない**)と根拠がある。
3. NG には、症状・再現条件・利用者から見えるか・修正の方向が付いている。
4. 実機ログを当てたか、当てられなかった理由が書いてある。
5. 「なお確認していないこと」(実機・本番Rules・水上・長時間)が明記されている。
6. S1 相当があれば、総合版へ切り替えるかの判断を利用者に渡している。
