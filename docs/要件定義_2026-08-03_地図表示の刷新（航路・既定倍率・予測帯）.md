## 1. 背景

### 1.1 いま何が起きているか

コードを調べた結果、次の3点が分かっている。

| 事実 | 根拠 |
| --- | --- |
| 航路レーンのデータは**既に6本ある**（往路/復路 × 霞ヶ浦・桜川河口・桜川上流） | `assets/data/sakuragawa_obstacles.json` の `navigableWaters` |
| そのデータは**地図に一度も描かれていない**。読み込み関数 `loadNavigableWaters()` は定義されているだけで、UI から呼ばれていない | [preset_obstacle_service.dart:356](../lib/services/preset_obstacle_service.dart:356) を参照している箇所が `lib/` に無い |
| 既定倍率は航行中・監視中とも `18.0` の固定値 | [home_map_screen.dart:197](../lib/screens/home_map_screen.dart:197) |
| 地図ポリゴンに `zIndex` を指定している箇所が**1つも無い**（重なり順が実装依存） | `lib/` 全体で `zIndex` の指定なし |

つまり航路表示は「新しく作る」のではなく「**既にあるデータを出す**」作業である。

### 1.2 なぜ倍率18では足りないか

桜川（北緯36.06度）・iPhone 縦持ち（論理幅390pt）での実測換算。

| zoom | 1px の実距離 | 画面幅の実距離 | 川幅40〜50mの見え方 |
| --- | --- | --- | --- |
| 18（現状） | 0.483 m | **188 m** | 川は画面の約1/4。周囲の田畑が主役 |
| **19（採用）** | 0.241 m | **94 m** | 川が画面の約半分。両岸＋対向艇が同時に入る |
| 19.5 | 0.171 m | 67 m | 川で画面が埋まり、前方の見通しが143mまで縮む |
| 20 | 0.121 m | 47 m | 川幅ちょうど。**両岸が見切れる**ので不採用 |

19 を選ぶ理由は2つ。

1. **川幅の約2倍が入る。** 「自分の岸」と「対向艇の岸」が同時に見える最小の倍率。
   右側通行の判断に必要な情報がちょうど収まる。
2. **予測が届く範囲より広い。** 予測地平は `defaultWarningTimeSeconds` = 10秒。
   5m/s で 50m 先までしか予測しない。zoom 19 の縦方向は 203m 見えるので、
   「予測が届く先が画面外」にはならない。

### 1.3 なぜ予測帯の簡素化が倍率とセットなのか

いまは1艇につき **最大24サンプル × 2枚 = 最大48枚**のポリゴンを重ねて描いている
（[home_map_screen.dart:788-833](../lib/screens/home_map_screen.dart:788)）。
zoom 18 では 50m の掃引帯が画面縦の 1/4 で済んでいたが、**zoom 19 では約 1/2 を覆う**。
中身は同じ六角形の平行移動の繰り返しなので、情報量は増えないまま画面だけが埋まる。

## 2. 変更しないこと（この作業の境界）

**以下に1つでも触れたら、その変更は誤りである。**

1. **安全判定に一切影響を与えない。** 触ってよいのは「地図に何をどう描くか」だけ。
   `collision_risk_evaluator_service` / `ship_domain_service` / `safety_orchestrator` /
   `alert_state_machine` / `lib/config/` の警告関連設定値には手を入れない。
2. **`ChannelLane`（安全用モデル）と `ChannelLaneResolver` を変更しない。**
   航路の色は表示専用の `NavigableWater` 側だけで決める（→ 3.1.2）。
3. **不変条件6を守る。** 地図に描く船体領域は今までどおり
   `getShipDomains(headingReliable: true)` の結果を使う。低速時の横方向拡張を
   描画へ持ち込まない。
4. **航行開始をブロックしない。** 航路データが読めなくても、倍率設定が失敗しても、
   航行は始まり警告は鳴る（原則1）。
5. **音は一切変えない。** この作業に音声・警告バンドの変更は含まれない。
6. **利用者が手で変えた倍率を上書きしない。**（→ 3.2.3 が本要件の核心）

## 3. 機能要件

### F1. 航路（往路・復路）を地図に表示する

#### 3.1.1 何を描くか

`navigableWaters` の6本のポリゴンを、**細い輪郭線＋ほぼ透明な塗り**で、
**存在感を極力抑えて**描く。

**この機能の主役は危険区域であって航路ではない。** レーンは川幅いっぱいの面積が
あるため、塗りが少しでも濃いとその下の岸・橋脚・中州の色を全部濁らせる。
線も、危険区域の輪郭（岸 width 1、橋脚 width 3）より目立ってはいけない。
航路は「言われて初めて気づく程度の、うっすらした帯」に徹する。

判断に迷ったら**薄いほうを選ぶ**こと。薄すぎて見えなければ現地で1段濃くすればよいが、
濃くて危険区域が沈んだ状態は、安全機能そのものを壊している。

#### 3.1.2 往路・復路の見分け方（重要）

**`direction`（along / against）から往路・復路を導いてはいけない。** 実データはこうなっている。

```
lane_kasumikagaura_outbound      往路 → direction: "along"
lane_sakuragawa_estuary_outbound 往路 → direction: "against"   ← 逆
```

`direction` は「中心線の頂点の並び順に対してどちら向きか」という**安全判定の内部量**であり、
往路/復路という**人間の呼び名**とは無関係である。

また **id や name の文字列（`_outbound` / `往路`）を見て色を決めてもいけない。**
データを編集した人が名前を変えた瞬間、赤と緑（本件ではグレーの濃淡）が静かに入れ替わる。
警告の向きを決めているのと同じデータで、色を推測しないこと。

→ **JSON に表示専用のフィールド `leg` を追加する。**

```json
{ "id": "lane_sakuragawa_upstream_outbound", "leg": "outbound", ... }
```

`leg` を読むのは `NavigableWater`（表示用モデル）だけ。`ChannelLane`（安全用モデル）は
今までどおり `leg` を一切見ない。**表示の都合が安全判定へ漏れない**構造を保つ。

`leg` が無い・不正な値のレーンは**無彩色で描く**（縮退運転。描かないのではなく、
「向きが不明な航路」として出す。原則1）。

#### 3.1.3 配色

ユーザー指定：**赤は使わない**（障害物の danger 赤と衝突するため）。**往路・復路とも
グレー系で、濃淡で区別する。**

配色の規則を1文で言うと：**往路 = コントラストの強いグレー、復路 = 弱いグレー。**
この言い方にしておくと、通常地図（明るい背景）でも航空写真（暗い背景）でも同じ意味を保てる。

| | 通常地図 `MapType.normal` | 航空写真 `MapType.hybrid` |
| --- | --- | --- |
| 往路（`leg: "outbound"`）線 | `#37474F` alpha **0.40** / width **2** | `#ECEFF1` alpha **0.45** / width **2** |
| 往路 塗り | `#607D8B` alpha **0.05** | `#ECEFF1` alpha **0.04** |
| 復路（`leg: "return"`）線 | `#90A4AE` alpha **0.40** / width **2** | `#78909C` alpha **0.45** / width **2** |
| 復路 塗り | `#B0BEC5` alpha **0.05** | `#78909C` alpha **0.04** |
| 不明（`leg` 無し）線 | `#9E9E9E` alpha 0.30 / width 1 | `#9E9E9E` alpha 0.30 / width 1 |
| 不明 塗り | なし（`Colors.transparent`） | なし |

**比較の基準（この関係が崩れていたら濃すぎる）:**

- 線の太さ：航路 2 ≦ 岸 1 … ではなく、**橋脚 3・杭 3 より必ず細い**こと。
- 塗りの濃さ：航路 0.05 は、いちばん薄い危険区域である**岸の 0.18 の 1/3 以下**。
  `HazardPalette.fillOpacityOf` の値（岸0.18 / 橋・カーブ0.28 / 橋脚0.52）と
  並べて確認すること。
- 往路と復路の差は**色の明度だけ**でつける。片方だけ太くしたり濃くしたりしない
  （どちらか一方が危険区域より目立ってしまう）。

`highContrastMapStyle` を有効にしているときも `normal` 用の色をそのまま使う
（このスタイルは地図側の彩度を落とすので、薄いグレーの帯でも輪郭は追える）。

#### 3.1.4 進行方向の矢印（シェブロン）— S5、任意

色だけでは「どちらへ進む帯か」が分からない。中心線に沿って一定間隔で
シェブロン（≫ の形）を打ち、右側通行の向きを示す。

**これは S4 が完成し、現地で見て「向きが分からない」と確認できてから着手する。**
S4 だけでも要件は満たしている。

#### 3.1.5 表示のON/OFF

メニュー（`MapMenuSheet`）に「航路を表示」のトグルを追加する。**既定はON**、
端末内に保存（`MapDisplaySettingsService`）。「高コントラスト表示」の項目が
そのまま手本になる（[home_map_screen.dart:420-433](../lib/screens/home_map_screen.dart:420)）。

#### 3.1.6 既知の制限（実装しないが記録する）

固定危険区域には現地校正オフセット（`FixedObstacleCalibration`）が
障害物IDごとに適用されるが、**航路レーンは校正対象外**なので、プロットしたままの
座標で描かれる。岸に大きな校正が入っている区間では、航路の帯が岸に対して
数m ずれて見えることがある。表示だけの問題であり、安全判定には影響しない。
気になる差が出たら、レーンのプロットをやり直す（校正機構をレーンへ広げない）。

### F2. 既定倍率とカメラ位置

#### 3.2.1 航行中：既定 zoom 19.0

**「航行スタート」を押した直後の1回だけ** zoom 19.0 へ移動する。

#### 3.2.2 航行中：自艇を画面の下から 1/3 に置く

漕手は後ろ向きに座っており、進行方向が見えない。地図は進行方向が上になるよう
回転している（`rowingMapBearing`）ので、**自艇を画面中央より下へ置くと前方の
見通しがそのまま増える。**

`GoogleMap` の `padding` に**上パディング**を入れる。Google Maps はパディングを
除いた領域の中心にカメラのターゲットを置くので、上に入れるほどターゲットは下がる。

```
上パディング P を入れたときのターゲットの画面Y = (P + H) / 2
これを 0.667 * H にしたい → P = H / 3
```

- 効果：zoom 19 縦203m のうち、前方が 約100m → 約135m に増える。
- **航行中のみ適用する。** 監視中・待機中は `EdgeInsets.zero`。

#### 3.2.3 利用者の手動操作を絶対に上書きしない（最重要）

現状 `zoomForMapRefocus()`（[map_render_update_policy.dart:20](../lib/services/map_render_update_policy.dart:20)）は
「いまの倍率をそのまま返す」実装で、利用者がピンチで変えた倍率を保っている。
**この関数と `focusP14y()` の既定動作を変えてはいけない。**

変えるのは「**航行開始の瞬間に1回だけ、明示的に 19.0 を渡す**」ことだけ。
そのために `focusP14y()` に**省略可能な引数**を1つ足す（→ S2）。

| 場面 | 倍率 |
| --- | --- |
| アプリ起動直後（待機中） | 18.0（現状のまま） |
| **航行スタート直後の1回** | **19.0**（新規） |
| 航行中に利用者がピンチ操作 | 利用者の値（現状のまま） |
| 航行中の毎秒の追従 | 利用者の値（現状のまま） |
| ジェスチャー後の自動復帰（3秒） | 利用者の値（現状のまま） |
| **監視スタート直後の1回** | **16.5**（新規） |
| 監視中の「全艇を表示」ボタン | 全艇が収まる倍率（新規） |

#### 3.2.4 監視中：既定 16.5 ＋「全艇を表示」ボタン

監視者は陸上にいて端末を操作できる（Wakelock を航行中だけに限っている理屈と同じ）。
拡大より俯瞰が要る。

- 監視スタート直後に 16.5 へ移動。
- 右側の操作ボタン列（「艇一覧」の下）に **「全艇」ボタン**を追加。
  押すと全艇が収まる `LatLngBounds` へフィットする。
- 艇が0隻のときはボタンを押しても何もしない（無効表示）。
  **1隻のときも必ず動くこと**（→ S2 の実装注意）。

### F3. 予測帯の描画を簡素化する

1艇あたり最大48枚のポリゴンを、**3つの図形**に置き換える。

| 図形 | 内容 | 見た目 |
| --- | --- | --- |
| ① 船体領域 | `t=0` の船体領域 1枚（現状と同じ） | 黒 線2 / 塗り alpha 0.08 |
| ② 掃引外形 | 全サンプルの排他領域の頂点をまとめた**凸包** 1枚 | `#F9A825` 線3 / 塗り alpha 0.06 |
| ③ 停止距離ライン | 停止距離の位置での排他領域の輪郭を1本のポリラインで | `#D32F2F` 線2 |

- 情報は減らない。「どこまで届くか」＝②、「どこまでなら止まれるか」＝③。
- 川なり予測（曲線）のとき、凸包は内カーブ側をわずかに（50m掃引・半径200mで約1.5m）
  外へ膨らませる。**表示専用なので許容する**が、コメントに必ず書くこと。
- 速度0のときは掃引が無いので ① だけを描く。③ は出さない。

### F4. 航行中の計器のメリハリ

漕手が常時見たいのは **ペースと SPM の2つだけ**。

| 項目 | 現状 | 変更後 |
| --- | --- | --- |
| ペース | 52px（警告中は32px） | **52px 固定** |
| SPM | 44px（警告中は非表示） | **44px 固定・常時表示** |
| 距離 | 20px | **16px** |
| 経過時間 | 20px | **16px** |
| 警告中の縮小（`deemphasized`） | あり | **廃止** |

**`deemphasized` を廃止する判断の記録：** 元の実装には「連続音が鳴っている間は
主計器を縮めて警告バナーへ視線の一等地を譲る」という意図があった。
今回これを外すのは、**計器の大きさが状況で変わること自体が読み取りを遅らせる**
という利用者判断による。警告バナーの表示・音・優先順位は一切変えないので、
警告が伝わらなくなることはない。

### F5. 監視中の地図と艇一覧の連動

- **艇一覧の行をタップ** → その艇へカメラを移動する。
- **異常チップ（`CoachAnomalyChip`）をタップ** → 艇一覧を開く（現状）**＋
  いちばん重い異常の艇へカメラを移動する**。
- 移動時の倍率：`max(現在の倍率, 18.0)`。引きすぎているときだけ寄せ、
  すでに寄っているなら**引き戻さない**。
- 陸上での操作なので確認ダイアログは不要。

### F6. 地図レイヤーの色と重なり順を1か所に書く

いま「塗り＝実在する危険 / 線＝予測」という規約がコードコメントに散らばっている。
航路（帯）が3層目として入るので、**意味と `zIndex` を1ファイルに集約する。**

| 層 | 意味 | zIndex |
| --- | --- | --- |
| 航路レーン（塗り・線） | そこを通ってよい帯 | 0 |
| 航路シェブロン | 進行方向 | 1 |
| 監視モードの航跡 | 過去に通った線 | 5 |
| 危険区域（塗り） | **実在する危険** | 10 |
| 船体領域・掃引外形（線） | **これから通る予測** | 20 |
| 開発者オーバーレイ | 判定形状の確認用 | 30 |

マーカー（艇アイコン）は Google Maps の仕様上つねにポリゴンより上に出るので、
指定は不要。

## 4. 実装計画

### S1. 地図レイヤー規約ファイルを作る（土台）

**目的:** 以降のステップが参照する定数と規約を先に置く。これ単体では画面は変わらない。

**新規ファイル:** `lib/theme/map_layer_spec.dart`

**やること:**

1. 3層の意味（航路＝帯／危険区域＝塗り／予測＝線）を説明する doc コメントを冒頭に書く。
   [F6](#f6-地図レイヤーの色と重なり順を1か所に書く) の表をそのまま入れる。
2. `zIndex` 定数を **int** で定義する（`google_maps_flutter` の `Polygon.zIndex` /
   `Polyline.zIndex` は int）。

```dart
const int laneFillZIndex = 0;
const int laneChevronZIndex = 1;
const int coachTrailZIndex = 5;
const int hazardPolygonZIndex = 10;
const int predictionShapeZIndex = 20;
const int developerOverlayZIndex = 30;
```

3. 航路の配色（3.1.3の表）を返す関数を置く。

```dart
/// 航路レーンの表示色。[isSatellite] は MapType.hybrid のとき true。
/// [leg] が null / 不明のときは無彩色で描く（描かないのではない）。
LaneStyle laneStyleFor({required String? leg, required bool isSatellite});
```

`LaneStyle` は `strokeColor` / `fillColor` / `strokeWidth` を持つ単純な値クラスにする。

**やらないこと:** `HazardPalette` の中身は変えない。このファイルから参照もしない。

**完了条件:** `dart analyze lib test` が通る。画面の見た目は変わらない。

**テスト:** `test/theme/map_layer_spec_test.dart` を新規作成。

- `leg: "outbound"` と `leg: "return"` で `strokeColor` が異なること
- `leg: null` / `leg: "unknown"` で無彩色（`#9E9E9E`）が返ること
- **航路の塗りの不透明度が、いちばん薄い危険区域（岸 = `HazardPalette.fillOpacityOf('shore')`）
  より必ず小さいこと。** 危険区域より航路が目立つ配色を、テストで恒久的に禁止する
- **航路の線幅が、橋脚（`HazardPalette.strokeWidthOf('bridgePier')`）より必ず細いこと**
- `isSatellite: true` と `false` で色が変わること
- zIndex が 航路 < 航跡 < 危険区域 < 予測 < 開発者 の順に並んでいること

### S3. 予測帯の簡素化（F3）

#### S3-1. 凸包の計算を純Dartサービスへ切り出す

**新規ファイル:** `lib/services/swept_outline_service.dart`

**やること:** 複数のポリゴンの頂点をまとめ、その凸包（外形）を返す。

```dart
/// 掃引した予測領域の外形を1枚のポリゴンにまとめる。
///
/// **表示専用。** 安全判定はサンプルごとの連続SATで行っており、この外形は
/// 判定に一切使わない。川なり予測（曲線）のときは内カーブ側をわずかに
/// 外へ膨らませる（50m掃引・半径200mで約1.5m）が、線で描く予測の外形
/// としては許容できる誤差である。
List<LatLng> sweptOutline(List<List<LatLng>> polygons);
```

**実装手順（この順で書く）:**

1. 全頂点を集める。3点未満なら入力の先頭ポリゴンをそのまま返す（縮退）。
2. 全頂点の平均緯度経度を原点として、メートル平面 (x, y) へ変換する。
   変換式は [metric_polygon_buffer.dart:124](../lib/utils/metric_polygon_buffer.dart:124) の
   `_toLocal` / `_fromLocal` と同じ考え方（緯度1度＝111320m、経度は cos(緯度) 倍）。
3. **Monotone Chain（Andrew's algorithm）**で凸包を求める。
   - x, y の辞書順でソート
   - 下側の殻・上側の殻を順に作り、外積が 0 以下の点を捨てる
   - 端点の重複を除いて連結
4. 緯度経度へ戻して返す。

**テスト:** `test/services/swept_outline_service_test.dart`

- 正方形1枚を入れたら、頂点4つがそのまま返る（順序は問わない）
- 正方形を東へ 10m ずつ 5枚ずらしたら、返る外形が全5枚を含む
  （各入力頂点が外形の内側または境界にあることを `isPointInPolygon` で確認）
- 空リスト → 空リスト。1点だけ → そのまま返す（例外を投げない）
- 全点が一直線上 → 例外を投げない

### S5. 進行方向シェブロン（F1・任意）

**S4 を現地で確認し、「向きが分からない」と実際に感じてから着手する。**

**新規ファイル:** `lib/services/lane_chevron_service.dart`

**アルゴリズム（この順で実装する）:**

各レーンについて：

1. `centerlineId` で紐付いた中心線の点列を得る（`loadChannelCenterlines()`）。
   紐付けが無い／解決できないレーンは**シェブロンを出さない**（推測しない）。
2. 中心線を先頭から **60m 間隔**で歩き、サンプル点と接線方位 θ を求める
   （`distanceMeters` / `computeOffset` を使う）。
3. サンプル点の左右に 8m ずらした候補点を2つ作る（θ+90度 と θ−90度）。
4. **`isPointInPolygon` でレーンの中に入るほうを選ぶ。**
   両方入る／両方入らない場合はそのサンプルを捨てる。
   → これでレーンが中心線のどちら側かを、名前や符号に頼らず決められる。
5. 進行方位を決める。**ここでは `leg` ではなく `direction` を使う。**
   `direction == along` なら θ、`against` なら θ+180度。
   （`leg` は色だけ、`direction` は向きだけ。混ぜない。）
6. シェブロンを2本の短い線分として作る。進行方位から ±140度 の向きへ、
   それぞれ 3m。`Polyline` として返す。

**色:** レーンの線色と同じ（`laneStyleFor`）。`zIndex: laneChevronZIndex`。

シェブロンは点在する短い線なので、帯の線と同じ alpha でも埋もれない。
**帯を薄くした埋め合わせにシェブロンを濃くしないこと。** 向きが読めなければ、
濃さではなく**間隔を詰める**（60m → 40m）で対処する。

**テスト:** `test/services/lane_chevron_service_test.dart`

- 中心線が真東へ伸び、レーンが中心線の北側にある場合、シェブロンが
  中心線の北側に生成される
- `direction: along` と `against` で、シェブロンの向きが180度反転する
- 中心線が紐付いていないレーン → 空リスト

## 9.8. 追補: 作図ツールへの `leg` 対応（2026-08-03・計画外）

9.5 の既知の制限 1 を**解消した**。作図ツール（`tool/obstacle-plotter`）が `leg` を
読み書きするようになったため、プロファイルを書き出し直しても往路・復路の指定は消えない。

| `src/app/App.tsx` | レーンのインスペクタへ「往路・復路（表示専用）」の独立した fieldset を追加 |

### 設計上の判断

1. **モデルのフィールド名は `laneLeg`。** JSON のキーは `leg` のままだが、`direction` が
   `laneDirection` になっているのと揃えた。
2. **書き出しの並びは `kind` → `leg` → `direction`。** 同梱プロファイルの並びと一致させている。
   並びが変わるとファイルの SHA-256 が変わり、`firestore.rules` に固定した
   `baseProfileSha256` との突き合わせが**中身は同じなのに外れる**。
   これは `profile.ts` の該当箇所にコメントで残した。
3. **検証は error ではなく warning。** `leg` は表示専用で、欠けてもアプリは無彩色の帯として
   描き、航行も警告も止めない（原則1）。error にすると、表示用の付加情報1つで
   プロファイル全体の書き出しがブロックされる。
4. **新規レーンに既定値を入れない。** `laneDirection` は `'along'` を既定にしているが、
   `laneLeg` は既定を持たせていない。既定を入れると2本とも往路になり、
   「指定したつもりで両方同じ」という**間違いに気づけない状態**が既定になる。
   未設定なら `lane.leg.missing` の warning が出るので、必ず選ぶことになる。
5. **UI を「規定進行方向」とは別の fieldset にした。** 同じ枠に入れると、
   安全判定に使う `direction` と表示専用の `leg` が同じ種類の設定に見える。
   説明文にも「桜川河口の往路のように、往路なのに中心線とは逆向きの組み合わせが
   実際にある」と明記し、片方から他方を推測させない。

### 追加したテスト

| ファイル | 内容 |
| --- | --- |
| `test/profile.test.ts` | **同梱プロファイルを import → export してバイト単位で一致すること**（`leg` を含む全レーン）／`leg` が `direction` から導けないこと／不正な `leg` を落としてもレーンは残ること |
