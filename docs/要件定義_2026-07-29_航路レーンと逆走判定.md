# 要件定義: 航路レーンの明示プロットと、逆走判定の堅牢化

作成日: 2026-07-29
対象: プロットツール(`tool/obstacle-plotter/`)とアプリ(`lib/`)の両方
上位規範: [docs/DESIGN_PRINCIPLES.md](DESIGN_PRINCIPLES.md)(食い違ったらそちらが優先)

**実際の座標プロットは本要件の範囲外**である。本書は、プロット作業を始める前に
整えておくべき「アプリ側の機能」と「ツール側の機能」を定義する。

---

## 0. 用語

| 用語 | 意味 | この文書での扱い |
| --- | --- | --- |
| 航路中心線(channel centerline) | 川の中央を通る1本の折れ線 | **1本しか存在しない。**予測経路生成と規定方位算出の両方が使う |
| 逆走注意区域(reverse zone) | 逆走判定を有効にする範囲を示すポリゴン | 既存 `kind: "reverse"`。判定の**有効範囲**を決める |
| 航路レーン(lane) | 往路・復路それぞれの通行帯を示すポリゴン | 新規に安全経路へ昇格。その位置での**規定進行方向**を決める |
| 規定進行方位 | 「その位置で進むべき向き」[度] | 中心線の接線方位を、レーンに応じて 0度 or 180度 回したもの |
| レーン判定 | 自艇が往路・復路どちらの帯にいるかの決定 | 本要件で `cross` 符号方式からポリゴン内包方式へ置き換える |

## 1. 背景と問題

### 1.1 現状

逆走判定は [collision_risk_evaluator_service.dart:825](../lib/services/collision_risk_evaluator_service.dart:825)
`evaluateReverseGuidance()` にある。手順は次のとおり。

1. `reverse` ポリゴン内に自艇がいるか(`isPointInPolygon`)
2. 自艇を航路中心線へ投影し、`ChannelFrame` を得る
3. **`frame.crossMeters` の符号**で、中心線のどちら側にいるかを決める
4. 右側通行なので、右側(`cross > 0`)なら規定方位 = 接線、左側なら 接線 + 180度
5. 保持方位との差が `reverseGuidanceHeadingErrorDegrees`(120度)以上なら逆走

中心線は現在 **手で引かれていない**。`assets/data/sakuragawa_obstacles.json`
(profile version 4)に `channelCenterline` フィールドが無いため、
[preset_obstacle_service.dart:676](../lib/services/preset_obstacle_service.dart:676)
が `ChannelCenterline.fromShorelines()` にフォールバックし、
北岸153点・南岸107点の岸基準線から中点列を自動導出している
(`isChannelCenterlineDerivedFromShores == true`)。

### 1.2 何が問題か

**中心線の横方向の位置誤差が、規定進行方位を180度反転させる。**

`cross` の符号だけがレーンを決めているため、中心線が真の航路中心から
横に大きくずれていると、右側通行を正しく守っている艇が「左レーンにいる」と
判定され、規定方位が 180度 ひっくり返る。その艇は**必ず逆走と誤判定される**。
これは原則4(過剰警告は安全機能の破壊である)に正面から反する。

誤差の許容量は次のように決まる。

```
中心線に許される横誤差 < レーン半幅 − GPS誤差
                      = 12.5m(狭所) − 5m(reverseGuidanceLaneAmbiguityMeters)
                      = 7.5m
```

岸の中点法は、**中州・ワンド・桟橋のある区間でこの 7.5m を容易に超える**。
`fromShorelines()` は川幅が想定外になった標本を捨てるため
([channel_centerline.dart:134](../lib/services/channel_centerline.dart:134))、
捨てられた区間には穴が空き、3点移動平均がその穴を跨いで中心線をさらに歪める。
中州(`island_sakuragawa_bridge` / `island_upstream` の2件)の周辺が最も危ない。

なお **接線方位の誤差は問題ではない**。閾値が120度なので、接線が20〜30度
ずれても判定は変わらない。効くのは符号だけである。

### 1.3 もう1つの問題: 瞬時判定

`evaluateReverseGuidance()` は毎評価で即断する。しかし DESIGN_PRINCIPLES 1.3・1.4 が
定義する正常な運用のうち、次の3つは**一瞬だけ逆走の条件を満たす**。

- 折り返しの回頭直後(方位は復帰しているがレーンをまだ移っていない)
- 対向艇を避けて反対レーンへ寄る
- 岸へ着ける・桟橋へ寄せる

`ShipDomainService.headingIsReliable()` のゲートが低速時を除外しているが、
0.5m/s を超えたまま反対レーンを斜行する場面は残る。

### 1.4 やること(一文)

**レーン判定を `cross` 符号からポリゴン内包へ置き換え、逆走の発報に 6秒 の確定時間を設ける。**

## 2. 設計方針

### 2.1 中心線は2つの用途を兼ねている。分けない

| 用途 | 消費者 | レーンとの関係 |
| --- | --- | --- |
| 予測経路の生成(川なりの折れ線) | [channel_path_predictor.dart:63](../lib/services/channel_path_predictor.dart:63) | 無関係。川の形が欲しいだけ |
| 規定進行方位の算出(接線) | [collision_risk_evaluator_service.dart:838](../lib/services/collision_risk_evaluator_service.dart:838) | レーンごとに符号が反転する |

したがって **往路用・復路用に中心線を2本引く設計は採らない。** 予測がどちらを
使うか決められなくなる。プロットツールも `channelCenterline` を
`SINGLETON_KINDS` として1つに制限している
([types.ts:118](../tool/obstacle-plotter/src/model/types.ts:118))。

**中心線は1本のまま(ただし手引きに置き換える)、レーンは別のポリゴンで表す。**

桜川のレーン間隔は川幅40m中の12.5〜20mなので、往路と復路で接線方位はほぼ同一である。
中心線を2本持っても得られる情報は増えず、3箇所に散った幾何が食い違うリスクだけが増える。

### 2.2 3種類の図形の役割分担

| 図形 | 答える問い | 欠けたときの縮退 |
| --- | --- | --- |
| `reverse` ポリゴン | **どこで**逆走判定を行うか | 判定しない(現状どおり) |
| 航路レーン ×2 | **どちら向き**が正しいか | `cross` 符号方式へ縮退 |
| 航路中心線 | 規定方位の**基準となる接線** | `unverified` → 区域内で発報(現状どおり) |

この分離により、**`cross` の符号を安全経路から外せる**のが本要件の核心である。
レーン判定がポリゴン内包になると、境界付近での失敗が「反転」ではなく
「どちらでもない = 判定しない」という穏やかな形になる。

### 2.3 レーン判定の優先順と縮退表

`evaluateReverseGuidance()` は次の順で解決する。**上から順に評価し、最初に成立したものを採る。**

| # | 条件 | レーン決定 | 結果 |
| --- | --- | --- | --- |
| 1 | 中心線が無い / 投影が被覆外 / 接線が非有限 | — | `unverified`(区域内で発報。現状維持) |
| 2 | 方位が信頼できない(`headingIsReliable == false`) | — | `compliant`(助言しない。現状維持) |
| 3 | レーンが2枚以上あり、自艇がいずれかの内部 | **ポリゴン内包** | 規定方位を算出して判定 |
| 4 | レーンがあるが、自艇がどのレーンにも入っていない | — | **`laneUndetermined`(発報しない)** |
| 5 | レーンが1枚も無い | `cross` 符号 | 規定方位を算出して判定(現状維持) |

**#4 を `unverified` にしてはいけない。** `unverified` は「区域内なら無条件発報」へ
縮退する経路であり、レーンの隙間(中心線付近)を通るたびに鳴ることになる。
実機ログで観測された「77分で16回」がそのまま戻ってくる。

**#4 は原則1(機能を止めない)に反しない。** レーンの隙間は「データが欠けている」のではなく、
**作図者が明示的に判定対象外と定めた領域**である。ジオメトリの不在(#1・#5)と、
ジオメトリがある上での意図的な非判定(#4)は別の事象として扱い、診断ログでも区別する。

### 2.4 不感帯はコード定数から地図上の隙間へ移る

現在の `reverseGuidanceLaneAmbiguityMeters = 5.0` は、GPS誤差で `cross` の符号が
反転するのを防ぐためのコード内不感帯である。レーン方式ではこれが
**2枚のレーンポリゴンの間の隙間**という目に見える形になる。

- プロットツール上で調整でき、地図で確認できる
- 狭所だけ隙間を狭める、といった場所ごとの調整ができる

ただし `reverseGuidanceLaneAmbiguityMeters` は **削除しない**。#5(レーン不在時)の
`cross` 符号経路が使い続けるためである。

## 3. データスキーマ要件

### 3.1 航路レーン

既存の `navigableWaters` 配列を使う。プロットツールは既に `kind: "lane"` を
`NAVIGABLE_KINDS` として同配列へ書き出しており
([types.ts:117](../tool/obstacle-plotter/src/model/types.ts:117)、
[profile.ts:159](../tool/obstacle-plotter/src/io/profile.ts:159))、
アプリも `NavigableWater` として読める
([navigable_water.dart](../lib/models/navigable_water.dart))。**足りないのは向きの情報だけ**である。

新規の最上位フィールドを作らない理由は、同じ形のポリゴンが2つの配列に分かれると
編集時に食い違うため。1つの幾何、1箇所の編集にする。

**追加するフィールド:**

```json
{
  "id": "lane_downstream",
  "name": "航路レーン(下り)",
  "kind": "lane",
  "direction": "along",
  "points": [ { "lat": 36.0, "lng": 140.1 }, ... ]
}
```

| フィールド | 型 | 必須 | 意味 |
| --- | --- | --- | --- |
| `direction` | `"along"` \| `"against"` | `kind == "lane"` のとき必須 | **航路中心線の頂点順**に対する向き。`along` = 中心線の始点→終点と同じ向きが正しい |

- `direction` は中心線の頂点順を基準にする。「上流/下流」という語を使わない。
  中心線を引き直したときに向きの意味が変わってしまうのを避けるためである
  (中心線の向きが反転したら `direction` も入れ替える必要がある。§6.2 の検証で担保する)
- `kind: "navigableWater"`(表示専用の水面)は `direction` を持たない。持っていても無視する
- **`direction` を欠く `lane` は安全経路へ渡さない。** 表示専用として扱い、
  レーンが1枚も揃わなければ §2.3 #5 へ縮退する

### 3.2 航路中心線

既存の `channelCenterline` フィールドをそのまま使う。**スキーマ変更は無い。**
現在このフィールドが JSON に存在しないため、手引きしたポリラインを追加するだけでよい。

追加されると `PresetObstacleService.isChannelCenterlineDerivedFromShores` が
`false` になり、岸からの自動導出は使われなくなる。

### 3.3 後方互換性

| 状況 | 挙動 |
| --- | --- |
| 旧プロファイル(`channelCenterline` なし、`lane` なし) | 現状と完全に同一。岸から導出 + `cross` 符号 |
| 中心線のみ追加 | `cross` 符号方式のまま、精度だけ向上 |
| 中心線 + レーン2枚 | 本要件の完成形 |
| レーンが1枚だけ / `direction` 欠落 | `cross` 符号方式へ縮退。診断ログに残す |

**どの段階でも航行開始をブロックしない。**(原則1・不変条件5)

## 4. アプリ側の要件(`lib/`)

### R-A1. `ChannelLane` モデルの新設

`lib/models/channel_lane.dart` を新設する。

- `NavigableWater` は**変更しない。** 「表示・検証用。安全判定に使わない」という
  既存の契約([navigable_water.dart:3](../lib/models/navigable_water.dart:3))を守る。
  安全経路へ入るデータは専用の型を通し、検証もそこで行う
- `ChannelLane.fromJson()` は `kind == "lane"` かつ `direction` が
  `"along"` / `"against"` のいずれかであることを要求し、満たさなければ
  `FormatException` を投げる(1件の不正で全体を落とさない方針は `loadAshoreAreas()` に倣う)
- 頂点数・座標範囲の検証は `NavigableWater.fromJson()` と同じ基準(3〜1000点、緯度経度範囲)
- 純Dart(`google_maps_flutter` の `LatLng` のみ)。単体テスト必須

### R-A2. `PresetObstacleService.loadChannelLanes()`

`navigableWaters` から `kind == "lane"` かつ `direction` が妥当な要素だけを
`List<ChannelLane>` として返す。

- 既存の `loadNavigableWaters()` は**そのまま残す**(地図表示が使っている)
- 不正な1件はスキップし `debugPrint` する。全件不正なら空リストを返す
- プロファイルの読み込みは既存の `_loadProfile()` キャッシュに相乗りする

### R-A3. `ChannelLaneResolver`(純Dart)

レーン解決だけを担う純Dartクラスを `lib/services/channel_lane_resolver.dart` に新設する。

```dart
enum LaneDirection { along, against }

/// 自艇位置から、その位置での規定進行方向を決める。
/// レーンが無い・どのレーンにも入っていない場合は null を返す。
LaneDirection? resolve(LatLng position);
```

- 内部で `StaticObstacleIndex` と同じグリッドハッシュを使うかは**任意**。
  レーンは2枚しかなく `isPointInPolygon` を2回呼ぶだけなので、
  初期実装は素直な線形探索でよい
- **2枚のレーンが重なっている位置**では、`null` を返す(判定しない)。
  作図ミスが誤警告になるより、判定しないほうが安全。§5 のバリデーションで
  そもそも重なりを禁止するが、実行時にも保険を置く

### R-A4. `evaluateReverseGuidance()` の改修

[collision_risk_evaluator_service.dart:835](../lib/services/collision_risk_evaluator_service.dart:835) を §2.3 の優先順に従って改修する。

- 引数に `ChannelLaneResolver? laneResolver` を追加(省略時は現状動作)
- `ReverseGuidanceOutcome` に **`laneUndetermined` を追加**する。
  呼び出し側での扱いは `compliant` と同じ(発報しない)だが、診断ログで区別できるようにする
- レーンで解決できた場合の規定方位:

  ```dart
  final requiredBearing = laneDirection == LaneDirection.along
      ? tangent
      : tangent + 180.0;
  ```

- **`cross` を見る分岐は残す**(§2.3 #5)。削除してはいけない
- 閾値 `reverseGuidanceHeadingErrorDegrees`(120度)は変更しない

### R-A5. `ReverseGuidanceDebouncer`(純Dart)

`lib/services/reverse_guidance_debouncer.dart` を新設する。
[receive_fault_debouncer.dart](../lib/services/receive_fault_debouncer.dart) と同じ型の非対称ヒステリシス。

```dart
/// 逆走の発報を、継続時間で確定させる。
/// 確定 6秒 / 解除 0秒 の非対称。
bool update({required bool isReverse, required DateTime at});
```

- `isReverse == true` が `reverseGuidanceConfirmSeconds` 継続して初めて `true` を返す
- `isReverse == false` になったら**即座に**リセットする(解除は遅らせない)
- 時刻は引数で受け取る。`DateTime.now()` を内部で呼ばない(テスト可能性)
- Timer を持たない。純Dart。単体テスト必須

### R-A6. `SafetyOrchestrator` — 待たせるのは音だけ

デバウンサの結果を**提示層で**適用する。
[safety_orchestrator.dart:620](../lib/services/safety_orchestrator.dart:620) `_presentGuidance()` を改修する。

| 対象 | 確定前(6秒未満)の扱い |
| --- | --- |
| 候補(`AlertCandidate`) | **即座に立てる** |
| 画面表示・バナー | **即座に出す** |
| `reasonCodes` | `REVERSE_CONFIRM_PENDING` を付ける |
| 音声(`audioAsset`) | **抑制する**(`null` + `clearAudioAsset: true`) |

**これを間違えて候補ごと遅らせてはいけない。** 「逆走しているのに画面にも
何も出ない6秒」ができ、system fault で一度踏んだ穴(原則6・不変条件3)を踏み直す。
`gps_unavailable` / `pipeline_unresponsive` が
`capabilityFaultConfirmSec` で音だけ待たせているのと同じ構造にする。

- 自艇が `reverse` 区域の外へ出たら、`_updateGuidanceExitState()` の経路で
  デバウンサをリセットする
- `reverseGuidanceRearmDuration`(60秒)とは**別物**。あれは鳴り直しの間隔、
  これは初回確定の遅延。両方が独立に効く

### R-A7. 設定値(`lib/config/risk_evaluator_config.dart`)

前提をコメントに書く(原則7)。

```dart
/// 逆走を発報として確定させるまでの継続時間 [秒]。
///
/// 折り返しの回頭直後・対向艇を避けての斜行・岸への寄せは、いずれも
/// 正常な運用でありながら一瞬だけ逆走の条件を満たす(1.3・1.4)。
/// 6秒 @ 5m/s = 30m 進む間の猶予にあたる。カーブ間隔は最短200mなので、
/// 気づくのが30m遅れても次のカーブまでの余裕は失われない。
/// 解除は非対称で即座に行う(音を残さない)。
const reverseGuidanceConfirmSeconds = 6.0;
```

### R-A8. `useNavigator` の配線

[use_navigator.dart:1053](../lib/hooks/use_navigator.dart:1053) の中心線読み込みに並べて、
レーンを読み込み `ChannelLaneResolver` を構築して評価へ渡す。

- 読み込み失敗は**握りつぶして継続**する(レーン無し = §2.3 #5 へ縮退)
- 中心線と同様に `useState` で保持し、評価の毎周期で再構築しない

### R-A9. 地図表示(任意)

レーンポリゴンの地図描画は**本要件の必須項目ではない**。
ただし現地検証(§7)でレーン境界の妥当性を目視するには表示できたほうがよい。
実装する場合は既存の `MapDisplaySettingsService` のトグル配下に置き、
**既定は非表示**とする(原則4 — 画面を混ませない)。

### R-T2. 地図上での向きの可視化

レーンポリゴンの上に、規定進行方向を示す**矢印を一定間隔で描く**。

これは装飾ではなく検証手段である。`along` / `against` の取り違えは
「正しく漕いでいる全艇に逆走警告が鳴る」という最悪の誤りに直結するが、
ラジオボタンの値を目で追っても気づけない。矢印が川下を向いているか、
2枚のレーンで矢印が逆を向いているかを地図上で一目で確認できるようにする。

- 矢印の向きは**中心線の接線から計算する**(`laneDirection` を接線へ適用する)。
  アプリの計算と同じ式にすること。ポリゴンの頂点順から計算してはいけない

### R-T3. バリデーション(`validate/project.ts`)

| コード | レベル | 条件 | メッセージの趣旨 |
| --- | --- | --- | --- |
| `lane.direction.missing` | **error** | `kind === 'lane'` で `laneDirection` が無い | 向きの無いレーンは安全判定に使われない |
| `lane.direction.duplicate` | **error** | `along` または `against` が2枚以上ある | 各向きのレーンは1枚 |
| `lane.count` | warning | レーンが0枚、または1枚だけ | レーンが揃わないと `cross` 符号方式へ縮退する |
| `lane.overlap` | **error** | 2枚のレーンが面で重なっている | 重なった領域では判定できない |
| `lane.centerline.missing` | **error** | レーンがあるのに中心線が無い | レーンは中心線の接線が無いと向きを決められない |
| `lane.outside.coverage` | warning | レーン頂点が中心線の被覆範囲(端点の外側)にある | その区間では逆走判定が働かない |
| `lane.reverse-zone.uncovered` | warning | `reverse` ポリゴン内に、どちらのレーンにも属さない**広い**領域がある | 逆走判定が事実上無効な区間がある |
| `centerline.derived` | warning → **強化** | 既存の `centerline.missing` を、レーンがある場合は **error** へ昇格 | — |

`lane.reverse-zone.uncovered` の「広い」の判定は、
**レーン間の隙間として意図した幅(既定10m相当)を大きく超える領域**とする。
具体的な閾値はツール実装時に決めてよいが、隙間そのものを毎回警告してはならない。

**中州の扱い。** 往路と復路が中州の両側に分かれる区間では、1本の中心線の接線が
両レーンに使えない。その区間は**レーンポリゴンを置かず、かつ `reverse` ポリゴンも
外す**(判定しない)。`lane.reverse-zone.uncovered` はこの作業漏れを検出するための警告である。

### R-T4. 変更適用パッケージへの反映(`server/changeset.ts`)

`changesetMarkdown()` の生成結果に、次の行を追加する。

```
- 航路レーン: 2枚(along / against) / なし(アプリは cross 符号方式へ縮退)
- 航路中心線: 手動プロット / 岸から自動導出(要手動プロット)
```

中心線については、現在の `hasCenterline ? 'あり' : 'なし'` では
「JSON に無い(=岸から導出されている)」状態が「なし」としか出ない。
**「岸から自動導出」であることを明示**し、それが暫定状態だと分かるようにする。

### R-T5. 実航跡オーバーレイ(推奨・任意)

中心線を「岸の中点」ではなく「実際に艇が通っている中央」に引くため、
練習ログの航跡をプロットツールの地図へ重ねられるようにする。

- 入力は既存の GPX / 練習一括ログ(JSONL)のいずれか。ファイル選択で読み込む
- 表示のみ。プロジェクトには保存しない(`profileExtras` を汚さない)
- **本要件の必須項目ではない**が、これがあると中心線の質が根拠を持つ。
  誰も通らない浅瀬・中州は航跡の束から自然に外れるため、
  目視で障害物を避けて引くより確実である

## 6. 壊してはいけないもの

変更後に必ず確認する。

1. **航行開始をブロックしない。** レーン・中心線・`direction` のいずれが欠けても開始できる(不変条件5)
2. **中心線の予測経路への影響を変えない。** `ChannelPathPredictor` の入力は
   1本の `ChannelCenterline` のままである。レーンは予測に一切関与しない(不変条件4)
3. **`cross` 符号方式の経路を削除しない。** レーン不在時の縮退先である(原則1)
4. **`reverseGuidanceLaneAmbiguityMeters` を削除しない。** #5 経路が使い続ける
5. **確定6秒で候補・表示を遅らせない。** 音だけである(原則6・不変条件3)
6. **カーブ(`curve`)の挙動を変えない。** 方向つき判定の対象外であり、
   1カーブ1回で妥当に働いている
7. **`NavigableWater` の「安全判定に使わない」契約を壊さない。**
   安全経路へ入るのは新設の `ChannelLane` である
8. **`reverse` 以外の障害物の座標を動かさない。** 動かした場合は §7.1 の
   `currentHazardProfileDataVersion` 更新が必要になる

## 7. 反映手順とバージョン管理

### 7.1 `currentHazardProfileDataVersion` を上げるか

**上げない**(現在 4 のまま)。

CLAUDE.md の規定は「**座標の意味が変わる変更**をしたら上げる」である。
本要件で行うのは `channelCenterline` と `navigableWaters` へのフィールド追加であり、
既存の岸・橋・中州の座標の意味は変わらない。現地で合わせた座標校正オフセットは
そのまま有効なので、バージョンを上げると**校正値が捨てられてしまう**。

ただし、**プロット作業中に既存の危険区域の頂点を1つでも動かしたら上げること。**
その場合は校正オフセットの前提が変わる。

### 7.2 必須の反映手順

プロットツールの変更適用パッケージが出す `CHANGESET.md` の手順に従う。

1. `files/sakuragawa_obstacles.json` を `assets/data/` へ反映
2. `files/sakuragawa_obstacles.layout.json` を `assets/data/` へ反映
3. `dart run tool/generate_hazard_constants.dart`
4. `tool/update_hazard_profile_hash.sh` — SHA-256 が `CHANGESET.md` の値と一致することを確認
5. `verify.sh`

**3 と 4 は省略できない。** ハッシュが古いままでも航行機能は止まらないが、
「検証済み」状態が外れ、診断ログに `hazard_profile_unverified` が残る。

## 9. 現地検証ゲート(省略不可)

コードとデータが揃っても、**水上での検証が完了するまで完了としない。**

| # | 確認内容 | 合格条件 |
| --- | --- | --- |

**#1 が最重要である。** ここで1回でも鳴るなら、原則4により不具合として扱い、
