## FUT-001 チーム作成・招待コード・チーム内共有

### 状態

- 状態: **完了**(チーム作成・招待コード参加・チーム別パス・管理者交代・メンバー削除・招待コード更新まで実装済み。本番Rules反映 2026-10-20)
- 優先度: 高
- 登録日: 2026-07-20

> 以下の「目的」〜「完了条件」は登録時の案として残す。**実際のデータ構造は [DESIGN.md](DESIGN.md) 3章と
> リポジトリ直下の Rules が正本**である(例: 位置は `teams/{teamId}/live_positions/{uid}` に置いた)。
> 残っている確認は「異なる2チームの実端末で越境アクセスが拒否されること」で、
> [store/公開までの手順_2026-10-20.md](store/公開までの手順_2026-10-20.md) で追う。

### 目的

現在のFirebase匿名認証では、アプリを入れた利用者を特定のチームだけに限定できない。将来は、利用者が所属するチームを明示し、艇の位置、監視情報、臨時危険区域、固定流木の更新を基本的に同じチームの中だけで共有できるようにする。

### 想定する利用の流れ

1. チーム管理者がアプリ内でチームを作成する
2. システムがチーム用の招待コードを発行する
3. 部員またはコーチがアプリ内で招待コードを入力する
4. 招待が有効なら、その利用者をチームメンバーとして登録する
5. 航行位置、他艇警告、監視、危険区域の共有対象を同じチームに限定する
6. 管理者は招待コードの無効化・再発行、メンバーの削除を行える

### 初期スコープ案

- チーム作成
- 招待コードによる参加
- チーム名の表示
- 管理者と一般メンバーの最低限の権限分離
- チーム単位の位置共有
- チーム単位の臨時危険区域・固定流木更新
- 招待コードの失効・再発行
- メンバーの退出・削除
- 現在の匿名アカウントからチーム所属への安全な移行

初期実装では、複雑な役職階層、複数チーム同時所属、一般公開チーム検索、チーム間交流機能は含めない。

### データ構造案

最終決定ではなく、設計開始時の叩き台とする。

- `teams/{teamId}`: チーム名、作成日時、管理者、状態
- `teams/{teamId}/members/{uid}`: role、参加日時、状態
- `team_invites/{inviteId}`: teamId、コードのハッシュ、期限、使用回数、無効化状態
- `live_positions/{teamId}/{uid}`: チーム内のリアルタイム位置
- `teams/{teamId}/temporary_obstacles/{obstacleId}`: チーム内の臨時危険区域
- `teams/{teamId}/managed_hazards/{hazardId}`: チーム内の固定危険区域更新

### セキュリティ上の必須条件

- チーム所属判定をアプリ画面だけで行わず、Firebase Security Rulesまたは信頼できるサーバー側で強制する
- 招待コードを平文のままデータベースへ保存しない
- 招待コードに失効、再発行、試行回数制限を設ける
- 招待コード総当たりへのレート制限を設ける
- 管理者権限の付与・削除を一般メンバーが変更できないようにする
- チームを跨いだ位置情報・危険区域のread/writeをテストで拒否確認する
- Firebase App Checkは補助対策として利用できるが、チーム所属認可の代わりにはしない
- 既存のグローバル共有データをチーム別パスへ安全に移行し、旧パスを閉じる

### 未決定事項

- 匿名認証を維持するか、Apple／Google／メール等のアカウントへ昇格できるようにするか
- チームを作成できる利用者を誰に限定するか
- 招待コードの有効期限と利用可能回数
- 1人が複数チームへ所属できるようにするか
- 管理者を失った場合の復旧方法
- チーム削除時の位置・危険区域・監査情報の保持期間
- ストア一般公開と、チーム招待制の初回導入方法

### 完了条件

- チーム作成から招待参加までを2台以上で完了できる
- 同じチーム内では位置・危険区域を共有できる
- 別チームからは位置・危険区域を読み書きできない
- 失効・無効化した招待コードでは参加できない
- 管理者がメンバーを削除すると、そのメンバーは以後チームデータへアクセスできない
- 旧版と新版の混在時に、チーム外へ位置が漏れない
- Security RulesまたはEmulatorテストで越境アクセス拒否を自動検証する
- プライバシーポリシー、Data safety、App Privacy、審査メモを新しい共有範囲に合わせて更新する

## FUT-002 iOS の Google Maps を SwiftPM へ移し CocoaPods をなくす

### 状態

- 状態: 実装予定
- 優先度: 中
- 初回公開への影響: なし(今の構成でビルド・配布できる)
- 登録日: 2026-10-20

### 目的

2026-10-20 に Firebase を Swift Package Manager へ移した(PR #68)が、Google Maps だけ
CocoaPods に残っている。iOS の依存を SwiftPM にそろえ、CocoaPods(`Podfile`・`pod install`・
`LANG` の指定)を手順から消して、後任が保守する対象を1つ減らす。

急ぐ理由はない。Firebase と違い、Google Maps SDK は 2026-10-20 時点で CocoaPods での配布が続いている。

### 現状(2026-10-20 調査)

- 既定の iOS 実装 `google_maps_flutter_ios` は、最新の 2.18.7 でも podspec しか持たず SwiftPM 非対応。
  これを上げても SwiftPM にはならない。
- flutter.dev が公開している代替実装 `google_maps_flutter_ios_sdk10`(2.19.0)は `Package.swift` を持つ。
  `pubspec.yaml` に依存を足すだけで既定実装を置き換え、Dart 側のコードは変えずに済む。
  - Google Maps SDK 10.x(`ios-maps-sdk` 10.0.0..<11.0.0)、`google-maps-ios-utils` 6.1.3(exact)
  - iOS 16 以上が必要(本アプリは iOS 17 以上なので満たす)
  - SDK 9.x 版の `google_maps_flutter_ios_sdk9` もある(iOS 15 以上)
- `google_maps_flutter_platform_interface` ^2.17.0 が必要なので、`google_maps_flutter` 本体を
  2.12.3 から 2.18 系へ上げる(2.19.0 は Flutter 3.47 以上が必要)。

### 初期スコープ案

1. `google_maps_flutter` を 2.18 系へ上げ、`google_maps_flutter_ios_sdk10` を依存に足す。
2. `flutter build ios --config-only --release` で pod が残らないことを確認し、`Podfile` を残すか消すか決める。
3. iOS は本体フォルダ、Android は英数字パスの複製で release ビルドを通す([ios_build.md](ios_build.md) 4章)。
4. [ios_build.md](ios_build.md) の構成表と手順を更新する。

### セキュリティ・安全上の条件

- 地図エンジンが Google Maps SDK 8.4.0 から 10.x へ2メジャー上がる。地図は航行中に見る画面なので、
  表示が変わっていないことを実機で確かめる。
- 警告・評価のロジックには触れない(地図描画は安全判定に使わない。不変条件6)。
- Firebase の更新(#67・#68)と同時に入れない。実機で問題が出たときに原因を切り分けられなくなる。

### 未決定事項

- SDK 10 版と SDK 9 版のどちらにするか(既定は SDK 10 版の想定)。
- `Podfile` を残すか(将来 pod を使うプラグインが増えたときのため)。

### 完了条件

- `ios/Podfile.lock` に pod が残らない、または `Podfile` 自体が不要になっている。
- 実機で、地図・危険区域・航路線・艇印の描画、ズームと回転、Maps API キー制限の通過、夜の配色を確認した。
- ios_build.md を更新した。

## FUT-003 その日のワークアウトを、1人からチーム全体へ配る

### 状態

- 状態: 候補
- 優先度: 未定
- 初回公開への影響: なし
- 登録日: 2026-10-06(旧「今後のアップデート計画.md」の UPD-001)

### 目的(利用者の要望・2026-10-06)

- チームの1人が、その日のワークアウトのメニューを決めて、チーム全体へ配る。
- 受け取った各自は、**そのワークアウトを始めるか、フリーで漕ぐかを、練習中に自分で選べる。**
  配られたからといって、自動で始まったり、やることを強制されたりしない。

### いまあるもの(2026-10-06 時点)

- ワークアウトのメニュー(`WorkoutPlan`)は端末内だけに保存している(登録・過去のメニュー)。
  サーバーへは送っていない(`WorkoutMenuStore`)。
- 航行前に決めたメニューは「準備ぶん」として持ち、航行が始まると準備された状態になる
  (`UseWorkout.prepared`)。入口は、出艇前のメニューと、航行開始の設定シート。
- 航行中は、ワークアウトのボタンから、登録・過去・準備したメニューを選んで始める。

### 未決定事項

- **配る人**: チームの誰でも配れるのか、管理者だけか。
- **受け取り方**: 配られたメニューを、各自の画面のどこに出すか。
  いまの「準備したメニュー」と同じ場所に「今日のメニュー」として並べる案が素直。
- **始め方**: 「始めるかフリーかを各自が選ぶ」を守るため、配られたメニューは自動で
  始めない扱いにするのか(「漕ぎ出したら始める」の設定を持つメニューをどう扱うか)。
- **配り直し・取り消し**: 練習中にメニューが差し替えられたとき、すでに始めている人の
  ワークアウトをどうするか。
- **有効期間**: 「その日」の区切り(日付か、配った人が取り消すまでか)。
- **通信**: 置き場所と、読み書きの権限(Firebase Rules の変更が要る。本番反映は
  [AGENTS.md](../AGENTS.md) のとおりマージ後にエージェントが行う)。

### セキュリティ・安全上の条件

- **ワークアウトは表示専用のまま。** 警告・安全判定・位置共有の経路へ混ぜない。
  位置の payload に足さず、別のノードに置く(不変条件12・13と同じ考え方)。
  配布の読み書きが失敗しても、航行・警告・位置共有は止めない(原則1)。
- **使い方は使い手が決める**(原則2)。配られたメニューを強制しない。
- 航行中に読ませない。受け取りの通知で、警告の音・表示を覆わない。
