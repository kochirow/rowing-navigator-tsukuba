## 0. 課題の因果と、一括実装で何が変わるか

5件は独立ではない。

```
[B] 位置更新 0.33Hz・8秒欠測 ──┬─→ 推定不確かさが実測精度の3倍(6.8m)へ膨張
                               │      └→ 岸の危険区域(岸から5m)へ「不確かさで」入る
                               └─→ 8秒ごとに候補が消えて復活
                                      └→ [E] alerting⇄clearing の往復
                                             └→ 音声エピソードが再武装し単発音が8秒周期で鳴り直す

[A] 背面で提示層が動かない ──→ 上の過剰警告が「音として」出ていなかっただけ
[C] 他艇の時計ずれ棄却 ──→ 他艇が間欠的に評価から消える（警告漏れ側）
[D] 桟橋という概念が無い ──→ 着艇時に両者停止でも他艇連続音
```

**段階実装なら A を最後に回す必要があった。** A だけ先に入れると、B・D・E が
作っている過剰警告が全部音になって噴き出すからである。

**一括実装ならこの順序リスクは消える。** 同一ブランチに全部入るので、
「音が復活した時点では過剰警告が既に無い」状態しか存在しない。
順序は**ビルド上の依存関係だけ**で決めればよい（第4章）。

## A. バックグラウンドで警告音が出ない

### A-1. 現象と根拠

| 指標 | 値 |
| --- | --- |
| 安全判定が出した音声指示 | **96回** |
| 提示層が音声層へ渡した回数(`warning_presentation_requested`) | **1回** |
| 実際の再生(`audio_play_requested` / `audio_playback_started`) | **各1回** |
| `diagnostic_heartbeat` 249回の `lifecycle` | **249回すべて `paused`** |

唯一鳴った1回は elapsed 6639秒。アプリが `paused → resumed` したのが 6539秒で、
**利用者が桟橋で端末を手に取った直後**である。

7/28 のプレイヤー固着（`audio_play_requested` は出るが再生が進まない）とは**別の障害**。
今回は `audio_play_requested` そのものが出ていない。

### A-2. 原因（確定）

提示層が `lib/hooks/use_navigator.dart:3837` の `useEffect` にある。

```dart
useEffect(() {
  final directive = audioDirective.value;
  ...
  appendRuntimeDiagnostic('warning_presentation_requested', {...});
  unawaited(alert.play(directive.asset));   // ← ここへ到達していない
}, [audioDirective.value?.alertId, ..., isAshore.value]);
```

`useEffect` は build の一部として実行される。iOS はアプリが `paused` の間フレームを
回さないため、`audioDirective.value` が更新されても build が起きず、effect body が
実行されない。GPS・1秒周期の安全評価・ハートビート・記録・位置共有は
すべてタイマー/ストリーム駆動なので**正常に動き続けていた**。

`use_navigator.dart` の `useEffect` は全部で3つしかなく、安全に関わるのはこれだけ。
**安全経路のうちここだけが描画に依存している。**

### A-3. 要件

| ID | 種別 | 要件 |
| --- | --- | --- |
| A-R1 | MUST | 音声指示から再生要求までの経路が、フレーム描画・ウィジェット再構築に依存しないこと |
| A-R2 | MUST | `paused` / `hidden` / `inactive` のいずれでも `imminent` バンドの警告が鳴ること |
| A-R3 | MUST | 陸上判定による停止、航行終了時の停止も同じ経路で描画に依存しないこと |
| A-R4 | MUST | 提示の判断（directive → play/playOnce/stop の写像、重複除去、`eventId` 管理）を**純Dartのクラス**へ切り出し、単体テストで検証できること |
| A-R5 | MUST | `warning_presentation_requested` / `_cleared` を同じ意味で残すこと（ログ互換） |
| A-R6 | MUST | 直前と同じ `(alertId, asset, mode, eventId)` なら再生要求を出さないこと。listener 経由は build より高頻度で走るため、これが無いと連打になる |
| A-R7 | MUST | 既存の直列キュー（`enqueueCommand`）を迂回しないこと。7/28 の固着はキュー迂回が原因であり、同じ穴を開けない |
| A-R8 | MUST | `paused` 中に出た音声指示の回数と、そのうち再生要求へ到達した回数を診断イベントへ残すこと。**再発を次回ログで自動検出できること** |

### A-4. 設計方針

1. `lib/services/warning_presenter.dart`（新規・純Dart）を作る。
   - 入力: `AudioDirective?` と `bool ashore`
   - 出力: `play` / `playOnce` / `stop` のコマンドと、`warning_presentation_requested` / `_cleared` の診断
   - 内部状態: `lastPresentedWarningKey` と A-R6 の重複除去
   - 音声層への依存は関数インターフェースで受け、テストからモックを差せるようにする
2. `use_navigator.dart:2141` で `audioDirective.value = directive` を設定している場所の直後に
   `presenter.apply(...)` を**同期的に呼ぶ**。build を経由しない。
   `isAshore` 側は `ValueNotifier` に `addListener` を張り、`useEffect` は
   「起動時に1回登録、破棄時に解除」だけにする（依存配列は空）。
3. iOS の背面再生資格は既に満たしている（`UIBackgroundModes` に `audio`、
   `AVAudioSessionCategoryPlayback`）。**新規プラグインは導入しない。**
   `audio_service` 等はメディア通知・ロック画面操作のための仕組みで、
   短い読み上げの自動再生には過剰であり、既存の直列キューと二重管理になる。

### A-5. 変更対象

- 新規 `lib/services/warning_presenter.dart`
- 変更 `lib/hooks/use_navigator.dart`（3837行目の `useEffect`、2141行目付近）
- 新規 `test/services/warning_presenter_test.dart`
- 変更 `lib/config/log_config.dart`（A-R8 の診断イベント種別）

### A-6. 完了判定

1. `WarningPresenter` の単体テスト: directive の null↔非null、loop↔playOnce、
   `eventId` 変化、`ashore` 切替、A-R6 の重複除去。
2. **`tester.pump()` を一度も呼ばないウィジェットテスト**で、
   `audioDirective` の更新だけから再生要求が出ること。これが A-R1 の機械的証明になる。
3. 既存の `use_alert` 関連テストがすべて緑（キュー迂回をしていないこと）。

## B. 位置更新レート 0.33Hz・欠測46%

### B-1. 現象と根拠

| 指標 | 今日 | 過去7ログ |
| --- | --- | --- |
| 測位点/時間 | 2609点 / 7990秒 = **0.33Hz** | 0.88〜0.98Hz |
| 測位間隔の中央値 | **2000ms** | 1000ms |
| 8秒以上の間隔 | **262回** | 0〜11回 |
| `gps_stream_error`（8秒無通知でストリーム再起動） | **251回** | 0〜9回 |
| `position_processing_gap` の合計 | **3688秒 = 全体の46%** | — |
| 測位精度の中央値 | **2.6m**（90%点 4.4m） | 同等 |
| Kalman 推定不確かさの中央値 | **6.8m**（90%点 9.8m） | — |

**衛星の受信品質は良い。配信レートだけが落ちている。** これが最重要の事実。

停止に向かうほど間隔が伸びる規則性がある（elapsed 3000〜3095秒）:

```
v=2.75m/s → 2秒間隔
v=1.75    → 3秒
v=1.08    → 4秒
v=0.92    → 5〜6秒
v=0.22    → 8秒 → 無通知 → 再購読
v=1.8〜3.5 → 2秒間隔へ復帰
```

### B-2. 原因の扱い（ここが方針転換点）

原因は**ログだけでは1つに絞れない**。

- 「背面だから」では説明できない（7/26 は背面78%でも 0.88Hz）
- 「処理が重いから」でもない（`totalDurationMs` 中央値 **2ms**、最大 7ms）
- `AppleSettings` も `Info.plist` も v1.0.0 から無変更
- 今回だけの条件: 背面率100% / 権限 `whileInUse` / 他アプリが音声再生中 / v1.1.1 で IMU 50Hz 常時駆動

**一括実装では「原因を特定してから対策を選ぶ」をやらない。**
代わりに、**どの仮説が正しくても正しく動く防御を全部入れる**。
これは妥協ではなく、外部要因（OS の省電力判断）に依存する問題に対する正しい設計である。
OS の配信レートは我々が制御できない。制御できるのは
**「レートが落ちても安全判定が壊れないこと」**であり、そこを完全にする。

### B-3. 要件（すべて今回実装する）

#### 防御（仮説に依存しない）

| ID | 種別 | 要件 |
| --- | --- | --- |
| B-R1 | MUST | **測位が疎になっても、それ自体が警告を作り出さないこと。** `gps_guard_entry`（GPS帯込みでのみ重なる）だけを根拠とする候補は、音声エピソードを**再武装させない**。検知・表示は従来どおり残す（原則1・6） |
| B-R2 | MUST | サイレンスタイマーによる再購読が、**測位が正常に届いている状況を悪化させない**こと。自艇が低速（`stableStopSpeedMetersPerSecond` 未満）かつ直前の測位精度が良好なときは、サイレンス閾値を 8秒 → **15秒**へ延ばす |
| B-R3 | MUST | B-R2 を入れても、真の途絶の検知が遅れないこと。`gps_unavailable` の system fault は `capabilityFaultConfirmSec`（10秒）を維持し、**サイレンス閾値の変更に引きずられない**こと |
| B-R4 | MUST | 閾値と分岐条件は `lib/config/navigator_config.dart` へ置き、**第1章のどの前提から導いたかをコメントへ書く**こと（原則7） |

#### 観測（原因を次回ログで確定させるため）

| ID | 種別 | 要件 |
| --- | --- | --- |
| B-R5 | MUST | 直近60秒の測位数・間隔の中央値・最大を `diagnostic_heartbeat` へ含めること |
| B-R6 | MUST | `gps_environment_snapshot` をセッション中も定期取得すること（現在は開始時1回）。`locationPermission` / `locationAccuracyAuthorization` / `lowPowerModeEnabled` / `thermalState` の変化を捉える |
| B-R7 | MUST | IMU 融合の有効/無効と、その切替を診断イベントへ残すこと（仮説H3の切り分け用） |

#### 運用（利用者の選択肢を増やす。強制はしない）

| ID | 種別 | 要件 |
| --- | --- | --- |
| B-R8 | SHOULD | 位置情報権限を `always` へ引き上げる導線を設定画面に用意すること。**既定は変えない。`whileInUse` のままでも航行は開始でき警告も出る**（原則1・2） |

### B-4. B-R1 の設計判断（記録として残す）

不確かさが膨らんだときに警告を増やすのは、一見「安全側」だが**原則4違反**である。
現在の実装は「確度が低い候補は1バンド下げる」で音を抑えているが、
**候補自体は立つ**ため、フラッピング（課題E）と組み合わさって単発音を撒き散らす。

検討した2案:

- **案1: 不確かさに上限を設ける。** 単純だが「本当に不確かなとき」を隠す。**不採用。**
- **案2（採用）: `gps_guard_entry` だけの候補は音声エピソードを再武装させない。**
  検知・表示は残す。`eventId` を据え置くことで「同じ不確かさが続く間は鳴り直さない」を保証する。
  課題E の E-R3 と**同じ仕組みで実現でき、実装が一本化される**。

### B-5. 変更対象

- `lib/hooks/use_navigator.dart`（heartbeat、GPSスーパーバイザ設定、環境スナップショット）
- `lib/services/resilient_stream_supervisor.dart`（サイレンス閾値を可変にする口）
- `lib/services/device_runtime_diagnostics_service.dart`（定期スナップショット）

- `lib/services/safety_orchestrator.dart`（B-R1。E-R3 と同一箇所）
- `lib/services/permission_service.dart` / 設定画面（B-R8）

### B-6. 完了判定

1. **replay**: 今日のログで、停止中（0.4m/s未満）に `gps_guard_entry` のみを根拠とする
   岸警告の音声指示が **0件**。
2. 単体テスト: 低速+高精度なら15秒無通知まで再購読しない。**それでも `gps_unavailable` は10秒で立つ。**
3. 単体テスト: 高速時・低精度時は従来どおり8秒で再購読する。
4. 既存の GPS 途絶テスト（`gps_health_monitor` / `receive_fault_debouncer`）が全緑。

## C. 他艇レコードの 1/3 を時計ずれで棄却

### C-1. 現象と根拠

| 指標 | 値 |
| --- | --- |
| `other_boat_record_rejected` | **693件**（過去7ログはすべて **0件**） |
| 拒否理由 | **全693件が `serverUpdatedAt:futureTimestamp`** |
| 対象艇 | `a079bb63` 374件 / `c2de456c` 319件（**在席していた他艇2艇の両方**） |
| 発生期間 | elapsed 3秒 〜 7926秒（**セッション全域**） |

### C-2. 原因（確定）

未来時刻の許容がゼロの箇所が**2つ**ある。

```dart
// lib/models/remote_boat_message.dart:179
if (serverUpdatedAt.isAfter(now)) {            // ← 1msでも先なら棄却
  return fail('serverUpdatedAt', ...futureTimestamp);
}
// 直後の observedAt は maxObservedAtFutureSkew(5秒) を許容している
```

```dart
// lib/services/other_boat_track_store.dart:139
var ageAtReceipt = serverNow.difference(message.serverUpdatedAt);
if (ageAtReceipt.isNegative) { return ...futureTimestamp; }   // ← ここも同じ
```

`now` は `DateTime.now() + .info/serverTimeOffset` の**推定値**。
オフセットは RTT 由来の誤差を持ち、端末時計は常時ドリフトする。
**推定が数十ms 遅れれば正常なレコードが「未来から来た」ことになる。**

`observedAt` に5秒を許して `serverUpdatedAt` に0を許さないのは非対称であり、
RTDB Rules 側が端末差を5秒まで許容していることとも整合しない。

### C-3. 安全上の意味

**警告漏れ側の欠陥である。** 他艇の位置が間欠的に落ちると

原則6「データ欠損は安全の根拠にならない」に正面から反する。

## D. 桟橋エリア（着艇時の他艇連続音）

### D-1. 現象と根拠

**着艇して艇を並べているだけ**であり、第1章の定義では正常な運用。
原則4により、ここで鳴る連続音は**不具合**である。

### D-2. 原因（確定）

停止中の抑制が他艇に効かない。設計上の明示的な除外になっている。

```dart
// lib/services/safety_orchestrator.dart:844

```

```dart
// lib/config/alert_presentation_config.dart:162

// other_boat は入っていない
```

除外の理由（「相手が接近してくるため」）は川の中では正しい。
**桟橋では双方が停まっているのでこの理由が成立しない。**

### D-3. 設計判断: 既存の陸上エリアを広げない

既存の `ashoreArea` を桟橋まで広げれば音は止まる。**が、採らない。**

- 陸上判定は**すべての音**を止める。桟橋の沖側は水面であり、そこを通過する他艇の警告まで消える
- 陸上確定は30秒。着艇の直前直後に30秒の空白ができる
- 「陸上にいる」は事実の判定、「桟橋にいる」は場所の宣言。混ぜるとログからどちらで止まったか読めない

→ **新しい概念として桟橋エリアを追加する。**

### D-4. 桟橋エリアの定義

| 効果の範囲外 | 静的危険区域（岸・橋・杭）の扱いは変えない。既存の低速静音がそのまま働く |

## E. 岸警告が毎秒 alerting⇄clearing で点滅

### E-1. 現象と根拠

桟橋付近（elapsed 6561〜6755秒、194秒間、平均速度 0.25m/s）:

| 指標 | 値 |
| --- | --- |
| 同一 `alertId`（`static_collision/shore/v:shore_north/-`）の再武装 | **79回** |
| 遷移（セッション全体） | `alerting→clearing` 130回 / `clearing→alerting` 100回 / `clearing→safe` 30回 |
| 同一ミリ秒での往復 | 例: `6571.002s alerting` と `6571.002s clearing` |
| その間の音声指示 | 24回。**うち18回が GPS 再接続の±2秒以内**（8秒周期と一致） |
| `reasonCodes` の `SOURCE_EDGE` | 同じ `shore_north` の **edge 23 / 24 / 25 が入れ替わる** |

### E-2. 原因（確定）

**原因1: 解除証拠が「候補が消えたこと」だけで立つ。**

```dart
// lib/services/safety_orchestrator.dart:203
final clearEvidence = previousById.entries
    .where((entry) => !byId.containsKey(entry.key) && !retireAlertIds.contains(entry.key))
```

前回あって今回ない候補は、それだけで解除証拠になる。
**測位が8秒来なければ候補は消える。** GPS の 8秒周期にぴったり同期していた。

**原因2: 再出現のたびに音声エピソードが再武装する。**

`clearing → safe` まで到達した30回は、次の出現が「新しい脅威」として扱われ新しい `eventId` が振られる。
`PRESENTATION_STABLE_STOP_SINGLE`（停止中は連続音→単発音）で正しく1段下げているのに、
**その「単発」が8秒ごとに新規発火する。安定停止の抑制がフラッピングで無効化されている。**

### E-3. 要件

| ID | 種別 | 要件 |
| --- | --- | --- |
| E-R1 | MUST | 測位が届かないことを警告の解除証拠にしないこと。候補が消えた理由が「脅威が消えた」ではなく「入力が来なかった」場合、`clearConditionsMet` を立てない（原則6） |
| E-R2 | MUST | E-R1 は既存の `AlertDataQuality.unusable` の3秒上限を壊さないこと。古い物理警告が永久に残ってはいけない。**対応する system fault が必ず同時に立つこと**（不変条件3） |
| E-R3 | MUST | 同一 `alertId` が短時間（`stableThreatEpisodeRetentionDuration` 以内）に再出現した場合、音声エピソードを**据え置く**こと。単発音が鳴り直さないこと。**B-R1 と同一の仕組みで実装する** |
| E-R4 | MUST | 集約された静的警告で代表 edge が入れ替わっても `alertId` と音声エピソードが変わらないこと。`SOURCE_EDGE` が診断表示専用であることをコード上明示すること |
| E-R5 | MUST | 同一 `alertId` の `alerting⇄clearing` 往復回数を単位時間あたりで診断イベントへ残すこと。**次回ログでフラッピングを自動検出できること** |
| E-R6 | MUST | 画面のバナーが1秒周期で点滅しないこと。`clearing` フェーズ中は表示を保持すること |

### E-4. 設計方針

**入力の有無と、脅威の有無を分けて表現する。**

現在 `SafetyOrchestrator` は「今回の候補集合」しか持たないため、
「脅威が無い」と「入力が無い」が同じ形（候補が無い）になっている。
評価バッチへ**「この評価は有効な測位に基づくか」**を渡し、

- 有効な測位あり + 候補なし → 従来どおり解除証拠を立てる
- 有効な測位なし（GPS欠測中） → 解除証拠を立てず `dataUnknown` として保持

とする。既に `AlertClearEvidence.isUsable` と `dataUnknown` の仕組みがあるので、
**新概念を足すのではなく既存の経路へ正しく流し込む。**

### E-5. 変更対象

- `lib/services/safety_orchestrator.dart`（203行目付近の解除証拠生成、音声エピソード管理）
- `lib/services/alert_state_machine.dart`（必要なら `_applyNonDanger` の分岐）
- `lib/hooks/use_navigator.dart`（評価バッチへ測位の有効性を渡す）
- `test/services/safety_orchestrator_test.dart` / `test/services/alert_state_machine_test.dart`

### E-6. 完了判定

1. 単体テスト: 岸の脅威が継続したまま測位が8秒欠測 → `alerting` を維持し、
   `gps_unavailable` の fault が同時に立つ。単発音は鳴り直さない。
2. 単体テスト: 測位は正常で脅威が本当に消えた → 従来どおり `clearing → safe`。
3. 単体テスト: 代表 edge が 24→25 に変わっても `eventId` が変わらない。
4. **replay**: 今日のログで同一 `alertId` の `clearing→alerting` が
   **岸100回 → 10回未満**、**他艇77回 → 10回未満**。
5. 既存の不変条件テスト（特に実データを使う統合テスト）が全緑。

### E-7. リスク

**E-R1 は警告が「消えにくく」なる方向の変更である。**
E-R2 の3秒上限と system fault の同時成立を必ずテストで固定すること。

## 5.5 実装中に見つかった、計画に無かった不具合

### (1) 抑制規則が「下げた結果を上書きして」いた

`safety_orchestrator.dart` の抑制チェーンが `baseBehavior`（抑制前）を見て
代入していたため、低速静音で `visualOnly` にした岸の警告が、直後の
安定停止の分岐で `singleAction` へ**戻っていた**。

実機ログの `PRESENTATION_STABLE_STOP_SINGLE` 292サンプルの正体がこれである。
抑制規則は**下げるだけ**にした（`_quieter`）。

### (2) 安定停止のしきい値にヒステリシスが無かった

係留中の艇は波と測位ノイズで 0.0〜0.6m/s を往復する。単一のしきい値
（0.4m/s）だと安定停止に入っては抜けるを繰り返し、そのたびに低速静音の
3秒確定待ちが巻き戻って単発音が漏れていた。

入るしきい値 0.4m/s / 出るしきい値 0.8m/s の非対称にした
（`stableStopExitSpeedMetersPerSecond`）。止まったと判定するのは今までどおり
速く、動き出したと判定するのは慎重になる。

### (3) 課題E の真因は「1ティックに2回の安全評価」だった

計画では解除証拠の生成ロジックを疑っていたが、実際は
`use_navigator.dart` の `runGpsWatchdogTick` が、同じティックで
**推測航法の評価（候補あり）と GPS断の空評価（候補なし）を両方**流していた。

実機ログで `alerting` と `clearing` が同一ミリ秒に並んでいたのはこれが理由。
1ティックにつき1回だけ適用するようにした。オーケストレータ側の解除証拠の
仕組みは変えていない（不変条件3を維持）。

### (4) プロットツールの空配列がプロファイルのハッシュを変えていた

`mooringAreas: []` を常に書き出すと、桟橋を1つも引いていないプロファイルでも
JSONのバイト列が変わり、`firestore.rules` に固定した SHA-256 と食い違う。
**1件以上あるときだけ**書き出すようにした（テストで固定）。

## 5.6 計画から意図的に外したもの

### B-R8（位置情報権限を `always` へ引き上げる導線）— 見送り

`permission_service.dart` には既に

> 停止中の自動起動は行わないため、「常に許可」は必須にしない

という明示的な設計判断があり、`whileInUse` + Background Location mode で
継続する前提が文書化されている。**この判断を覆す証拠がまだ無い。**

かわりに B-R5〜B-R7 の観測（測位レート・環境スナップショットの定期取得）を
入れたので、次回ログで `locationPermission` と実効レートを突き合わせられる。
そこで `always` が効くと分かってから導線を作る。

### D-R15〜D-R18（プロファイル JSON の version 9 / hash 更新）— 座標プロット後

`assets/data/sakuragawa_obstacles.json` は**一切変更していない**。
桟橋の座標が入る前に version と hash を上げても、中身の無い変更で
「検証済み」状態を動かすだけになる。座標をプロットしたあとに実行する。

アプリ・ツールは `mooringAreas` が無い状態で完全動作する（テストで固定）。

### 桟橋エリア内では岸の警告音も止める（計画に無かった追加）

計画では桟橋エリアの効果を「他艇の音だけ」に限定していたが、replay の結果、
桟橋での岸の音声指示が残った（44 → 9）。桟橋は定義上いつも岸の隣にあり、
艇は必ず岸へ寄せて止めるので、そこで岸の警告を鳴らすのは原則4に正面から当たる。

**区域内かつ自艇が低速のときだけ**、`lowSpeedMutedCategories`（岸・橋・橋脚・
逆走）の音も止めるようにした。流木・杭・中州は視認しづらく帰結が大きいので
対象外のまま。漕いでいれば従来どおり鳴る。これで 9 → 5 になった。

## 5.7 2台目のログによる検証と、B-R2 の撤回（2026-08-05 追記）

2台目（iPhone15,4 / 1x / 151分）のログが入り、**実装時に存在しなかったデータ**で
検証できた。ホールドアウト検証の結果と、そこで判明した誤りを記録する。

### 確定したこと

2台の数字がほぼ一致し、「今日だけ・この端末だけ」の可能性が消えた。

| 指標 | A機(iPhone15,4) | B機(iPhone17,5) |
| --- | ---: | ---: |
| 測位間隔の中央値 | **2003ms** | **2000ms** |
| 音声指示 → 提示層へ到達 | **152 → 0** | 96 → 1 |
| 他艇レコードの棄却(futureTimestamp) | 806 | 693 |
| 他艇を保持できていた評価 | **61.3%** | 76.0% |

### ホールドアウト検証（A機のログ、開発に未使用）

| 指標 | 修正前(実測) | 修正後(replay) |
| --- | ---: | ---: |
| 音声指示の総数 | 152 | **16** |
| `clearing→alerting` | 282 | **2** |

### ❌ B-R2（無通知の判定を15秒へ延長）は誤りだった。撤回する

計画では「OSが配信を絞っているところへ8秒で購読を張り直すと暖機を捨てる」と
判断した。**2台のログはこれを否定した。**

```
無通知に対する getCurrentPosition の実績
  A機: 290/290 成功  所要 中央値4ms  得た測位の鮮度 中央値64ms
  B機: 251/251 成功  所要 中央値2ms  得た測位の鮮度 中央値42ms
```

**OS は常に新鮮な測位を持っていて、stream だけが配信していない。**
そして one-shot 復旧は stream のタイムアウトが引き金である
(`use_navigator.dart` の `onError`)。閾値を延ばせば、確実に取れる測位を
その分だけ捨てることになる。

| | 延長条件を満たす stream_error | 追加で失う位置なし時間 |
| --- | ---: | ---: |
| A機 | 126 / 290 (43%) | +882秒（欠測合計の +21%） |
| B機 | 176 / 251 (70%) | +1232秒（同 +33%） |

さらに推測航法の不確かさは gpsAge 4.6秒で既に 29.8m まで膨らむ。欠測を伸ばせば
不確かさが増え、B-R1 で抑えた `gps_guard_entry` の過剰警告が戻ってくる。
**両方向に悪い。**

### 代わりに入れたもの: 測位ポーリング（B-R2 改）

待つのをやめて、こちらから取りに行く。

| ID | 種別 | 要件 |
| --- | --- | --- |
| B-R2' | MUST | stream が `gpsPositionPollAfterSilence`(2秒)届かなければ `getCurrentPosition` で測位を取りに行くこと。以後 `gpsPositionPollMinimumInterval`(1秒)ごと |
| B-R2'' | MUST | 取れた測位が stream の最新より新しくなければ流さないこと（二重処理の防止） |
| B-R2''' | MUST | ポーリングの失敗で stream・推測航法・警告経路を止めないこと（原則1） |
| B-R2'''' | MUST | 無通知での再購読(8秒)は「購読そのものが死んだ」検知として残すこと |

**見積り**（1回2〜4msで成功する前提。根拠は上の541/541）:

| | 現状 | ポーリング後の見込み |
| --- | ---: | ---: |
| A機 | 3005点 / 0.33Hz / 2秒以上の穴 2004回 | **0.84Hz / 穴 0回** |
| B機 | 2609点 / 0.33Hz / 2秒以上の穴 1302回 | **0.82Hz / 穴 0回** |

これは**見積りであって実測ではない**。次回の実機ログで
`gps_position_poll_succeeded` の件数と `positionIntervalMedianMs` を見て確定する。

### 併せて満たした計画の未達項目

| ID | 内容 | 状態 |
| --- | --- | --- |
| E-R5 | フラッピングの診断イベント | `alert_phase_flapping` を追加（60秒窓で10回超のとき1件） |
| A-6-2 | 描画非依存の機械的証明 | `test/hooks/warning_presentation_frame_independence_test.dart`。**pump を呼ばなければ `useEffect` が走らないこと**（障害の再現）と、直接呼び出しは届くこと（対策）を対で固定。あわせて `use_navigator.dart` が `useEffect` から音声層を呼んでいないことをソース契約として検査する |

### replayハーネスの測定汚染を修正

`SCENARIO` 未指定のとき同梱シナリオ（合成他艇3艇）を自動で読んでいたため、

`SCENARIO=default` と明示させる。
