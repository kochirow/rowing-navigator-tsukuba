## 1. 争点の詳細と、そこから出た新しい事実

### 1.1 自己エコー案と「別teamId」仮説は撤回する

撤回理由は codex の指摘どおりで、RTDB はオフライン中の書き込みをローカルに保持し、
ローカル更新でもlistenerを発火させる。したがって自分の書き込みが自分に見えても、
サーバーでの書き込み受理と読み取り認可を独立に証明できない
([公式: Offline capabilities](https://firebase.google.com/docs/database/flutter/offline-capabilities))。
自分の書き込みが自分のストリームへ戻っても、サーバーから読めた証明にはならない。

さらに調べたところ、**「読み取り拒否が静かに起きる」という前提も、
現行コードで確認できる主経路には当てはまらない。**
`lib/services/message_service.dart:365` の `onStreamError` は、
`onChildAdded` 系すべての購読エラーを `transportFaultCodes` に積み、
`controller.addError` で `ResilientStreamSupervisor` にも伝える。
読み取りが Rules で拒否されればここに出る。つまり認可の失敗は既に可視である。

ただし、**購読がエラーなしで開いていることと、最新のサーバーデータを受け取れていることは同じではない。**
RTDBの `/.info/connected` もその端末とサーバーの接続状態であり、別端末の接続や相互受信は保証しない
([公式: Detecting Connection State](https://firebase.google.com/docs/database/flutter/offline-capabilities#section-connection-state))。

また、公開資料調査後に5パッケージを再確認すると、A〜Eの `teamIdHash` は全て `bdbe2f79` だった。
したがって「B・Eだけが別teamIdを見ていた」という仮説は、現存ログと矛盾する。

**採用する対策**:

- 「端末とデータ」に、同一チームか確認する**短いteam指紋**、端末を区別する**短いboat/UID指紋**、
  **ビルド指紋**を表示する。生のUID、teamId、招待コードは表示・ログ保存しない。
- 二端末確認では、**team指紋とビルド指紋は同じ、boat/UID指紋は異なる**ことを見る。
- 本当のend-to-end証拠は、二端末が互いの異なるboat/UID指紋を受信し、
  サーバー時刻付きの位置が更新され続けたことを両方のログで確認して作る。

指紋表示は将来の向き先誤りを切り分ける予防策としては有用だが、
それをB・Eの原因対策とは扱わない。

### 1.2 `permission-denied`:P1の修正 + P0の確認ゲート

事実関係は確定している。

- C(…5757700)は起動直後に `permission-denied` を2回出し、**19.7秒で自力回復した**
  (`elapsedMs` 133 / 9,579 → 19,731 で `position_sharing_recovered`)。
  したがって少なくともこの事例では、拒否状態は恒久障害ではなかった。
- 回復できたのは、送信経路(`LatestOnlyAsyncPublisher.onFailure`、`use_navigator.dart:592`)が
  **エラー種別を見ずに再送し続ける**ためである。
- 一方、`245eb79` で入った setup 経路(`sharing_capability_monitor.dart:171`)は
  `permissionDenied.isRetryable = false` で**1回も再試行しない**。

ここで追加の注意がある。`permission-denied` は「認証トークン不備」と同義ではない。
RTDB Rulesは読み書きの認可に加え、値の検証もサーバー側で行う
([公式: Realtime Database Security](https://firebase.google.com/docs/database/security))。
現行Rulesの `live_positions/$boatId/u` には、前回のサーバー到着時刻から1,700ms以上開ける検証がある。
したがってCの送信拒否は、認証やチーム所属の伝搬待ちだけでなく、
レート制限や他の `.validate` 不成立であった可能性も残る。
失敗時のペイロードとRules判定内訳が過去ログにないため、原因は確定できない。

私は前回これを「P0の確定不具合」と書いたが、行き過ぎである。
ログで観測された `permission-denied` は**送信経路のもの**であり、
clear / onDisconnect の setup 経路で同じことが起きた実例はまだない。
したがって正しい位置づけは **「同一症状に対する方針が経路間で矛盾している」= P1の設計不整合**で、
出艇可否に関わるのは「修正版で実際に共有が確立するか」という **P0の確認ゲート**のほうである。

修正の形:

- 失敗を `clear` / `onDisconnect arm` / `initial write` / `periodic write` に分ける。
  `onDisconnect` は登録時と実行時の2回、サーバーがRulesを確認する
  ([公式: How onDisconnect Works](https://firebase.google.com/docs/database/flutter/offline-capabilities#how_ondisconnect_works))。
  登録成功と最終的な削除成功は別の証拠とする。
- `permission-denied` で認証更新を機械的に行わない。認証ユーザー有無、IDトークン更新時刻、
  team membership、App Check有効化状態、直前の書き込みACKからの間隔を記録し、
  **再試行で変化する前提がある場合だけ**更新・再取得する。
- 有限回(3回程度)で打ち切る。**5s/10s/20s という具体値に実ログ上の根拠はない**ので、
  「起動直後の回復に約20秒かかった実例が1件ある」ことだけを根拠として明記し、
  設定値のコメントにそう書く(設計原則7)。
- 各試行の工程・時刻・失敗理由を残す。
- 純Dartテストに加えて、Firebase Emulator で「未認証」「所属なし」「Rules検証不成立」
  「一時切断」を別ケースで固定する。

### 1.3 【新規・P1】1点目の粗い測位が、後続の良い測位を17秒間はじいていた

codex の指摘に従って原文 5.5 を読み直し、C セッションの先頭30秒を精査した結果、
**両者が見落としていた実装上の欠陥**が出てきた。

```
elapsed_ms      0  raw 36.08141,140.21385  accuracy 1026.5m  → accepted(推定不確かさ 2512m)
elapsed_ms  2,006  accuracy 3.54m  speed 0.0  → rejected
elapsed_ms  3,006  accuracy 3.54m           → rejected
elapsed_ms  4,007  quality degraded → unusable(consecutiveRejected 3)
elapsed_ms  4,007 / 6,015 / 7,017 / 9,010    → rejected(3.5〜4.7m)
elapsed_ms 11,010  accuracy 4.75m           → accepted
elapsed_ms 17,006  quality unusable → good
```

棄却された測位はすべて 36.08182,140.21481 付近で、**1点目から約97m離れている**。
`lib/services/gps_position_filter.dart:79` の速度飛び判定は、直前の受理点との距離を経過時間で割る。
97m ÷ 2s = 約48m/s となり、当然はじかれる。
精度3.5〜4.7mの測位が複数回一貫した集団を作っているため、
そちらが実位置に近い可能性は高い。ただし基準点との実測がなく、
このログだけで「後続点が正しい座標」と絶対的には証明できない。

問題は逃げ道の条件である。

```dart
if (distance / elapsedSeconds > maxSpeedMetersPerSecond &&
    !(acceptLowAccuracy && isLowAccuracy(position))) {
  return false;
}
```

例外は**入ってくる測位が低精度のとき**にしか効かない。
**基準側(`_lastAccepted`)が低精度であることは考慮されていない。**
その結果、精度1,026m の1点目が基準として居座り、精度3.5m 前後の一貫した後続測位を
「ありえない飛び」として連続で拒否し、4〜17秒のあいだ品質 `unusable` が続いた。

これは「運用でGPSの安定を待つ」だけで片付けず、コードでも扱うべき再捕捉の不整合である。
実際にこのセッションでは十数秒間、自艇位置の不確かさが大きいままか、GPS品質が使用不能になった。
頻度は5セッション中1件(他の開始時accuracyは2.3〜33m)。

公式仕様上、Androidのaccuracyは「真の位置がその半径内にある確率68%の推定値」、
Appleでも「位置の不確かさの半径」である
([公式: Android `Location.getAccuracy`](https://developer.android.com/reference/android/location/Location#getAccuracy()),
[公式: Apple `horizontalAccuracy`](https://developer.apple.com/documentation/corelocation/cllocation/horizontalaccuracy))。
そのため、前回accuracy + 今回accuracyを「許可する移動距離」へ単純加算する案は採用しない。
前回が1,026mなら、1km級の不正ジャンプまで事前フィルタが通すおそれがある。

採用する最小修正案(実装前提は確認済み。`acceptLowAccuracy` は
`enableRobustPositionFilter = true`(`navigator_config.dart:52`)により**本番で真**なので、
下の条件は実際に発火する):

- `acceptLowAccuracy` の場合、**今回fixだけでなく前回受理fixが低精度のときも**、
  速度だけの事前ゲートで拒否せず `RobustPositionEstimator` へ渡す。
- 下流には既に、測位精度と推定共分散を使う正規化innovation、soft/hard gate、
  連続した候補による再捕捉がある。統計的な判断を2か所に重複させず、その既存経路で判断する。
- `GpsPositionFilter.accepts` のbool返却を理由付き結果へ変え、`gps_fix_envelope` に
  `invalidAccuracy` / `staleTimestamp` / `nonMonotonic` / `implausibleSpeed` /
  `lowAccuracyAnchorBypassed` を残す。現状は速度飛びも `FixRejectionReason.stale` と記録されるため、
  将来ログだけでは今回のような原因を直接判定できない。
- 前回/今回accuracy、距離、単調時間差、下流のestimator dispositionも、採用・棄却理由と同じイベントへ残す。
- 単体テストは少なくとも次の3本にする。
  1. 粗い基準点 → 良好な一貫測位が下流へ渡る。
  2. 良好な基準点 → 現実的でない良好精度のジャンプは今までどおり拒否する。
  3. 実ログ相当の連続点で `RobustPositionEstimator` が有限時間内に再捕捉する。

原文 5.5 の運用上の提案(GPSが正常になるまで離岸しない)は**そのまま有効**であり、残す。

### 1.4 `useNavigator` のテストに関する表現の訂正

`test/hooks/warning_presentation_frame_independence_test.dart:79` は

### 1.5 他艇の判定スナップショット:P2へ戻す。ただし形を変える

codex の反論は妥当で、`otherBoatCount` と棄却件数だけでは
「受信した」以降(判定へ渡った / 候補が生成された / 危険なしと判定された)を分けられない。

ただしリングバッファ(他艇の位置・精度・受理結果を前後2分保持)は、
実装量とプライバシー負担が段階として重い。**先に、周期サンプルを1行拡張するほうが良い。**

`position_processing_sample`(10秒周期、既存)へ次を足す:

- 最近接他艇までの距離、その相対到達時間(DCPA/TCPA相当)
- その tick で生成された衝突候補数
- 候補が0だった理由の区分(受信0 / 全艇が遠い / 掃引で重ならない)

これで「危険なしと判定された」が証拠になる。位置そのものは保存しないので、
プライバシー負担はほぼ増えない。リングバッファは、これで足りないと分かってから。

### 2.1 共有不能だった端末では、他艇入力も全期間ゼロだった

| session | 艇・席 | heartbeat の共有状態 | `otherBoatCount` |
| --- | --- | --- | --- |
| …4599956 (A) | 4x・bow | healthy | 0:80 / 1:243 / 2:240 |
| …5014567 (B) | 8+・7 | unavailable 82/82 | **0:224(全サンプル)** |
| …5757700 (C) | 2x・stroke | healthy 208/209 | 0:90 / 1:230 / 2:253 |
| …7606648 (D) | 8+・cox | healthy | 0:4 / 1:78 / 2:254 |
| …7619060 (E) | 8+・7 | unavailable 143/143 | **0:394(全サンプル)** |

E の時間帯(22:07–23:21)は A・C・D と完全に重なり、その間 A・C・D は常時1〜2隻を受信していた。
B・E の `events.jsonl` には受信系の fault が1件もない。

**言えること**: 過去の B・E では、位置送信の初期設定失敗と他艇入力ゼロが同時に発生していた。
その間、この艇には他艇衝突警告の入力が存在しなかった。計118分。
A・C・Dの最大観測数が、Eを除く相互3艇のうち2艇だったことから、Eも他艇側へ配信されていなかった可能性が高い。
ただし、各時刻の艇識別子を保存していないため「他艇の画面にEが一度も出なかった」は強い推定であり、直接証拠ではない。

**言えないこと**: 送信失敗が受信失敗を「引き起こした」こと、原因が認証・App Check・
チーム所属のどれであること。相関は極めて強いが、**原因は候補の段階である。**

**現行コードで直ったかも未確認である**(2026-08-07 以降の実機ログが存在しない)。

### 2.1a 送受信が同時に落ちる条件は、Rules上に1つだけ存在する(最有力候補)

`database.rules.json` を読むと、`live_positions` の読み書きは**同じ述語**に依存している。

- `.read`(チーム全体): `root.child('team_members').child($teamId).child(auth.uid).exists()`
- `$boatId/.write`: `auth.uid === $boatId && (… || root.child('team_members').child($teamId).child(auth.uid).exists())`

つまり **`team_members/<teamId>/<uid>` がサーバー側に無い端末は、送信も受信も同時に拒否される。**
B・E の症状(送信不能 + 他艇入力ゼロ、同一端末で再発)を、単一の条件で説明できる唯一の経路である。
`teamIdHash` が5端末で一致していても矛盾しない。**teamIdHash は端末内設定の指紋であって、
サーバー上の所属レコードの有無ではない**からである。

しかもこの述語は `team_members/$teamId/$uid` の `.read` により、**その端末自身が読める**
(`auth.uid === $uid` かつ `team_users/<uid>/teamId` が一致する場合)。
したがって航行開始時に1回読んで、次を診断へ残せばよい。

- `team_members` に自分のレコードがあるか(true/false)
- `team_users/<uid>/teamId` と、いま使っている teamId 指紋が一致するか
- 読み取り自体が拒否されたか

**booleanが2つ増えるだけで、B・Eの原因が次のログで確定する。** 実装量に対して回収が最も大きい。
これも候補であり確定ではないが、**最初に潰すべき候補**である。

### 2.2 その他

### P0:実運用開始前に通す確認ゲート(コードの確定不具合という意味ではない)

問題が出た 8+・7番端末を含む2台で行う。端末操作は5〜10分を目安とし、
Rules・App Checkの管理画面確認と診断ZIP照合は別枠で行う。

1. 両端末へ同じ最新ビルドを入れ、**Git SHA まで控える**。
2. 「端末とデータ」で、**team指紋とbuild指紋は一致し、boat/UID指紋は異なる**ことを確認する。
3. 屋外でGPSが `good` になるまで待ってから開始する(原文 5.5 の運用提案)。
4. 両端末で共有状態が正常、相互に地図表示され、移動に追随すること。
5. 一方を終了し、他方から約30秒以内に消えること。これは `onDisconnect` 登録成功とは別に、
   サーバー側削除まで働いたことの確認になる。

7. 本番RTDB Rules がリポジトリと一致すること。画面の目視だけでなく、取得した本番Rulesと

8. Firebase ConsoleのApp Checkメトリクスで、テストに使った配布版からRTDBへのリクエストが
   `Verified` として到達していることを確認する。App Check公式は、enforcement前に正規利用者を

1. **P1-1(GPSフィルタ)を先に入れる。** 安全機能そのもので、純Dartで閉じ、短い対象テストで検証できる。
2. 次に P1-2〜6 をまとめて1回のビルドへ載せる。ログ改善は**同じビルドで水上へ出さないと1回分無駄になる**。

   teamId相違を第一候補にはしない。
5. 切り分いた結果に応じて P2 を選ぶ。順番を決めるのは次のログであって、本書ではない。

### 4.1 管理者が手動で行う確認

次の操作は、アプリのコード変更やローカルテストでは代替できない。

1. **本番Rulesの取得と比較**
   - Firebase Consoleで対象プロジェクトと対象Realtime Databaseインスタンスを確認する。
   - 管理権限のある環境から、本番の `/.settings/rules.json` を**GETだけ**で取得する。
     Firebase公式はこのパスで配備中Rulesを取得できるとしている
     ([公式: Managing RTDB Rules via REST](https://firebase.google.com/docs/database/rest/app-management))。
   - アクセストークンは秘密情報なので、文書、診断ZIP、Git、チャットへ貼らない。
   - JSONのキー順・空白を正規化してSHA-256を計算し、リポジトリの `database.rules.json` と比較する。
   - RESTのPUTは既存Rulesを上書きするため、この確認作業では実行しない。

2. **App Checkの確認**
   - Firebase Console → App Check → Realtime Databaseを開く。
   - P0試験の時刻帯を絞り、`Verified` / `Outdated client` / `Unknown origin` /
     `Invalid` の割合を記録する。メトリクスは集計値なので、単独で特定端末の成功証明にはしない。
   - enforcement状態と変更日時も記録する。enforcementを変更する場合は別作業とし、
     正規端末が `Verified` になることを確認してから行う。
   - Release版は現行コードどおりPlay Integrity / App Attest with DeviceCheck fallbackを使い、
     debug providerやdebug tokenを含むビルドを配布しない。公式もdebug tokenとdebug buildを
     秘密にし、本番配布しないよう警告している
     ([公式: App Check debug provider](https://firebase.google.com/docs/app-check/flutter/debug-provider))。

3. **実機の対応表を残す**
   - 試験日時、端末名、艇・席、アプリ版、build番号、Git SHA、team指紋、boat/UID指紋、
     診断ZIP名を1行で対応付ける。
   - 生のUID、teamId、招待コード、App Check tokenは書かない。
   - 音声については「アプリが再生開始したログ」と「人が実際に聞こえた確認」を別欄にする。

## 6. 公開資料から採用した設計上の要点

- RTDBはローカル更新でもlistenerを呼ぶため、自己エコーをサーバー往復の証明にしない。
- `/.info/connected` は各クライアント固有であり、他端末との相互通信成功を意味しない。
- `onDisconnect` は登録時と実行時にRulesが評価される。登録ACKと実際の削除を別々に記録する。
- `/.info/serverTimeOffset` は大きな時計差の検出用で、精密な時刻源として扱わない。
- App Checkは、配布版のリクエストメトリクスを確認してからenforcementを判断する。
- GNSS accuracyは不確かさであり、物理速度制限へそのまま足す免責距離ではない。
- 本番Rulesは「デプロイした記憶」ではなく、配備中Rulesを再取得してハッシュ比較する。
