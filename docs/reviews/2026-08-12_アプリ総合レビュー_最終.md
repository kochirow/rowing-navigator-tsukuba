## 1. 争点の詳細と、そこから出た新しい事実

### 1.1 自己エコー案は撤回する。ただし「静かに空になる」穴は別の形で残る

撤回理由は codex の指摘どおりで、RTDB はサーバー確認前にローカルで購読イベントを発火する。
自分の書き込みが自分のストリームへ戻っても、サーバーから読めた証明にはならない。

さらに調べたところ、**そもそも「読み取り拒否が静かに起きる」という私の前提が誤っていた。**
`lib/services/message_service.dart:365` の `onStreamError` は、
`onChildAdded` 系すべての購読エラーを `transportFaultCodes` に積み、
`controller.addError` で `ResilientStreamSupervisor` にも伝える。
読み取りが Rules で拒否されればここに出る。つまり認可の失敗は既に可視である。

**残る本当の穴は、認可ではなく「向き先」である。**
自艇が別の `teamId` パスを購読していれば、読み取りは成功し、エラーも出ず、
ただ永久に0隻になる。B・E がまさにその見え方をしていた
(受信エラー0件・他艇0隻・共有不能)。この穴は自己エコーでは検出できない
(自艇の書き込みも同じ間違ったパスへ行くため、エコーは正常に返る)。

**代替案(こちらを採用する)**:

- 「端末とデータ」画面と診断 manifest に、**認証UID・teamId(またはそのハッシュ)・購読パス**を出す。
- 出艇前の二端末確認で、**両端末のその値が一致していること**を目視で突き合わせる。

実装は表示とログだけで、安全経路に触れない。B・E の再発を人が5秒で切り分けられるようになる。

### 1.2 `permission-denied`:P1の修正 + P0の確認ゲート

事実関係は確定している。

- C(…5757700)は起動直後に `permission-denied` を2回出し、**19.7秒で自力回復した**
  (`elapsedMs` 133 / 9,579 → 19,731 で `position_sharing_recovered`)。
  したがって起動直後のアクセス拒否は恒久障害ではない。
- 回復できたのは、送信経路(`LatestOnlyAsyncPublisher.onFailure`、`use_navigator.dart:592`)が
  **エラー種別を見ずに再送し続ける**ためである。
- 一方、`245eb79` で入った setup 経路(`sharing_capability_monitor.dart:171`)は
  `permissionDenied.isRetryable = false` で**1回も再試行しない**。

私は前回これを「P0の確定不具合」と書いたが、行き過ぎである。
ログで観測された `permission-denied` は**送信経路のもの**であり、
clear / onDisconnect の setup 経路で同じことが起きた実例はまだない。
したがって正しい位置づけは **「同一症状に対する方針が経路間で矛盾している」= P1の設計不整合**で、
出艇可否に関わるのは「修正版で実際に共有が確立するか」という **P0の確認ゲート**のほうである。

修正の形(codex 案を採用):

- アクセス拒否時に**認証状態とチーム所属を再確認**してから再試行する。
- 有限回(3回程度)で打ち切る。**5s/10s/20s という具体値に実ログ上の根拠はない**ので、
  「起動直後の回復に約20秒かかった実例が1件ある」ことだけを根拠として明記し、
  設定値のコメントにそう書く(設計原則7)。
- 各試行の工程・時刻・失敗理由を残す。
- 純Dartテストに加えて、Firebase Emulator で工程全体を通す。

### 1.3 【新規・P1】1点目の粗い測位が、後続の良い測位を17秒間はじいていた

codex の指摘に従って原文 5.5 を読み直し、C セッションの先頭30秒を精査した結果、
**両者が見落としていた実装上の欠陥**が出てきた。

```
elapsed_ms      0  raw 36.08141,140.21385  accuracy 1026.5m  → accepted(推定不確かさ 2512m)
elapsed_ms  2,006  accuracy 3.54m  speed 0.0  → rejected
elapsed_ms  3,006  accuracy 3.54m           → rejected
elapsed_ms  4,007  quality degraded → unusable(consecutiveRejected 3)
elapsed_ms  4,007 / 6,015 / 7,017 / 9,010    → rejected(3.5〜4.7m)
elapsed_ms 11,010  accuracy 4.75m           → accepted
elapsed_ms 17,006  quality unusable → good
```

棄却された測位はすべて 36.08182,140.21481 付近で、**1点目から約97m離れている**。
`lib/services/gps_position_filter.dart:79` の速度飛び判定は、直前の受理点との距離を経過時間で割る。
97m ÷ 2s = 約48m/s となり、当然はじかれる。

問題は逃げ道の条件である。

```dart
if (distance / elapsedSeconds > maxSpeedMetersPerSecond &&
    !(acceptLowAccuracy && isLowAccuracy(position))) {
  return false;
}
```

例外は**入ってくる測位が低精度のとき**にしか効かない。
**基準側(`_lastAccepted`)が低精度であることは考慮されていない。**
その結果、精度1,026m の1点目が基準として居座り、精度3.5m の正しい測位を
「ありえない飛び」として連続で拒否し、4〜17秒のあいだ品質 `unusable` が続いた。

これは「運用でGPSの安定を待つ」で片付く話ではない。**離岸直後の十数秒、自艇位置が約100mずれるか
使用不能になる**という、再現条件の明確な欠陥である。頻度は5セッション中1件(他は2.3〜33m)。

最小の修正案:

- 飛び判定の許容距離に**両測位の精度を加算する**
  (`distance <= maxSpeed × dt + (前回accuracy + 今回accuracy)`)。
  基準が粗いときだけ自動的に緩み、両方が良いときは今までどおり厳しい。対称で、恣意的な閾値が要らない。
- 併せて、bootstrap の精度を診断へ残す(既に `gps_bootstrap_unusable` があるので詳細追加のみ)。
- 検証は `test/services/gps_position_filter_test.dart` に
  「粗い基準点 → 良好な測位」のケースを1本足すだけで固定できる。

原文 5.5 の運用上の提案(GPSが正常になるまで離岸しない)は**そのまま有効**であり、残す。

### 1.4 `useNavigator` のテストに関する表現の訂正

`test/hooks/warning_presentation_frame_independence_test.dart:79` は
`lib/hooks/use_navigator.dart` のソース文字列を読み、提示層が `useEffect` から
呼ばれていないことを検査している。したがって「触るテストが1本もない」は誤りである。

正確には:

- **ソースの不変条件を検査するテスト: 1本ある**(しかも空振り防止まで書かれている良いテスト)。
- **フックを実行して状態遷移を確認する統合テスト: 0本。**

方針(純Dartへ切り出して固定する)は変わらない。むしろ上記テストは、
「フックを起動せずに不変条件を守る」という同じ思想の先例であり、これに倣うのが自然である。

### 1.5 他艇の判定スナップショット:P2へ戻す。ただし形を変える

codex の反論は妥当で、`otherBoatCount` と棄却件数だけでは
「受信した」以降(判定へ渡った / 候補が生成された / 危険なしと判定された)を分けられない。

ただしリングバッファ(他艇の位置・精度・受理結果を前後2分保持)は、
実装量とプライバシー負担が段階として重い。**先に、周期サンプルを1行拡張するほうが良い。**

`position_processing_sample`(10秒周期、既存)へ次を足す:

- 最近接他艇までの距離、その相対到達時間(DCPA/TCPA相当)
- その tick で生成された衝突候補数
- 候補が0だった理由の区分(受信0 / 全艇が遠い / 掃引で重ならない)

これで「危険なしと判定された」が証拠になる。位置そのものは保存しないので、
プライバシー負担はほぼ増えない。リングバッファは、これで足りないと分かってから。

### 1.6 カタログ完全性テスト:正規表現の限界は実在した

codex の懸念は具体的に正しい。私が前回使った正規表現は、
`use_navigator.dart:2049` の

```dart
appendRuntimeDiagnostic(
  unconfirmed ? 'sharing_capability_unconfirmed' : 'sharing_capability_confirmed', …)
```

を**取りこぼしていた**(欠落60件の一覧にこの2件が入っていない)。
実際の未記載は最低62件である。

したがって段階を分ける。

1. まず正規表現テストを入れて、**取りこぼしを「検出漏れ」として明示する**
   (拾えた件数と `appendRuntimeDiagnostic(` の出現数を突き合わせ、
   一致しなければ失敗にする。1.4 のテストが既に同じ手法を使っている)。
2. その上で、イベント名を定数へ一元化し、カタログ側と型で結ぶ。

工数見積もりも訂正する。**テスト自体は1時間、説明文62件の執筆は数時間**であり、
「30分」は楽観的だった。ただし優先度は変えない。ログの読解可能性は
今後の実機検証すべての土台になる。

**言えること**: 過去の B・E では、位置送信の初期設定失敗と他艇入力ゼロが同時に発生していた。

チーム所属のどれであること。相関は極めて強いが、**原因は候補の段階である。**

**現行コードで直ったかも未確認である**(2026-08-07 以降の実機ログが存在しない)。

## 3. 最終的な優先順位

### P0:実運用開始前に通す確認ゲート(コードの確定不具合という意味ではない)

問題が出た 8+・7番端末を含む2台で、5〜10分。

1. 両端末へ同じ最新ビルドを入れ、**Git SHA まで控える**。
2. 「端末とデータ」で**認証UIDとteamIdが両端末で整合していること**を確認する(1.1 の追加項目)。
3. 屋外でGPSが `good` になるまで待ってから開始する(原文 5.5 の運用提案)。
4. 両端末で共有状態が正常、相互に地図表示され、移動に追随すること。
5. 一方を終了し、他方から約30秒以内に消えること。
6. 安全な条件で、他艇警告の画面・音声経路が働くこと(本体スピーカー・Buddycom併用)。
7. 本番RTDB Rules がリポジトリと一致すること。
8. **終了後、両端末の診断ZIPを保存し、`position_processing_sample` の
   `otherBoatCount` が0以外を含むことを確認する。**画面表示ではなく内部入力の証拠を取る。

このどれかが通らないうちは、実運用可能とは判断しない。

### P1:優先して直す(コード・ログ)

1. **粗い bootstrap が良好な測位をはじく問題**(1.3)。精度加算による飛び判定 + 単体テスト1本。
   → 唯一「安全機能そのもの」に効く修正であり、P1の先頭に置く。
2. **`permission-denied` の有限再試行**(1.2)。認証・所属の再確認を伴う。純Dartテスト + Emulator。
3. **イベントカタログ完全性テスト**(1.6)。取りこぼし検出込み。説明文の追記は段階的で可。
4. **共有開始の工程別ログ**(clear / onDisconnect / 初回write を started/completed/failed で)。
5. **受信の実績値を heartbeat へ**(受信件数・受理件数・棄却件数・最終受信時刻・購読パス・teamId)。
6. **manifest に Git SHA・ビルド日時・flavor**、および OS版・スキーマ版を**航行時点の値**へ。
7. 共有能力と再試行方針の純Dart化と状態遷移テスト(1.4 の手法に倣う)。

### P2

1. Firebase時刻取得の成功・失敗・フォールバックを独立イベントに
   (現在 `serverTimeOffsetUpdatedAt` が759回すべて null で、`0` の意味が判別できない)。
2. 匿名化方式の統一(`boatIdHash` にセッション別 salt を混ぜる。manifest の文言はそのまま正しくなる)。
3. 他艇判定の限定スナップショット(1.5 の周期サンプル拡張から)。
4. 重要な共有経路の Firebase Emulator 統合テスト。

### P3(価値はあるが、いま着手すると P1 の実機検証が薄まる)

ログ上限の優先度制御(実績8,435件/上限20,000、drop 0件、drop数も記録済み)、

## 4. 実施順序

1. **P1-1(GPSフィルタ)を先に入れる。** 安全機能そのもので、純Dartで閉じ、テストが1本で済む。
2. 次に P1-2〜6 をまとめて1回のビルドへ載せる。ログ改善は**同じビルドで水上へ出さないと1回分無駄になる**。

4. 取れたログで、B・E の再発有無と原因(認証 / teamId / App Check)を切り分ける。
5. 切り分いた結果に応じて P2 を選ぶ。順番を決めるのは次のログであって、本書ではない。

## 5. なお証明されていないこと

- 本番Firebase に配備されている Rules の内容
- 署名済み Archive・TestFlight 配布物との対応
