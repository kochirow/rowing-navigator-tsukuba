> 打ち手のうち **5-1「受信0隻を fault にする」は誤り**（0隻は正常状態でもあり得る）。

## 0. 何が本当の原因か

ログから確定した因果は1本の鎖である。症状に個別対応するとこの鎖は切れない。

```
[R1] 測位が実効0.4Hz (1Hzは出ているのに2/3を捨てている)
      ↓ dt が2〜3秒に伸びる
[R2] 推定器が全力漕ぎ中にテールで発散する (innovation 26m / 最大32m)
      ↓ 位置が20〜30mずれる瞬間が74分中372秒(8.4%)
[R3] ありもしない岸接近・レーン逸脱が立つ → 警告総量が基準の6倍
      ↓ その過剰警告を抑えるために提示ポリシーへ例外が積み上がる
[R4] 例外の相互作用で、本物の他艇警告が無音化された(regression)
```

これと独立に、もう1本:

```
[R5] 能力が欠けていることを誰も観測していない
     (受信0隻・共有unavailable・推定器の棄却 が fault にも記録にもならない)
```

### 根拠となる実測値

| 指標 | 実測 | 意味 |
| --- | --- | --- |
| GNSS測位間隔 | **2.0s / 3.0s に量子化**、1.0s はA/Eで5%・B/C/Dで0% | 1Hzの fix は存在する。**2つに1つ以上を捨てている** |
| `getCurrentPosition` ポーリング | 919回中918回が「ストリームより新しい」 | OSは持っている。取りこぼしはアプリ側かCLの設定 |
| D–E の raw 位置差 | med 1.7m(停止)/ 2.7m(航行)、**8m超は677中6回** | 真値1.5〜2mとほぼ一致。**生GNSSの相対誤差はほぼ0** |
| D–E の filtered 位置差 | med 3.6/2.1m だが **p99 19.2m・max 32m** | 誤差はすべて推定器が作っている |
| 10m超のずれ | **5回・合計372秒 / 74分 (8.4%)** | 稀ではない。毎練習で数分間まちがっている |
| ずれている最中の状態 | 速度 med **3.40 m/s**、innovation med **26.1m** | **全力漕ぎ中**。`hardGateNormalizedSquared=25` の近傍 |
| 読み上げ回数 | A: 106分で123回 = **70回/時** | EEMUA 191 の「操作者が捌ける上限12回/時」の**5.8倍** |

**R2の機序**: dt が2〜3秒に伸びる → 予測が外れる → innovation が大きくなる →
soft gate(6)/hard gate(25)が正しい測位を down-weight/棄却する → さらに予測へ寄る、という
古典的なフィルタ発散。再捕捉は3サンプル連続を要求するが
(`reacquisitionSampleCount=3`, `maximumReacquisitionSampleGap=3s`)、測位間隔が2〜3秒なので
このゲート自体が成立しにくい。**R1 を直さずに R2 のパラメータだけ触っても直らない。**

## Phase 1 — R1: 測位を1Hzへ戻す

**これが最大のレバー。** 他のすべての精度問題の上流にある。

### 1-A. 2つの仮説を1回の実機ランで切り分ける

**仮説α: アプリ側の900msゲートが、OSのまとめ配信を間引いている。**
`processPosition` のゲートは **到着時刻(`safetyClock.elapsed`)** で判定している。
iOS が複数の fix をまとめて配信すると、バッチの2つ目以降が900ms以内に到着して捨てられる。
捨てられるのは**新しいほう**なので、rate が半減すると同時に遅延も増える。
間隔が 2.0s / 3.0s ちょうどに量子化されている事実と整合する。

**仮説β: `distanceFilter: 0` が `kCLDistanceFilterNone` になっていない。**
`geolocator_apple 2.3.13` の `LocationDistanceMapper.m` は:

```objc
+(CLLocationDistance)toCLLocationDistance:(NSNumber *)value {
    if (!value) return kCLDistanceFilterNone;
    return value > 0 ? value.doubleValue : kCLDistanceFilterNone;   // ← value は NSNumber*
}
```

`value > 0` は **NSNumber ポインタの比較**で、非nilなら常に真。
したがって `distanceFilter: 0`(`geo_service.dart:36`)は
`kCLDistanceFilterNone`(= -1.0)ではなく **0.0 のまま** CLLocationManager へ渡る。
Apple は iOS 16.4 以降、継続配信には `kCLDistanceFilterNone` を要求している。
なお同プラグインの**一発取得の経路だけは `kCLDistanceFilterNone` をハードコードしている**
(`GeolocationHandler.m:83`)。**ポーリングが常に新しい fix を返していた事実と一致する。**

- 対処(β): `geo_service.dart` の iOS 経路を `distanceFilter: -1` にする。
  `toCLLocationDistance` は `-1.0` をそのまま返すので `kCLDistanceFilterNone` になる。
  Android 経路(`intervalDuration: 1s`)は変えない。
- 対処(α): ゲートを **fix のタイムスタンプ基準**にし、まとめ配信では
  **最新の fix を採用して古いほうを捨てる**(現状は逆)。

**実機で1回、Phase 0-2 の診断を入れたビルドを走らせて切り分ける。**
両方とも安全側の変更なので、切り分け後に両方入れてよい。

### 1-B. 受け入れ基準
- `track.csv` の測位間隔 med **1.0s**、`>2.5s` の割合 **5%未満**。
- `gps_dead_reckoning_prediction` の件数がセッション秒数の **5%未満**（現在 A 14%・C 26%）。
- D/E相当のペア試験で filtered 位置差 p99 が **8m未満**。

## Phase 2 — R2: 推定器を「低レート耐性」にする

R1 で1Hzに戻れば大半は消えるが、橋の下・木立では必ず疎になるので、**疎でも壊れない**ようにする。
恣意的なパラメータいじりではなく、**統計的整合性(NIS/NEES)で決める**。

### 2-1. 観測ノイズの下限を実測に合わせる
`minimumAccuracyMeters = 4` は、C が報告した実測 2.0m を **4m へ切り上げて**いる。
= 良い測位をわざと半分しか信じていない。dt が長いときこれは発散を助長する。

- D/E ペアで **測位ノイズの真値**が測れる(相対誤差 ≈ 0〜1m、報告accuracy med 2.0〜6.0m)。
  端末報告 accuracy と実誤差の対応表を作り、下限を実測から決める。
- **注意**: 相対誤差は共通誤差(電離層・軌道)が相殺するので、**絶対**精度の代用にはならない。
  下限は絶対誤差の下限として別に置く(`uncertaintyFloorMeters` の役割)。

### 2-2. ゲートを dt に応じて広げる
`softGateNormalizedSquared = 6` / `hardGateNormalizedSquared = 25` は固定。
dt が伸びれば予測誤差が増えるのだから、**正規化に予測共分散が入っている以上、本来は自動で追随するはず**。
それでも innovation 26m が出ているということは、**プロセスノイズが dt に対して過小**である
(=共分散が十分膨らまない → 正規化 innovation が過大 → 正しい測位を棄却)。

- `surge 1.5 / sway 0.3 / maneuvering 1.2 m/s²` を、D/Eペアで **NIS が理論分布に一致するまで**較正する。
  正規化 innovation の二乗平均が自由度に一致するのが正しい状態。
  過小なら共分散が足りず(=いまここ)、過大なら測位を信じすぎる。
- 特に **sway 0.3 は艇の横滑りを想定した値**だが、全力漕ぎ中の 3.4m/s で発散しているので
  surge 側とゲートの相互作用を疑う。較正で決める。

### 2-3. 発散を検出して自力で抜ける
`reacquisitionSampleCount = 3` × `maximumReacquisitionSampleGap = 3s` は、
測位間隔が2〜3秒だと成立しにくい。**サンプル数ではなく経過時間で規定する**
(例: 連続して棄却が N 秒続いたら再捕捉)。

- 併せて、棄却が続いている間は `uncertaintyMeters` を**膨らませる**。
  現在は「自信満々にずれている」状態になる(自己申告10m・実誤差32m)。これは原則6に反する。

### 2-4. 受け入れ基準
- D/Eペア試験で **10m超 excursion が0回**(現在5回372秒)。
- filtered 位置差の p99 が **raw の p99 を上回らない**。
  「フィルタが生GNSSより悪い瞬間を作らない」を不変条件にする。
- `test/services/robust_position_estimator_test.dart` に、
  **dt=3秒で1Hz相当と同等の追従をする**ケースを追加。

## Phase 3 — R4: 提示ポリシーの例外を構造化する（**最優先で1件だけ先行**）

### 3-0.【先行・単独リリース】他艇の無音化 regression を直す

**これは Phase 1・2 を待たない。今日直す。**

`safety_orchestrator.dart:488`:

```dart
if (_isUncertaintyOnlyEntry(candidate) && _isLowSpeed) {
  behavior = AlertBehavior.visualOnly;   // ← カテゴリを問わない
```

- `_isLowSpeed` は **自艇**の速度。`_isUncertaintyOnlyEntry` は `gps_guard_entry` の有無。
- 同ファイルには意図的な除外規則が既にある:
  `_canSuppressAtRest(candidate) => candidate.category != 'other_boat'`
  ——「自艇が停止していても他艇側が接近する可能性は残るため」(原文コメント)。
- 直下の桟橋分岐(:520)は正しく `_isOtherBoatAtRest` で**相手の速度**を見ている。
- **488行だけがこの除外を通っていない。** 2026-08-05 の岸の過剰警告対策で入り、
  他艇を巻き添えにした。

**実害(A の 52〜53分)**: 自艇は停止、他艇が 20〜26m まで接近、DCPA 0〜1.7m、
`actionDeadlineSec` が **3.7秒**まで詰まった lv2 候補 —— **すべて表示のみ、音は一度も鳴らず**。
5端末合計で他艇警告の音は0回。**止まっている艇は避けられない側**であり、最も鳴るべき場面である。

修正:

```dart
if (_isUncertaintyOnlyEntry(candidate) &&
    _isLowSpeed &&
    _canSuppressAtRest(candidate)) {   // 他艇を除外
```

他艇については、桟橋分岐と同じく **相手も止まっているときだけ**静音する。
速度が取れない相手は静音しない(原則6)。

- 回帰テスト: `test/services/safety_orchestrator_test.dart` に
  「自艇停止・他艇接近・`gps_guard_entry` 付き」で **音が鳴る**ことを固定する。
  さらに `tool/replay_field_log.dart` の SCENARIO 機能で A のログ + 接近他艇を再生し、
  実ログ上で鳴ることを確認する。

### 3-1. 静音規則を1つの表にする
現在 `_applyPresentation` には**下げる規則が7つ**、順序依存で並んでいる
(低速静音 / 不確かさのみ / 桟橋 / 安定停止×3 / 反復停止)。
コメントには過去2回、順序を間違えて鳴り直した記録がある。
3-0 も「どの規則がどのカテゴリに適用されるか」が一覧化されていないために起きた。

- **`SuppressionRule` を宣言的に列挙**する:
  `{ id, 対象カテゴリ, 前提条件, 下げ先, 理由コード }`。
  適用は「すべての規則を評価し、最も静かなものを採る」に統一する(現在の `_quieter` の意図)。
- **各規則に「他艇に適用してよいか」を必須フィールドにする。**
  型で強制すれば 3-0 の取りこぼしは二度と起きない。
- 表そのものを `test/` から読み、**全カテゴリ×全規則の組み合わせ表**をゴールデンテストにする。

### 3-2. 不確かさ帯の出どころを分ける（DGNSS の原理）
`pairGpsCenterDistanceGuardMeters` は `sqrt(accA² + accB²) × 0.20`(上限2.5m)。
`boat.accuracy` には推定器の **95%半径(≈10m)** が入るので、
**この帯は常に上限2.5mで飽和している** —— 測位が良くても悪くても同じ値。情報を持っていない。

物理的には、**同じ水域・同じ時刻の2受信機の誤差は共通成分(電離層・軌道・衛星時計)が相殺する**
(DGNSS が成り立つ原理)。今回それを実測した: **真値1.5〜2m に対し raw 位置差 med 1.7m**。
つまり艇間の相対誤差はほぼ0で、**絶対精度10mを2乗和する現在の式は二重計上**である。

- **静的危険区域**(絶対座標に固定)には **絶対**不確かさを使う ← 現状のままで正しい。
- **他艇**には **相対**不確かさを使う。実測から導いた小さな値 + 外挿分。
- 飽和した定数ではなく、実際の測位品質に応じて**伸び縮みする**ようにする。
  良い日は帯が締まって `definite` が増え、悪い日は広がる。これが本来の設計意図のはず。

> 効果の向きに注意: 帯が狭くなると `gps_guard_entry` による重なり自体が減る。
> **3-0 と組で入れること。** 3-0 なしに帯だけ締めると、他艇の検知が単に減る。

## Phase 4 — R3: 警告総量に予算を設ける

### 4-1. 目標値を外部基準から決める
プロセス産業の警告管理標準 **EEMUA 191** は、定常運用で
**「10分に1件(6件/時)が許容、12件/時が操作者の捌ける上限」**としている。
海事側の **IEC 62923 (Bridge Alert Management)** は警告を4段階
(emergency alarm / alarm / warning / caution)に分け、
**集約(aggregation)**と**一時消音**を必須機能としている。

本アプリの実績は **A: 70回/時**。上限の5.8倍。C は 9.4回/時で基準内。
**同じ水域・同じ時間帯で7倍の開きがある**こと自体が、頻度が状況ではなく
端末側のばらつき(=R1・R2)で決まっている証拠である。

- **`log_config.dart` に読み上げ予算を定義する**: 定常 6回/時、上限 12回/時。
- `replay_field_log.dart` を5ログすべてで走らせ、**予算超過を CI で落とす**。
  Phase 1・2 の効果はこの数値で測る。閾値いじりではなく、上流を直して達成する。

### 4-2. 集約を導入する(IEC 62923 の aggregation)
現在 `sourceId` 単位の集約はあるが、**種別をまたぐ集約がない**。
逆走(band 3)と岸(band 1)が持続音チャンネルで競合し、
同じ状況で艇によって読み上げ回数が 0〜8回とばらつく(D/E: 各8回、A: 96回)。

- 「同じ原因群」を1つの集約警告にまとめ、**個別警告が複数の集約警告を立てない**ようにする。
- 逆走の `guidanceRepeatInterval`(5秒)は、A で **1エピソード平均7.4回**の読み上げになった。
  **エピソードあたりの読み上げ回数に上限**を設ける(例: 3回で打ち切り、区域を出るまで再武装しない)。

### 4-3. 水域データを実測から引き直す
これは Phase 1・2 が終わってから。**ずれた位置で引いたデータを固定してしまわないため。**

- **`mooringAreas`**: 岸警告クラスタの中心
  (36.0806,140.2151)付近と(36.0818,140.2150)付近は、
  どちらも `ラクスマリーナ桟橋`(36.08153–36.08218 / 140.21389–140.21469)の**外**。
  後者は東端から約30m外。5ログの停止点から待機水域を実測で引き直す。
- **`lane_kasumikagaura_*`**: 航跡の **17〜44% がどちらのレーンにも入っていない**(A は44%)。
  レーン外では中心線予測も逆走判定も効かない。
- 引き直したら `tool/update_hazard_profile_hash.sh` を実行し、
  座標の意味が変わるので `currentHazardProfileDataVersion` を上げる。

### 4-4. 霞ヶ浦の運用前提を DESIGN_PRINCIPLES へ書く
**DESIGN_PRINCIPLES 第1章は桜川(川幅40〜50m・右側通行・片側1レーン)だけを前提としている。**
今回の練習は全区間が霞ヶ浦側で、この前提は成立していない
(南岸まで520m以上、両岸60m以内の点は0%)。

前提が違う水域へ同じ設定値を適用したことが、逆走警告と岸警告のばらつきの根にある。
**水域ごとに運用前提を分けて記述し、そこから設定値を導く。**
これを書かないまま 4-3 でレーンだけ引き直すと、また同じことが起きる。

## Phase 5 — R5: 能力の欠如を観測する

原則6(データ欠損は安全の根拠にならない)の実装漏れ。**表示のみ・音は増やさない。**

### 5-1. 「受信0隻」を fault にする
`rawDynamicReceiveDegraded` はストリームの `onError` か `receiveDegraded` フラグでしか立たない
(`use_navigator.dart:1813,1848`)。
**最初から1隻も来ない状態は検出できない。**
B/E は2セッション118分にわたり他艇0隻・`positionSharingState=unavailable` のまま走り、
`dynamic_obstacle_stream_error` は**0件**、乗員には何も表示されなかった。

- 位置共有が `unavailable` のまま一定時間(例: 60秒)経過したら **表示 fault** を立てる。
- 「他艇0隻」と「他艇がいない」を区別して表示する。
  **音は足さない**(漕ぎながら対処できない情報を読み上げない)。

### 5-2. 共有確立を再試行する
`publishingSetupUnavailable` は `startWatching` 直後の
`clearMessage` + `registerOnDisconnect` が5秒でACKされないと立ち、
**その後の復帰経路がない**(`use_navigator.dart:3232-3276`)。

今回、`ack_timeout` は A・D でも発生し(A 1回・D 3回)、C は起動直後に
`permission-denied`(`likelyCause: rtdb_rules_or_team_membership`)を3回出している。
**起動直後の共有確立は全端末で不安定。**

- 指数バックオフで再試行し、成功したら `position_sharing_recovered` を出す。
- 終了時の `Remote position cleanup` の TimeoutException(B・E)も同じ経路。
- degraded 起動を続ける方針は変えない(原則1)。**復帰経路を足すだけ。**

### 5-3. `safety_evaluation_stalled` の閾値を測位間隔から決める
閾値3秒に対し、実測の測位間隔が med 2.0〜3.0s。C では
`lastSafetyEvaluationAgeMs` 3002/3012/3015/3190ms で **6回 fault が立った**。
正常な運用で立つ警告は不具合(原則4)。

- 実効測位間隔の移動中央値から動的に決める。**Phase 1 で1Hzに戻れば自然に解消するので、
  Phase 1 の効果測定を兼ねる。** 先に閾値だけ上げると R1 を隠してしまう。

### 5-4. 端末音量の低下を知らせる
B/E は全期間 `outputVolume` **0.30 固定**(他3台は1.00)。
読み上げが聞こえたかはログでは判定できないが、`audio_route_snapshot` で毎回取れている。

- 航行開始時と、低音量が続くときに**画面へ**表示する。音は足さない。

## やらないこと

- **閾値を上げて警告を減らすこと。** 総量は R1・R2 の結果であり、原因ではない。
  先に閾値を触ると、位置が直ったときに今度は警告漏れになる。
- **`gps_guard_entry` の降格ルールそのものを消すこと。** 設計として正しい。
  直すのは入力(帯の出どころ)であって規則ではない(3-2)。
- **水域データの引き直しを Phase 1・2 より先に行うこと。**
  ずれた位置で引いた線を正解として固定してしまう。
- **system fault に音を足すこと。** 5-1・5-4 はいずれも表示のみ。

## 参考

- EEMUA 191(警告管理): 定常時 6件/時が許容、12件/時が操作者の上限。
- IEC 62923-1/-2(Bridge Alert Management): 4段階の優先度、集約、一時消音。
  「個別警告が複数の集約警告を立ててはならない」。
- Apple CoreLocation: 実効上限は約1Hz。iOS 16.4以降、継続配信には
  `kCLDistanceFilterNone` が必要(0 では不可)。
- `geolocator_apple 2.3.13` `LocationDistanceMapper.m`: `NSNumber*` のポインタ比較により
  `distanceFilter: 0` が `kCLDistanceFilterNone` にならない。
- DGNSS: 近接する2受信機の誤差は共通成分が相殺する。相対精度は絶対精度より良い。
- 適応カルマンフィルタ: NIS/NEES による整合性検定でプロセス/観測ノイズを較正する。
