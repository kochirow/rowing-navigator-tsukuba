## 第1部: 再検証による訂正

報告書を読み直し、実装計画の前提になる主張をコードで再確認した。**2件の誤りと1件の過小評価**が見つかった。

### 訂正1（重要）: 「下限を上げれば S2-B と S2-C が同時に解ける」は**誤り**

[P15](P15_横断総括.md) 第3章でそう書いたが、成立しない。

- **S2-B**（警告時間を5秒に下げると全脅威が連続音になる）
  → `minWarningTimeSeconds` を上げれば解ける ✓
- **S2-C**（`continuousAudioDeadline` 7秒 < 8+ の停止時間 8.15秒）
  → **`continuousAudioDeadline` そのものを変えないと解けない。**
  予測地平を何秒にしても、連続音が鳴り始めるのは 7秒前のままである。

2つは独立した修正が要る。

### 訂正2（重要）: S2-H の余裕は「100ms」ではなく「**ゼロ**」

[P09](P09_通信.md) では「送信間隔2秒に対しサーバー下限1.9秒、余裕100ms」と書いたが、
クライアント側の実装を読み直すと余裕は残っていない。

`use_navigator.dart:2030-2032`:

```dart
if (lastQueuedTick.value == null ||
    sendTick - lastQueuedTick.value! >=
        Duration(milliseconds: intervalSec * 1000 - 100)) {
```

- **クライアントは意図的に `interval − 100ms` で発火する。** 2秒間隔なら **1900ms**。
  （1Hz tick の粒度で間隔が 3秒へ伸びるのを防ぐための補正と思われる）
- サーバー側 `database.rules.json` の下限も **1900ms**。
- さらに `u` は `ServerValue.timestamp`（`message_model.dart:196`）＝**サーバー到着時刻**である。
  比較されるのは「連続する2回の書き込みのサーバー到着間隔」であり、
  クライアントのローカル間隔ではない。

**したがって、2回目の書き込みが1回目より相対的に速く届くだけで下限を割り、
書き込み全体（位置＋プロファイル）が permission-denied で拒否される。**
ネットワークジッタは日常的に数十〜数百 ms あるので、これは「起こりうる」ではなく
「ときどき起きているはず」と考えるべき。

拒否されると自艇の位置が1周期ぶん更新されず、他艇からは古い位置のままになる。
**最も起きやすいのはリスク上昇中（2秒送信）** である。

### 訂正3: 実装順序に依存関係がある（当初の計画になかった）

S2-C を直すために `continuousAudioDeadline` を 8.5秒へ上げると、
断続音バンド（8.5〜10秒）が **1.5秒**しか残らず、段階的な予告が実質消える。
それを避けて予測地平（`defaultWarningTimeSeconds`）を 12秒へ広げると、
**カーブでの直線予測の膨らみが 50m → 60m に増える**。

ところが **S2-A（逆向き航行では中心線予測が効かない）が未修正のままだと、
航行時間の約半分でその膨らみをまともに受ける。**

→ **S2-A を先に直さないと、S2-C の修正が過剰警告を悪化させる。**
