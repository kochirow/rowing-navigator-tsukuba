## 2. 指摘

### P6-01（S2）「警告時間」設定と音のバンドが連動していない

**P0 の F-01 を確定させ、内容を訂正する。**

- `SafetyOrchestrator` は `use_navigator.dart:2414` で構築されるが、
  **`presentationConfig` を渡していない**（grep 済み）ため `defaultAlertPresentationConfig` の
  固定値 7秒 / 10秒 を使う。
- 利用者設定 `warningTimeSeconds` は `assessRisk`（`:1954-1959`）にしか渡らず、**予測地平だけ**を変える。
- 設定 UI（`danger_zone_settings_screen.dart:216-220`）の文言は
  「初回警告の目標: N秒前」「危険区域への到達予測に対して、初回警告を開始する目標時間です」。

**帰結（P0 の記述は不正確だったので訂正する）:**

| 設定値 | 予測地平 | 検知される脅威の TTE | 音の挙動 |
| --- | --- | --- | --- |
| 5秒（下限） | 5秒 | すべて ≤ 5秒 | **すべて `imminent` = 連続音。** 3秒間隔の断続音の段階が消える |
| 10秒（既定） | 10秒 | ≤ 10秒 | 7秒以下は連続音、7〜10秒は断続音（設計どおり） |
| 25秒（上限） | 25秒 | ≤ 25秒 | 10〜25秒は `monitoring` = **表示のみ**。音は10秒前から変わらない |

- **下げた場合が問題。** 利用者は「警告を控えめにしたい」つもりで下げるが、
  実際には**検知された脅威がすべて連続音になる**。段階的な予告が失われ、原則4（過剰警告）に近づく。
- **上げた場合は音が増えない。** 「25秒前に警告」と設定しても鳴り始めは10秒前のまま。
  バナー表示は25秒前から出るので UI 文言と矛盾はしないが、**利用者の期待とはずれる可能性が高い**。
- 再現条件: 安全設定で「初回警告の目標」を5秒にする → 以後、検知されるすべての衝突脅威が連続音になる。
- CLAUDE.md は「上限10秒は予測地平（`defaultWarningTimeSeconds`）と一致させている。
  『予測が届かない先では音が鳴らない』が不変条件」と書いており、**既定値でのみ成立する不変条件**である。
- 修正案: `AlertPresentationConfig` の2つの deadline を保存設定値から導出する
  （例: `intermittentAudioDeadline = warningTime`、`continuousAudioDeadline = warningTime × 0.7`）。
  ただし S2-4（8+ の停止時間 8.15秒）との整合も要るため、単純な比例では足りない。
  **設定範囲そのものを見直す（下限を8秒程度に上げる）ほうが素直かもしれない。**

### P6-02（S3）視覚優先 system fault の単発キュー機構が実効を持たない

- `_isCueEligible`（`safety_orchestrator.dart:406`）は `_isVisualFirstSystemFault` を返す。
  対象は `visualFirstSystemFaultCategories` = 受信途絶・送信停止・臨時区域受信途絶の3種。
- しかし `use_navigator.dart:1486-1520` を見ると、**これらの候補はすべて `audioAsset: null`** で作られる。
- `_collectOneShotCues:364` は `asset == null` で `continue` するため、キューには何も積まれない。
- 連鎖して不要になっているもの:
  - `systemFaultRecueInterval`（5分・`alert_presentation_config.dart:163`）
  - `_systemFaultCueContexts` と `_applyVisualFirstFaultPresentation`（`:310-334`）が設定する `audioEventId`
- コメント（`:384`）の「いまは誰も該当しない」は結論として正しいが、
  **理由が「全アセットが読み上げ音声になったから」ではなく「対象カテゴリに音声アセットが無いから」**である。
  読み手が理由を取り違えると、将来 fault に音声を付けたとき意図せず2本目が鳴り出す。

### P6-03（S3）`enqueueCommand` の追い越しで単発要求が失われうる

- `use_alert.dart:657-686` — 待機中の要求は常に最新1件へ置き換えられ、追い越された要求は
  **実行されずに完了扱い**になる（`superseded?.complete()`）。
- 持続音の状態同期としては正しい設計（コメント `:651-656` に理由あり）。
- ただし `playOnce(assetPath, eventId:)` のように**イベント固有の1回きりの再生**も同じ経路を通る。
  1つのドレインサイクル中に2つの異なる `eventId` の単発要求が来ると、先の1件は鳴らずに消える。
- 実際には音声指令は 1Hz のスナップショットから1件ずつ出るため、追い越しはまれ。**予防的な指摘。**
