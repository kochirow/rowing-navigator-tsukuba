## 1. 指摘

### P13-01（S2・実測で確認）連続音の警告が再び最上位バンドへ入ると、警告チップが画面から消える

**本パス最大の所見。読むだけでなく実際に走らせて確認した。**

- 該当箇所: `safety_banner.dart:279-341` の `_PulseFrame`
- `_PulseFrameState` は `SingleTickerProviderStateMixin` を使い、
  `didUpdateWidget` で `enabled` が false→true になるたびに `_startAnimation()` で
  **新しい `AnimationController` を作る**（`:303-308`）。
- Flutter の `SingleTickerProviderStateMixin.createTicker` は、
  古い Ticker が dispose 済みかどうかに関係なく **2本目の作成を assert で拒否する**。

**再現条件（実測）**: 同一カテゴリの警告が `imminent` → `action` → `imminent` と遷移する。

```
PROBE 1回目 imminent: OK
PROBE action へ降格: OK
PROBE 2回目 imminent の例外: FlutterError
PROBE 「他艇」テキストの数: 0
PROBE ErrorWidget の数: 1
```

**帰結**: `_PulseFrameState is a SingleTickerProviderStateMixin but multiple tickers were created.`
が投げられ、**警告チップが `ErrorWidget` に置き換わる**。「他艇」の文字は画面から消える。

**到達性は高い。** バンドは到達までの時間だけで決まる（TTE ≤ 7秒 → imminent、7〜10秒 → action）。
相対速度が揺れる他艇は 7秒の境界を何度も跨ぐ。`confidence < 1.0` による1段下げも、
GPS帯だけで重なる状態と確実に重なる状態を行き来するたびにバンドを上下させる。

**影響範囲の限定**: この `FlutterError` は Flutter の `assert(() {...}())` の中にあるため、
**release ビルドでは投げられない**（assert が除去される）。release では2本目の Ticker が作られ、
古い controller は既に dispose 済みなので実害は無い。

**それでも S2 とする理由**:
- 実機テストは `flutter run`（debug）や profile ビルドで行われることが多い。
  そのとき「連続音が鳴り直した瞬間にバナーが消える」という、最も重要な表示の欠落が起きる。
- 2026-07-26 の実機テスト記録が残っているが、そこで使われたビルド種別は不明。
  **もし debug だったなら、この現象は既に起きていた可能性がある。**
- release で動くのは assert が消えるからであって、状態管理が正しいからではない。

**修正案**: `SingleTickerProviderStateMixin` → `TickerProviderStateMixin` に変えるか、
より良いのは **controller を `initState` で1度だけ作り、`didUpdateWidget` では
`repeat()` / `stop()` を切り替える**こと。後者なら Ticker は1本のままで、生成コストも消える。

### P13-02（S2・実測で確認）速度が NaN になると航行画面全体がビルド不能になる

- 該当箇所: `home_map_screen.dart:1026-1034`

```dart
paceSeconds: navigator.myBoat.value != null
    ? navigator.myBoat.value!.speed != 0
        ? (500 ~/ navigator.myBoat.value!.speed)
        : 0
    : 0,
```

- `~/` は double に対して `(a / b).truncate()` を行う。実測:

```
speed=0.0001    -> 5000000        （_formatPace が '--:--' にする。問題なし）
speed=NaN       -> 例外: Unsupported operation: Infinity or NaN toInt
speed=Infinity  -> 0
```

- **`speed` が NaN だと `HomeMapScreen.build` が例外を投げ、航行画面全体が描画できなくなる。**
  地図・警告バナー・計器・終了ボタンがすべて失われる。
- **再現条件**: `navigator.myBoat.value.speed` が NaN になること。
  `buildMyBoat`（`use_navigator.dart:1680`）は
  `speed_ = estimate?.speedMetersPerSecond ?? rawSpeed` で、
  推定器側は `sqrt(vE² + vN²)`。P3-03 で指摘したとおり **共分散に非負クランプが無い**ため、
  桁落ちで分散が負→ `sqrt` が NaN → 速度が NaN という連鎖がありうる。
- **このコードベースは他のあらゆる場所で NaN を潰している**
  （`_usableBoat` / `_gpsAccuracyMeters` / `normalizeBearing` / `relativeDirectionLabelOf` /
  `rowingMapBearing`）。**ここだけが素通しである。**
- 帰結の重さ（画面全損）に対して、防御は `speed.isFinite` の1条件で足りる。

## 2. 検証して正しかったこと

### 2.1 P01-01（自己交差ポリゴン）は、アプリ UI からは到達不能

`use_map_editor.dart` を全行読んだ結果、**この画面には自由曲線のポリゴン描画が存在しない**。

- 臨時危険区域: `createTemporaryCircle` → `StaticObstacleService.createCirclePoints`（**円のみ**）
- 固定流木: プリセットの基本形状に対する `ManagedHazardTransformer.transform`
  （平行移動・拡大縮小・回転＝**アフィン変換**。単純多角形は単純なまま）

**どちらも自己交差しない。** 自己交差ポリゴンが入るのは、Firestore やプリセット JSON を
手で書き換えた場合だけである。P01-01 / P02 の実測（過剰警告方向）と合わせて、
**この指摘は S3 のまま据え置きでよい**と確認できた。

### 2.2 不変条件6 の唯一性

## 3. 判断を保留した点

**`SafetyBanner._groupByCategory` は `other_boat` も1枚に集約する。**

岸が基準線の辺ごとに複数枚出るのを1枚にまとめる、という趣旨のコメント（`:34-38`）は
静的区域を想定している。しかし実装はカテゴリ単位なので、**前方と後方に1艇ずつ脅威がいても
チップは「他艇 ×2」の1枚**になり、表示される方向は最も切迫した側だけになる。

件数は出るので「2艇いる」ことは分かるが、2つ目の方向は分からない。
2〜12艇が同時に出る運用（DESIGN_PRINCIPLES 1.3）でこれが問題になるかは、
実際の警告同時発生頻度を知らないと判断できない。**利用者判断としてP15へ送る。**
