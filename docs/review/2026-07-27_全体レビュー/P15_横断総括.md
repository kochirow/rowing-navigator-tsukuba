## 3. 修正の優先順位（提案）

### 第1優先: リリース手順を壊さないための修正

**S1-A（版の厳格一致）。** これだけは他と性質が違う。
コードの不具合ではなく、**アプリを更新する行為そのものが安全機能を一時的に壊す**構造である。
次のリリース前に決着させる必要がある。

提案する方向:
1. `RemoteBoatMessage.tryParse` の `appVersion` 検証を**廃止**し、`protocolVersion` だけで互換を判断する。
   `protocol_config.dart` のコメントは元々その設計思想（「通信スキーマを変えるときは protocolVersion を更新する」）
   で書かれており、`appVersion` の一致要求がそれを打ち消している。
2. `database.rules.json` の `appVersion` バリデーションを、値の固定から**文字列長のみ**へ変更する。
3. `firebase_rules_contract_test.dart` に **`protocolVersion` / `profileVersion` の値が
   config と一致すること**の検証を追加する（S2-I）。危険区域プロファイルのハッシュには同種の検証が
   既にあるので、それに倣う。

### 第2優先: 正常な運用で鳴る警告（原則4）

**S2-A（逆向き航行）** — 修正は `channel_path_predictor.dart:94` の
`alongSpeed <= 0` を「`alongSpeed.abs()` が小さすぎる（横断）」の判定へ変えるだけ。
負方向の受け皿（`along < 0` → `_appendStraightTail`）は既に実装済み。
**テスト（`channel_path_predictor_test.dart:152`）が現在の挙動を固定しているので、
テストの意図から見直すこと。** 「横断」と「逆行」を分離する。

**S2-B（警告時間と音の非連動）** — 選択肢は2つ。
- (a) `AlertPresentationConfig` の deadline を保存設定値から導出する。ただし S2-C との整合が要る
- (b) 設定範囲の下限を上げる（5秒 → 8.5秒程度）+ UI 文言に音のタイミングを明記する

**(b) を推奨する。** 理由: 現在の下限5秒は、8+ の停止時間8.15秒（S2-C）より短く、
そもそも設定できてはいけない値である。

> **2026-07-27 訂正。** ここで「下限を上げれば S2-B と S2-C が同時に解ける」と書いたのは**誤り**。
> 予測地平を何秒にしても、連続音が鳴り始めるのは `continuousAudioDeadline`（7秒）のままである。
> S2-C を解くにはその定数自体を変える必要がある。
> 詳細と実装順序は [99_最終報告と実装計画.md](99_最終報告と実装計画.md) 第1部を参照。

**S2-D（8+ のすれ違い）** — config の検算コメントを全艇種へ拡張したうえで、
許容するか値を調整するかを決める。**8+ の実測データが要るので利用者判断。**

## 6. 総評

**このコードベースの水準は高い。** 15パス（うち完了11）を通して、
**S1 は1件、警告漏れ（FN）方向の S2 は3件**しか出なかった。

特筆すべきは3点。

1. **設定値の 16ファイル中15ファイルで「なぜこの値か」が運用前提から辿れる。**
   実機ログの実測値（「77分で16回」「173回のうち99回」「最大23.3 LU」）が根拠として引用されている。
2. **不変条件が「将来の誤設定を含めて」テストされている。**
   `static_sweep_clearance_test.dart` の「設定を取り違えて過大な値を渡しても broad-phase を破らないこと」は、
   設計意図をテストとして残す良い例。
3. **捨てた選択肢とその理由が書かれている。**
   2本目のプレイヤーを使わない判断、方位の二重平滑化をやめた理由（数値つき）、
   config が hooks を import しない理由。これらはレビューの速度を大きく上げた。

**弱点は一貫している: 「テストが書きにくい層」に穴が集中している。**
hooks（`use_navigator` 3,189行・`use_alert` 1,003行）と画面（`home_map_screen` 1,546行）。
2026-07-26 の安全レビューが S3-1 で指摘した構造的問題が、そのまま残っている。
純Dartへ切り出せる部分（鮮度分類・`buildMyBoat` の方位保持・`enqueueCommand` の直列化）を
services 層へ移すのが、最も費用対効果の高い改善だと考える。
