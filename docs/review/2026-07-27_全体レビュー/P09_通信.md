## 1. P5 からの持ち越し1: 時計ズレ耐性 — **完全に解決**

安全レビューのシナリオ5で「`serverUpdatedAt` が常に入っているかが決定的」と保留した点を確認した。

| 段階 | 実装 | 判定 |
| --- | --- | --- |
| 書き込み | `message_service.dart:68` `serverUpdatedAt: ServerValue.timestamp`（RTDB サーバー側で採番）。Firestore 経路も `:83` `FieldValue.serverTimestamp()` | **端末時計を使っていない** ✓ |
| 読み取り基準 | `_estimatedServerNow()`（`:45-47`）= `DateTime.now()` + `.info/serverTimeOffset` | ✓ |
| 必須性 | `remote_boat_message.dart:147-161` — `serverUpdatedAt` が無い・不正なら `tryParse` が失敗する（**必須フィールド**） | ✓ |
| 未来時刻 | `:167` `serverUpdatedAt.isAfter(now)` を拒否 | ✓ |
| オフセット取得の縮退 | `:265` 2秒のフォールバックタイマー。取得できなくても受信を止めない | ✓（原則1） |

**端末時計が ±5秒ずれていても、鮮度・外挿の判断はサーバー時刻基準で行われる。**
シナリオ5 で懸念した「27.5m の誤外挿に対しマージン 2m」は発生しない。

残る懸念（S3・下記 P9-03）は、オフセットが取得できないまま2秒のフォールバックで進んだ場合、
`_serverTimeOffsetMillis` が 0 のまま＝生の端末時計で判断することになる点。

## 2. P0 F-03（アプリ版の厳格一致）の再評価 — **S1 を維持し、影響範囲を拡大**

P0 では「拒否したことを利用者へ伝える経路がない」と書いたが、これは**不正確だった**。経路はある。

```
版不一致 → tryParse 失敗 → OtherBoatTrackUpdateStatus.rejectedInvalidMessage
        → message_service.dart:159 rejectedBoatIds.add(boatId)
        → :139 MessageReceiveFault('REMOTE_DATA_REJECTED')
        → dynamic_obstacle_service:58 streamFaultCount++ → receiveDegraded
        → other_boat_receive_unavailable の system fault（表示のみ）
```

`rejectedBoatIds` に入るのは `rejectedInvalidMessage` と `rejectedCapacity` だけで、
重複・順序逆転は入らない（`:157-158`）ため、**正常運用では立たない** ✓ 設計は妥当。

**訂正: 利用者には持続的なバナーが出る。** ただし内容は「他艇の受信に問題」という一般的なもので、
どの艇が・なぜ弾かれたかは分からない。**その艇は衝突評価から完全に消えたまま**である。

### さらに重い事実: サーバー側ルールでも版が固定されている

`database.rules.json` の `boat_profiles` バリデーション:

```json
"protocolVersion": { ".validate": "newData.isNumber() && newData.val() === 1" },
"appVersion":      { ".validate": "newData.isString() && newData.val() === '1.0.0'" },
"profileVersion":  { ".validate": "newData.isString() && newData.val() === 'sakuragawa-v3'" }
```

**アプリ版がサーバーのセキュリティルールにハードコードされている。**

- 1.0.1 を配信すると、更新した端末は**プロファイルを書き込めない**（ルールが拒否）。
  位置共有が成立せず、他艇からもまったく見えなくなる。
- ルールを先に「1.0.0 と 1.0.1 の両方を許可」へ更新しても、
  **クライアント側の `supportedPositionAppVersions = {currentPositionAppVersion}` が残る**ため、
  異なる版どうしは互いを読めない。
- つまり **バージョンアップに「全員が同時に更新を完了する」瞬間が必要**であり、
  それが成立しない限り、混在期間中はどちらかの群が衝突警告の対象から消える。

**重大度 S1 を維持する。** 影響は「クライアントのフィルタ」に留まらず、
**リリース手順そのものが安全機能を壊しうる構造**である。

修正の方向（P15 で判断）:
1. 通信スキーマが同じなら版を問わない（`protocolVersion` だけで互換を判断する）。
   `protocol_config.dart` のコメントは元々その意図で書かれている
   （「通信スキーマを変えるときは protocolVersion を更新する」）が、`appVersion` の一致要求がそれを打ち消している。
2. ルール側も `appVersion` の値検証をやめ、文字列長のみ検証する。
3. どうしても版を絞るなら、**受理する版の集合を複数持てる形にし、ルールとクライアントの両方を同時に更新する手順を文書化する**。

## 4. 指摘

### P9-01（S1・P0 F-03 の継続）アプリ版の厳格一致が、クライアントとサーバールールの両方に埋め込まれている

第2章のとおり。**リリース手順そのものが安全機能を壊しうる。**

### P9-02（S2）送信レート制限の余裕が**ゼロ**である

> **2026-07-27 訂正。** 当初「余裕100ms」と書いたが、クライアント実装を読み直すと余裕は残っていない。
> `use_navigator.dart:2032` は `intervalSec * 1000 - 100` で発火する、すなわち 2秒間隔なら
> **意図的に 1900ms で撃つ**。サーバー下限も 1900ms。さらに `u` は `ServerValue.timestamp`
> （`message_model.dart:196`）＝**サーバー到着時刻**なので、比較されるのは到着間隔である。
> 2回目の書き込みが1回目より相対的に速く届くだけで下限を割り、書き込み全体が拒否される。
> 「起こりうる」ではなく「ときどき起きているはず」と読むべき。

（以下、当初の記述）

- `database.rules.json` の `"u"` バリデーション: `newData.val() >= data.val() + 1900`
- 最短の送信間隔は `sendIntervalElevatedRiskSec` / `sendIntervalNearOthersSec` = **2秒**。
- 余裕は **100ms のみ**。タイマーの発火が早い方向へ 100ms 揺れると、
  **サーバーが書き込みを拒否する**。
- 拒否されると自艇の位置が更新されず、他艇から見ると 1周期ぶん古いままになる。
  リスク上昇中（`elevatedRisk`）に最も起きやすい。
- Dart の `Timer` は通常「遅れる」方向へ揺れるので実害は小さいと見られるが、
  **余裕 5% は設計値として薄い**。20% 程度（1600ms）が妥当。
- 書き込み拒否が起きたときに、それが診断へ残るかは未確認（P15 で扱う）。

### P9-03（S3）サーバー時刻オフセットを取得できないまま進んだ場合の記録がない

- `:265` の2秒フォールバックは「受信を止めない」ために正しい（原則1）。
- しかしフォールバックした場合 `_serverTimeOffsetMillis` は 0 のままで、
  **端末の生の時計で鮮度を判断する**ことになる。端末時計が数秒ずれていれば、
  艇が早く消えたり、古い位置を新しいと誤認したりする。
- オフセット未取得のまま動作している事実が、診断イベントにも system fault にも残らない。
  `onError` は `debugPrint` のみ（`:247-249`）。
- 原則6（データ欠損は安全の根拠にならない）の観点では、
  **「時刻の基準が取れていない」ことは表示すべき状態**である。

安全レビュー S3-1 と同じ。関数側 30秒 / 呼び出し側 6秒。

## 6. 総評

**通信層は本レビューで最も作り込みが深い層。** サーバー時刻の採用、差分購読、プロファイルの差分送信、
`onDisconnect`、レート制限、全フィールドのバリデーション、購読の独立解放。
無料枠での運用とセキュリティの両方を、具体的な手段で満たしている。

その一方で、**唯一の S1（P9-01）もこの層にある。** 版の厳格一致が
クライアント・サーバールールの両方に埋め込まれており、**アプリを更新する行為そのものが
一時的に安全機能を壊す**構造になっている。これは実装のバグではなく、リリース設計の問題である。
