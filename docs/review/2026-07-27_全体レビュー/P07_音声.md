## 1. 検証して正しかったこと

### 1.1 再生要求の直列化（CLAUDE.md の中核要件）

CLAUDE.md は「**再生要求は直列キューで1本ずつ実行する**（並行実行すると、段階が上がる瞬間に
古い要求が新しい音を止める）」と明記している。`enqueueCommand`（`use_alert.dart:657-686`）:

- 実行中は `commandDraining` フラグで新規ドレインを起こさない ✓
- 待機は常に最新1件（`pendingCommand`）。追い越された要求は `superseded?.complete()` で
  **待ち手を放置せずに**破棄する ✓
- 個別要求の失敗でキュー全体を止めない（`:674-676` の try/catch）✓
- `play` / `playOnce` / `playPeriodic` / `stop` の**全経路**が `enqueueCommand` を通る（`:688-702`, `:894`）✓

コメント（`:651-656`）が「直列化しないと、単発音→連続音へ上がる瞬間に、古い要求が世代チェックで
`player.stop()` を呼び、**新しい連続音を自分で止める**経路が開く」と、防いでいる具体的な事故を明記している。

### 1.2 OS 割込みからの自動復旧

- `AudioPlaybackProgressWatchdog` が「OS上は再生中のままなのに実際の再生位置が止まる」状態を検出する
- 検出後の復旧手順（`:390-455`）: 初期化待ち → seek(0) → pause → `applyAudioContext` 再適用 → resume
- `recoveryInFlight` で多重復旧を防ぐ ✓
- 復旧の各段階が診断イベントとして残る（`audio_recovery_started` / `_succeeded` / `_failed`）✓
- **周期音の正常な無音区間を stall と誤認しない**ための分岐がある（`:366-371`
  `isPeriodicRepeat ? 'audio_periodic_repeat' : 'audio_playback_stalled'`）。
  コメントが「実機ログが正常な動作でノイズだらけにならないように」と理由を書いている ✓

### 1.3 音声セッション設定

`createWarningAudioContextConfig`（`warning_audio_config.dart:113-123`）:

- `respectSilence: false` — iPhone のサイレントスイッチ中も鳴らす ✓（警告として正しい）
- `focus: mixWithOthers` — Buddycom などの通話音声を止めない ✓
- `gain` / `duckOthers` を使わない理由がコメントにある ✓

### 1.4 音圧の CI 検証

`tool/check_warning_audio.sh` は3段構えで、設計意図が明快:

1. `assets/audio/*.mp3` に対応する `tool/audio_src/*.wav` マスターが存在するか
2. 絶対値が −13〜−8 LUFS の範囲か（正気度チェック）
3. **ファイル間の差が 2.5 LU 以内か（本命）**

スクリプト冒頭のコメントが「端末のボリュームは利用者が1つのつまみで決めるので、
ファイルごとに音圧が違うと『読み上げが聞こえる音量にするとアラート音が耳をつんざく』状態になり、
どちらかが必ず犠牲になる。**聞こえない警告は警告漏れと同じ**」と、
なぜこれが音質ではなく安全の問題なのかを説明している ✓

## 2. 指摘

### P7-01（S2）GPS途絶と評価停止が同じ音を共有している

**P0 の F-06 を、提示ポリシーの観点から S2 へ引き上げる。**

- `gpsFaultWarningAudioAsset` と `pipelineFaultWarningAudioAsset` はどちらも
  `systemFaultWarningAudioAsset`（= `system_fault_warning.mp3`）を指す（`warning_audio_config.dart:65, 71`）。
- CLAUDE.md は「**種類ごとに別の音声を割り当てること**（同じ音を使い回すと振り向く先を選べない）」を
  規範として明記している。
- この2つは system fault のうち**音声を持つ唯一の2種**であり、意味が明確に違う:
  - `gps_unavailable` = 「GPS異常。目視で確認」（測位が来ていない）
  - `pipeline_unresponsive` = 「警告が停止。目視で確認」（測位は来ているが評価が回っていない）
- 同じ音では、聞いた人が**どちらが起きたか判別できない**。どちらも「目視へ切り替えろ」なので
  取るべき行動は同じだが、**復旧の見込みが違う**（GPS は橋を抜ければ戻る／評価停止は戻らない可能性がある）。
- コード内に `TODO(audio): VOICEVOX の読み上げ音声ができたら差し替える` と明記されているので、
  **既知の未達**である。S2 とするのは、実アセットが読み上げでない仮の通知音のままであり、
  P0 F-06 の「同じパスが `warningAudioAssets` に2回入る」も併発しているため。
- 併せて `coachAnomalyAlertAudioAsset` も同じアセットを指す。こちらは
  「監視者は画面を見られる位置にいる」という理由で既定無音（`coachAudibleAnomalyKindNames` が空）なので
  実害は小さいが、**3つの意味が1つの音に集約されている**状態ではある。

### P7-02（S3）未使用アセットが CI の音圧制約を縛っている

**P0 の F-05 の続き。利用者判断（「将来使うので残す」）を踏まえた記述。**

- `add_warning.mp3` / `alert_beep.mp3` / `alert_high_tempo.mp3` / `alert_low_tempo.mp3` /
  `proximity_warning.mp3` の5本は、コードから一度も再生されず `warningAudioAssets` にも入っていない。
- `check_warning_audio.sh` は `assets/audio/` の**全 mp3** を対象にファイル間の差 2.5 LU を要求する。
  つまり**使っていない5本が、実際に鳴る10本の音圧を縛っている**。
- 将来使う予定があるなら、そのとき揃っていることに意味があるので現状維持で構わない。
  ただし**コード上どこにも「未使用である」と書かれていない**ため、
  次に触る人は `proximity_warning.mp3` が近接注意で鳴っていると誤解する。
  実際の近接注意は `defaultWarningAudioAssetFor` が返す kind 別の読み上げ（流木・中州）を使う。
- 対応方針: `warning_audio_config.dart` に「現在未使用・将来◯◯で使う」というコメントブロックを設ける。

### P7-03（S3）`playOnce` の追い越しでイベント固有の1回再生が失われうる

P6-03 と同じ所見。持続音の状態同期としては正しい設計だが、
`eventId` を持つ単発再生も同じ経路を通るため、1ドレインサイクル内で追い越されると鳴らずに消える。
音声指令は 1Hz のスナップショットから1件ずつ出るため実際には稀。**予防的な指摘。**

1. **直列化の回帰テスト。** CLAUDE.md が中核要件として名指しし、
   「並行実行すると古い要求が新しい音を止める」という具体的な事故を防いでいるのに、

   `enqueueCommand` 相当のロジックを純Dartへ切り出せば固定できる

2. **アセット網羅テスト。** 「`assets/audio/` の全ファイルが `warningAudioAssets` か
   `defaultWarningAudioAssetFor` のいずれかから参照される」ことを検証するテストがあれば、
   未使用アセットの発生を CI で検出できる。

## 4. 総評

**直列化・復旧・音圧という「聞こえること」に関わる3つの要件は、いずれも実装と根拠が揃っている。**
特に音圧を CI で守る発想（聞こえない警告 = 警告漏れ）と、
周期音の正常な無音を stall と誤認しない配慮は、実機ログから学んだ跡が明確に残っている。

弱点は2つ。**音の種類が意味の種類より少ないこと**（P7-01。既知の TODO）と、
**中核要件である直列化にテストが無いこと**。

指摘: S2 が1件、S3 が2件。テスト不足2件。
