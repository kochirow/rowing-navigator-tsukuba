## 1. 検証して正しかったこと

### 1.1 船体領域の六角形（`ship_domain_service`）

`getShipDomainPoints` が作る6頂点を、進行方向を前・右舷を正とする局所座標へ展開して確認した。

| 頂点 | 局所座標（前, 右） |
| --- | --- |
| 1 | (h/2, 0) 船首 |
| 2 | (s/2, w/2) |
| 3 | (-s/2, w/2) |
| 4 | (-h/2, 0) 船尾 |
| 5 | (-s/2, -w/2) |
| 6 | (s/2, -w/2) |

**巡回順が単純多角形として正しく、凸性の条件が `h > s` に一致する。** 不変条件9（`s <= h`）はこの凸性そのものである。

- `_inflate` は h・w・s に等しく `2·margin` を足すので `h - s` が不変 → 凸性保存 ✓
- `_widenForHeadingUncertainty` は w だけを広げるので `h - s` 不変 ✓
- `staticSweepParam` は h・s を排他領域のまま、w だけ `min(body.w + 2c, exclusive.w)` にするので `h - s` 不変 ✓
- 現行の全艇種で `h - s` は 1x:4.2 / 2x:5.4 / 4x:4.9 / 8+:3.9（船体）、5.4 / 7.8 / 6.8 / 4.02（排他）で余裕がある

### 1.2 不変条件8（broad-phase の到達半径）を検算した

`assessRisk` の到達半径（`collision_risk_evaluator_service.dart:1024` / `:1036`）は次の形をしている。

```
broadPhaseReach = 速度 × 予測地平 + effectiveExclusiveRadius + staticGpsInflatePerSide + 曲率マージン
```

narrow-phase 側は `ContinuousCollisionService._sweepConvex` が **inflate を静的ポリゴン側の投影区間へ加える**（`:188-189`）。つまり掃引領域そのものは膨らまず、障害物が膨らむ。したがって必要な到達距離は

```
移動距離 + R(掃引領域) + inflate + 曲率マージン
```

であり、`R(掃引領域) ≤ R(排他領域)` は 1.1 のとおり w が排他領域で頭打ちだから成立する。**式は正しく、取りこぼしは生じない。**

（当初は「inflate 後の外接円半径は元の半径 + margin より大きく育つので取りこぼす」と疑ったが、inflate が領域側ではなく障害物側に効くため、その心配は当たらない。）

### 1.4 `ContinuousCollisionService` の数値的な正しさ

- `_sweepConvex` は等速並進に対する連続SAT（区間 [enter, exit] の交わり）として正しい。`overlapsAtZero` は全軸のAND ✓

## 2. P1 からの持ち越しの検証結果（重要・P1-01 を修正）

**P1-01「自己交差ポリゴンで警告が漏れる」という仮説は、実測の結果、成立しなかった。**

一時プローブを書いて（レビュー後削除）、「8の字」型の自己交差ポリゴン（SW→NE→SE→NW）に対し、19×19 = 361 点の格子で
`isPointInPolygon`（winding、真値の代用）・`polygonsOverlap`（utils）・`sweepAgainstStatic`（continuous）を突き合わせた。

| 経路 | 不一致 | うち**警告漏れ方向** | 例外 |
| --- | --- | --- | --- |
| utils（`sat_algorithm` + `triangulation`） | 19 / 361 | **0** | 266 / 361 |
| continuous（`ContinuousCollisionService`） | 46 / 361 | **0** | 0 |

**両経路とも、不一致は全て「重なっていないのに重なりと判定する」＝過剰警告の方向だった。** 警告漏れは1点も出なかった。

理由は、耳刈りが自己交差ポリゴンに対して**実面積より広い**三角形集合を作る傾向にあるため。さらに utils 側は 361 回中 266 回が例外になり、その場合は呼び出し側の保守的フォールバック（外接円距離）へ落ちる。

したがって P1-01 は次のように読み替える。

- ✅ **警告漏れの根拠にはならない**（P1 での記述は誤り）
- ⚠️ **過剰警告（原則4）の根拠にはなる** — 自己交差区域を1つ描くと、その周辺で実面積外まで警告が出る
- ⚠️ **性能の根拠にもなる** — utils 経路では 7 割超が例外になり、例外のたびに `findCollisionThreat` のフォールバックと **P1-02 の無条件 `debugPrint`** が走る
- ✅ `isSelfIntersecting` が未使用である事実は変わらない（検証機構が存在するのに呼ばれていない）

**P1-01 の severity を S2 から S3 へ下げ、性質を「警告漏れ」から「過剰警告 + 無駄な例外」へ訂正する。**

なお continuous 側の `_triangulate` は「8の字」では例外を投げなかった。頂点4個では耳が必ず見つかるため。頂点数が多い自己交差では例外になる可能性が高い。

### P2-03（S3）`_segmentsIntersect` が共線・非重複の線分を「交差」と判定する

- `continuous_collision_service.dart:444` — `abC * abD <= _epsilon && cdA * cdB <= _epsilon`。
- 4点すべてが共線なら4つの外積が全て 0 になり、**線分が離れていても true** を返す。
- 帰結: `_polygonDistance` が 0 を返す → `minimumSeparationMeters` が 0 → `nearMissSeparationMeters`（2.0m）を下回るので **すれ違い注意（lv1）が誤って立つ**。
- ただし lv1 は `monitoring` バンド（表示のみ・無音）なので、耳に届く過剰警告にはならない。また船体領域の辺と危険区域の辺が浮動小数点で厳密に共線になる確率は低い。
- 正しくは、共線の場合は投影区間の重なりを見る必要がある。

### P2-04（S3）`_epsilon = 1e-9` を異なる次元の量に使い回している

`continuous_collision_service.dart:69` の単一定数が、次の全てに使われている。

| 使用箇所 | 次元 |
| --- | --- |
| `_edgeNormals` の `length <= _epsilon` | m |
| `_sweepConvex` の `speed.abs() <= _epsilon` | m/s |
| `enter > exit + _epsilon` | **秒** |
| `_pointInTriangle` の `c1 >= -_epsilon` | m² |
| `_segmentsIntersect` の積 | **m⁴** |
| `_cleanPolygon` の点間距離 | m |

実用上 1e-9 はどの次元でも十分小さいので現在は問題を起こさない。ただし「1つの定数を全てに使う」設計は、座標のスケールや単位を変えたときに一斉に崩れる。次元ごとに名前を分けるほうが安全。

### P2-05（S3）`getShipDomains` が `effectiveParamsFor` を使わず BoatType の switch を再実装している

- `ship_domain_service.dart:148-169` が艇種ごとの switch でパラメータを取り出し、そのあと `_widenForHeadingUncertainty` を自前で適用している。
- 同じ処理は `effectiveParamsFor`（`:110`）にもあり、そちらは `boatConfigs.byBoatType()` を使う。
- **不変条件8は「両者が同じ実効パラメータを返すこと」に依存している**（`effectiveExclusiveRadius` は `effectiveParamsFor` 経由、実際の領域は `getShipDomains` 経由）。片方だけ変えると、到達半径と実際の領域が食い違う。
- 現在は一致しているし、テストも一致を確認している。ただし**構造として二重管理**であり、`getShipDomains` は `effectiveParamsFor` を呼ぶべき。

### P2-06（S3）`boundingRadius` のコメントが現行の設定値と矛盾している

- `ship_domain_service.dart:292` — 「`s > h` の艇種(8+など)では側方頂点のほうが遠いため」と書かれている。
- しかし 8+ は船体 h=19.9 / s=16、排他 h=22.9 / s=18.88 で、**いずれも `s < h`**。
- そもそも不変条件9が `s <= h` を要求しており、`s > h` の艇種は存在してはならない。
- `s <= h` のとき側方頂点 `0.5·√(s²+w²)` は必ず外接長方形の対角 `0.5·√(h²+w²)` 以下なので、**`max` の第2項は決して選ばれない**。実害はない（過大側に倒れるだけ）が、コメントが禁止されている状態を根拠にしているのは危険。

### P2-07（S3・到達不能）`StaticObstacleIndex._key` のセル座標が20ビットで折り返す

- `static_obstacle_index.dart:124` — `(x << 20) ^ (y & 0xFFFFF)`。y は下位20ビットだけを使う。
- セルサイズ 40m なので、y と y + 2²⁰ が衝突するのは **41,943 km 離れた区域どうし**。地球上で到達不能。
- 衝突しても `_bounds.touches` が二次フィルタで落とすため結果は変わらない（保守側）。**記録のみ。**

### P2-08（S3）`StaticObstacleIndex` のコンストラクタが `_originOf(source)` を2回走らせる

- `static_obstacle_index.dart:34-36` — 初期化子リストで `_origin` と `_originCosLatitude` がそれぞれ `_originOf(source)` を呼ぶ。
- `_originOf` は最初の有限座標が見つかるまで走査するので、通常は即座に返る。実害はほぼない。
