## 1. 検証した数学的性質

### 1.1 座標変換の一貫性

| 関数 | 方式 | 地球半径 |
| --- | --- | --- |
| `geo_math.computeOffset` | 大円航法（球面） | 6378137 |
| `geo_math.distanceMeters` | 正距円筒近似・平均緯度 | 6378137 |
| `geo_proximity.*` | 正距円筒近似・対象点の緯度 | 6378137 |
| `metric_polygon_buffer._toLocal` | 正距円筒近似・平均緯度 | 6378137 |

**半径定数は全ファイルで一致している。** 値は赤道半径であり、緯度36°の子午線曲率半径（約6367km）より 0.17% 大きい。50m の距離で 8.6cm の過大評価になるが、全経路で同じ定数を使っているため相対的な整合は保たれる。距離を過大評価する方向は警告が遅くなる側だが、35m に対して 6cm なので実害はない。**指摘としない。**

### 1.2 SAT が度空間で正しい理由（確認済み・要文書化）

`sat_algorithm.polygonsOverlap` は `Vector2(latitude, longitude)` すなわち**度**の座標で分離軸判定を行う。緯度36°では経度1度と緯度1度の実距離が 0.809 倍違うため、この平面は等方でない。

にもかかわらず**判定結果は正しい**。度への変換は東西・南北を独立に正の係数で拡大する可逆線形写像であり、凸形状の重なり・凸性・三角形内外判定はいずれもアフィン不変だからである。分離軸そのものは metric 空間の法線と一致しないが、SAT は「変換後の空間での辺法線」を使う限り正しい。

**この前提はコードのどこにも書かれていない。** → P1-03

### 1.3 個別に確認して正しかったもの

- `winding_algorithm.windingNumber` — Sunday の winding number 法として正しい。`isLeft` の符号（経度をx・緯度yとする）も整合。度空間の非等方性は符号を変えない（両項が同じ係数で拡大されるため）
- `winding_algorithm` を頂点2個のポリゴンに適用した場合 → 往復する2辺の寄与が打ち消し合い必ず 0 を返す。`minDistanceToPolygonMeters:35` が2頂点でも `isPointInPolygon` を呼ぶが、誤って「内部」にはならない
- `relative_direction.relativeBearingDegrees` — `(b - h + 540) % 360 - 180`。Dart の `%` は除数の符号に従い常に非負を返すため、任意の入力で -180〜180 に収まる。8方位ラベルの境界（22.5 / 67.5 / 112.5 / 157.5）に隙間・重複なし
- `rowing_navigation.normalizeBearing` / `rowingMapBearing` — 非有限入力を 0 へ落とし、`% 360` で正規化。負値も正しく 0〜360 になる
- `heading.getHeading` — 大円の初期方位として正しい。返り値は -180〜180 で、呼び出し側（`use_navigator:1701` / `collision_risk_evaluator:297` / `channel_path_predictor:234`）が正規化する前提。呼び出し側の確認は P3・P4・P5 へ持ち越し
- `self_intersection.doLinesIntersect` — 交差判定は標準形。`onSegment` の bbox 判定は `d == 0`（共線）のときだけ呼ばれるので正しい
- `geo_proximity._distancePointToSegment` — 線分への射影を `clamp(0,1)` で正しく制限。ゼロ長線分も `lenSq == 0` で保護
- `metric_polygon_buffer` — 符号付き面積で向きを判定してから法線を外向きに取り、鋭角では miter 長で bevel へ切り替える。各辺からの距離が保たれる設計として正しい
- **例外処理の設計が良い**: `collision_risk_evaluator_service:645` / `:699` は幾何例外を捕捉し、外接円ベースの保守的フォールバックへ落ちる。「幾何が壊れても警告経路は止めない」（原則1）が実装されている

## 2. 指摘

### P1-01（S2 → **S3 へ訂正**）自己交差の検証関数が完全な未使用で、自己交差ポリゴンを防ぐ経路がどこにもない

> **2026-07-27 P2 での実測により訂正。**
> 「8の字」型の自己交差ポリゴンに対し 361 点の格子で突き合わせたところ、
> `polygonsOverlap` も `sweepAgainstStatic` も**不一致は全て過剰警告の方向**で、
> 警告漏れは1点も出なかった（utils は 361 回中 266 回が例外→保守的フォールバック）。
> 以下の「警告が出ない」という記述は誤りである。正しい帰結は
> **過剰警告（原則4）と、例外多発による無駄な処理**。詳細は
> [P02_掃引と索引.md](P02_掃引と索引.md) 第2章。

- `lib/utils/self_intersection.dart` の `isSelfIntersecting` / `doLinesIntersect` は、**`lib` 内・`test` 内ともに参照0**。
- 一方で `PolygonTriangulation.triangulate`（ear clipping）は**単純多角形であること**を前提にしている。自己交差した多角形に対しては、耳判定が「他の頂点が三角形内にない」だけを見るため、**多角形の実面積を覆わない三角形集合を返しうる**。その場合 `polygonsOverlap` は重なりを見落とす。
- 臨時危険区域の入力経路に自己交差の検証がない:
  - `static_obstacle_service.dart:140` — 頂点数（3〜上限）のみ検証
  - `static_obstacle_service.dart:100` — 読み込み時も頂点数のみ
  - `managed_hazard_model.dart:94` `validate()` — 中心座標・スケール・回転・マージンの範囲のみ
  - `use_map_editor.dart:138` — `length < 3` のみ
- 再現条件: 利用者が地図上で「8の字」型の臨時危険区域（流木など）を描いて保存する → 保存は成功する → `triangulate` が実面積を覆わない三角形を返す → 交差部分の内側に艇が入っても `polygonsOverlap` が false → **その区域に対する衝突警告が出ない**。`geometryOk` は true のままなので距離ベースのフォールバックにも落ちない。
- 帰結の重さ: 対象は「現地で見つけた流木」= `driftwood`（`risk_evaluator_config.dart:46` で「水面下で見えず、帰結が最悪」と位置づけられている区域）。
- 補足: 自己交差が `triangulate` の例外（`No ear found`）になる場合はフォールバックが働くため安全側に倒れる。**危険なのは例外にならず静かに誤った分割を返す場合。**
- 確認先: 実際に誤分割が起きる頂点列を構成できるか（P2 で `continuous_collision_service` の独自 ear clipping と併せて検証する。同サービスにも同じ前提がある）

### P1-02（S3）障害物ループの `debugPrint` が release ビルドでも出力される

- `collision_risk_evaluator_service.dart:646` は `debugPrint` を無条件に呼ぶ。
- 同じファイルの他艇ループ `:700` は `if (kDebugMode)` で囲んでいる。**同じ役割のログで扱いが違う。**
- Flutter の `debugPrint` は release でも無効化されない（`assert` と違い実行される）。岸の危険区域は release で約310枚（CLAUDE.md）あり、幾何が壊れる状況では **1Hz の評価ループごとに最大310回の文字列生成と出力**が走る。
- 幾何例外が出るのは異常時だけなので常時の負荷ではないが、**最も負荷をかけたくない異常時に負荷が乗る**。
- 修正方針の候補: 他艇ループと同じく `kDebugMode` で囲む。ただし「例外が起きた事実」は診断イベント（`log_config` の診断カタログ）へ残すほうが望ましい。現状は release では痕跡が残らない設計になっていない点も含めて P5 で扱う。

### P1-03（S3）度空間で SAT を行っている前提が無記載

- `sat_algorithm.dart` には座標系についての記述が一切なく、`Vector2(point.latitude, point.longitude)` と書かれているだけ（`:13`）。
- 1.2 のとおり**現状の実装は正しい**が、正しさはアフィン不変性に依存している。同じ空間へ「距離」「半径」「クリアランス」を持ち込むと即座に破綻する（緯度36°で東西方向が 0.809 倍に歪むため）。
- 他ファイル（`geo_proximity` / `metric_polygon_buffer`）は明示的にメートル座標へ変換してから計算しており、**このファイルだけ流儀が違う**。
- 加えて `sat_algorithm` は `Vector2(latitude, longitude)`（緯度がx）、`geo_proximity` は経度がx と、**軸の割り当ても逆**。重なり判定には影響しないが、読む側の負担になる。

### P1-04（S3）`isPointInTriangle` の境界判定が非対称

- `triangulation.dart:34` — `(u >= 0) && (v >= 0) && (u + v < 1)`。`u`・`v` 側は境界を含み、`u + v` 側だけ含まない。
- 帰結: 辺 `ca` の上にちょうど乗る頂点が「三角形の外」と判定され、その頂点を含む耳が切り出される。共線な頂点を持つ多角形で、面積の重なる三角形が生成されうる。
- 実データ（岸の長方形・橋・六角形の船体領域）は全て凸なので現状は顕在化しない。利用者が描いた多角形で共線頂点が出たときに効く。
- 併せて `:30` の `invDenom = 1 / (dot00 * dot11 - dot01 * dot01)` は退化三角形でゼロ除算になるが、呼び出し元の `isEar` が `cross <= 0` を先に弾くため到達しない。**保護は偶然成立している**ので、前提をコメントに書いておく価値がある。

### P1-05（S3）`geo_proximity` に同一のループが2つある

- `minDistanceToPolygonMeters:37-45` と `_distanceToPolygonEdgesMeters:75-83` は、局所座標変換・`edgeCount` の決め方・最短距離ループが完全に同じ。
- 前者は内部を 0 に潰し、後者は符号を付ける、という違いだけ。片方だけ直す事故が起こりうる。
- 不変条件7（`ThreatInfo.distanceMeters` は符号付き）に関わる箇所なので、共通化しておくと壊しにくくなる。

### P1-06（S3・実害なし）`MetricPolygonBuffer` の往復変換が厳密には可逆でない

- `_toLocal:125` は origin と対象点の**平均緯度**の cos を使う。`_fromLocal:140` は **origin の緯度**の cos を使う。
- 往復させると誤差が残る。50m 離れた点で相対誤差 2.8e-6、実距離で約 0.14mm。**実害はない。**
- 記録する理由は、将来この変換を再利用したときに「なぜ往復で一致しないのか」を追う時間を省くため。

### P1-07（S2候補・P5で確認）空ポリゴンで `signedDistanceToPolygonMeters` が `+infinity` を返す

- `geo_proximity.dart:55` — `if (polygon.isEmpty) return double.infinity;`
- 不変条件7 は「`ThreatInfo.distanceMeters` は符号付き（危険区域の内部で負）」であり、`+infinity` は「無限に遠い＝安全」と解釈される値である。
- `minDistanceToPolygonMeters` 側は関数コメントで「頂点0点: 判定不能のため無限大」と明記しており、**判定不能を安全側の値で返している**。これは原則6「データ欠損は安全の根拠にならない」と正面から向き合うべき箇所。
- ただし呼び出し側（`collision_risk_evaluator_service:593`）は `if (obstacle.points.isEmpty) continue;` で先に弾いている可能性が高い。**関数単体としての危うさ**の指摘であり、実際に到達するかは P5 で確認する。

## 5. 総評

**計算そのものは正しい。** 座標変換・分離軸・winding number・線分距離・相対方位のいずれも、境界と符号を追った限り誤りはなかった。度空間での SAT という一見危うい実装も、アフィン不変性により正しい。例外時に外接円へ縮退する設計は原則1をよく実装している。

**弱点は2つ。** 第一に、単純多角形であることを前提にしている ear clipping に対して、その前提を保証する検証（`isSelfIntersecting`）が実装されているのに一度も呼ばれていない（P1-01）。第二に、この層に単体テストがほとんどない。上位のテストが手厚いぶん、幾何プリミティブの境界の誤りだけが検出されない構造になっている。

指摘: S2 が1件（P1-01）、S2候補が1件（P1-07）、S3 が5件。テスト不足7ファイル。
