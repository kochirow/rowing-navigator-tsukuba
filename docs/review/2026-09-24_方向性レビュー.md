## 4. 方向性の提案

### 4.1 フェーズA: 実証(最優先・2〜3週間)

コード変更はほぼ無く、**人の作業が中心**になる。

1. **固定配布を作る**: 現 `main` を1つのビルドにし、TestFlight / Play 内部テストで部内配布。
   Git SHA とbuild番号を控える。
2. **P0 二端末確認**(08-12 §3 P0 の10項目)。8+・7番で問題が出た端末を必ず含める。
   本番RTDB Rulesの取得・ハッシュ比較、App Check の Verified 確認もここで行う。
3. **通常練習1回を全艇で**: 特別な試験ではなく普段の練習で全端末に入れて漕ぐ。
4. **ログを replay**: `tool/replay_field_log.dart` で1練習あたりの発報回数、
   `otherBoatCount` 分布、`permission-denied` 件数、所属 probe の結果を数える。
5. 結果を `docs/review/` に「実機検証レビュー」として残す。

**この結果が、以降のすべての優先順位を決める。**
他艇受信ゼロが再発すれば共有経路の修正が最優先になり、
過剰警告が出れば提示ポリシーの調整が最優先になる。何も出なければ B・C へ進める。

### 4.2 フェーズB: 利用者価値(Aと並行可)

- 練習記録の再設計(ピース単位・スプリット表・DPS×レート・上り/下り)。
- 安全経路に触れないので、Aの検証対象ビルドとは別ブランチで進めてよい。
  **Aで配るビルドには混ぜない**(検証対象を動かさないため)。

### 4.3 フェーズC: 保守(Aの後)

- 09-02 計画の PR1(`SessionDiagnosticBuffer`)→ 結果を見て PR2 以降。
- 同時に不変条件5(航行開始をブロックしない)を切り出し単位で保護するテストを用意する。
  開始工程の分解は、このテストが先。

### 4.4 見送り(当面)

- **ストア一般公開**: 部内運用で他艇警告が機能する証拠が1つも無い段階では早い。
  チーム招待制・Rules・資料は揃っているので、Aが通れば短期間で再開できる。
- **他水域展開**: DESIGN_PRINCIPLES 1.2c の前提記述が先。霞ヶ浦ですら岸が北岸だけ。
- **新しい安全機能の追加**: ラチェット余白が無く、検証もされていない状態で積むと、
  どの変更が現場の挙動を変えたのか分からなくなる。
