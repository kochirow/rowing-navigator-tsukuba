# 実装計画 2026-10-28 記録画面の共有とログ回収

状態: A〜E は実装済み(2026-10-28、ブランチ `agent/2026-10-28-record-share-and-log-bulk`)。F(自動回収)は未着手で、別の作業として検討する。
「練習時間」はアプリ内の定義(艇が動いていた時間)で数える(2026-10-28 利用者決定)。

## 0. 背景と、コードで確かめた事実

ログは各自の端末から LINE で送ってもらって集めている。そのため「共有まで迷わず届くこと」が安全機能の改善速度を決める。

| 症状 | 原因(コードで確認) |
| --- | --- |
| 共有ボタンまで遠い | `record_tools.dart` が警告エピソードを**1件ずつドロップダウン付きで全件**並べ、その下に GPX/CSV/診断ZIP を置いている |
| 警告エピソードが多すぎる | 実機ログ(2026-08-06 の5本)で 1練習あたり **41 / 444 / 59 / 50 / 794 件**。多いのは `position_sharing_unavailable`(426件・750件)と `shore`(13〜34件)。時刻だけ並んでも、いつの何か分からない |
| 「この日の練習」の「共有」が反応しない | `record_replay_screen.dart` の `shareText()` だけが `sharePositionOrigin` を渡さず、`try/catch` も無い。iOS 26 以降は位置の無い共有シートが出ない・落ちる報告がある(share_plus #3769 ほか)。`onShare` は `VoidCallback` なので例外は画面に出ずに消える。GPX/CSV/ZIP はボタンの位置を渡しているので動く |
| 「絞る」の意味が不明 | 実体は `zoomTimelineToSelection`(時間軸を選択区間へ拡大)。動詞だけで対象が無い |
| 未送信かどうか分からない | `Session` に送信済みを表す項目が無い |

## 1. 要件

### A. 警告エピソードの評価を「全件」から「気になったものだけ」にする

- 一覧は全件を並べない。**種類ごとの件数の要約**(例: 「岸 22回・逆走注意 12回・他艇 4回」)を1行で出し、タップで開く折りたたみにする。初期状態は閉じる。
- 評価の対象から**システム系**(`gps_unavailable` / `position_sharing_unavailable` / `pipeline_unresponsive` / `other_boat_track_lost`)を外す。これは「警告が適切だったか」を人が判断する対象ではなく、件数は診断ZIPに既に入っている。
- 開いた中も、種類ごとに**最大5件**(最大危険度の高い順→時刻順)だけ出し、残りは「残り N件を表示」。
- 評価は1件ずつのドロップダウンをやめ、**横並びのチップ**(適切/早すぎる/誤警告/位置ずれ/鳴りすぎ)にする。1タップで保存。
- 代わりに、**この練習全体への一言評価**を1つ置く: 「今日の警告は: ちょうどよい / 多すぎた / 足りなかった」。`Session.alertOverallRating`(新規・任意)として保存し、診断ZIPの manifest に入れる。大量の個別評価より回答されやすい(質問を減らすほど回答率が上がるという調査は下の参考を参照)。
- 「地図で見る ›」(その時刻へ移動)は残す。いつの警告かを地図で確かめてから評価できる。
- 評価の対象は危険区域の種類(`StaticObstacleKind` の全種類)と他艇。種類を足せば自動で対象に入る。
- 既存の `alertEpisodeRatings`(エピソードID→評価)はそのまま使い、保存形式は変えない。

### B. 共有ボタンを上に、迷わない場所へ

- `RecordTools` の順番を入れ替え、**共有カード(診断ログを送る・GPX・CSV)を警告エピソードより上**に置く。削除ボタンは最下部に残す。
- 画面の見出し(戻るボタンの行)の右端に**「ログを送る」アイコンボタン**を置き、スクロールしなくても届くようにする。中身は診断ZIPの共有と同じ。
- 診断ZIPのボタンは文言を「診断ログを送る(開発用)」にし、GPX(Strava用)より目立たせる。ログ回収が最優先のため。
- 送信済みなら、ボタンの下に「送信済み 10/28 18:02」と小さく出す(Dで記録)。

### C. 「この日の練習」の共有を直す・「絞る」を言い換える

- `shareText()` に `sharePositionOrigin`(押したボタンの `RenderBox` から)を渡し、`try/catch` で失敗を SnackBar に出す。`onShare` を `ValueChanged<BuildContext>` か `Future<void> Function(Rect)` に変え、ボタンの位置を受け取れるようにする。
- 既存の `shareOrigin()` と同じ処理を共通の関数へ出し、記録画面の共有はすべてそこを通す(位置の取り忘れを再発させない)。
- 文言: 「共有」→「**結果を共有**」(数値の文章を送る機能だと分かるように。ログの共有と区別する)。
- 文言: 「絞る」→「**時間軸を拡大**」(虫眼鏡アイコン付き)。押した後は既にある「時間軸を全体に戻す」が出る。「この日の練習」(全体選択)のときは拡大しても変わらないので、このボタンを出さない。

### D. 送信済みの記録

- `Session` に `diagnosticsSharedAt`(`DateTime?`、未送信は null)を追加。`toJson`/`fromJson`/`copyWith` を対応させる。古い記録は未送信として読む(スキーマ番号は上げずに任意項目として足す。`alertEpisodeRatings` と同じ扱い)。
- 送信済みにする条件:
  - `ShareResultStatus.success` → 自動で送信済み。
  - `unavailable`(Android の一部など、結果が取れない)→ 「送れましたか? はい/いいえ」を1回聞く。
  - `dismissed` → 未送信のまま。
- 一覧(記録カード)に「未送信」の小さな印を出す(対象条件を満たす記録だけ)。
- 送信済みを手で戻す操作(「未送信に戻す」)を記録画面の共有カードに置く。送り直したいときのため。
- 説明の確認ダイアログで「共有先を選ぶ」を押してから作成中の表示を出す(押す前から回すと、テストの待ちが終わらず、画面でも作業中に見える)。

### E. 練習記録トップで「未送信のログをまとめて送る」

- 対象: `diagnosticsSharedAt == null` かつ **練習時間 15分以上** かつ **距離 2km 以上**。
  - 「練習時間」はアプリ内の定義(記録画面の「練習時間 = 艇が動いていた時間」= `summary.movingTimeSec`)に合わせる。記録の長さ(`durationSec`)ではない。※要確認(下の決めること1)。
  - 距離は `summary.totalDistanceMeters`。
  - 条件の数値は `lib/config/` に前提付きの定数として置く(設計原則7)。
- 置き場所: `record_list_screen.dart` の集計カードの上に、対象が1件以上あるときだけカードを出す。
  「未送信のログ 7件 [まとめて送る]」(合計の大きさは圧縮しないと分からないので出さない)
- 押すと確認シート: 対象の記録をチェックボックス付きで一覧(既定は全部オン)。外した記録は今回送らない。シートの下に「送らずに送信済みにする」(過去に LINE で送った分を片付ける用)。
- 出力: 1つの ZIP `rowing_diagnostics_bundle_<端末ローカル日付>_<件数>.zip`。中身は記録ごとのフォルダ `rowing_diagnostics_<id>/`(今の単体ZIPと同じ5ファイル)+ `bundle_manifest.json`(件数・各記録の開始時刻・距離・時間・アプリ版)。
  受け取り側は今の保存場所(実機テストログデータ/日付/rowing_diagnostics_*)へそのまま展開できる。
- サイズ: 実測で単体ZIPは 1練習 約0.1〜0.55MB。1つのZIPを **25MB 以下** に区切り、超えるときは複数ZIPにして一度に共有シートへ渡す(LINE の上限は1GBとされるが、端末の空きや通信を考えて小さく保つ)。
- ZIP の作成は `compute()`(別 isolate)で行い、作成中は進捗を出す。画面を固めない。
- 共有結果で D の規則どおり、送った記録をまとめて送信済みにする。
- 診断ZIPと同じプライバシー説明(正確な航路・端末情報を含む、自動送信しない)を確認シートに出す。

## 5. 自動回収(F)— 判断が必要

いまの方針は「自動送信しない」(`automaticUpload: false`、2026-07-23・07-28 の設計、プライバシー画面の文言)。Firebase は課金を避けるため Spark プランで運用している(docs/store/無料枠・可用性検証_2026-07-21.md)。自動回収はこの2つを変えるので、利用者が決める。

| 案 | 中身 | Spark のまま | 手間 | 注意 |
| --- | --- | --- | --- | --- |
| F0. やらない(A〜Eだけ) | まとめて送るで手作業を1回にする | ○ | なし | 送ってもらう声かけは残る |
| F1. Firestore に分割保存 | 練習終了後、対象条件を満たすZIPを900KB以下に分けて `teams/{teamId}/diagnostic_uploads/` へ書く。開発者は `tool/` のスクリプトで取り出して消す | ○(保存1GiB・書込2万回/日の範囲。1練習 約0.5MB→約1〜2件の書込) | 中 | Firestore は大きなファイル置き場ではない。容量1GiBを他のデータと共有するので、取り出したら消す運用が要る |
| F2. Cloud Storage に保存 | 普通のファイルアップロード。失敗時は送信待ちの列に残して次回再送 | ×(2026-02-03 以降 Storage は Blaze 必須) | 小〜中 | Blaze へ上げる必要。CLAUDE.md は課金設定の変更を AI に禁じているので、移行は利用者が行う。無料枠内(5GB)なら実費0だが、予算アラート・上限の設定と、Maps 課金プロジェクトとの分離方針の見直しが要る |

F1/F2 どちらでも共通に必要なこと:
- 利用者の同意(設定でオン/オフ、既定はオフで初回に案内)。プライバシー画面と規約(`termsVersion`)の更新。
- チームの管理者だけが読めるルール(Firestore/Storage Rules と `firebase_rules_test` のテスト)。
- 送信待ちの列(端末内)と再送。D の `diagnosticsSharedAt` をそのまま「回収済み」に使える。
- アップロードは航行終了後・Wi-Fi 時だけ(航行中の通信と電池を使わない)。

推奨: **まず A〜E を入れ、F は F1 を別の作業として検討する。** A〜E だけで「送る手間」は1回のタップになり、F の同意・ルール・規約更新は安全経路と無関係に後から足せる。
