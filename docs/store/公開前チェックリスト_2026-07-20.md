## 1. 採用した配布・認可モデル

### チーム招待制 — 実装済み

- [x] 初回画面を「チームを作成する」「招待コードでチームに参加する」の二択にする
- [x] メール/パスワード画面は設けず、内部でFirebase Anonymous Authを使う
- [x] 参加済み端末は保存済み匿名UIDと所属を起動時に自動復元し、通常は操作不要にする
- [x] 通常機能にサインアウト/再匿名化を置かず、認証消失時だけ固定コード再参加へ戻す
- [x] チーム作成時に12文字・約59bitの固定コードを1回だけ生成し、既存20文字コードも継続受理する
- [x] コードは自動変更・自動失効させず、チーム員全員が表示・コピーできる
- [x] Firestoreを所属情報の権威、RTDBを位置共有用の最小bridgeとする
- [x] RTDB/Firestore共有データを`teams/{teamId}/...`へ分離する
- [x] 未認証・未所属・別チームをRulesで拒否する
- [x] チーム員全員が臨時危険区域を作成・編集・削除できる
- [x] チーム員全員が固定流木を更新できる。基準形状そのものの削除は許可しない
- [x] 招待コード一覧取得を拒否し、正確なコードを知る端末だけ参加できる
- [x] 偽コードを既存の別チームへ紐付ける操作を拒否する
- [x] アカウント削除時は自艇位置、艇profile、所属を原子的に消し、作成者UIDを匿名化する

固定コードは共有された時点で参加資格になる。一般公開では運用上の注意書きだけでは紛失端末・退部者・漏えいコードを失効できないため、管理者によるメンバー失効とコード更新をリリース条件とする。実装までは限定配布に留める。

## 5. Firebase無料枠・省電力の運用ゲート

前提は週6日、1回2時間、同時12台。平均26.07回を保証側へ切り上げ、月27回・1台あたり194,400秒/月で評価する。

- 位置payloadの代表実測: 約146 bytes、テスト上限250 bytes未満
- 全時間最短2秒送信の位置payload本体: 約3.50GB/月（12送信×12受信の最悪fan-out）
- 1練習2時間の位置payload本体: 約129.6MB
- 自動テストで固定するアプリpayload予算: 4GB/月以下
- RTDB downloadにはキー名、WebSocket、TLS、再接続等のoverheadが加算される
- Spark RTDB上限は保存1GB、download 10GB/月、同時接続100。理論値だけで10GB未満を保証しない
- Firestore危険区域100件時の想定readは約1,248件/練習日（50,000件/日の約2.5%）

公開前の合格条件:

- [ ] 12台×2時間の1練習で、RTDB download増分が200MB以下、月予測が6GB以下に収まる
- [ ] 全状態でクラウド送信が2/5/10秒となり、2秒未満のwriteがRulesで拒否される
- [ ] 警告判定/GPS/画面上の地図と現在位置はローカルで継続し、送信間隔だけを間引く
- [ ] 低電池モード、画面点灯2時間、画面消灯30分、別アプリ30分の消費率と端末温度を記録する
- [ ] quota 70%、85%、95%相当で担当者が気付ける日次確認手順を用意する
- [ ] quota超過時は安全機能が一部停止し得るため、アプリを唯一の安全手段として扱わない

## 13. GO判定条件

一般公開のGOは次のすべてが揃った時だけ出す。

1. 本番Rules、Anonymous Auth、App Checkが正規配布版で動き、2チームの相互遮断が通る。
2. 12台×2時間の通信量が運用基準内で、電池・発熱・警告遅延が許容範囲にある。
3. 同じ署名済みRCがiOS/Androidの背景動作、圏外復帰、削除を含む実機試験に合格する。
4. 危険区域、録音音声、複数艇、安全運用を現地責任者が承認する。
5. 公開URL、削除、UGC運用、App Privacy/Data safetyが実コードと一致する。
6. ストア素材、固定審査コード、審査手順、提出証跡がRCへ固定される。

1項目でも未完了なら一般公開せず、TestFlight / Play Internal testingを継続する。
