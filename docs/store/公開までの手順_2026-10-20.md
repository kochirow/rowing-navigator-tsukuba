## 1. Firebase(最優先・10〜30分)

### 1-1. Rules を本番へ反映する

PR #64(管理者の交代)と #65(危険区域の削除を元に戻せるようにする)は Rules の変更を含む。
**反映するまで、アプリの「管理者にする」「管理者を引き継ぐ」「削除」「元に戻す」は
permission-denied で失敗する**(航行・警告・位置共有には影響しない)。

```bash
firebase deploy --project rowing-navigator-tsukuba --only firestore:rules,database
```

- **反映と、新しいビルドの配布をそろえる。** 新しい Rules では、旧版アプリの「削除」は
  他人の区域で拒否される(区域は残る＝安全側)。新しいアプリの削除は新しい Rules が無いと拒否される。
- 反映した日時と、反映したコミット(`git rev-parse HEAD`)を記録しておく。

### 1-2. App Check を「強制」にする

アプリは匿名認証なので、アプリさえあれば誰でもアカウントを作れ、チームも無制限に作れる。
不正利用・課金の暴走を止める最後の関門が App Check である。

1. Firebase Console > App Check で、Android(Play Integrity)と iOS(App Attest)が登録済みか確認する。
2. **Monitor(監視)のまま**、配布版で数回練習し、「Verified requests」がほぼ100%になるのを確認する。
3. Realtime Database と Cloud Firestore を **Enforce(強制)** に切り替える。
4. 切り替えた後、配布版で航行開始・他艇表示・危険区域の追加ができることを確認する。
   - debug ビルド(Xcode から直接入れたもの)は、debug token を登録しないと弾かれる。

### 1-3. 予算アラートを確認する

Google Cloud Console > お支払い > 予算とアラート で、月の予算と 50%・90%・100% の通知が
有効か確認する(7月に設定済みのはず)。**公開後1週間は毎日**、Firebase Console の
Realtime Database / Firestore の「使用状況」を見る。

## 2. API キー(公開リポジトリのため必須・15分)

リポジトリ `kochirow/rowing-navigator-tsukuba` は **PUBLIC** で、git の履歴から古いキーを
誰でも取り出せる。

| 履歴にあるキー(先頭だけ) | 入った時期 | 対処 |
| --- | --- | --- |
| `AIzaSyDogp…`(iOS の Google Maps 用) | 2024-06-08 に追加、2026-07-30 に削除 | **無効化(削除)する** |
| `AIzaSyAf05…` / `AIzaSyAoAS…` / `AIzaSyBRfx…` | 2024-06(旧 Firebase 設定) | 今のプロジェクトのキーでなければ無効化する |

Google Cloud Console > API とサービス > 認証情報 で:

1. 上の古いキーが残っていれば **削除** する(または「キーを再生成」)。
2. 今使っている Maps キー(`ios/Flutter/Secrets.xcconfig` と `android/secret.properties` の値)に制限をかける。
   - iOS 用: 「iOS アプリ」制限で bundle ID `jp.kosei.rowingnavigator.tsukuba`、API 制限は Maps SDK for iOS だけ。
   - Android 用: 「Android アプリ」制限でパッケージ名 `jp.kosei.rowingnavigator.tsukuba` と、
     署名の SHA-1(アップロード鍵 `ED:24:8E:D1:…:DA:2E`、Play App Signing を使うならその証明書も、
     debug 鍵 `4F:51:B4:20:…:BA:AC`)、API 制限は Maps SDK for Android だけ。
3. Firebase の API キー(`lib/firebase_options.dart` にあるもの)は公開されても仕方のない設計だが、
   「API の制限」を Firebase に必要な API(Identity Toolkit、Firebase Installations、
   Firebase App Check、Realtime Database、Cloud Firestore など)に絞ると、ほかの API での課金悪用を防げる。
   **絞りすぎるとアプリが動かなくなる**ので、変更後に配布版で航行開始まで確認する。

## 4. ストア(段階を踏む)

いきなり一般公開せず、次の順に進める。

### 4-1. まず「部内だけ」に配る(TestFlight / Google Play のクローズドテスト)

- **iOS**: App Store Connect でアプリを作り、TestFlight の内部テスター(最大100人)へ配る。
- **Android**: いまの Firebase App Distribution / APK 配布から、**Google Play Console のクローズドテスト**へ移す。
  - Google は、Play 以外から入れるアプリにも開発者の本人確認を求める方針で、2026年9月から4か国で始まり、
    2027年に全世界へ広がる予定。日本は最初の対象外だが、早めに Play へ移すほうが安全。
  - **個人の開発者アカウント**(2023年11月以降に作成)では、本番公開の前に
    「12人以上が14日間続けてテストに参加する」条件がある。部員で水上テストをすれば、そのまま満たせる。
    組織アカウント(D-U-N-S 番号が必要)ならこの条件は無い。
- 配布ビルドの作り方(Git SHA が必ず入る):
  - Android: `zsh tool/flutter_with_provenance.sh build appbundle --release`(英数字パスの複製で作る)
  - iOS: Xcode の Archive でよい(SHA は自動で入る)。

### 4-2. 次に「URL を知る人だけ」に出す(任意)

- **Apple の Unlisted App Distribution**(非表示配布): 検索に出ず、リンクを知る人だけが入れる。
  桜川の部だけで使う今の運用に合う。App Store Connect から申請する(通常の審査も受ける)。
- Android はクローズドテストのまま運用を続けてもよい。

### 4-3. 審査に出すときの入力

[ストア掲載・審査資料案.md](ストア掲載・審査資料案.md) と [データ取扱い台帳.md](データ取扱い台帳.md) にそのまま使える文面がある。

- 審査用のチームを1つ作り、その招待コードを審査メモに書く(審査期間中はコードを更新しない)。
- 「審査で質問されやすい点」(Background Modes の audio/location、ユーザー投稿、アカウント削除、クレジット)を審査メモへ貼る。
- App Privacy(Apple)/ データ セーフティ(Google)は台帳の回答案どおり。位置情報は「収集する」と答える。
- 説明文に **「警告音声: VOICEVOX:ずんだもん」** と原開発者の表記を入れる(アプリ内にも表示済み)。
- Google Play の位置情報フォアグラウンドサービスの申告には、実演動画が要る(撮る画面は審査資料案に列挙済み)。

## 5. 運営の手順(起きたときに使う)

### 管理者の端末を紛失し、交代もできないとき

アプリの「管理者を引き継ぐ」は、管理者が**もうメンバーでない**ときだけ使える。紛失した管理者を
運営がメンバーから外せば、残ったメンバーが引き継げる。

1. 依頼者から、チーム名と、紛失した管理者のメンバーID(先頭8文字。各自の「チーム」画面に出ている)を聞く。
   本人確認(部の責任者に確認するなど)をする。
2. Firebase Console > Firestore で `teams/{teamId}` を開き、`adminUid` がそのメンバーIDで始まることを確認する。
3. 次を削除する(`{uid}` は `adminUid` の値):
   - Firestore: `teams/{teamId}/members/{uid}`、`users/{uid}`
   - Realtime Database: `team_members/{teamId}/{uid}`、`team_users/{uid}`、
     `teams/{teamId}/live_positions/{uid}`、`teams/{teamId}/boat_profiles/{uid}`
4. 依頼者に「チーム」画面の「管理者を引き継ぐ」を押してもらう。
5. 新しい管理者に「招待コードを更新」を押してもらう(紛失端末が古いコードで再参加できないように)。

### 不適切な危険区域の通報を受けたとき

- Firebase Console > Firestore > `teams/{teamId}/temporary_obstacles/{ID}` を確認し、不適切なら削除する
  (通報文に「ID: …」が入っている)。
- 投稿したメンバーを外す必要があれば、そのチームの管理者に依頼する(管理者が不在なら上の手順)。
- Apple は、通報への対応を 24 時間以内に求めることがある。受付フォームの通知をメールで受け取れるようにしておく。
