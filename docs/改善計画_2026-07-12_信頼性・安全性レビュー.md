# 信頼性・安全性レビューと改善計画(2026-07-12)

対象: rowing-navigator-tsukuba 全体(lib/ 76ファイル、約6,100行)
観点: ①エラーなく確実に動作するか ②実用上の問題 ③安全面
前提: 2026-07-07の衝突警告安全レビューで対処済みの項目(幾何判定のfail-safe、NaN正規化、幽霊艇フィルタ、不確実性マージン等)は再掲しない。本レビューはその「外側」——GPS入力の品質、ストリームの死活、無音故障(silent failure)——に焦点を当てた。

---

## 1. 総評

衝突判定ロジック自体は前回レビューで多層防御が入っており堅牢。一方で、**「判定に入る前のGPS入力の品質管理」と「システムが死んだことに気づく仕組み」がほぼ存在しない**。安全支援アプリで最も危険なのは誤警告ではなく、「動いているように見えて実は保護が止まっている」無音故障であり、現状これが複数経路で起こりうる。

具体的には: GPSストリームがエラーで止まっても `print` されるだけで漕手には何も知らされない。精度30m超の劣悪なfixもそのまま衝突判定に使われる。送信失敗が続いても自分は気づかず、他艇の画面から自艇が消える。緊急警告の音声読み上げ中にコーチシグナルが来ると緊急警告が打ち切られる。

## 2. 所見一覧

重大度: 【高】安全機能の無音停止・警告の欠落につながる / 【中】運用で顕在化しうる / 【低】品質向上

### A. 安全面

#### A-1【高】GPS途絶の無音故障 — 死活監視(ウォッチドッグ)がない
`useNavigator.startNavigation()` の位置ストリームは `onError: print` のみ。位置情報サービスがOFFにされた・ストリームが例外で終了した・fixが来なくなった場合、**リスク評価・記録・送信がすべて静かに止まり、画面は最後の状態のまま表示され続ける**。漕手は保護されていると信じたまま航行する。マリンナビ界隈(SignalK等)でも「stale dataを現在値のように表示し続ける」ことが最重要課題とされている。
→ 対処: 最終fix時刻を監視するウォッチドッグタイマー(例: 5秒fixなしで画面バナー、10秒で TTS「GPS信号が途絶えています」+警告音)。ストリームの自動再購読も併せて実装。

#### A-2【高】GPS品質ゲートがない — 劣悪fix・外れ値がそのまま判定に入る
`processPosition()` は accuracy がどんなに悪くても(50m超でも)そのまま採用する。水面はマルチパス(反射)でスマホGPSの誤差が増えやすく、瞬間的な数十mのジャンプも起こる。ジャンプは誤警告(存在しない接近)と警告漏れの両方を生む。不確実性マージン(上限8m)はこれを吸収しきれない。
→ 対処(業界標準の3段フィルタ):
1. **精度ゲート**: accuracy > しきい値(例25m)のfixは棄却
2. **ジャンプ検出**: 前回位置からの移動速度が物理的上限(例10m/s)を超えるfixは棄却
3. **平滑化**: 位置に軽量なEMAまたは簡易カルマンフィルタ
ただし「棄却しすぎ→無防備化」が新たな無音故障になるため、**棄却が連続したらA-1のウォッチドッグに接続して「GPS精度低下」を漕手に通知**すること。棄却中も最後の正常位置での近接警告は継続する。

#### A-3【高】TTSに優先度制御がない — コーチシグナルが緊急警告を打ち切る
`TtsService.speak()` は常に `stop()` してから読み上げる。「緊急。ただちに停止」の読み上げ中にコーチのクイックシグナルが届くと、**緊急警告が途中で打ち切られてシグナルが読まれる**。
→ 対処: 優先度付きキュー(緊急 > 警告 > 注意 > シグナル)。高優先度の読み上げ中は低優先度を待機または破棄。緊急はビープ音と併走しているが、読み上げの方向情報(「右前方、他艇接近」)が失われるのは実害がある。

#### A-4【中】サイレントモード・低音量で警告が聞こえない
audioplayers は音量0.5固定・メディア音量依存。iOSのサイレントスイッチON、メディア音量ゼロだと**警告音もTTSも一切鳴らない**。乗艇前に気づく手段がない。
→ 対処: ①iOSで playback カテゴリの AudioContext を設定(サイレントスイッチを無視して再生)②ナビ開始時にテスト音を鳴らし「聞こえたら開始」フロー、または volume_controller 等でメディア音量を検査し低ければ警告表示。

#### A-5【中】画面ロック・バックグラウンドでGPSが静かに止まる
wakelock は「アプリが前面にある限り」画面を保つだけ。誤ってホームボタン/電源ボタンを押すと、iOSは約2分〜でsuspendされ追跡停止。Androidもメーカー独自の省電力で殺される。再度開くまで自艇は他艇から幽霊艇として消え、自分の警告も止まる。
→ 対処: ①`AppLifecycleState` を監視し、ナビ中にバックグラウンド化したら即座に通知+復帰時に「◯秒間追跡が停止していました」を表示 ②geolocator の foregroundNotificationConfig(Android)/ allowBackgroundLocationUpdates(iOS)でバックグラウンド追跡を有効化する。現行実装は利用者がフォアグラウンドで明示的に開始し、Androidはlocation foreground service、iOSはBackground Location modeを使うため、停止中の自動追跡を行わず「常に許可」を必須にしない。

#### A-6【中】端末間の時計ズレの実測補正がない
幽霊艇フィルタ(30秒)・不確実性のaging・シグナルの `since` はすべて各端末の `DateTime.now()` 依存。スマホの自動時刻同期がOFFの端末が1台混ざると、**健全な艇が幽霊艇扱いで消える/古いデータが新鮮扱いされる**。コメントで「余裕を持たせている」とあるが実測補正はない。
→ 対処: RTDB の `.info/serverTimeOffset` を購読し、送信タイムスタンプと受信側の鮮度判定の両方をサーバー時刻基準に補正する。実装コストは小さい。

### B. 信頼性(エラー処理)

#### B-1【高】起動時初期化のエラーが未処理 — 「Loading...」のまま永久スタック
`home_map_screen` の初期化 useEffect 内で `permission.requestLocationServicePermission()`(権限拒否で Future.error)や `getCurrentPosition`(屋内で長時間かかる/失敗)が throw すると、`Future(() async {...})` 内の例外は握りつぶされ **loading が true のまま復帰手段なし**。権限を拒否した部員のアプリは永久に起動しない。
→ 対処: try/catch でエラー画面(理由+「設定を開く」+「再試行」ボタン)。位置が取れない間は既定座標(桜川艇庫)で地図を出す選択肢も。

#### B-2【高】getCurrentPosition に timeLimit がない — Start Nav が無限ハング
`GeoService.getCurrentPosition` / `startNavigation` の初期fix取得にタイムアウトなし。GPSが掴めない状況では **Start Nav を押してもモーダルが閉じたきり何も起こらない**。deprecated な `desiredAccuracy` 引数も使用中(geolocator 14 では LocationSettings 推奨)。
→ 対処: `timeLimit: Duration(seconds: 15)` + TimeoutException 時のリトライUI。API を LocationSettings ベースに更新。

#### B-3【高】受信ストリーム内部の listen に onError がない
`MessageService.getMessagesStream`(Firestore側)・`DynamicObstacleService`・`StaticObstacleService` の StreamTransformer 内の `stream.listen((..) {...})` はいずれも onError 未指定。**上流エラー1発で他艇/障害物の受信が完全停止**する(前回レビューS2-3で鮮度フィルタによる緩和はされたが、ストリーム自体の復旧はない)。危険区域リストが空のまま固まると近接警告も出ない。
→ 対処: onError の伝播+指数バックオフ付き自動再購読。障害物ストリームが途絶した場合は「危険区域情報が古い可能性」を表示。

#### B-4【中】位置送信の失敗が握りつぶされる — 「自分が見えていない」ことに気づけない
`messageService.sendMessage(message)` は await されず、失敗時の catchError もない(未処理Future例外)。圏外・RTDB障害で送信が失敗し続けても本人は正常に見え、**他艇の画面からだけ自艇が消える**。
→ 対処: `.catchError` +連続失敗カウンタ。N回連続失敗で「位置を共有できていません(他艇からあなたが見えません)」とバナー+TTS通知。UI に最終送信成功時刻を出す(C-2)。

#### B-5【中】セッション記録がクラッシュで全損
`sessionPoints` はメモリ上のみで、保存は `stopNavigation()` 時の一回だけ。電池切れ・クラッシュ・強制終了で練習1回分のログが完全に消える。
→ 対処: 60秒ごと等の定期チェックポイント保存(同一IDに上書き)。起動時に未クローズのセッションを検出して復元。

#### B-6【低】シグナル購読の取りこぼし
`watchSignals` の `since: DateTime.now()` は端末時計依存(A-6と同根)。また購読エラー時は print のみで再購読なし。

### C. 実用上の問題

#### C-1【中】方位平滑化の重み付けが逆 — 旋回時に表示・判定が遅れる
`buildMyBoat` の平均計算は 現在値1/4 + 前回1/4 + **前々回1/2** という重みになっており、最も古いサンプルが最大の重みを持つ。旋回中は heading が実際より大きく遅れ、船首方向の予測(衝突判定の進行方向)にも影響する。
→ 対処: 円環EMA(新しい値に大きい重み、例 α=0.5)に置き換え。ユニットテストで180度境界と旋回追従を検証。

#### C-2【中】通信・GPS状態の可視化がない
現状、漕手が「自分は今ちゃんと共有されているか/GPSは正確か」を知る手段がない。
→ 対処: NavStatusCard に ①GPS精度(m)②最終送信成功からの秒数 ③受信中の他艇数 の小さなインジケータを追加。精度・通信の劣化を色で表示。

#### C-3【中】艇の識別が匿名UIDのみ
boatId = 匿名認証UID。再インストールでIDが変わり、コーチ画面では艇種ラベルしか区別できない。同型2クルーが出ると見分けられない。
→ 対処: ナビ設定モーダルに艇名(クルー名)入力を追加し、Message に載せて表示。SharedPreferences に保存。

#### C-4【低】電池関連
bestForNavigation+画面常時ON+毎秒処理で消費は大きい(設計上の割り切りは妥当)。自艇の電池残量が閾値(例20%)を切ったら漕手本人とコーチ双方に通知すると安心感が上がる(コーチ側の表示は既にある)。

#### C-5【低】ペース表示の異常値
`500 ~/ speed` は speed が 0.01m/s のとき5万秒と表示される。停止判定しきい値(0.5m/s)未満は「--」表示に。

#### C-6【低】アラート音の再生継続性
オーディオフォーカス喪失(通話・他アプリ音声)後にループ再生が復帰しない可能性。ナビ中は毎回 play を発行しているため実害は限定的だが、実機で通話割り込みテストをすること。

### 実装上の注意
- フィルタ類(品質ゲート・平滑化)は**必ずユニットテストを先に書く**(既存の test/ の流儀に合わせる)。棄却しすぎで警告が止まる回帰が最も危険。
- しきい値(精度25m・ジャンプ10m/s・途絶5/10秒)はすべて config に定数として置き、桜川での実走で調整する。
- フェーズ1完了までは、部の運用ルールとして「アプリはあくまで補助。目視・声掛けが主」を明示しておくこと。
