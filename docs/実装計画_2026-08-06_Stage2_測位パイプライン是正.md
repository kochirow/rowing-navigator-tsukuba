## 0-0. 受け入れ基準の読み方【Stage 2・3 共通・必読】

Stage 1 で、受け入れ基準の書き方が原因で作業が止まった。同じことを繰り返さないための規約。

> **何が起きたか**: S1-02 に「再生した S1 が実機 `filtered_*` と med 1m 以内」という
> 基準を書いた。D で 5.60m となり不合格。担当は「初期状態が復元できない」と判断して停止した。
> 実際の原因は別（再生に前方前進の再現が漏れていた）で、しかも**同じ基準を C で測れば
> 0.71m で合格していた**。基準の値が「どのログを選ぶか」で変わることを、書いた側が想定していなかった。

### 規約1: すべての数値基準に3点を書く

| 要素 | 意味 |
| --- | --- |
| **目的** | この基準が守っている判断は何か。守れないと何が言えなくなるか |
| **出典** | 実測値か、設計値か、勘か。実測なら**どのログのどの指標か** |
| **不合格時の分岐** | 止まるのか、記録して進むのか、誰に相談するのか |

**「不合格時の分岐」が書かれていない基準は、実装者が勝手に止めてよい。**
書き手（計画側）の不備である。

### 規約2: 端末差のある指標は、必ず端末別に基準値を持つ

以下は**端末ごとに 8 倍の開きがある**。単一の閾値を置いてはいけない。

| 指標 | A:4x | B:8+前 | C:2x | D:8+cox | E:8+後 |
| --- | --- | --- | --- | --- | --- |
| \|filtered − raw\| med | 2.48m | 2.71m | **0.71m** | **5.57m** | 2.75m |
| 10m 超のずれ | 165点 | 0点 | 85点 | 202点 | 44点 |
| 岸警告エピソード | 50 | 13 | 16 | 64 | 107 |
| 測位間隔 med | 2001ms | 2530ms | 2658ms | 2003ms | 2039ms |

**「5ログすべてで」測り、端末別に判定する。1ログで代表させない。**

### 規約3: `track.csv` はアプリが見たものの全部ではない

Stage 1 で判明した具体例:

```
elapsed=1ms  gps_bootstrap_unusable {"accuracyMeters": 8.13, "timestamp": "…21:23:21Z"}
```

D のセッション開始は 22:06:46。**43分前のキャッシュ測位**が推定器の初期値になった可能性があるが、
**座標が診断イベントに記録されていないため復元できない。**
`track.csv` の1行目より前に、アプリは既にこの1点を見ている。

→ **再生と実機を突き合わせる基準には、必ずウォームアップ除外窓（60秒）を設ける。**
→ 再生が実機と合わない原因を「ログの不足」に帰する前に、
  **端末別の差分が §規約2 の表と対応していないか**を必ず先に確認する。
  対応していたら、それは再生側の再現漏れであってログの問題ではない。

### 規約4: ゼロを要求する基準は、根拠と許容を書く

「0回」「0件」は、達成できないとき**判断の余地がない**。次のどちらかにする。

- **真に0でなければならない**（安全に直結）→ その旨を明記し、不合格時は止まる
- **改善方向を示したい**→ 「現状 X から減っており、かつ Y を上回らない」と書く

### 規約5: 独立したタスクは、他タスクの不合格で止めない

Stage 1 では、出荷物である S1-01 が、無関係な S1-02 の不合格で止まりかけた。
**§1 のタスク一覧の「依存」欄に無いタスクは、他が赤でも進めてよい。**

### 規約6: 挙動を変える Release ごとにベースラインを取り直す

本計画は**挙動を変える Release が連続する**。
最初のベースライン（`baseline_2026-08-06.json`）と比べ続けると、
**前の Release で既に直った項目を「まだ直っていない」と誤判定する。**

| 比較の基準にするもの | |
| --- | --- |
| Release 2a の判定 | Stage 1 完了時点のベースライン |
| Release 2c の判定 | **2a 完了時点で取り直したベースライン** |
| Stage 3 の各判定 | **Stage 2 完了時点で取り直したベースライン** |

取り直しは `CAPTURE_REPLAY_BASELINE=true` で行い、
**ファイル名に基準時点を入れる**（`baseline_after_2a.json` など）。
古いベースラインは消さない（変化の履歴が診断に効く）。

# Release 2a — Fix Ingress のアプリ側是正

## S2-01. 900ms ゲートを fix timestamp 基準へ

### 目的
測位間隔が **2.0s / 3.0s ちょうどに量子化**され、1.0s は A/E で 5%・B/C/D で 0%。
fix のタイムスタンプが1秒境界に並んでいるので、**CoreLocation は 1Hz で出しており、
アプリが 2/3 を捨てている。**

### 現状

```dart
// use_navigator.dart:2579-2587
final processTick = safetyClock.value.elapsed;      // ← 到着時刻
if (lastProcessedTick.value != null &&
    (processTick - lastProcessedTick.value!).inMilliseconds <
        positionUpdateInterval * 1000 - 100) {       // 900ms
  return;                                            // ← 何も記録せず捨てる
}
lastProcessedTick.value = processTick;
```

**判定が到着時刻である。** iOS が複数 fix をまとめて配信すると、
バッチの2つ目以降が 900ms 以内に到着して捨てられる。
捨てられるのは**新しいほう**なので、rate が半減し遅延も増える。

### 変更

```dart
// 間引きの判定は「到着時刻」ではなく「fix の時刻」で行う。
// 到着時刻で判定すると、OSがまとめて配信したときにバッチの新しい側を
// 捨ててしまい、実効レートが半減し遅延も増える(2026-08-06 実機ログ:
// 測位間隔が 2.0s/3.0s に量子化され、1.0s は 5% 以下)。
final fixTimestamp = rawPos.timestamp;
final previousFixTimestamp = lastProcessedFixTimestamp.value;
if (previousFixTimestamp != null &&
    fixTimestamp.difference(previousFixTimestamp).inMilliseconds <
        positionMinimumFixIntervalMs) {
  appendRuntimeDiagnostic('gps_position_coalesced', {
    'arrivalDeltaMs': (processTick - lastProcessedTick.value!).inMilliseconds,
    'fixTimestampDeltaMs':
        fixTimestamp.difference(previousFixTimestamp).inMilliseconds,
    'droppedFixAgeMs': now.difference(fixTimestamp).inMilliseconds,
    'reason': 'fix_interval',
  });
  return;
}
```

### 新しい設定値
`lib/config/navigator_config.dart`

```dart
/// 安全評価を回す最小のGNSS fix間隔 [ms]。
///
/// 到着時刻ではなく **fixのタイムスタンプ** に対する下限である。
/// iOS の実効上限は約1Hzなので、1秒より詰めても新しい情報は増えない。
/// 900ms ではなく 700ms にするのは、1Hz の fix が 1000±ジッタ で
/// 並ぶときに、ジッタで1件飛ばすのを避けるため。
const positionMinimumFixIntervalMs = 700;
```

> **900 → 700 にする理由**: 1Hz の fix 時刻が 1000ms 間隔でも、
> 端末時計の丸めで 950ms などになり得る。fix 時刻基準にした以上、
> 到着ジッタの心配は無いので、閾値は「重複除去」の役割だけでよい。
> 逆に 0 にすると同一 fix の重複（`duplicate_fix`）を弾けない。

### 時刻の逆行への備え
`rawPos.timestamp` は端末時計であり、**逆行し得る**（時刻同期・手動変更）。

```dart
if (previousFixTimestamp != null &&
    fixTimestamp.isBefore(previousFixTimestamp)) {
  // 逆行した fix は採用しない(FIX_TIMESTAMP_MONOTONIC 契約)。
  // ただし逆行が continuously 続く場合は時計が飛んだので、
  // 単調時計側で generation を進めて受け入れ直す。
  return; // rejectionReason: timestampRegression
}
```

**逆行が `fixTimestampRegressionResetSec`（既定 10秒）続いたら、
基準をリセットして受け入れ直す。** そうしないと時計が戻ったとき永久に測位を捨てる
（機能を止めない・原則1）。

### テスト
`test/hooks/position_ingress_test.dart`（新規。純ロジックへ切り出して単体化する）

`processPosition` は巨大な hook の中にあるので、**間引き判定を純関数へ抽出する**:

```dart
// lib/services/fix_ingress_policy.dart
class FixIngressPolicy {
  FixIngressDecision decide({
    required DateTime fixTimestamp,
    required Duration arrivalMonotonic,
    required DateTime now,
  });
}
```

| # | 入力 | 期待 |
| --- | --- | --- |
| 1 | 1Hz の fix が 1000ms 間隔で到着 | **全件採用**（現行は約半分） |
| 2 | 3件がまとめて到着（fix時刻は 1s ずつ違う） | **全件採用**（S2-02 と合わせ） |
| 3 | 同一 fix の重複 | 2件目を `duplicate` で棄却 |
| 4 | fix 時刻が逆行 | `timestampRegression` で棄却 |
| 5 | 逆行が 10 秒続く | 基準リセットして採用再開 |
| 6 | 到着が 100ms 間隔でも fix 時刻が 1s ずつ | 全件採用 |

### 受け入れ基準

**(a) バッチ配信で測位を取りこぼさない**
- 目的: 仮説αの是正が効いていることの証明。これが本タスクの存在理由。
- 出典: 設計値（変換の定義から導かれる）。
- 判定: S1-04 の `batch_delivery`（batchSize 2/3/5）を適用した再生で、
  **採用測位数が変換前から減らない**。
  > 「同数」ではなく「減らない」。`batch_delivery` は fix タイムスタンプを
  > 保存したまま到着だけまとめる変換なので、原理的には同数になるはずだが、
  > 700ms の重複除去に引っかかる境界があり得る。
  > **変換の前提条件として「バッチ内の fix タイムスタンプは 700ms 以上離す」ことを
  > テスト側で保証する。** これを満たしても減るなら実装のバグ。
- 不合格時: 止まる。本タスクの目的そのものが達成できていない。

**(b) 欠測で取りこぼしが増えない**
- 判定: `drop_burst` を入れても、採用測位数が「入力測位数 − 欠落数」を下回らない。
- 不合格時: 止まる。

**(c) 警告エピソードの変化**
- 目的: 測位が増えたことによる副作用の把握。**合否ではなく観測項目である。**
- 出典: `baseline_2026-08-06.json`（S1-14）。
- 判定: `replay_regression_test` のカテゴリ別エピソード数を**端末別に**記録し、
  ベースラインとの差分を残す。
- **不合格時の分岐**:
  - 増えた → 想定内。測位が 2.5 倍になるので当然。**進んでよい。**
  - 減った → **止まらない。原因を1つ特定して記録してから進む。**
    正当な理由の例:
    - 測位が密になり、以前は別々だったエピソードが1つに統合された
    - 以前は欠測で消えていた警告が、連続して1エピソードになった

    これらは**改善**である。説明がつかない減り方（特定カテゴリだけ半減など）だけ、
    差分探索（S1-13）で原因を作り込んでから判断する。
  > **Stage 1 の教訓**: 「減っていたら異常。理由を突き止めるまで進まない」と書いたが、
  > これは止まる基準としては強すぎる。総量は Release 2c まで含めて §2 の辞書式で評価する。

### リスク
- 測位が増えることで警告総量が増える可能性。
  → **これは想定内。** R2（前方外挿）と R3（水域データ）を直す前は、
  むしろ警告が増える方向に振れる。**Release 2a 単独では出さず、
  2c（S2 primary）まで含めて総量を評価する**——という判断もあり得る。
  → **判断: 2a は出す。** 測位が正しくなることのほうが優先で、
  総量は §2 の辞書式基準で 2c 完了時に評価する。ただしリリースノートに明記する。

## S2-02. まとめ配信で最新 fix を採る

### 目的
S2-01 で fix 時刻基準にしても、**同一ティックに複数 fix が来たとき
どれを採るか**が未定義。現行は「先着1件」＝**最も古いもの**を採っている。

### 変更
`geo_service.dart` のストリーム購読と `processPosition` の間に
**1ティックぶんのバッファ**を置く。

```dart
// lib/services/fix_batch_collector.dart
/// 同一イベントループのティックに届いた測位をまとめ、
/// fix タイムスタンプ順に並べて最新を選ぶ。
///
/// 過去状態を再計算しないので、窓内の最新だけを採る。
/// 途中の fix は FixEnvelope に supersededInBatch として記録する。
class FixBatchCollector {
  void add(Position position);
  /// マイクロタスク境界で確定した最新 fix。
  Stream<FixBatch> get batches;
}
```

### 設計判断: 全件処理か最新のみか
[RTA版] B-3 は2案を挙げていた。**最新のみを採る。**

理由:
- 安全評価は「いまどこにいるか」で回る。過去の中間点を追加処理しても、
  最終的な位置は同じで、処理時間だけ増える。
- 航跡記録の密度は落ちるが、**`track.csv` には棄却された fix も
  `FixEnvelope` として残る**ので、事後解析での情報損失は無い。
- 電池が測れない状況で処理回数を増やしたくない。

ただし **`supersededInBatch` の件数を必ず記録する**。
まとめ配信が常態化しているなら、それ自体が仮説αの証拠になる。

### テスト
- 3件を同一ティックで投入 → 最新1件が採用され、2件が `supersededInBatch`
- 順不同で投入 → fix 時刻で並べ替えてから最新を選ぶ
- 1件だけなら従来どおり

## S2-03. 安全評価と送信・描画の間引きを分離

### 目的
現在は `processPosition` の1つのゲートが、安全評価・記録・送信・描画のすべてを間引いている。
**間引くべきは送信と描画だけである。**

### 変更
`processPosition` の中を3層に分ける。

```text
1. 安全評価・記録   … 単調に新しい妥当 fix を原則すべて処理する
                      (S2-01 の positionMinimumFixIntervalMs のみ)
2. 位置共有         … 既存の SendPolicy（停止10s / 他艇なし5s / 近傍2s）
3. 地図描画         … 既存の MapRenderUpdatePolicy
```

既に `lib/services/send_policy.dart` と
`lib/services/map_render_update_policy.dart` があるので、
**「安全評価のゲート」だけを分離すればよい。**

### 不変条件（CLAUDE.md 不変条件1）
> リスク評価は送信間隔と独立に毎秒実行される。

**この不変条件は現在、実質的に破れている**（測位が 0.4Hz なので評価も 0.4Hz）。
本タスクで回復する。

### テスト
`test/services/safety_evaluation_liveness_test.dart`（既存）に追加:
- 送信間隔を 10 秒にしても、安全評価が fix ごとに走ること
- 描画抑制が安全評価に影響しないこと

### 受け入れ基準
- `position_processing_sample` の件数が、採用測位数と一致する。
- 送信件数は `SendPolicy` どおりで変わらない
  （`test/services/firebase_usage_budget_test.dart` が緑）。

# Release 2b — `distanceFilter` の是正【単独・未検証】

## S2-04. `distanceFilter` を `kCLDistanceFilterNone` へ

### なぜ単独リリースか
**この変更はオフラインで検証する手段が一切ない。** CoreLocation の挙動だからである。
2a や 2c と混ぜると、次に実機ログが取れたとき**どれが効いたのか永久に分からない。**

### 根拠（コード読解のみ。実機未検証）
`geolocator_apple 2.3.13`
`darwin/geolocator_apple/Sources/geolocator_apple/Utils/LocationDistanceMapper.m`:

```objc
+(CLLocationDistance)toCLLocationDistance:(NSNumber *)value {
    if (!value) return kCLDistanceFilterNone;
    return value > 0 ? value.doubleValue : kCLDistanceFilterNone;
}
```

`value` は `NSNumber *`。**`value > 0` はポインタ比較**で、非 nil なら常に真。
したがって `distanceFilter: 0` は `kCLDistanceFilterNone`（= -1.0）ではなく
**0.0 のまま** `locationManager.distanceFilter` へ渡る。

Apple は iOS 16.4 以降、継続配信に `kCLDistanceFilterNone` を要求している。

**傍証**: 同プラグインの一発取得の経路だけは `kCLDistanceFilterNone` を

## S2-05. `CapsuleSet`（進行方向カプセル）

### 目的
Stage 1 の `CircleSet` は停止・低速用。**航行中に等方で膨らませてはいけない。**

> 4m/s で 3 秒の欠測なら前方 12m。円で表すと**横にも 12m** 広がる。
> 川幅 40〜50m の水域では、それだけで岸区域へ食い込む。
> **§1-2 が示したのは「横方向の誤差は小さい」ことだった**（|cross| med 0.09〜0.20m）。
> 等方に膨らませると、直したはずの過剰警告を別経路で復活させる。

### 実装
`lib/services/bounded_position_set.dart` に追加。

```dart
/// 進行方向に伸びた領域。線分 + 半径で表す(カプセル)。
///
/// 前方成分   : 速度 × 経過時間 × 前方係数
/// 後方成分   : 減速し得る量(0 まで落ちるので前方より小さい)
/// 横方向成分 : 測位誤差 + 旋回率 × 経過時間による横変位のみ
class CapsuleSet implements BoundedPositionSet {
  final LatLng start;
  final LatLng end;
  final double radiusMeters;   // 横方向の半幅
  …
}
```

### 膨らませ方

```text
grownBy(dt, speed, heading, headingReliable):
  forward  = speed * dt * forwardGrowthFactor      // 加速し得るぶん
  backward = min(speed * dt, stoppingDistance(speed))  // 減速し得るぶん
  lateral  = maxTurnRateRadPerSec * dt * speed * dt / 2 + measurementSigma

  headingReliable == false のとき:
    → 方位が信頼できないので円へ縮退する(全方向に forward を取る)
      ただしこれは低速時に限られる。高速で方位不明は実質起きない。
```

### 設定値
`lib/config/risk_evaluator_config.dart`

```dart
/// 到達領域の前方成分の係数。1.0 で「現在速度を維持」。
/// 艇は数秒で大きく加速できないので、わずかな余裕だけ持たせる。
const reachableForwardGrowthFactor = 1.15;

/// 到達領域の横方向へ効く最大旋回率 [rad/s]。
/// 8+ の回頭でも 0.15 rad/s 程度。折り返しの回頭を含む値にする。
const reachableMaxTurnRateRadPerSecond = 0.2;
```

### テスト
- 停止時（speed=0）は円と一致する
- 4m/s・3秒で前方 ≈13.8m、**横 ≈ 測位誤差 + 数m**（12m にならないこと）
- `headingReliable = false` で円へ縮退する
- `boundingRadiusMeters` が実寸を下回らない（不変条件8）
- 平行移動・回転不変

## S2-06. `ConservativePositionEstimator`（S2 本体）

### 目的
**位置は生 fix、速度だけ平滑化、前方外挿しない、集合で不確かさを表す。**

### 新規ファイル
- `lib/services/conservative_position_estimator.dart`（純Dart）
- `test/services/conservative_position_estimator_test.dart`

### 設計

| 量 | 扱い | 理由 |
| --- | --- | --- |
| **位置（代表点）** | 生 fix をそのまま。外れ値ゲートのみ。**前方外挿しない** | 補正が害になっている軸（\|cross\| med 0.09〜0.20m で寄与ゼロ、\|along\| で最大 32m の害） |
| **速度・方位** | α-β の固定係数で平滑化 | `getStoppingDistance`・船体領域の低速拡張・TTE に必要。落とせない |
| **安全集合** | `CapsuleSet`。fix が古いほど単調に拡大 | 前進の可能性を点ではなく領域に残す |
| **不確かさ** | 実測に基づく。95%半径であることを明記 | 原則6 |

```dart
class ConservativeSolutionOutput {
  final LatLng representativePoint;   // 前へ飛ばさない。表示・Boat.lat/lng
  final double speedMetersPerSecond;  // α-β 平滑
  final double headingDegrees;
  final bool headingReliable;
  final BoundedPositionSet safetySet; // 安全判定はこちら
  final ProtectionBudget budget;
  final double uncertaintyMeters;     // 95%半径。budget.totalMeters と整合
}

class ConservativePositionEstimator {
  ConservativeSolutionOutput? update({required ConservativeFix fix});
  /// fix が来ない秒。代表点は動かさず、集合だけ広げる。
  ConservativeSolutionOutput? predict({required Duration elapsed});
}
```

### 外れ値ゲート（唯一の「補正」）

```dart
/// 前回の妥当位置から、物理的に到達不可能な距離へ飛んだ fix を棄却する。
/// Kalman の正規化 innovation と違い、**共分散に依存しない**。
/// 共分散が壊れていても機能することが、S1 と独立である条件。
bool _isPhysicallyReachable(LatLng from, LatLng to, Duration dt) {
  final maxSpeed = conservativeMaxBoatSpeedMetersPerSecond;  // 例: 8.0
  final allowance = conservativeOutlierAllowanceMeters;      // 例: 15.0
  return distance(from, to) <= maxSpeed * dt.inSeconds + allowance;
}
```

> **S1 と内部関数を共有しすぎない。** 座標変換などの純粋関数を除き、
> 別実装にする。共通原因で同時に壊れないため（Simplex の独立性）。

### 停止検出を推定器の速度状態から切り離す

**現在は「フィルタの速度状態が停止を判定し、そのフィルタの速度状態が壊れている」
という循環になっている。**

```dart
// lib/services/motion_state_detector.dart（新規・純Dart）
enum MotionState { moving, decelerating, stopped, restarting }

/// 停止・再発進を、推定器の内部状態を使わずに判定する。
///
/// 入力はすべて推定器の**外**から取る。単一閾値ではなく、
/// 弱い証拠を時間方向に蓄積する。
class MotionStateDetector {
  MotionState update({
    required double rawGnssSpeedMetersPerSecond,
    required double rawDisplacementMeters,   // 直近の生位置の変位
    required Duration since,
    required double? alongSpeedTrend,        // along 方向速度の連続低下
  });
}
```

- CUSUM / 逐次尤度比は**入れない**。多証拠の逐次蓄積で足りなければ Stage 3 で検討する。
- Core Motion も**入れない**（既存 IMU の available 率が 20〜44% しかない理由が先）。

> **停止判定の権限を限定する（最重要）。**
> 「停止した」は**位置モデルを切り替える根拠にはなるが、他艇音声を消す根拠にはしない。**
> これは Stage 1 の S1-01 regression の教訓そのものである。
> `MotionStateDetector` の出力を `SafetyOrchestrator` へ**直接渡さない**。
> 渡すのは `ConservativePositionEstimator` だけ。
> S1-06 の契約 `OTHER_BOAT_NOT_SILENCED_ON_UNKNOWN_SPEED` と
> `URGENT_NOT_SUPPRESSED_BY_LOW_PRIORITY` で機械検査する。

### 停止距離の扱い（設計上の分離）
現行 `velocityDecayTimeConstantSeconds = 8` は
「艇は数秒では止まらないので、速度を 0 にすると停止距離が 0 になって
警告レベルを不当に下げる」ための意図的設計である。

**この意図は保つが、実現方法を変える。**

```text
これまで: 速度状態を保持し続ける → 位置が前へ飛ぶ（害）
これから: 速度状態は素早く落とす → 停止距離は安全集合の前方成分で表す（害なし）
```

**停止距離の確保と、位置を前へ飛ばすことは別物である。**

## S2-07. `PositionIntegrityMonitor` と状態機械

### 目的
S1 が壊れていることを**独立に**検出する。
D/E ログが検出器の妥当性を先に証明している——
raw と filtered が 20〜32m 食い違った 372 秒は、S1 と S0 の分離を見るだけで全区間検出できる。

### 状態機械

```text
trusted
  → suspect      解分離・NIS・連続棄却のいずれかが悪化
suspect
  → trusted      回復条件を連続して満たす
  → ambiguous    どの解が正しいか判定できない
  → fallback     複数条件が一致、または上限超過
ambiguous
  → trusted / fallback（滞在上限あり）
fallback
  → reacquiring  新しい良好 fix が到着
reacquiring
  → trusted      規定時間、3解が整合
  → fallback     再び分離
```

**サンプル数ではなく経過時間**を条件にする（測位周期が変わっても意味が保たれる）。

### 解分離の判定
固定距離ではなく、運動量と各解の不確かさで正規化する。

```text
separationScore = distance(S1, referenceConsensus)
                / max(minimumScale,
                      protectionS1 + protectionConsensus + motionAllowance)
```

`referenceConsensus` の決め方:

| 状況 | 判断 |
| --- | --- |
| S0 と S2 が整合し、S1 だけ離れる | **S1 を suspect / fallback**（今回のデータはこれ） |
| S0 だけ離れる | 単発 GNSS 外れ値候補。S1/S2 を維持し保護半径を拡大 |
| 全解が離れる | 正解不明。最新の妥当 fix を基準に保護半径を最大化 |
| fix が古い | どの解も trusted にしない |

### `ambiguous` での和集合（**限定的に**）

**無条件の和集合は過剰警告製造機である。**

> S1 が 20〜32m ずれていた 372 秒に S0∪S1∪S2 を素直に取れば、
> 安全集合は約 30m 幅になる。川幅 40〜50m でそれは、岸とも他艇とも常時重なる。
> 原則4に正面から反する。

したがって:

```dart
/// 和集合に入れるのは plausible な仮説だけ。
///
/// 一定時間 separation 試験に落ち続けた解は「もっともらしくない」ので外す。
/// 壊れた解を抱き続けて領域を膨らませない。
bool _isPlausible(String solutionId) =>
    _consecutiveSeparationFailure[solutionId]! < ambiguousPlausibilityDuration;
```

- 和集合を使うのは**判定がつかない短時間だけ**。
- **`ambiguous` の滞在時間に上限**（`ambiguousMaxDuration`、既定 5秒）を置き、
  超えたら `fallback`（= S2 単独 + 拡大集合）へ落とす。

### `indeterminate`（集合が交差しない）
`predictedSet.intersect(measurementSet) == null` は
「予測か観測のどちらかが誤っている」ことを意味する。平均を取らない。

**D/E の 32m 発散区間で継続的に発火することを回帰試験で確認する。**

### fallback 時の安全動作
- **危険判定を止めない。**
- selected を S2 にする。
- 静的危険物には拡大した**絶対**保護集合。
- 他艇には通信遅延込みの到達可能領域（Stage 3 で本格化）。
- 画面に「測位精度低下・目視優先」を表示。**音は足さない。**

### テスト
- 人工的に S1 だけを 20m 偏らせる → 規定時間内に fallback
- raw に単発 50m 外れ値 → selected が同じ大きさで飛ばない
- 全解不一致 → trusted を維持しない
- **`ambiguous` に上限時間以上留まらない**
- **plausible でない解が和集合に入らない**（安全集合が 30m 幅にならない）
- 契約 `INTEGRITY_LEAVES_TRUSTED_ON_SEPARATION` / `INTEGRITY_NO_PREMATURE_TRUST` が緑

  **S2 と S0 は絶対に落とさない**（S2 が primary、S0 が独立監視の基準）。

  CI では**倍率だけ**を見る（絶対値を基準にしない）。

> **注意**: この予算は電池の証明ではない。計算量が電池の唯一の要因でもない
>（画面点灯・GNSS・無線が支配的）。**「明らかに重くしていない」ことの確認**にすぎず、
> 電池そのものは §4 の持ち越し表で実機再開時に確認する。

## S2-09. 不変条件7・8 の集合版への再定義

### 対象（CLAUDE.md）

> 7. `ThreatInfo.distanceMeters` は符号付き（危険区域の内部で負）。
>    0へ潰すと停止中の再接近検出が単調でなくなる
> 8. `ShipDomainService.boundingRadius` は領域の実寸を下回ってはならない。

### 集合化で変わること
- **距離が「点から区域まで」ではなく「集合から区域まで」になる。**
  → 定義: **集合の最近点**からの符号付き距離。
  集合が区域と交差していれば負（最深部までの距離）。
- **`boundingRadius` は集合の外接半径を含む。**
  → `max(shipDomainRadius, positionSetBoundingRadius)` ではなく、
  **両者の Minkowski 和の外接半径**。過小評価すると broad-phase で取りこぼす。

### 変更対象
- `lib/services/ship_domain_service.dart` — `effectiveExclusiveRadius()` に集合半径を合成
- `lib/services/collision_risk_evaluator_service.dart` — 距離計算を集合基準へ
- `lib/services/static_obstacle_index.dart` — broad-phase の到達半径

### テスト
`test/services/static_sweep_clearance_test.dart`（既存）に集合版を追加:
- 集合を大きくしたとき、拾う障害物が**減らない**（単調性）
- 符号付き距離が集合の拡大に対して単調に減少する
- `boundingRadius` が実寸を下回らない（乱数テスト 10000 ケース）

### 注意
**CLAUDE.md 本文の不変条件7・8 を更新する。** 実装だけ変えて記述を放置しない。

## S2-11. `SafetyContractMonitor` をランタイムへ（shadow）

### 目的
Stage 1 で作った契約を、**実機ログにも残す**。次に実機が使えたとき即座に解析できる。

### 実装
`use_navigator.dart` の1秒ウォッチドッグから `observe()` を呼び、
違反だけを診断イベントへ。

```text
safety_contract_violation { contractId, severity, detail }
```

- **違反しても挙動は変えない**（Stage 2 では観測のみ）。
- 違反が頻発するとログを圧迫するので、`contractId` ごとに
  **60秒に1件**へ間引き、件数は別途集計する。

### 受け入れ基準
- 目的: 契約が実装に対して機能していることの確認。
- 出典: 契約の定義そのもの（設計値）。
- 判定: 5ログの再生で、S2 primary にした後の違反件数を**契約 ID 別に**記録する。
- **不合格時の分岐**（違反が出たとき、以下を判定してから進む）:

| 判定 | 例 | 対応 |
| --- | --- | --- |
| **実装のバグ** | `PROTECTION_NEVER_SHRINKS_WHILE_STALE` が航行中に出る | 止まって直す |
| **契約の書き方が誤り** | `FIX_TIMESTAMP_MONOTONIC` が、実ログに本当に存在する端末時計の逆行で出る | 契約を直す（逆行の許容と回復を明文化）。止まらない |
| **ログ固有の異常** | C の `permission-denied` 直後だけ出る | 記録して進む。実機再開時の確認項目へ |

> 「違反が出るなら実装のバグである」と断定していたが、
> **契約側が誤っている可能性を排除していなかった。**
> 契約は今回はじめて書くもので、実データに当てて初めて妥当性が分かる。
