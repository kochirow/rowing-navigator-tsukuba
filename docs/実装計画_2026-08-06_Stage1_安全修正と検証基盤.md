
## 0. この段階の前提と方針

### 0-1. 実機テストは当面できない

これは検証設計を根本的に変える。**「実機で確かめる」を計画から外す。**

| 種別 | 扱い |
| --- | --- |
| **オフラインで証明できる** | 純Dartロジック、提示ポリシー、Fix Ingress のゲート挙動、推定器の相対誤差（D/Eペア）、警告総量 |
| **オフラインで証明できない** | CoreLocation の実配信頻度、電池、実可聴性、通信復帰、橋下・樹木下の測位 |

**証明できないものは「未検証のまま入れる」か「入れない」かを、変更ごとに明示する。**
黙って仮定に乗らない。未検証で入れるものは §5 の持ち越し表に必ず載せる。

### 0-2. Stage 1 のゴール

1. **今日直せる安全 regression を単独で出す**（S1-01。これだけが利用者へ届く）。
2. **残り全部を、実機なしで判定できる状態にする**（検証基盤）。

Stage 1 では **S1-01 以外は本番挙動を一切変えない。** 記録と計測だけを足す。

### 0-3. Stage 1 で判明済みの重要な前提（設計に影響する）

**`tool/replay_field_log.dart` は `track.csv` の `filtered_*` 列を読んでいる**
（`iLat = col('filtered_lat')`）。つまり現在の再生は
**「推定器の出力を入力として、提示パイプラインだけを再生する」**ものである。

→ **このままでは S1 と S2 を比較できない。** Stage 2 の中心的な判断
（どちらを primary にするか）を支える試験が存在しない。
S1-02 で **raw 駆動の経路**を新設する。これは Stage 1 の最重要タスクである。

既存資産（活かす）:

- `tool/replay_alerts.dart` の `replaySessionDirectory` と
  `test/replay/replay_regression_test.dart` + `baseline_2026-07-28.json`
  に、**セッション単位のベースライン比較の仕組みが既にある。** 拡張して使う。
- `test/replay/mooring_scenario.json` に他艇注入シナリオの形式がある。
- 実機ログはリポジトリに入れない（個人航跡）。テストはログ不在時 `markTestSkipped` する。
  この作法を新規テストでも守る。

## S1-01. 他艇無音化 regression の修正【唯一の出荷物】

### 目的
自艇が停止しているとき、接近してくる他艇の警告が**音を出さずに終わっていた**のを直す。
5端末合計で他艇警告の音は0回だった。

### 根拠（実機ログ A、経過52〜53分）
自艇停止、他艇が 20〜26m まで接近、DCPA 0〜1.7m、`actionDeadlineSec` が 3.7 秒まで短縮。
reasonCodes は
`continuous_domain_entry` / `gps_guard_entry` /
`PRESENTATION_UNCERTAINTY_ONLY_VISUAL` / `PRESENTATION_STABLE_STOP_SILENT`。
**すべて表示のみで終了。**

### 変更対象
`lib/services/safety_orchestrator.dart:488`

```dart
// 現在
if (_isUncertaintyOnlyEntry(candidate) && _isLowSpeed) {
  behavior = AlertBehavior.visualOnly;
  repeating = false;
  extraReasonCodes.add('PRESENTATION_UNCERTAINTY_ONLY_VISUAL');
}
```

同ファイルには意図的な除外が既にある:

```dart
// safety_orchestrator.dart:978 付近
/// 岸・橋など固定物のそばで休憩するときだけ反復音を抑える。
/// 自艇が停止していても他艇側が接近する可能性は残るため、他艇の
/// 緊急警告は安定停止による無音化の対象にしない。
static bool _canSuppressAtRest(AlertCandidate candidate) =>
    candidate.category != 'other_boat';
```

直下の桟橋分岐（:520）は正しく `_isOtherBoatAtRest` で**相手の速度**を見ている。
**488行だけがこの除外を通っていない。**

### 具体的変更

```dart
if (_isUncertaintyOnlyEntry(candidate) && _isLowSpeed) {
  // 固定物は自艇が低速なら止めてよい。
  // 他艇は「相手も止まっているとき」だけ。相手が動いていれば鳴らす。
  // 速度が取れない相手は静音しない(原則6)。
  final silenceable = _canSuppressAtRest(candidate) ||
      _isOtherBoatAtRest(candidate, otherBoatSpeedById);
  if (silenceable) {
    behavior = _quieter(behavior, AlertBehavior.visualOnly);
    repeating = false;
    extraReasonCodes.add('PRESENTATION_UNCERTAINTY_ONLY_VISUAL');
  }
}
```

**2点、意図的に変えている。**

1. `_canSuppressAtRest || _isOtherBoatAtRest` の形にする。
   他艇は相手の速度で判断し、速度不明なら `_isOtherBoatAtRest` が `false` を返すので鳴る。
2. **直接代入をやめて `_quieter()` にする。**
   現行コードはここだけ直接代入で、**規則の適用順に依存して結果が変わる**。
   （他の分岐は `_quieter` を使っている。Stage 3 の構造化まで、これ以上増やさない。）

`otherBoatSpeedById` は `_applyPresentation`（:429）の引数に既にある。追加の配線は不要。

### テスト
`test/services/safety_orchestrator_presentation_test.dart` に追加。
既存の `staticThreat()` ヘルパの隣に `boatThreat()` を用意する。

| # | 条件 | 期待 |
| --- | --- | --- |
| 1 | 自艇停止・**他艇 2.0m/s で接近**・`gps_guard_entry` 付き | **音が鳴る**（`audioDirective != null`） |
| 2 | 自艇停止・**他艇の速度が null**・`gps_guard_entry` 付き | **音が鳴る**（原則6） |
| 3 | 自艇停止・他艇も 0.1m/s・`gps_guard_entry` 付き | 表示のみ（従来どおり） |
| 4 | 自艇停止・**岸**・`gps_guard_entry` 付き | 表示のみ（**回帰させない**） |
| 5 | 自艇停止・他艇接近・`gps_guard_entry` **なし** | 音が鳴る（従来どおり） |

さらに `tool/replay_field_log.dart` で、
A のログ + 接近他艇シナリオ（`test/replay/approaching_boat_scenario.json` を新規作成）を再生し、
**`playsByCategory['other_boat'] > 0`** を確認する。

### 受け入れ基準
- 上記5件が緑。
- `test/replay/replay_regression_test.dart` の
  **`episodeCountOutsideMooring` の `shore` が増えていない**（過剰警告を戻していない）。
- `dart analyze lib test tool` が緑。

### リスクとロールバック

  → ただし**相手が動いているなら鳴るべき場面**であり、設計意図どおり。
  桟橋分岐（:520）が別途「双方停止なら静音」を担保している。
- ロールバック: 1コミットで戻せる。

### 出荷
**単独リリース。** Stage 1 の他タスクを待たない。

## S1-02. replay に raw 駆動（推定器を通す）経路を新設【基盤の要】

### 目的
現在の再生は `filtered_*` を入力にしているため、**推定器そのものを評価できない。**
Stage 2 の中心的判断（S1 と S2 のどちらを primary にするか）を支える試験を作る。

### 新規ファイル
`tool/replay_estimator.dart`（純ロジックは `lib/` 側へ置かない。ツール専用）

### 入力
`track.csv` の **`raw_lat` / `raw_lng` / `timestamp` / `gnss_accuracy_m` /
`raw_gnss_speed_mps` / `heading_deg` / `gnss_quality`**。
`filtered_*` は**比較対象としてのみ**読む（入力にしない）。

> `raw_lat` / `raw_lng` が空の行がある場合はスキップし、件数を報告する。
> 全5ログでは埋まっていることを確認済み。

### 交換可能な推定器インタフェース

```dart
/// 再生で差し替える位置解。lib/ の実装を包む薄いアダプタ。
abstract class ReplaySolution {
  String get id;                       // 's0_raw' / 's1_kalman' / 's2_conservative'
  /// 1測位ぶん進める。fixが無い秒は [fix] を null で呼ぶ。
  ReplaySolutionOutput step({
    required Duration elapsed,
    ReplayFix? fix,                    // null = この時刻に測位が無い
  });
}

class ReplaySolutionOutput {
  final LatLng representativePoint;    // 表示・Boat に渡す点
  final double speedMetersPerSecond;
  final double headingDegrees;
  final double uncertaintyMeters;
  final BoundedPositionSet? safetySet; // S1-10。無ければ円で代用
  final String dispositionName;
  final double? normalizedInnovationSquared;
}
```

初期実装は3つ:

- `S0RawSolution` — 最新の妥当 fix をそのまま返す。速度・方位は生値。
- `S1RecordedSolution` — **`filtered_*` を実機 S1 が実際に出した値として読む。**
  Stage 2 の比較ではこれを S1 の参照値にする。既存推定器を再実行して実機と
  一致させることは、この段階の目的にしない。
- `S2ConservativeSolution` — 生 fix だけから固定係数 alpha-beta で計算する。
  Stage 1 では shadow / replay 専用で、本番の選択解は変えない。

`S1KalmanSolution` は将来 S1 を改変して評価する Stage 3 の実験用に残すが、
今回の S1/S2 比較の基準には使わない。

### 出力
既存 `replay_field_log.dart` と同じ提示パイプラインへ流す。
`Boat` を作る箇所を `ReplaySolutionOutput` から組み立てるよう差し替える。

### CLI

```bash
flutter test tool/replay_estimator.dart \
  --dart-define=LOG_DIR=…/rowing_diagnostics_1785967606648 \
  --dart-define=SOLUTIONS=s0_raw,s1_kalman \
  --dart-define=OUT=/tmp/result.json
```

### テスト
`test/replay/replay_estimator_smoke_test.dart`
- 合成した直線・停止・旋回の track を作り、`S0RawSolution` が入力を素通しすることを確認。
- `S1RecordedSolution` が `filtered_*` をそのまま返すことを確認する。
- `S0RawSolution` / `S2ConservativeSolution` は、先頭60秒をウォームアップとして
  指標から除外する。起動時の状態は比較対象ではない。

### 受け入れ基準
- S1 は実機記録値を参照するため、推定器再実行の絶対一致を要求しない。
- S0/S2 の相対比較は、`|cross| med ≤ 0.5m`、停止時 along offset・10m超
  excursion の実測値との比較、絶対差 med ≤ 3m を確認する。
- ログが無い環境では skip し、CI を落とさない。

### リスク
- **最大のリスクは「再生が実機と違う」こと。** 受け入れ基準の1m一致がその歯止め。
- 実機は IMU 融合（`imuFusion.navigationFusionEnabled = true`）を使っているが、
  track.csv には `imu_confidence` / `imu_quality` しかない。
  **IMU 入力を完全再現できない可能性がある。**
  その場合は「IMU 無効時の推定器」を比較対象とし、**その旨を出力へ明記する**
  （実機の IMU available 率は 20〜44% なので、無効時が支配的な条件でもある）。

## S1-03. ペアログ突き合わせモードと指標

### 目的
D/E（同一 8+ 搭載、**真の位置差 1.5〜2m**）を使い、推定器変更の合否を機械判定する。

### CLI

```bash
flutter test tool/replay_estimator.dart \
  --dart-define=LOG_DIR=…/rowing_diagnostics_1785967606648 \
  --dart-define=PAIR_LOG_DIR=…/rowing_diagnostics_1785967619060 \
  --dart-define=PAIR_TRUE_SEPARATION_MIN_M=1.5 \
  --dart-define=PAIR_TRUE_SEPARATION_MAX_M=2.0 \
  --dart-define=SOLUTIONS=s0_raw,s1_kalman \
  --dart-define=OUT=/tmp/pair.json
```

### 対応付け
`timestamp` を UTC epoch にし、**0.6秒以内**で最近傍対応させる（1.0秒だと
移動による見かけの差が混入する。0.6秒は今回の分析で使った値）。

### 出力指標（すべて solution ごと）

```text
pairDistance:      med / p90 / p99 / max
excessOverTruth:   max(0, pairDistance - 1.75) の med / p99
countOver8m, countOver10m
excursions(>10m):  回数 / 合計秒数 / 最大値
alongCross:        |along| med, |cross| med, |cross| p99, cross>5m の割合
stoppedAlongOffset: 自艇<0.4m/s のときの along オフセット med / p99
```

### 基準値（2026-08-06 実測。回帰の起点）

| 指標 | raw | S1（現行 Kalman） |
| --- | --- | --- |
| pairDistance med（停止） | 1.7m | 3.6m |
| pairDistance med（航行） | 2.7m | 2.1m |
| pairDistance p99（航行） | — | **19.2m** |
| max | 10.9 / 5.7m | **32m** |
| 8m 超 | **6 / 677** | **197 / 677** |
| 10m 超 | **1 / 677** | **176 / 677** |
| excursion(>10m) | 0 | **5回 / 372秒** |
| \|cross\| med（D / E） | — | **0.20m / 0.09m** |
| stoppedAlongOffset med（D） | — | **5.56m**（p99 25.24m） |

これを `test/replay/pair_baseline_2026-08-06.json` として固定する。

### テスト
`test/replay/pair_regression_test.dart`
- ログがあれば実行、無ければ skip。
- **合成ペア**（既知の真値で作った2系列）での単体テストも用意し、
  ログ不在の CI でも指標計算そのものは検証する。

### 受け入れ基準
- 上表の数値が再現する（分析時の計算と一致）。
- 合成ペアで along/cross 分解が期待値と一致（回転・平行移動に対する不変性を含む）。

## S1-04. 障害注入変換とレシピ/seed

### 目的
実機なしで、欠測・遅延・まとめ配信・外れ値・通信劣化を再現する。

### 新規ファイル
`tool/replay_fault_injection.dart`

### 変換カタログ

| ID | 変換 | パラメータ例 | 狙い |
| --- | --- | --- | --- |
| `drop_periodic` | N件ごとに欠落 | 2, 3, 5 | 0.5Hz / 0.33Hz 相当 |
| `drop_burst` | 連続欠落 | 3, 6, 10秒 | 橋下・一時停止 |
| `delivery_delay` | 到着だけ遅延 | 0.3〜3秒 | fix時刻と到着時刻の分離 |
| `batch_delivery` | 複数fixを同時到着 | 2, 3, 5件 | **900msゲートの検証（最重要）** |
| `duplicate_fix` | 同一fixを再送 | 1〜3回 | 重複耐性 |
| `out_of_order` | 隣接fixを逆順化 | 2〜5件 | 時刻逆行耐性 |
| `stale_replay` | 古いfixを後着 | 2〜10秒遅れ | 過去位置への巻き戻り防止 |
| `accuracy_scale` | accuracyだけ変更 | 0.5, 2, 4倍 | 自己申告誤差への依存検査 |
| `residual_block` | D/E残差ブロックを加算 | 10〜60秒 | 時間相関を保った誤差 |
| `bias_ramp` | 偏りを徐々に増加 | 0→5/10/20m | 遅い発散の検出 |
| `heading_loss` | headingを欠損 | 区間指定 | 到達領域の保守性 |
| `remote_delay` | 他艇だけ遅延 | 1〜30秒 | 位置共有の鮮度低下 |
| `remote_speed_null` | 他艇速度欠損 | 区間指定 | 欠損時に静音しないこと |

### 設計上の要点
- **元ログは書き換えない。** 変換は読み出し時に適用する。
- **レシピ JSON + seed を保存**し、同一条件を完全再現できるようにする。

```json
{
  "recipeVersion": 1,
  "seed": 20260806,
  "logDir": "rowing_diagnostics_1785967606648",
  "transforms": [
    {"id": "batch_delivery", "batchSize": 3, "startSec": 600, "endSec": 1200},
    {"id": "drop_burst", "durationSec": 6, "atSec": [900, 1500]}
  ]
}
```

- **ブロック・ブートストラップ**: GNSS 誤差は時間相関を持つ。点単位でランダム化しない。
  `residual_block` は D/E の残差を **10〜60秒のブロック**で再標本化する。
- **セッション分離**: 校正用・選択用・評価用を**セッション単位**で分ける。
  D/E の片側を調整に使ったら、同時刻のもう片側を評価に使わない。
  これはコードで強制する（同一 `sessionId` の相方を評価集合から除く）。
