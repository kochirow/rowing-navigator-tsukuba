# 実装計画：iOSの速度・方位の検証と、監視端末への警告通知（2026-10-30）

作成：2026-10-30
根拠：実機ログ分析（`../実機テストログデータ/2026_10/2026-10-27_28_実機ログ分析と提案.md` 第6版）と、そのCodexレビュー
状態：2026-10-30 に実装した(9章)。7.2の実機確認は未実施。

## 1. 目的

次の2つを実装する。

1. **自艇の速度・方位の検証**：iOSが「方位を出せない状態」（方位精度±180°・速度精度±3.75m/s）を返している間、その値を自艇の速度・方位として使わない。代わりに、位置の変化から求めた値を使う。警告・表示・共有・低速時の消音のすべてが、実際の動きに沿うようにする。
2. **監視端末への警告通知**：監視モードで、航行中の艇の漕手に警告の音が鳴ったら、監視端末をバイブさせる。あわせて、地図と艇一覧でその艇を目立たせる。

地図の座標の修正（中心線・西端の折り返し・突堤・杭1）は、この計画には含めない（6章）。

## 2. 背景（分析で確定したこと）

### 2.1 何が起きていたか

- iOSは漕いでいる最中にも、方位精度±180°・速度精度±3.75m/sの状態に入る。7〜10月の機種の分かっている6機種、iOS 18.7〜27.0.1で起きている。
- 10/27・10/28の3台では、漕いでいた時間の37〜52%がこの状態だった。この間、iOSの速度は実際の約1/4（最大1.8m/s）で、方位は直前の値で止まっていた。
- 同じ艇に載せた2台で、この状態に入る時刻が別々だった。原因は空や水面ではなく、端末ごとのiOSの処理にある。

### 2.2 アプリ側で確定した原因

**(a) 採用中の推定に、精度の情報が届いていない。**
警告・表示・共有に使っているのは保守側の推定（`PrimarySolution.conservative`、`navigator_config.dart`）である。その入力 `ConservativeFix`（`conservative_position_estimator.dart`）は、速度と方位の値を受け取るが、精度は受け取らない。そのため、方位精度180°の方位もそのまま使っていた。

一方でこの推定には、速度・方位が無い（null）ときに、1秒間の位置の変化から求め直す処理がすでにある。

**(b) 加速度センサー側の推定も、同じ誤りを共有している。**
`RowingMotionFusion.observeGnss`（`rowing_motion_fusion.dart`）は、iOSの速度を基準速度として取り込み、加速度から得た変動を加えている。速度精度は受け取らない。信頼度はストロークの検出の質だけで決まる。

10/27 6:36:16付近の記録では、実際は約2.6m/sだったのに、次の値が出ていた。

- 推定速度：0.23m/s
- 精度：±0.54m/s
- 品質：`good`
- 信頼度：0.91

**(c) 測位品質の `good` は、位置の品質だけを表している。**
方位精度180°の間も、3台とも `gnss_quality` は `good` だった。

**(d) 診断ログに、iOSの生の方位が残っていない。**
`track.csv` の `heading_deg` は、アプリが採用した方位である。ただし、iOSの方位が負（無効）なら保守側の推定は位置の変化から方位を求め直すので、実際の進行方向に沿うはずである。それでも方位が止まっていたことから、iOSは止まった正の方位を返していたと考えられる。生の値を記録して確定させる。

### 2.3 置き換えに使う値の精度（実測）

iOSの速度・方位が正常な区間（方位精度90°未満・速度精度3.0m/s未満、速度1m/s以上、3台・5,542点）を基準にした。位置の変化から求めた速度と方位を、今の保守側の推定と同じ平滑化（前回0.7・今回0.3）で比べた結果は次のとおり。

| 位置の変化を取る間隔 | 速度の偏り | 速度の誤差 中央値 / 90% / 99% | 方位の誤差 中央値 / 90% / 99% |
| --- | --- | --- | --- |
| 1秒（今の仕組み） | −0.05m/s | 0.15 / 0.36 / 0.60 m/s | 2° / 8° / 38° |
| 3秒 | −0.09m/s | 0.22 / 0.51 / 0.86 m/s | 1° / 5° / 31° |
| 5秒 | −0.10m/s | 0.22 / 0.52 / 1.03 m/s | 1° / 4° / 28° |

今の仕組み（1秒）のままで、速度の誤差の9割が0.36m/s以内、方位の誤差の9割が8°以内に収まる。平滑化も今と同じなので、加速や旋回への追従が今より遅れることはない。5〜10秒の間隔は、分析には有用だが実時間の警告には使わない。

正常なときと問題の状態とで、精度の値は重ならない（4機種の漕いでいる区間）。

| | 速度精度 | 方位精度 |
| --- | --- | --- |
| 正常 | 99%が2.55m/s以下 | 99%が119°以下 |
| 問題の状態 | 99%が3.72m/s以上 | 常に180° |

## 3. 要件

### 3.1 速度・方位の検証（R1〜R6）

**R1 判定**
iOSの1回の測位ごとに、速度と方位を別々に「使える／使えない」と判定する。

- 速度が使えない：速度精度が3.0m/s以上。
- 方位が使えない：方位精度が179°以上、または方位の値が負。
- 精度が0以下（Androidで精度を出さない端末など）のときは、「精度不明」として今までどおり値を使う。Androidの実機ログはまだ分析していないため、この計画では挙動を変えない。

しきい値は `lib/config/` に置き、2.3の実測を根拠として書く。

**R2 採用中の推定への反映**
保守側の推定 `ConservativeFix` に、速度精度と方位精度を渡す項目を追加する。R1で使えないと判定した速度・方位は、推定の中で null として扱い、既存の「位置の変化から求め直す」処理へ回す。

**R3 方位の信頼度**
保守側の推定の `headingReliable` を、次のどちらかのときは false にする。

- 方位が「使える」iOSの値から来ていない。
- 位置の変化から求めた方位を、直近の一定時間（例えば3秒）更新できていない（1秒の移動が1.5m未満の状態が続く）。

`headingReliable` が false の間は、既存の「方位が不確かなときの横方向の拡張」が働く。

**R4 加速度センサー側の基準速度**
`observeGnss` に渡す基準速度と方位も、R1で判定した値を使う。

- iOSの値が使えない間は、保守側の推定が位置の変化から求めた速度・方位を渡し、速度精度に代わる値（例えば1.0m/s）を付ける。
- 基準がiOSの値でない間は、融合結果の信頼度の上限を下げる。これで、間違った基準を高い信頼度で使い続けないようにする。

**R5 影響を受ける判定の確認**
次の各所が、選ばれた推定の速度・方位を使っていることをテストで固定する。

- 低速時の消音（`lowSpeedMutedCategories`）
- 安定停止、桟橋での消音
- 逆走判定
- 静的区域・他艇の到達予測
- 位置共有の送信値と送信間隔

**R6 診断ログ**
- `track.csv` に、iOSの生の値（`raw_course_deg`）と、採用した速度・方位の出どころ（`speed_source` / `heading_source`：`gnss` / `position` / `held`）の列を足す。
- 判定が切り替わった瞬間に `gnss_motion_validity_changed` イベントを残す（速度・方位それぞれ）。
- ハートビートに、直近の判定結果を入れる。
- 既存の `gnss_quality` の意味（位置の品質）は変えない。

### 3.2 監視端末への警告通知（R7〜R12）

**R7 入力**
監視中（`NavMode.observer` かつ `isWatching`）に受信している各艇の最新メッセージの `presentationState`（`w`）を使う（`receivedPracticeLogMessages`）。

- `w` は「帯（0=表示のみ / 1=単発の読み上げ / 2=連続音）＋種類（他艇・橋・橋脚・岸・中州・流木・杭・カーブ・逆走・その他・system fault）」である。
- 帯1・2を「漕手に音が鳴った」とみなす。帯0とsystem faultは通知しない。
- 一定時間（例えば10秒）より古いメッセージは使わない。

**R8 バイブの条件**（2026-10-30 利用者決定：音が鳴った警告すべて）
次のときに1回バイブさせる。

- ある艇の `w` が、「音なし（null・帯0・古い）」から「音あり（帯1・2）」に変わったとき。
- 音ありのまま、種類が変わったとき。

同じ艇・同じ種類の音ありが続く間は、繰り返さない。逆走・カーブは5秒あけて2回の読み上げを1組として繰り返すため、音なしが一定時間（例えば10秒）続いてから、次の音ありで再び鳴らす。複数の艇が同時に変わっても、バイブは最短2秒に1回にまとめる。

**R9 バイブの強さ**
- 連続音（帯2）：長めの振動を2回。
- 単発（帯1）：1回。

`HapticFeedback.vibrate()` を使い、失敗しても例外を投げない（`TactileFeedback` と同じ扱い）。

**R10 画面表示中だけ**（2026-10-30 利用者決定）
アプリが前面（`AppLifecycleState.resumed`）にある間だけ鳴らす。画面が消えている間の変化は、復帰したときにまとめて鳴らさない（古い通知を鳴らしても役に立たないため）。画面OFFで鳴らすローカル通知は次の段階の検討事項とし、実機でバイブが届くかを確かめてから決める。

**R11 地図と艇一覧の表示**（2026-10-30 利用者決定：バイブと監視地図の表示）
音ありの艇を、次の2か所で目立たせる。

- 監視画面の地図の艇印：例えば赤い外枠と種類の短い文字（「他艇」「岸」「杭」「逆走」など）。
- 艇一覧：「警告：他艇に注意（連続音）」のような行と、継続時間。

これは表示専用で、監視端末自身の対向・逆走の判定（`ObserverPriorityBanner`）とは別物として区別がつくようにする。艇側が `w` を送らない古い版のときは、「警告状態なし」を「安全」と表示しない。

**R12 オン・オフ**
監視のメニューに「警告をバイブで知らせる」のオン・オフを置く。既定はオン。端末内に保存する。音は今までどおり既定で鳴らさない（DESIGN_PRINCIPLES 3.5-3）。

**R13 記録**
監視ログ（練習一括ログ）に、通知した時刻・艇・種類を `observer_warning_notified` として残す。後から過剰でないかを確かめるためである。

### 3.3 変えないこと

- 衝突判定・提示ポリシーの設定値（鳴り始めの13秒・10秒、すれ違い間隔、低速消音の1.67m/s など）は変えない。今回は入力を正すだけにする。
- 逆走判定の仕組み（6秒の確定、鳴り直しの間隔）は変えない。方位が正常な区間では、誤表示が3人とも6秒以下だった。
- 用途指定（`ActivityType.fitness`）は変えない。比較実験（7.2）の後に決める。
- 他艇の警告状態は、航行中の端末の衝突評価・地図描画には今までどおり渡さない。

## 4. 規範との関係

- **不変条件12**（受信した他艇の警告状態は記録専用）は、利用者の決定（2026-10-30）により次のように改める。

  > 受信した他艇の警告状態（`w`/`m`/`a`）は、記録と、**監視端末での通知（バイブ）・表示**にだけ使う。航行中の端末の地図描画・衝突評価には渡さない。`Boat` には持たせない。

  理由（他艇の警告が自艇の判断を汚染しない）は、航行中の端末について変わらない。監視端末は衝突評価をしないので、この理由に当たらない。CLAUDE.md の不変条件12と、DESIGN_PRINCIPLES 3.5-3 を合わせて直す。

- **原則4（過剰警告）**：R8の繰り返し抑制と2秒のまとめで、監視者への通知が形骸化しないようにする。13の記録で、実練習での通知回数を確かめる。
- **原則6（データ欠損は安全の根拠にならない）**：R1の判定で使えない速度・方位は、位置の変化から求めた値に置き換える。値を捨てて0や「止まっている」として扱わない。
- **DESIGN_PRINCIPLES 1.2b の記述**：「開水面ではレーンの逆走判定は誤発報しない」とある。しかし今回のログでは、方位が止まったことによる誤表示と、西端の折り返し・中心線付近の誤報が実測された。事実の訂正として、測定結果を1.2bへ追記する（判定を止めるかどうかの判断は、地図の修正の段階で利用者と決める）。
- **ドキュメントとコードの食い違い**：CLAUDE.md「衝突警告の仕組み」2は、「RobustPositionEstimator が位置・速度・方位を推定」としている。しかし実際に安全判定に使っているのは、保守側の推定（`ConservativePositionEstimator`）である。中核の表にも保守側の推定が無い。今回あわせて直す。

| R2 | `ConservativeFix` に速度精度・方位精度を足した。使えない速度は1秒間の位置の変化(測位時刻の差で割る)、使えない方位は1.5m以上の移動の向きで求め直す。平滑化は今と同じ(前回0.7・今回0.3)。ただし方位が古い(3秒更新なし・初回)ときは平滑化せず、その値をそのまま採る |
| R3 | `headingReliable` は、使えるGNSSの方位か位置の変化で直近3秒以内に方位を更新できているときだけ true。この値が効くのは、測位が途切れた間の到達範囲(`predict` の集合)である。船体領域の横方向の拡張(`ShipDomainService.headingIsReliable`)は従来どおり艇の速度で決まり、速度が正しくなったことで実際の動きに沿う |
| R4 | 加速度側の基準は `FusionBase.select`(`motion_fusion_base.dart`)。GNSSの速度が使えない間は位置由来の速度に速度精度1.0m/sを付けて渡し、融合の信頼度を0.6まで(`imuFusionNonGnssBaseConfidenceCap`。安全経路へ使う0.68・品質good の0.72より下)に抑える。比較用のKalman(S1)の入力は変えていない(精度で重み付けしているため) |
| R5 | 低速時の消音・安定停止・逆走・到達予測・共有は、すべて `buildMyBoat` が作る自艇(保守側の推定の速度・方位)を使っていることを確認した。この経路は変えていない。実データでの効果は9.2で確かめた |
| R6 | `track.csv` の末尾に `raw_course_deg`・`speed_source`・`heading_source`。判定の切り替わりで `gnss_motion_validity_changed`(field=speed/heading)。ハートビートに `gnssMotion.*`・`speedSource`・`headingSource` |
| R7〜R10・R13 | `observer_warning_notifier.dart`(純Dart)と `use_observer_warning_alerts.dart`。通知は監視ログに `observer_warning_notified`(艇・種類・鳴り方・バイブしたか)。バイブをオフにしても表示と記録は続く |
| R11 | 地図の札を赤地・太い白枠にし、種類を添える(「他艇｜4+ 後藤」)。艇一覧の行に「警告：他艇に注意(連続音) 12秒」 |
| R12 | オン・オフは**艇一覧の上**に置いた(計画では監視のメニュー)。`home_map_screen.dart` の行数予算(上限2255行)にメニュー項目の配線が収まらず、艇一覧は監視中だけ出る画面なので、監視の操作として同じ役割を果たせるため |
