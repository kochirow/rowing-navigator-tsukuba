## S1 — 安全経路の修復(W1〜W6)

安全機能そのものが壊れている項目。ここを最優先で終わらせる。

### W1. 音声プレイヤー操作の完全直列化とタイムアウト

**対象**: `lib/hooks/use_alert.dart`

**目的**: 1つのプラットフォーム呼び出しが返らなくても、警告音システム全体が死なないようにする。

**現状の問題**

1. `runPlaybackWatchdogTick`(`:336` 付近)の `unawaited(Future<void>(() async { ... }))` が
   `enqueueCommand` を通さずに `player.pause()` / `player.resume()` / `player.stop()` /
   `player.getCurrentPosition()` を直接呼んでいる。
   同ファイル `:518-520` に「**直接呼ばないこと。必ず enqueueCommand 経由で1つずつ実行する**」と
   明記されているルールの唯一の例外になっている
2. すべての `await player.*` にタイムアウトが無い
3. `enqueueCommand`(`:657`)は **待機中の要求を無条件に最新1件へ置き換える**。
   復旧要求をそのままこのキューへ流すと、**待機中の `stop` を復旧要求が追い出して
   音が鳴り止まなくなる**新しい経路を作ってしまう

**変更内容**

- `_AlertCommand` に種別 `_AlertCommandKind { play, stop, recover }` を持たせる
- `enqueueCommand` の置換ポリシーを種別ごとに変える
  - `play` 待機中に新しい `play` → 置換(現行どおり)
  - **`stop` 待機中に何かが来ても `stop` は捨てない**。`stop` は必ず実行してから次へ
  - `recover` はキューが空のときだけ積む。待機中の要求があるなら捨てる
- 復旧処理を `enqueueCommand(..., kind: recover)` 経由に移す
- プラットフォーム呼び出しラッパを1本作る

  ```dart
  Future<T> _platformCall<T>(String op, Future<T> Function() run) async {
    try {
      return await run().timeout(alertPlatformCallTimeout);
    } on TimeoutException {
      emitDiagnostic('audio_platform_call_timeout', {'operation': op});
      rethrow;
    }
  }
  ```
  `stop` / `resume` / `pause` / `setSource` / `setReleaseMode` / `setVolume` /
  `setAudioContext` / `getCurrentPosition` / `seek` をすべてこれで包む
- **タイムアウトした呼び出しは中止されない**(Dart の `.timeout()` は待つ側だけを打ち切る)。
  したがって、**タイムアウト後にそのプレイヤーへ触り続けてはいけない**。
  連続 `alertPlayerRecreateFailureThreshold` 回で `AudioPlayer` を
  **捨てて作り直す**(古いインスタンスは `unawaited(old.dispose())` で放流し、
  以降の操作は新インスタンスへ向ける)。プレイヤーは差し替え可能な保持
  (`useRef<AudioPlayer>`)に変える
- 作り直しも失敗したら `error.value` を設定 → 既存の `audio_unavailable` system fault が立つ
  (**表示のみ。読み上げは増やさない**)

**新規設定**(`lib/config/warning_audio_config.dart`)

```dart
/// プラットフォーム音声呼び出し1回の上限。
/// 実機ログ(2026-07-28)では stop → setSource の間で無限待ちが発生した。
/// 読み上げは1秒前後なので、3秒を超える応答は異常である。
const alertPlatformCallTimeout = Duration(seconds: 3);

/// この回数だけ連続でタイムアウトしたらプレイヤーを作り直す。
const alertPlayerRecreateFailureThreshold = 2;
```

**やってはいけないこと**

- タイムアウトを理由に警告候補・表示・`runMode` を落とすこと(原則1・不変条件3)
- `NavigationWarningService` に既定音フォールバックを足すこと(音の有無は提示ポリシーが決める)

**受け入れ条件**

- `player.stop()` が永久に返らないフェイクで、3秒後に `audio_platform_call_timeout` が出る
- 次の再生要求が実行される / `alert.stop()` が有限時間で返る
- 待機中の `stop` が後続の `play` / `recover` に追い出されない
- タイムアウト後、古いプレイヤーへの操作が新しい状態を書き換えない

**テスト**: `test/hooks/use_alert_command_queue_test.dart`(新規)。
`AudioPlayer` をインタフェース越しに差し替えられるようにし、純ロジックとして検証する。

### W2. ループ再生の「完了通知」を故障として扱わない

**対象**: `lib/hooks/use_alert.dart`、`lib/services/audio_playback_progress_watchdog.dart`

**目的**: 最も切迫した警告である連続音を、実際に連続させる。復旧処理の発動回数を桁で減らす。

#### ループの管理者を1つに決める(必須)

**ネイティブの `ReleaseMode.loop` とアプリ側の自前ループを二重に動かさないこと。**
本作業では **アプリ側を唯一の管理者**とする。

| 項目 | 決定 |
| --- | --- |
| 連続音の `ReleaseMode` | **`stop`**(`loop` は使わない) |
| ループの継続 | `onPlayerComplete` を受けて **アプリが** `enqueueCommand(kind: recover)` で `seek(0)` + `resume()` |
| 理由 | iOS で `ReleaseMode.loop` が1周ごとに `completed` を出しており、ネイティブのループ挙動が信用できない。管理者を1つにすれば、状態遷移が一意になる |

語句末尾 0.15 秒の無音がループ間隔になる設計は維持する(CLAUDE.md)。

#### 故障の定義を1つに絞る

「`PlayerState.playing` のまま再生位置が `stallThreshold` を超えて進まない」場合のみ故障。
**`completed` は故障ではない。**

- `audio_playback_stalled` は本当の停滞のときだけ出す
- 自前ループの1周は `audio_loop_restarted` として**別イベント**にし、
  診断が正常動作で埋まらないようにする

**受け入れ条件**

- 0.89秒アセットの連続音再生を模したテストで、`audio_playback_stalled` が0件、
  `audio_loop_restarted` が周期ぶんだけ出る
- `playing` のまま位置が進まないケースでは従来どおり復旧が走る
- `setReleaseMode(ReleaseMode.loop)` の呼び出しがコードから消えている

**テスト**: `test/services/audio_playback_progress_watchdog_test.dart` を更新。

### W3. 航行終了を音声処理から独立させる

**対象**: `lib/hooks/use_navigator.dart`(`stopNavigation` : 2621〜)

**目的**: 何が詰まっても航行終了は必ず完了し、練習ログが必ず保存される状態にする。

#### 設計上の落とし穴(必ず読むこと)

**Dart の `.timeout()` は待つ側を打ち切るだけで、元の非同期処理は動き続ける。**
全体 `.timeout(15秒)` で画面だけ観測モードへ戻すと、裏で古い終了処理が生き残り、
あとから次のいずれかを起こしうる。

- 新しい航行の状態を古い終了処理が消す
- 完了済みセッションを未完了状態で上書きする
- 音声・Wakelock を後から勝手に止める

したがって **タイムアウトだけでは不十分で、世代番号による無効化が要る。**

#### 変更内容

1. **終了処理専用の世代番号 `stopGeneration` を持つ。**
   `stopNavigation` の冒頭で `+1` し、各工程は**自分の世代が最新のときだけ**
   状態を書き換える。世代が変わっていたら、完了しても**何も書かずに黙って終わる**
2. **終了開始の痕跡を最初に残す。**

   ```dart
   queueSessionWrite(buildSessionSnapshot(isComplete: false));
   await attempt('Stop-start checkpoint', waitForSessionWrites,
       timeout: navigationStopCheckpointTimeout);
   ```
   `queueSessionWrite` は `void` だが、**既存の `waitForSessionWrites()`
   (`use_navigator.dart:1180`)が完了待ちに使える。**新しいAPIは要らない
3. **各工程に「残り時間」を渡す。** 全体を `.timeout()` で包むのではなく、
   開始時刻からの経過を見て `min(工程既定, 残り時間)` をその工程のタイムアウトにする

   ```dart
   Future<void> attempt(String label, Future<void> Function() operation,
       {Duration? timeout}) async {
     final myGeneration = stopGeneration.value;
     final remaining = navigationStopTotalBudget - stopWatch.elapsed;
     if (remaining <= Duration.zero) {
       appendRuntimeDiagnostic('navigation_stop_step_skipped', {'step': label});
       return;
     }
     try {
       await operation().timeout(
         timeout == null ? remaining : (timeout < remaining ? timeout : remaining),
       );
     } catch (error) {
       appendRuntimeDiagnostic('navigation_stop_step_failed',
           {'step': label, 'errorType': error.runtimeType.toString()});
     }
     if (myGeneration != stopGeneration.value) return; // 世代が変わったら何も書かない
   }
   ```
4. **UI状態の後片付けは1回だけ実行する。**
   `mode = observer` / `isTransitioning = false` / `navigationStopInProgress = false` を
   `finally` で行い、**世代が最新のときだけ**書く
5. **順序を変える。** 音声停止(`alert.stop`)は**最終セッション保存より後**に回す。
   保存・位置共有停止・画面復帰が音声に一切依存しないこと。
   音声停止は `unawaited` + タイムアウトでよい

**新規設定**(`lib/config/navigator_config.dart`)

```dart
/// 航行終了の「開始チェックポイント保存」の上限。
/// これだけは必ず待つ。以降どこで詰まっても記録が残る。
const navigationStopCheckpointTimeout = Duration(seconds: 5);

/// 航行終了処理1工程あたりの既定上限。
const navigationStopStepTimeout = Duration(seconds: 5);

/// 航行終了処理全体の予算。超過した工程は実行せずに飛ばす。
const navigationStopTotalBudget = Duration(seconds: 15);
```

**受け入れ条件**

- `alert.stop` が永久に返らないフェイクでも、`stopNavigation` が15秒以内に返る
- その場合でもセッションが保存され、`mode` が `observer` に戻る
- **タイムアウトした工程が後から完了しても、新しい状態を書き換えない**
- `navigation_stop_step_failed` / `navigation_stop_step_skipped` に工程名が残る

## S4 — データ・診断の整理(W17, W18, W21)

### ⚠ この段階の最重要事項 — プロファイル SHA と Firestore Rules

**`assets/data/sakuragawa_obstacles.json` を1バイトでも変えると、
ファイル全体の SHA-256 が変わる。** そして SHA は**2か所**に書かれている。

| 場所 | 内容 | `tool/update_hazard_profile_hash.sh` が更新するか |
| --- | --- | --- |
| `lib/config/hazard_profile_config.dart:6` | `currentHazardProfileSha256` | **する** |
| `firestore.rules:256` | `data.baseProfileSha256 == '03b7dcb...'` | **しない** |
| `firestore.rules:248` | `data.baseProfileVersion == 4` | **しない** |

SHA が食い違うと次が起きる:

- アプリは新しい SHA で共有安全設定を書こうとする → **Rules が拒否する**
- 既に公開済みの共有設定は古い SHA を持つ → `mayApplyCalibrations` が false になり、
  **現地で合わせた校正値が全部落ちる**

#### 対策 — S4 では JSON を一切変更しない

**W17・W21 は JSON を変更せずに実装する。** 具体的には:

| 作業 | 従来案 | **改めた案** |
| --- | --- | --- |
| W17(水域外の削除) | JSON から `operationalCoveragePolygon` と `practiceArea` を削除 | **コードから読むのをやめるだけ。JSON のキーはそのまま残す**(死んだデータになるが SHA は変わらない) |
| W21(陸上消音区域) | `sakuragawa_obstacles.json` に `landSilenceZones` を追加 | **別ファイル `assets/data/sakuragawa_land_silence_zones.json` を新設**。危険区域プロファイルの SHA 対象外にする |

これで **S4 では SHA が一切変わらず、Rules の更新も再公開も不要**になる。

死んだキーの削除は、**どうせ SHA と version が変わる W22(座標更新)と同時に1回で行う。**
`sakuragawa_obstacles.json` の該当キーには、削除予定である旨をコメント相当の
`"_deprecated"` フィールドで示さず、**W22 のチェックリストに書いて忘れないようにする**
(JSON にフィールドを足すと SHA が変わるため)。

#### あわせて実施 — ハッシュ更新スクリプトの拡張

`tool/update_hazard_profile_hash.sh` を拡張し、**`firestore.rules` の SHA と version も
同時に更新・検証する**。これは JSON を変えないので S4 で安全に実施できる。

- `--check` で Dart 側と Rules 側の**両方**を検証する
- `.github/workflows/ci.yml` の検証にも Rules 側を含める
- スクリプト末尾に
  「**Rules を変更したら `firebase deploy --only firestore:rules` が必要**」
  と表示する。**デプロイ自体はスクリプトにやらせない**(利用者の操作)

**変更内容**

- `isAshore` **または** `reason` が前回と変わったときだけ記録する
- 距離の推移は `diagnostic_heartbeat`(30秒周期)に
  `ashoreLandSideDistanceMeters` と `ashoreReason` を1項目ずつ足す

**期待効果**: 診断イベントが 1/10 以下になり、長時間航行でも
`diagnosticEventLimit`(20000)に余裕ができる。

### W21. 「陸上消音区域」の新設【判断済み 2026-07-28: 実装する】

**対象**: `lib/services/ashore_detector.dart`、`lib/services/preset_obstacle_service.dart`、
`lib/config/ashore_config.dart`、
**`assets/data/sakuragawa_land_silence_zones.json`(新規ファイル)**、
`lib/hooks/use_navigator.dart`

**利用者の判断**: 実装する。**機能を先に入れておき、区域の座標は後日渡す。**

#### なぜ必要か

現行の陸上判定は「岸の基準線から陸側へ12m以上」でしか成立しない。
今回の出艇地点は岸基準線から**水面側へ43.8m**の位置にあり、
艇庫・桟橋では**原理的に陸上判定が成立しない**。

#### データ形式 — 危険区域プロファイルとは別ファイル

**`assets/data/sakuragawa_land_silence_zones.json`(新規)**

```json
{
  "version": 1,
  "notice": "警告音だけを止める区域。危険区域ではない。危険区域プロファイル(sakuragawa_obstacles.json)のSHA-256検証の対象外。",
  "zones": []
}
```

**なぜ別ファイルにするか**: `sakuragawa_obstacles.json` へ足すと、
空配列を1つ加えるだけでファイルの SHA-256 が変わり、
Firestore Rules の更新と共有安全設定の再公開が必要になる(§S4 冒頭)。
陸上消音区域は危険区域ではないので、同じ検証対象に入れる理由がない。

- **この作業では `"zones": []`(空配列)で入れる。**
  スキーマと読み込み経路を先に通し、座標は後日の差し込みだけで済むようにする
- `pubspec.yaml` の `assets:` に追加する
- 校正(`FixedObstacleCalibration`)の**対象外**。
  `SharedSafetyCalibrationState.allowedSourceIds` にも**追加しない**
- `DangerZoneKind` にも**追加しない**。これは危険区域ではない

#### 判定ロジック

`AshoreDetector` に `landSilenceZones` を渡し、**基準線の距離判定より先に**評価する。

| 状況 | 判定 | 理由 |
| --- | --- | --- |
| **GPS誤差円が区域内に完全に収まる**状態が `landSilenceZoneConfirmationDuration`(既定10秒)継続 | 陸上確定 | 下記参照 |
| 区域外へ出た(誤差円が区域からはみ出した) | **即座に**水上へ戻す | 現行の非対称(入るのは遅く、出るのは速く)を維持 |
| 区域が空/読めない | 現行の基準線判定へ縮退 | 原則1「機能を止めない」 |
| GPS品質が不良、または accuracy が不明 | **水上扱い**(現行どおり) | 原則6「データ欠損は安全の根拠にならない」 |

**「点が区域内」ではなく「GPS誤差円が区域内に完全に収まる」ことを要求する。**
点だけで判定すると、桟橋脇の水面にいるのに持続的な測位ずれで区域内と読まれ、
**水上で音が消える**。これは警告漏れそのものであり、10秒の継続確認では防げない
(ずれは持続するため)。判定式:

```
区域の境界からの最短距離(区域内を正) >= max(accuracy, assumedGpsAccuracyMeters)
```

区域は艇庫・桟橋の陸側に**余裕をもって**描くこと。この判定式は、
区域を小さく描くほど成立しにくくなる。

- `AshoreDecisionReason` に `insideLandSilenceZone` を追加する
- **止めるのは音だけ。** リスク評価・画面表示・セッション記録・位置共有は
  この判定に一切影響されない(現行の設計を維持)
- 点in多角形判定は `lib/utils/winding_algorithm.dart` の既存実装を使う
- `AshoreDetector` は**純Dart**のままにすること(Timer・通信・センサーを持たない)

#### 新規設定(`lib/config/ashore_config.dart`)

```dart
/// 陸上消音区域の内側にいることを確定するまでの継続時間。
///
/// 岸の基準線からの距離判定([ashoreConfirmationDuration] = 30秒)より短くてよい。
/// 区域は人が明示的に描いた陸の上の範囲であり、加えて
/// 「GPS誤差円が区域内へ完全に収まる」ことを要求するため。
const landSilenceZoneConfirmationDuration = Duration(seconds: 10);
```

#### 地図表示

区域を地図に描く。ただし**危険区域と誤解させないこと**。
既存の規則「**塗り = 実在する危険 / 線 = 予測**」を守り、
**危険区域と同じ赤系の塗りにしない**。輪郭線 + ごく薄い中立色(灰・青灰)、
ラベルは「消音区域」。

#### やってはいけないこと

- 区域内で**検知・表示・記録・位置共有を止める**こと。止めるのは音だけ
- 区域が無いことを理由に航行開始をブロックすること
- **この作業で `sakuragawa_obstacles.json` に触ること**

#### 受け入れ条件

- 空配列でビルド・起動でき、陸上判定の挙動が現行から変わらない
- `./tool/update_hazard_profile_hash.sh --check` が成功する(SHA は変わっていないはず)
- ダミー座標を入れたテストで
  - 誤差円が完全に収まって10秒継続 → `isAshore == true`
  - 誤差円が境界にかかる → `isAshore == false`(区域内に点があっても)
  - 区域外1点 → 即座に `false`
- 区域内でも `activeWarnings` / セッション記録 / 位置共有が継続する

**テスト**: `test/services/ashore_detector_test.dart` に上記を追加。
既存の「基準線の向き(頂点順の左手が水面側)」を固定するテストは**必ず残す**。
