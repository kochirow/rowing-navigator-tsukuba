# Release 3a — S1 の改良と昇格判定

## S3-01. 前方外挿の抑制（第一候補・最小変更）

### 目的
§1-2 の実害への直接の答え。**横方向には元々ほぼ寄与していないので
（\|cross\| med 0.09〜0.20m）、前方外挿を削っても岸・レーン判定は悪化しない。**
これが安全に削れる根拠である。

### 変更対象
`lib/services/robust_position_estimator.dart`

### 変更内容

1. **`MotionStateDetector`（Stage 2 で作成）を入力に取る。**
   `stopped` / `decelerating` のとき速度状態を素早く落とす。

2. **`velocityDecayTimeConstantSeconds = 8` の役割を分離する。**
   現行の意図は「艇は数秒では止まらないので、速度を 0 にすると停止距離が 0 になり
   警告レベルを不当に下げる」。この意図は保つが、実現方法を変える。

   ```text
   これまで: 速度状態を保持し続ける → 位置が前へ飛ぶ（害）
   これから: 速度状態は素早く落とす → 停止距離は安全集合の前方成分で表す（害なし）
   ```

3. **fix age が閾値を超えたら位置の前進を止め、集合だけ広げる。**

   ```dart
   /// この時間を超えて測位が来ないときは、位置の外挿をやめる。
   /// 前へ進めるのではなく、到達し得る領域を広げて表す。
   ///
   /// 2026-08-06 実機ログ: 停止中(0.2〜0.5m/s)に進行方向へ
   /// 16〜18m 投影され、それが岸警告と flapping を生んでいた。
   const positionExtrapolationCutoffMs = 1500;
   ```

### テスト

| 4 | 停止後の停止距離 | 集合の前方成分として残る（0 にならない） |

## S3-02. `Q(dt)` の是正と観測ノイズ下限（第二候補）

**S3-01 で受け入れ基準を満たしたら、これはやらない。** 複雑さを足さない。

### 観測ノイズ下限
`minimumAccuracyMeters = 4` は、C の報告値 med 2.0m を **4m へ切り上げている**。
= 良い測位をわざと半分しか信じていない。dt が長いとき発散を助長する。

- D/E ペアで、端末報告 accuracy と実誤差の対応表を作り、下限を実測から決める。
- **注意**: 相対誤差は共通誤差（電離層・軌道）が相殺するので、**絶対**精度の代用にはならない。
  絶対の下限は `uncertaintyFloorMeters` の役割として別に置く。

### `Q(dt)`
innovation 26m が出るのは**プロセスノイズが dt に対して過小**で共分散が十分膨らまず、
正規化 innovation が過大になって正しい測位を棄却しているため。

- `Q` が dt, dt², dt³, dt⁴ のどの項を持つかをモデル式とテストで固定する。
- 停止・定速・加速・旋回を別 fixture にする。
- **全 dt 範囲で共分散が正定値・有限であることを検査する。**
- 連続棄却中に共分散を膨らませる（現在は「自信満々にずれている」状態になる）。

### 再捕捉
`reacquisitionSampleCount = 3` × `maximumReacquisitionSampleGap = 3s` は、
測位間隔が 2〜3 秒だと成立しにくい。**サンプル数ではなく経過時間で規定する。**
（Stage 2 で 1Hz に戻っていれば緩和されるが、橋下では依然疎になる。）

### 第三・第四候補（保留）
- Innovation-Adaptive（適応係数に上下限と変化率制限、適応状態をログへ）
- 軽量 IMM（Stop/Drift・Cruise・Maneuver）
  Stop/Drift モードは §1-2 への正攻法でもあるが、**複雑さの割に S3-01 で足りる可能性が高い。**

# Release 3b — 保護半径と他艇の到達可能領域

## S3-04. `ProtectionBudget` の合成規則を確定

### 現状の問題
`pairGpsCenterDistanceGuardMeters` は `sqrt(accA² + accB²) × 0.20`、上限 **2.5m**。
`boat.accuracy` に 95%半径（≈10m）が入るため **常に上限で飽和**している。
測位が良くても悪くても同じ 2.5m で、**情報を持っていない。**

### 相対と絶対を分ける（DGNSS の原理）
同じ水域・同じ時刻の 2 受信機は、誤差の共通成分（電離層・軌道・衛星時計）が相殺する。
**今回それを実測した——真の位置差 1.5〜2m に対し raw 位置差 med 1.7m。**
絶対精度 10m を 2 乗和する現在の式は**二重計上**である。

| 対象 | 使う不確かさ |
| --- | --- |
| **静的危険区域**（絶対座標に固定） | **絶対**。現行のままで正しい |
| **他艇**（相対幾何） | **相対** + 通信遅延分 + 解分離マージン |

### 合成規則
Stage 1 では決めなかった `ProtectionBudget.totalMeters` をここで確定する。

```dart
/// 用途別に合成する。全部を二乗和にしない。
///
/// - 独立とみなせる成分(測位雑音・モデル不一致)は二乗和
/// - 上限として効く成分(fix age による運動、通信遅延)は**線形加算**
///   これらは「最悪どこまで動けたか」であり、確率的に打ち消し合わない
double relativeTotalMeters() =>
    sqrt(gnssMeasurementMeters² + modelMismatchMeters²)
    + fixAgeMotionMeters
    + remoteLatencyMeters
    + solutionDisagreementMeters
    + headingUnknownMeters
    + speedUnknownMeters;
```

**飽和した定数（現行 2.5m 上限）をやめ、測位品質に応じて伸び縮みさせる。**
良い日は帯が締まって `definite` が増え、悪い日は広がる。これが本来の設計意図である。

### D/E ペアは校正ではなく検証に使う
> 校正データは 1水域 × 1ペア × 1セッション × 677対応点しかない。
> 「停止/低速/通常/全力 × 直進/旋回 × fix age帯 × accuracy帯 × disposition ×
> integrity状態」に層別すると1層十数サンプルで、**過適合が保証される。**
> **半径は物理と設計から決め、ペアでは被覆率だけを確認する。**

被覆の目標:

```text
95% 被覆: relativeTotalMeters >= 実測のペア超過誤差 が 95% のサンプルで成立
99% 被覆と、連続未被覆時間も記録する
未被覆が特定の状態(停止/旋回/fix age大)へ集中していないかを確認する
```

### 被覆率を合否に使うときの注意（サンプル数の限界）

**対応点は 677 組しかない。**

| 目標 | 裾のサンプル数 | 判定できるか |
| --- | --- | --- |
| 95% 被覆 | 約 34 点 | **できる**（±2% 程度の幅で） |
| 99% 被覆 | **約 7 点** | **できない。**1 点の増減で 0.15% 動く |

- **95% 被覆だけを【止】の基準にする。**
- **99% は【記】**。数値を残すが合否にしない。「99% 保証」と書かない。
- 未被覆が特定状態へ集中しているかは、**件数ではなく分布の偏り**として記録する
  （7 点の内訳を眺めても統計的な意味は無いが、全部が「停止時」なら設計上の示唆になる）。

**「一般的な 99% 保証」とは呼ばない。「2026-08-06 条件に対する経験的値」と明記する。**

**不合格時の分岐**: 95% 被覆に届かない場合、
半径を上げる前に**未被覆の状態分布を見る**。特定状態に集中していれば、
その状態の成分（例: `fixAgeMotionMeters`）だけを直す。
全域で一様に足りないときだけ、全体を上げる。
**一律に係数を上げて被覆率を達成しない**——それは飽和した 2.5m 定数へ戻る道である。

### テスト
- 単調性（Stage 1 の `BUDGET_MONOTONIC_*` 契約）
- 各成分を 0 にしたとき、合計がその成分ぶんだけ減る（分解可能性）
- D/E ペアでの被覆率レポート

## S3-07. `SuppressionRule` の型付けと静音権限

### 目的
現在 `_applyPresentation`（`safety_orchestrator.dart:462-569`）には
**下げる規則が7つ**、順序依存で並んでいる
（低速静音 / 不確かさのみ / 桟橋 / 安定停止×3 / 反復停止）。

**問題が2つ実証されている。**

1. **一部が `_quieter()`、一部が直接代入**（:497 など）。適用順で結果が変わる。
   コメントには過去2回、順序を間違えて鳴り直した記録がある。
2. **Stage 1 の S1-01 regression** は「どの規則がどのカテゴリに適用されるか」が
   一覧化されていないために起きた。

### 宣言的な規則表

```dart
class SuppressionRule {
  final String id;
  final Set<String> allowedCategories;      // 空 = 全カテゴリ
  final Set<String> forbiddenCategories;    // other_boat をここへ
  final AlertUrgency maximumSuppressibleUrgency;  // これを超える緊急度は抑制不可
  final Set<RequiredInput> requiredKnownInputs;   // 欠損時は適用しない(原則6)
  final AlertBehavior targetBehavior;
  final String reasonCode;
  final bool Function(SuppressionContext) predicate;
}

enum RequiredInput { ownSpeed, otherBoatSpeed, ownPosition, mooringArea }
```

### 不変条件（型と全組み合わせゴールデンテストで強制）

- `other_boat` は明示許可されない限り抑制不可
- **相手速度不明を静音の根拠にしない**（`requiredKnownInputs` に `otherBoatSpeed`）
- `urgent` は low_speed / mooring / stable_stop 規則で抑制されない
- 下位カテゴリの規則が上位警告を上書きしない
- 集約前の個別危険を記録に残す

### 適用アルゴリズム

```text
1. 全規則を評価する
2. 権限（category / urgency / requiredKnownInputs）を満たさない規則を除外する
3. 残った規則の中で **最も静かな targetBehavior** を採る
4. 適用された規則と、適用されなかった規則＋その理由を、すべて reasonCodes へ
```

**「権限を満たす規則の中で最も静か」に統一する**（`_quieter` と直接代入の混在を解消）。

### ゴールデンテスト
`test/services/suppression_rule_matrix_test.dart`（新規）

**全カテゴリ × 全規則 × 主要な状態の組み合わせ表**を JSON として固定する。

```text
カテゴリ: other_boat, shore, bridge, bridgePier, island, driftwood, pile, curve, reverse
状態:     自艇停止/低速/航行 × 相手停止/接近/速度不明 × 桟橋内/外 × urgency 4段階
```

規則を足したり変えたりすると差分が出るので、レビューで気づける。

### 移行
既存7規則を1つずつ表へ移す。**1規則ごとにコミットし、
その都度 `replay_regression_test` が不変であることを確認する。**
まとめて移すと、どれが挙動を変えたか分からなくなる。

## S3-08. `AlertEpisodeManager`

### 目的
サンプルごとの候補生成と、人に伝える警告単位を分離する。

**実害**: A では逆走が **13エピソードで96回読み上げ**（1エピソード平均 7.4 回）。
D/E は 8エピソードで各8回（1回ずつ）。**同じ状況で艇によって 0〜8 回のばらつき。**

### 状態

```text
inactive → observing → announced → escalating → stable → cleared
```

### エピソード識別子

```text
episodeKey = hazardFamily + physicalTarget + causalContext
```

| 状況 | 扱い |
| --- | --- |
| 同じ岸へ停止中に接近・離脱を繰り返す | 1エピソード |
| 同じ逆走区間に連続滞在 | 1エピソード |
| 同じ他艇との接近 | 1エピソード |
| 一度十分に離れ、再接近した | **新エピソード** |

### 音声規則

| 遷移 | 音 |
| --- | --- |
| 初回（`announced`） | 対象と行動を **1回** |
| 危険度が上がった（`escalating`） | より短いエスカレーション音声 |
| 危険度不変（`stable`） | **表示更新のみ** |
| 改善 | 音なし |
| 解除（`cleared`） | 原則音なし |
| 再侵入 | rearm 条件を満たしたときだけ新規音声 |

**「5秒ごとに最大3回」のような回数制限ではなく、状態変化を意味として扱う。**
`guidanceRepeatInterval`（5秒）は `stable` では発火しなくなる。

### 既存機構との関係
- `lib/services/alert_state_machine.dart` は
  **候補のライフサイクル（candidate→alerting→clearing→safe）** を管理している。
  エピソードはその**上位**の概念であり、置き換えない。
- `lib/services/reverse_guidance_debouncer.dart` の rearm ロジックは
  エピソードの `cleared → 新エピソード` 判定へ吸収する。

### テスト
- 【止】同一危険のサンプル数を増やしても初回音声は1回（メタモルフィック不変条件8）
- 【止】危険度悪化では再通知できる（**減らすだけの実装になっていないことの確認**）
- 【止】十分離れて再接近したら新エピソード
- 【記】A のログ再生での逆走の読み上げ回数
  - 目的: エピソード化の効果測定
  - 出典: 実測 A 96回 / 13エピソード（1エピソード平均 7.4 回）
  - 期待: **エピソード数（13）以上、現行（96）の 1/3 以下**
    > 「13回程度」と書くと、悪化検知による再通知が1回でも入ると不合格になる。
    > 悪化での再通知は**あるべき挙動**なので、上限に幅を持たせる。
  - 不合格時: エピソード数を下回る → **止まる**（初報を落としている疑い）。
    1/3 に届かない → 記録して進み、`episodeKey` の粒度を見直す

## S3-12. 再試行の原因別分類

### 実害
`publishingSetupUnavailable`（`use_navigator.dart:3232-3276`）は
`clearMessage` + `registerOnDisconnect` が5秒でACKされないと立ち、
**その後の復帰経路がない。**

今回 `ack_timeout` は A（1回）・D（3回）でも発生し、
C は起動直後に `permission-denied`（`likelyCause: rtdb_rules_or_team_membership`）を3回。
**起動直後の共有確立は全端末で不安定。**

### 分類

| 原因 | 再試行 |
| --- | --- |
| timeout / network unavailable | **jitter 付き指数バックオフ**（1s → 2s → 4s … 上限60s） |
| transient disconnect | 即時1回 → 指数バックオフ |
| **permission-denied** | **無限再試行しない。** 認証・所属・Rules 原因として表示・記録 |
| invalid data contract | 再試行せず、互換性 fault |

### 方針
**degraded 起動を続ける方針は変えない**（原則1）。**復帰経路を足すだけ。**
成功したら `position_sharing_recovered` を出す。

終了時の `Remote position cleanup` の TimeoutException（B・E で発生）も同じ経路。

### テスト
- timeout → バックオフして復帰
- permission-denied → 有限回で諦め、表示 fault
- 復帰後に `position_sharing_recovered` が出る
- **degraded のまま航行が継続できる**（機能を止めない）

## S3-17. `safety_evaluation_stalled` の閾値

### 実害
閾値3秒に対し、実測の測位間隔が med 2.0〜3.0s。
C では `lastSafetyEvaluationAgeMs` が 3002 / 3012 / 3015 / 3190ms で
**6回 fault が立った**（`pipeline_unresponsive` 6エピソード）。
正常な運用で立つ警告は不具合である（原則4）。

### 方針
**Stage 2 で 1Hz に戻れば自然に解消する。だから Stage 2 の効果測定を兼ねる。**

```text
Stage 2 後の実測で fault が 0 件 → 閾値は触らない（R1 が直った証拠）
Stage 2 後もまだ立つ           → 実効測位間隔の移動中央値から動的に決める
```

> **先に閾値だけ上げてはいけない。** R1 を隠してしまう。
