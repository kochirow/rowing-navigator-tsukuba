## 0. 統合にあたっての判断

両案は診断（根本原因の鎖）では一致している。違いは**打ち手の構え**である。

- [根治版] = 原因を特定して直す。速いが、推定器の較正が開放的な調整作業になる。
- [RTA版] = 直す前に「壊れても安全な構造」を作る。堅いが、最大のレバーの投入が遅れる。

**統合方針: 観測を先に、構造を次に、レバーは早く、較正は最後。**

### 0-1. [RTA版] から全面採用するもの

| 採用 | 理由 |
| --- | --- |
| **Solution Separation / Runtime Assurance**（C） | [根治版] の最大の弱点を突いている。推定器の較正は終わりの見えない調整だが、**発散の検出は有界な問題**である。しかも D/E ログが検出器の有効性を先に証明している——raw と filtered が 20〜32m 食い違った 372 秒は、S1 と S0 を比べるだけで全区間検出できた |
| **反実仮想ログ実験室 / 障害注入**（A） | [根治版] の Phase 0 の上位互換。特に `batch_delivery` 変換は、**実機を待たずに 900ms ゲートの挙動を検証できる** |
| **メタモルフィック不変条件**（A-5） | 安い・恒久的・今回の regression をまさに捕まえる種類の網。不変条件9「より緊急な候補を追加しても既存の緊急音声が静音規則で消えない」は、Release 0 の bug をそのまま検出する |
| **辞書式の失格判定**（A-6） | **安全系の候補選択として唯一正しい形。**加重平均スコアは「見逃し1件」と「うるさい10件」を交換できてしまう。辞書式はそれを禁じる |
| **SuppressionRule の権限モデル**（G-4） | [根治版] 3-1 の上位互換。`maximumSuppressibleUrgency` と `requiredKnownInputs` が効く。後者は**原則6を型で強制する** |
| **Alert Episode Manager**（G） | [根治版] 4-2 の「エピソードあたり3回上限」より良い。回数ではなく**状態変化（初回・悪化・解除）**で鳴らすほうが意味に忠実 |
| **能力監視の分解**（H-1） | **[根治版] の誤りを正している。** 下記 0-3 |
| **再試行の原因別分類**（H-2） | `permission-denied` を無限再試行しないのは正しい。[根治版] は一律バックオフと書いていた |

### 0-2. [RTA版] から**採らない / 縮小する**もの

| 項目 | 判断 | 理由 |
| --- | --- | --- |
| **時系列 Conformal Calibration**（E-4） | **今は採らない。原則だけ採る** | 校正データが `1水域 × 1ペア × 1セッション × 677対応点`。これを「停止/低速/通常/全力 × 直進/旋回 × fix age帯 × accuracy帯 × disposition × integrity状態」へ層別すると、1層あたり十数サンプルになる。**過適合が保証されている。**[RTA版] 自身が「一般的な99%保証と呼ばない」と正しく留保しているが、留保して使うより**校正には使わず検証に使う**ほうが誠実である。→ 保護半径は物理と設計から決め、**D/Eペアは「その半径が被覆しているか」の合否判定にだけ使う。** 複数水域・複数ペアのデータが貯まったら E-4 を再検討する |
| **`gps_guard_entry` による降格の全廃**（C-5 / F-3） | **他艇に限定する** | [RTA版] は「不確かさが大きいだけで降格しない」と広く書いているが、CLAUDE.md の提示ポリシーでは**1バンド降格は連続音の信頼性を守るための意図的設計**である。静的区域まで含めて外すと過剰警告が戻る。**他艇については降格をやめる代わりに到達可能領域＋相対保護半径で判定する**（F）。静的区域は現行の降格を維持する。この区別を書かずに実装すると、意図的な設計を事故で外す |
| **警告総量予算の CI ゲート廃止**（§15） | **辞書式の第5基準として残す** | [RTA版] の懸念（件数上限だけを合否にすると、本物を消して達成できる）は正しい。しかし A-6 の辞書式では、見逃しと初報遅延が**件数比較の前に**失格する。したがって**単独ゲートにはしないが、失格を免れた候補どうしの比較基準としては残す**。EEMUA 191 の 6件/時・12件/時は目標値として維持する |
| **3解並列の実行コスト** | **予算を明示して制約にする** | [RTA版] は CPU 記録に触れるが、**D が 61分で 70%→15%（54%/時）で終わった**事実に向き合っていない。これは安全問題である（2時間の朝練を完走できない）。S0 は実質無料（最新妥当 fix の保持）、S2 は α-β で軽い。実質 S1 + 軽量2本。**それでも電池は辞書式の失格基準に入れる**（下記 3-4） |

### 0-3. [根治版] の誤りを [RTA版] が正した点

[根治版] 5-1 に「**受信0隻を fault にする**」と書いたが、これは誤りである。
**0隻は正常状態でもあり得る**（最初に出艇した艇、他艇が全部上がった後）。
[RTA版] H-1 のとおり、監視すべきは隻数ではなく**能力**である。

- publish setup / publish ACK の鮮度 / subscription 接続 / 認可状態 /
  server time offset の鮮度 / 最後の受信時刻 / チーム名簿の取得可否

を別々に持ち、「他艇がいない」と「他艇を受信できる状態を確認できない」を区別して表示する。
B/E が 118 分にわたり無自覚に走った件は、隻数ではなく
**`positionSharingState=unavailable` が全 heartbeat で継続していた**ことで検出できた。

### 0-3b. GPS補正分析から採用したもの（既定の反転）

「補正はかけすぎ。生GPS優先＋外れ値抑制のほうが信頼できる」という結論を**採用する**。
提示された数値（8m超 6組 vs 197組、10m超 1組 vs 176組、D の |補正−生| med 5.6m / p90 13.1m、
E の med 2.8m / p90 3.5m）は**すべて再計算して一致を確認した**。

そのうえで **along/cross 分解を追加調査**したところ（§1-2）、結論を補強する事実が出た:
**補正はほぼ100%が進行方向で、横方向へは中央値 0.1〜0.2m しか効いていない。**
岸・レーン・逆走はすべて横方向で決まるので、**補正をやめてもその軸では失うものがない。**
これにより「生GPS優先」は、消極的な妥協ではなく**積極的に正しい選択**になった。

反映先: **§2-1（S2 を primary にする方針転換）**、**§3 の基準 4-b**、
**Release 4 の目的の変更**、**Release 5 の第一候補の差し替え**。

なお提示された次回合格条件（「補正後 p99 が生GPSより悪化しない」「10m超ずれ 0 回」）は、
本統合版が独立に定めていた §3 の基準 4・3 と一致した。**中心的な合否基準として固定する。**

### 0-4. 順序について——[RTA版] と変える1点

[RTA版] は Fix Ingress を Release 4（RTA fallback の後）に置いている。**ここだけ前に出す。**

- 測位を 0.4Hz → 1Hz へ戻すのは**プログラム全体で最大のレバーかつ最小の変更**である。
  ゲートの条件式とプラグイン設定の2箇所。
- dt が 1 秒へ戻れば、**推定器の発散そのものが大幅に減る可能性が高い**
  （発散の機序は「dt が伸びる→予測が外れる→ゲートが正しい測位を棄却」である）。
  先に RTA を作ると、**消えるかもしれない発散を捕まえる監視器を先に作る**ことになる。
- これは新機構の導入ではなく、**意図した挙動（1Hz）の回復**である。

ただし [RTA版] の懸念（挙動変更には網が要る）は正しいので、**観測と実験室を先に置き、
Ingress は機能フラグ＋実験室検証＋shadow メトリクス付きで入れる**。
RTA fallback は Ingress の直後、推定器交換の前に入る。

## 1. 根本原因（両案で一致）

```
[R1] 測位が実効 0.4Hz（1Hz は出ているのに 2/3 を捨てている）
      ↓ dt が 2〜3秒へ伸びる
[R2] 推定器が全力漕ぎ中にテールで発散（innovation 26m / 最大 32m）
      ↓ 74分中 372秒（8.4%）位置が 10m 以上ずれる
[R3] ありもしない岸接近・レーン逸脱 → 警告総量が基準の 6 倍（A: 70回/時）
      ↓ 過剰警告を抑えるため提示ポリシーへ例外が積み上がる
[R4] 例外の相互作用で本物の他艇警告が無音化（regression）
[R5] 能力の欠如を誰も観測していない（独立した鎖）
```

**D/E の真の位置差 1.5〜2m** を基準にした実測:

| 指標 | 実測 | 意味 |
| --- | --- | --- |
| GNSS 測位間隔 | **2.0s / 3.0s に量子化**、1.0s は A/E で 5%・B/C/D で 0% | 1Hz の fix は存在する |
| ポーリング | 919 回中 918 回が「ストリームより新しい」 | OS は持っている |
| raw 位置差 | med 1.7m（停止）/ 2.7m（航行）、8m 超は 677 中 6 回 | **生 GNSS の相対誤差はほぼ 0** |
| filtered 位置差 | med 3.6 / 2.1m だが **p99 19.2m・max 32m** | 誤差はすべて推定器が作っている |
| 10m 超のずれ | **5 回・合計 372 秒 / 74 分（8.4%）** | 毎練習で数分間まちがっている |
| ずれている最中 | 速度 med **3.40 m/s**、innovation med **26.1m** | **全力漕ぎ中**。`hardGate=25` の近傍 |
| 読み上げ | A: **70 回/時** | EEMUA 191 の操作者上限 12 回/時の 5.8 倍 |

補足（[根治版] から引き継ぐ具体値）:

- `minimumAccuracyMeters = 4` が、C の報告値 2.0m を 4m へ切り上げている
  = **良い測位をわざと半分しか信じていない**。dt が長いとき発散を助長する。
- `pairGpsCenterDistanceGuardMeters` は `sqrt(accA²+accB²)×0.20`、上限 2.5m。
  `boat.accuracy` に 95%半径（≈10m）が入るため**常に上限で飽和**しており、
  測位品質に関わらず定数である。Release 6 で相対保護半径に置き換える理由。

### 1-2.【追加調査で判明】R2 の正体は「停止時の前方外挿」だった

補正ベクトル（filtered − raw）を進行方向 along / 横方向 cross に分解すると、
**5端末すべてで補正はほぼ100%が along（進行方向）**である。

| | \|d\| med | \|d\| p99 | \|along\| med | **\|cross\| med** | 10m超のずれの速度 med |
| --- | --- | --- | --- | --- | --- |
| A:4x | 2.48m | 16.36m | 2.46m | **0.12m** | 2.10 m/s |
| B:8+前 | 2.71m | 5.40m | 2.69m | **0.10m** | — |
| C:2x | 0.71m | 16.70m | 0.70m | **0.09m** | **0.52 m/s** |
| D:8+cox | 5.57m | 25.24m | 5.56m | **0.20m** | **0.20 m/s** |
| E:8+後 | 2.75m | 18.95m | 2.74m | **0.09m** | **0.22 m/s** |

閾値で数えると差は極端になる（D/E 677組）:

| | 生GNSS | filtered |
| --- | --- | --- |
| 8m 超 | **6組** | **197組** |
| 10m 超 | **1組** | **176組** |

**読み取れること（計画に直接効く3点）:**

1. **横方向の補正は実質ゼロ（med 0.09〜0.20m）。**
   岸・レーン・逆走の判定はすべて横方向の距離で決まる。
   **つまり「補正をやめて生GNSSにする」ことで、この軸で失うものはほぼ無い。**
2. **符号は along が正（前方）。大きなずれは速度 0.2〜0.5 m/s、ほぼ停止時に集中する。**
   止まった艇を進行方向へ十数〜数十m先へ置き続けている。
   航行中の実効先行量は D で med 1.58 秒ぶん、E で 0.66 秒ぶん。
   機序: 測位が 2〜3 秒空く → 直前の速度で前へ外挿 → 停止しても
   `velocityDecayTimeConstantSeconds = 8` で速度が緩やかにしか落ちない
   （「艇は数秒では止まらない」という意図的設計）。
3. **岸警告の発生時速度 med 0.02〜0.45 m/s は、この前方飛ばしが起きる速度域と一致する。**
   桟橋では艇はあらゆる方向を向くので、16m の前方投影は容易に岸区域へ食い込む。
   `dataQuality=good` のまま flapping していたのはこのためで、GPS の質の問題ではない。

> **訂正**: [根治版] と本統合版の初版は R2 を「全力漕ぎ中の発散」と書いた。
> D/E の**ペア差**が10mを超える区間は確かに速度 med 3.40 m/s だが、
> **端末ごとの |filtered − raw|** が10mを超えるのは 0.2〜0.5 m/s に集中する。
> 両方とも実在する別事象で、**後者のほうが件数も影響も大きい。**

```text
              +------------+-------------+
                           v
              Reachable-Set Risk Evaluation
                           v
                    Alert Episode Manager
                           v
              表示 / 音声 / 記録 / 理由コード
```

**追加の制約（統合で加える）**: S0 は状態を持たない（最新妥当 fix の保持のみ）。
S2 は α-β で固定係数。**計算コストの主体は S1 のままに保つ。**

### 2-1.【方針転換】既定の選択解を反転する — S2 を primary にする

§1-2 の結果を受けて、[RTA版] の構えを1点変える。

- **[RTA版]の想定**: S1 が primary。監視器が発火したら S0/S2 へ退避する。
- **統合版の決定**: **S2（生GNSS優先＋外れ値抑制）を primary にする。
  S1 は §3 の合否試験に合格して初めて primary へ昇格する。**

理由:

1. **横方向では S1 が何も足していない**（cross 補正 med 0.09〜0.20m）。
   岸・レーン・逆走はすべて横方向で決まるので、**この軸では失うものがない。**
2. **進行方向でだけ S1 は寄与するが、それが害の全部でもある。**
   停止時に十数〜数十m前へ飛ばす（§1-2）。
   生GNSSの 8m 超は 6/677 だが filtered は 197/677。
3. **退避の閾値調整が要らない。** [RTA版] の構えでは、監視器が正しく発火する閾値を
   決めきるまで危険な解が primary に居座る。反転すれば**保守的な解が既定**になり、
   監視器は「S1 を昇格させてよいか」の判定に使える。**より早く、より安全に出せる。**

**S2 の設計（重要な但し書き）**

「生GNSSをそのまま使う」ではない。**位置と速度で扱いを分ける。**

| 量 | 扱い | 理由 |
| --- | --- | --- |
| **位置** | 生 fix をそのまま採用。外れ値ゲートのみ（物理的にあり得ない飛びを棄却）。**前方外挿しない** | 補正が害になっている軸 |
| **速度・方位** | 軽く平滑化（α-β）。生の速度は雑音が大きい | `getStoppingDistance` と船体領域の低速拡張、TTE に効く。落とせない |
| **不確かさ** | 実測（§1-3）に基づく正直な値。fix が古いほど単調に増やす | 原則6 |

- **fix が古い間は、位置を前へ進めずに保護半径を膨らませる。**
  これが今回の「前方飛ばし」への直接の答えである。
  艇が実際どこまで進み得るかは、位置をずらすのではなく**領域**で表す（下記 2-2）。
- 生GNSS単独で十分と主張しているのではない。端末報告精度は D med 3.6m / p90 8.4m、
  E med 4.8m / p90 8.6m。ペア比較では**両端末に共通する絶対誤差は検証できない**し、
  今回のログには**橋の下・樹木下・岸際が含まれていない**。
  **「現行の強い補正より、控えめな補正のほうが信頼できる」**という限定的な主張である。

**S1 は捨てない。** RTA の枠内に残し、Release 5 で §3 に合格したら primary へ戻す。

### 2-2. S2 は点推定器ではなく**集合値推定器**にする（重要）

上の「位置を進めず半径を膨らませる」を、**S2 の正式な出力の形として定義し直す。**

```text
S2 の出力 = 代表点（表示用） + BoundedPositionSet（安全判定用）
```

- **代表点** = 最新の妥当 GNSS 位置。前へ飛ばさない。地図・数値表示はこれを使う。
- **安全判定** = 集合。fix が届かない間、艇が物理的に到達し得る量を足していく。

```text
predictedSet(t+dt) = previousSet ⊕ (dt 秒で到達可能な運動集合)
newSet             = predictedSet ∩ measurementSet     // 新しい fix が来たとき
```

**なぜ点推定では解けないのか。** 点は必ず1か所を選ばされる。fix が古いとき選択肢は
「前へ飛ばす」（＝現行、実害の元）か「凍結する」（＝停止距離と実際の前進を失う）しかない。
集合なら**代表点は凍結したまま、前進の可能性は領域に残せる**。§1-2 の問題が構造的に消える。

**等方の円ではだめである（この計画に固有の理由）。**
4m/s で 3 秒の欠測なら前方 12m。これを円で表すと**横方向にも 12m** 広がる。
川幅 40〜50m の水域では、それだけで岸区域へ食い込む。
**§1-2 が示したのは「横方向の誤差は小さい」ことだった。**
等方に膨らませると、せっかく直した過剰警告を別の理由で復活させる。
→ **進行方向に伸びたカプセル**（前方は速度×dt、横方向は旋回率と測位誤差だけ）にする。

**段階実装。zonotope ライブラリは要らない。**

1. 円（最小実装。停止中はこれで十分——前方成分がほぼ 0 のため）
2. **進行方向カプセル**（航行中。ここまでで実用に足る）
3. 円・カプセルの和集合（2-3 の ambiguous 用）
4. 楕円・zonotope（必要が実証されたときだけ）

**交差しなかったとき**（predictedSet ∩ measurementSet = ∅）は、予測か観測のどちらかが誤っている。
平均を取らず integrity を `indeterminate` に落とす。
**D/E の 32m 発散区間は、まさにこれが継続的に発火する区間である**——回帰試験に使える。

既存資産との接続:
- `ship_domain_service` / `swept_outline_service` に凸形状と掃引の機構が既にある。流用する。
- **CLAUDE.md 不変条件6「地図描画は安全判定用の拡張を反映しない」は、
  この表示点／安全集合の分離とそのまま同じ思想である。**新しい原則ではない。
- 不変条件8（`boundingRadius` は領域の実寸を下回らない）と
  不変条件7（`distanceMeters` は符号付き）は、集合化で意味が変わる。Release 4 で再定義する。

### 2-3. 解が食い違うときは1つを選ばず、**限定的に**仮説を束ねる

`ambiguous` 状態を状態機械へ加える（`trusted / suspect / ambiguous / fallback / reacquiring`）。
表示は常に S2 の代表点、安全判定は「もっともらしい仮説の和集合」。

**ただし無条件の和集合は過剰警告製造機になる。** ここは慎重に設計する。

> S1 が 20〜32m ずれていた 372 秒間、S0∪S1∪S2 を素直に取れば安全集合は約 30m 幅になる。
> 川幅 40〜50m でそれは、岸とも他艇とも常時重なる。原則4に正面から反する。

したがって:

- 和集合に入れるのは **`plausible` な仮説だけ**。
  **一定時間 separation 試験に落ち続けた解は「もっともらしくない」ので、和集合から外す。**
  今回のデータでは外れるのは S1 側である。壊れた解を抱き続けて領域を膨らませない。
- 和集合を使うのは**どれが正しいか判定できない短時間だけ**。
  判定がついたら単一仮説へ戻す。
- **`ambiguous` の滞在時間に上限を置き、超えたら `fallback`**（＝ S2 単独 + 拡大半径）へ落とす。

考え方は RAIM の Multiple Hypothesis Solution Separation に近いが、**適合は名乗らない。**

## 3. 受け入れ基準（辞書式・失格判定）

候補は加重平均で選ばない。**上から順に評価し、1つでも該当したら失格。**

1. **必須他艇警告の見逃しが baseline より 1 件でも増えたら失格。**
2. **最初の警告が baseline より遅れたら失格**（許容差は実装時に固定）。
3. **D/E ペアで 10m 超の相対誤差 excursion が増えたら失格**（現状 5 回 372 秒 → 目標 0）。
4. **filtered 相対誤差 p99 が raw の p99 を上回ったら失格。**
   「フィルタが生 GNSS より悪い瞬間を作らない」を不変条件にする。
   > 3・4 は codex の GPS 補正分析が提示した合格条件
   > （「補正後の p99 が生GPSより悪化しない」「補正後の 10m 超ずれが 0 回」）と一致する。
   > 独立に同じ結論へ到達したので、**この2つを推定器変更の中心的な合否基準として固定する。**
4-b. **停止時（<0.4 m/s）の along 方向オフセットが 5m を超えたら失格。**
   §1-2 の前方飛ばしを直接測る。現状 D med 5.56m / p99 25.24m。
5. **保護半径の被覆率が目標未満なら失格**（D/E ペアで検証。校正には使わない）。
6. **電池が baseline より悪化したら失格。**
   D は 61 分で 70%→15%（**54%/時**）。2 時間の朝練を完走できない端末が既にある。
   3 解並列はここを悪化させ得るので、**明示的に失格基準へ入れる**。
   Mac 上の CPU 値を電池の証明として扱わない（[RTA版] §13-5）。
7. 以上を満たした候補間で、**不要反復（EEMUA 191: 定常 6 回/時・上限 12 回/時）**、
   計算量、コードの複雑さを比較する。

### Release 3 — Fix Ingress の是正（**機能フラグ＋実験室検証**）

R1 を潰す。2 つの原因候補があり、**どちらも安全側なので切り分け後に両方入れてよい**。

**仮説α: 900ms ゲートが OS のまとめ配信を間引いている。**
`processPosition`（[use_navigator.dart:2582](../lib/hooks/use_navigator.dart)）は
**到着時刻**（`safetyClock.elapsed`）で判定する。iOS が複数 fix をまとめて配信すると
バッチの 2 つ目以降が 900ms 以内に到着して捨てられる。捨てられるのは**新しいほう**なので
rate が半減し遅延も増える。**間隔が 2.0s / 3.0s ちょうどに量子化されている事実と整合する。**

→ ゲートを **fix timestamp 基準**にし、まとめ配信では**最新 fix を採用**する（現状は逆）。
**Release 1 の `batch_delivery` 変換で、実機を待たずに検証できる。**

**仮説β: `distanceFilter: 0` が `kCLDistanceFilterNone` になっていない。**
`geolocator_apple 2.3.13` `LocationDistanceMapper.m`:

```objc
+(CLLocationDistance)toCLLocationDistance:(NSNumber *)value {
    if (!value) return kCLDistanceFilterNone;
    return value > 0 ? value.doubleValue : kCLDistanceFilterNone;   // value は NSNumber*
}
```

`value > 0` は **NSNumber ポインタの比較**で非 nil なら常に真。
`distanceFilter: 0`（`geo_service.dart:36`）は **0.0 のまま**渡る。
Apple は iOS 16.4 以降、継続配信に `kCLDistanceFilterNone` を要求している。
**同プラグインの一発取得の経路だけが `kCLDistanceFilterNone` をハードコードしている**
（`GeolocationHandler.m:83`）——**ポーリングが常に新しい fix を返した事実と一致する。**

→ iOS 経路を `distanceFilter: -1` にする（mapper はそのまま `-1.0` を返す）。
Android（`intervalDuration: 1s`）は変えない。
**mapper の挙動を単体テストで固定し、プラグイン更新時に再確認する。**

**併せて（[RTA版] B-1）**: 安全評価・位置共有・地図描画・診断を**同じ周期で間引かない**。
安全評価は単調に新しい妥当 fix を原則すべて処理する。間引くのは送信と描画だけ。

機能フラグ: `iosDistanceFilterNone` / `processAllMonotonicFixes` / `latestFixPerWindow`。

受け入れ:
- 測位間隔 med **1.0s**、`>2.5s` が **5% 未満**
- DR がセッション秒数の **5% 未満**（現在 A 14%・C 26%）
- §3 の失格判定を通過（特に 6. 電池）

### Release 4 — S2 を primary にする + RTA Fallback

**§2-1 の方針転換により、このリリースの主目的は「退避経路の用意」ではなく
「保守的な解へ既定を移す」ことになる。** Release 3 と並ぶ主要リリース。

[RTA版] Workstream C を、既定反転の形で実装する。

- **S2 Conservative（→ primary、集合値）**: §2-2 のとおり
  「代表点（表示用）+ `BoundedPositionSet`（安全判定用）」を出す。
  位置は生 fix + 外れ値ゲート、**前方外挿しない**。速度・方位のみ α-β で平滑化。
  fix が古い間は代表点を進めず**集合を前方カプセル状に広げる**（等方の円にしない。§2-2）。
  S1 と内部関数を共有しすぎない（座標変換などの純粋関数を除く）。共通原因で同時に壊れないため。
- **`BoundedPositionSet`**: 円 → 進行方向カプセル → 和集合の順で段階実装。
  静的危険区域との交差、他艇領域との交差を提供する。
  `ship_domain_service` / `swept_outline_service` の凸形状・掃引機構を流用する。
- **`predictedSet ∩ measurementSet = ∅` を integrity `indeterminate` として扱う。**
  **D/E の 32m 発散区間で継続的に発火することを回帰試験で確認する。**
- **状態機械に `ambiguous` を加える**（§2-3）。
  和集合は `plausible` な仮説だけ・短時間だけ・滞在上限つき。
- **不変条件7・8 の再定義**（CLAUDE.md）: `distanceMeters` の符号付き距離と
  `boundingRadius` の下限保証を、点ではなく集合に対して定義し直す。
  **集合化で「実寸を下回らない」の意味が変わるので、ここは明示的にテストを書く。**
- **S1 は shadow に降りる。** 計算と記録は続け、§3 の合否を毎回出す。
- **切替は機能フラグ**（`primarySolution = conservative | advanced`）で、
  実験室と実機の両方で比較できるようにする。
- **計算コストの上限を守る**（§3 基準 6）。集合は円とカプセルまで。
  zonotope は必要が実証されるまで入れない。
- **`PositionIntegrityMonitor`**: 解分離・fix 鮮度・NIS・共分散・連続棄却時間・集合の交差有無。
- **状態機械** `trusted → suspect → ambiguous → fallback → reacquiring`。
  **サンプル数ではなく経過時間**を条件にする（測位周期が変わっても意味が保たれる）。
- **解分離の判定**は固定距離ではなく、運動量と各解の不確かさで正規化（C-4）。
  参照合意の決め方 4 パターン（S1 だけ離れる / S0 だけ離れる / 全解が離れる / fix が古い）を実装する。
- **fallback 中も危険判定を止めない。** selected を raw か S2 に切り替え、
  静的危険物には拡大した絶対保護半径、他艇には通信遅延込みの到達可能領域。
  画面に「測位精度低下・目視優先」を表示。

**D/E ログが検出器の妥当性を先に証明している**: raw と filtered が 20〜32m 食い違った
372 秒は、S1 と S0 の分離を見るだけで全区間検出できる。**Release 4 の回帰試験にそのまま使う。**

### Release 5 — Advanced Estimator（S2 primary の内側で、昇格に挑む）

**S1 の目標は「S2 より良いこと」に変わった。** 中央値の改善だけでは昇格しない
（§3 の 3・4・4-b をすべて満たすこと）。

- **第一候補: 前方外挿の抑制 + 停止検出の独立化**（§1-2 への直接の答え。最小変更）。
  - 停止・減速判定時に速度状態を素早く落とす。
    現行 `velocityDecayTimeConstantSeconds = 8` は「艇は数秒では止まらない」ための
    意図的設計だが、**停止距離の確保と、位置を前へ飛ばすことは別物**である。
    **停止距離は速度状態からではなく保護集合・到達可能領域で表す**ことにして、
    位置の外挿からは切り離す。
  - fix age が閾値を超えたら位置の前進を止め、集合だけを広げる。
  - **横方向には元々ほぼ寄与していないので、ここを削っても岸・レーン判定は悪化しない**
    （§1-2 の 1）。これが安全に削れる根拠である。

  **停止検出を推定器の速度状態から切り離す（0-3c #3）。**
  現在は「フィルタの速度状態が停止を判定し、そのフィルタの速度状態が壊れている」
  という循環になっている。**判定の入力を推定器の外から取れば循環が切れる。**

  - 入力: 生 GNSS speed / 生位置の変位 / along 方向速度の連続低下 /
    innovation の符号と継続 / S1 と S0 の along 分離。
  - 単一閾値（`0.4 m/s` を1回下回ったら停止）ではなく、
    **弱い証拠を時間方向に蓄積**して `moving → decelerating → stopped → restarting` を決める。
  - CUSUM / 逐次尤度比は**保留**。多証拠の逐次蓄積で足りなければ次段で導入する。
  - Core Motion は**保留**（0-3c 参照。既存 IMU の available 率が 20〜44% しかない理由が先）。

  > **停止判定の権限を限定する（重要）。**
  > 「停止した」は**位置モデルを切り替える根拠にはなるが、他艇音声を消す根拠にはしない。**
  > これは Release 0 の regression の教訓そのものである。
  > §Release 2 の `SafetyContractMonitor` の契約として書き、
  > 停止検出の実装が提示ポリシーへ漏れ出さないことを機械検査する。
- **第二候補: `Q(dt)` の是正**。
  固定ゲートを直接広げる前に、プロセスノイズの dt 依存を確認する。
  併せて `minimumAccuracyMeters = 4` を実測から決め直す
  （C の報告値 2.0m を 4m へ切り上げている）。
  停止・定速・加速・旋回を別 fixture にし、全 dt で共分散の正定値性を検査する。
- **第三候補: Innovation-Adaptive**。適応係数に上下限と変化率制限、適応状態をログへ。
- **第四候補: 軽量 IMM**（Stop/Drift・Cruise・Maneuver）。
  innovation 増大時に観測を異常扱いせず M2 確率を上げる。
  **Stop/Drift モードは §1-2 への正攻法**でもある（停止を「モード」として認識すれば
  速度状態を素早く落とせる）。ただし複雑さの割に、第一候補で足りる可能性が高い。

**採用判断**: 前方外挿を抑えるだけで §3 の 3・4・4-b を満たすなら、それ以上やらない。
テールを改善しても**警告時刻を遅らせるなら不採用**（§3 の基準 2）。
IMM は明確な追加利益があるときだけ。**どの候補でも RTA Monitor と S2 は残す。**

**S1 が §3 に合格しない場合、S2 primary のまま出荷してよい。**
「Kalman を使うこと」自体は目的ではない。

### Release 6 — 保護半径と到達可能領域

**保護半径（[RTA版] E を縮小して採用）**

- **相対と絶対を分ける。** 同じ水域・同じ時刻の 2 受信機は誤差の共通成分
  （電離層・軌道・衛星時計）が相殺する（DGNSS が成立する原理）。
  今回それを実測した——**真値 1.5〜2m に対し raw 位置差 med 1.7m**。
  絶対精度 10m を 2 乗和する現在の式は**二重計上**である。
  - **静的危険区域**（絶対座標に固定）→ 絶対不確かさ。現行のままで正しい。
  - **他艇** → 相対保護半径 + 通信遅延分 + 解分離マージン。
- **D/E ペアは校正ではなく検証に使う**（0-2 の判断）。
  半径は物理と設計から決め、ペアで被覆率を確認する。層別フィッティングはしない。
- 飽和した定数（現行 2.5m 上限）をやめ、測位品質に応じて伸び縮みさせる。
- **`ProtectionBudget`（Release 2 で導入済み）の由来別内訳をここで使い切る。**
  合計半径ではなく構成要素で判断できるようにする——
  「通信遅延で広い」のか「自艇 GNSS が悪くて広い」のかで、表示も復旧手段も違う。

**到達可能領域（[RTA版] F）**

- 点予測から領域予測へ。**Release 4 の `BoundedPositionSet` をそのまま他艇へ広げる**
  （自艇と他艇で別実装にしない）。最初はカプセルか複数円でよい。
- **情報欠損時**: 相手速度不明 → 0m/s ではなく設定上限まで動ける領域。
  方位不明 → 全方向へ拡大。remote age 増加 → 到達距離を単調に増やす。
  共有 unavailable → 「他艇なし」と判定しない。**原則6の実装。**
- **`gps_guard_entry` の 1 バンド降格は、他艇についてのみ廃止し、到達可能領域で置き換える。**
  静的区域の降格は維持する（0-2 の判断）。
  **Release 0 と組で意味を持つ。** Release 0 なしに帯だけ締めると検知が減るだけになる。

### Release 7 — Alert Episode Manager と静音権限

- **エピソード**: `inactive → observing → announced → escalating → stable → cleared`。
  `episodeKey = hazardFamily + physicalTarget + causalContext`。
  同じ岸へ停止中に接近・離脱を繰り返す = 1 エピソード。
  十分離れて再接近 = 新エピソード。
- **音声規則**: 初回 1 回 / 悪化でエスカレーション / 不変は表示のみ / 改善・解除は無音 /
  再侵入は rearm 条件を満たしたときだけ。
  A で逆走が 1 エピソード平均 7.4 回読み上げられた問題は、回数上限ではなくこれで解く。
- **`SuppressionRule` の型付け**（G-4）:

```text
SuppressionRule {
  id, allowedCategories, forbiddenCategories,
  maximumSuppressibleUrgency, requiredKnownInputs,
  targetBehavior, reasonCode,
}
```

不変条件（型と全組み合わせゴールデンテストで強制）:
- `other_boat` は明示許可されない限り抑制不可
- 相手速度不明を静音の根拠にしない
- urgent は低速・桟橋・安定停止規則で抑制しない
- 下位カテゴリの規則が上位警告を上書きしない
- 集約前の個別危険を記録に残す

適用は「**権限を満たす規則の中で**最も静かなものを採る」に統一する
（Release 0 で見つけた `_quieter` と直接代入の混在を解消する）。

- **カテゴリ横断の集約**（IEC 62923 の aggregation）。個別警告が複数の集約警告を立てない。

### Release 8 — 位置共有の能力監視

- **能力を分解して持つ**（H-1）: publish setup / ACK 鮮度 / subscription 接続 /
  認可状態 / server time offset 鮮度 / 最後の受信 / 名簿取得可否。
  **「他艇がいない」と「受信できる状態を確認できない」を区別して表示する。**
- **再試行の原因別分類**（H-2）:

| 原因 | 再試行 |
| --- | --- |
| timeout / network unavailable | jitter 付き指数バックオフ |
| transient disconnect | 即時 1 回 → 指数バックオフ |
| **permission-denied** | **無限再試行しない。**認証・所属・Rules 原因として表示・記録 |
| invalid data contract | 再試行せず、互換性 fault |

  `publishingSetupUnavailable`（`use_navigator.dart:3232-3276`）は一度立つと
  **復帰経路がない**。degraded 起動を続ける方針は変えない（原則1）。**復帰経路を足すだけ。**
  今回 `ack_timeout` は A・D でも発生し、C は起動直後に `permission-denied` を 3 回出している。
  **起動直後の共有確立は全端末で不安定。**
- **表示のみ。音は足さない**（漕ぎながら対処できない情報を読み上げない）。
- **端末音量**: B/E は全期間 `outputVolume` **0.30 固定**（他 3 台は 1.00）。
  `audio_route_snapshot` で毎回取れているので、開始時と継続時に**画面へ**出す。

## 6. やらないこと

両案の「やらないこと」を統合する。

- **閾値を上げて警告を減らすこと。** 総量は R1・R2 の結果であり原因ではない。
  先に触ると、位置が直ったとき今度は警告漏れになる。
- **警告件数の固定上限だけを CI 合否にすること。** 辞書式の第 5 基準としてのみ使う。
- **`gps_guard_entry` の降格を静的区域まで含めて廃止すること。** 他艇に限定する。
- **水域データの引き直しを測位改善より先に行うこと。**
- **5 ログへの過適合を「一般的な安全保証」と呼ぶこと。**
  保護半径は「**2026-08-06 条件に対する経験的値**」と明記する。
- **平均誤差の改善だけで候補を採用すること。** テールが問題である。
- **高性能推定器を単独で本番の唯一解にすること。** RTA Monitor と S2 は常に残す。
- **「生GNSSだけで安全判定に十分」と結論すること。**
  §2-1 は「現行の強い補正より控えめな補正のほうが信頼できる」という限定的な主張である。
  端末報告精度は D med 3.6m / p90 8.4m、E med 4.8m / p90 8.6m。
  同一艇のペア比較では**両端末に共通する絶対誤差は検証できない**し、
  今回のログには**橋の下・樹木下・岸際が含まれていない**。速度・方位の平滑化も外さない。
- **停止距離の確保を、位置の前方外挿で代用すること。**
  停止距離は保護集合・到達可能領域で表す。位置を前へずらすのは別問題である（§1-2）。
- **保護集合を等方（円）だけで膨らませること。**
  川幅 40〜50m では、前方 12m のつもりの円が横 12m にもなり、
  §1-2 で直したはずの岸の過剰警告を別経路で復活させる。進行方向カプセルにする（§2-2）。
- **食い違う解を無条件に和集合すること。**
  壊れた S1 を抱き続けると安全集合が 30m 幅になり、常時どこかと重なる（§2-3）。
  `plausible` な仮説だけ・短時間だけ・滞在上限つき。
- **「停止した」ことを他艇音声の静音根拠にすること。**
  位置モデルの切替根拠にはなる。Release 0 の regression と同じ誤りを繰り返さない。
- **推定器の速度状態で停止を判定すること。**
  その速度状態自体が壊れている（循環）。判定入力は推定器の外から取る。
- **欠落・速度不明・共有 unavailable を安全の根拠にすること**（原則6）。
- **system fault に音を足すこと。** Release 8 はすべて表示のみ。
- **ローカル再生結果を、実機可聴性・水上安全性・電池の証明と呼ぶこと。**
- **新しい実機データがないことを理由に開発を止めること。**

## 7. 最初の作業単位

**意図的に小さく保つ。** 追加提案は強力だが、全部を先頭に積むと
**Release 0（今日直せる1条件）が埋もれる。** それが最悪の結果である。

1. **Release 0**: 他艇無音化 regression の単独修正（依存なし・即）
2. **Release 1 の最小版**: 欠落・バッチ・遅延・重複・逆順の 5 変換 + ペア突き合わせモード。
   **along/cross 分解と、停止時 along オフセット（§3 の 4-b）をレポート項目に含める。**
   \+ `CounterexampleReducer`（反例を最小 fixture へ縮める）
3. **Release 2 の Shadow**: FixEnvelope・disposition/NIS・S0/S1/S2 の解分離を記録のみ。
   \+ **`SafetyContractMonitor`**（timestamp 単調性 / 保護集合の単調拡大 /
   解分離後の遷移期限 / 他艇静音の禁止条件）
   \+ **`ProtectionBudget`**（由来別の内訳を記録するだけ。判定には使わない）
4. **`BoundedPositionSet` の最小版**（円のみ、Release 4 の下地）。
   停止中は前方成分がほぼ 0 なので、**円だけでも §1-2 の実害の大半に効く。**
   カプセルは Release 4 で足す。

この 4 つで、**実機を待たずに推定器候補を安全に比較する基盤**が完成する。
そのうえで **Release 3（Ingress: 測位を 1Hz へ）と Release 4（S2 を primary へ）**を
最優先で投入する。この2つが R1・R2 への直接の答えであり、
Release 5 以降（S1 の改良）は**それらが済んでから、余力で取り組む**位置づけになった。
