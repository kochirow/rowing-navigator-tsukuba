# 設計ブラッシュアップ提案

作成日: 2026-07-07
対象: Rowing Navigator 桜川版
方針: **運用費ゼロ(ストア登録料のみ)を維持したまま**、通信・電池・監視・ログ・コミュニケーションを根本から底上げする。

---

## 0. 現状の構造的なボトルネック

改修の前提として、現行設計には3つの構造的な問題がある。

**(1) Firestoreに1秒ごとに書き込む設計は、課金モデルと相性が最悪。**
Firestoreは「操作回数」で課金される。1秒1回の位置送信は、8艇×2時間の練習で書き込み57,600回。さらに全端末が全艇を購読しているので、読み取りは約52万回/練習に達する。無料枠(書き込み2万/日・読み取り5万/日)を1回の練習で10倍以上超える。**READMEに「インフラ乗り換えが課題」とある根本原因はここ。**

**(2) GPSを毎秒ポーリングしている。**
`getCurrentPosition()` を毎秒呼ぶ方式は、位置ストリーム購読(`getPositionStream`)よりも電池効率が悪く、GPSチップの省電力機構(バッチング)も効かない。

**(3) 画面常時点灯+最高精度GPS+毎秒通信の三重苦。**
電池消費の主犯は「画面」「GPS」「通信モデム」。現状は3つとも常時フル稼働している。

---

## 1. 柱1: データ通信と電池持ち

### 1-1. リアルタイム位置共有を Firestore → Realtime Database に移す【効果:特大】

Firebase Realtime Database (RTDB) は同じFirebaseプロジェクト内で使え、課金が「操作回数」ではなく「転送量」。位置メッセージは150バイト程度なので:

| | Firestore(現行) | RTDB(提案) |
|---|---|---|
| 課金単位 | 操作回数 | 転送量 |
| 8艇2h練習の負荷 | 書込5.8万+読取52万回 | 転送 約78MB |
| 月20練習 | 無料枠を大幅超過 | **約1.6GB(無料枠10GB/月に収まる)** |
| レイテンシ | 数百ms | より低い(常時接続) |

- `messages` コレクションだけRTDBの `/live_positions/{boatId}` に移す。危険区域(`static_obstacles`)は低頻度なのでFirestoreのまま。
- 実装は `message_api.dart` / `message_service.dart` の差し替えで済み、上位層(hooks)は無変更。`firebase_database` パッケージを追加するだけ。
- `onDisconnect()` で切断時に自艇データを自動削除でき、幽霊艇対策がサーバー側でも効く。

### 1-2. 適応送信(いつも1Hzで送らない)【効果:大】

「全員が常に1Hz」は無駄が多い。状況に応じて送信間隔を変える:

- **停止中(speed < 0.5m/s)**: 5秒間隔に落とす(整列待ち・休憩中の通信を1/5に)
- **周囲300m以内に他艇がいない**: 3秒間隔
- **他艇が近い/リスクレベル≥lv1**: 1秒間隔(現行どおり)
- 受信側は前回の位置+速度+針路から**推測航法(dead reckoning)で補間**するので、地図上の動きは滑らかなまま。補間ロジックは `predictPosition()` が既にあるのでほぼ再利用できる。

安全性への配慮: リスク評価は自艇のGPS(常に1Hz)と他艇の補間位置で毎秒行うので、警告の応答性は落ちない。

### 1-3. GPSポーリング → ストリーム購読【効果:中】

`useNavigator` の毎秒 `getCurrentPosition()` を `getPositionStream()` 購読に変更。`geo_service.dart` にストリームは実装済みで未使用。電池効率が上がり、取得失敗時の欠落も減る。

### 1-4. 画面まわり【効果:中〜大、段階導入】

- **すぐ**: ナビ中は地図の描画負荷を下げる(航跡・船舶領域ポリゴンの描画を設定でオフ可能に)、ダークマップ切替
- **将来**: 「音声のみ航行モード」— バックグラウンド位置取得(geolocatorが対応)+音声警告のみで画面オフ運用。漕手は画面を見られないのだから、**画面は本来コーチ用**という割り切り。電池持ちが最も伸びる施策。

## 2. 柱2: 練習の監視(コーチモード)

観察者モード(observer)は既にあるので、これを「コーチダッシュボード」に育てる。

- **艇一覧パネル**: 全艇の艇種・速度・最終更新・**電池残量**(メッセージに1フィールド追加するだけ)を一覧表示。地図を見なくても異常が分かる。
- **航跡表示**: 各艇の直近N分の軌跡をポリラインで表示。誰がどのコースを通ったか一目で分かる。
- **異常の自動検知(監視の核心)**:
  - 一定時間(例3分)動いていない艇 → 「○○艇が停止しています」
  - 練習水域(ジオフェンス=危険区域と同じポリゴン形式で定義)から出た艇 → 通知
  - 更新が途絶えた艇(電池切れ/アプリ落ち) → 通知
- **陸上監視Webページ**: Firebase Hosting(無料)+Leaflet(無料の地図JS)でRTDBを読むだけの閲覧専用ページを作れば、**アプリを入れていない保護者・OBもブラウザで見られる**。読み取り専用なのでセキュリティルールで安全に公開範囲を制御できる。

## 3. 柱3: 練習ログ(Strava的な記録機能)

CSV記録の下地(recordData)は既にあるので、構造化して「見える化」する。

- **セッション記録の構造化**: 練習ごとに「軌跡(緯度経度+時刻)+イベント(警告発生など)」をローカルDB(sqlite)に保存。**サーバー不要=費用ゼロ**。
- **自動サマリー**: 距離、総時間、最高速度、平均ペース(/500m)、500mごとのスプリット、警告回数。
- **レート(SPM)の計測**: 端末の加速度センサ(`sensors_plus`、無料)で艇の前後加速の周期を拾い、ピーク検出でストロークレートを算出。CrewNerd等の市販アプリと同じ原理で、艇に固定された端末なら十分実用になる。
- **自動ピース検出**: 速度プロファイルから「一定速度以上が続いた区間」を自動で切り出し、区間ごとのタイム・レートを表示。「今日の2000m×3本」が勝手にログになる。
- **GPX/CSVエクスポート**: GPX形式で出力できれば**Stravaにそのまま手動アップロード可能**(無料)。共有は既存のshare_plusを流用。Strava API連携(自動アップロード)も無料だが、まず手動で十分。
- **航跡リプレイ**: 記録一覧画面から地図上で再生。事故・ヒヤリハットの振り返りにも使える。

## 4. 柱4: 水上コミュニケーション(Buddycomの将来統合)

音声通話をゼロから作るのは費用・複雑さともに重い(WebRTCはTURNサーバー代がかかり得る)。段階的に攻める:

- **Phase 1(すぐ・費用ゼロ): クイックシグナル+読み上げ**
  コーチ画面に定型ボタン(「集合」「戻れ」「スタート」「注意」など)を置き、RTDB経由で送信。受信した艇の端末が**TTS(flutter_tts、無料・オフライン動作)で自動読み上げ**する。宛先は全艇/特定艇を選択可。トランシーバーの用途の大半(コーチ→艇の一方向指示)はこれで置き換えられる。
- **同時に: 警告のTTS化**
  現在のビープ音に加えて「右前方、他艇接近」「前方、危険区域」のように**方向+種別を音声で読み上げ**る。警告の質が一段上がる(実装は既存のuseAlertにflutter_ttsを足すだけ)。
- **Phase 3(検証してから): 音声PTT**
  flutter_webrtc + Google公開STUNで艇同士のP2P音声を実験。キャリア回線のNAT越え成功率を現地で検証し、TURNが必要ならその時点でコスト(月数百円のVPS)と相談。**それまではBuddycom併用が最も合理的**。無理に統合しない判断も「地に足」のうち。

## 7. リスクと検証方法

- **RTDB移行**: メッセージ形式は現行と同一にし、旧Firestore実装をフラグで残して切り戻し可能にする。陸上2台→実艇の順で検証。
- **適応送信**: 補間表示のズレが警告に影響しないか、2台で接近試験をしてから展開。
- **レート計測**: 端末の固定方法で精度が変わるため、まず1艇で市販アプリ(またはコーチの目視カウント)と突き合わせて校正する。
- **電池関連**: 施策ごとにビフォーアフターを実測(2時間練習で残量%を記録)して効果を数値で確認する。
