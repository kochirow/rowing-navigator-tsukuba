# 警告システム実装前シミュレーション・補強仕様

- 作成日: 2026-07-15
- 対象: `rowing-navigator-tsukuba` 公開初版
- 位置づけ: [警告システム包括再設計](./2026-07-14_警告システム包括再設計.md) の必須補強仕様
- 状態: 連続衝突判定を含め、実装時に必ず適用する規範仕様
- 公開方針: 単一release candidateへ実装し、一括テストで合否判定
- 2026-07-15方針更新: `operationalCoveragePolygon`は航行を制限する境界にしない。未設定・範囲外でも航行と既知の警告を継続し、検証状態だけを表示する
- 2026-07-16方針更新: コーチ指示はトランシーバーへ一本化し、クイックシグナルの送受信・表示・RTDBデータをアプリから削除する

## 0. 適用規則

本書は、包括再設計をそのまま実装した場合に起こり得る問題を、イベント時系列と故障注入で事前シミュレーションし、追加で必要になった仕様を定める。

包括再設計と本書が競合する場合は、本書を優先する。本書に記載のないカテゴリ固有の物理判定は包括再設計と[他艇接近アラート再設計](./2026-07-14_他艇接近アラート再設計.md)に従う。

このシミュレーションは未実装コードの実行結果ではない。状態遷移、非同期処理、OS停止、通信順序、データ品質を入力として行ったモデルベースの事前検証である。したがって、本書で解決した設計問題とは別に、実装後の自動・実機・実地試験も必要である。

## 1. 結論

包括再設計の方向性は妥当だが、そのまま実装すると次の問題が生じ得る。

1. GPS喪失時に、まだ目前の物理危険が残っているのにP2へ音声を切り替えてしまう
2. GPS callback、通信送信、評価が重なると、古い処理結果が新しい警告を上書きする
3. watchdogを安全パイプラインと同じDart isolateで動かすと、isolate停止中は検知できない
4. start／stop／画面disposeが競合し、停止後に古い非同期処理が警告や共有を復活させる
5. 他艇メッセージの順序・セッションを識別できず、古い位置が新しい位置を上書きする
6. アプリ利用艇しか検出できないのに「安全」と表示し、全艇を見張っているような誤解を作る
7. 桜川用危険区域を対応水域外で使うと、障害物がないことを安全と誤認する
8. GPS不確実性と旧危険区域の安全余裕を重複加算し、警告が常時鳴る
9. 開始時点ですでに案内区域内にいると、進入イベントが発生せず案内されない
10. 音声割込復帰と警告切替が競合し、解除済み音声が復活する
11. ログ、入力件数、予測反復に上限がない箇所が残ると、処理遅延が安全判定を止める

対策の中心は、**単一writerのSafetyOrchestrator、世代付きの不変SafetySnapshot、セッション／sequence付き通信、能力別の運用モード、物理危険とデータ喪失の並存**である。

## 2. シミュレーションモデル

### 2.1. 入力イベント

次のイベントを任意順序・任意遅延で発生させた。

- GPS fix受信、棄却、長時間停止、回復
- 他艇位置受信、順序逆転、重複、stale、セッション切替
- 静的危険区域内外への移動
- 複数警告の同時開始・解除
- 音声開始、完了、割込、経路変更、再生失敗
- ネットワーク送信遅延、切断、復帰、cached snapshot
- 航行start、stop、画面再構築、background、process kill
- プロファイル不一致、対応水域外、設定変更
- ログ遅延、入力過多、不正データ

### 2.2. 評価観点

各シナリオで次を確認した。

- 見逃しが生じないか
- 古い状態が新しい状態を上書きしないか
- 誤警告がループし続けないか
- 「警告なし」と「判定不能」が混ざらないか
- 音、表示、振動が同じ状態を示すか
- 一つの失敗が他検出器を止めないか
- process／画面／通信の寿命差を扱えるか
- 利用者へ能力の限界が正しく伝わるか

## 3. 発見事項の優先順位

| 優先度 | 問題 | 未対策時の結果 |
|---|---|---|
| P0 | 非同期評価の順序逆転 | 解除済み警告の復活、危険警告の上書き |
| P0 | GPS喪失で物理危険をP2へ置換 | 衝突直前に対象警告が弱まる |
| P0 | 同一isolate watchdogの限界 | アプリが固まった瞬間に無音死を検出できない |
| P0 | 対応水域外で「警告なし」 | 未登録危険物を安全と誤認 |
| P0 | 非アプリ艇を検出できない事実の非表示 | 全艇検知という誤安心 |
| P0 | start／stop／dispose競合 | 停止後に共有・音声・timerが復活 |
| P0 | 他艇データの順序・session欠落 | 過去位置への巻き戻り、幽霊艇 |
| P1 | 音声指令の非同期競合 | 古い音声の復活、ループ中断 |

| P1 | 開始時すでに区域内 | 案内漏れ |
| P1 | 不確実性の二重加算 | 常時警告と警告疲れ |
| P1 | protocol version混在 | 艇ごとに異なる意味で位置を評価 |
| P1 | 入力・ログの無制限化 | event loop遅延、電池・容量圧迫 |
| P2 | セッション中の設定変更 | 同じ航行内で警告境界が変わる |

## 4. 時系列シミュレーション

### S01. 他艇衝突8秒前に自己GPSが止まる

```text
t=0  他艇とのactionDeadline=8秒、他艇警告active
t=1  自己GPS更新停止、GPS faultもactive
t=5  旧仕様のlost猶予5秒が終了
t=5  個別警告を止めてGPS fault音へ切替
t=8  最後の予測上は衝突時刻
```

問題: t=5でP0の物理危険をP2へ置換すると、まだ3秒残る他艇危険の音が弱まる。

必須対応:

- 物理危険とGPS faultを同時activeで保持する
- 個別危険の音声保持時間を次で決める

```text
hazardHoldSeconds = clamp(lastActionDeadlineSeconds + 3, 5, 12)
```

- `lastActionDeadline`が不明なら5秒
- 保持時間中は個別危険音を主音声とし、GPS faultは固定表示と開始時振動で併記
- 保持終了後も安全解除せず、GPS fault音へ移り、最後の危険対象を30秒または回復まで画面に残す
- 新しいGPSがない状態で新規の幾何学的安全判定を作らない

### S02. 岸境界でGPSが毎秒内外へ揺れる

```text
inside -> outside -> inside -> outside ...
```

問題: サンプル数だけで開始・解除すると、評価周期の揺れやscheduler遅延で音声が断続する。

必須対応:

- sample countではなく単調時刻の継続時間で判定する
- 通常開始は条件継続1秒以上かつ、時刻が増加する異なる観測2件
- 現在重なり、またはactionDeadline 2秒以下は即時開始
- 解除は安全条件3秒以上、異なる観測3件、退出余裕をすべて満たす
- `clearing`中も行動警告音を継続する
- GPS quality自体にも別のヒステリシスを持たせる

### S03. 位置送信が2秒停止し、次のGPS callbackが先に完了する

```text
revision 100: GPS A -> battery取得・send待ち
revision 101: GPS B -> 評価完了、危険active
revision 100: send完了後に評価を続行、古いsafeで上書き
```

現行`processPosition()`は送信をawaitしてから評価し、stream callbackはasyncであるため、この種類の順序逆転が起こり得る。

必須対応:

- 安全状態の更新は単一の`SafetyOrchestrator`だけが行う
- GPS評価、FSM、調停を単一writerの直列処理にする
- 通信送信、battery取得、ログ書出しを安全評価の前にawaitしない
- 各入力と結果へ`sessionGeneration`と`revision`を付ける
- UI、音声、共有は現在revisionより古い結果を無視する
- GPS入力が過剰な場合は未処理GPSだけ最新値へcoalesceし、stop、fault、audio eventは捨てない

### S04. start処理中にstopまたは画面dispose

```text
idle -> starting
権限確認中にstop
古いstartが後から完了
位置streamと音声が再登録される
```

必須対応:

```text
idle -> preflight -> starting -> runningFull/runningDegraded -> stopping -> idle
```

- startごとに新しい`sessionGeneration`を作る
- stop開始時にgenerationを増加させ、古いcallbackを全て無効化する
- start／stopは冪等にする
- `stopping`中は新規startを受け付けない
- stop順序は「generation無効化 -> audio停止 -> 入力購読解除 -> server削除試行 -> ログ確定」
- server削除失敗でもUIをrunningへ戻さず、onDisconnectとTTLへ委ねる

### S05. 他艇メッセージが順序逆転する

```text
sequence 51を受信
ネットワーク復旧後にsequence 49を受信
```

boatIdと端末timestampだけでは、49が古いと確実に判断できない。

必須対応:

- 航行開始ごとにUUID `sessionId`を生成
- 送信ごとに単調増加`sequence`を付ける
- `(boatId, sessionId)`内で最大sequenceだけを採用する
- 新sessionId受信時は旧sessionのtrackとFSMを閉じる
- 遅れて届いた旧sessionは無視する
- stream復帰時は履歴を順番に再生せず、艇ごとの最新有効snapshotだけを評価する

### S06. 同じboatIdを二端末が使用する

問題: RTDBの`child(boatId).set()`では、二端末が互いを上書きする。

必須対応:

- DB pathと書込権限を認証UID、boatId、sessionIdへ結び付ける
- 同じboatIdの同時active sessionをサーバールールまたはsession registryで拒否する
- 競合を検出した端末は共有を停止し、`BOAT_ID_CONFLICT`を表示する
- boatId競合時に一方を黙って正としない

### S07. 古いアプリと新しいアプリが混在する

問題: sessionId、sequence、accuracy semanticsが異なるデータを同じ品質で扱うと、相手位置の鮮度を誤る。

必須対応:

- `protocolVersion`と`capabilities`を送信する
- 公開初版の最低互換version未満は、完全な他艇trackとして使用しない
- 非互換艇は地図上に「互換性不明」と表示し、他艇検出能力を`degraded`にする
- 同一練習では全艇のapp/protocol/profile version一致をコーチ画面で確認する

### S08. アプリを使っていない艇が近づく

問題: アルゴリズムが正常でも、その艇のデータは存在しない。「安全」は誤表示になる。

必須対応:

- 利用者向けの`安全`表示を廃止する
- 正常時表示を次へ変更する

```text
現在警告なし
アプリで共有中の艇のみ検出
周囲を目視確認してください
```

- 内部enum名も可能なら`safe`から`noActiveAlert`へ変更する
- コーチ艇、一般艇、データ未送信艇を検出できないことを開始前と航行中に表示する

### S09. 桜川以外で航行開始する

問題: 登録障害物がないため「警告なし」になり、未登録水域を安全と誤認する。

必須対応:

- 危険区域プロファイルには、確認できた場合だけ検証済み`operationalCoveragePolygon`を持たせる
- 自艇がcoverage外またはcoverage未設定でも、航行開始・航行継続・既知の危険区域警告・他艇警告を制限しない
- coverage外では`runningDegraded`とし、UIへ「この位置の固定危険区域は未検証です。通常の目視確認を継続してください」と無音で固定表示する
- coverage未設定のRelease版では`runningDegraded`とし、UIへ「固定危険区域の網羅範囲は未検証です。警告は継続します」と無音で固定表示する
- coverageはコーチ水域外判定用practice areaと別データにする
- coverageは警告データの検証状況を伝えるための補助情報であり、行動許可、航行禁止、警告停止の根拠には使わない

### S10. ネットワークがない状態で航行開始

一律blockすると岸警告まで使えない。一律許可すると他艇警告が動いているように見える。

必須対応:

| mode | 必須能力 | 表示 |
|---|---|---|
| `runningFull` | GPS、audio、profile、検証済みcoverage内、dynamic receive、share send | 利用者向けに「完全安全」とは表示せず、各能力を個別表示 |
| `runningDegraded` | GPS、audio、profile | coverage未設定・範囲外、または利用不能な通信能力だけを個別に固定表示 |

- GPS、audio、profile不成立はhard blocker。coverage不成立はhard blockerにしない
- dynamic receiveまたはshare sendだけが不成立なら、開始前に`runningDegraded`を明示選択できる
- dynamic receive可・share send不可なら、他艇受信警告は継続しつつ「他艇から自艇が見えません」と表示する
- dynamic receive不可・share send可なら、自艇共有は継続しつつ「他艇を受信できません」と表示する
- 航行中に通信能力が失われても停止を強制せず、`runningDegraded`へ遷移して能力別に周期通知する
- 通信回復は受信接続だけでなく、自艇送信成功と新鮮なsnapshotを確認してから`runningFull`へ戻す

### S11. 開始時点ですでにカーブ区域内

問題: outside -> insideのedgeがなく、entry guidanceが鳴らない。

必須対応:

- preflight完了後の最初の信頼位置で区域内ならsynthetic entryを1回生成する
- hard obstacle内ならdebounceなしで行動警告を開始する
- guidance区域内なら1回案内し、同じsession中は退出・再武装まで繰り返さない
- 短いGPS喪失からの復帰ではzone membershipを保持する
- process再起動後は安全上、区域内なら再度1回案内してよい

### S12. 二件の警告が同じ音声ファイルを使う

```text
boat A active -> add_warning.mp3
boat B active -> add_warning.mp3
boat A clear、boat B active
```

問題: Aのclear handlerがplayerをstopすると、Bの警告まで止まる。

必須対応:

- 各alertがplay／stopを直接呼ばない
- `AlertArbitrator`が全active集合から一つの`AudioDirective`を毎revision生成する
- directiveは`asset、mode、ownerAlertIds、revision`を持つ
- ownerが変わってもassetとmodeが同じなら再スタートしない
- stopは「最新directiveに音声要求がない」ときだけ行う

### S13. 電話・Bluetooth切替中に警告が変わる

問題: 割込前の非同期resumeが、割込中に解除された古い音声を復活させる。

必須対応:

- `AudioCoordinator`は直列command queueとgenerationを持つ
- audio focus interruption中は再生を連打せず、表示・振動を維持する
- interruption終了時に古い要求ではなく最新`AudioDirective`を再照合する
- route change後も最新directiveだけを再適用する
- OSが再生を拒否した状態を「再生中」とみなさない
- 通常のOS interruption中は失敗回数へ数えず、interruption終了後に3回連続再生失敗または5秒復旧不能で`AUDIO_PATH_UNAVAILABLE`

### S14. main Dart isolateが固まる

問題: 同じisolateの`Timer.periodic` watchdogも止まり、停止中には警告できない。

必須対応:

- アプリ内watchdogの保証範囲を「event loopが再開した後のgap検出」と明記する
- `Timer.periodic`の回数ではなく単調時刻の差を使う
- process／isolate停止の一次検出はサーバーheartbeatとコーチ側lost判定にする
- Android継続通知は、実機で判定継続を確認するまで「位置共有と衝突警告が継続」と断定せず、「航行セッション実行中」とする
- background／lock試験で10秒以上の無告知停止が1件でもあれば公開しない
- 将来、独立native layerまたは別isolateで監視しない限り、端末内の完全な無音死検出を保証しない

### S15. GPS回復用の3fixがcached／重複

必須対応:

- 回復fixは測位timestampが厳密に増加すること
- 3fixが2秒以上の実時間幅を持つこと
- 緯度経度、accuracy、timestamp、speed、courseの有限性を検証し、accuracyは0より大きいこと
- 同じ座標でもtimestampが新しく、静止として整合する場合だけ有効とする
- speedが欠落または負なら、直近二つの採用fixの距離を経過秒で割って求める。距離そのものをspeedとして使わない
- courseが無効または低速で不安定なら、端末compassで補わず`unknown`にする
- mock／simulated locationはproductionで`unusable`とし、専用test buildだけ許可する

### S16. GPSがdegradedからunusableへ悪化

問題: 不確実性を拡大し続けると、全障害物へ同時警告した後、急にGPS faultだけになる。

必須対応:

- `good`: 通常の幾何学評価
- `degraded`: 予測時間短縮と不確実性拡大。ただし不確実性だけでP0へ上げない
- `unusable`: 新規幾何学警告を生成しない。既存activeだけS01のhold規則で保持
- GPS quality遷移にも開始・回復ヒステリシスを持たせる
- GPS不確実性が運用上限を超えたら巨大marginで全警告せず`unusable`へ移す

### S17. 旧危険区域の余裕とGPS marginを重ねる

必須対応:

各形状へ次を持たせる。

```text
geometryIncludesSafetyMargin: true/false
geometryUncertaintyMeters
responseMarginMeters
```

静的障害物の追加margin:

```text
effectiveMargin = hullRadius
                + gpsUncertainty
                + geometryUncertainty
                + (geometryIncludesSafetyMargin ? 0 : responseMargin)
```

- legacy基準線から生成した区域には、生成時の左右offsetを再加算しない
- `defaultObstacleProximityCautionMeters=0`の意味を維持する
- GPSがunusableになる値までmarginを無制限拡大しない

他艇の相対margin:

```text
relativeMargin = ownHullRadius + targetHullRadius
               + ownGpsUncertainty + targetGpsUncertainty
               + targetAgeGrowth
```

相関を仮定して係数を恣意的に小さくせず、一括試験の誤警告結果から変更する。

### S18. セッション中に警告時間スライダーを変更

問題: 走行中に判定境界が突然変わり、状態機械の継続性が壊れる。

必須対応:

- `SessionConfig`をstart時に不変snapshotとして固定する
- boat type、seat、warning max、profile version、protocol version、feature flagsを含める
- 設定変更は次回sessionから適用する
- user maxが25秒でも、実効予測時間はdata qualityが許す値との最小値にする
- 実効値をログへ残す

### S20. 不正なremote targetが大量に届く

必須対応:

- Firebase Rulesで認証、型、範囲、文字列長を検証する
- クライアントでもNaN、Infinity、座標、時刻、accuracy、speed、sequenceを再検証する
- 不正boat typeを小さい`1x`へ黙って変換しない。最大対応艇相当の保守的domainで`degraded`表示するか、protocol不正として隔離する
- remote target数の公開初版上限を100件とする
- 上限超過は黙って切り捨てず、近傍100件を評価し`TARGET_CAPACITY_EXCEEDED`を表示する
- ポリゴン点数、予測step、文字列長、ログqueueにも上限を持たせる

### S21. ログ保存が遅い／端末容量がない

必須対応:

- ログ書出しを安全評価でawaitしない
- memory queue上限を1000 event、1sessionファイル上限を10MBとする初期値を採用
- 上限時は古いdiagnostic eventを先に落とし、警告状態遷移とfaultを優先する
- ログ失敗は`LOGGING_DEGRADED`とするが、行動警告を止めない
- 位置履歴保持量と削除方針をプライバシー説明へ含める

### S22. process kill後にサーバーへ幽霊艇が残る

必須対応:

- `onDisconnect`を維持する
- server timestampとTTLを必須にする
- session heartbeatが期限を超えた艇をactive targetから外す
- active警告中に途絶した艇は、即削除せずS01のholdを適用する
- 同じboatIdの新session受信時に旧sessionを即閉じる

### S23. UIと音声が異なるrevisionを表示する

必須対応:

```dart
class SafetySnapshot {
  String sessionId;
  int sessionGeneration;
  int revision;
  MonotonicTime evaluatedAt;
  RunMode runMode; // runningFull / runningDegraded等
  CapabilitySnapshot capabilities;
  List<ActiveAlert> activeAlerts;
  DetectorHealthSnapshot health;
  AudioDirective? audioDirective;
  VisualDirective visualDirective;
}
```

- snapshotは不変オブジェクトとして一括発行する
- UI、audio、haptic、loggerは同じrevisionを受け取る
- 各consumerは現在値より古いrevisionを無視する
- 一部フィールドだけ先に公開しない

### S24. 未検証端末でbackgroundが停止する

問題: 公開ストアでは端末・OS・省電力設定が多様で、一回の実機合格を全端末へ一般化できない。

必須対応:

- 公開前に検証した端末、OS、電池最適化設定を記録する
- minimum OSと必要権限を明示する
- 未検証端末でも動作保証と表示しない
- preflightでbackground権限・音声・位置更新を確認する
- 航行開始後、最初のbackground移行から復帰した際にgapを表示する
- target端末群のどれかで無告知停止が再現した場合、常時画面ON運用へ明示的に制限するか公開を止める

### S25. 予測終点が危険を通過し、近づくほど警告が消える

問題: `n` 秒後の一点だけを判定すると、現在位置と予測終点の間にある危険区域や他艇との接触時刻を飛び越す。これは離散衝突判定の tunneling に相当する。

現行実装は一点判定ではない。現在から予測範囲までを相対移動量およそ2mごとに同期評価し、高速8+が微速1xを横切る回帰テストも持つ。このため直進・一定速度・正常な形状では、利用者が懸念した見逃しを既に大きく抑えている。ただし、2mという経験的刻みは連続時間の保証ではなく、旋回、細い形状、数値誤差、GPSジャンプでは判定根拠が弱い。

時系列シミュレーション:

| ケース | 終点だけの判定 | 2m離散判定 | 必須の連続判定 |
|---|---|---|---|
| 自艇0m、4m/s、5秒先20m、危険帯9〜11m | 20mが安全なので見逃す | 通常は検知 | `[0,5]`秒の最初の侵入時刻を検知 |
| 2艇の航跡が同じ場所で交差するが到着時刻が違う | 実装次第 | 同期時刻なら除外可能 | 相対位置が同時刻に合成領域へ入らないので除外 |
| 平行な航跡で後艇が追いつく | 線同士が交差せず見逃す | 同期サンプルが合えば検知 | 相対運動区間が合成領域へ入るので検知 |
| GPSが一度に20m跳ね、危険帯の反対側へ見える | 通過済みと誤認 | サンプル生成方法により誤認 | raw fix間を実航跡として掃かず、fixを棄却・degraded化 |

必須対応:

1. 物理警告は予測終点ではなく、閉区間 `[0, effectiveHorizon]` 全体で判定する。
2. 戻り値に `firstEntryTime`、`firstEntryDistance`、`minimumSeparation`、`currentOverlap` を持たせる。現在重なっていれば `firstEntryTime=0` とする。
3. 静的危険はゼロ幅の延長線ではなく、自艇の排他領域と上限付きGPS補助帯を予測経路に沿って掃いた `swept domain` で判定する。GPS accuracy全量を左右それぞれへ加えない。
4. 他艇は2本の地理的延長線の交差を条件にしない。同じ将来時刻の相対位置区間と、双方の船体安全領域を合成した領域の連続交差を判定する。
5. `firstEntryTime` が予測窓内にある限り、予測終点が危険の先へ出ても候補を消さない。
6. 解除は「予測終点が安全」ではなく、現在非接触、予測区間全体に侵入なし、退出余裕、離反傾向、有効データが3秒継続した場合だけ許す。
7. raw GPS fix同士を無条件に直線で結ばない。物理的に不可能なジャンプは`GpsPositionFilter`で棄却し、直前のactive警告とGPS faultを並存させる。
8. 5〜25秒の利用者設定は予測窓・警告開始感度へだけ使い、衝突判定の刻み幅や連続性を変えない。

## 5. 補強後の規範アーキテクチャ

### 5.1. 単一writer

安全状態を書き換えられるのは`SafetyOrchestrator`だけとする。

```text
Input adapters
  -> bounded event mailbox
  -> SafetyOrchestrator(single writer)
  -> immutable SafetySnapshot(revisioned)
  -> Audio / Visual / Haptic / Logger consumers
```

禁止事項:

- evaluatorから音声playerを直接操作する
- network send完了を待ってから安全評価する
- widgetの複数effectが同じ警告状態を書き換える
- alert個別のclear handlerが音声をstopする
- 古いFuture完了時に現在snapshotを上書きする

### 5.2. event mailbox

| event | coalesce | 優先 |
|---|---|---|
| GPS fix | 未処理分は最新1件へ集約可 | 高 |
| stop／dispose | 集約不可 | 最優先 |
| audio interruption | 集約不可 | 高 |
| system fault | 同一keyは最新化 | 高 |
| remote snapshot | 艇ごとの最新sequenceへ集約 | 通常 |
| battery／diagnostic | 最新化可 | 低 |

mailboxが上限へ達した場合、診断・battery・古いGPSから落とし、stopとfaultを残す。drop数をhealthへ反映する。

### 5.3. alert comparator

配列順へ依存しない決定順を固定する。

```text
1. behavior band
2. current physical overlap (trueが先)
3. normalized actionDeadline (短い方)
4. data quality
5. current primary lock
6. stable alertId lexical order (最終tie breaker)
```

- `actionDeadline=null`は無限大として扱い、P0へ暗黙昇格させない
- current overlapはdeadline=0
- primary lockは2秒の優先余裕内だけ維持し、それ以上緊急な新対象を妨げない
- comparatorは全候補順列で結果が同じことをproperty testする

### 5.4. stable ID

```text
alertId = detectorId / category / targetStableId / targetSessionId
```

- 静的障害物はprofile version内のstable ID
- 他艇はboatIdだけでなくtarget sessionIdを含める
- システムfaultはfault typeと現在sessionを含める
- 表示文言、配列index、audio file名からIDを作らない

### 5.5. capability snapshot

```text
gpsUsable
staticProfileUsable
insideSupportedCoverage
audioUsable
dynamicReceiveUsable
positionShareUsable
pipelineResponsive
```

`noActiveAlert`とcapabilityを一つのbooleanへまとめない。UIは能力ごとに表示する。

### 5.6. 座標・単位規約

- 緯度経度はWGS84
- 距離はmeter、速度はmeter/second、時間はsecond
- courseは真北0度、時計回り0〜360度
- 局所計算は共有したENU座標系
- GPS courseと地図camera bearingを混同しない
- 端末compassの磁北方位を物理予測へ混ぜない
- 音声・UIの左右を将来追加する場合は艇首基準の右舷／左舷

### 5.7. 予測区間の連続衝突判定

全ての物理検出器は、`positionAt(horizon)` の一点判定を禁止し、予測経路の各時間区間を連続評価する。離散予測点はデバッグ表示と回帰比較には残してよいが、安全判定の唯一の根拠にはしない。

共通出力:

```text
ContinuousIntersection
  intersects
  currentOverlap
  firstEntryTimeSeconds
  firstExitTimeSeconds
  minimumSeparationMeters
  confidence
  reasonCodes[]
```

#### 5.7.1. 静的危険区域・岸

1. WGS84座標を自艇近傍の共有ENU座標へ変換する。
2. 空間インデックスで、予測経路と最大安全余裕の外側にある区域を除外する。
3. 直進区間では、自艇の排他領域`D`と障害物`O`について、基準点の線分が `O + (-D)` へ入る最初の線分パラメータを求める。これは、自艇領域を線分に沿って掃いた形状と障害物の交差と同値である。
4. 凹ポリゴンは検証済みの三角形分割または凸分割後に評価し、全要素の最小`firstEntryTime`を採用する。
5. GPS accuracyは「全幅へ加える補助帯」として次で計算する。ポリゴンの左右へ加える実装値は、この半分である。

```text
staticGpsGuardFullWidth = clamp(accuracy * 0.25, 0, 2.0m)
domainInflatePerSide    = staticGpsGuardFullWidth / 2
```

6. 旧アプリ由来区域など、形状自体に安全余裕が埋め込まれている区域は`staticGpsGuardFullWidth=0`とする。GPS・区域形状・旧余裕を重複加算しない。
7. GPS accuracyが悪化しても2mを超えて帯を広げない。データ経過、方位不明、旋回誤差は帯幅へ加算せず、予測窓短縮と`dataDegraded`で扱う。
8. 旋回区間は長い直線として扱わず、向きを保った排他領域を短いpiecewise区間ごとに掃引する。艇の全長を半径とする外接円capsuleはbroad phaseに限り、接触だけで行動警告を開始しない。分割できない場合は予測窓を短縮して`dataDegraded`を返す。

#### 5.7.2. 他艇

直進・一定速度を仮定できる区間では、同期時刻の相対運動を使う。

```text
r(t) = (pOther - pOwn) + (vOther - vOwn) * t
pairAccuracy = sqrt(ownAccuracy^2 + otherAccuracy^2)
gpsCenterDistanceGuard = clamp(pairAccuracy * 0.125, 0, 1.5m)
baseLateralCenterDistance = ownExclusiveWidth / 2 + otherExclusiveWidth / 2
alertLateralCenterDistance = baseLateralCenterDistance + gpsCenterDistanceGuard
C = ownDomain + (-otherDomain) + gpsCenterDistanceGuard

collision exists
  iff r([0, effectiveHorizon]) intersects C
```

- `C`は双方の向きと艇種を反映した合成安全領域である。
- GPS補正は2艇の中心間距離しきい値へ一度だけ加える。双方の領域へ同じ値を個別加算しない。
- 1x同士では基本中心間距離は`4.5m + 4.5m = 9m`。双方accuracy 5mなら補正は約0.9mなので、横方向の中心間距離約9.9m以内が候補となる。
- 最初に`r(t)`が`C`へ入る時刻を`firstEntryTime`とする。
- CPA/TCPAは粗判定、順位付け、説明値として残すが、最終衝突判定をCPA一点だけへ依存させない。
- 絶対座標上の2本の航跡線が交差することだけでは警告しない。到着時刻が違えば除外する。
- 絶対航跡が交差しない並走・追越しでも、相対区間が`C`へ入れば警告する。
- 旋回または方位不明では予測窓を短くし、区間ごとの合成領域と不確実性を更新する。長時間の直線外挿で穴を埋めない。

#### 5.7.3. 二段階評価と処理負荷

```text
軽量broad phase
  static: swept AABB / 空間インデックス
  boat: 相対距離、closing speed、円近似CPA
    -> 候補のみ
精密narrow phase
  static: segment vs expanded polygon
  boat: relative segment vs combined ship domain
```

- 評価周期は1Hzを維持し、連続判定のためにGPS取得頻度を上げない。
- 直進なら予測窓全体を1線分で扱えるため、2mごとの多数のポリゴン判定より軽くできる。
- 旋回分割数が安全上必要な上限を超えた場合、後半を黙って捨てず、予測窓を短縮して`dataDegraded`を返す。
- 候補過多・計算時間超過時は`safe`を返さず、detector healthへ反映する。

#### 5.7.4. 警告開始・継続・解除

- 開始候補: `firstEntryTime <= effectiveHorizon`
- 即時開始: `currentOverlap`、または補正後action deadlineが2秒以下
- 継続: 同じ警告IDで連続交差がある間。予測終点が危険の先でも継続する
- 解除候補: 現在非接触かつ予測区間全体に交差なし
- 最終解除: 解除候補に退出余裕・離反・3秒継続・異なる観測3件を追加
- データ劣化: 直前の物理警告を即解除せず、S01のholdとsystem faultを並存

## 6. 通信プロトコル補強

公開初版の他艇messageへ最低限次を追加する。

```json
{
  "protocolVersion": 1,
  "appVersion": "...",
  "profileVersion": "...",
  "boatId": "...",
  "sessionId": "uuid",
  "sequence": 1,
  "serverUpdatedAt": 0,
  "observedAt": 0,
  "lat": 0,
  "lng": 0,
  "accuracy": 0,
  "course": 0,
  "courseAccuracy": null,
  "speed": 0,
  "speedAccuracy": null,
  "battery": null,
  "capabilities": []
}
```

時刻の役割:

- `observedAt`: GPS観測時刻。物理予測に使用
- `serverUpdatedAt`: Firebase server timestamp。通信鮮度とghost判定に使用
- local monotonic receive time: 端末内のage増加と順序制御に使用

異なる端末のmonotonic clockは比較しない。端末epochだけを信頼してtarget freshnessを決めない。

他艇鮮度の公開初版初期値:

| serverUpdatedAtからのage | 状態 | 扱い |
|---:|---|---|
| 0〜3秒 | `fresh` | 通常予測 |
| 3〜6秒 | `degraded` | 予測時間短縮、不確実性増加 |
| 6〜10秒 | `lostForPrediction` | 新しい直線外挿を止め、active警告はhold |
| 10秒超 | `expired` | 新規予測対象外。直前危険と通信途絶表示は保持 |

30秒の直線外挿は行わない。ageは推定server nowと`serverUpdatedAt`から求め、未来時刻、負のage、server offset異常はdata quality faultにする。

## 7. 初期定数

一括試験前の実装初期値を固定する。

| 項目 | 初期値 |
|---|---:|
| 評価目標周期 | 1秒 |
| 通常警告開始確認 | 1秒継続+異なる観測2件 |
| 即時開始 | current overlapまたはdeadline 2秒以下 |
| 解除確認 | 3秒継続+異なる観測3件+退出余裕 |
| GPS回復 | timestamp増加3fix、合計2秒以上 |
| GPS幅補正係数 | accuracyの0.25倍 |
| 静的GPS補助帯上限 | 全幅2m。旧余裕入り区域は0m |
| 他艇GPS補正上限 | 中心間距離へ1.5m追加 |
| lost hazard hold | `clamp(deadline+3, 5, 12)`秒 |
| 最後の危険表示 | hold終了後30秒または回復まで |
| remote target上限 | 100件 |
| log memory queue | 1000 event |
| log session file | 10MB |
| primary lock優先余裕 | 2秒 |
| 音声復旧不能判定 | 3回失敗または5秒 |

システムfaultの再通知:

| fault | 初回 | 継続 |
|---|---|---|
| GPS unusable | 専用音声を2回+振動 | 15秒ごと |
| dynamic receive/share unavailable | 専用音声1回+固定表示 | 30秒ごと |
| pipeline gapを復帰後検出 | 専用音声2回+固定表示 | 状態回復まで15秒ごと |
| profile/audio hard blocker | 航行開始不可 | 開始画面で固定表示 |
| audio path unavailable | 強い振動+固定表示 | 音声は使用不能 |

P0/P1行動警告中はfault音を再生せず、表示・振動だけ併記する。行動警告解除後、faultが継続していれば直ちにfault音を再生する。

## 8. 利用者向け文言

禁止:

- 「安全です」
- 「周囲に艇はいません」
- 「すべての他艇を検出中」
- 対応水域外での「警告なし」
- 実判定していない左右・逆走・橋脚安全の断定

推奨:

```text
現在警告なし
アプリで共有中の艇のみ検出します
周囲を目視確認してください
```

```text
機能を限定して航行中
他艇受信: 利用不可
自艇共有: 利用不可
```

```text
この水域の危険区域データはありません
警告モードを開始できません
```

foreground notificationも、実機で安全評価継続を確認するまでは「衝突警告を継続」と断定しない。

## 9. 公開初版で必須の追加テスト

### 9.1. 順序・競合

- GPS Aの処理遅延中にGPS Bを完了させ、BがAで上書きされない
- start中stop、stop中start、dispose後callback
- 音声play中clear、新primary開始、OS interruption復帰
- 同じassetを使う二alertの片方だけ解除
- remote sequence逆転、session切替、重複

### 9.2. 能力と誤安心

- 非アプリ艇がいてもUIが全艇検知を主張しない
- coverage外でも開始・継続でき、既知の警告が動作したまま`runningDegraded`と無音の固定表示になる
- coverage未設定のRelease版でも開始・継続でき、既知の警告が動作したまま`runningDegraded`と無音の固定表示になる
- networkなしで`runningDegraded`だけ選べ、受信／共有能力が個別表示される
- running中network喪失・回復で能力表示が正しく変わる
- profile／audio／GPS不成立で開始をhard blockする

### 9.3. GPS・警告状態

- deadline 0、2、8、15秒でGPS喪失
- degradedとunusableの境界揺れ
- cached／重複fixで回復しない
- active中のlost holdとfault並存
- guidance区域内start
- 短いGPS喪失後にentry guidanceを再連打しない

### 9.4. 負荷・入力

- remote target 0、1、20、100、101件
- 不正boat type、NaN、未来時刻、巨大sequence、長い文字列
- log queue満杯、disk書込失敗
- 最大ポリゴン点数、最大予測step
- 位置callbackが評価より速い場合のcoalesce

### 9.5. 実機

- Android／iOSで画面ON、lock、background、復帰
- phone call、Bluetooth切断、音量ゼロ、DND
- process kill後のcoach lostとghost TTL
- 省電力モードと電池最適化
- 対象端末／OSごとのgap記録

### 9.6. 連続衝突判定

- 危険区域が現在位置と予測終点の間だけにある場合も検知する
- 危険区域通過前、侵入中、退出直後で、警告が「開始・継続・解除確認」の順にだけ遷移する
- 旧2mサンプル点のちょうど中間に細い危険形状を置いても見逃さない
- 高速艇が1評価周期内に自艇前方を横切っても検知する
- 2艇の航跡が同じ場所で異なる時刻に交差する場合は衝突警告にしない
- 平行な中心航跡で後艇が追いつき、合成安全領域へ入る場合は検知する
- 現在重なっていて予測終点だけ離れている場合、`firstEntryTime=0`で即時警告を維持する
- GPSジャンプが危険区域を横切っても、棄却fix間の偽のswept domainを作らない
- 旋回中に直線予測から外れる場合、予測窓短縮または保守的capsuleへ移り、`safe`へ落ちない
- 警告時間設定を5秒から25秒へ変えても、同じ予測区間内の交差有無そのものは変わらない
- accuracy 5mで1x〜4xの静的swept domain全幅が10.25m、8+が11.75mになる
- 双方accuracy 5mの1x同士で、横方向の中心間距離しきい値が9mから約9.9mになる
- 旧余裕入り危険区域ではGPS補助帯が0mで、排他領域幅のままになる
- `inflateMeters`へ全幅補正値を直接渡して2倍にしない
- 他艇0、1、20、100艇でbroad phaseとnarrow phaseの対象数、p95評価時間を記録する

## 10. 一括release candidateへの実装順

時間をかけたPoCには分けないが、同じbranch内で依存順を守る。

1. `SessionConfig`、run state、generation、revision
2. bounded mailboxとsingle-writer `SafetyOrchestrator`
3. `SafetySnapshot`とconsumer側の古いrevision拒否
4. GPS health、duration-based FSM、lost並存
5. audio directiveと直列`AudioCoordinator`
6. protocol version、sessionId、sequence、server timestamp
7. 非制限型coverage表示、capability、`runningFull/runningDegraded`
8. UI文言、foreground notification
9. input/log limits、feature flags
10. §9と包括再設計§23.7をまとめて実行

途中の一部実装を公開しない。release candidateでは、旧pipelineと新pipelineが同じ状態を書き換える期間を作らない。比較が必要なら旧結果はログ専用とし、音声・UIへ接続しない。

## 11. 手動で必要な追加作業

### 11.1. 実装前または実装中

1. **対応水域の任意設定**  
   危険区域が網羅されていると現地確認できた桜川の範囲は、任意で`operationalCoveragePolygon`として設定する。コーチ練習水域とは別であり、未設定でも航行を制限しない。

2. **運用モード文言の確認**  
   `runningDegraded`時に、他艇受信と自艇共有のどちらが使えないかを部員が取り違えないことを確認する。

3. **旧アプリとのversion統一運用**  
   一括試験と公開初回練習では全艇を同じapp/protocol versionへ更新する。

### 11.2. 実装後の一括試験

1. Android・iPhoneを含む2台以上を用意する
2. §9の順序・故障シナリオをチェック表どおり実行する
3. 音声を艇上騒音下でブラインド試聴する
4. 対応水域未設定・境界内・境界外のすべてで開始と既知の警告が継続し、境界外だけが`runningDegraded`と無音の固定表示になることを確認する
5. app kill、通信断、GPS OFF、Bluetooth切断を発生させる
6. app version、protocol version、profile version、端末、OS、合否を記録する

具体的な画面操作、Firebase Console設定、成功表示、失敗時の戻し方は、実装が完了した時点で別の一括試験手順書にする。

## 13. 最終判断

包括再設計だけでも現行より大幅に安全になるが、非同期処理と能力表示を定義しないまま実装すると、アルゴリズムが正しくても古い結果の上書き、無音死、誤安心が残る。

公開初版で最優先するのは、高度な予測精度ではなく次の5点である。

1. 安全状態を一つの直列writerだけが更新する
2. 物理危険とデータ喪失を排他的にせず並存させる
3. 通信をsession／sequence／server timeで順序付ける
4. 「警告なし」を「安全」と表現しない
5. 対応水域・アプリ共有艇・background保証の限界を明示する

これらを本書どおり実装し、一括release candidate試験を全て通した場合にのみ公開判定へ進む。
