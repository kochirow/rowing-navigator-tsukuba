# チーム招待制・Firebase無料枠・省電力設計

基準日: 2026-07-20  
対象: Rowing Navigator 1.0.0

## 結論

次の方針を実装する。

- 初回は「チームを作成する」「招待コードでチームに参加する」の二択
- 利用者にメール/パスワード登録を求めず、Firebase匿名認証を内部利用
- 参加済み端末はFirebase SDKの保存認証と所属を起動時に自動復元し、通常は再入力不要
- 機能画面からの再匿名化・サインアウトは行わず、認証が本当に消失した場合だけ固定コード再参加へ戻す
- チーム作成時に長さ12文字（約59bit）の推測困難なコードを1回だけ作成。更新前に発行済みの20文字コードも受理する
- 招待コードに自動期限・自動ローテーションなし
- チームメンバーは全員、同じコードを表示・コピー可能
- 位置、艇プロファイル、臨時危険区域、固定流木の更新状態を`teamId`で完全分離
- 同一チームのメンバーは全員、危険区域の作成・更新・削除が可能
- マップ、自艇の現在位置、自艇の危険判定、航行記録は従来どおり端末内1Hz
- 通信だけを適応的に間引き、送信ACK待ちを端末内1Hz処理から分離してFirebase転送量と無線/電池負荷を削減
- 航行開始時の名前・艇種・座席は直前の確定値を端末内へ保存し、次回に編集可能な状態で復元

## データ構成

### Firestore（永続・低頻度）

```text
users/{uid}
teams/{teamId}
teams/{teamId}/members/{uid}
invite_codes/{inviteCode}
teams/{teamId}/temporary_obstacles/{obstacleId}
teams/{teamId}/managed_hazards/fixed_driftwood_01
teams/{teamId}/messages/{uid}  # RTDB障害時の切り戻し用
```

- `users/{uid}`は1ユーザ1チームを保証するインデックス。
- `teams/{teamId}`と`members`は、参加後のメンバーだけが読める。
- `invite_codes`は、コードを知る認証済み端末に限って単一文書`get`を許可し、`list/query`は禁止。
- チーム、招待、メンバー、ユーザーインデックスはFirestore transactionで同時に作成する。
- 危険区域は全メンバーが更新可能だが、座標範囲、形状、半径、時刻、revisionをRulesで検証する。

### Realtime Database（航行中・高頻度）

```text
team_meta/{teamId}
team_invites/{inviteCode}
team_users/{uid}
team_members/{teamId}/{uid}
teams/{teamId}/boat_profiles/{uid}
teams/{teamId}/live_positions/{uid}
```

- RTDB RulesはFirestoreを参照できないため、位置共有に必要な最小所属bridgeだけをRTDBに持つ。
- `team_meta`はcreate-once。`team_invites`の作成者と`teamId`を結び、攻撃者が既知の別チームIDへ偽招待コードを差し込むことを防ぐ。
- 招待コード衝突やFirestore確定前の既知失敗では、所属が1件もない未使用予約だけを作成者が削除できる。確定済みチームの固定コード削除はRulesが拒否する。
- `live_positions/{uid}`は自分のUIDだけがwrite/delete可能。読取は同チームメンバーだけ。
- メンバーUID一覧のlist/readは公開せず、各端末は自分自身の所属レコードだけを読める。
- 共有位置は、型、必須key、緯度経度範囲、速度、誤差、server timestamp、sequence単調増加、最短1900ms間隔をRulesで検証する。改変・旧クライアントの過剰送信も無料枠を消費しにくくする。
- 航行開始時に`onDisconnect().remove()`を登録し、強制終了時もライブ位置を残さない。

Firestore→RTDBの順で所属確定中に通信が切れた場合は、次回起動または同じ画面の復元処理がFirestoreの確定状態を読み、RTDB bridgeを再構成する。片方の書込失敗で別チームのデータを読めるようにはしない。

## 自動接続と認証消失時の扱い

- Android/iOSのFirebase Authは認証状態を端末へ標準保存する。起動時は`authStateChanges()`の初回イベントを待ってから所属を確認し、復元途中の一時的な`null`を未参加と誤判定しない。
- 通常のトークン更新、アプリ終了、端末再起動では同じ匿名UIDを使う。利用者向けログイン画面とログアウト操作は設けない。
- ホーム、監視、危険区域編集は、認証がないときに`signInAnonymously()`を呼ばない。新UIDを勝手に作らず、中央の入口へ戻す。
- `unavailable` / `deadline-exceeded` / `resource-exhausted` / `permission-denied` / `unauthenticated`では、現在のAuth UIDと過去にサーバー確認済みのcache UIDが一致する場合だけ端末内利用を継続する。サーバーアクセスはRulesが拒否したままなので権限は拡大せず、UIDも自動破棄しない。
- Auth状態が実際に`null`または別UIDへ変わった場合だけ、以前のチーム名と固定コードを再参加用ヒントとして表示する。自動参加はせず、利用者が「参加する」を押して所属を再作成する。
- アプリのデータ消去、Androidのアプリデータ削除、Firebase側のアカウント削除等で旧UIDを完全に失うと、旧Firestore member文書は端末から安全に消せない。旧位置/profileは`onDisconnect`とTTLで共有から除外し、運用担当が旧UIDを整理する。

## 通信量と省電力

想定:

- 週6日
- 1回2時間
- 12人同時
- 平均26.07練習日を保証側へ切り上げ、1か月27練習日（54時間）として試算

旧形式は名前・艇種・version等を毎回送信し、代表payloadが約523B。全員1秒送信とプロトコル余裕を650B/配信とする保守的な試算では、月約17.52GBとなり、SparkのRTDB download 10GB/月を超え得る。

実装後は、名前・艇種・protocol/app/profile versionを`boat_profiles`へ分離し、session IDも短縮。代表的な位置payloadは約146B、上限テストは250B未満とした。`onValue`で全艇を毎回処理せず、`onChildAdded/Changed/Removed`で変化した1艇だけを受け取る。

| 状態 | クラウドへの送信間隔 | 端末内のGPS/安全判定 |
|---|---:|---:|
| 危険度lv1以上 | 2秒 | 1秒 |
| 300m以内に他艇、リスクなし | 2秒 | 1秒 |
| 300m以内に他艇なし | 5秒 | 1秒 |
| 停止中（近傍艇なし） | 10秒 | 1秒 |

位置の受信側は速度・針路から毎秒外挿する。自艇マーカーと危険判定はクラウド送信間隔に依存しない。

送信はGPS処理から切り離したlatest-only publisherが担当する。Firebase writeは同時に1件だけとし、その間に複数の測位が来た場合は待機値を最新1件へ置き換える。5秒ACKがない場合はUIを「位置共有不可」にするが、端末内の地図、静的危険区域判定、他艇判定、警告、記録は継続する。失敗時は1/2/5/10秒のbackoffで再試行し、SDKのoffline queueを無制限に増やさない。

艇profileと位置の初回/再接続時writeは同じRTDB root updateで原子的に行う。`.info/connected`の再接続ごとに`onDisconnect`削除を再登録し、profile fingerprintを無効化するため、通信断で削除されたprofileが位置だけ復帰する状態を作らない。

位置payload本体を最大250B、12台の各更新を12接続が受け取る最悪fan-outで評価:

- 全員が2時間ずっと最短2秒送信: 約3.50GB/月（約129.6MB/練習）
- 自動テストのアプリpayload予算: 4GB/月以下（Spark 10GBの40%以下）
- protocol/WebSocket/TLSを含む運用合格値: 12台・2時間のFirebase Console download増分200MB以下、月予測6GB以下

FirebaseはSDK・WebSocket・TLS overheadもdownloadへ算入するため、コード上のpayload計算だけで無料枠を保証しない。1練習200MBを超えた版は公開せず、月6GB到達時は原因を確認する。無料枠超過時も端末内の地図、固定危険区域警告、GPS、音声、記録を継続し、共有機能だけを「利用不可」と明示する。

Firestoreの臨時危険区域listenerは期限降順・最大100件に制限し、Rulesもlimitなしqueryを拒否する。100件時でも想定readは1練習日約1,248件で、50,000 reads/日の約2.5%である。

GPS、他艇受信、臨時危険区域受信はstreamのerror/doneを1/2/5/10秒backoffで再購読する。GPSは15秒無通知も停止とみなし再購読する。App Check初期化は3秒で端末内機能を先に起動し、失敗時は5/15/30/60/300秒でバックグラウンド再試行する。

## App Check

- Debug build: Debug provider
- Android release: Play Integrity
- iOS release: App Attest with DeviceCheck fallback
- token TTL: 公式defaultの1時間を推奨（短縮は認証回数・電池・quotaを増やす）
- リリース候補を先に配布し、有効/無効requestのメトリクス確認後にRTDBとFirestoreを強制適用

App Checkは「正規アプリ/端末」の証明であり、チーム所属確認の代替ではない。チーム分離はRulesで強制する。

## 公開前の実測ゲート

- Rules Emulator 13件が全件成功する
- 2チーム×2台以上で、他チームの位置・危険区域を読書きできない
- チーム作成と参加の途中で通信を切り、再起動後に同じチームを復元する
- 参加済み端末を10回終了/再起動しても作成/参加画面が再表示されず、同じUID・チームへ自動接続する
- 機内モード再起動では同じUIDの検証済みキャッシュで地図を開き、復帰後に同じチーム共有へ戻る
- アプリデータ消去等で認証を本当に失った場合だけ再参加画面となり、新UIDを裏で自動作成しない
- 全メンバーが臨時危険区域の作成・編集・削除と固定流木の編集を行える
- 航行中に危険区域編集画面へ進んでも、背景の位置共有と警告処理が継続する
- 12台・2時間の転送量が200MB以下、月換算6GB以下であることと、発熱、電池消費、再接続、強制終了を記録
- 同一航行中に機内モードON/OFFを2回行い、毎回profileと位置が揃って復帰し、端末内警告が止まらない
- 航行終了/OS kill後にライブ位置がサーバー上へ残り続けない
- アカウント削除後、チーム所属と自分のライブ位置が削除され、初回二択へ戻る

## 手動設定が必要な項目

1. Firebase AuthenticationでAnonymousを有効化する。Identity Platformの匿名アカウント30日自動クリーンアップは必ずOFFのままにする。過去にONにした場合、OFFへ戻しても削除予定済みアカウントは予定が残るため、公開前テストチームはOFF確認後の新しい端末認証で作り直す。
2. 検証済み`firestore.rules`と`database.rules.json`を公開する。旧グローバルpathから移行するまで旧アプリと新アプリを同じ本番データで混在させない。
3. Firebase Console > App CheckでAndroidにPlay Integrity、iOSにApp Attest/DeviceCheckを登録する。
4. Android release signingのSHA-256をFirebase/Play Consoleに登録し、Play ConsoleとCloud projectを連携する。
5. 先にInternal/TestFlightで配布し、App Checkメトリクスを確認してからRTDB/FirestoreのEnforceを有効化する。反映に最大15分かかる。
6. Firebase Sparkの課金上限を守る場合、課金が必須のGoogle Maps projectとFirebase projectを分ける。同じGoogle Cloud projectにbilling accountを結び付けるとFirebaseもBlazeへ移行する場合がある。
7. Firestore TTLはbilling必須のため、Sparkを維持する本方針では有効化しない。期限切れ臨時危険区域はquery/画面から除外し、保存量を監視する。
