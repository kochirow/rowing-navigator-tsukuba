# 練習一括ログ(監視端末による全艇記録)設計

- 作成日: 2026-07-28
- 対象: Rowing Navigator 桜川版
- 状態: 実装前の設計・要件定義
- 目的: 1回の練習に参加した全艇と監視者の動き、および各艇のアプリが出していた警告を、監視端末に一括で記録し、1つのZIPとして取り出せるようにする
- 非対象:
  - 各艇の詳細ログのサーバー集約(**採用しない**。3章)
  - 他艇の警告状態を航行中の画面へ表示すること(**採用しない**。5.4)
  - ログの自動アップロード、解析・可視化ツール(別途)

> 本書は既存の `docs/design_notes/2026-07-20_チーム招待制・無料枠・省電力設計.md` の無料枠前提を引き継ぐ。
> 判断はすべて [DESIGN_PRINCIPLES.md](../DESIGN_PRINCIPLES.md) から導く。食い違ったら DESIGN_PRINCIPLES.md が優先する。

---

## 1. 結論

次の2つだけを実装する。

1. **監視端末に、受信中の全艇データをそのまま記録する機能を足す。**
   終了時に「練習一括ログZIP」として共有する。Firebase の追加費用はゼロ。
2. **位置共有プロトコルに、その艇がいま出している警告の状態を足す。**
   記録専用であり、**航行中の画面には他艇の警告を一切出さない。**

各艇からサーバーへログを集約する仕組み(事後アップロード)は作らない。
事故が起きたときは、当該艇の端末から既存の診断ZIPを提出してもらう。

この構成で、

- **一括ログ** = 全艇 + 監視者が「どこにいて、何の警告が鳴っていたか」
- **詳細ログ**(既存の診断ZIP) = 1艇のアプリが「なぜそう判断し、実際に音が出たか」

という棲み分けになる。一括ログで事象を再構成し、疑わしい艇の詳細ログを突き合わせる。

## 2. 現状(事実)

| いま在るもの | 中身 |
| --- | --- |
| `lib/services/session_store_service.dart` | 自艇セッションを端末内JSONで保存。サーバー送信なし |
| `lib/services/gpx_export_service.dart:83` | 診断ZIP(`manifest.json` / `track.csv` / `alerts.jsonl` / `events.jsonl` / catalog)を1セッション単位で生成・共有 |
| `lib/hooks/use_coach_watch.dart` | 監視側は全艇を**受信しているが保存していない**。航跡はメモリ上 `trailDurationSec` のTTLで捨てている |
| `lib/api/live_position_api.dart:25` | RTDB `teams/{teamId}/live_positions/{boatId}`。チーム境界は既にある |
| `lib/models/message_model.dart:192` | `toCompactRtdbJson` = 1Hz送信の実体。実測200B未満(`test/models/message_model_test.dart:89`) |

一括ログに必要な配線はほぼ揃っている。

- `boatId` は Firebase Auth の uid(`lib/screens/home_map_screen.dart:1538`)なので、**端末をまたいで安定した結合キー**になる
- `RemoteBoatMessage` は `sessionId` + `sequence` + `serverUpdatedAt` を持つ。**`sequence` の飛びで欠測を定量化できる**
- RTDB の `serverTimeOffset` 補正済み時刻があるため、**12台の端末時計を揃える共通時間軸が既にある**

足りないのは「捨てずに書く」ことと、「警告状態が電波に乗っていない」ことの2点だけである。

## 3. 事後アップロードを採用しない理由と、その代償

各艇が練習後に軽量トラックをクラウドへ上げる案は、次の理由で採らない。

- 事故は稀であり、そのときだけ端末から詳細ログを提出すれば足りる
- 位置履歴をサーバーに常時蓄積すると、同意・保持期間・削除責務がすべて発生する
- 一括ログの目的(全体像の把握)には、監視端末が受信できた範囲でほぼ足りる

**代償は、記録に穴が開きうることである。** これは設計上の既知の欠落として、次の3つで扱う。

1. **穴を必ずログに書く。** 受信できなかった区間を `gap` として明示する。
   空白を「そこに艇がいなかった」と読ませない(原則6: データ欠損は安全の根拠にならない)
2. **穴の原因を分けて書く。** 艇側の途絶(`seq` の飛び)と、監視端末側の中断(バックグラウンド遷移)は別イベントにする
3. **画面を消してもアプリが動き続けるようにする。** 手段は6.3に書く。
   これは Wakelock(常時点灯)とは別の話であり、設計原則1.4 は変更しない

穴が許容できないほど重要な練習は、監視端末を2台走らせるか、当該艇の詳細ログを提出してもらう。

## 4. データの流れ

```
各艇(航行中)
  SafetySnapshot ──► 提示状態を2〜3文字へ符号化 ──► Message.toCompactRtdbJson
                                                        │
                                              RTDB teams/{teamId}/live_positions
                                                        │
監視端末(監視中)                                        ▼
  MessageService.getMessagesStream ──► otherBoats ──┬─► useCoachWatch(既存・表示)
                                                    └─► PracticeLogRecorder(新規)
                                                             │ 重複排除・欠測検出
                                                             ▼
                                              PracticeLogStoreService(JSONL追記)
                                                             │
                                                             ▼
                                              PracticeLogExportService ──► ZIP共有
```

**記録は安全判定・監視表示の後段にだけ置く。** 記録の失敗・遅延・容量超過が、
警告経路にも監視表示にも影響してはならない(原則1)。

## 5. プロトコル拡張(警告状態)

### 5.1 送る値

`toCompactRtdbJson` に、次のフィールドを足す。いずれも省略可能。

| キー | 型 | 意味 | 例 |
| --- | --- | --- | --- |
| `w` | string(2文字) | 提示中の警告。1文字目 = 緊急度バンド、2文字目 = カテゴリ | `"2o"` |
| `m` | string(1文字) | `SafetyRunMode`。`f`=runningFull / `d`=runningDegraded / `u`=unavailable | `"d"` |
| `a` | number(1) | 陸上判定で音を止めている間だけ 1。それ以外は省略 | `1` |

`w` の1文字目(`AlertUrgency` に対応。`lib/config/alert_presentation_config.dart:120`):

| 値 | 意味 |
| --- | --- |
| `0` | monitoring(表示のみ) |
| `1` | approaching(断続音) |
| `2` | imminent(連続音) |

`w` の2文字目(カテゴリ):

| 値 | category |
| --- | --- |
| `o` | `other_boat` |
| `b` | `bridge` |
| `s` | `shore` |
| `i` | `island` |
| `d` | `driftwood` |
| `c` | `curve` |
| `r` | `reverse` |
| `g` | `generic` / `testZone` |
| `f` | system fault 全般(`gps_unavailable` / `pipeline_unresponsive` ほか) |

警告が何も出ていないときは `w` を**送らない**(省略する)。`"0-"` のような値を毎秒送らない。

対象は `SafetySnapshot.audioDirective` の対象ではなく、**表示 primary(`primaryAlertId`)でもない。**
「音の鳴り方」を記録したいので、**持続音チャンネルが選んだ候補**(`audioDirective.alertId` に対応する
`ActiveAlert`)を第一候補とし、音声対象がないときだけ `primaryAlertId` を使う。
どちらも無ければ省略する。この選択規則は `PresentationStateCodec` に閉じ込め、単体テストを付ける。

### 5.2 データ量

現行の compact payload は実測200B未満。追加は最悪でも `,"w":"2o","m":"d","a":1` = 約22B。

`FirebaseUsageBudget.maxCompactPositionBytes` は **既に250B**で見積もられているため、
**無料枠の試算は変わらない**。`test/models/message_model_test.dart` の200B未満というしきい値も
維持できる見込みであり、実装時に同テストで確認する。超えた場合は `m` を
「`f` のときは省略」に変えて削る(既定値は runningFull なので情報を失わない)。

### 5.3 protocolVersion は上げない

`lib/config/protocol_config.dart:3` の方針どおり、互換の判断は `protocolVersion` だけで行う。
今回の追加は**省略可能かつ後方互換**であり、

- 旧版が新版のデータを読む → 未知キーは `expandCompactRtdbJson` が拾わないだけで無害
- 新版が旧版のデータを読む → `w` が無い = 「警告状態を送れない版」

のどちらも成立する。ここで版を上げると `supportedPositionProtocolVersions` の
混在期間が発生し、**配信のたびにどちらかの群が互いの地図から消える**リスクだけが増える。
上げる利益がないので上げない。

代わりに `capabilities` へ `'presentation_state'` を足し、受け手が
**「警告が無かった」と「送れない版だった」を区別できる**ようにする。
`Message.expandCompactRtdbJson` / `toRtdbJson` の `capabilities` は現在ハードコードされた
定数配列なので、`w` の有無で要素を足す形へ変える。

### 5.4 受け取った警告状態は、記録以外に使わない

**不変条件(新規): 受信した `w` / `m` / `a` は、地図描画にも衝突評価にも渡さない。**

理由:

- 他艇の警告は自艇の判断材料にならない。自艇に必要な警告は自艇が自分で出す
- 表示すると画面が混み、**正常な運用で他艇の警告が常時見えることになる**(原則4: 形骸化)
- 安全経路へ入れると、**他艇のアプリの不具合が自艇の警告を汚染する**

したがって `Boat`(`lib/models/boat_model.dart`)には持たせない。
`RemoteBoatMessage` / `Message` までで止め、`PracticeLogRecorder` だけが読む。

### 5.5 セキュリティルールの先行デプロイ(必須)

`database.rules.json` の `live_positions/$boatId` は `"$other": { ".validate": false }` である。
**ルールを先にデプロイしないと、新版アプリは位置を1件も書けなくなる**(permission-denied)。
これは「他艇の地図から消える」= 原則1違反の実害になる。

手順は必ずこの順で行う。

1. `database.rules.json` に `w` / `m` / `a` の `.validate` を追加してデプロイする
   - `w`: `newData.isString() && newData.val().matches(/^[012][obsidcrgf]$/)`
   - `m`: `newData.isString() && newData.val().matches(/^[fdu]$/)`
   - `a`: `newData.isNumber() && newData.val() === 1`
2. ルールが有効になったことを確認する
3. アプリを配信する

`protocolVersion === 1` の検証(`boat_profiles`)は据え置きなので変更しない。

## 6. 監視端末での記録

### 6.1 記録の対象

| 対象 | 取得元 | 間隔 |
| --- | --- | --- |
| 他艇の位置・速度・針路・精度・電池・警告状態 | 既存の `otherBoats` ストリーム | 各艇の適応送信間隔(2〜10秒) |
| 監視者自身の位置 | 監視中だけ起動する位置ストリーム | `observerTrackIntervalSec`(**10秒**) |
| 監視側が観測した異常 | `useCoachWatch` の `anomalies` | 状態変化時 |
| 欠測・記録中断 | recorder 自身 | 発生時 |

**監視者の位置ストリームは記録専用であり、安全経路には入れない。**
現在 `NavMode.observer` では位置ストリームを起動していない(`use_navigator.dart:2857` は航行開始時のみ)。
記録のために新しく起動する。精度は `LocationAccuracy.high`(6.2 の検討結果)とし、
取得できない・権限が無い場合は**監視者トラックだけを欠測として記録し、他艇の記録は続ける**(原則1)。

**新しい測位が来なくても10秒ごとに最新の測位を書き、`age_sec` を付ける。**
監視者が動かないと記録点が出ない作りにすると、「岸で立って見ていた」と
「記録が死んでいた」が区別できなくなる(原則6)。

**記録は監視機能の一部であり、OFFにできない。** 監視開始 = 記録開始で固定する。
監視者だけが記録から抜けられると、事故検証で「監視者がどこにいたか」だけが空白になり、
一括ログの価値が落ちる。設定トグルは置かない。

### 6.2 監視中の測位設定(精度と電力の検討)

#### 何が電力に効くか

`geolocator 14.0.2` の実装を確認した結果は次のとおり。**間隔を空けるだけでは電力は下がらず、
プラットフォームで挙動が違う。**

| 設定 | Android(`geolocator_android 5.0.2`) | iOS(`geolocator_apple 2.3.13`) |
| --- | --- | --- |
| 記録間隔 | **効く。** `AndroidSettings.intervalDuration` → `LocationRequest.setIntervalMillis()`(`FusedLocationClient.java:106`) | **指定できない。** `AppleSettings` に間隔のパラメータが無い。CLLocationManager は連続測位のままで、間引きはアプリ側の処理にしかならない |
| `accuracy` | `PRIORITY_HIGH_ACCURACY` / `BALANCED_POWER_ACCURACY`(`FusedLocationClient.java:136-146`) | `LocationAccuracyMapper.m`: `medium`→`kCLLocationAccuracyHundredMeters`、`high`→`kCLLocationAccuracyNearestTenMeters` |
| `distanceFilter` | 効く | コールバックは減る(測位自体は続く) |

#### 精度を下げるのは割に合うか — 結論: 合わない

**誤差の側(確定値)**

| 設定 | 誤差 |
| --- | --- |
| `medium` | **100m**(iOS `kCLLocationAccuracyHundredMeters` / Android balanced) |
| `high` | **10m**(iOS `kCLLocationAccuracyNearestTenMeters` / Android GNSS) |

これを運用前提(DESIGN_PRINCIPLES 1.1)に当てると:

| 前提の寸法 | 100m 誤差だと |
| --- | --- |
| 川幅 40〜50m(狭所35m) | **川幅の2倍以上。どちらの岸にいたかも判別できない** |
| カーブ間隔 最短200m | **隣のカーブと取り違えうる** |
| 橋(休憩場所) | どの橋の近くにいたか特定できない |

監視者の位置を記録する目的は「事故のとき、監視者が艇の見える位置にいたか」を検証することである。
**100m 誤差はその目的を達成できない。** 記録する意味そのものが消える。

**電力の側(概算)**

以下は公開されている一般的な消費電力の桁であり、**本アプリでの実測ではない**。
ただし結論は悲観側でも変わらないため、判断には足りる。

- 端末電池を小さめに見て **13 Wh**(3,349 mAh × 3.87 V 相当)
- GNSS 連続測位を **25〜50 mW**(悲観的に見て 100 mW)
- 監視時間 **2時間**

| | 消費 | 電池比 |
| --- | --- | --- |
| GNSS 2時間(25 mW) | 50 mWh | **0.4%** |
| GNSS 2時間(50 mW) | 100 mWh | **0.8%** |
| GNSS 2時間(悲観 100 mW) | 200 mWh | **1.5%** |

`medium` でも Wi-Fi / セル測位の電力はゼロではないため、**実際の節約はこの半分程度**、
すなわち **0.2〜0.8%** にとどまる。

**比較対象**: 監視者は屋外・日中なので画面は最大輝度になる(およそ 1,000〜1,500 mW)。

> **画面を10分見る ≒ GNSS を2時間高精度で回す**

2時間の練習で画面を見るのが10分で済むとは考えにくい。
**GPS精度は監視端末の電力収支において主要因ではない。**

**したがって 0.2〜0.8% の電池と引き換えに 100m の誤差を負うのは割に合わない。**
省電力を効かせたいなら削るべきは画面であり、監視中に Wakelock を持たない方針(6.3)が既にそれである。

#### 採用する設定

```dart
// 監視者トラック専用。航行用(bestForNavigation)とは別物にする。
accuracy: LocationAccuracy.high,   // 10m。川幅40mの1/4で、岸・橋・カーブとの関係が読める
distanceFilter: 5,                 // 止まっている間のコールバックを減らす
// Android のみ
intervalDuration: Duration(seconds: observerTrackIntervalSec), // 10秒
```

記録は `observerTrackIntervalSec` ごとに**最新の測位を書く**。新しい測位が来なくても書き、
`age_sec` を添える(6.1)。

**`pauseLocationUpdatesAutomatically: true` は採用しない。**
iOS では電力に効くが、一度止まると再開がOS任せになる。監視者が岸で長時間動かないのは
正常な運用であり、これを入れると**動かない監視者ほど記録が死ぬ**。
測位が止まればバックグラウンド継続の資格(6.3)も同時に失う。

**根本的なトレードオフ**: バックグラウンドで動き続けるには位置情報を使い続けるしかない(6.3)。
GPSを完全に止めると記録ごと死ぬ。したがって「止める」ではなく「安く回し続ける」方向にしか行けない。

### 6.3 画面を消しても記録を続ける(Wakelock とは別の話)

**Wakelock は画面を点けたままにする機能であり、バックグラウンド実行とは無関係である。**
設計原則1.4 が「監視中は常時点灯しない」と定めているのは、監視者が端末を手で操作できるから
画面を点けておく理由がない、という話であって、アプリが動き続けるかどうかとは別問題である。

このアプリはバックグラウンド実行の許可を既に持っている。

- iOS: `ios/Runner/Info.plist:40` の `UIBackgroundModes` = `location`, `audio`
- Android: `AndroidManifest.xml:7` の `FOREGROUND_SERVICE_LOCATION`
- `lib/services/geo_service.dart:21`(Android 常駐通知)、`:40`(`allowBackgroundLocationUpdates: true`)

ただし**この許可は位置情報を使い続けている間だけ有効**である。

| モード | 位置ストリーム | 画面を消したとき |
| --- | --- | --- |
| 航行 | 起動中 | 動き続ける(location background mode / フォアグラウンドサービス) |
| 監視(現状) | **起動していない** | **止まる。** iOS は数秒〜十数秒でサスペンドされ、RTDB購読も切れる |

したがって、**6.1 の監視者トラックは「監視者の動きを残す」機能であると同時に、
バックグラウンド実行の資格を得るための手段でもある。** 記録を有効にすれば、
画面を消しても記録が続く見込みになる。

これに伴う実装上の要件:

1. **Android の常駐通知の文言を、監視中は別のものにする。**
   現在は「Rowing Navigator が航行を記録中」で固定されており(`geo_service.dart:22`)、
   監視中に出ると事実と食い違う
2. **iOS では画面上部に青いインジケータが出る**(`showBackgroundLocationIndicator: true`)。
   監視者は陸上にいるため実害はないが、初回に説明する
3. **保証ではない。** バックグラウンドでの WebSocket 維持は最終的に OS の裁量であり、
   特に Android はメーカー独自の省電力機能でアプリを終了させることがある。
   **`recorder_gap` の記録は、この対策を入れたあとも必須である**(原則6)
4. **実機検証を完了するまで、UI では「継続する」と断言しない。**
   検証前は「画面を消すと記録が途切れることがあります」と表示し、
   検証後に文言を更新する(`geo_service.dart:23` の既存コメントと同じ姿勢)

### 6.4 重複排除と欠測検出

`MessageService.getMessagesStream` は1秒タイマーでも全艇を再emitするため、**重複が必ず来る**
(`use_coach_watch.dart:174` が timestamp 比較で同じ問題を避けている)。

- **重複排除キー**: `(boatId, sessionId, sequence)`。同じ組は1回だけ書く
- **欠測(艇側)**: 同一 `sessionId` 内で `sequence` が飛んだら `gap` イベント。
  飛び幅と時間幅を記録する
- **セッション交替**: `sessionId` が変わったら `boat_session_changed`。艇の再起動を意味する
- **消失**: `trailDurationSec` 相当のTTLを過ぎたら `boat_lost`
- **記録中断(監視端末側)**: `AppLifecycleState` の遷移で `recorder_paused` / `recorder_resumed`。
  再開時に空白時間を `recorder_gap` として書く

**艇側の欠測と監視端末側の中断は必ず別イベントにする。** 混ぜると、後から見たときに
「艇が消えた」のか「こちらが見ていなかった」のか判別できなくなる。

### 6.5 保存形式

**JSONL 追記型にする。** 既存 `SessionStoreService` は毎回JSON全体を書き直す方式だが、
2時間 × 12艇 = 最悪 43,200点(約5MB)になるため、その方式では O(n²) になる。

```
{documents}/practice_logs/{practiceId}/
  ├── meta.json      記録開始時に作成、終了時とチェックポイントで更新
  ├── track.jsonl    位置記録の追記(1行1点)
  └── events.jsonl   欠測・異常・ライフサイクルの追記
```

- `practiceId` は記録開始時刻ベース(`practice_20260728_0530`)
- 書き込みは `practiceLogFlushIntervalSec`(既定10秒)ごとにバッファをまとめて追記する。
  1点ごとのI/Oは監視スキャンと競合する
- `meta.json` は `practiceLogCheckpointIntervalSec`(既定60秒)ごとに更新する。
  アプリが強制終了しても、そこまでの記録は完全なJSONLとして残る
- 記録点が `maxPracticeLogPoints` に達したら**記録を止め、`recorder_limit_reached` を書く**。
  警告経路には影響させない

### 6.6 記録の開始・終了

- 「監視スタート」で記録も開始する。別ボタンにしない(監視中に記録し忘れる意味がない)
- 記録をしたくない場合のために、設定に「練習ログを記録する」トグルを置く(既定ON)
- 「監視終了」で `meta.json` を確定し、一覧へ出す
- 前回の未確定記録は次回起動時に検出し、`isComplete: false` として一覧へ出す
  (既存セッションの `session_recovery_detected` と同じ扱い)

## 7. 出力(ZIP)

`GpxExportService` と同じ流儀(`archive` + `share_plus` + `sharePositionOrigin` 検証)で生成する。

```
practice_20260728_0530.zip
├── practice_manifest.json
├── boats.csv
├── tracks.csv
└── events.jsonl
```

### practice_manifest.json

```json
{
  "practiceLogSchemaVersion": 1,
  "practiceId": "practice_20260728_0530",
  "teamId": "...",
  "recordedBy": "boat-1",
  "startedAt": "2026-07-27T20:30:00Z",
  "endedAt": "2026-07-27T22:15:00Z",
  "isComplete": true,
  "app": { "version": "1.0.0", "buildNumber": "..." },
  "device": { "platform": "ios", "operatingSystemVersion": "..." },
  "hazardProfile": { "version": 3, "sha256": "..." },
  "protocol": { "positionProtocolVersion": 1, "presentationStateAvailable": true },
  "boats": [
    { "alias": "boat-2", "sessionCount": 1, "pointCount": 3120,
      "firstSeenAt": "...", "lastSeenAt": "...",
      "gapCount": 4, "missingSeconds": 96,
      "capabilities": ["course", "accuracy", "session_sequence",
                       "display_name", "presentation_state"] }
  ],
  "recorderGaps": [ { "from": "...", "to": "...", "reason": "app_background" } ],
  "anonymized": false,
  "privacy": {
    "containsPreciseRoute": true,
    "automaticUpload": false,
    "scope": "team_members_only"
  }

```

`boats[].capabilities` に `presentation_state` が無い艇は、**`w` 列が空でも
「警告が無かった」とは読めない**。この区別が manifest の存在意義である。

### tracks.csv

全艇を1枚にまとめる。Excel でもそのまま時系列比較できる。

```
utc_time, elapsed_ms, boat_alias, session_id, seq, lat, lng, speed_mps,
course_deg, accuracy_m, battery, warn_band, warn_category, run_mode,
ashore, age_sec, source
```

- `source` = `live`(他艇受信) / `observer`(監視者自身)
- `age_sec` = 受信時点でのそのデータの古さ。適応送信の間隔が見える
- `warn_band` / `warn_category` は `w` を展開したもの。未対応版の艇は空

### events.jsonl

`{ "t": ..., "elapsedMs": ..., "type": "...", "details": {...} }` の1行1件。既存 `events.jsonl` と同じ形。

`type`: `gap` / `boat_session_changed` / `boat_lost` / `boat_anomaly` /
`recorder_paused` / `recorder_resumed` / `recorder_gap` / `recorder_limit_reached` /
`observer_position_unavailable`

### 匿名化

既定は**実名(displayName)を含める**。チーム内の検証が主用途であり、
誰の艇か分からないログでは事故検証にならない。
外部へ提出する場合のために、共有時に「艇名を伏せる」を選べるようにし、
選んだ場合は `boat-N` エイリアスへ置換する(既存 `gpx_export_service.dart:194` と同じ方式)。

## 8. 費用・容量

| 項目 | 見積もり | 枠 |
| --- | --- | --- |
| Firebase 追加費用 | **0**(既に受信しているデータを書くだけ) | — |

| 端末内容量 | 1練習あたり最大5MB程度 | `maxStoredPracticeLogs`(既定20)で上限 |

## 9. プライバシー

- **端末内保存のみ。自動アップロードはしない。** manifest の `automaticUpload: false` を維持する
- 共有は監視者の明示操作(共有シート)でのみ行う
- 記録対象はチームメンバーの位置であり、**本人以外の端末に保存される**点が
  既存の自艇セッションと異なる。監視モードの説明文に明記する
- `AccountDataDeletionService.deleteCurrentAccountAndData` に **`practice_logs` の削除を追加する**
  (現在は `SessionStoreService.deleteAllSessions` のみ)。
  ただし削除できるのは自分の端末に入っている記録だけであり、
  他人の端末に残った記録は消せない。この限界を `privacy_data_screen` に明記する

## 11. 守るべき不変条件(追加分)

1. **受信した `w` / `m` / `a` は、地図描画にも衝突評価にも渡さない。** 記録専用である(5.4)
2. **記録の失敗・遅延・容量超過が、警告経路と監視表示を止めてはならない**(原則1)
3. **欠測は必ずログに書く。** 空白を「そこに艇がいなかった」と読ませない(原則6)
4. **艇側の欠測と、監視端末側の中断は別イベントにする**
5. **監視中に Wakelock を保持しない。** 記録を続けるために常時点灯を使わない(設計原則1.4)。
   画面を消しても動き続けるかどうかは Wakelock ではなく位置ストリームの有無で決まる(6.3)
6. **`protocolVersion` は上げない。** 追加フィールドは省略可能かつ後方互換であり、
   版を上げる利益がない一方、混在期間の相互不可視というリスクだけが増える(5.3)
