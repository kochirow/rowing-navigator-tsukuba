## 2. 実施しなかったもの（判断と理由）

### 2-1. Release 3a（S3-01/02/03: S1 の改良と昇格）— **実施しない決定**

計画に明記された許容される結末である:

> S1 が §3 に合格しない場合、S2 primary のまま出荷してよい。
> 「Kalman を使うこと」自体は目的ではない。

**判断の根拠:**

1. Stage 2 で `primarySolution = PrimarySolution.conservative` が既定になっており、
   実害（停止時の前方飛ばし）は S2 primary によって既に解消している。
   S1 の改良は**精度の上積み**であって、安全上の未解決課題ではない。
2. Stage 3 §0-0b で決めたとおり、改変 S1 を評価するには
   raw 駆動の S1 再生が要る。Stage 1 でそれが達成できず、選択肢B
   （改変 S1 と S2 を同じ再生条件で比較）を既定にした。
   **その基盤を作るところから始まる作業であり、実機ログが無い状態で
   着手すると Stage 1 と同じ止まり方をする危険がある。**
3. 旧 S1 の性能はログの `filtered_*` に記録されており、次に実機ログが
   取れた時点で再判定できる。判断材料は失われない。

**記録すべき決定**: `primarySolution` は `conservative` のまま。
これは失敗ではなく決定である。次の実機ログで再判定する。

### 2-2. S3-09（カテゴリ横断の集約）— 見送り

S3-08 の読み上げ上限で、実測された害（逆走96回）は解消の見込みが立った。
集約は**さらに減らすための最適化**であり、
提示の中核（`SafetyOrchestrator`）へ追加の状態を持ち込む。
効果が測れない状態で安全経路の複雑さを増やす判断はしない。

次の実機ログで、読み上げ回数が §S3-10 の予算（12回/時）に収まらなければ着手する。

### 2-3. S3-14（`mooringAreas` の実測引き直し）— 見送り

計画では「Stage 2 完了後のログから停止点群を抽出して引き直す」としていた。

**Stage 2 完了後のログが存在しない。** 2026-08-06 のログは Stage 2 以前の
推定器（前方飛ばしのある S1）で記録されており、
そこから抽出した停止点群は**前方へ最大32m ずれた位置**を含む。

> **ずれた位置で引いた線を正解として固定してしまう。**
> これは計画の「やらないこと」に明記した禁止事項そのものである。

次の実機ログ（Stage 2 の推定器で記録されたもの）が取れてから実施する。

### 2-4. `AlertEpisodeManager` の全面導入 — 縮小して実施

計画では状態機械（`inactive → observing → announced → escalating → stable → cleared`）
を新設するとしていた。**読み上げ上限による打ち切りに縮小した。**

**理由**: 既存の `_ThreatPresentationContext` と `_GuidancePresentationContext` が
既にエピソード相当の意味（`audioEventId` の世代、再武装、保持時間）を持っている。
その上へ別の状態機械を重ねると、**同じ概念が2箇所に分かれ、
どちらが勝つかが順序依存になる**。これは Stage 1 の regression と同じ構造である。

計画の受け入れ基準（初報を落とさない／悪化で再通知できる／
サンプル数を増やしても初報は1回）は、縮小版でも満たしてテストで固定した。

### 2-5. S3-05 の幾何的な到達可能領域 — 予算での表現に留めた

計画では「点予測から領域予測へ」としていた。
実装は `ProtectionBudget` 由来の帯の拡大で表現している。

**受け入れ基準はすべて満たしている**（速度不明で領域が縮まない／
remote age で単調に増える／停止が分かっていれば広がらない）。

**`extrapolateToNow` の点前進は残した。** 計画では自艇と同じく
「点を進めるのをやめる」としていたが、他艇の速度は**相手の報告値**であり、
相手が止まれば報告速度も 0 になるので前へ進まない。
自艇で起きた「ローカルのフィルタが発散して速度状態が残る」という
病理は転移しない。速度が取れないときは `predictPosition` が 0 扱いで
点を動かさず、帯だけが広がる——これは計画の
「点を進めず領域を広げる」がすでに成立している状態である。

## 3. 実装中に見つかったもの

### 3-1. ゴールデンテストが規則の宣言と実挙動の不整合を検出した

`SuppressionRule` の全組み合わせテストを書いた時点で、
`uncertaintyOnly` と `mooringArea` が `other_boat` へ適用され得るのに
**相手速度を必須入力に宣言していない**ことが判明した。

インラインの述語（`_isOtherBoatAtRest`）では正しく見ていたので実挙動は
正しかったが、**宣言と実装が食い違っていた**。
これは 2026-08-06 の他艇無音化とまったく同じ構造である。宣言を実挙動へ合わせた。

### 3-2. S3-06 の初版テストが空振りしていた

`ThreatInfo.confidence` の既定が `definite` なので、
`gps_guard_entry` の reasonCode だけ付けても降格の分岐に入らない。
最初に書いたテストは**変更前のコードでも通る**状態だった。
`confidence: ThreatConfidence.uncertain` を明示し、
`candidate.confidence < 1.0` をテスト内で表明して、
降格経路を実際に通ることを固定した。

### 3-3. 危険区域プロファイルの sha256 は `firestore.rules` が固定している

`assets/data/sakuragawa_obstacles.json` を変えると
`test/firebase_rules_contract_test.dart` が落ちる。
ルールを配備し直すまで、アプリが新しいハッシュで書く共有校正値は
**サーバ側で拒否される**。

ルール配備は行える立場にないため、S3-15 の除外は設定値側へ置いた。
`ChannelLane.reverseGuidance` のフィールドは用意してあるので、
ルールを更新できるときにプロファイルへ移せる。
