### 2-1. Release 3a（S3-01/02/03: S1 の改良と昇格）— **実施しない決定**

計画に明記された許容される結末である:

> S1 が §3 に合格しない場合、S2 primary のまま出荷してよい。
> 「Kalman を使うこと」自体は目的ではない。

**判断の根拠:**

1. Stage 2 で `primarySolution = PrimarySolution.conservative` が既定になっており、
   実害（停止時の前方飛ばし）は S2 primary によって既に解消している。
   S1 の改良は**精度の上積み**であって、安全上の未解決課題ではない。
2. Stage 3 §0-0b で決めたとおり、改変 S1 を評価するには
   raw 駆動の S1 再生が要る。Stage 1 でそれが達成できず、選択肢B
   （改変 S1 と S2 を同じ再生条件で比較）を既定にした。
   **その基盤を作るところから始まる作業であり、実機ログが無い状態で
   着手すると Stage 1 と同じ止まり方をする危険がある。**
3. 旧 S1 の性能はログの `filtered_*` に記録されており、次に実機ログが
   取れた時点で再判定できる。判断材料は失われない。

**記録すべき決定**: `primarySolution` は `conservative` のまま。
これは失敗ではなく決定である。次の実機ログで再判定する。

### 2-5. S3-05 の幾何的な到達可能領域 — 予算での表現に留めた

**受け入れ基準はすべて満たしている**（速度不明で領域が縮まない／
remote age で単調に増える／停止が分かっていれば広がらない）。

**`extrapolateToNow` の点前進は残した。** 計画では自艇と同じく

点を動かさず、帯だけが広がる——これは計画の
「点を進めず領域を広げる」がすでに成立している状態である。

## 2-6. 事後レビューで見つかった、自分の実装の不足

Stage 3 完了後に自己レビューを行い、**2件の実質的な未達**を見つけた。
どちらもテストは緑で、コミットメッセージの記述が実態より強かった。

### F1【中】S3-05 の情報欠損ガードは、本番経路から到達できない

`speedUnknownMeters` / `headingUnknownMeters` は**常に 0 になる**。理由が2つ重なっている。

1. `RemoteBoatMessage` の検証が speed 欠損・非有限・範囲外を弾く
   （`speed == null → fail`）。受信した他艇の速度は必ず有効値である。
2. 仮に欠損しても、**`_usableBoat` が評価の手前で `0.0` へ正規化する**
   （`final speed = (b.speed.isFinite && b.speed > 0) ? b.speed : 0.0;`）。

テストが緑なのは、`pairProtectionBudget` を直接呼んで NaN を渡しているためで、
**production の呼出経路を再現していない**。S3-06 の初版テストが空振りしていたのと同じ形である。

**原則6 の本丸は `_usableBoat` の正規化のほうである。**
「速度が取れない」を「速度0」へ潰しているので、下流は両者を区別できない。
直すには 0 へ潰さず「不明」を型で運ぶ必要があり、
下流（`predictPosition` / `getStoppingDistance` / `ShipDomainService`）が
すべて有限値前提で書かれているため、**評価器の中核に触る変更**になる。

対応: 今回は直さず、`_usableBoat` と `_isSpeedKnown` にこの経緯をコメントで残した。
実装は防御的な二重化として残す（害はない）。次の作業項目とする。

### F2【中】S3-04 の「飽和の解消」は達成していない

コミットメッセージに「飽和した2.5m定数を置き換える」趣旨で書いたが、
`gnssMeasurementMeters` の `clamp(0, maxPairGpsCenterDistanceGuardMeters)` は**残したままである**。
達成したのは**内訳の分解と相対/絶対の合成規則**であって、飽和の解消ではない。

**ただし、これは残すのが正しい。** クランプを外すと
DESIGN_PRINCIPLES 3.2 の検算（狭所で 8+ 同士がすれ違うと最悪 13.90m 必要で、
レーン幅 12.5m を既に 1.4m 超過）がさらに悪化し、桜川の狭所で過剰警告になる。
外してよいかは **Stage 2 後の accuracy 分布を実機ログで確認してから**判断する。

対応: `ProtectionBudget` のクラスドキュメントへ「未達」として明記した。

### F3【低】`ChannelLane.reverseGuidanceEnabled` は常に true

除外は設定値 `reverseGuidanceDisabledLaneIds` 側だけで効いている。
フィールドは firestore.rules のハッシュ固定を解けるようになったときの
移行先として残してある。**現状は門が二重にあり、片方が常に開いている。**
意図的だが、片方だけ見て「無効化されている」と誤読しないこと。

### F4【情報】S3-06 の過剰警告リスクは実測で無視できる

`gps_guard_entry` 付きの他艇候補は 5端末・約6.5時間で **16サンプルのみ**。
うち `actionDeadline ≤ 7s`（＝降格廃止で連続音になる）は **4サンプル**で、
すべて A の 52〜53分の実遭遇（他艇 20〜26m 接近・DCPA 0〜1.7m）である。
**まさに鳴らしたかった場面**であり、過剰警告の増加はない。

### F5【情報】`_quieter` への置換は挙動不変

`visualOnly` は最も静かなので `_quieter(behavior, visualOnly) == visualOnly` が常に成り立つ。
低速静音の直接代入を `_quieter` に変えたのは、
**将来この規則の後ろに別の規則が入ったときの順序依存を消すため**で、現在の挙動は変えていない。

### F6【仕様変更・記録漏れだったもの】自艇速度が取れないと安定停止の静音が効かなくなった

`canSuppressAtRest` に `permitted(SuppressionRules.stableStop)` を掛けたので、
`ownSpeedMetersPerSecond` が null / 非有限のときは安定停止による静音が**適用されなくなった**。
従来はカテゴリだけで判定していたので適用されていた。

**原則6として正しい方向**（速度が取れないことを静音の根拠にしない）で、
音が増える側＝安全側の変化だが、当初の記録に書いていなかったので追記する。

### F7【重大・撤回】S3-15「開水面の逆走判定を外す」は誤った判断だった

**利用者の確認により、実機ログで鳴った逆走警告はすべて正しかった**
（本当に逆走していた）。したがって S3-15 は、**正しく働いていた安全機能を
止める変更**だった。撤回した。

**推論の誤り**: 「航跡の 17〜44% がどちらのレーンにも入っていない」を
根拠に「開水面では逆走判定が不安定」と結論したが、
**レーンから外れているときは判定が発火しない**。つまりレーンのずれが生むのは
**被覆不足（警告漏れ）であって誤発報ではない**。
過剰警告の指標として使えない統計で、過剰警告対策を正当化してしまった。

同一艇の2台が同じ時刻に同期して発火していた観測を
「検出は一貫している」と書きながら、結論では止める側へ倒していた。
**自分の分析の中に反証があったのに拾えていない。**

計画（Stage 3 §S3-15）の判定基準「レーン外率が 10% 未満にできなければ B案」
そのものが、測る対象を取り違えていた。**次に同種の判断をするときは、
「その統計は誤発報を測っているか」を先に確認する。**

対応: `reverseGuidanceDisabledLaneIds` を空に戻し、
DESIGN_PRINCIPLES 1.2b / 1.2c と CLAUDE.md の結論も訂正した。
うるささは F8 の頻度制御で解く。

### F8【方針変更】読み上げ上限を撤回し、2回1組のペース制御にした

F7 と同じ理由で、**回数で打ち切る方式も誤りだった**。
逆走は「入った」という一度きりの事実ではなく、**是正されるまで続く状態**である。
3回で打ち切ると、状態が続いているのに黙ることになり、警告漏れと同じになる。

`guidanceRepeatMaxCount` は `null`（無制限）へ戻した。
代わりに**頻度**で解く。

```
再生 → 5秒 → 再生   ← 1組（guidanceBurstCount = 2）
      ↓ 15秒
再生 → 5秒 → 再生
      ↓ 30秒
再生 → 5秒 → 再生
      ↓ 60秒（上限）
   ... 状態が続く限り鳴り続ける
```

一定間隔で鳴らし続けると聞き手はすぐ慣れて無視する。2回続く音で
「いま起きている」が伝わり、そのあとの静寂が次の組で「まだ続いている」を
再認識させる。静寂は組ごとに倍へ伸ばし、60秒で頭打ちにする
（完全には黙らない）。

5分間区域内に留まった場合: 均等5秒なら61回 → この方式で約12回。
**打ち切らずに約1/5へ減る。**

### F9【確認】徐行の定義は既存の定数と一致していた

利用者提案の「500m/5分より遅い」= 1.667 m/s は、既存の
`lowSpeedAudioMuteSpeedMetersPerSecond = 100 / 60` と**完全に同じ値**だった。
`lowSpeedMutedCategories` に `reverse` が入っているので、
**徐行時の逆走読み上げは既に止まっている**。

ログの艇速分布（全5端末 9,979 サンプル）は明確に二峰性で、
谷は **2.00〜2.25 m/s**。1.667 は谷より手前（漕航側）にあり、
静音を早く解除する安全側である。変更不要。

なお 96回の読み上げのうち**徐行中はわずか3回（3%）**、速度中央値 3.44 m/s。
**問題は漕いでいる最中に起きていた**ので、速度条件付きの制御では解決しない。

`confidence: ThreatConfidence.uncertain` を明示し、
`candidate.confidence < 1.0` をテスト内で表明して、
降格経路を実際に通ることを固定した。

### 3-3. 危険区域プロファイルの sha256 は `firestore.rules` が固定している
