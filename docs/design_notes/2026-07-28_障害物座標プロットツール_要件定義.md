## 0. この文書の位置づけと、既存実装から判明した重要事項

本書は、提示された要件案（利用環境・費用・公開範囲 / オブジェクト管理機能）を、
既存コードベースと突き合わせて具体化したものである。

要件案の「追加費用0円・localhost 専用・本人 1 名利用・秘密鍵を Mac 外へ出さない」
「Google Earth 相当の作図・ツリー・フォルダ・KML」は**全面的に採用する**。

一方、**出力仕様に関する 4 点は、要件案の前提が現行実装と食い違う**。
ここを直さずに実装すると、出力した JSON をアプリが読めないか、読めても
危険区域が川と反対側へ広がるか、現地で合わせた補正が二重に掛かる。

### 訂正1: 出力先は Firestore ではなく、アプリ同梱 JSON である

要件案 15 章は「1 ポリゴン = Firestore の静的障害物ドキュメント 1 件」としていた。
しかし現行の設計では、**固定危険区域は Firestore に保存しない**。

> 固定危険区域: `assets/data/sakuragawa_obstacles.json` を編集 → ビルド。Firestoreには保存しない
> — CLAUDE.md「危険区域データの管理」

Firestore（`temporary_obstacles`）が扱うのは**当日だけ共有する臨時危険区域**で、
24 時間で失効する。本ツールの主目的は恒久的な地形なので、
第一の出力先は `assets/data/sakuragawa_obstacles.json` とする。
臨時危険区域は**インポート元**としては一級の対象である（§7.5、§7.7）。

### 訂正2: 座標のキーは `latitude` / `longitude` ではなく `lat` / `lng`

```dart
// lib/services/preset_obstacle_service.dart:211
final lat = point['lat'];
final lng = point['lng'];
```

キー名を間違えると `points[i] is out of range` の `FormatException` になり、
プリセット読み込みが丸ごと失敗する。
Firestore 側（`GeoPoint`）は `latitude` / `longitude` なので、
**同じツール内に 2 つのキー規約が同居する**。型で区別する（§3.5）。

### 訂正3: 岸・橋・島・流木は「ポリゴン」ではなく、向きを持つ「基準線」である

`dangerZoneBaselines` の `points` は**完成ポリゴンではない**。
アプリは各辺（連続する 2 頂点）を長方形へ展開して危険区域を生成する。

```dart
// lib/services/legacy_danger_zone_generator.dart
final bearing = _bearing(start, end);
final waterBearing = bearing - 90.0;   // 進行方位の左 = 水面側
final landBearing  = bearing + 90.0;   // 進行方位の右 = 陸側
```

**頂点の並び順が、どちら側へ何メートル広がるかを決めている。**
向きが実際に効くのは片側距離が左右非対称な `shore` のみで、
`bridge` / `island` / `driftwood` / `testZone` は 5m / 5m の対称なので向きは無害である。

| kind | 水面側 | 陸側 | 向きが結果を変えるか |
| --- | --- | --- | --- |
| `shore` | 5.0 m | **15.0 m** | **変える** |
| `bridge` / `island` / `driftwood` / `testZone` | 5.0 m | 5.0 m | 変えない |

岸の頂点順を逆にすると川の中へ 15m 張り出す危険区域ができる。
桜川の狭所は川幅 35m・片側レーン 12.5m なので、
片側航路を潰して常時警告を発生させる＝設計原則4 の破壊に直結する。

**この方式は v4 でも維持する。** 岸は引き続き単一の基準線として持つ。
本ツールは岸だけを「向きを持つ線」として扱い、
拡張後の実形状をプレビューし、向きを可視化・反転・自動検出する（§5.1）。
島・橋・流木・テスト区域は向きの概念を出さず、図形として描かせる（§5.2）。

判断の経緯（全図形化を検討して見送った理由）は §5.9 に残す。

### 訂正4: 座標を 1 点動かすと、更新すべきファイルは 6 つある

`sakuragawa_obstacles.json` の内容は、以下の場所に**手書きで複製されている**。

| 場所 | 何が複製されているか |
| --- | --- |
| `lib/config/hazard_profile_config.dart` | ファイル全体の SHA-256、`currentHazardProfileDataVersion` |
| `lib/models/shared_safety_calibration.dart` の `allowedSourceIds` | 全 21 件の `id` |
| 同 `vertexPointCounts` | 全 21 件の**頂点数**（`shore_north: 153` など） |
| 同 `documentId` | プロファイルの世代（現在 `fixed_obstacle_calibrations_v2`） |
| `firestore.rules` の `validScaledVertexOffsets` | 全 21 件の `id` と頂点数を再度ベタ書き |
| 同 `baseProfileVersion == 4` / `baseProfileSha256 == '<hash>'` | version と SHA-256 |

さらに `_calibrationsFromFirestore` は**固定長の位置配列**で校正値を読む。

```dart
// lib/models/shared_safety_calibration.dart:309
if (rawOffsets is! List || rawOffsets.length != allowedSourceIds.length) {
  throw const FormatException('Invalid calibration offset list');
}
```

配列に名前は入っておらず、**「何番目か」が名前の代わり**である。
したがってオブジェクトを 1 つ追加すると、更新していない端末は
校正値を一切読めなくなる。頂点数を変えても Rules の固定値と食い違って書き込みが拒否される。
`documentId` が `v2` なのは、まさにこの理由で v1 を作り直したためである。

**対策は 2 つある。両方とも v4 で実施する。**

1. 影響を受ける全ファイルの新しい値を機械的に算出し、まとめて引き渡す
   **変更適用パッケージ**を成果物とする（§9）
2. 固定長配列をやめ、**名前付きマップへ移行する**（§10.6）。
   これにより、以後は要素数が変わっても壊れなくなる

同時に、手書き複製そのものを減らす生成器を導入する（§10.8）。

### v4 の中心的な設計判断: 暗黙の導出を明示データへ置き換える

現行実装には、**岸の基準線から暗黙に導出されている機能が 2 つ**ある。

| 機能 | 現行の導出 | 問題 |
| --- | --- | --- |
| 陸上判定 | 最寄りの岸線分からの符号付き距離。右手が陸 | 岸データが途切れる領域で判定できない。中州の上でも「水上」。湾曲部の内側で符号が不安定 |
| 航路中心線 | 左右の岸の中点 | **中州を貫通する。** 実際の航路は障害物に応じて中心からずれる |

**v4 では、この 2 つを明示プロットのデータへ置き換える。**

| 新データ | 役割 |
| --- | --- |
| `ashoreAreas`（陸上エリア＝警告停止エリア） | 陸上判定の唯一の根拠。この中にいるときだけ音を止める |
| `channelCenterline`（航路中心線） | 予測経路の生成。手動プロット |
| `navigableWaters`（航路・レーン） | 表示と検証。初期版では安全判定に使わない |

**岸の基準線と危険区域の生成経路は一切変更しない。**
`LegacyDangerZoneGenerator`・`DangerZoneSettings`・`StaticObstacleIndex` は
現行のまま残る。安全経路への変更は `AshoreDetector` と中心線の取得だけに限定される。

この置き換えには、副次的だが重要な利点がある。
**陸上エリアが無ければ「陸上ではない」＝音を鳴らし続ける**、という
フェイルセーフが自然に成立する。データ欠損が音を止める方向へ働かない
（設計原則6・不変条件3）。

## 1. 目的とスコープ

### 1.1 目的

Apple Maps の航空写真を見ながら、桜川の危険区域・陸上エリア・航路を
名前付きオブジェクトとして作成・再編集し、
Rowing Navigator がそのまま読み込める `sakuragawa_obstacles.json` と、
その反映に必要な変更適用パッケージを生成する。

現状このデータは旧 iOS アプリからの移植分を手作業で編集している。
`shore_north` は 153 頂点、`shore_south` は 107 頂点あり、
テキストエディタでの編集は現実的ではない。

### 1.2 運用サイクル

本ツールは、以下の一巡を成立させるために作る。単発の作図ツールではない。

```text
  ①  Mac でプロット・編集
        ↓  変更適用パッケージ（§9）
  ②  AI エージェントがシステムファイルを更新 → ビルド → 配布
        ↓
  ③  現地でアプリを使う
        ├─ 固定区域の位置がずれていた → アプリ内の校正機能で調整（Firestore へ共有）
        └─ 新しい流木を発見 → 臨時危険区域として登録（Firestore、手動削除まで保持）
        ↓  インポート（§7）
  ①' Mac で「現地の調整結果」を取り込み、恒久データへ昇格させる
```

**③ → ①' の経路が中核機能である。**
現状、現地での調整結果は Firestore 上の差分としてしか存在せず、
アプリ同梱データへ反映する手段がない。臨時危険区域は 24 時間で消える。
つまり**現地で得た知見が、放っておくと失われる**。

### 1.3 このツールが安全上果たす役割

本ツールが出力するのは、衝突警告と陸上判定に使われるデータそのものである。
座標が数メートルずれれば、警告が鳴らない、あるいは常時鳴る。
陸上エリアを誤れば、水上で音が止まる。
**品質要件は「作図しやすさ」より「出力の正しさの検証可能性」を優先する。**

### 1.4 スコープ内

- Apple Maps 航空写真上での作図、名前付きオブジェクトの独立管理、フォルダ階層
- 岸の基準線（向きあり）/ 閉じた基準線 / ポリゴン / 折れ線 / ポイントの作成・再編集
- 基準線から生成される実際の危険区域形状のプレビュー
- **陸上エリア・航路中心線・航路ポリゴンの作図**（v4 の新規、§5.3〜5.5）
- 同梱プロファイル・Firestore 共有校正・Firestore 臨時危険区域のインポート（§7）
- 臨時 → 固定への昇格、校正差分の焼き込み（§7.7）
- `sakuragawa_obstacles.json` と**変更適用パッケージ**の生成（§8、§9）
- GeoJSON / KML の入出力、IndexedDB 自動保存

### 1.5 スコープ外（初期版）

要件案 10 章の対象外リストを維持する。加えて:

- **Firestore への書き込み**。読み取り専用とする（§7.6）
- 片側距離（waterSide / landSide）の編集。アプリ内設定の担当であり、
  ツールは既定値でのプレビュー表示のみ行う
- `lane`（南北レーン）を使った右側通行の判定。データとして持つだけにする
- `warningAudio` の音声アセット自体の作成
- `point` / `polyline` からのバッファ生成（将来拡張、§5.7）
- 3D・過去画像・ツアーなど Google Earth の非作図機能

## 3. データモデル

### 3.1 プロジェクト

```ts
type Project = {
  schemaVersion: 3;
  id: string;                          // proj_<uuid>
  name: string;
  // --- プロファイルのトップレベル情報（書き戻し時に失わないため保持する）
  area: string;                        // 例: 桜川（茨城県土浦市）
  profileVersion: number;              // 既定 4
  source: string;
  notice: string;
  howToEdit: string;
  defaultObstacleProximityCautionMeters: number;
  // --- インポート元の記録（§9 の差分算出、§7.8 の二重適用防止に使う）
  importedFrom: ImportProvenance;
  folders: Folder[];
  objects: MapObject[];
  camera: { center: Coordinate; distance: number };
  selectedObjectId: string | null;
  createdAt: string;
  updatedAt: string;
};

type ImportProvenance = {
  profileSha256: string | null;        // 読み込んだ時点の同梱JSONのSHA-256
  profileVersion: number | null;
  calibrationRevision: number | null;  // 共有校正文書の revision
  calibrationFetchedAt: string | null;
  temporaryFetchedAt: string | null;
  teamId: string | null;
};
```

`area` が空だと `Hazard profile area is missing` で読み込みが失敗する
（`preset_obstacle_service.dart:233`）ため、必ず保持する。

### 3.2 フォルダ

```ts
type Folder = {
  id: string;                 // fld_<uuid>
  name: string;
  parentFolderId: string | null;
  expanded: boolean;
  visible: boolean;
  locked: boolean;
  order: number;
};
```

フォルダは専用のレイアウトファイルとして永続化し、アプリ側も認識する（§10.9）。
ただし `sakuragawa_obstacles.json` 自体には書かない。理由は §10.9 に記す。

### 3.3 オブジェクト

```ts
type MapObject = {
  id: string;                       // obj_<uuid>（ツール内部の一意ID）
  exportId: string;                 // プロファイルの "id"。例: shore_north
  name: string;                     // プロファイルの "name"。例: 北の岸
  description: string;
  kind: ObjectKind;                 // §3.4
  geometry: Geometry;               // §3.5
  warningAudio: string | null;      // 例: audio/bridge_warning.mp3
  parentFolderId: string | null;
  visible: boolean;
  locked: boolean;
  order: number;                    // プロファイル配列内の順序（§7.4 の注意点）
  verificationStatus: VerificationStatus;
  origin: ObjectOrigin;             // どこから来たか（§7）
  style: ObjectStyle;
  createdAt: string;
  updatedAt: string;
};

type ObjectOrigin =
  | { kind: "profile" }                                   // 同梱JSON由来
  | { kind: "drawn" }                                     // ツールで新規作図
  | { kind: "temporary"; docId: string; createdAt: string; expiresAt?: string }
  | { kind: "calibrated"; baseExportId: string; revision: number };
```

**`id` と `exportId` を分ける理由**: プロファイルの `id` は
`SharedSafetyCalibrationState.allowedSourceIds` の要素であり、
Firestore Rules の allowlist にも書かれ、端末内の校正値と
`FixedObstacleWarningSettings` のキーでもある。
`exportId` を変えると現地で合わせたオフセットと「この区域の警告を切る」設定が
迷子になり、Rules 違反で共有校正の公開が失敗する。
変更時には**影響範囲を列挙した警告**を出す（§11.3）。

`exportId` の制約（`preset_obstacle_service.dart:250`）:

- 非空の文字列、128 文字以下
- **全配列を横断して**一意（`dangerZoneBaselines` / `obstacles` /
  `ashoreAreas` / `navigableWaters`）
- 慣習として `[a-z0-9_]+`

### 3.4 オブジェクト種別

プロファイルの `kind` に一対一で対応させる。**ツール独自のカテゴリ体系を作らない。**

**危険区域**（現行のまま。v4 で変更なし）:

| `kind` | 出力先配列 | ジオメトリ | 編集モード | 表示名 | 生成される区域 |
| --- | --- | --- | --- | --- | --- |
| `shore` | `dangerZoneBaselines` | `baseline`（開いた線） | **向きのある線** | 岸 | 各辺 → 長方形。水面側 5m / 陸側 15m |
| `bridge` | `dangerZoneBaselines` | `baseline`（閉じた環） | 図形 | 橋 | 各辺 → 長方形。内外 5m |
| `island` | `dangerZoneBaselines` | `baseline`（閉じた環） | 図形 | 中州 | 各辺 → 長方形。内外 5m |
| `driftwood` | `dangerZoneBaselines` | `baseline`（閉じた環） | 図形 | 流木 | 各辺 → 長方形。内外 5m |
| `testZone` | `dangerZoneBaselines` | `baseline`（閉じた環） | 図形 | テスト区域 | 各辺 → 長方形。内外 5m |
| `curve` | `obstacles` | `polygon` | 図形 | カーブ | ポリゴンそのまま（区域進入イベント） |
| `reverse` | `obstacles` | `polygon` | 図形 | 逆走注意区域 | ポリゴンそのまま（区域進入イベント） |
| `generic` | `obstacles` | `polygon` | 図形 | 危険区域 | ポリゴンそのまま |

**向きのある線として扱うのは `shore` だけである。**
他はすべて図形として描き、UI にリング方向・矢印・反転ボタンを出さない
（片側距離が左右対称なので向きが結果を変えないため）。

**危険区域ではないデータ**（v4 で新設）:

| `kind` | 出力先配列 | ジオメトリ | 表示名 | 役割 |
| --- | --- | --- | --- | --- |
| `ashoreArea` | `ashoreAreas` | `polygon` | **陸上エリア（警告停止エリア）** | **陸上判定の唯一の根拠**（§10.4） |
| `navigableWater` | `navigableWaters` | `polygon` | 航路（水面） | 表示・検証。初期版では安全判定に使わない |
| `lane` | `navigableWaters` | `polygon` | 航路レーン（南／北） | 表示のみ。将来の右側通行判定 |

**これらは危険区域ではない。**
`StaticObstacleIndex` へ登録せず、衝突判定へ渡さない。
混入すると水面や陸地の全体が危険区域になり、常時警告になる。
§10.3 の不変条件として明記する。

加えて、プロファイルの単独フィールドを 3 つの特殊オブジェクトとして扱う。
いずれも 0 個または 1 個で、複製・複数作成の対象外とする。

| `kind` | 出力先 | ジオメトリ |
| --- | --- | --- |
| `practiceArea` | `practiceArea.points` | `polygon`（3点以上） |
| `operationalCoverage` | `operationalCoveragePolygon.points` | `polygon`（3点以上） |
| `channelCenterline` | `channelCenterline.points` | `polyline`（2点以上） |

**`channelCenterline` は v4 で必須になる。**
現在このフィールドは存在せず、アプリは左右の岸基準線から自動導出している
（`preset_obstacle_service.dart:644-660`）。v4 では**自動導出を削除する**（§10.5）。
中心線は予測経路の生成に使われ、提示ポリシー全体がこれを前提にしている
（CLAUDE.md「提示ポリシー」末尾）。**手動でプロットする。**

### 3.5 ジオメトリと座標

```ts
type Geometry = BaselineGeometry | PolygonGeometry | PolylineGeometry | PointGeometry;

/** 向きを持つ基準線。頂点順が水面側/陸側を決める（訂正3） */
type BaselineGeometry = {
  type: "baseline";
  points: Coordinate[];       // 2 点以上、1000 点以下
  closed: boolean;            // true なら書き出し時に先頭点を末尾へ複製する
};

type PolygonGeometry  = { type: "polygon";  points: Coordinate[] };   // 3 点以上
type PolylineGeometry = { type: "polyline"; points: Coordinate[] };   // 2 点以上
type PointGeometry    = { type: "point";    point: Coordinate };

/** プロファイル形式。内部表現は常にこちらを使う */
type Coordinate = { lat: number; lng: number };

/** Firestore 形式。io/firestore.ts の境界でのみ現れ、即座に Coordinate へ変換する */
type GeoPointLike = { latitude: number; longitude: number };
```

内部表現を `lat` / `lng` に統一し、`latitude` / `longitude` は
Firestore 入出力の境界だけに閉じ込める。境界を 1 ファイルに限定すれば、
訂正2 の取り違えはそこだけを見ればよくなる。

**`closed` の実データ上の根拠**（現行 `sakuragawa_obstacles.json` の全件調査）:

| id | kind | 点数 | 先頭==末尾 |
| --- | --- | --- | --- |
| `shore_north` | shore | 153 | **false** |
| `shore_south` | shore | 107 | **false** |
| `bridge_*`（7件） | bridge | 5 | true |
| `island_sakuragawa_bridge` / `island_upstream` | island | 9 / 12 | true |
| `driftwood_estuary` | driftwood | 6 | true |
| `test_zone_land` | testZone | 5 | true |
| `curve_1`〜`curve_7` | curve | 5〜7 | true |
| `reverse_main_channel` | reverse | 59 | true |

岸だけが開いた折れ線で、他はすべて閉じた環である。
環を閉じ忘れると**最後の辺の長方形が生成されず、そこだけ危険区域に穴が空く**
（`LegacyDangerZoneGenerator` は `points.length - 1` 本の辺しか作らない）。
警告漏れであり目視では気づきにくいので、`closed` を明示フィールドにする。

### 3.6 確認状況

```ts
type VerificationStatus =
  | "draft"           // 作図しただけ
  | "aerial_only"     // 航空写真で確認済み
  | "field_verified"  // 現地で確認済み
  | "field_calibrated"// 現地でアプリの校正機能により調整済み（§7.3 由来）
  | "needs_review";   // 要再確認
```

プロファイル本体には出力しない。レイアウトファイル（§10.9）と
KML の `<description>` に保持する。
`draft` を含んだまま書き出そうとした場合は確認を求める。

## 4. 座標の出力形式

### 4.1 内部表現

- WGS84 の 10 進度。度分秒は扱わない
- IEEE 754 倍精度の `number`。文字列で持たない
- 配列 `[lat, lng]` を使わない。GeoJSON の `[lng, lat]`、KML の `lng,lat` と
  取り違えるため、常に名前付きフィールドで持つ

### 4.2 プロファイル出力時の丸め

**小数点以下 7 桁に丸める。**

- 7 桁 = 緯度方向で約 11mm。GNSS の実用精度（数 m）に対して十分細かい
- 8 桁以上は無意味な桁を diff に載せるだけ。実際 `test_zone_land` は 9 桁を持つ
- `Math.round(v * 1e7) / 1e7` ではなく `Number(v.toFixed(7))` を使う
- 末尾の 0 は落とす（`140.1820000` → `140.182`）

### 4.3 座標の妥当性

`preset_obstacle_service.dart:213-221` と同一の検査を書き出し前に行う。

```ts
isFinite(lat) && isFinite(lng) && lat >= -90 && lat <= 90 && lng >= -180 && lng <= 180
```

加えて桜川用の範囲チェックを**警告レベル**で行う（`operationalCoveragePolygon` 由来）:

```text
lat  36.05 〜 36.10 ／ lng 140.09 〜 140.23
```

さらに `driftwood_estuary` は `ManagedHazardState` がより狭い範囲を強制している
（`managed_hazard_model.dart:19-22`）。この外へ動かすとアプリ側の変形が拒否される。
エラーとして扱う。

```text
lat 36.060 〜 36.100 ／ lng 140.195 〜 140.230
```

### 4.4 ファイル整形

現行の `sakuragawa_obstacles.json` は**整形が 2 種類混在している**。
`dangerZoneBaselines` は各座標が 4 行に展開され、`obstacles` は
`{"lat": …, "lng": …}` の 1 行形式である。

本ツールは**単一の正規形**で書き出す:

- インデント 2 スペース、座標オブジェクトは 1 行形式
  （4 行展開だと `shore_north` だけで 600 行を超え、diff が読めない）
- キー順を固定。トップレベルは `version, area, source, notice, howToEdit,
  defaultObstacleProximityCautionMeters, practiceArea, operationalCoveragePolygon,
  channelCenterline, ashoreAreas, navigableWaters, dangerZoneBaselines, obstacles`。
  各要素は `id, name, kind, warningAudio, points`
- UTF-8、BOM なし、LF、日本語をエスケープしない、末尾に改行 1 つ

**整形の正規化は、v4 の新データ追加と同じコミットで一度に行う。**
どうせ SHA-256 が変わるため、分けても得がない。

**`currentHazardProfileDataVersion` は、既存座標を動かさない限り上げない。**
新しい配列（`ashoreAreas` / `navigableWaters` / `channelCenterline`）の追加は
既存の危険区域の座標の意味を変えないので、**現地で合わせた校正値は有効なまま残る**。
これは v4 の重要な利点である（全図形化案では全員の校正がリセットされていた）。

岸の形を航空写真から引き直すなど、既存座標を動かす場合にのみ version を上げる。
判定はツールが差分から自動で行う（§9.2）。

### 4.5 出力の完全性

書き出しは全体置換とする。読み込んだプロファイルの未知フィールドは
プロジェクトに保持し、そのまま書き戻す。
将来アプリ側にフィールドが追加されたとき、ツールで一度開いただけで
それが消える事態を防ぐ。

## 5. 作図機能

### 5.1 岸の基準線（向きのある線）の作図——最重要

`shore` のみがこのモードで作る。

**必須のプレビュー**: 作図中および選択中、`LegacyDangerZoneGenerator` と
**同一のアルゴリズム**で生成した長方形群を地図上へ半透明で重ねる。
利用者が見るべきは基準線ではなく、**実際に警告を出す形状**である。

```text
辺 i について:
  bearing      = 初期方位角(start → end)
  waterBearing = bearing - 90
  landBearing  = bearing + 90
  矩形 = [ dest(start, waterBearing, waterSide), dest(end, waterBearing, waterSide),
           dest(end,   landBearing,  landSide),  dest(start, landBearing, landSide) ]
  dest は球面（地球半径 6371000m）の測地線公式
```

移植の正しさは **Dart 実装との数値一致テスト**で担保する（§11.5）。

**プレビューに使う既定の片側距離**（`danger_zone_settings.dart`）:

| kind | 水面側 | 陸側 |
| --- | --- | --- |
| `shore` | 5.0 m | 15.0 m |
| `bridge` / `island` / `driftwood` / `testZone` | 5.0 m | 5.0 m |

利用者はプレビュー用の値をスライダで変えられるが、**プロファイルへは出力しない**
（アプリ内設定の担当領域）。UI に「この値は確認用です」と明記する。
共有校正をインポートしている場合は、そこに含まれる `dangerZoneOffsets` を
初期値として使う（現地で調整した値でプレビューできる）。

**向きの可視化**:

- 基準線上に一定間隔で進行方向の矢印を描く
- 水面側の拡張を青系、陸側を茶系で塗り分ける
- ツールバーに「向きを反転」ボタン。押すと `points` を反転し、プレビューが即座に入れ替わる
- 生成区域の陸側が `practiceArea` や `navigableWater` の内部へ食い込んでいる場合は
  「向きが逆の可能性があります」と警告する（§11.2）

**v4 で、向きの影響範囲は「危険区域の形」だけに縮小する。**
v3 までは岸の向きが陸上判定の符号と中心線の導出にも波及していたが、
陸上エリアと中心線を明示データへ移すため、その 2 つは向きから切り離される。
それでも川へ 15m 張り出す事故は残るので、検証は維持する。

**閉じた環の扱い**: `closed = true` のとき、UI 上は最終点と始点を結ぶ辺も
編集対象とし、`points` 配列には始点の複製を持たない。複製の付与は書き出し時に行う。

### 5.2 図形モード（閉じた基準線・危険区域ポリゴン）の作図

`bridge` / `island` / `driftwood` / `testZone` / `curve` / `reverse` / `generic` /
`practiceArea` / `operationalCoverage` はこのモードで作る。

- クリックで頂点追加、3 点以上で確定可能。Enter で保存、Escape で破棄
- **リング方向・矢印・反転ボタンを一切表示しない**
- 自己交差を検出して警告する
- 閉環（先頭点の複製）は書き出し時に付与する。編集中は保持しない

**閉じた基準線（`bridge` / `island` / `driftwood` / `testZone`）のプレビュー**は
§5.1 と同じ矩形生成で行う。結果は輪郭線を中心とした幅 10m の帯になり、
**内部は危険区域にならない**。これはデータ形式の帰結なので、
利用者が誤解しないよう帯として正確に描く（§18.2-4 の未確定事項も参照）。

### 5.3 陸上エリア（警告停止エリア）の作図——v4 の新規・安全上重要

`ashoreArea` は**陸上判定の唯一の根拠**であり、
この中にいると判定されている間だけ音が止まる。

**作図の指針**:

- 艇を陸へ上げる場所を覆う。艇庫前、スロープ、桟橋、艇置き場、
  そこへ至る通路など、**「艇がそこにあれば漕いでいない」場所**
- **水面を含めない。** 水上にいるのに音が止まるのは、
  本アプリで最も重い失敗である
- 桟橋の扱いは慎重に。桟橋に着けている艇はもう漕いでいないので含めてよいが、
  桟橋の脇の水面を含めると、着艇待ちで浮いている艇の音が止まる
- 複数のポリゴンへ分けてよい。艇庫・上流の休憩所などを別オブジェクトにすると、
  表示・編集がしやすい

**専用の表示**:

- 他のオブジェクトと明確に違う色（例: 赤系のハッチング）で描く
- 陸上エリアと `navigableWater` / `practiceArea` の重なりは、
  **地図上で見えるように描くだけにする。検査も警告もしない**（下記の優先順位）
- 陸上エリアの縁から内側 12m（`ashoreLandSideMarginMeters`）の線を
  点線で重ね描きする。**この線より内側に入って初めて陸上判定が始まる**ので、
  実効的な境界がどこかを見えるようにする

**重なりの優先順位: 陸上エリアが最優先である。**

岸の延長距離によっては、陸上エリアが `navigableWater` や `practiceArea` と
重なることがある。**重なった領域は陸上として扱い、警告音を鳴らさない。**

- 陸上判定は `ashoreAreas` だけで決まる。
  `navigableWater` / `practiceArea` は陸上判定に一切影響しない（§10.4）
- したがって重なりはエラーでも警告でもなく、**定義された動作**である
- 重なりの程度が支障のない範囲に収まっているかは、作図する人の判断に委ねる。
  ツールは重なりを見えるように描くだけで、検査はしない

**航跡ログとの照合は行わない。**
航行の記録は**艇を担いだ陸上から開始する**ため、航跡が陸上エリアを通るのは正常である。
「航跡が陸上エリアに入っていたら広すぎる」という検査は必ず発火するので、設けない。
陸上エリアは、確実に陸上である場所だけを登録する運用で担保する。
（航跡の重ね描き自体は、中心線の作図（§5.4）と写真のずれ確認（§11.4）に使う）

### 5.4 航路中心線の作図——v4 の新規・安全上重要

`channelCenterline` は予測経路の生成に使われる。
提示ポリシー全体がこれを前提にしている。

> この提示ポリシーは航路中心線予測が前提。直線予測のままだと、5m/s で 7〜10 秒先
> （35〜50m）はカーブで外岸へ 5m 以上膨らみ、蛇行区間のたびに音が鳴ってしまう。
> — CLAUDE.md「提示ポリシー」

**作図の指針**:

- **「川の幾何学的中心」ではなく「艇が実際に進む線」を引く。**
  これが自動導出をやめる理由そのものである
- **中州を貫通させない。** `island_upstream` は 122m × 149m ある。
  幾何学的中心を通すとここを突き抜ける
- 橋脚を避ける
- 頂点は詰めすぎない。曲率が滑らかに変化するよう、
  カーブで密に、直線区間で疎に置く

**補助機能**:

- 既存の自動導出（`ChannelCenterline.fromShorelines`）の結果を
  **読み取り専用の下敷きとして重ね描きし、そこから引き始められる**ようにする。
  ゼロから引くより速く、どこが中州を貫通しているかも一目で分かる
- 実機の航跡ログを重ね描きする。**これが最も信頼できる基準である**——
  実際に艇が通った軌跡の中央が、求める中心線に近い
- 中心線が `island` / `bridge` の基準線が作る区域と交差する場合は警告する（§11.2）

### 5.5 航路（水面）ポリゴンの作図

`navigableWater` と `lane` は、**初期版では安全判定に使わない**。
用途は以下に限る。

- 地図表示
- 岸の基準線の向き検査（§11.2）——危険区域が航路へ大きく食い込んでいないか
- 将来の右側通行判定（§18.2-3）

旧 iOS アプリは航路（逆走注意エリア）と南北のレーンを図形で持っていた。
`lane_south` / `lane_north` はその構造を再現するものである。

**安全判定に使わないと決めているので、多少の粗さは許容する。**
陸上エリアと違い、誤っても音の開始・停止に直結しない。

### 5.6 頂点編集

- ドラッグで移動。Shift 併用で微調整
- 辺の中点をクリックして頂点を挿入、Delete で削除（最小点数を下回る削除は拒否）
- 緯度・経度の数値直接入力、頂点順の反転、図形全体の平行移動、Undo / Redo

**頂点数を変えると `vertexPointCounts` と Firestore Rules に波及する**（訂正4）。
ただし §10.6 の名前付きマップ移行後は、
**頂点数の変化が他の障害物の校正値を巻き込まなくなる**。
波及するのは生成される定数と Rules だけになり、
変更適用パッケージが自動で算出する（§9）。

`shore_north` の 153 頂点を扱うため、**頂点ハンドルは表示領域内のものだけ描画する**。

### 5.7 プロファイルへ出力できない図形

`point` と、`channelCenterline` 以外の `polyline` を出力しようとした場合:

```text
このオブジェクトは Rowing Navigator の危険区域として出力できません。
ポイント・折れ線に対応する形式がプロファイルにないためです。
ポリゴンまたは基準線へ変換してから出力してください。
```

将来「指定幅のバッファを付けてポリゴン化」を足せるよう、
`Geometry` を判別可能なユニオン型にしておく。初期版では実装しない。

### 5.8 頂点の間引き・追加

- Douglas–Peucker による間引き（許容誤差をメートルで指定、既定 0.5m）。
  適用前に「何点が何点になるか」を提示し、間引き後の形状を差分表示する
- 隣接頂点が極端に近い（既定 0.3m 未満）箇所の検出と統合

**間引きは安全側の操作ではない**（形状が単純化され、実際の岸より水面側へ後退しうる）。
既定では実行せず、明示操作でのみ行う。実行後は `verificationStatus` を
`needs_review` へ落とす。

### 5.9 設計判断の記録: 全図形化を検討し、見送った

**検討した案**: 岸・橋・島・流木をすべて「線」ではなく「図形」として持ち、
`dangerZoneBaselines`（基準線 + 自動展開）を廃して完成ポリゴンへ寄せる。
陸上判定は航路ポリゴンの内外で行う。

**結論: 見送る。基準線方式を維持し、陸上判定と中心線だけを明示データへ置き換える。**

この検討自体は無駄ではなかった。**「岸の線が 3 つの役割を兼ねている」**
という問題が明確になり、そのうち 2 つ（陸上判定・中心線）を
切り離すという v4 の設計に至った。

#### 見送った理由

**1. 危険区域の生成経路を丸ごと作り直す必要がなくなる**

全図形化は `PresetObstacleService`・`LegacyDangerZoneGenerator`・
`DangerZoneSettings`・`StaticObstacleIndex` の登録経路——
**安全経路の中核 4 つ**——を同時に書き換える改修だった。
陸上判定と中心線を明示データへ移すだけなら、
安全経路への変更は `AshoreDetector` と中心線の取得の 2 箇所に限定される。

**2. 現地校正が失われない**

全図形化は座標の意味を変えるため `currentHazardProfileDataVersion` の
引き上げが必須で、**全員の校正値がリセットされる**。
v4 は既存座標を動かさないので、校正値は有効なまま残る（§4.4）。

**3. 空間索引の分解が不要**

`StaticObstacleIndex` は外接矩形をセル 40m のグリッドへ登録する。
延長 3.5km の岸ポリゴン 1 枚では外接矩形が水域全体を覆い、
毎回の問い合わせで必ず返る。全図形化にはポリゴンを凸片へ分解する
新しい仕組みが要った。基準線方式なら、辺ごとの矩形分割が
そのまま索引に適した粒度になっている。

**4. 片側距離の実行時調整が残る**

`DangerZoneSettings` により kind ごとに 0〜30m で変更でき、チームで共有される。
川幅 35m の狭所で「水面側 5m か 15m か」は、
常時警告になるか見逃すかを分ける最重要のつまみである。

**5. 作図の手間が増えない**

全図形化では汀線と陸側の縁を二重に描く必要があり、
`shore_north` だけで 153 → 300 点超になる見込みだった。

#### 見送りに伴い残る制約

- **岸の向きは依然として重要である。** 逆にすると川へ 15m 張り出す。
  ただし影響は危険区域の形だけに縮小する（§5.1）
- **中州の内部は危険区域にならない。** 閉じた環に片側 5m の帯を作る仕組みのため、
  `island_upstream` の内部に約 112m × 139m の穴が残る。
  艇は必ず帯を横切るので連続掃引が捉えるが、
  GPS が数秒欠測して内側で再捕捉した場合は警告が出ない。
  §18.2-4 の未確定事項として残す

## 7. インポート

**v2 の中核機能。** §1.2 の運用サイクルにおける ③ → ①' の経路を成立させる。

### 7.1 3 つの取り込み元

| 取り込み元 | 実体 | 何が得られるか |
| --- | --- | --- |
| A. 同梱プロファイル | `assets/data/sakuragawa_obstacles.json` | 現在の恒久データの基準形状 |
| B. 共有校正 | Firestore `teams/{teamId}/managed_hazards/fixed_obstacle_calibrations_v2` | 現地でアプリの校正機能により調整した**差分** |
| C. 管理流木 | Firestore `teams/{teamId}/managed_hazards/fixed_driftwood_01` | 流木の**変形パラメータ**（中心・拡大・回転） |
| D. 臨時危険区域 | Firestore `teams/{teamId}/temporary_obstacles` | 現地で登録した**当日限りの区域**（24 時間で失効） |

**B と C は座標ではなく差分・パラメータである。** ここを取り違えると
二重適用（§7.8）を起こす。取り込み時には必ず A を基準に適用して実座標を作る。

### 7.2 A. 同梱プロファイルの取り込み

- ローカルサーバー経由でリポジトリ内のファイルを直接読む（ファイル選択も可）
- `dangerZoneBaselines` → `baseline` オブジェクト、`obstacles` → `polygon` オブジェクト
- `ashoreAreas` / `navigableWaters` → 陸上エリア・航路オブジェクト（無ければ空）
- `practiceArea` / `operationalCoveragePolygon` / `channelCenterline` → 特殊オブジェクト
- `closed` は「先頭点 == 末尾点」で判定し、**末尾の複製点を取り除いてから**保持する
- トップレベルのメタ情報と `warningAudio` を保持する
- 読み込んだファイルの SHA-256 を `importedFrom.profileSha256` に記録する
- フォルダ構造はレイアウトファイル（§10.1）があればそれを使い、
  無ければ `kind` ごとに自動生成する（「河岸」「橋」「中州」「流木」「カーブ」
  「逆走注意」「テスト区域」「安全データ」「プロジェクト設定」）
- **配列内の順序を `order` として保持する**（§7.7 の管理流木の判定に効く）

**読み込み → 無編集 → 書き出しでバイト単位に一致すること**を必須の完了条件とする
（§11.5、正規化コミット適用後）。これが成立していれば、
diff に現れる変更はすべて利用者が意図した変更である。

### 7.3 B. 共有校正の取り込み

`SharedSafetyCalibrationState` は以下を保持している。

| フィールド | 内容 |
| --- | --- |
| `baseProfileVersion` / `baseProfileSha256` | どのプロファイルに対する差分か |
| `revision` | 版数 |
| `scaledOffsets` | 各 `sourceId` の全体オフセット（北 / 東、メートル、±30m） |
| `scaledVertexOffsets` | 各 `sourceId` の**頂点ごと**のオフセット |
| `dangerZoneOffsets` | kind ごとの水面側 / 陸側の拡張距離 |
| `disabledWarningSourceIds` | 警告を切っている区域 |

**取り込み手順**:

1. `baseProfileVersion` / `baseProfileSha256` が、取り込んだ A と一致するか検査する。
   一致しなければ**校正値を適用しない**。アプリ側も `mayApplyCalibrations = versionMatched`
   で同じ判断をしている（`preset_obstacle_service.dart:44, 184`）
2. 一致した場合、A の各頂点へ全体オフセットと頂点オフセットを加えて
   「校正適用後の実座標」を算出する。計算は
   `FixedObstacleCalibrationService.translatePoints` の移植であり、
   §11.5 のゴールデンテストで Dart 実装との一致を担保する
3. **既定では、校正適用後の座標を破線で重ね描きするだけ**にとどめ、
   オブジェクトの座標は書き換えない。書き換えは §7.7 の明示操作で行う
4. `dangerZoneOffsets` は §5.1 のプレビュー既定値へ反映する
5. `disabledWarningSourceIds` に含まれる区域は、ツリー上で「警告オフ」と表示する
   （現在の既定は `island_upstream` 1 件）

**位置配列の落とし穴**: `scaledOffsets` は `allowedSourceIds` の**列挙順**に並んだ
固定長 21 の配列である（`shared_safety_calibration.dart:305-320`）。
ツール側でも同じ順序定数を持つ必要があるが、これを手書きで二重管理すると
ずれる。§10.3 の生成器が出力する定数を読み込んで使う。

### 7.4 C. 管理流木の取り込み

`ManagedHazardState`（`fixed_driftwood_01`）は座標ではなく、
基準形状に対する変形パラメータ（中心・長軸倍率・短軸倍率・回転角・外側マージン）である。

- `driftwood_estuary` の基準形状へ `ManagedHazardTransformer` と同じ変形を適用し、
  実座標を算出する
- 変形結果は §7.3 と同じく既定では重ね描きのみ
- `baseShapeVersion` が一致しない場合は適用しない

**順序に関する注意**: アプリは `_managedDriftwoodBaseline` で
`dangerZoneBaselines` の中から**最初に見つかった `driftwood`** を管理対象としている
（`preset_obstacle_service.dart:699-705`）。
したがって、新しい流木を `driftwood_estuary` より**前に**挿入すると、
管理対象が入れ替わり、Firestore 上の変形パラメータが別の形状へ適用される。
ツールは新規の `driftwood` を必ず既存の後ろへ配置し、
順序を変えようとした場合はエラーとする。

### 7.5 D. 臨時危険区域の取り込み

`temporary_obstacles` コレクションから、臨時障害物を最大100件読む。自動失効は行わない。

| フィールド | 内容 |
| --- | --- |
| `name` | 名前（1〜40 文字） |
| `kind` | `StaticObstacleKind` の名前。未指定なら `generic` |
| `points` | `GeoPoint` の配列（3〜200 点） |
| `shape` / `center` / `radiusMeters` | 円形の場合の再編集用パラメータ |
| `expiresAt` | 旧アプリが作成した文書だけに残る互換フィールド。失効判定には使わない |
| `createdBy` / `createdAt` / `confirmedAt` | 記録 |

- `GeoPoint` の `latitude` / `longitude` を `lat` / `lng` へ変換する（§3.5 の境界）
- `origin: { kind: "temporary", docId, createdAt }` を付ける。旧文書に限り`expiresAt`も記録する
- ツリー上は「臨時（取込）」フォルダへ入れる
- その日限りの障害物（釣り人や漂流中の流木など）は、練習後に不要を確認してアプリから削除する
- 新たに発見した固定障害物は、このツールで形状を確認して固定候補へ昇格する
- 円形（`shape == "circle"`）は 24 点のポリゴンとして格納されているので、
  そのまま `polygon` として取り込み、円のパラメータは `description` に記録する

**取り込みは読み取りのみ。ツールから Firestore の文書を削除・更新しない。**
昇格後の臨時文書の削除は、固定データを含む配布版を実機確認した後に、アプリ側の編集機能で利用者が行う。配布前に削除してはならない。

### 7.6 Firebase への接続方式

**採用: Firebase Web SDK（`firebase-js-sdk`、Apache-2.0、無料）で、
ツール専用の匿名Firebase IDを作り、初回だけ招待コードでチームの読取り所属を作る。**

判断の根拠:

- `lib/firebase_options.dart` に **web 用の `FirebaseOptions` が既に存在する**
  （`projectId: rowing-navigator-tsukuba`、web の `appId` あり）。
  新たに Firebase の設定を作る必要がない
- 匿名認証と既存の招待コード・Firestore Rulesをそのまま使う。Firebaseプロジェクト設定・認証方式・課金設定は変更しない
- Firestore Rules がそのまま効く。招待コードを知る利用者だけが所属を作れ、チーム外のデータは読めない
- 読み取り量は 1 日あたり数十ドキュメント。Spark プランの無料枠（50,000 reads/日）に
  対して無視できる。**追加費用 0 円は維持される**

**採らない案: Firebase Admin SDK + サービスアカウント鍵。**
Rules をバイパスするため鍵の管理責任が重く、
サービスアカウントの新規発行は Firebase プロジェクト設定の変更にあたる。
読み取りしかしない用途にこの権限は過大である。

**元要件との整合**: 要件案 7 章は「アプリ内のユーザー認証機能は実装しない」としていた。
これは**ツール独自のユーザー管理を作らない**という意味であり、
本方式はそれに反しない——ツールはユーザーを登録・管理せず、
既存の Firebase アカウントでサインインするだけである。
ログイン画面・パスワード再設定・権限管理は一切実装しない。

**実装上の制約**:

- Firebase 関連のコードは `src/io/firestore.ts` に閉じ込める。危険区域・共有校正へ書き込む API（`setDoc` / `updateDoc` / `deleteDoc` / `addDoc`）は禁止する
- 初回だけ`users/{uid}`と`teams/{teamId}/members/{uid}`を`writeBatch`で同時作成する。この書込みは招待コードによる読取り権限の確立だけであり、臨時障害物・固定障害物・共有校正は変更しない
- サインインしていない状態でもツールは起動し、A（同梱プロファイル）の読み書きは完全に動作する。Firebase はインポート時にのみ必要とする（設計原則1）
- `teamId` はツールに保存・手入力しない。初回に入力する招待コードから取得する
- オフライン時・認証失敗時は、その旨を表示して A のみで続行する

### 7.7 昇格ワークフロー

インポートしたものを恒久データへ格上げする操作を、明示的な 3 つのコマンドとして用意する。

#### (a) 臨時 → 固定への昇格

対象: `origin.kind == "temporary"` のオブジェクト。

1. 昇格先の `kind` を選ぶ（`driftwood` / `island` / `generic` など）
2. `exportId` を入力する。既存と衝突しないことを検証する
3. 出力先配列を決める（`kind` から自動決定。§3.4 の表）
4. 形状を確認・編集する。臨時区域は現地で素早く作られるため頂点が粗い。
   航空写真上で整えることを促す
5. `verificationStatus` を `field_verified` にする（現地で作られたデータなので）
6. `origin` を `{ kind: "drawn" }` へ変え、「臨時」フォルダから移動する

**昇格は `allowedSourceIds` と `vertexPointCounts` への追加を伴う**（訂正4）。
昇格した時点で、§9 の変更適用パッケージに以下が必須項目として立つ。

- `allowedSourceIds` へ新 `exportId` を追加
- `vertexPointCounts` へ新 `exportId` と頂点数を追加
- `firestore.rules` の allowlist と `values.size()` の上限（現在 21）を更新
- **共有校正の `documentId` を `v3` へ更新**（固定長配列の長さが変わるため）

#### (b) 校正差分の焼き込み（bake）

対象: `origin.kind == "profile"` かつ共有校正（§7.3）または管理流木（§7.4）を
取り込んでいるオブジェクト。

1. 「校正適用後の座標を確定する」を実行すると、
   破線で重ねていた校正適用後の座標が、オブジェクトの座標そのものになる
2. `verificationStatus` を `field_calibrated` にする
3. **`currentHazardProfileDataVersion` の引き上げが必須項目として立つ**（§7.8）

#### (c) 拡張距離の反映

共有校正の `dangerZoneOffsets` が既定値と異なる場合、
`lib/models/danger_zone_settings.dart` の既定値を変えるべきかを検討対象として提示する。
これはツールが自動で決めることではないので、**変更適用パッケージの
「検討事項」欄に載せるだけ**にする。

### 7.8 二重適用の防止——最重要の安全要件

**校正値は「同梱 JSON の座標 + オフセット」で実座標を作る仕組みである。**

したがって、校正適用後の座標を JSON へ焼き込んだ（bake した）のに、
端末・Firestore 側に校正値が残ったままだと、
**次回起動時にオフセットがもう一度乗り、ずれが 2 倍になる**。
校正の上限は ±30m なので、最大 60m ずれる。川幅 40m の桜川では致命的である。

アプリ側には既に防波堤がある。

```dart
// lib/services/preset_obstacle_service.dart
bool get mayApplyCalibrations => versionMatched;   // :44
// :184  version が違えば校正値を一切適用しない
```

**`currentHazardProfileDataVersion` を上げれば、古い校正値は適用されない。**
これが唯一の正しい解除手段である。

したがってツールは、以下を**機械的に強制する**。

1. bake（§7.7(b)）を 1 件でも実行したプロジェクトは、
   `profileVersion` を +1 しない限り**変更適用パッケージを生成できない**。
   警告ではなくブロックする
2. 逆に、座標を一切変えていないのに `profileVersion` を上げようとした場合は
   警告する（現地で合わせた校正が理由なく失われるため）
3. `profileVersion` を上げる場合、変更適用パッケージには必ず以下が含まれる:
   - `lib/config/hazard_profile_config.dart` の `currentHazardProfileDataVersion`
   - `firestore.rules` の `data.baseProfileVersion` の期待値
   - 「この変更で全員の現地校正値が無効になる」旨の注記と、
     移行後の初回練習で取り直す必要があること

   **§10.6 の名前付きマップ移行後は、`documentId` の世代交代は不要である。**
   要素数や頂点数が変わっても壊れなくなるため、
   世代交代が要るのは「座標の意味が変わったとき」だけになる。
   `version` の引き上げだけで校正値は適用されなくなるので、
   文書を作り直す必要はない
4. bake 後の画面に、次の文言を消えない形で表示する:

```text
校正差分を座標へ焼き込みました。

currentHazardProfileDataVersion を 4 → 5 へ上げてください。
上げないと、端末とFirestoreに残っている校正値が新しい座標へ
もう一度適用され、ずれが2倍（最大60m）になります。

変更適用パッケージにはこの変更が必須項目として含まれています。
```

**なお、ツール側で一律のオフセットを掛けてはならない**（§11.4 も参照）。
座標のずれを吸収する仕組みは既にアプリ側にある。
二重に補正すると、どちらがどれだけ効いているか誰にも分からなくなる。

### 8.1 プロファイル書き出し

- §4 の形式で全体を生成する

フォルダ構造・表示順・確認状況を `sakuragawa_obstacles.layout.json` として書き出す（§10.1）。

### 8.3 GeoJSON

- 出力: `FeatureCollection`。座標順は `[lng, lat]`（RFC 7946）
- `baseline` は `LineString` として出力し、`properties` に
  `{ "kind": "shore", "rowingNavigatorGeometry": "baseline", "closed": true }` を付す
- `polygon` は `Polygon`（外環のみ、閉環必須）
- `properties` に `exportId` / `name` / `kind` / `verificationStatus` / `description` を含める
- 入力: 上記の `properties` があれば種別を復元。なければ幾何型から推定して利用者に割り当てさせる

### 8.4 Firestore 形式（臨時危険区域の下書き用、副次的）

`StaticObstacle.toJson()` に対応する形へ出力する。ポリゴンのみ、3〜200 点。

```json
{
  "sourceObjectId": "obj_...",
  "name": "上流の流木",
  "kind": "driftwood",
  "points": [ { "latitude": 36.0754321, "longitude": 140.2138200 } ]
}
```

ここでは `latitude` / `longitude` になる（`GeoPoint` の表現）。
プロファイル形式と**キー名が異なる**ため、出力形式の選択 UI で明示する。
**ツールから Firestore へ書き込むことはしない**（§7.6）。

### 8.5 KML / KMZ

要件案 16 章のとおり。座標順は `lng,lat,alt`。

- 出力: `<Folder>` でツリー階層を再現。`<Placemark>` に `<name>` `<description>`。
  `baseline` は `<LineString>` として出力し、`<ExtendedData>` に
  `kind` / `closed` / `exportId` / `verificationStatus` を格納する
- 入力: `<Folder>` → フォルダ、`<Placemark>` → オブジェクト。
  `<ExtendedData>` があれば完全復元、なければ幾何型から推定させる
- KMZ は将来拡張。初期版は KML のみ必須

### 8.6 座標一覧

選択中オブジェクトの座標のみを表示する。

```text
選択中: 北の岸 ／ 基準線（開）／ 153 点 ／ 由来: 同梱＋校正(rev.7)

  #    緯度          経度           前点からの距離   校正差分
  1    36.0754321    140.2138200    —                北 +0.4m / 東 -0.2m
  2    36.0754612    140.2138789    6.2 m            —
  3    36.0754498    140.2139010    2.3 m            北 +0.4m / 東 -0.2m
```

「前点からの距離」は頂点の抜けや重複を目視で見つけるため、
「校正差分」は現地でどこを触ったかを見るために出す。
コピー形式は CSV（`lat,lng`）と JSON（プロファイルと同一形式）の 2 種。

### 10.4 陸上判定を陸上エリアの内外へ置き換える

`AshoreDetector` を書き換える。**安全経路の中で最も慎重を要する改修である。**

#### 現行の方式とその問題

```dart
// lib/services/ashore_detector.dart:381
// 進行方向の右手(時計回り90度 = landBearing)を正とする。
```

最寄りの岸線分からの符号付き距離で判定している。これは局所的な近似であり:

- 岸データが途切れる領域（霞ヶ浦側、対応水域の縁）では判定できない
- 中州の上にいても、最寄りが「岸」なら水上と判定される
- 湾曲部の内側では隣接線分の法線が交差し、符号が不安定になりうる
- **岸の基準線の頂点順を誤ると、判定が丸ごと反転する**

#### 新しい方式

**陸上エリアポリゴンの内外（point-in-polygon）で判定する。**

| 状態 | 条件 |
| --- | --- |
| 陸上の候補 | いずれかの `ashoreArea` の内側に、実効マージン以上入っている |
| 水上 | 上記以外（**陸上エリアが無い場合を含む**） |

**判定に使うのは `ashoreAreas` だけである。**
`navigableWaters` も `practiceArea` も陸上判定に参照しない。
したがって陸上エリアが航路や練習水域と重なっていても、
**重なった領域では陸上エリアが優先され、音が止まる**。
これは仕様であり、例外処理ではない。
実装上も「重なりを検査して優先順位を決める」コードを書かない——
そもそも他のポリゴンを見ないので、優先順位が自動的に成立する。

**これは自然にフェイルセーフである。** データが無ければ「陸上ではない」となり、
音は鳴り続ける。全図形化案（航路ポリゴンの外＝陸上）では
「データが無い＝陸上」になりかねず、3 値判定で明示的に防ぐ必要があった。
陸上エリア方式ではその配慮が構造的に不要になる。

#### 維持する挙動

- **陸上確定は 30 秒**（`ashoreConfirmationDuration`）、
  **水上復帰は陸上エリアの外の測位 1 点で即座**。この非対称は変えない
- **実効マージン** = `max(ashoreLandSideMarginMeters, accuracy × ashoreAccuracyMarginFactor)`
  （12m、係数 2.0）。現行は「岸線から陸側へどれだけ入ったか」だったものを、
  「**陸上エリアの境界から内側へどれだけ入ったか**」へ読み替えて維持する。
  測位精度が悪いときに境界付近で陸上と判定しないため
- **陸上判定が止めるのは音だけ。** 検知・表示・記録・位置共有は続く
- 純 Dart を維持し、単体テストを保つ
- `AshoreObservation` の「精度が無ければ陸上と判定しない」も維持する

#### 計算

- ray casting による point-in-polygon
- 境界からの距離は、各辺への最短距離の最小値。内側なら正
- `ashoreBaselineRelevanceRadiusMeters`（200m）に相当する事前フィルタは、
  各陸上エリアの外接矩形での早期棄却へ置き換える
- 陸上エリアは多くても数枚、頂点も各数十点なので、毎秒 1 回の判定で問題にならない

#### 判定理由の再定義

```dart
enum AshoreDecisionReason {
  onWater,                 // どの陸上エリアの内側でもない
  ashoreConfirmed,         // 陸上エリアの内側が 30 秒続いた
  insideMargin,            // 陸上エリアの内側だが、境界から十分入っていない
  ashoreAreasUnavailable,  // 陸上エリアが未整備 → 陸上と判定しない
  accuracyUnavailable,     // 測位精度が不明 → 陸上と判定しない
  …
}
```

`ashoreAreasUnavailable` は診断ログとデバッグ表示に残す。
**「陸上エリアを入れ忘れている」ことが見えるようにする。**
音は鳴り続けるので安全側だが、気づかないまま運用するのは望ましくない。

### 10.5 中心線の自動導出を削除する

```dart
// 削除する: lib/services/preset_obstacle_service.dart:641-660
final shores = <List<LatLng>>[];
… if (map['kind'] != DangerZoneKind.shore.name) continue; …
_cachedCenterline = ChannelCenterline.fromShorelines(…);
```

**削除する理由は、導出そのものが誤っているからである。**
左右の岸の中点は「艇が実際に進む線」ではなく、中州があればそこを貫通する。
`island_upstream` は 122m × 149m あり、幾何学的中心を通せば
予測経路が中州を突き抜ける。

残しておくと「中心線のプロットを忘れたときに、
黙って誤った中心線が使われる」という気づきにくい劣化が起きる。
**明示が無ければ直線予測へ縮退する**ほうが、状態が明快で安全である。

- `ChannelCenterline.fromShorelines` は他に使い道がないので削除してよい
- `ChannelCenterline.fromPolyline` は残す
- 縮退したことを診断ログとデバッグ表示に残す

**ただし削除は、中心線を明示プロットしたのと同じリリースで行う。**
先に削除すると、その間は直線予測になり蛇行区間で誤警告が出る。

### 10.6 共有校正を名前付きマップへ移行する

**この移行は確定事項である。** v4 の他の変更と同時に行う。

#### 現行の問題

```dart
// lib/models/shared_safety_calibration.dart:309
if (rawOffsets is! List || rawOffsets.length != allowedSourceIds.length) {
  throw const FormatException('Invalid calibration offset list');
}
```

固定長 21 の配列で、位置が名前の代わりになっている。
障害物を 1 つ足すと、更新していない端末が校正値を一切読めなくなる。
そのたびに `documentId` の世代交代が必要で、**全員の校正値がリセットされる**。

#### 新形式

```jsonc
{
  "kind": "fixed_obstacle_calibrations",
  "baseProfileVersion": 4,
  "baseProfileSha256": "<新しい64桁>",
  "scaledOffsets": { "shore_north": GeoPoint, "bridge_gakuen": GeoPoint },
  "scaledVertexOffsets": { "shore_north": [GeoPoint, …] },
  "dangerZoneOffsets": { … },        // 現行のまま維持（片側距離は残る）
  "disabledWarningSourceIds": ["island_upstream"],
  "revision": 0,
  "updatedAt": …, "updatedBy": …
}
```

- `scaledOffsets` を**キー付きマップ**にする。値が無いキーは「差分なし」。
  **キーが増減しても壊れない**
- 読み取り時、**未知のキーは無視する**（例外を投げない）。
  これが移行の要点であり、以後の世代交代を不要にする
- `scaledVertexOffsets` のリスト長は引き続きプロファイルの頂点数と一致させるが、
  **長さ不一致はそのキーだけ捨て、他のキーは活かす**（現在は全体が例外）
- `dangerZoneOffsets` は**維持する**（v4 では片側距離の概念が残るため）
- `documentId` を `fixed_obstacle_calibrations_v3` にする。
  **これが最後の世代交代になる想定**である
- 旧 `v2` 文書は読み取り専用として残す（v1 → v2 のときと同じ扱い）

#### 移行時の校正値の引き継ぎ

**`currentHazardProfileDataVersion` を据え置くため、校正値そのものは有効である。**
`baseProfileSha256` だけが変わるので、以下のいずれかを選ぶ。

1. **推奨**: アプリ起動時、`v2` 文書が旧 SHA-256 で存在し `v3` が無い場合に限り、
   値をそのまま `v3` へ書き写す移行処理を 1 度だけ走らせる。
   利用者は何もしなくてよい
2. 移行を実装せず、初回練習で校正を取り直す

1 を採る場合、移行処理は**書き込み権限を持つ利用者が最初に起動したとき**に走る。
競合を避けるため、`revision` の楽観ロック（既存の
`SharedSafetyCalibrationConflictException`）をそのまま使う。

### 10.7 Firestore Rules の変更

- `validScaledVertexOffsets` の 21 件ベタ書きを、生成ブロックへ置き換える（§10.8）
- `scaledOffsets` をリストからマップへ。キーは allowlist で制限し、
  `values.size()` に上限を設ける
- `data.baseProfileSha256 == '<新しい64桁>'`（`baseProfileVersion` は 4 のまま）
- `match /managed_hazards/fixed_obstacle_calibrations_v3` を追加。
  `v2` は読み取りのみ許可へ変更
- `firebase_rules_test` を新形式へ更新する

### 10.8 手書き複製をやめ、生成器を導入する

`tool/generate_hazard_constants.dart` を新設する。

- 入力: `assets/data/sakuragawa_obstacles.json`
- 出力:
  - `lib/models/shared_safety_calibration.g.dart`（`allowedSourceIds`、`vertexPointCounts`）
  - `firestore.rules` の生成ブロック
    （`// GENERATED: hazard-allowlist BEGIN` 〜 `END` を置換）
- `--check` で乖離を検出する（書き換えない）
- CI（`.github/workflows/ci.yml`）へ `--check` を追加する。
  既存の `tool/update_hazard_profile_hash.sh --check` の直後が適切である

**`ashoreAreas` / `navigableWaters` の `id` は allowlist に含めない。**
これらは校正の対象外であり、含めると「校正できるかのように見える」誤解を生む。

これにより、変更適用パッケージ（§9）が指示すべき「手で直す場所」は
`hazard_profile_config.dart` の SHA-256 だけになる。

### 10.9 フォルダ構造は別ファイルへ置く

**判断: `sakuragawa_obstacles.json` にフォルダ情報を追加しない。
`assets/data/sakuragawa_obstacles.layout.json` を新設する。**

理由は訂正4 に尽きる。`sakuragawa_obstacles.json` は**バイト単位で
SHA-256 の契約に縛られている**。Firestore Rules に
`data.baseProfileSha256 == '<64桁>'` がベタ書きされており、
ファイルを 1 バイト変えるだけで共有校正の公開が Rules で拒否される。

フォルダ構造は**安全判定に一切関与しない表示上の都合**である。
それを安全データと同じハッシュ契約に縛るのは設計として誤りである。
分離すれば、フォルダ名を変えただけで Firestore の共有文書を触る事態を避けられる。

```json
{
  "layoutVersion": 1,
  "profileVersion": 4,
  "folders": [
    { "id": "fld_banks",  "name": "河岸", "parentId": null, "order": 0 },
    { "id": "fld_safety", "name": "安全データ", "parentId": null, "order": 9 }
  ],
  "objects": {
    "shore_north": {
      "folderId": "fld_banks", "order": 0,
      "description": "2026-07-26 現地確認済み",
      "verificationStatus": "field_verified"
    }
  }
}
```

- `profileVersion` が不一致ならレイアウトを使わない
- `objects` のキーは `exportId`。プロファイルに存在しないキーは無視する
- プロファイルにあってレイアウトに無いオブジェクトは `kind` ごとの既定フォルダへ落とす

`pubspec.yaml` の `assets:` は `assets/data/` をディレクトリごと宣言しているため、
**新ファイルの追加に `pubspec.yaml` の変更は要らない**。

### 10.12 検証（移行の受け入れ条件）

**陸上判定は音を止める機能であり、誤ると水上で警告が消える。**
本アプリで最も重い失敗なので、以下をすべて満たすまでリリースしない。

1. `dart analyze lib test` と `flutter test` が通る
2. `firebase_rules_test` が通る
3. `tool/update_hazard_profile_hash.sh --check` と
   `dart run tool/generate_hazard_constants.dart --check` が通る
4. **陸上エリアが無い状態での動作確認**: `ashoreAreas` を空にしても起動でき、
   警告が鳴り、**一度も陸上と判定されない**（不変条件13）
5. **航跡ログの再生比較**: 移行前後で同じ実機ログを
   `tool/replay_field_log.dart` / `tool/replay_alerts.dart` に通し、
   警告と陸上判定の差分を比較する。
   **陸上判定が変わるのは想定内である。**
   記録は艇を担いだ陸上から始まるので、開始直後と終了直前が
   新方式で「陸上」になるのはむしろ正しい。
   **止めるのは、漕いでいる区間（速度が出ている区間）で
   新たに「陸上」になった箇所が 1 つでも出た場合である**
6. **実データ統合テストの維持**: `assets/data/sakuragawa_obstacles.json` を使う
   既存の統合テストを維持する。CLAUDE.md が
   「設定値の意図と実効値の乖離を検出する唯一の手段」としているもの
7. **中心線の目視確認**: 明示中心線が中州・橋脚を貫通していないこと
8. **陸上判定の現地確認**: 出艇・着艇・橋の下での休憩・岸際の並走・
   桟橋への係留で、音の開始と停止が正しいこと。
   特に**水上で音が止まらないこと**を重点的に見る

## 11. 検証機能

**この章が本ツールの存在価値である。** 作図ツールは他にもあるが、
「Rowing Navigator が読める形か」「岸の向きが正しいか」
「陸上エリアが水面へはみ出していないか」「補正が二重に掛からないか」を
検査できるものはない。

### 11.1 エラー（書き出しをブロックする）

| `obstacles` / `practiceArea` / `operationalCoveragePolygon` / `ashoreAreas` / `navigableWaters` が 3 点以上 | `:238, :276, :288` |
| いずれの `points` も 1000 点以下 | `maxPolygonPoints = 1000` |

### 11.4 航空写真の位置ずれの確認

Apple の航空写真と Google Maps（アプリの表示に使用）の写真は、
測地系が同じ WGS84 でも**オルソ補正の基準が異なり、数メートルずれうる**。

**v4 では、このずれが陸上判定に直接効く。**
陸上エリアの境界が数メートル水面側へずれると、そこで音が止まる。

対策として以下を必須機能とする:

- 既存プロファイルを**参照レイヤーとして重ね描き**し、
  既存の橋・岸が Apple の写真上で正しい位置に乗っているかを目視確認する
- **実機の航跡ログ（`SessionStoreService` の JSON / GPX）を重ね描きする。**
  漕いでいる区間は必ず水面上にあるので、**航路中心線は航空写真より航跡を優先して引く**。
  ただし記録は艇を担いだ陸上から始まるため、
  **開始直後と終了直前の航跡は陸上にある**。陸上エリアの作図では基準にしない
- 共有校正（§7.3）の適用後座標を重ね描きする

**ずれが確認されても、ツール側で一律のオフセットを掛けてはならない**（§7.8 と同じ理由）。
ツールは「ずれている」ことを可視化するに留める。

9. **カテゴリの分離**: `ashoreArea` / `navigableWater` が
   `dangerZoneBaselines` / `obstacles` へ出力されない（不変条件12）
10. **座標順序**: GeoJSON / KML / Firestore との相互変換で `lat` / `lng` が
    入れ替わらない。桜川の座標（36, 140）は取り違えても両方とも有効な値になるため、
    南半球・西半球を含む合成データでも検査する
11. **定数生成**: 変更適用パッケージが出力する `allowedSourceIds` と
    `vertexPointCounts` が、生成したプロファイルと完全に一致する。
    `ashoreArea` / `navigableWater` の `id` が含まれない
12. **Firestore 読み取り専用**: `src/io/firestore.ts` が書き込み API を import していない
13. **パーサ条件**: §11.1 の各エラー条件について、違反データが検出される

## 12. 状態管理・自動保存

### 12.1 Undo / Redo

- プロジェクト全体で 1 本の履歴。各エントリに対象オブジェクト ID と操作名を持つ

## 13. MapKit JS 認証

### 13.1 トークン生成

ローカル Node サーバーが ES256 の JWT を生成する。

```text
header:  { "alg": "ES256", "kid": <Key ID>, "typ": "JWT" }
payload: { "iss": <Team ID>, "iat": <now>, "exp": <now + 1800> }
```

- 有効期限 30 分。ブラウザは MapKit JS の `authorizationCallback` で再取得する
- **`.p8` の内容をレスポンスに含めない。** 返すのは JWT 文字列のみ
- サーバーは `127.0.0.1` にのみバインドする（`0.0.0.0` にしない）

### 13.2 `origin` クレームの扱い

MapKit JS の `origin` クレームはページのオリジンと一致する必要があり、
Maps ID にドメイン制限を掛けた場合、`http://localhost:*` が許可されない可能性がある。

1. まず `origin: "http://localhost:5173"` を含めて動作を確認する
2. Apple 側の制約で動かない場合は `origin` クレームを省略し、
   Maps ID 側のドメイン制限も設定しない
3. 2 を採る場合の残存リスクは、有効期限 30 分・ローカル専用・
   `127.0.0.1` バインドで受容する

実装時に Apple の最新仕様を確認して確定し、README に記録する。

### 13.3 環境変数

```dotenv
APPLE_TEAM_ID=
APPLE_KEY_ID=
APPLE_MAPS_ID=
APPLE_PRIVATE_KEY_PATH=/Users/<user>/.config/rowing-navigator/mapkit/AuthKey_XXXXXXXXXX.p8
TOKEN_TTL_SECONDS=1800
PORT=5174
REPO_ROOT=                      # 空なら git rev-parse で自動解決
PROFILE_WRITE_PATH=             # 空なら直接書き出しを無効化（既定）
```

Firebase の設定値は `.env` に書かない。
`lib/firebase_options.dart` の web 設定をビルド時に読み込む
（値は公開情報であり、秘密情報ではない）。

### 13.4 起動

```bash
cd tool/obstacle-plotter
npm install
npm run dev
```

1 コマンドで Vite（5173）とローカルサーバー（5174）を起動する
（`concurrently`、MIT）。Vite の `server.proxy` で `/api` を 5174 へ転送し、
ブラウザから見えるオリジンを 5173 に一本化する。

`.env` が無い、または必須変数が欠けている場合は、
**何が足りないかを具体的に示して**起動を中止する。

### 13.5 ローカル直接書き出し（オプトイン）

`PROFILE_WRITE_PATH` を設定した場合にのみ有効化する。

1. 書き出し前に既存ファイルを
   `assets/data/.backup/sakuragawa_obstacles.<ISO8601>.json` へ複製する
2. サーバー側で再検証する（ブラウザ側の検証だけを信頼しない）
3. `PROFILE_WRITE_PATH` と完全一致するパスにのみ書き込む。
   パス結合やパストラバーサルを一切行わない
4. `tool/update_hazard_profile_hash.sh` を**自動実行しない**。
   ハッシュ更新は「データを確認した」という人間の意思表示であり、
   自動化すると検証の意味が失われる

- `.p8` 秘密鍵と作成した座標データが Mac の外へ送信されない
- README の手順だけでローカル起動できる

### 17.2 オブジェクト管理

- 複数の名前付きオブジェクトが独立した座標を持ち、個別に選択・編集・
  表示切替・ロック・出力できる
- 1 つを編集しても他が変化しない
- フォルダ・サブフォルダを作成し、オブジェクトを移動できる
- ツリーと地図の選択が連動する
- 保存・再読込後も階層構造が維持される
- KML の Folder と Placemark を読み書きでき、階層と名前が維持される

### 17.3 Rowing Navigator との整合

- 現行 `sakuragawa_obstacles.json` を読み込み、無編集で書き出すとバイト単位で一致する
- 書き出した JSON を `PresetObstacleService` が例外なく読み込める
- 基準線から生成される危険区域の形状が `LegacyDangerZoneGenerator` の出力と 1mm 以内で一致する
- 岸の向きが逆の場合はエラーとして書き出しがブロックされる
- 島・橋・流木・テスト区域を、向きを意識せず図形として描ける
- 閉じるべき環が閉じていない場合に警告が出て、書き出し時に閉じられる
- 座標が `lat` / `lng` のキーで、小数 7 桁で出力される
- `exportId` や頂点数を変えると、波及するファイルが列挙される

### 17.4 陸上エリア・中心線・航路（v4 の中心）

- 陸上エリアを作図でき、専用の色と実効境界（内側 12m）が表示される
- **陸上エリアが `navigableWater` / `practiceArea` と重なっても書き出しできる。
  重なった領域は陸上として扱われ、音が鳴らない**
- 航路中心線を作図でき、自動導出の結果を下敷きとして重ね描きできる
- 中心線が中州・橋脚の区域と交差すると警告が出る
- 航路ポリゴンを作図でき、地図上で確認できる
- `ashoreArea` / `navigableWater` が危険区域の配列へ出力されない
- `ashoreArea` / `navigableWater` の `id` が `allowedSourceIds` に含まれない

### 17.5 アプリ側の改修（v4）

- `AshoreDetector` が陸上エリアの内外による判定になっている
- **陸上エリアが無くても起動でき、警告が鳴り、一度も陸上と判定されない**（不変条件13）
- 陸上確定 30 秒 / 水上復帰即座の非対称と、精度に応じた実効マージンが維持されている
- 陸上判定が止めるのは音だけで、検知・表示・記録・位置共有は続く
- 中心線の自動導出が削除され、明示指定のみになっている
- 中心線が無い場合は直線予測へ縮退し、診断ログに残る
- 陸上エリア・航路が衝突判定へ渡らない（不変条件12）
- `LegacyDangerZoneGenerator` / `DangerZoneSettings` / `StaticObstacleIndex` /
  判定則 / 提示ポリシーが**変更されていない**
- 移行前後で同じ航跡ログを再生し、**漕いでいる区間で新たに「陸上」になった箇所が無い**
  （開始直後・終了直前が「陸上」になるのは正しい挙動）
- 出艇・着艇・橋の下での休憩・岸際の並走・桟橋への係留で、
  音の開始と停止が現地で確認されている
- 共有校正が名前付きマップになり、**未知のキーがあっても例外を投げない**
- 共有校正の頂点リスト長が不一致でも、そのキーだけが捨てられ他は活きる
- `documentId` が `fixed_obstacle_calibrations_v3` になり、v2 は読み取り専用で残る
- `currentHazardProfileDataVersion` が据え置かれ、**現地校正が有効なまま残っている**
- `allowedSourceIds` / `vertexPointCounts` / Rules の allowlist が
  プロファイルから生成され、CI が乖離を検出する

### 17.6 インポートと昇格

- 同梱プロファイル・共有校正・管理流木・臨時危険区域の 4 つを取り込める
- 取り込んだ校正差分・変形パラメータが、基準形状へ正しく適用されて重ね描きされる
- 校正適用後の座標が Dart 実装と 1mm 以内で一致する
- 期限切れの臨時危険区域も、明示操作で取り込める
- 臨時危険区域を固定へ昇格でき、波及する定数が自動で算出される
- 校正差分を焼き込んだ場合、`currentHazardProfileDataVersion` を上げない限り
  変更適用パッケージを生成できない
- Firestore への書き込み API がコード上に存在しない
- Firebase に接続できない状態でも、ツールは起動しプロファイルの編集ができる

### 17.7 変更適用パッケージ

- 影響を受ける全ファイルについて、新しい値または手順が出力される
- `CHANGESET.md` が、この会話の文脈なしで単独で実行可能である
- `verify.sh` が、反映後の整合性を機械的に検査できる
- 算出できない項目が「検討事項」として自動変更の対象から明示的に外れている

4. **中州の内部を危険区域にすべきか**（§5.9 末尾）。
   閉じた基準線に片側 5m の帯を作る仕組みのため、
   `island_upstream` の内部に約 112m × 139m の穴が空いている。
   艇は必ず帯を横切るため連続掃引が捉えるが、
   GPS が数秒欠測して内側で再捕捉した場合は警告が出ない。
   塗りつぶすなら `obstacles`（完成ポリゴン）へ移すことになるが、
   片側距離の実行時調整を失う。
   `island_upstream` は現状 `defaultDisabledWarningSourceIds` により
   既定で警告対象外なので、まず現地確認で存在と形状を確定させるのが先である

5. **共有校正 v2 → v3 の値の引き継ぎを実装するか**（§10.6）。
   `currentHazardProfileDataVersion` を据え置くため校正値自体は有効である。
   自動で書き写す移行処理を入れれば利用者は何もしなくてよいが、
   実装と競合制御が要る。入れない場合は初回練習で取り直す。
   **推奨は実装する側**（せっかく校正が有効なまま残るのに、
   手続きの都合で失うのはもったいない）

6. **陸上エリアの粒度**（§5.3）。
   艇庫前を 1 枚で覆うか、桟橋・スロープ・艇置き場を分けるか。
   分けたほうが「どこで音が止まったか」を診断しやすいが、
   境界の重なりを管理する手間が増える。実地で決める

7. **臨時危険区域の保持期間**（§7.5）。
   24 時間で失効するため、昇格作業を後日に回すと元データが消える。
   まずツール側で定期的に取り込んで IndexedDB へ退避することで対応する。
   アプリ側の TTL 変更は行わない
