# IMU融合艇速・距離・ストローク分析

## 目的

艇へ固定したスマートフォンの加速度・ジャイロを、既存のGNSSロバスト推定へ補助入力し、
艇速、距離、1ストローク距離、2〜5秒のGNSS欠測を改善する。同時に、直近1ストロークの
艇速変化を画面・診断ログへ出す。

## 根拠

- Wingほかのスマートフォン実艇研究は、GNSSの低周波成分と加速度の高周波成分を融合し、
  GPS単独より艇速44〜48%、距離22〜42%、1ストローク距離73〜82%の改善を報告した。
  ただし2人・2艇・300mの小規模検証で、全端末・全艇への一般化は未確認。
  <https://doi.org/10.1371/journal.pone.0225690>
- 艇速変動は抵抗増加と関係し、艇速・加速度曲線はローイング分析で使われる。
  <https://pubmed.ncbi.nlm.nih.gov/18510593/>
- キャッチから初期ドライブの負加速度、加速度jerk、リカバリーは性能との関連が報告されるが、
  技術評価としての解釈はまだ一意ではない。
  <https://pmc.ncbi.nlm.nih.gov/articles/PMC8378734/>
  <https://pmc.ncbi.nlm.nih.gov/articles/PMC11436553/>
- Apple Core Motion / Android motion sensorsは、重力除去加速度、角速度、姿勢融合を提供する。
  実際の更新間隔は要求値どおりとは限らないため、必ずサンプル時刻で積分する。
  <https://developer.apple.com/documentation/coremotion/cmdevicemotion>
  <https://developer.android.com/develop/sensors-and-location/sensors/sensors_motion>

## 安全設計

1. IMUだけから絶対位置を作らない。加速度の二重積分とジャイロ積分はドリフトする。
2. GNSS艇速をドリフトしない低周波基準とし、1ストローク内で平均0になる加速度積分だけを足す。
3. 加速度軸は固定取付方向を強制せず、15秒窓のPCAで艇長軸を求める。
4. ジャイロは重力軸へ射影した相対回頭だけに使い、GNSS方位ごとにリセットする。
5. 信頼度0.68未満、2秒より古い解析、非周期運動、サンプル欠落では従来GNSSへ縮退する。
6. GNSS欠測のIMU補助も既存どおり最大5秒。不確実性はKalman共分散で増加させる。
7. IMU推測点を生GNSS、他艇共有、正式航跡として偽装しない。
8. 画面は本番向けの中立的な数値表示とし、良い・悪いを断定しない。
9. 舟速分析の表示は計測と分離し、既定OFFのオプションとする。非表示でも
   GPS補正・距離・SPM・ログは継続する。開始前と航行中のメニュで切替可能。

## ストローク指標

- `1漕距離`: GPS低周波艇速とストローク内IMU艇速を1周期積分。
- `キャッチ減速`: キャッチ境界から周期前半25%までの最大艇速低下。
- `終盤加速/失速`: キャッチ最小艇速からフィニッシュまでの中点と終点の差。
- `艇速保持`: 推定フィニッシュの艇速増分を次キャッチまで何割保ったか。
- `フィニッシュ位相`: 周期12〜68%内の加速から減速への持続的な転換点。
  転換が不鮮明な場合のみ周期20〜58%の最大艇速点に縮退する。

スマホだけではブレード入水・抜水や漕手の身体部位を直接観測できない。そのため、キャッチ・
フィニッシュは艇加速度からの推定境界であり、オール角・力・動画の測定と同一ではない。

## 実機検証

- 1x/2x/4x/8+、複数端末、レート12〜40spm、直進・回頭・停止で比較する。
- 良好なGNSS区間から2/3/5秒を隠し、従来等速予測とIMU補助の位置・艇速誤差を比較する。
- 可能ならRTK-GNSSを基準とし、中央値だけでなく95パーセンタイルと警告漏れを確認する。
- 診断ZIPの`track.csv`、`stroke_motion_analyzed`、`imu_fusion_health`を使う。
- 少なくとも15〜20%の誤差改善があり、停止時距離、横ずれ、過剰警告が悪化しない場合に
  「有意な改善」と判断する。
