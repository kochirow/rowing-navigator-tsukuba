# 監視モード警告・艇間早期注意喚起 要件定義と実装計画

- 作成日: 2026-08-03
- 対象: Rowing Navigator 桜川版
- 状態: **要件承認済み・実装は未着手**
- 根拠: 監視者の実機テスト所感、および `DESIGN_PRINCIPLES.md`
- 最優先原則: 過剰警告で監視画面を使いにくくしてはならない。同時に、接近・逆走という監視者が行動判断に使える情報は埋もれさせない。

> 本書は、航行中の衝突警報を弱めたり置き換えたりしない。監視者向けの早期注意喚起を新設し、将来必要なら航行中の選手にも表示専用で転用できるようにする要件定義である。

---

## 1. 決定事項

### 1.1 監視画面の表示を三分類する

| 区分 | 監視者への表示 | 色・形 | 表示文言 | 目的 |
| --- | --- | --- | --- | --- |
| 逆走 | 上部の強調バナー | 赤 + 反転矢印 | `逆走：A艇・B艇` | 航路ルールから外れた艇をすぐ把握する |
| 艇間早期注意 | 上部の強調バナー | 濃い橙 + 対向矢印 | `接近中：A艇・B艇・C艇` | 衝突警報より前に、すれ違いの組を監視者へ知らせる |
| 機能・状態 | 小さな状態アイコン | 青 + 情報アイコン | 数字だけ。例: `ⓘ 3` | 詳細確認はできるが、地図と重要バナーを占有しない |

- 色だけに意味を持たせない。矢印・アイコン・短い文言でも区別する。
- 上部バナーは**最大2本**（逆走1本、接近1本）。艇・組ごとのカードを並べない。
- 艇名は先頭3艇までを表示し、それ以上は `ほかN艇` とする。
- バナーのタップは、該当艇だけの詳細一覧を開き、必要なら該当艇群が収まるよう地図を寄せる。
- 状態アイコンのタップは、下から開く「艇の状態」一覧を表示する。地図を覆う常設パネルにはしない。

概念レイアウト:

```text
┌────────────────────────────────────────────┐
│ [赤 ↩ 逆走：A艇・B艇]             [青 ⓘ 3] │
│ [橙 ↔ 接近中：C艇・D艇・E艇]               │
│                                            │
│                   地図                     │
│                                            │
└────────────────────────────────────────────┘
```

横幅が足りない場合だけ、赤・橙の順に二段へ折り返す。状態アイコンはバナー内へ混ぜず、右上に独立して置く。

### 1.2 現行機能との区別

| 機能 | 現行 | 本要件後 |
| --- | --- | --- |
| 航行中の衝突警報 | 連続的な船体領域・相対運動・不確実性を用いて危険度と到達時刻を評価する | **変更しない** |
| 監視の更新途絶・長時間停止 | 小型チップと艇一覧で表示する | 状態アイコンと詳細一覧に移す。上部バナーにはしない |
| 監視の逆走 | 未実装 | 赤バナーで表示する |
| 監視の艇間早期注意 | 未実装 | 150m以内の対向接近を橙バナーで表示する |
| GPS途絶・陸上判定などの各艇状態 | 監視端末では完全には把握できない | 監視用の状態データを整備し、状態アイコンの詳細へだけ表示する |

`長時間停止` は機能不全そのものではないが、沈・体調不良・休憩を区別できない観測事実である。情報を削除せず、主バナーには昇格させない。詳細では「停止継続」として、更新途絶・低電池・GPS品質低下などと区別して表示する。

### 1.3 音声方針

- 監視者向けの新しい逆走・接近通知は、初回実装では**音を鳴らさない**。
- 赤・橙の常時表示と地図上の該当艇強調で伝える。
- Buddycom等との干渉、近隣への騒音、注意喚起の見逃し率を実機で確認した後にだけ、短い単発音を別要件として判断する。
- 航行中の既存の衝突警報の音声方針は、この変更の対象外である。

## 2. 背景と設計境界

### 2.1 桜川の運用前提

- 川幅は概ね40〜50m、狭所は35m。右側通行で、対向艇とは日常的にすれ違う。
- 同時に2〜12艇が航行する。巡航速度は概ね3〜5m/s。
- 狭所で規定どおり走る8+同士は、艇中心間が約12.5mになりうる。**近いすれ違い自体は正常運用**である。
- GPS精度は5〜15m程度の揺れがあり、他艇の位置は新鮮なときだけ予測に使える。
- 監視者は陸上で画面を操作できるが、選手は航行中に端末操作できない。

### 2.2 150m/100mの意味

150mは「衝突の危険距離」ではなく、監視者が複数艇の動きを前もって把握するための**早期注意半径**である。巡航速度5m/sずつの正面接近では、150mはおよそ15秒前、100mはおよそ10秒前に相当する。

したがって、次を混同しない。

1. **早期注意**: 対向し、近づいている組が150m以内にいる。監視者が注目するための表示。
2. **衝突警報**: 船体・オール・GPS不確実性を含む安全領域へ入る、または入る見込みがある。選手が目視確認・安全行動を取る契機。
3. **機能状態**: 情報の鮮度やアプリ能力が低下しており、1・2の確度を下げうる事実。

早期注意を衝突警報と同じ閾値や音へ混ぜると、正常なすれ違いのたびに警告が形骸化する。逆に、衝突警報の閾値を150mへ広げることもしない。

## 3. 機能要件

### R-1 監視用の逆走バナー

1. 監視中の各艇について、既存の航路中心線・レーン・右側通行に基づく逆走判定を行う。
2. 停止・回頭・方位不確か・レーンの判定対象外では逆走と表示しない。
3. 現行の逆走確認時間（連続6秒）と同等以上のデバウンスを用い、単発GPS点で表示しない。
4. 複数艇が逆走中なら、赤バナー1本に集約する。
5. 表示文言は `逆走：艇名`、複数時は `逆走：艇名・艇名・ほかN艇` とする。説明文・進行方位・内部理由コードを主画面へ出さない。
6. 監視の逆走検知失敗は、航行中の逆走警告、位置共有、記録を停止させてはならない。

### R-2 監視用の艇間早期注意

#### R-2.1 不変の入口条件

以下をすべて満たす艇の組だけを、150m早期注意の候補にする。

1. 2艇とも監視中であり、最新位置が予測に使える鮮度である。
2. 2艇とも航行中と見なせる速度である（初期案: 0.5m/s以上）。
3. 2艇の進行方位が「概ね対向」である（初期案: 方位差120度以上）。
4. 艇中心間の現在距離が150m以下である。
5. 方位・速度・位置のいずれかが不確かなら、通常の対向接近とは断定しない。その不確かさは状態アイコン側へ回す。

この条件は「150m以下なら必ず衝突の危険がある」という意味ではない。**対向する艇を監視者が見失わないための候補化条件**である。

#### R-2.2 初期の確定・解除案

| 項目 | 初期案 | 意図 |
| --- | --- | --- |
| 候補確定 | 2〜3秒連続で入口条件を満たす | GPSの1点飛びを抑える |
| 強制即時確定 | 既存の衝突警報が同じ組で有効、または距離が急速に縮小 | 本当に切迫した組を待たせない |
| 解除距離 | 180m超 | 150m境界で点滅させないヒステリシス |
| 解除確認 | 非該当が3〜5秒継続 | すれ違い直後の通信・方位揺れを吸収する |
| 古い位置 | 新しい接近を作らない。既存表示は状態劣化を伴って保持・解除を判断する | 「情報がない」を「安全」にしない |

これらは実装値ではなく、ログ再生と3艇以上の実機試験で見直す初期値である。最終値は、付録Aの検討結果と実測で決定する。

#### R-2.3 3艇以上の集約

- 艇を頂点、早期注意を満たす対向ペアを辺とする無向グラフを作る。
- 連結成分ごとに1件の「接近グループ」とする。
- 例: A–B と B–C が成立するなら、`接近中：A艇・B艇・C艇` と1本にする。
- A–BとD–Eが別の場所なら、内部では2グループとして保持する。ただし主画面は橙バナー1本に集約し、先頭グループの艇名と `ほか1組` を出す。
- タップ後の詳細では、各グループ、各ペアの距離・鮮度・対向判定根拠を確認できる。

#### R-2.4 地図表現

- バナー表示中の艇は、既存の艇名マーカーを保ったまま外周リングまたは薄い強調色を付ける。
- 150mの巨大な円は常時描画しない。狭い水域で地図を覆い、距離を危険境界と誤解させるためである。
- 詳細表示を開いたときだけ、該当ペアまたはグループを結ぶ細線と距離を一時表示してよい。

### R-3 航行中の選手への将来転用（未承認の第2段階）

監視用の純粋な判定部は、航行中の自艇と他艇の組にも再利用可能にする。ただし、選手向けの表示・音声は本書では**実装を決定しない**。

検討対象として、次を候補にする。

| 項目 | 候補 |
| --- | --- |
| 条件 | 自艇と他艇が対向し、100m以内で接近中 |
| 初期表示 | `近くに他艇：艇名` または `対向艇に注意` の表示専用チップ |
| 音声 | 初期は鳴らさない。既存衝突警報より優先しない |
| 解除 | 既存衝突警報の状態機械と別のヒステリシスを持つ |

この第2段階を採用する前に、以下を確認する。

- 100m表示が既存の衝突警報や逆走案内を隠さないこと。
- 正常なすれ違いで繰り返し表示されても、選手が無視する表示にならないこと。
- 「近くにいる」という情報が、後方を振り向く・監視するという実際の行動に結びつくこと。
- 音声を足さなくても安全価値があること。音声を足す場合は別の実機検証を行うこと。

### R-4 機能・状態アイコン

#### R-4.1 主画面の扱い

- 異常の件数が0ならアイコンを表示しない。
- 1件以上なら青い情報アイコンと件数だけを表示する。赤いSnackBar、全幅バナー、繰り返し音は使わない。
- アイコンをタップすると、艇名・種別・最初の検知時刻・最終更新時刻・観測根拠を一覧表示する。
- 状態情報は、逆走・接近バナーより常に下位である。

#### R-4.2 詳細に出す状態

| 種別 | 初期扱い |
| --- | --- |
| 更新途絶 | 既存の90秒しきい値を保ち、詳細へ表示 |
| 長時間停止 | 既存の3分・低速条件を保ち、詳細へ表示 |
| 低電池 | 既存データがある場合だけ詳細へ表示 |
| GPS品質低下・測位不能 | 共有できるようになった場合だけ詳細へ表示 |
| 位置共有不能 | 各艇が明示送信できる場合だけ詳細へ表示。送信そのものが止まった場合は更新途絶として扱う |
| 警告処理の能力低下 | 各艇が明示送信できる場合だけ詳細へ表示 |
| 陸上判定・音声抑制 | 監視者が対処できる情報かを実機で確認するまで、主画面には出さない |

「GPS途絶」「水域外」を見ても監視者がただちに取れる行動がない場合、それを主バナーへ出さない。必要なら詳細画面で確認できるようにする。

## 4. アーキテクチャ要件

### A-1 判定を分離する

新しい判定は仮称 `ObserverTrafficAwarenessEvaluator` とする。

- Flutter UIやFirebaseに依存しない純粋Dartの部品とする。
- 入力は監視中の艇一覧、評価時刻、鮮度、航路レーン・中心線、位置精度とする。
- 出力は逆走艇、早期注意ペア、接近グループ、状態アイコン用の観測状態とする。
- 既存の `CollisionRiskEvaluatorService` の衝突警報結果を置き換えない。
- 既存の逆走方向判定は再利用してよいが、監視の状態・表示用のデバウンスを航行側の音声状態機械と共有してはいけない。

### A-2 データ鮮度と不確実性

- 他艇の新規予測には既存の鮮度上限（現行6秒）を超える値を使わない。
- 位置精度、更新齢、方位信頼性が悪いとき、150m条件を勝手に大きくして常時接近表示にしない。
- 代わりに「状態アイコンで確度低下を示す」「新しい対向接近としては確定しない」「既存の衝突警報を安全と誤認して解除しない」を分離する。
- 距離・方位の計算には地球座標ではなくメートル系の共通ユーティリティを用い、全ペアを同じ時刻基準へそろえる。

### A-3 状態データの共有

現行の位置共有には、位置・速度・方位・電池・精度に加え、記録用のコンパクトな提示状態が存在する。一方、監視画面が各艇の機能状態として安全に使う契約は未整備である。

実装時は、次の順を守る。

1. 監視へ出す状態を最小限の列挙値として定義する。詳細な診断ログや個人情報を常時送らない。
2. 旧アプリが未知のフィールドを無視して位置共有を継続できることを確認する。
3. `Message`、RTDB送受信、監視用の状態モデル、表示の責務を分ける。状態を衝突判定入力やマーカー位置更新へ混ぜない。
4. RTDB Rulesの許可フィールド・型・サイズ・書込主体を更新し、Rules Emulatorで検証する。
5. 本番Rules反映は、アプリのコードテスト・CI・署名済みビルド・実機試験とは別のゲートとして扱う。

### A-4 表示責務の分離

- `SafetyBanner` は航行中の既存警告用として維持する。
- 監視用には専用の `ObserverPriorityBanner` と `ObserverStatusIcon` を置く。
- 監視の表示処理は、位置共有、1Hzの安全判定、航跡記録、地図マーカー更新を止めたり遅らせたりしてはならない。
- 状態詳細の開閉は監視者が操作する補助UIであり、画面常時点灯や航行中の安全経路へ依存させない。

## 5. 実装計画

### フェーズ0: 設計確定（本書の後）

1. 付録AのAI検討依頼を実施する。
2. 提案を、既存の連続衝突判定・桜川の運用前提・実装可能性でレビューする。
3. 次の数値を決定する: 対向方位差、最低速度、確認時間、解除距離、解除時間、低品質データ時の扱い。
4. 航行中100m表示を第2段階へ入れるか、表示のみか、保留かを明示決定する。

**完了条件:** 数値の根拠と「採用しなかった案」が記録されていること。

### フェーズ1: 純粋な判定・集約ロジック

1. 逆走監視と早期注意の入力・出力モデルを定義する。
2. 全艇のペアを評価し、連結成分へ集約する。
3. 確定・解除・鮮度劣化を状態機械で実装する。
4. 既存衝突警報の有効状態を、必要に応じて早期注意の強制確定根拠として読めるようにする。ただし航行側の状態を書き換えない。

**必須テスト:**

- 151mでは出ず、150m以内で確認後に出る。
- 149〜151mのGPS揺れで点滅しない。
- 対向でない並走・追い越し・停止・回頭では出ない。
- 3艇の連結グループと、離れた2グループが正しく集約される。
- 古い位置では新規接近を作らない。
- 既に衝突警報中の組を誤って早期注意から消さない。
- 逆走のレーン外・方位不確か・6秒確認を守る。

### フェーズ2: 監視UI

1. 上部最大2本のバナーを実装する。
2. 状態アイコンと詳細ボトムシートを実装する。
3. バナー・状態アイコン・艇一覧・地図フォーカスの遷移を接続する。
4. 縦画面・横画面・2艇・12艇で地図面積を確認する。

**必須テスト:**

- 逆走・接近・状態の3色とアイコンがテキストなしでも区別できる。
- 重要バナーが最大2本である。
- 多数艇でも画面上部の占有率が増え続けない。
- タップで正しい艇・グループの詳細と地図位置へ遷移する。
- 既存の航行中 `SafetyBanner` の表示が変わらない。

### フェーズ3: 状態共有とRules（必要になった場合だけ）

1. 監視に必要な最小状態を決める。
2. 後方互換な送受信・表示を実装する。
3. RTDB RulesとRules Emulatorテストを更新する。
4. 実機で、送信できる状態・送信途絶・旧クライアント混在を確認する。

### フェーズ4: ログ再生・実機・水上検証

| 試験 | 確認すること |
| --- | --- |
| ログ再生 | 既存の航跡で表示件数、継続時間、点滅、既存衝突警報への非干渉を確認 |
| 陸上3端末試験 | 151m→149m、対向・同方向・停止・通信断・3艇グループを再現 |
| 水上試験 | 実際の対向すれ違いで、早期注意が監視に有用で、常時表示にならないことを確認 |
| 選手向け試験（第2段階のみ） | 100m表示が既存警報を覆わず、漕手の視認・音声と干渉しないことを確認 |

コード解析・単体テスト・CIの成功は、RTDB Rulesの本番反映、署名済みアプリ、実機、水上での安全性を証明しない。それぞれを独立した完了条件として記録する。

## 6. 非機能要件と禁止事項

- 監視表示の追加によって、航行中の1Hz安全判定、位置共有、航跡記録を遅らせない。
- 全ペア評価は最大12艇（66ペア）を前提に、毎秒評価してもUIを詰まらせない設計にする。
- 同じ事象を表示するたびに新しいアラートIDを作らない。組・グループの安定した識別子を持つ。
- 150mを「危険区域」や「必ず回避すべき境界」として地図上に恒常表示しない。
- 機械学習モデルや外部AIのオンライン推論を、航行中の安全経路へ組み込まない。採用するロジックは端末上で決定的・説明可能・テスト可能であること。
- 監視者の早期注意を根拠に、選手向けの既存衝突警報を抑制・解除・遅延しない。
- 新しい状態共有を追加する場合、秘密情報、個人の詳細診断、長期位置履歴をRTDBへ保存しない。

私は日本の狭い河川で使うローイング（ボート）安全アプリを開発しています。

## 絶対に守る前提

- 水域: 茨城県土浦市の桜川。川幅は概ね40〜50m、狭所は35m。カーブは最短約200m間隔。
- 運用: 右側通行、片側1レーン。対向艇とは日常的にすれ違う。2〜12艇が同時に航行する。
- 艇種: 1x / 2x / 4x / 8+。巡航速度は概ね3〜5m/s。
- 狭所では、規定どおりの8+同士でも艇中心間がおよそ12.5mまで近づきうる。
  したがって「近い」だけで衝突危険や異常とは判定できない。
- GPSの精度は典型的に5〜15m程度。各艇から位置、速度、方位、accuracy、時刻を受信する。
- 新しい衝突予測に使える他艇情報は最大6秒程度まで。古い情報を長時間直線外挿してはならない。
- 監視者は陸上で画面を操作できる。選手は漕いでいる間、端末操作できない。
- 通信断・GPS不良は「安全」の証拠ではない。ただし、不確かなデータで早期注意を大量発報してもならない。
- 解法は端末上で決定的、説明可能、ユニットテスト可能であること。オンラインの機械学習・ブラックボックスAIは採用しない。

## 既存の安全機能

既存アプリには、別系統の衝突警報があります。

- 自艇・他艇の将来運動、艇種ごとの船体/安全領域、GPS不確実性を用いて、連続的な領域侵入を評価する。
- 既存の衝突警報は弱めない・置き換えない・150mへ拡張しない。
- 逆走は航路中心線とレーンの規定方向で判定し、停止・回頭・方位不確かでは出さず、約6秒継続してから確定する。

## 新しく作りたいもの（必須）

### A. 監視者向け150m早期注意

- 2艇がすれ違う向き（概ね対向）で進行し、150m以内に接近したら、監視者へ注意喚起したい。

- 3艇以上では、関係する艇を1つのグループへ集約して `接近中：A艇・B艇・C艇` と表示したい。
- バナーは最大1本に集約したい。艇ごとのカードを多数並べて地図を覆ってはならない。
- 初期は無音。誤報、点滅、通信断を安全扱いすることを避けたい。

### B. 将来の選手向け100m表示（任意の第2段階）

  `近くに他艇` と伝える案を検討している。
- 既存の衝突警報より優先させず、初期は音を鳴らさない。
- この案を採用すべきか、監視専用に留めるべきかも評価してほしい。

## 現時点の素朴な案

早期注意の入口条件を、次の全てとする案です。

1. 両艇の更新が新鮮（6秒以内）
2. 両艇が0.5m/s以上
3. 方位差が120度以上
4. 艇中心間の距離が150m以下
5. 2〜3秒連続で成立したら確定
6. 180m超かつ非該当が3〜5秒続いたら解除

しかし、カーブ、レーン、方位の揺れ、GPS誤差、3艇以上の集約、すれ違った後の解除、
停止艇、通信断の扱いが不十分だと考えています。
