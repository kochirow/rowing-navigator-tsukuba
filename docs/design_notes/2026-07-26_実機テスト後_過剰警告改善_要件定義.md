## 2. 根本原因

### 原因A: 岸の掃引に「排他領域」を使っている(過剰警告の本体)

岸の警告1133サンプルの理由コードは全て `continuous_domain_entry`。
近接注意(`shoreProximityCautionDistanceMeters = 3.0`)ではなく、
**排他領域の連続掃引**が立てている。近接距離を下げても直らない。

1x の領域寸法(`lib/config/boat_config.dart`):

| | h(前後) | w(横) | s |
| --- | --- | --- | --- |
| 船体領域 | 8.2 | **6.0**(片側3.0) | 4.0 |
| 排他領域 | 11.2 | **9.0**(片側4.5) | 5.8 |

排他領域は船体領域を全周1.5m膨らませたもの(全艇種で共通)。
さらにGPS帯が片側1.5m(`maxStaticGpsGuardFullWidthMeters = 3.0`)。

→ **岸区域の縁から6.0mで重なる = 岸の基準線から11mで鳴る。**

運用設定は `shore: waterSide 5.0m / landSide 15.0m`(manifest確認済み)。
第1章の狭所(川幅35m・実効航路幅25m・片側レーン12.5m)では、
レーン中央を完璧に守っても艇中心は岸から 5 + 6.25 = **11.25m**。
つまり **規定どおり漕いでも常に発報する境界に乗っている。**

実測もそのとおりになった。連続音が鳴った488サンプルのうち **368サンプル(75%)は
艇中心が岸区域の縁より外側**(= 岸の基準線から8m以上)にいた。
最大 9.5m 外側でも「重なっている」判定になっている。

### 原因B: `currentOverlap` が無条件に「切迫(連続音)」になる

`safety_orchestrator.dart:499` — `currentOverlap` なら即 `AlertUrgency.imminent` = 連続音。

岸と並走している状態や、桟橋に着けている状態は「重なっている」が
**切迫していない**。距離が縮まっていないのに連続音が鳴り続ける。
原則5(まずさと切迫度を混ぜない)の観点では、
`currentOverlap` は「どれだけまずいか」であって「どれだけ切迫しているか」ではない。

現状の停止時抑制(`_stableStopped`)は**自艇が止まっているとき**しか働かない。
「距離が止まっているとき」には働かない。

### 原因C: 岸・橋が辺ごとの長方形に分解され、別々の警告として扱われる

`legacy_danger_zone_generator.dart:63` — `id: 'default_${baseline.id}_$i'`。
基準線の各辺が独立した `StaticObstacle` になり、`alertId` も別になる。

- **岸**: 北岸153辺・南岸107辺。岸沿いを走ると
  `shore_south_65 → _66 → _67` と次々に「新しい脅威」が立ち、
  そのたびに新しい音声エピソードが始まる。実測で28区画が発報。
- **橋**: 橋は5点=4辺。実測で発報したのは各橋の `_0`(手前の面)と `_2`(奥の面)。
  **手前の面で1回、橋の下で奥の面がもう1回鳴る。**
  これが「橋の真下で鳴る」の直接の原因。

### 原因D: 音声チャンネルがprimary1本しかなく、上位カテゴリに占有される

`use_navigator.dart:1456` → `currentWarning = primary候補`。音は primary からしか出ない。

`alert_state_machine.dart:224` の帯順:

```
continuousAction 0 > singleAction 1 > persistentSystemFault 2 > entryEvent 3 > visualOnly 4
```

**`entryEvent`(カーブ・逆走)は system fault より下。**
本セッションでは `operational_coverage_unverified` が全区間、
`other_boat_receive_unavailable` がほぼ全区間 alerting だったため、
カーブ・逆走は525+171サンプル中 **primaryに一度もなれなかった**。
「逆走注意が鳴らなかった」の正体はこれ。検知は正常に働いていた。

さらに、`operational_coverage_unverified` は `audioAsset: null` である
(`use_navigator.dart:1355`)。これが primary になると
`use_navigator.dart:2782` で **`alert.stop()` が呼ばれ、鳴っていた音が止まる。**
無音のsystem faultが他の警告音を消す経路が存在する。

橋の遅れも同じ構造。実測(railway橋・t=1547〜1585s):

```
1547s bridge 33m 検知  ← primary は shore(2〜5m)
1553s bridge 19m       ← primary は shore
1564s bridge  7m       ← primary は shore
1573s bridge  0m       ← primary は shore
1574s bridge -1m 発音  ← ここで初めて overlap して primary を奪取(= 橋の真下)
```

岸が primary を握り続けている間、橋は一切鳴けない。
**岸の過剰警告を直すと橋のタイミングも直る**(依存関係)。

### 原因E: `other_boat_receive_unavailable` が数秒周期でフラップする

`dynamic_obstacle_service.dart:29` — 受信メッセージに1件でも不正な要素があると
`receiveDegraded = true`。デバウンスが無い。

実測: 315エピソード、`safe→alerting→clearing→safe` を数秒周期で反復。
periodic再生は10秒間隔(`use_alert.dart:186`)なので、
これだけで `add_warning.mp3` 94回の提示要求になっている。

### 原因F: 陸上で岸の連続音が鳴る

`assets/data/sakuragawa_obstacles.json` に `operationalCoveragePolygon` が無い。
このため release では `isOperationalCoverageUnverified = true` が常時成立し、
「未検証水域」バッジが出っぱなしで、かつ原因Dの無音primary問題を常時引き起こしている。

航跡を北岸基準線で符号判定すると、**0〜約600秒は陸側**(最大50m内陸 → 桟橋で0〜2m)。
t=172s(陸側約35m)に `shore_warning.mp3` の `once` + `loop` が発火している。
艇庫での準備・艇の運搬中に岸区域の中にいるため、当然のように連続音になる。

停止中は既存の安定停止抑制(`PRESENTATION_STABLE_STOP_SILENT` 190サンプル)が
効いていたが、**歩いて艇を運んでいる間は抑制対象外**になる。

### 原因G: 監視モードの異常通知が大きすぎる

`home_map_screen.dart:583` — 監視異常のたびに
`playCoachAnomalyAlert()`(= `add_warning.mp3` 単発)+ 赤い danger SnackBar 6秒。
`anomalyReannounceSec = 120` で継続中も2分おきに鳴り直す。

`lostAlertSec = 45` は、停止中送信10秒 + 画面OFF + 通信ジッタで容易に超える。
`BoatListPanel` に既に艇種・速度・電池・最終更新・異常が全部出ているので、
音と赤バナーは情報を足していない。

`practiceAreaUnavailable` の赤SnackBar(8秒)も同様。

## 3. 改善提案

### 提案1: 静的区域の掃引領域を kind 別にする 【最優先・原因A】

静的区域の連続掃引に使う領域を「**船体領域 + kind別クリアランス**」へ変える。
既定クリアランスを1.5mにすれば非岸カテゴリは現状と完全に一致する
(排他領域 = 船体領域 + 全周1.5m は全艇種で成立)。

`lib/config/risk_evaluator_config.dart` に追加:

```dart
/// 静的危険区域の掃引に使う片側クリアランス [m](船体領域からの追加分)。
///
/// 既定 1.5m は排他領域と一致する。排他領域は「他船に空けてほしい水面」を
/// 表す船舶領域の概念であり、**並走することが正常な岸**へ適用すると
/// DESIGN_PRINCIPLES 1.4「岸から数mを走るのは正常」と衝突する。
const defaultStaticSweepClearanceMeters = 1.5;

/// 岸。船体+オールが危険区域へ入るまで鳴らさない。
/// 1x で片側3.0m(=船体領域の実寸)。岸区域は水面側5mなので、
/// 「オールの先が岸から5m以内に入ったら鳴る」という説明可能な基準になる。
const shoreStaticSweepClearanceMeters = 0.0;
```

**効果(実測ログへの適用)**: 発報開始が岸区域の縁6.0m → 3.0m。
連続音488サンプルのうち **368サンプルが消える**。
第1章の狭所レーン中央(岸から11.25m)に対して2m以上の余裕ができる。

**安全側の担保**:
- 前後方向(`h`)は変えないので、**岸へ向かって進んでいる艇の検知時刻は変わらない**。
  減らすのは「並走で横に触れる」偽陽性だけ。
- 領域を縮める方向なので、不変条件8(`boundingRadius` の過小評価禁止)は
  broad-phase が過大側になるだけで破れない。
- 不変条件9(六角形の凸性 `s <= h`)にも影響しない。

### 提案2: 重なりの「切迫度」を接近速度で判定する 【原因B】

`AlertPresentationConfig` に追加:

```dart
/// 静的区域と重なっていても、この速度以上で距離が縮まっていなければ
/// 連続音まで上げない [m/s]。並走・係留は「まずい」が「切迫していない」。
final double staticOverlapClosingRateMetersPerSecond; // 0.3
/// 縮まらないまま重なり続けた場合に表示のみへ落とすまでの猶予。
final Duration staticOverlapImminentGrace; // 5秒
```

`_basePhysicalBehavior` の `currentOverlap → imminent` を
静的カテゴリに限って次へ変える。

1. 距離が縮まっている(または距離が取れない) → 従来どおり `imminent`
2. 縮まっていない → `approaching`(3秒間隔の断続音)へ1段下げる
3. 猶予を過ぎても縮まらない → `monitoring`(表示のみ)
4. 再び `stableStopRealertApproachMeters`(2m)縮まったら再武装

**距離が取得できない場合は「接近中」として扱う**(原則6: データ欠損は安全の根拠にならない)。
他艇(`_canSuppressAtRest` が false)は対象外。

これは既存の安定停止抑制を「自艇が止まっている」から
「距離が止まっている」へ一般化するもの。桟橋での押し出し、
岸沿いの休憩、艇の運搬がここで静かになる。

### 提案3: 静的警告を `sourceId` 単位に集約する 【原因C・橋の二重発報】

`ThreatInfo` に `obstacleSourceId` を追加し、`_fromRiskThreat` の `targetId` を
`sourceId`(= `shore_north` / `bridge_railway`)にする。
`SafetyOrchestrator` の `_prefer` が既に「最も切迫した候補」を選ぶため、
辺の集合が自動的に1つの警告へまとまる。

**効果**:
- 岸沿いの `_65 → _66 → _67` の音の連鎖が1エピソードになる。
- 橋の手前の面と奥の面が同一警告になり、**橋の下での再発音が消える**。
- 表示名も「北岸 126」ではなく「北岸」になり読みやすい。

### 提案4: 音声チャンネルを primary から分離する 【原因D・逆走が鳴らない】

`SafetyOrchestrator.processAssessment` を2点変更する。

1. **音声対象は「音声アセットを持つ候補」の中から選ぶ。**
   表示のprimaryとは独立にする。無音のsystem fault
   (`operational_coverage_unverified` / `outside_operational_coverage` /
   `audio_unavailable`)が音を止める経路がなくなる。

2. **`SafetySnapshot` に `oneShotAudioCues` を追加する。**
   `entryEvent`(カーブ・逆走)と `bandCappedCategories`(橋)の単発キューは、
   音声対象でなくてもキューへ積み、`use_alert` の直列キューで順に鳴らす。
   持続音(loop/periodic)は従来どおり1本だけ。

   単発キューは元々レート制限されている(区域進入1回 + `guidanceRearmDuration`、
   橋は提案3で1通過1回)ので、音の総量は増えない。
   本セッションに適用しても橋8 + カーブ10 + 逆走16 = 34回、
   削減される岸48 + `add_warning` 94 を大きく下回る。

### 提案5: system fault の鳴らし方を見直す 【原因E】

1. **デバウンスを入れる。** `lib/config/` に追加:

   ```dart
   /// 他艇受信の劣化をsystem faultとして確定するまでの継続時間 [秒]。
   /// 送信間隔10秒 + 通信ジッタでは発報しない。
   const dynamicReceiveFaultConfirmSec = 15;
   /// 復旧を確定するまでの継続時間 [秒]。
   const dynamicReceiveFaultClearSec = 15;
   ```
   → 315エピソードのフラップがほぼ消える。

2. **`receiveDegraded` の粒度を分ける。**
   「一部レコードが壊れている」(記録して継続)と
   「ストリーム自体が落ちている」(system fault)を区別する。
   現状は1件の不正レコードで全体が fault になる。

3. **system fault 専用の音声アセットを作り、`add_warning.mp3` の流用をやめる。**
   衝突音と同じ音を通信エラーに使うのは、衝突音そのものを形骸化させる。

4. **`other_boat_receive_unavailable` は periodic(10秒)ではなく
   「確定時に1回 + 5分ごとに鳴り直し + 常時バナー表示」にする。**
   原則1・6を満たしたまま(表示は消さない)音だけ減らす。

5. `assets/data/sakuragawa_obstacles.json` に
   **`operationalCoveragePolygon` を追加する。**
   「未検証水域」の常時表示が消え、提案6の陸上判定にも使える。

### 提案6: 陸上判定で音だけ止める 【原因F】

「川や霞ヶ浦にいない時は鳴らさない。ただし水上で誤って抑制しない」を満たす設計。

**判定**(全て満たしたときだけ「陸上」):
- 岸の基準線より**陸側**にいる(基準線の頂点順から水面側/陸側は既に確定している)
- 陸側への距離 > `max(12m, 2 × GPS accuracy)`
- その状態が **30秒継続**
- GPS品質が `good`(劣化・途絶中は判定しない ← 原則6)

**解除**: 水面側の測位を **1点でも**観測したら即時。判定は完全に非対称にする。

```dart
/// 岸の基準線より陸側へこれ以上入っていれば陸上候補とする [m]。
/// 川幅40〜50m・通常は岸から8m以上を走る(DESIGN_PRINCIPLES 1.4)ため、
/// 水上でこの条件が成立するには 20m 級のGPS誤差が要る。
const ashoreLandSideMarginMeters = 12.0;
const ashoreAccuracyMarginFactor = 2.0;
const ashoreConfirmationDuration = Duration(seconds: 30);
```

**止めるのは音だけ**(原則1)。検知・画面表示・記録・位置共有は継続する。
画面に「陸上と判定して警告音を止めています」を常時表示し、
**「音を戻す」ボタンで即座に手動解除できる**(原則2)。
状態遷移は診断イベント `ashore_state_changed` に残す。

本ログへの適用: 0〜600秒(陸側最大50m)が対象になり、t=172s の連続音が消える。
桟橋(陸側0〜2m)は余裕12mに満たないので陸上判定では静かにならないが、
**提案2(距離が縮まらないので表示のみ)がここを引き受ける**。二重に守る形になる。

### 提案7: 監視モードは無音・小さく表示 【原因G】

- **`playCoachAnomalyAlert()` を既定で無効にする。**
  監視者は画面を見られる。音はトランシーバーと干渉し近隣にも響く。
  設定で「長時間停止のみ音を鳴らす」を選べるようにする(既定OFF)。
- **赤い danger SnackBar をやめる。** 異常は `BoatListPanel` の行に既に出ている。
  地図上部に `異常 1` のような小さなチップだけ出し、タップで一覧を開く。
- **`practiceAreaUnavailable` の赤SnackBarもチップへ格下げする。**
- `lostAlertSec` を 45秒 → **90秒**へ。送信間隔10秒 + 画面OFF + ジッタでは鳴らない値にする。
  一覧の「N秒前」表示は今までどおり出るので、情報は失われない。

### 提案8: 逆走注意の扱い 【要判断】

逆走注意は**検知そのものは正常に動いていた**(16回進入)。
鳴らなかったのは原因Dによるもので、提案4で鳴るようになる。

ただし航跡を `reverse_main_channel` ポリゴンと突き合わせると、
**77分で16回出入りしている**(滞在時間5〜163秒、多くは30秒以下)。
現在の判定は「区域内に現在地があるか」だけで、**進行方向を見ていない**
(`collision_risk_evaluator_service.dart:855`)。

このまま提案4で音を出すと、正常に漕いでいるだけで16回鳴る。原則4に反する。
先に次のどちらかを決める必要がある。

- **案A(推奨)**: 逆走判定を方向つきにする。航路中心線と右側通行ルールから
  「その位置で進むべき向き」を出し、自艇の進行方位が90度以上ずれているときだけ発報する。
  中心線は既に `ChannelCenterline` として存在するので実装は素直。
- **案B**: 区域の形を見直し、`guidanceRearmDuration` を 5秒 → 60秒にする。
  実装は軽いが、正しく漕いでいても鳴る問題は残る。

カーブは10回で、1カーブあたり1回に相当するため現状のままで問題ない。

## 4. 実施順序

依存関係があるので、この順で入れる。

1. **提案1 + 提案2**(岸の過剰警告) — 単独で最も効く。橋の遅れも副次的に改善する
2. **提案3**(sourceId集約) — 橋の二重発報、岸の音の連鎖

## 5. テストへの影響

CLAUDE.md「警告ロジックを変更する場合は、必ず `test/` の単体テストを更新すること」に従う。
特に**実データ(`assets/data/sakuragawa_obstacles.json`)を使う統合テスト**は
設定値の意図と実効値の乖離を検出する唯一の手段なので、次を追加する。

- 提案1: 実データの北岸に対して、**岸から11m/9m/8m/6mを並走する1x**の
  発報有無を固定するテスト。桜川の狭所レーン中央(11.25m)で鳴らないことを不変条件にする。
- 提案1: 岸へ**向かっている**艇の検知時刻が変わらないことの回帰テスト(前後方向の担保)。
- 提案2: 重なったまま距離一定 → 連続音にならない / 再接近 → 連続音に戻る。
- 提案3: 1つの橋を通過して音声エピソードが1回であること。
- 提案4: system fault が alerting でも `entryEvent` のキューが出ること。
  無音のsystem faultが primary でも鳴っている音が止まらないこと。
- 提案6: 水上での GPS 誤差15mが陸上判定を成立させないこと。
  陸上判定中でも `SafetySnapshot` の検知結果が変わらないこと。

- 近接注意距離を0にして止めること(「やらないこと」)
