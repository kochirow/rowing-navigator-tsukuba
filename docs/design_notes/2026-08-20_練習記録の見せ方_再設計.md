作成日: 2026-08-20

`lib/models/session_model.dart`
位置づけ: **提案**。実装着手前のたたき台。安全経路には一切触れない(すべて表示専用)。

## 0. 結論(先に3行)

1. **記録の単位を「セッション」から「ピース(本)」へ移す。** いまの画面はセッション平均しか
   語らないので、何をやった日でも似た数字になる。
2. **ペースを単独で見せるのをやめ、`ペース = 1漕距離 × レート` の三角で見せる。**
   1漕距離(DPS)は `TrackPoint.distancePerStrokeMeters` としてすでに記録済みなのに、
   記録画面には1度も出していない。
3. **折れ線を減らし、表を主役にする。** グラフはピースごとに1枚だけ(ペース+レートの2軸)、
   全体は帯のタイムラインへ。スプリットは表。

## 1. いま何が起きているか(コードを読んだ事実)

### 1.1 記録詳細画面の現在の構成

`RecordDetailScreen`(`record_list_screen.dart:432-`)は上から順に:

| 順 | ブロック | 中身 |
|---|---|---|
| 1 | サマリーカード | 距離・時間・平均ペース・最高速度・艇種/シート・ワーク/休憩・警告秒数 |
| 2 | ペース推移 | セッション全体を1枚の折れ線(`_PaceTrendPainter`) |
| 3 | ピース(自動検出) | 1本ごとに「距離・時間・平均ペース・spm」+ **同じ形の折れ線をもう1枚ずつ** |
| 4 | 警告エピソード | 分類・時刻・最大危険度・最短距離・緯度経度・評価ドロップダウン |
| 5 | 下部ボタン | 削除 / GPX / CSV / 診断ZIP |

### 1.2 見づらさの原因(8点)

**(a) セッション平均しか語っていない。**
距離・時間・平均ペースは、アップも折り返しも休憩も本漕も混ぜた数字である。
`500m×5` をやった日と `20分UT2` をやった日で、この4つの数字はほとんど同じになる。
**「1回1回の記録が生かされていない」の正体はここ。** 練習の実体はピース(本)であって、
セッションの平均ではない。

**(b) 時間軸が「漕いでいない時間」に幅を配っている。**
`_PaceTrendPainter` の x 軸は `points.first.t` から `points.last.t` までの実時刻の線形写像
(`record_list_screen.dart:1073-1081`)。90分の練習で実際に漕いでいるのが20分なら、
グラフの**8割は空白**で、肝心のピースは横幅の数%に潰れる。

**(c) 除外した点をまたいで直線で結んでいる。**
`buildPaceTrend` は艇種別のしきい値より遅いサンプルを**黙って捨てる**
(`session_analyzer_service.dart:214-218`)。描画側の断線判定は「**描かれた点どうし**の間隔が
10秒超か」なので、10秒未満の減速は線でつながれる。
つまり**実際には起きていないペース変化が線として描かれる**。

**(d) y軸がセッション全体の最小・最大に自動追従する。**
下り1本で速い区間が1つあると、それが上端になり、UT区間の5秒差が潰れる。
目盛りは5秒刻みだが、レンジが広ければラベルは間引かれる(`record_list_screen.dart:1163`)。

**(e) 同じ形の折れ線が縦に並ぶ。**
ピースごとの120pxの折れ線が本数ぶん積み上がる。それぞれ**別々のy軸レンジ**で描かれるので、
**隣どうしを見比べても速い遅いが分からない**。面積は食うのに比較の役に立っていない。

**(f) 500m/250mスプリットは計算しているのに、1度も画面に出していない。**
`analyze()` は `splits`(500m)と `splits250` を作って `SessionSummary` に持たせている
(`session_analyzer_service.dart:110-150`)が、`lib/` の中で**読んでいる場所がない**。
つまり「スプリットのグラフが不要」以前に、スプリットの表はまだ存在しない。

**(g) すでに持っているストローク指標を捨てている。**
`TrackPoint` は 1漕距離 `distancePerStrokeMeters`、キャッチ減速、終盤加速、艇速保持を
1秒ごとに持っている。記録画面はこれを CSV へ書き出すだけ(`gpx_export_service.dart:206-209`)で、
**画面には出していない**。ローイングでいちばん技術に近い数字を、書き出し専用にしている。

**(h) 川なのに上り/下りを区別していない。**
桜川は流れと風があり、同じ出力でも上りと下りでペースが違う。いまはピースを検出順に
並べるだけなので、`#1 2:06 / #2 2:18 / #3 2:05 / #4 2:17` を見て
「調子が上下している」と読んでしまう。実際は往復しているだけである。

## 2. 設計の芯(この3つから全部を導く)

### 原則A: 記録の単位はピース(本)

セッションは「その日の入れ物」であって、振り返りの対象ではない。
振り返るのは **1本ずつ**と、**本どうしの比較**。
→ 画面は「一覧(日をまたぐ比較)」「セッション(今日やったこと)」「ピース(この1本の中身)」の3層。

### 原則B: ペースは単独では意味を持たない

ローイングの恒等式:

```
艇速 [m/s] = 1漕距離 [m] × レート [spm] / 60
ペース [秒/500m] = 500 × 60 / (1漕距離 × レート)
```

同じ `2:10/500m` でも、

- レート26 × 1漕距離 8.8m
- レート32 × 1漕距離 7.2m

はまったく別の漕ぎである。**ペース・レート・1漕距離は常に3つセットで出す。**
2つ出せば3つ目は決まるので、3つ並べても情報が増えないように見えるが、
**どれを動かして速くしたのかが読めるのは3つ並べたときだけ**である。

### 原則C: 有効・無効を明示して分ける(黙って落とさない)

いまは遅いサンプルを黙って捨てている。これは DESIGN_PRINCIPLES 原則6
(データ欠損を黙って扱わない)と同じ筋で、**表示にも当てはまる**。
除外するなら「何秒を、なぜ除外したか」を画面に書く。
川では**方向(上り/下り)**も分けないと比較にならない。

## 3. 何を出すか(指標の一覧と根拠)

| 指標 | 定義 | なぜ要るか | データ源 | 現状 |
|---|---|---|---|---|
| ペース | 秒/500m | 競技の共通言語 | 既存 | 表示済 |
| レート | spm | 出力の作り方 | `TrackPoint.spm` | ピースのみ |
| **1漕距離(DPS)** | 艇速×60/レート | **技術の代理指標**。同じペースをどう作ったか | `distancePerStrokeMeters` | **未表示** |
| **区間タイム** | 250m/500mごとの実タイム | 「本の中でどこが落ちたか」 | `splits250`/`splits` | **未表示** |
| **ばらつき** | 区間ペースの最速−最遅 | 一定に漕げているか。艇速変動は抵抗増加につながる | 計算のみ | なし |
| **前半/後半差** | 後半平均−前半平均 | フェード(垂れ)の有無 | 計算のみ | なし |
| **方向** | 上り/下り | 流れ・風の影響を分離 | 中心線 or 方位 | なし |
| ワーク/休憩 | 既存 | 練習密度 | 既存 | 表示済 |
| 参考: キャッチ減速 / 艇速保持 | 既存 | 1漕の中の質 | 既存 | 未表示(既定折りたたみ) |
| 警告エピソード | 既存 | 安全側の振り返り | 既存 | 表示済(維持) |

**外部の実務との整合。** NK SpeedCoach は「スプリット・レート・距離・1漕距離(glide)」を基本4点とし、
セッション後は 100m / 30秒などの**区間ごとの表**で振り返る形をとる。rowsandall は
インターバル(work/rest を色分けした表)を分析の入口に置く。
つまり **「区間の表」が業界の標準的な入口**であり、折れ線はその後の掘り下げに使われている。
いまのアプリは順序が逆になっている。

## 5. 「有効なタイム」の定義(ご要望の1点目)

現在の条件は「艇種別ペースしきい値より速い」1つだけ。これを次の3つに分ける。

| 除外理由 | 判定 | 画面表示 |
|---|---|---|
| 漕いでいない | 艇速 < `RowingPaceProfile.minimumDisplaySpeedMps` | 休憩として集計 |
| **回頭中** | 15秒窓の方位変化が60°超、または中心線に対する進行方向が反転 | 「回頭 m:ss」 |
| **測位が使えない** | `gnssQuality` / `positionFilterResult` が不採用、`estimateUncertaintyMeters` が大 | 「測位不良 m:ss」 |

**線は必ず断線させる。** 除外区間をまたいで直線で結ばない(1.2c の欠陥を潰す)。
除外した合計秒数を内訳つきでサマリーに出す(原則C)。

回頭の除外は特に効く。桜川は往復で必ず回頭が入り、そこは
**低速 + 方位が90°ずれる**ので、ペースにもDPSにも意味がない区間である。

## 6. スプリットの再定義(ご要望の2点目)

現在の `splits` はセッション全体を通した500m累積で、
**休憩や回頭をまたいで1区間になる**ため、その区間のタイムは何も意味しない。

変更:

1. **スプリットはピースの内側でだけ数える。** ピースをまたがない。
2. **既定を250mにする。** 桜川の直線は最短200m・最長700m
   (DESIGN_PRINCIPLES 1.1)。500m刻みだと1本に1〜2行しか出ず、表にならない。
   ピースが1500m超なら500m刻みへ自動で切り替える。
3. **列は「タイム・ペース・レート・1漕距離・ピース平均との差」。**
   グラフは出さない(ご指摘のとおり不要)。
4. 端数区間は現行どおり残すが、**端数と明記**して平均には入れない。

`Split` に `avgSpm` と `avgDistancePerStrokeMeters` を追加する必要がある
(いまは距離と時間しか持っていない)。

## 7. データモデルと解析の変更

```dart
// models/session_model.dart
class Split {
  final int index;
  final double distanceMeters;
  final double timeSec;
  final double? avgSpm;                       // 追加
  final double? avgDistancePerStrokeMeters;   // 追加
  final bool isPartial;                       // 追加(端数区間)
}

class Piece {
  // 既存 + 追加
  final List<Split> splits;                   // ピース内スプリット
  final PieceDirection? direction;            // upstream / downstream / unknown
  final double? paceSpreadSec;                // 最速区間−最遅区間
  final double? secondHalfDeltaSec;           // 後半−前半
  final double? avgDistancePerStrokeMeters;
}

class SessionSummary {
  // 既存 + 追加
  final double excludedTurningSec;
  final double excludedPoorFixSec;
  final List<RateBandSummary> rateBands;      // レート帯別の距離・時間・平均ペース
}
```

- `schemaVersion` を 4 へ。追加はすべて optional なので旧記録も読める。
- **詳細画面は保存済みサマリーではなく `points` から再解析している**
  (`record_list_screen.dart:492-500`)ため、**過去の記録もそのまま新表示になる**。
  移行スクリプトは不要。一覧カードだけは保存値を使うので、
  「本数」「最速ピース」は再計算値が無い旧記録では `--` にする。
- 方向判定は中心線があれば `ChannelCenterline.frameFor()` の `alongMeters` の増減で、
  無ければ平均方位で決める(縮退。CLAUDE.md の「機能を止めない」に合わせる)。
  中心線を解析へ渡すのは**任意引数**にし、`SessionAnalyzerService` は純Dartのまま保つ。

## 8. 段階計画(効く順)

| 段階 | 内容 | 見返り | 規模 |
|---|---|---|---|
| **P1** | ピース表 + ピース詳細画面(区間表 + グラフ1枚)。全体ペース折れ線を帯へ置換。ピースごとの折れ線を削除 | **最大**。ご要望2点がここで解決 | 中 |
| **P2** | 1漕距離(DPS)を全階層へ。ばらつき・前半後半差 | 大。技術の話ができるようになる | 小 |
| **P3** | 有効区間の厳密化(回頭・測位不良の除外と内訳表示)、断線描画 | 大。数字が信用できるようになる | 中 |
| **P4** | 上り/下り判定と往復ペア平均 | 中(桜川では大) | 中 |
| **P5** | 一覧カードの帯・最速ピース、レート帯別ベスト、期間トレンド | 中。継続の動機になる | 中 |
| **P6** | 航跡地図(ピース位置・警告位置)、メニュータグ、共有テキスト | 中 | 大 |

**最小構成(まずこれだけ)= P1 + P2。**
折れ線を N 枚消して表を1つ足し、列に spm と m/漕 を入れるだけで、
画面の情報量は減り、読める情報は増える。

### 共有テキスト(P6の一部・低コストで効く)

```
8/20(木) 4x 桜川 12.4km
500m×5  1:58 / 1:59 / 2:01 / 2:00 / 1:57  (r32, 7.9m/漕)
```
LINE へそのまま貼れる1タップの共有。部活の運用では地味に大きい。

## 10. やらないこと(非目標)

- **安全経路には触れない。** 記録画面は表示専用であり、警告判定・地図描画・位置共有へ
  1バイトも戻さない(不変条件12・13と同じ立場)。
- **サーバーへ送らない。** 端末内解析のまま。共有は利用者の明示操作だけ。
- **良い・悪いを断定しない。** キャッチ減速・艇速保持は参考値として折りたたみに置き、
  評価語を付けない(IMU設計ノートの方針)。
- **手入力を増やさない。** タグは選択式1タップまで。漕手に記入作業を課さない。
- **他艇との比較を記録画面に持ち込まない。** 監視端末の練習一括ログの領分。
