# 他艇接近アラート再設計

- 作成日: 2026-07-14
- 対象: Rowing Navigator 桜川版
- 状態: 実装前シミュレーション・連続衝突判定を反映済みの詳細仕様
- 目的: 他艇接近の警告漏れ、過剰警告、断続音、古い位置情報による誤判定をまとめて改善し、実運用で信頼できる警告へ移行する
- 非対象: 静的危険区域そのものの形状・位置の見直し、操船の自動指示、COLREGに基づく法的な避航判断の自動化

> この文書は既存の `改善計画_2026-07-12_信頼性・安全性レビュー.md` を置き換えない。既存文書がアプリ全体の無音故障を扱うのに対し、本書は「他艇接近」に限定して、判定・通信・警告提示・検証・移行を一続きの仕様として定める。

---

## 1. 結論

他艇接近は、危険区域への接近と同じ衝突評価ループに入れず、専用の `BoatEncounterEvaluator` として分離する。

設計の中心は次の6点とする。

1. **30秒の一律有効期限を廃止する**
   - 「予測に使える時間」と「最後に存在を表示してよい時間」を分ける。
   - 古い位置を長時間直線外挿しない。
2. **相対運動を評価する**
   - 現在距離だけでなく、接近速度、TCPA、DCPA、相対方位、船体領域、GPS不確実性を組み合わせる。
   - 予測終点や少数の時刻だけでなく、同期した相対運動区間と双方の合成安全領域を連続評価する。
3. **警告を状態機械で管理する**
   - GPS揺れ1回で音を止めない。
   - 危険開始と解除に別のしきい値を使う。
4. **複数艇を同時に保持する**
   - 最初に見つかった艇ではなく、行動期限が最も近い艇を主対象にする。
   - 対象を短時間で切り替えない。
5. **通信障害を安全状態と誤認しない**
   - 警告中の艇が途絶したら、即座に「安全」へ落とさず「位置更新遅延」へ移る。
6. **軽量な粗判定と精密判定を二段化する**
   - 全艇に対するベクトル計算は軽く行い、船体ポリゴン判定は危険候補だけに絞る。

危険区域評価と共通化するのは、GPS品質管理、位置不確実性、警告統合、音声再生、画面表示、ログだけとする。

## 2. 設計原則

### 2.1. アプリは見張りの代替ではなく、振り向く契機を作る

このアプリは回避方向を命令しない。「他艇が接近している可能性を知らせ、漕手が後方を目視確認する」ことを役割とする。

したがって、警告には次の性質が必要になる。

- 遅すぎない
- 誤報が多すぎて無視されない
- 一度鳴ったら、危険が解消するまで途切れない
- 通信やGPSが壊れたとき、正常に見せかけない
- 画面を注視させない

### 2.2. 「不明」は「安全」ではない

位置情報が古い、方位が信用できない、通信が途絶した、という状態は衝突なしを意味しない。

内部状態では少なくとも次を分離する。

- `safe`: 有効な観測に基づき、危険候補なし
- `candidate`: 危険候補を検出したが、確認中
- `alerting`: 他艇接近警告中
- `clearing`: 解消確認中。音声は継続
- `dataDegraded`: 対象艇または自艇のデータ品質低下
- `targetLost`: 警告対象だった艇の位置更新が途絶

### 2.3. 予測精度が落ちたら、予測時間を短くする

不確実性を無制限に膨らませると、川幅全体が危険判定になり警告の価値を失う。一方、8mなどの小さな上限で切ると警告漏れにつながる。

そこで、誤差が大きくなるほど次の順に処理する。

1. 船体領域を適度に拡張する
2. 予測可能時間を短くする
3. 直線外挿を停止する
4. データ品質低下として利用者へ示す

### 2.4. 警告の信頼性を数で管理する

「なんとなく良さそう」で調整しない。シャドーモードと実艇試験で、次を計測する。

- 有効警告数
- 誤警告数
- 見逃し数
- 警告開始から最接近までの秒数
- 1件の接近で音声が開始・停止した回数
- 主対象が切り替わった回数
- 受信データの年齢
- 評価処理時間

## 3. 現行実装の整理

### 3.1. 現在できていること

- 自艇と他艇を同じ将来時刻へ進めて衝突判定している
- 艇種別の船体領域・排他領域がある
- GPS `accuracy` とデータ経過時間を位置不確実性へ反映している
- 相対速度を使って予測刻みを細かくし、高速艇のすり抜けを防いでいる
- NaNや範囲外座標を除外している
- 警告対象ごとに録音音声を選び、同じ音声をループ再生できる
- RTDBの `onDisconnect()` により、異常終了した艇の位置削除を試みている

これらは新設計でも残す。ただし責務を分割して再利用する。

### 3.2. 構造上の弱点

#### A. 30秒間の直線外挿

現在は、他艇の最終更新から30秒まで、速度と方位が変わらないものとして現在位置まで外挿する。

- 3.0m/s × 30秒 = 90m
- 5.5m/s × 30秒 = 165m

これに対し、1艇あたりの不確実性マージンは最大8mである。外挿距離と不確実性が釣り合っていない。

#### B. 停止艇の送信が近接時にも10秒

現在の送信ポリシーは、警告中でなければ「停止中」を「他艇が近い」より先に判定する。停止扱いでも漂流、GPS速度の過小評価、相手艇からの接近があるため、近接時10秒は長い。

#### C. 低速時のコンパス方位

1.67m/s未満ではスマホコンパスを艇の進行方位に使用する。コンパスは端末の向きであり、艇のCourse Over Groundではない。ローイングでは漕手の向き、端末設置方向、艇の移動方向が一致しない場合がある。

#### D. 静的障害物と他艇の競合

静的障害物と他艇を同じ探索関数で評価し、橋以外の確実な障害物を見つけると他艇確認前に返る経路がある。同一レベルでは最初の脅威が残るため、他艇警告が静的障害物または受信配列順に左右される。

#### E. 警告状態が毎秒の判定値へ直結

現在は `RiskAssessment -> NavigationWarning?` を毎秒直接変換する。GPS揺れで `危険 -> 安全 -> 危険` となると、音声停止・再開が発生し得る。複数艇の順序が変わる場合も警告対象キーが揺れる。

#### F. 送信時刻が端末時計

メッセージの `timestamp` は送信端末の時刻である。自動時刻同期が無効な端末や大きな時計ずれがあると、新鮮な艇の除外、古い艇の新鮮扱い、過剰外挿が起こる。

## 4. 危険区域と他艇で分けるもの・共通にするもの

| 項目 | 危険区域 | 他艇 |
|---|---|---|
| 対象の位置 | 固定 | 毎秒変化し得る |
| 入力の鮮度 | プリセット更新時のみ | 常時評価が必要 |
| 予測対象 | 自艇のみ | 自艇と相手艇 |
| 主な判定 | 自艇将来領域と固定ポリゴン | 相対運動、CPA/TCPA、双方の船体領域 |
| 方位不確実性 | 自艇のみ | 双方に存在 |
| 通信途絶 | 原則なし | 中心的な故障モード |
| 複数対象 | 区域ごとの個別音声 | 主対象ロックと複数艇集約が必要 |
| 時間設定 | 5〜25秒の利用者設定が可能 | 状況適応型を基本とする |

共通化するもの:

- 自艇GPS品質ゲート
- 緯度経度の局所座標変換
- 不確実性の表現
- 警告表示・音声出力
- データ品質低下の表示
- 構造化ログ
- 性能計測

## 5. 推奨アーキテクチャ

```text
Position stream / RTDB stream
        |
        v
InputQualityGate
  - 値域、時刻、精度、ジャンプ、順序、重複
        |
        +---------------------------+
        |                           |
        v                           v
OwnBoatTrackEstimator       OtherBoatTrackStore
  - COG、速度、旋回率          - 艇ごとの短期履歴
  - 品質、共分散                - 鮮度、接続状態、品質
        |                           |
        +-------------+-------------+
                      v
             BoatEncounterEvaluator
             1. 粗い候補抽出
             2. CPA/TCPA/DCPA
             3. 船体領域の精密確認
             4. 全候補を返す
                      |
          +-----------+-----------+
          |                       |
          v                       v
HazardEvaluator            AlertArbitrator
                                |
                                v
                         AlertStateMachine
                                |
                       +--------+--------+
                       v                 v
                  Audio loop         Safety banner
```

### 5.1. サービス責務

#### `OtherBoatTrackStore`

艇IDごとに直近5〜8サンプルだけを保持する。

- 受信順序の補正
- 重複・巻き戻りメッセージの破棄
- サーバー時刻と受信時刻の保持
- COG、速度、旋回率の推定
- 鮮度状態の判定
- 最終有効位置の保持
- 同一艇IDを複数端末が使った可能性の検知

長時間の全航跡はこのサービスに持たせない。メモリと責務を限定する。

#### `BoatEncounterEvaluator`

入力された全艇について個別の `BoatThreatAssessment` を返す。単一の `primaryThreat` だけを返さない。

#### `AlertArbitrator`

他艇、危険区域、GPS途絶、位置共有失敗など異種警告を比較し、表示対象と音声対象を決める。静的障害物が先に列挙されたという理由で他艇が隠れないようにする。

#### `AlertStateMachine`

候補確認、警告継続、解除確認、対象ロック、通信途絶への遷移を担当する。音声プレイヤーは状態機械の最終出力だけを見る。

## 6. 位置・運動推定

### 6.1. 衝突計算では端末コンパスを使わない

表示用方位と衝突予測用速度ベクトルを分離する。

- 速度が十分あり、直近GPS変位がGPS誤差を上回る:
  - 直近3〜5点の変位からCOGを求める
  - 円環EMAで平滑化する
- 低速または変位不足:
  - 方位を `unknown` とする
  - 速度が小さければ停止・漂流物として全方向の安全領域を使う
- 旋回中:
  - 直線予測の信頼度を下げる
  - 予測時間を短くする

初期仮説:

- `speed < 0.8m/s`: 方位依存の長時間予測をしない
- GPS変位が `max(3m, 1.5 × accuracy)` 未満: COG更新に使わない
- 直近3秒の旋回率が大きい: 予測上限を6〜8秒へ短縮

数値は実艇ログで調整する。1.67m/sという現行境界は、艇速としては通常航行域に近く、衝突計算のコンパス切替境界として高すぎる。

### 6.2. 局所直交座標で相対運動を計算する

対象範囲が数百mなので、自艇周辺をENU相当の平面座標へ変換して計算する。

```text
r = p_other - p_own
v = v_other - v_own
tcpa = clamp(-(r dot v) / |v|^2, 0, horizon)
dcpa = |r + v * tcpa|
closingSpeed = -d(|r|)/dt
```

`|v|` が小さい場合はTCPAが不安定になるため、CPA値で無理に判定せず、現在距離、船体領域、相対距離の増減を優先する。

### 6.2.1. 相対運動区間と合成安全領域

CPA/TCPAは中心点同士の最接近を説明する値であり、それだけでは長さ・幅のある艇同士の最初の接触時刻を表せない。直進・一定速度を仮定できる各区間では、次の連続判定を最終判定に使う。

```text
r(t) = r0 + vRelative * t
pairAccuracy = sqrt(ownAccuracy^2 + otherAccuracy^2)
gpsCenterDistanceGuard = clamp(pairAccuracy * 0.125, 0, 1.5m)
baseLateralCenterDistance = ownExclusiveWidth / 2 + otherExclusiveWidth / 2
alertLateralCenterDistance = baseLateralCenterDistance + gpsCenterDistanceGuard
C = ownExclusiveDomain + (-otherBodyDomain) + gpsCenterDistanceGuard

intersects = r([0, horizon]) intersects C
tEnter     = r(t)がCへ最初に入る時刻
tExit      = r(t)がCから最後に出る時刻
```

- `C`はMinkowski和で作るconfiguration-space obstacleで、双方の艇種・船体寸法・方位を保持する。
- 確実判定では`ownExclusiveDomain + (-otherBodyDomain)`と逆側の組合せを評価する。
- GPS補正は「2艇の中心間距離しきい値へ何m足すか」で管理する。両艇へ個別に全量を加えない。
- 排他領域は実幅7〜8mに対して既に余裕を持つため、GPS accuracy全量を衝突帯へ反映しない。初期値は合成accuracyの0.125倍、中心間距離への追加上限は1.5mとする。これは従来記述の「合成全幅へ0.25倍、最大3m追加」と同じ幾何だが、実装と説明では中心間距離表現を使う。
- 1x同士は基本中心間距離9m、双方accuracy 5mならGPS補正約0.9mを加え、約9.9m以内を候補とする。
- データ経過、旋回、方位不明は帯幅を際限なく広げず、予測窓短縮と`dataDegraded`で扱う。
- `tEnter=0`は現在すでに安全領域が重なることを意味する。
- 予測終点が`C`の反対側へ通り抜けていても、区間途中に`tEnter`があれば衝突候補を維持する。
- 2本の絶対航跡が交差しても、同期相対区間が`C`へ入らなければ時間差交差として除外する。
- 絶対航跡が平行でも、追越し等で同期相対区間が`C`へ入れば検知する。

第1段階では合成領域を外接円で近似し、次の二次不等式の解区間を軽量に求めてよい。

```text
|r0 + vRelative * t| <= combinedRadius
```

円近似は候補を落とさないbroad phase専用とし、最終判断は向きを持つ合成安全領域で行う。方位変化・旋回がある場合は時間区間を分割して`C`を更新する。艇の全長を半径とする外接円capsuleは行動警告の直接条件にせず、精密分割ができない場合は予測時間を短縮して`dataDegraded`を返す。

### 6.3. 相対位置と進行状態を分類する

内部分類:

- `headOn`: 正面接近
- `crossing`: 交差
- `overtaking`: 追越し
- `parallel`: 並走
- `stationaryOrDrifting`: 停止・漂流
- `diverging`: 離反
- `uncertain`: 方位・速度・鮮度不足

これは法的な避航指示を出すためではなく、予測方法としきい値を選ぶために使う。

例:

- `diverging`: 現在近くても距離増加が安定していれば解除を早める
- `parallel`: TCPAだけでは不安定なので横距離と船体領域を重視
- `overtaking`: 同方向・速度差が小さくても長時間接近するため、相対速度だけで除外しない
- `stationaryOrDrifting`: 方位を信用せず、円形または低速用領域で評価

### 6.4. 不確実性を速度・古さ・旋回へ連動させる

現行の「経過1秒につき0.5m、最大8m」は高速艇と変針に追随できない。

新設計では概念的に次を持つ。

```text
positionUncertainty
  = gpsComponent
  + ageComponent(speed, age)
  + headingComponent(speed, age, headingQuality)
  + turnComponent(turnRate, age)
```

重要な制約:

- 不確実性を小さな固定上限で切って予測を続けない
- 許容範囲を超えたら `dataDegraded` にする
- GPS誤差をそのまま単純加算すると誤警告が増えるため、実ログで相関を確認する
- 橋付近などマルチパスが増える地点は、将来必要なら場所依存の品質情報を記録する

## 7. データ鮮度と通信

### 7.1. 鮮度状態

初期仮説:

| 最終受信から | 状態 | 衝突予測 | 表示・警告 |
|---:|---|---|---|
| 0〜3秒 | `fresh` | 通常予測 | 通常表示 |
| 3〜6秒 | `degraded` | 予測時間短縮、不確実性増加 | マーカーを薄くする候補 |
| 6〜10秒 | `lostForPrediction` | 直線外挿停止 | 最終位置を点線表示。直前の危険を即解除しない |
| 10秒超 | `expired` | 対象外 | 通常一覧から除外。直前に警告中なら通信途絶を明示 |

「3/6/10秒」は確定値ではない。実測するネットワーク遅延の95/99パーセンタイルを基に調整する。

### 7.2. 警告中の通信途絶

危険艇の更新が途絶した場合:

1. 0〜6秒: 不確実性を増やしながら警告継続
2. 6秒超: 「他艇接近」の確定的な軌道表示を止め、`targetLost` へ移行
3. 音を突然無音にしない
4. 画面には「接近していた他艇の位置更新が途絶」と表示
5. 10秒超で通常の衝突予測対象から外す

`targetLost` の音を他艇接近音のままにするか、位置共有異常音へ切り替えるかは実機確認で決める。音声ファイル追加を最小にしたい場合は、他艇接近音を継続し、画面だけ状態変更する。

### 7.3. 送信ポリシー

推奨優先順位:

1. 自艇または他艇の警告中: 1秒
2. 300m以内に他艇あり:
   - 移動中: 1秒
   - 停止・低速: 2秒
3. 他艇なし・移動中: 5秒
4. 他艇なし・停止中: 10秒

変針を検知した場合は、周囲に他艇がいなくても次の2〜3送信だけ1秒へ上げる案を検討する。AISでも変針時は報告頻度を高める考え方が使われる。

### 7.4. メッセージスキーマ

追加候補:

```text
schemaVersion       int
boatId              string
sessionId           string
sequence            int
deviceTimestampMs   int
serverTimestampMs   int
lat/lng             double
speed               double
courseOverGround    double?
headingQuality      enum
turnRate            double?
accuracy            double?
navigationState     moving/stopped/turning/unknown
```

要点:

- `sequence` で遅延到着した古いメッセージを破棄する
- `sessionId` で同一艇IDの前回セッションと区別する
- `serverTimestampMs` で端末時計ずれを吸収する
- `schemaVersion` で段階配信中の旧アプリと互換性を持たせる
- 不明なフィールドは無視し、旧メッセージには安全な既定動作を使う

### 7.5. プレゼンス

RTDBの `onDisconnect()` は継続使用する。ただし削除だけではなく、可能なら接続状態と最終オンライン時刻を分けて持つ。

- `/live_positions/{boatId}`: 最新位置
- `/presence/{boatId}/{sessionId}`: online/offline、lastSeen

削除イベントと一時的な再接続を区別できるため、対象艇が消えた理由を判断しやすい。

## 8. 衝突候補の二段階評価

### 8.1. 第1段階: 軽量な候補抽出

全艇へ毎秒実施する。

1. 入力品質・鮮度を確認
2. 現在距離が探索範囲外なら除外
3. 相対速度、TCPA、DCPA、距離増減を計算
4. 船体領域を外接円または簡易楕円で近似
5. 危険候補スコアを算出

探索範囲は固定300mを上限候補としつつ、実評価は次で絞る。

```text
candidateDistance
  = relativeSpeed * effectiveHorizon
  + combinedSafetyDomain
  + uncertainty
```

### 8.2. 第2段階: 船体領域による精密確認

第1段階の上位候補、または一定スコア以上の艇だけに実施する。精密確認は現在・TCPA等の数点だけではなく、§6.2.1の相対運動区間と合成安全領域の連続交差を求める。

出力する時刻:

- `tEnter`: 合成安全領域へ最初に入る時刻
- `tCPA`: 中心点間距離が最小になる時刻
- `tExit`: 合成安全領域から出る時刻
- 自艇・相手艇の停止／操船に必要な時刻

`tCPA`前後の離散サンプルはデバッグ比較には使えるが、連続交差なしを証明する根拠にはしない。旋回中や方位不明では、長い直線予測や無制限な予測点追加を避け、予測時間を短くして安全領域を保守的にする。

### 8.3. 時間差交差を誤警告しない

航跡が地理的に交差しても、同じ時刻に交差点へ到達しなければ衝突ではない。必ず自艇・他艇を同一の将来時刻へ進めて確認する。現在の同期予測の長所を維持する。

### 8.4. CPA/TCPAだけに依存しない

次の場合はCPA/TCPAが不安定または不十分になる。

- 相対速度が小さい並走
- 追越し
- 停止艇
- 急旋回
- GPS速度が0付近で揺れる
- 川の屈曲で直線予測が成立しない

したがって最終判定は、CPA/TCPA、現在距離、接近速度、相対方位、船体領域、データ品質の組み合わせとする。

### 8.5. ゼロ幅の延長線だけに依存しない

「両艇の進行方向へ線を伸ばし、線が交わったら警告」は候補抽出の直感としては正しいが、最終条件にはしない。

- 到着時刻が違う交差で誤警告になる
- 平行な中心線でも追越し・横幅接触は起こる
- 艇の長さ・幅、オール、排他余裕、GPS誤差を表せない
- 停止艇は有効な進行線を持たない
- 旋回中は一本の直線が実経路を表さない

したがって、延長線は`時間付き相対線分`へ、線の交差は`合成安全領域への侵入`へ置き換える。これは利用者案の目的である「区間途中の危険を飛び越さない」を保ちつつ、誤警告と別種の見逃しを防ぐ。

## 9. リスク評価と主対象選択

### 9.1. 戻り値

```text
BoatThreatAssessment
  targetId
  sessionId
  encounterType
  currentDistanceMeters
  closingSpeedMps
  tcpaSeconds
  dcpaMeters
  firstEntryTimeSeconds
  firstExitTimeSeconds
  currentOverlap
  minimumSeparationMeters
  predictedContactPoint
  actionDeadlineSeconds
  confidence
  freshness
  reasonCodes[]
  riskScore
```

`reasonCodes` 例:

- `domain_overlap_now`
- `domain_overlap_predicted`
- `continuous_domain_entry`
- `path_crossing_time_separated`
- `dcpa_below_domain`
- `head_on_closing`
- `parallel_too_close`
- `stale_target`
- `heading_unknown`
- `gps_uncertainty_high`

### 9.2. 行動期限

単純なリスクレベルではなく、概念的に次を使う。

```text
actionDeadline
  = firstEntryTime
  - lookBackTime
  - recognitionAndCrewResponseTime
  - maneuverOrStoppingTime
```

値が小さいほど先に行動が必要である。`firstEntryTime`は中心点のTCPAではなく、合成安全領域へ最初に入る時刻を使う。現在重なっていれば0秒である。連続交差が無い場合、TCPAが存在することだけで衝突警告を作らず、並走近接・データ劣化等の別reasonで評価する。TCPAが同じでも艇種・速度・停止距離で優先度が変わる。

`lookBackTime` と `recognitionAndCrewResponseTime` は現地試験で確認する。机上だけで固定しない。

### 9.3. 主対象ロック

- 警告開始後、主対象を最低3秒保持
- 新対象へ切り替えるのは、次のいずれかの場合
  - 現在領域が重なった
  - 行動期限が現対象より明確に短い
  - リスクスコアが一定割合以上高い
  - 現対象が解消・失効した
- 同程度の艇同士では、RTDBの配列順で切り替えない
- 画面は主対象に加えて「他に危険候補N艇」を表示可能にする

## 10. 警告状態機械

### 10.1. 状態遷移

```text
safe
  -> candidate
     -> alerting
        -> clearing
           -> safe
        -> targetLost
        -> alerting (危険継続)
  -> alerting (即時条件)
```

### 10.2. 警告開始

通常条件:

- 2回連続、約2秒間の危険判定で `candidate -> alerting`

即時条件:

- 現在すでに船体安全領域が重なる
- TCPAが4〜5秒以内
- 現在距離が緊急近接しきい値以下
- 高速の正面接近で行動期限が0以下

これによりGPSの一時的な跳ねを抑えながら、本当に切迫した接近を2秒遅らせない。

### 10.3. 警告解除

次をすべて満たす状態が3秒継続したら解除する。

- 距離が安定して増えている
- TCPAが過去、または衝突方向でない
- DCPAが解除しきい値を超えた
- 現在の船体安全領域が離れている
- データが有効である

開始と解除の境界を分ける。

- 進入境界: 船体領域 × 1.0
- 解除境界: 船体領域 × 1.3 を初期値候補

`clearing` 中は音声を止めない。1回でも危険判定へ戻れば `alerting` へ復帰し、音声は再起動せず同じループを継続する。

### 10.4. 音声制御

- 状態機械の警告キーが同じ間は `play()` を再発行しても再スタートしない
- 主対象が同じなら音声を継続
- 同じ他艇音声を使う対象間で主対象が変わっても、音を止めて頭出ししない
- 新しい別種の重大警告が発生したときだけ音声切替を検討
- オーディオフォーカス喪失後に警告中なら再開を確認
- ナビ開始前の音声テストは維持

### 10.5. 画面表示

漕手へは短く、判断可能な情報だけを出す。

通常:

- タイトル: `他艇に接近`
- 本文: `後方を振り向いて目視確認してください`

追加表示候補:

- `危険候補 2艇`
- `位置更新が遅れています`
- 地図上の危険艇強調
- 古い位置は点線円・低彩度

CPA/TCPAの数値を航行中の主画面へ常時出す必要はない。デバッグ画面またはログ確認用とする。

## 11. 予測時間

### 11.1. 他艇は固定25秒にしない

危険区域の予測秒数スライダー5〜25秒は維持してよいが、他艇へ同じ設定を流用しない。

他艇の初期仮説:

- 基本予測: 12秒
- 正面接近・相対速度大: 最大18秒
- 変針中・鮮度低下・方位不明: 6〜10秒
- 現在近接: 予測時間にかかわらず評価

30秒予測は採用しない。25秒も、利用者が明示的に「早め」を選んだだけで全状況へ適用しない。

### 11.2. 設定UI

他艇は秒数スライダーより、次の3段階を推奨する。

- `早め`
- `標準`
- `遅め`

内部では予測時間だけでなく、確認回数、解除余裕、候補スコアを安全な範囲で調整する。利用者が「25秒にしたから必ず25秒前に鳴る」と誤解しない表現にする。

## 12. 実運用リスク一覧と対応

| リスク | 起こること | 対応 |
|---|---|---|
| GPS揺れ | 危険・安全を往復し音が断続 | 2回確認、3秒解除確認、1.3倍ヒステリシス |
| 通信遅延 | 古い位置へ警告、または突然消える | 鮮度段階、予測停止、`targetLost` |
| 端末時計ずれ | 新鮮な艇を除外、古い艇を外挿 | サーバー時刻、受信時刻、sequence |
| 低速コンパス | 艇と無関係な方向へ予測 | COG利用、低速時は方位不明 |
| 急旋回 | 直線予測が外れる | 旋回率検知、予測時間短縮 |
| 予測点のすり抜け | 区間途中で接触するのに両端が安全 | 相対線分と合成安全領域の連続交差、`tEnter` |
| 延長線交差だけの判定 | 時間差交差を誤警告、並走追越しを見逃す | 時刻同期した相対運動、艇幅を持つ合成領域 |
| 時間差交差 | 航跡だけ交差し誤警告 | 同一将来時刻で評価 |
| 並走 | TCPAが不安定 | 横距離、船体領域、距離傾向を重視 |
| 追越し | 相対速度が小さく長く接近 | 同方向専用条件、長時間近接の扱い |
| 停止・漂流 | 10秒送信中に移動 | 近接時2秒送信、方位非依存領域 |
| 複数艇 | 対象が毎秒切り替わる | 全候補保持、主対象3秒ロック |
| 静的障害物との競合 | 他艇警告が隠れる | 評価器分離、AlertArbitrator |
| 音声切替競合 | ループが再スタート | 同音声維持、警告キーと音声キーを分離 |
| アプリ背景化 | 自艇更新・警告が止まる | 既存のGPS死活監視、共有失敗表示と接続 |
| 音量・サイレント | 警告に気づけない | 開始前音声テスト、AudioContext維持 |
| 受信艇が多い | UI停止、電池消費 | 粗判定O(N)、精密判定を上位候補へ限定 |
| 不正データ | 全評価停止 | 艇単位の検証・例外分離、有限性確認 |
| 同一boatIdの重複 | 位置が瞬間移動 | sessionId、sequence、重複検知 |
| Firebaseルール不備 | 他者による位置改変・閲覧 | 認証必須、本人ノードのみ書込、値域検証 |
| 誤警告の常態化 | 警告を無視・機能OFF | シャドーモード、誤警告率計測、理由ログ |

## 13. 性能・電池設計

### 13.1. 現状負荷

プリセット危険区域は基準線313区間と個別障害物を含む。現在は予測ステップごとに静的障害物と他艇を同じ関数で探索するため、25秒予測と高い相対速度の組合せでは、毎秒数万回規模のポリゴン判定になり得る。

### 13.2. 改善方針

- 他艇評価を静的障害物ループから分離
- 全艇への第1段階はベクトル演算のみ
- 船体ポリゴンは上位候補または一定スコア以上だけ
- 静的障害物は空間インデックスまたは近傍キャッシュで絞る
- 評価周期は1Hzを基本とし、GPSイベントごとに無制限実行しない
- UIへ渡す値は必要なときだけ更新し、同じ警告状態で再描画を増やさない
- バッテリー残量は毎送信で取得せず、30〜60秒キャッシュ
- ログ書込はメモリへ集約し、一定間隔でまとめて永続化

### 13.3. 性能受入基準

中程度のAndroid実機を基準に、初期目標を置く。

- 他艇20艇、静的区域現行データで、リスク評価p95が10ms未満
- 1秒周期を連続して超過しない
- 60分航行で処理遅延が増加しない
- メモリ使用量が艇数に対して無制限増加しない
- 音声ループ中も地図操作が明らかにカクつかない

電池は端末差が大きいため固定%だけで合否にしない。同一端末・同一条件で現行版と新設計版を比較する。

## 14. セキュリティ・プライバシー

位置情報は部員の行動を示すため、安全機能であっても公開範囲を最小化する。

確認事項:

- RTDB読み取りは認証済み利用者に限定
- 各端末は自分の `boatId` ノードだけ書き込める
- lat/lng、speed、timestamp、accuracyの値域をルールで検証
- 古い `schemaVersion` を拒否せず、安全に読み替える
- live positionは練習終了時・切断時に削除
- 詳細な衝突判定ログは原則端末内保存
- 開発用ログへ緯度経度・匿名認証UIDを常時出さない
- 実艇検証ログを共有する場合は艇IDを仮名化し、保存期間を決める

Firebase設定ファイルがリポジトリにあること自体より、サーバー側Security Rulesが適切かが重要である。実装時には管理画面上のルールも必ず確認する。

## 15. ログと観測可能性

安全機能では、警告が出た理由と出なかった理由を後から確認できる必要がある。

### 15.1. 構造化イベント

```text
boat_track_freshness_changed
boat_candidate_detected
boat_alert_started
boat_alert_target_switched
boat_alert_entered_clearing
boat_alert_cleared
boat_target_lost
boat_message_out_of_order_ignored

```

記録項目:

- 対象の仮名ID
- encounterType
- distance、TCPA、DCPA、closingSpeed

- reasonCodes
- 評価時間

ログ保存失敗で衝突評価を止めない。ログは非同期・容量上限付きとし、位置履歴を際限なく保存しない。

## 16. テスト計画

### 16.1. ユニットテスト

必須シナリオ:

1. 正面接近
2. 同時刻に交差
3. 同じ場所を異なる時刻に通過
4. 同方向追越し
5. 安全距離で並走
6. 過近距離で並走
7. 離反中
8. 停止艇への接近
9. 0.49m/s程度の漂流艇
10. 急旋回艇
11. 低速・方位不明
12. GPS accuracyが大きい艇
13. 2/4/7/11秒古い艇
14. 通信途絶直前まで危険だった艇
15. 複数艇の受信配列順入替
16. より危険な新対象による主対象切替
17. 同一boatIdのsessionId変更
18. sequence巻き戻り
19. 端末時計が±2分ずれたメッセージ
20. NaN、Infinity、範囲外、欠損フィールド
21. 予測終点が接触地点を通過済みでも区間途中の`tEnter`を検知
22. 現行2mサンプル点の中間だけで接触する高速交差
23. 中心航跡は交差するが到着時刻が異なる2艇
24. 中心航跡は平行だが後艇が安全領域へ追いつく2艇
25. 現在重なり、将来終点では離れるケースで`tEnter=0`
26. 相対速度ほぼ0の過近距離並走
27. 一方または双方が旋回し、予測窓短縮・不確実性判定へ移るケース
28. GPSジャンプで相手艇が反対側へ見えても即時safeへ落ちないケース
29. 5〜25秒の感度設定変更で、同一区間の連続交差結果が変わらないこと

### 16.2. 状態機械テスト

- `danger, safe, danger` で音声が停止しない
- 危険2回連続で警告開始
- 即時条件は1回で警告開始
- 安全2秒では解除せず、3秒で解除
- clearing中に危険へ戻っても音声を再スタートしない
- 同音声の別艇へ主対象が変わっても無音区間を作らない
- 警告中のtargetLostで即時停止しない

### 16.3. シミュレーション

GPXまたは生成軌跡で、速度・GPS誤差・通信間隔を再現する。乱数を使う場合はseedを固定し、回帰テスト可能にする。

最低限のパラメータ範囲:

- 自艇速度: 0〜5.5m/s
- 相手艇速度: 0〜6m/s
- GPS誤差: 2〜25m
- 更新間隔: 1〜10秒
- パケット欠落: 0〜30%
- 時刻ずれ: ±120秒
- 他艇数: 0、1、5、20

### 16.4. 実機陸上試験

艇へ載せる前に2〜3台のスマホで実施する。

- 徒歩で正面接近・すれ違い
- 片方を停止、もう片方が接近
- 機内モードON/OFF
- 端末時計をずらす
- 画面ロック・バックグラウンド
- 音声再生中の通知・通話割込み
- AndroidとiPhoneの混在

### 16.5. 実艇試験

安全員・コーチの監視下で段階的に行う。

1. 1艇のみでGPS・方位品質を採取
2. 2艇の安全距離並走
3. 低速の正面接近
4. 追越し
5. 安全余裕を取った交差
6. 停止・漂流艇への接近
7. 複数艇

実艇試験では意図的に危険距離へ入らない。判定しきい値は安全距離を保ったまま縮尺したシナリオまたはログ再生で確認する。

## 17. 受入基準

### 17.1. 機能

- 警告条件中は音声が連続ループする
- GPS揺れ1回で音声が止まらない
- 明確な離反後、3〜5秒程度で警告が解除される
- 複数艇の受信順を変えても主対象が不合理に変わらない
- 古い艇を30秒直線外挿しない
- 警告艇の通信途絶を安全扱いしない
- 静的障害物が他艇警告を隠さない
- 低速時の端末向きで予測方向が変わらない

### 17.2. 運用

- 利用者が「なぜ鳴ったか」を実艇ログから説明できる
- 誤警告が繰り返す場所・状況を特定できる
- 旧方式へ切り戻せる
- 新旧アプリ混在期間でもクラッシュ・全警告停止が起こらない

### 17.3. 安全

- 入力不明・通信途絶を `safe` に変換しない
- 評価例外が他艇全体の警告停止へ波及しない
- 新方式の誤警告削減が、正面接近・交差・停止艇の見逃し増加と引き換えになっていない
- 予測区間途中の接触が、終点位置・離散サンプル間隔・受信配列順によって消えない

## 18. 段階移行

### Phase 0: 計測準備

- 現行判定へ理由コードと処理時間ログを追加
- 実際の受信間隔・GPS accuracy・時計ずれを確認
- 音声開始停止回数を記録

### Phase 1: データ層

- Message schemaVersion、sessionId、sequence、serverTimestamp
- OtherBoatTrackStore
- 鮮度状態
- 低速COGと方位品質
- 送信ポリシーの近接優先

この段階では警告結果を変えない。

### Phase 2: シャドー評価

- BoatEncounterEvaluatorを現行評価と並行実行
- 新評価では音を鳴らさない
- 新旧差分を端末内ログへ記録
- シミュレーションと陸上試験で比較

### Phase 3: 他艇警告だけ切替

- 危険区域評価は現状維持
- AlertStateMachineを有効化
- 旧他艇評価へ戻せるfeature flagを残す
- 少数端末で実艇試験

### Phase 4: 性能最適化と本運用

- 空間インデックス
- 候補上位への精密判定限定
- バッテリー取得キャッシュ
- 閾値の実艇ログ調整
- feature flag撤去は安定運用後に判断

## 24. 最終方針

最初に着手すべきなのは、しきい値調整ではなく次の順序である。

1. 他艇履歴と鮮度状態を独立させる
2. 低速コンパスを衝突予測から外す
3. 相対運動評価を専用サービスへ分離する
4. 警告状態機械を導入する
5. シャドーモードで現行方式と比較する
6. 実艇試験後に他艇警告だけ切り替える

この順序なら、危険区域や既存音声など動いている機能を保ったまま、他艇接近だけを段階的に刷新できる。
