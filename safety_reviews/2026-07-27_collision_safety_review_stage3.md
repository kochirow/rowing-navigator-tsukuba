## 3. 所見一覧

### S3-γ: 辺が共線のとき `minimumSeparationMeters` が0に潰れる

- 該当箇所: `continuous_collision_service.dart:439-445`（`_segmentsIntersect`）→ `:271-286`（`_polygonDistance`）
- 内容: 交差判定を外積の符号だけで行うため、**共線だが重なっていない**辺の組
  （平行かつ同一直線上）は全ての外積が0になり、`abC*abD <= eps && cdA*cdB <= eps` が成立して
  「交差」と判定される。結果 `_polygonDistance` が 0 を返す。
- 再現（新規テストで固定済み）: 自艇領域が半幅2mの正方形、危険区域も半幅2m、区域は真北100m。
  掃引の先端は +52m で、実際の最接近は **46m**。しかし返る値は **0**。
  上下の辺（x = ±2）が共線であることが原因。区域を半幅3mにすると正しく 45m を返す。
- 影響: **FP 方向。** `minimumSeparationMeters` は `intersects` の判定には使われない
  （SAT の軸判定が決める。`:185-244`）。効くのは
  `nearMissSeparationMeters`(2.0m) による lv1（**表示のみ**）と、記録上のすれ違い余裕だけ
  （`collision_risk_evaluator_service.dart:1272`）。**警告漏れにはならない。**
- 発生確率: 低い。艇の六角形領域は針路に応じて回転し、区域は任意形状なので、
  厳密な共線（1e-9 m² 以内）はまず起きない。軸並行の合成データでのみ再現する。
- 重大度: **S3**（FP 側 + 低頻度。ただし記録されるすれ違い余裕が0に化けるため、
  練習ログの分析には効く）
- 修正案: `_segmentsIntersect` に共線時の区間包含判定（on-segment 判定）を足す。
  修正すると `minimumSeparationMeters` が実距離になり、**過剰警告が減る**方向。
  `intersects` には影響しないため FN リスクは無い。
  テスト（`continuous_collision_service_test.dart` 最終グループ）が現状の値を
  固定しているので、直すときはそこの期待値を実距離へ更新する。

### S3-δ: 保存済みの警告時間が、利用者に知らせず引き上がる

### シナリオ10（新規）: 利用者が警告時間を最小に設定した 4x

- 旧: `warningTimeSeconds = 5.0` を選べた。4x の停止時間は 6.68 秒なので
  地平 = max(5.0, 6.68) = **6.68 秒**。8+ の相手が 8.15 秒かけて止まる状況でも、
  自艇の静的区域評価は 6.68 秒先までしか見ない。
  5m/s なら **33.4m** 先までで、停止距離 33.4m とちょうど同じ。
  **停止距離の縁にある脅威が地平の縁にあり、余裕がゼロ。**
- 新: 下限 9.0 により地平 = max(9.0, 6.68) = **9.0 秒 = 45m**。停止距離 33.4m に対し
  11.6m（2.3秒）の余裕ができる。
- 音への影響: バンドは TTE で決まる（連続音 ≤7秒 / 断続音 ≤10秒）ため、
  新たに検知される 6.68〜9.0 秒の脅威は**断続音**になる。連続音は増えない。
- **判定: OK（FN を減らし、増える音は断続音に留まる）**

### 8.4 S2-β（新規・段階1〜3 とは無関係）: 共有校正は一度公開すると更新できない

- 該当箇所: `firestore.rules:454-470`（`fixed_obstacle_calibrations_v2` の update）、
  `validSharedSafetyCalibration`（`:233-264`）、`validScaledVertexOffsets`（`:160-190`）、
  クライアント側は `managed_hazard_service.dart:119`（`previousState` を必ず添える）
- 症状: 初回公開（create・revision 1）は成立するが、**2回目以降の公開（update）は
  `Unable to evaluate the expression as the maximum of 1000 expressions to evaluate has been reached`
  で permission-denied になる。**`previousState` の検証が加わることで、
  `request.resource.data` 側と `previousState` 側の二重検証になり式数が上限を超える。
  `validScaledVertexOffsets` が21区域ぶん `values.keys()` を呼び直す構造が主因と見られる。
- 影響: **共有校正（チームで座標のズレ補正を共有する機能）が実質1回きりになる。**
  衝突警告そのものは端末内の同梱プロファイルで動作するため止まらないが、
  現地で合わせた補正をチームへ配れない。
- 発覚が遅れた理由: 上記 D により、ルールテストが5件目で中断しており、
  16件目のこのテストへ到達していなかった（チェックリストの「Emulator 14/14成功」は
  テスト追加前の記録）。
- 重大度: **S2**（安全経路は止まらないが、機能が成立していない）
- 修正案: ルールの式数を削る。(a) `validScaledVertexOffsets` で `let keys = values.keys();` を
  使い21回の再評価をやめる、(b) `validScaledOffsetList` の21要素の逐次 `is latlng` を
  見直す、(c) `previousState` の検証を「保存済みドキュメントとの一致」に寄せて
  再検証を減らす。**セキュリティルールの構造変更でありデプロイを伴うため、着手前に判断が要る。**
