## 2. S2 所見

### A-1: 停止・回頭中の艇と、そばを通る他艇が確実に連続音になる

- 該当箇所: `lib/services/ship_domain_service.dart:94-103, 204-211` /
  `lib/services/safety_orchestrator.dart:579-580`
- 数値トレース(8+ が折り返しで回頭中、別の艇が 12.5m 横を通過):
  - 回頭中は `speed < 0.5` → `headingIsReliable` false →
    横方向へ片側 `min(4.0, 22.9/2 × sin35°) = 4.0m` 拡張。
  - 自艇 排他領域の半幅 = (10.5 + 8)/2 = **9.25m**
  - 他艇 船体領域の半幅 = 7.5/2 = **3.75m**
  - 合計 **13.0m** > 実際の横距離 12.5m → **GPSマージン無しで領域が重なる**
  - `currentOverlap = true` → `confidence = definite` → lv3 →
    `AlertUrgency.imminent` → **連続音**
- 抑制が効かない理由: `_canSuppressAtRest` は `category != 'other_boat'` のみを
  対象にする。安定停止の無音化は**固定障害物専用**で、他艇には一切かからない。
  低速拡張が最大になる場面(回頭)と、抑制が効かない対象(他艇)が完全に一致する。
- 影響: 桜川の折り返し地点で回頭するたび、通過する全艇に対して連続音が鳴る。
  練習中に最も繰り返される場面なので、**警告そのものが形骸化する**。
  false positive だが、連続音の信頼を壊すため実質的な安全問題。
- 修正案(誤報だけを減らし、警告漏れを増やさない案):
  低速拡張ぶんでしか重ならない候補は `confidence` を 1.0 未満にして、
  既存の1バンド降格(`AlertUrgency.oneStepDown`)へ載せる。連続音→断続音になり、
  検知そのものは失われない。実装は静的区域の `gps_guard_entry` と同じ形にできる
  (`collision_risk_evaluator_service.dart:970-990` のパターン)。
- 前提の確認: 他艇を安定停止の無音化対象に入れる案は**採らないこと**。
  停止艇に背後から突っ込まれる経路を消してしまう。

### A-2: 他艇 broad-phase が曲率マージンを含まず、狭い帯で narrow-phase と食い違う

- 該当箇所: `lib/services/collision_risk_evaluator_service.dart:947-951`
- 内容: `evaluateBoatContinuousIntersection` は `inflateMeters` に
  `pairGuard + curvatureMargin`(最大 3.0m)を渡す(:459-466)のに、
  その手前の到達距離判定 `relativeReach` には `pairGpsCenterDistanceGuardMeters`
  しか入っていない。静的区域側(:830-833, :841-844)は
  `maxChannelCurvatureMarginMeters` を正しく含めており、**他艇側だけ不整合**。
- 再現シナリオ: 8+ 同士が 5m/s で正面接近。horizon 10s。
  `relativeReach = (5+5)×10 + 12.60 + 12.60 + 2.2 = 127.4m`。
  中心間距離が 127.4〜130.4m の帯にある間、narrow-phase なら曲率マージンで
  重なる候補が broad-phase で捨てられる。
- 影響: 前回 S1-1/S1-3 と同種(broad-phase の過小評価)。ただし取りこぼす帯は
  最大3mで、かつ**予測地平の最遠端**なので、1秒後の評価(相対10m接近)で必ず拾う。
  実害は最初の検知が最大1周期(1秒)遅れることに留まる。
  それでも「到達半径は必ず実効値以上」という不変条件が破れているので直す。
- 修正案: `relativeReach` に `maxChannelCurvatureMarginMeters` を加える1行。

### A-3: 他艇情報を受信できない艇が、自分も半分見えなくなる

- 該当箇所: `lib/services/send_policy.dart:18-22` /
  `lib/hooks/use_navigator.dart:1748-1757`
- 内容: 送信間隔は `hasNearbyBoat` で決まり、`hasNearbyBoat` は
  **自艇が受信できた他艇**(6秒以内)からしか作られない。
  受信経路が落ちている艇(`isDynamicReceiveUnavailable = true`)は
  常に「周囲に他艇なし」と判断し、停止中10秒 / 航行中5秒で送信する。
- 数値トレース: 停止中の艇が10秒間隔で送信 → 受信側は
  `boatPredictionTimeoutSeconds = 6s` で予測入力から外す →
  **10秒周期のうち4秒は衝突評価の対象から消える**。5m/sで接近する艇にとっては
  最初の検知が最大4秒(20m)遅れる。停止距離が 8+ で 40.8m なので無視できない。
- 通常運用では、受信が生きていれば300m以内で必ず2秒送信へ切り替わるので
  この経路は塞がっている。**受信だけが落ちた片系故障のときだけ**開く。
  つまり「他艇が見えない艇ほど、他艇からも見えなくなる」という相関故障。
- 修正案: `sendIntervalSecondsFor` に `receiveUnavailable` を渡し、
  true なら `sendIntervalNearOthersSec`(2秒)を返す。
  片系故障中だけなので通信量の増加は限定的。

### A-4: 警告音の play/stop が直列化されておらず、段階が上がる瞬間に自分で止め得る

- 該当箇所: `lib/hooks/use_alert.dart:344-375` /
  `lib/hooks/use_navigator.dart:2696-2741`
- 内容: 提示は1Hzで変わり、`unawaited(alert.play/playOnce/playPeriodic)` で
  投げっぱなしにしている。`playWithMode` の中は
  `setAudioContext → stop → setReleaseMode → setVolume → setSource → resume`
  と6回 platform channel を await するため、負荷時は容易に1秒を超える。
- 競合の具体形: 要求N(単発音)の実行中に要求N+1(連続音)が入ると、
  N は `await player.resume()` の直後(:372-375)で世代の古さに気づき
  **`player.stop()` を呼ぶ**。このとき player が鳴らしているのは N+1 の音源なので、
  **より緊急な連続音を自分で止める**。
- 影響: 復旧は `AudioPlaybackProgressWatchdog` が拾うので1〜2秒。
  ただし止まるのが「単発音→連続音へ上がった直後」= 最も鳴っていてほしい瞬間。
- 位置づけ: `2026-07-22 システム全体レビュー` の次期保守課題
  「警告音のstop/playを単一latest-onlyキューで完全直列化する」が**未着手のまま**。
  今回、実際に音を消し得る具体経路として確認できたので優先度を上げるべき。
- 修正案: `LatestOnlyAsyncPublisher`(すでに `lib/services/` にある)へ
  再生要求を通し、常に1本だけ実行する。世代チェックによる `player.stop()` は
  「自分が最後に鳴らした対象がまだ current のときだけ」に限定する。

### A-5: 電池残量の取得が1Hzの安全ループ上にある

- 該当箇所: `lib/hooks/use_navigator.dart:1762-1781`
- 内容: 60秒に1回、`await battery.batteryLevel.timeout(2秒)` を
  `processPosition` の中で待つ。位置処理は `enqueuePosition` の
  drain ループが直列に回すため、この待ちの間は**次のfixの処理が始まらない**。
- 影響: 衝突評価そのものは電池取得より前に終わっているので、その回の警告は遅れない。
  遅れるのは次の1回で、最悪2秒。60秒に1回、最大1周期の欠落。
  `position_processing_gap` 診断(2.5秒)にちょうど引っかからない値なので、
  ログからは見えにくい。
- 修正案: 電池取得を `unawaited` にして前回値を送る(すでに前回値フォールバックの
  仕組みはある)。取得完了は次回の送信に反映されれば十分。

## 3. S3 所見

### B-1: 低速時の横方向拡張が、船体の「長さ」も伸ばしている

- 該当箇所: `lib/services/ship_domain_service.dart:204-211`
- `_widenForHeadingUncertainty` は `w` と **`s`** に `2×lateral` を足す。
  `s` は六角形の平行辺の長さ(=前後方向の寸法)なので、コメントの
  「長さは広げない。艇の占める面積は方位が変わっても増えないため」と食い違う。
- 数値: 8+ 排他領域 低速時 → `h = 22.9`, `s = 18.88 + 8 = 26.88`。
  `s/2 = 13.44 > h/2 = 11.45` となり、**六角形が凹になる**(船首頂点が引っ込む)。
  実効的な全長は 22.9m → 26.88m へ、前後に約2mずつ伸びる。
- 現状の安全性: 掃引側は `_convexHull` を通す(`continuous_collision_service.dart:83,
  120-121`)ため凹形状は凸包へ丸められ、判定は**安全側(大きい側)**。
  `polygonsOverlap` 側も ear-clipping が凹を処理できる。よって警告漏れは起きない。
- ただし A-1 の過剰警告の一因になっており、`boundingRadius` が
  3候補の max を取らざるを得なくなっている(前回 S1-3)のも元はこれ。
  意図どおり `w` だけを広げれば `s ≤ h` が保たれ、凸性も戻る。

### B-2: `buildMyBoat` のコメントが実装と逆のことを言っている

- 該当箇所: `lib/hooks/use_navigator.dart:1517-1521`
- 「Kalman共分散だけで端末の報告accuracyより楽観的にしない」とあるが、
  実装は `estimate?.uncertaintyMeters ?? rawPos.accuracy` で、
  `uncertaintyMeters` は報告値の0.5倍(下限3m)まで下がり得る
  (`robust_position_estimator.dart:693-708`)。
- 前回レビューの S2-4 で**意図的に緩めた**設定なので実装が正しい。
  コメントだけが旧仕様のまま残っている。安全マージンの根拠に直結する行なので、
  次に読む人が「max を取っているはず」と誤読するリスクが高い。修正すべきはコメント。

### B-3: 方位が二重に平滑化されている

- 該当箇所: `lib/hooks/use_navigator.dart:89-97, 1471-1490`
- Kalman が推定した `headingDegrees` を、さらに `_blendHeading(weight: 0.5)` で
  1Hzの一次遅れに通している。定常旋回では**1ステップぶんの旋回角がそのまま遅れ**になる
  (旋回10°/s なら約10°遅れる)。5m/s・10秒先の予測では終端で約8.7mの横ずれ。
- 中心線予測が入ったことで実害は薄まっているが、Kalman を入れた目的
  (方位のジッタ低減)と重複しているので、weight を上げるか
  推定器出力のときは blend を通さないかを検討する価値がある。

### B-4: `relativeDirectionLabel` が完成しているのに使われていない

- 該当箇所: `lib/utils/relative_direction.dart`(lib配下から参照ゼロ・テストのみ)
- 警告バナーは「岸」「他艇」の一語だけで、**方向も残り秒数も画面に出ない**
  (`safety_banner.dart:61-62, 104-120`。`predictionText` を作っているのに
  `Semantics` ラベルにしか渡していない)。
- 漕手は後ろ向きで、警告を受けてから振り向く方向を決める必要がある。
  「他艇 左後方」「岸 右 4秒」まで出せる材料(`ThreatInfo.position` と
  `actionDeadline`)は評価側で揃っている。UI/UXの改善余地としては最大。
  → 詳細は C-1。

### B-5: `SafetyBanner.activeCount` と `coach_config.anomalyReannounceSec` が未使用

- `safety_banner.dart:19` の `activeCount` はどこからも読まれない。
- `coach_config.dart:24` の `anomalyReannounceSec`(「同じ異常を再度読み上げる間隔」)は
  lib/test 双方から参照ゼロ。**監視側の読み上げ機能が存在しない**ことの痕跡
  (→ C-4)。設定だけ残っていると「実装済み」と誤解される。

### B-6: 排他領域と船体領域の差が、`s` だけ艇種でばらついている

| 艇種 | h差(片側) | w差(片側) | s差(片側) |
| --- | --- | --- | --- |

| 2x | 1.50 | 1.50 | **0.15** |

## 4. 実運用上の設計判断(C: 欠陥ではないが判断が要る)

### C-1: 警告が「何が」しか伝えず、「どちら」「あと何秒」を伝えない

- 漕手は進行方向を見ていない。警告を聞いて振り向くとき、
  **振り向く側が分からないと2秒失う**。桜川の川幅50m・5m/sでは2秒=10m。
- 材料はすべて揃っている:
  - 方向: `ThreatInfo.position` と自艇 heading → `relativeDirectionLabel`(B-4)
  - 秒数: `AlertCandidate.actionDeadline` → `NavigationWarning.secondsUntilDanger`
    (すでに算出済みで、画面に出していないだけ)
- 提案: バナーのチップを「岸」→「岸 右 4秒」の2行にする。
  音を増やさずに情報量だけ増やせるので、過剰警告の副作用が無い。

### C-2: 同じ種類の警告が複数チップに分かれる

- 岸の危険区域は基準線の各辺を長方形へ展開したもの(release で約310枚)。
  警告は `obstacle.id` ごとに別 `alertId` になる(`safety_orchestrator.dart:614-635`)
  ため、岸沿いを走ると**「岸」チップが2〜4枚並ぶ**ことがある。
  `SafetyBanner` は `Wrap` で全件並べるので上限もない。
- 提案: 表示側で category 別に集約し、最も近い1件だけを出す(件数はバッジ)。
  判定側は今のまま(集約は表示だけ)にすれば安全性に影響しない。

### C-3: 航行中に「障害物の追加」を開くと、地図と警告バナーが隠れる

- 該当箇所: `lib/screens/home_map_screen.dart:252-265`
- 航行中でも開ける唯一のメニュー項目で、これは意図した設計
  (「第一発見者がすぐ登録できる」)。音声警告と位置共有は継続する。
- ただし `AreaSettingScreen` は全画面 push なので、**視覚警告の経路だけが
  無告知で落ちる**。1x で漕ぎながら操作する状況も想定される。
- 提案: 航行中に開いた場合だけ、画面上部に `SafetyBanner` を重ねるか、
  「航行中・警告表示は音のみ」の常設バーを出す。

### C-4: 監視モードは、コーチが画面を見続けていないと機能しない

- 異常通知は SnackBar(6秒・無音)だけ(`home_map_screen.dart:466-479`)。
- Wakelock は `startNavigation` の中でしか有効化されない
  (`use_navigator.dart:2132`)。**監視モードでは画面が消灯する。**
- `anomalyReannounceSec = 120`(読み上げ間隔)が未使用のまま残っており、
  音声通知は実装されていない(B-5)。
- 結果として「岸からコーチが監視する」という本来の使い方では、
  更新途絶(=沈・電池切れの可能性)に気づけない。
- 提案(優先順):
  1. 監視モード中も Wakelock を有効にする
  2. 新規異常だけ音を鳴らす(`anomalyReannounceSec` を使って再通知を間引く)
  3. SnackBar の表示を `boatId` から `displayName` へ直す
     (`home_map_screen.dart:468` は生IDを出しており、
     `BoatListPanel` が `displayName` を出しているのと不一致。コーチにはIDが読めない)

### C-4 補足: 監視側の異常検知にも fail-silent がある

- `useCoachWatch` の水域外判定は `practiceArea.value != null` のときだけ動く
  (`use_coach_watch.dart:210-219`)。読み込み失敗は `debugPrint` のみで、
  **コーチ画面には「水域外検知が働いていない」ことが一切出ない**
  (`use_coach_watch.dart:101-105`)。
  航行側には `static_profile_unavailable` / `operational_coverage_unverified` の
  system fault があるのに、監視側には対応する表示が無い。
- `BoatAnomaly.detectedAt` は毎スキャンで `now` に作り直されるため、
  「いつから停止しているか」がコーチに分からない。
  初検知時刻を保持すれば「3分前から停止」と出せる。

### H1 停止距離 [m](式は速度の1次式)

| --- | --- | --- | --- | --- | --- |
| 1x | 6.95 | 13.9 | 24.3 | 34.8 | 6.95 s |
| 2x | 6.60 | 13.2 | 23.1 | 33.0 | 6.60 s |
| 4x | 6.68 | 13.4 | 23.4 | 33.4 | 6.68 s |
| 8+ | 8.15 | 16.3 | 28.5 | 40.8 | 8.15 s |

いずれも `warningTime = 10s` 内。前回と一致。

### E3 マージン合計 vs 想定GPS誤差(再検算)

前回レビューは相談事項1の採用で E1/E3/F3 を「解消」としているが、
数値を置き直すと**緩和であって解消ではない**。

- 送信する `accuracy` は Kalman の `uncertaintyMeters`。
  端末報告8mなら `max(3, 8×0.5, cov95)` ≒ 5m。
- `accuracyGuard = sqrt(5² + 5²) × 0.20 = 1.41m`
- 齢2秒の `extrapolationGuard = 0.4 × 2 = 0.80m`
- **pair guard 合計 ≒ 2.2m**(上限は 2.5 + 2.5 = 5.0m)

一方、2端末の相対測位誤差は、それぞれ5〜8mなら合成で7〜11m。
2.2mでは 20〜30% しか埋まらない。**これは是正すべき欠陥ではなく、
狭い川では上げられないという交換条件**である(下記FP側の検算)。
「解消」と書くと次の担当者が再検討しなくなるので、
「有界に緩和・残差は目視確認で担保」と書き直すのが正確。

### FP側: 狭い区間ですれ違うときの余裕(新規)

35m区間・キープライトで艇間12.5m、8+ 同士の正面すれ違い:

- 警告(領域の重なり)まで: 5.25 + 3.75 + 2.2 = **11.2m**
- lv1(DCPA 2.0m)まで: 11.2 + 2.0 = **13.2m**

→ 実際の 12.5m は **lv1 の内側**、lv2 まで 1.3m しかない。
横方向のGPS揺れが数m入るので、**狭い区間のすれ違いでは
表示警告が毎回出て、音も断続的に出る**と予測される。
`separationMeters` はすでに記録されているので、実走ログの分布で確認できる。

### F1 鮮度の階層

`freshUntil 3s < boatPredictionTimeoutSeconds 6s < boatStaleTimeoutSeconds 30s`
かつ `sendIntervalStoppedSec 10s < 30s`。成立。
ただし A-3 のとおり、10s送信は 6s の予測TTLを超えるため、
**受信が落ちた艇だけ** 10秒周期のうち4秒は評価対象から外れる。

### 追加した回帰テスト

- 回頭中の低速拡張だけで重なる他艇は、検知は残しつつ確度を下げる

- 現在発生中の警告は、予測中の同種警告より優先して代表になる
