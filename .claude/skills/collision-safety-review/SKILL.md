# 衝突警告 安全レビュー(false negative 監査)

## 目的と判断基準

このアプリは漕手の背後方向の視界を補う衝突警告システムであり、**「鳴らなかった警告」が事故に直結する**。
誤報(false positive)は煩わしさと信頼低下の問題だが、警告漏れ(false negative)は人身事故の問題である。
したがってこのレビューでは一貫して次の基準で判断する:

- 迷ったら「指摘する側」に倒す。無根拠のOKは禁止。
- fail-silent(失敗を握りつぶして「脅威なし」を返す)は、それ自体を欠陥として扱う。
- 誤報を増やす修正案と警告漏れを減らす修正案が衝突する場合、警告漏れの削減を優先する。

## レビュー対象(標準セット)

変更の有無にかかわらず、毎回この警告経路一式を対象にする:

- `lib/services/collision_risk_evaluator_service.dart`(リスク評価本体)
- `lib/services/ship_domain_service.dart`(船体・排他領域)
- `lib/services/send_policy.dart`(適応送信)
- `lib/config/risk_evaluator_config.dart` / `navigator_config.dart` / `boat_config.dart`(しきい値・停止距離式)
- `lib/utils/sat_algorithm.dart` / `triangulation.dart` / `geo_proximity.dart` / `geo_math.dart` / `winding_algorithm.dart`(幾何計算)
- `lib/services/dynamic_obstacle_service.dart`(幽霊艇フィルタ)
- `lib/hooks/useNavigator.dart`(GPS入力の加工・評価の呼び出し・警告の提示/抑制)

変更ファイルがこのリスト外でも、「GPS入力 → 自艇情報構築 → 送受信 → 鮮度フィルタ → 外挿 → リスク評価 → レベル変換 → 警告提示」の経路に影響するなら対象に加える。

## 手順

1. **データフローの把握** — 上記経路を実コードで追い、段階ごとに「ここで情報が落ちる/遅れる/歪む可能性」をメモする。過去のレビュー報告書(`safety_reviews/`)があれば先に読み、既知の指摘の再発・修正の劣化(regression)がないかを確認対象に含める。
2. **チェックリスト適用** — 下のA〜Hを全項目、判定(OK / NG / 要確認)+根拠(ファイル名:行番号)付きで記録する。判定できない項目をOKにしない。
3. **境界シナリオのトレース** — 「定番境界シナリオ」を最低限、具体的な数値を入れて手でトレースする(式に数字を代入して警告が出るか計算する)。コードを読むだけで済ませない。
4. **設定値の検算** — チェックリストHを数値で検算する(不等式が成り立つかを計算して示す)。
5. **重大度分類** — 所見を S1(警告漏れに直結)/ S2(条件が重なると警告漏れに寄与)/ S3(品質・保守性)に分類する。false positive側の問題はS2以下とする。
6. **報告書の作成・保存** — 下のフォーマットで `safety_reviews/YYYY-MM-DD_collision_safety_review.md` に保存する。
7. **完了条件の確認** — 最後に完了条件を1つずつ照合し、満たさないものがあればレビューを完了と称さない。

## チェックリスト

### A. 数値比較・浮動小数点の境界
- **A1** しきい値比較の等号の向き(`<=` vs `<`)は安全側か。境界値「ちょうど」で警告が出るか。
- **A2** 浮動小数点の完全一致比較(`== 0.0` 等)はないか。微小速度・負値・NaNで分岐が意図どおり動くか。NaNは全ての比較がfalseになることに注意(NaNが「条件を満たさない=脅威なし」に落ちる経路を探す)。
- **A3** 先読みループの終了条件が最終評価点を取りこぼさないか(警告距離ちょうどの地点が評価されるか)。
- **A4** 単位([m]・[s]・[m/s]・度・ラジアン)とint/double混在の取り違え。

### B. 予測・時間軸の境界
- **B1** 先読みの時間刻みで**すり抜け(tunneling)**が起きないか。刻みは自艇速度基準だが、1ステップあたりの**相対**移動量(自艇+相手艇)が最小ドメイン寸法を超えると、交差の瞬間を飛ばして「衝突なし」になる。最悪ケース(最速艇種同士の正面接近)で検算する。
- **B2** 先読みの範囲(停止距離+警告時間)が最高速度で十分か。
- **B3** 受信データの外挿(`extrapolateToNow`)の上限・下限。他端末の時計ズレ(timestampが未来/過去)で外挿が止まる・過剰になる条件。
- **B4** 「停止」判定(速度しきい値)と実際の漂流の乖離。停止扱いの艇が漂流して接近するケース。

### C. 幾何計算の頑健性
- **C1** 頂点数<3・自己交差・重複頂点のポリゴンが入力されたとき、判定が例外→「衝突なし」に落ちないか。
- **C2** 三角形分割・SATが例外を投げる入力の洗い出しと、投げたときの扱い。
- **C3** 緯度経度をそのまま平面座標として使う計算の妥当性(交差判定はアフィン変換不変なので正しいが、**距離・角度**の計算に流用していないか)。
- **C4** ポリゴンの辺上・頂点上の点の内外判定。

### D. 例外処理・フェイルセーフ
- **D1** try/catch が例外を握りつぶして「脅威なし」を返す経路(fail-silent)がないか。安全クリティカルな判定の失敗は、無視ではなく保守的な代替判定(距離ベースの円判定など)か警告側へのフォールバックにする。
- **D2** ログ出力だけして処理継続する経路の一覧化と、それぞれの「継続した場合に警告が漏れるか」の評価。
- **D3** 受信メッセージの欠損・型不正・異常値(NaN/Infinity/範囲外の緯度経度)の扱い。

### E. 入力の不確実性(GPS・センサー)
- **E1** GPS位置誤差(水上のスマホで5〜15mは普通に起きる)が排他領域のマージンを超えていないか。`Position.accuracy` を評価に反映しているか。**排他領域と船体領域の差[m]を実際に計算し、想定GPS誤差と比較して示す。**
- **E2** 速度・方位の誤差/欠損時のフォールバック(heading=0固定、speed<0時の代替計算など)が危険側に働く条件。
- **E3** マージン合計(排他領域マージン+近接注意距離)>(自艇GPS誤差+相手GPS誤差+外挿誤差)が成り立つかの数値検算。

### F. データ鮮度・通信
- **F1** 送信間隔の最大値+処理遅れ < 幽霊艇タイムアウト、が余裕をもって成り立つか。
- **F2** 幽霊艇フィルタが「実在する艇」を落とす条件(相手アプリのクラッシュ・電池切れ・圏外)。落ちた艇は警告対象から消えることを運用でどう補うか。
- **F3** 受信間隔が空いた間の相手位置の不確実性(最大 送信間隔×速度+加減速分)がマージンでカバーされるか。
- **F4** リスク上昇時に送信間隔が即時短縮されるか(前回評価結果を使うことによるラグは何秒か)。

### G. 警告提示の抑制・降格
- **G1** リスクレベル→SafetyLevel→アラート種別の写像で段階が落ちないか。
- **G2** 「レベル上昇時のみ読み上げ」等の抑制が、継続中の脅威・一旦離れて再接近する脅威を隠さないか。
- **G3** primaryThreat の選択が実際の最重大脅威と一致するか(レベルを上げた脅威と表示される脅威のずれ)。

### H. 設定値の整合性(数値検算必須)
- **H1** 各艇種の停止距離式の出力を代表速度(2, 3.5, 5 m/s)で計算し、直感・実測と乖離がないか(過小評価はFN)。
- **H2** `evalIntervalDistance` vs 最小ドメイン寸法(B1と併せて)。
- **H3** `obstacleProximityCautionDistance` vs 想定GPS誤差。
- **H4** `warningTime` / `cautionTime` が回避操作に要する時間として妥当か。

## 定番境界シナリオ(毎回、数値でトレースする)

1. 微速(0.3 m/s)で危険区域へ横向きに漂流(予測は進行方向のみ・近接判定が効くか)。
2. 最速艇種(8+、約5.5 m/s)と低速の1x(0.6 m/s)の交差 — B1のすり抜け検算を兼ねる。
3. 2艇が並走、双方のGPS誤差が10mずつ内側に寄って見えている(実際は接触寸前なのに画面上は離れている)。
4. 停止中(送信間隔最大)の艇に、別の艇が背後から接近。
5. 相手端末の時計が±5秒ずれている状態での外挿と鮮度フィルタ。
6. 頂点2点しかない・自己交差している危険区域ポリゴンのすぐそば。
7. 障害物が警告距離の境界ちょうど(warningDistance ± evalIntervalDistance)にある。

## 報告書フォーマット

```markdown
# 衝突警告 安全レビュー報告 YYYY-MM-DD
## 1. サマリ(所見数を重大度別に)
## 2. チェックリスト結果(A1〜H4の表: 判定/根拠)
## 3. 所見一覧
### S1-1: <タイトル>
- 該当箇所: <ファイル:行>
- 再現シナリオ: <具体的な数値を入れた状況>
- 影響: <どのように警告が漏れるか>
- 修正案: <方針。誤報増との交換条件があれば明記>
## 4. 境界シナリオのトレース記録
## 5. 設定値の検算記録
## 6. テスト実行結果(または実行不能の理由と代替検証)
## 7. 完了条件の充足確認
```

## 完了条件(すべて満たすまで「レビュー完了」と言わない)

1. チェックリスト全項目(A1〜H4)に OK / NG / 要確認 のいずれかの判定と、根拠(ファイル名:行)が記録されている。根拠のないOKが1つもない。
2. 定番境界シナリオ7件すべてについて、数値を入れたトレース記録がある。
3. すべてのNG項目に、再現シナリオ(具体値)・FN/FPの別・重大度(S1〜S3)・修正案が付いている。
4. チェックリストHの数値検算の記録がある。
5. 既存テスト(`test/services/` 以下)の実行結果、または実行できない環境ではその理由と代替検証(静的解析・手計算)が記録されている。
6. 報告書が `safety_reviews/` に保存されている。
7. S1所見が0件である、または各S1所見に対処方針(修正する/しない理由)が明記されている。
