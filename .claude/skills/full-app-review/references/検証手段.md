# 検証手段(読むだけで終えないための道具)

指摘は**確定前に必ずどれかで裏を取る**。取れなかったものは証拠の格付けを「未確認」にする。
過去のレビューでは、この工程で仮説が3件覆った(自己交差=過剰警告だった / 頂点2点=到達不能 /
「余裕100ms」=実は余裕ゼロ)。**訂正は成果であり、失敗ではない。**

## 1. 静的解析とテスト(必要な分だけ動かす)

**ビルドはしない。** `flutter build` / `flutter run` / Xcode / Gradle / シミュレータ起動は
レビューの作業に含まない(SKILL.md §1.1)。

```bash
dart analyze lib test tool
```

実測約7秒。`flutter analyze` はこの作業パス(日本語ディレクトリ)では必ずクラッシュする。
`tool` を必ず含める。

```bash
flutter test test/services/<レビュー中の対象>_test.dart
```

**全実行(`flutter test`・約101秒)は原則しない。** PR で CI が必ず走らせるので、
ローカルで繰り返しても新しい情報は増えない。動かすのは、いま読んでいる範囲のテストだけでよい。

**テストを読むのはコードを読むのと同じくらい重要。** テストが実装と同じ式で期待値を作っていたら、
それは恒真であって検証ではない(H観点の指摘になる)。**読むのは無料で、走らせるのは有料**という
前提で、まず読む。

## 2. 数値検算(表計算ではなく本文に残す)

しきい値・距離・時間の主張は、**代表値を入れて計算した式を記録に書く**。

- 代表速度: 巡航 3〜5 m/s、最速 8+ で約5.5 m/s、低速 1x で 0.6 m/s、静音境界 1.667 m/s(分速100m)。
- 代表寸法: 川幅40〜50m、狭所35m、艇長は `boat_config.dart` の艇種別値。
- 代表時間: 予測地平10秒、連続音7秒、確定10秒、解除0秒、鮮度 3s/6s/30s、送信 2/5/10秒。

「余裕がある」と書くときは、**引き算の結果を数字で書く**。符号が逆になっていないかまで見る。

## 3. replay(実機ログを通す)

実機ログはリポジトリ外の
`../実機テストログデータ/<日付>/rowing_diagnostics_*` にある(`docs/実機ログ保存場所.md`)。
**成果物へ航跡や個人情報をコピーしない。** 引用するのは集計値と件数まで。

**replay はログの長さに比例して時間がかかる。実行前に利用者へ一声かける。**
どのログを・何のために当てるのかを言ってから走らせる。

| 目的 | コマンド |
| --- | --- |
| 1回の練習で警告が**何回鳴ったか**(過剰警告は総量の問題) | `flutter test tool/replay_field_log.dart --dart-define=LOG_DIR=<診断フォルダ>` |
| 固定障害物・提示パイプラインへ航跡を1Hzで再生 | `dart run tool/replay_alerts.dart --session <診断フォルダ>` |
| 測位解(S0/S1/S2)の比較・2台同時搭載のペア指標 | `flutter test tool/replay_estimator.dart --dart-define=LOG_DIR=... [--dart-define=PAIR_LOG_DIR=...]` |
| 欠損・遅延を注入したときの振る舞い | `tool/replay_fault_injection.dart` |
| 差分探索・反例の縮小 | `tool/replay_difference_search.dart` / `tool/counterexample_reducer.dart` |

使い方の詳細は `docs/design_notes/replay_lab_使い方.md`。
先頭60秒は初期条件の影響が残るので数値指標から除く。

## 4. ログの読み方(観点 L)

`events.jsonl`(診断・通信エラー・時計ずれ)、`alerts.jsonl`(警告の状態変化と音声指示)、
`track.csv`(自艇の測位)。

- 「起こりうる」と書く前に、**起きた形跡を数える**。件数が分かれば重大度が変わる。
- **ログに出ていない ≠ 起きていない。** その事象がログに出る経路があるかを先に確かめる。
  出る経路が無いなら、それ自体が指摘(記録されない失敗は運用でも見えない)。
- 端末間で比べる。片方だけ全期間ゼロ、という形は強い手がかりになる。
- **相関を因果と書かない。**「送信失敗が受信失敗を引き起こした」と書けるのは、
  その経路をコードで示せたときだけ。示せないなら「相関が強い。原因は未特定」と書く。

## 5. 自己反証(指摘を確定する前に必ず)

指摘を1件ずつ取り上げ、**否定材料を能動的に探す**。探す先は決まっている。

1. 上位の呼び出し元 — その分岐に到達できるか。到達不能なら S3 へ落ちる。
2. 既存テスト — 既に固定されている振る舞いか。
3. `lib/config/` のコメント — 意図的な妥協として根拠が書かれていないか。
4. Rules・サーバー側 — クライアントだけを見た結論が、サーバー側で覆らないか。
5. 実機ログ — 実際にその条件が発生しているか。頻度は。

否定材料が見つかったら**取り下げて経緯を残す**。「撤回した」記録は、
次のレビューが同じ道を辿らないための資産になる。

## 6. 書いてはいけない結論

- 「CI が緑なので安全」— CI は analyze / format / test / hazardハッシュ / 生成allowlist / 音圧 まで。
  実機の配信頻度・電池・音量・水上の測位精度・本番Rules は**一切見ていない**。
- 「テストがあるので正しい」— テストが実装のコピーでないことを確認してから書く。
- 「コメントにそう書いてある」— コメントと実装が食い違うときは、実装が事実で、コメントが指摘対象。
- 断定できない推定を断定形で書く。**格付けを付けて、推定は推定と書く。**
