# アプリレビュー(動くことの監査)

## 0. 最優先の問い

**「現場で機能が動かない事態が起きないか」。**

このアプリで失敗とは、コードが汚いことではなく、次が起きることである。

1. **鳴るべき警告が鳴らない**
2. **位置共有が止まり、自艇が他艇から見えなくなる**
3. **他艇が画面と衝突評価から消える**
4. **航行が始まらない、途中で止まる**
5. **落ちる・固まる・電池が尽きる**
6. **上の失敗が誰にも見えないまま走り続ける**

レビューの価値は、この6つのどれかを1つでも減らせたかで測る。
指摘の数ではない。**「動く証拠を1つ増やす」か「壊れ方を1つ塞ぐ」かのどちらかになっていない指摘は、S3 に落とす。**

## 1. モードを選ぶ

| モード | 対象 | 所要 | 使う場面 |
| --- | --- | --- | --- |
| **軽量版(既定)** | 壊れ方 F1〜F6 を症状から辿る | 1〜2セッション | 実機テストの前後・機能追加の後・リリース前 |
| **総合版** | 実装全体を P00〜P17 で網羅 | 複数セッション(前回は18パス) | 大きな設計変更の後・半年に一度の棚卸し・軽量版で S1 が出たとき |

**迷ったら軽量版から始める。** 軽量版で S1 相当(鳴らない・止まる・消える)が出たら、
その場で報告し、総合版へ広げるかを利用者に確認する。
利用者が「総合レビュー」「全体レビュー」と明示したときは総合版で始める。

- 軽量版 → [references/軽量版_動作確認レビュー.md](references/軽量版_動作確認レビュー.md) に従う
- 総合版 → 本ファイルの §3 以降 + [references/パス割り.md](references/パス割り.md)

どちらのモードでも、最初に必ず実行する:

```bash
bash .claude/skills/full-app-review/scripts/smoke_check.sh
```

## 2. 共通のルール(両モード)

- **指摘のみ。修正はしない。** 優先度を確定してから別作業で直す。
  レビュー中にコードが動くと、後の判断の前提が崩れる。
- **根拠のない OK を書かない。** 判定には `ファイル:行` か実行結果を添える。
  判断できないものは「要確認」であって OK ではない。
- **見ていないものは「見ていない」と書く。** 薄く見て OK と書くのが最も悪い。
  次のレビューがそこを「確認済み」として飛ばす。
- **読んだだけで確定しない。** 数値検算・テスト・replay・実機ログのどれかで裏を取り、
  取れなかったものは証拠の格付けを「未確認」にする
  ([references/検証手段.md](references/検証手段.md))。
- **自己反証する。** 指摘を確定する前に「これを否定する材料はどこにあるか」を探す。
  過去のレビューでは、この工程で仮説が3件覆った。**訂正は成果であり、失敗ではない。**
- **CI が担保している層は再確認しない。** `dart format` / `flutter analyze` / `flutter test` /
  hazardハッシュ / 生成allowlist / 音圧 は `.github/workflows/ci.yml` が守っている。
  CI が見られない層(運用時の振る舞い・境界条件・移行・現場の失敗)に集中する。
- **`flutter analyze` はこの作業パスでは必ずクラッシュする。** `dart analyze lib test tool` を使う。
- **CI が緑であることは、実機・本番Rules・水上での安全の証拠にならない**(AGENTS.md)。
  報告には必ず「なお確認していないこと」を書く。

## 3. 総合版の進め方

### 3.1 開始手順

1. `scripts/inventory.sh <前回レビューのSHAか日付>` で規模・テスト有無・変更範囲を取る。
2. `CLAUDE.md`、`docs/DESIGN_PRINCIPLES.md`、`AGENTS.md` を読む。**要約で代用しない。**
3. 前回の指摘を回収する。`docs/review/`・`docs/reviews/`・`safety_reviews/` の最新報告から
   **未解決の S1/S2 と「証明されていないこと」を一覧化**し、再発・劣化の確認対象に入れる。
4. `docs/review/YYYY-MM-DD_全体レビュー/00_計画.md` を
   [references/報告書テンプレート.md](references/報告書テンプレート.md) の形で作る。
   パス割りは [references/パス割り.md](references/パス割り.md) を規模の変化に合わせて調整する。
5. 以降パスごとに §3.2 を繰り返す。**1セッションで進めるのは1〜2パス。途中で終わってよい。**
   `00_計画.md` の状態表が進捗の唯一の真実で、再開はここを読むところから始める。

### 3.2 1パスの手順

1. **対象ファイルを全行読む。** 抜粋読みはしない。境界条件は抜粋の外にある。
   読み切れない規模ならパスを分割する(黙って一部読みで終えない)。
2. **照合する規範を先に列挙する。** 設計原則・不変条件(CLAUDE.md の13項目)・設定値の根拠を、
   コードを読む前に書き出す。後から辻褄を合わせない。
3. **観点を当てる。** [references/観点.md](references/観点.md) の A〜N から、パス割り表が指定する
   主観点 ＋ 全パス共通の **B(警告漏れ)・D(不変条件)・G(縮退運転)・N(制御動作)**。
4. **裏を取る**(§2)。5. **自己反証する**(§2)。
6. **分類して記録する。** 重大度 S1/S2/S3、FN/FP、証拠の格付け。
   「テストが無い」は指摘とは別枠に書く。
7. **持ち越しを書く。** 他パスを見ないと判断できない疑問を明記し、該当パスで回収する。
8. `00_計画.md` の状態表と指摘件数を更新する。

### 3.3 重大度

| 重大度 | 意味 |
| --- | --- |
| **S1** | §0 の6つが実際に起きる。鳴らない・止まる・消える・落ちる・見えない |
| **S2** | 条件が重なると S1 に寄与する。誤報側の問題はここが上限(ただし**鳴り続けて形骸化する**ものは S1) |
| **S3** | 保守性・一貫性・死んだコード・根拠コメントの欠落 |

| 格付け | 書いてよい根拠 |
| --- | --- |
| **確認済** | 該当行を読んだ + 数値検算・テスト実行・ログ・replay のいずれかで確かめた |
| **推定** | コードからの論理的帰結。実行や観測では確かめていない |
| **未確認** | 仮説。実機・本番Rules・水上でしか確かめられないものを含む |

### 3.4 総合版の完了条件

1. `00_計画.md` の全パスに到達度(**全行読了 / 一部 / 未読**)と完了日がある。
   未完了があってよいが、**その事実が最終報告の先頭に書かれている**こと。
2. 各パス記録に、規範の列挙・観点ごとの判定+根拠・持ち越しがある。根拠のない OK が1つもない。
3. すべての NG に、再現条件(入力→誤った出力)・FN/FP・重大度・格付け・修正の方向がある。
4. P05 が `collision-safety-review` skill の完了条件を満たしている。
5. 前回レビューの未解決 S1/S2 を、再発・劣化・解消のいずれかで判定した表がある。
6. P16 で F1〜F6(軽量版の壊れ方)を通しで確認し、同時に鳴りうる警告の競合表を作った。
7. P17 で重複・矛盾・訂正を整理し、優先順位と実装順序(依存関係)を出した。
8. `99_最終報告と実装計画.md` に「なお証明されていないこと」「利用者(人)がやること」がある。
9. S1 が0件、または各 S1 に対処方針(直す/直さない理由)が明記されている。
